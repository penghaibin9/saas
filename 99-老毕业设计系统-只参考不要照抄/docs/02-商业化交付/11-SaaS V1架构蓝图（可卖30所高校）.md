# 《SaaS V1 架构蓝图（可卖 30 所高校）》——岗位实习与毕业设计管理系统

## Context（为什么做这件事）

目标不是新增功能，而是把一套**已开发完成、可运行**的「岗位实习与毕业设计管理系统」从「能用的毕设系统」升级为「**可招投标、可规模销售给 30 所高校的标准化 SaaS 产品 V1**」。

**关键事实校正（决定整份蓝图的写法）**：
- 本系统真实技术栈是 **Node.js 20 + Express 5 + MySQL 8（mysql2）**，**不是 Python/FastAPI**。本蓝图基于现有 Node 栈做 SaaS 商用化，**不重写 Python**（重写会丢弃全部成果、回归风险极高，对"卖出去"无收益）。
- 系统**已不是裸单体**：`config/tenancy.js` 已用 `AsyncLocalStorage` + 连接池 Proxy 实现 **DB-per-tenant 多租户**（single/multi 双模式同码）；已有 RBAC（5 内置角色）+ 增量式自定义角色/数据范围权限引擎（`models/permModel.js`、`middlewares/perm.js`）、审计（`middlewares/audit.js`）、限流（可 Redis）、对象存储抽象、分布式锁、结构化日志 + `/metrics`、幂等迁移版本表。
- 本交付物 = **架构蓝图文档**（供评审/招投标/对外讲），不立即改代码。落地实施待蓝图批准后另行分阶段进行。

> 因此本蓝图的重心是：**补齐"能跑的系统"与"能卖的 SaaS 产品"之间的差距**——租户运营控制台、计费/配额、配置化流程、Service 层工程化、API 规范化（/v1 + OpenAPI），而**不重复已完成的多租户与权限引擎**。

# 第一部分：系统 CT 体检（基于真实代码结构）

## 1.1 架构定级

| 维度 | 现状 | 结论 |
|---|---|---|
| 分层 | route(57) → controller(55) → model(49)；**无 service / schema / domain 层**，业务逻辑全堆在 controller（7105 行/55 文件≈129 行/个，含事务、校验、编排） | **模块化单体** |
| 多租户 | `tenancy.js` DB-per-tenant（每校独立库），JWT 带 `tid`，请求级 ALS 路由 | **已达"半 SaaS"** |
| 权限 | 内置 5 角色 + `requireRole` + 自定义角色/数据范围引擎 | 较完整 |
| 运营面 | **无租户管理控制台、无计费、无配额、无开通自助** | **缺 SaaS 运营面** |
| API | 无版本、无 OpenAPI、RESTful 不严格（动词混入路径如 `/read-all`） | 待规范化 |

**定级结论：当前是「模块化单体 + DB 级多租户的半 SaaS」。距离"可售 SaaS 产品 V1"差的不是隔离能力，而是 ① 工程分层（Service 层）② SaaS 运营面（控制台/计费/配额）③ 配置化（流程不写死）④ API 契约（v1 + OpenAPI）。**

## 1.2 最大的 5 个技术债（结合代码结构）

1. **无 Service 层，逻辑堆在 Controller**。`controllers/*.js` 同时承担 HTTP 解析、参数校验、业务编排、事务、通知。后果：逻辑无法跨入口复用（HTTP/定时任务/批处理）、难单测、招投标"代码质量"评分吃亏。
2. **无统一入参校验/Schema 契约**。校验分散在各 controller（手写 `if (!x) return error`），无 DTO/Schema 层，前后端无契约文档。
3. **API 未版本化、未规范化**。`routes/index.js` 直接 `/api/xxx`，含 `/read-all`、`/unread-count` 等动词路径；无 OpenAPI，对接/招标交付缺接口文档。
4. **控制面（master 库）过薄**。`t_tenant` 仅 code/name/db_name/status，**无套餐、配额、计费、到期、开通审计**——这是 SaaS 商品化的核心缺失。
5. **业务流程写死在代码里**。审批/实习阶段流转散落在各 controller 的状态码 if-else（虽有 `workflowConfigModel` 雏形但未成引擎），**30 所学校流程不一致时只能改代码**，无法配置化交付。

## 1.3 最危险的 3 个扩展性问题（上 30 校会爆）

1. **连接池随租户线性膨胀**。`tenancy.poolFor(dbName)` 每库一个池（默认 `connectionLimit:10`）。30 校 × 多实例 = 数百连接，MySQL `max_connections` 与内存先爆。**必须**做池上限/LRU 回收 + 单库连接数下调 + 读写分离预留。
2. **DDL 迁移要对 N 个库逐库执行**。`scripts/migrate.js` 只作用默认库；`provision-tenant.js` 建新库。30 校后**一次升级 = 30 次迁移**，无编排/版本对账会出现"各校 schema 漂移"。**必须**做"全租户迁移编排 + 每库迁移版本对账"。
3. **跨租户的全局任务/聚合无统一入口**。定时任务（`scheduler.js`）当前在默认库上下文跑；多租户下"扫所有校的保险/风险"需遍历租户并切上下文，否则只覆盖默认库。监管局版"跨校大屏"同理。**必须**有"按租户迭代执行"的运行器。

## 2.2 分层职责与"哪些必须拆"

| 层 | 只做什么 | 不许做 |
|---|---|---|
| controller | 解析 req、调 1 个 service、`success/error` 包装 | ❌ 业务规则、❌ 事务、❌ 直接拼 SQL |
| service | 业务编排、事务边界、跨 repo 协作、发通知 | ❌ 读 req/res、❌ HTTP 状态码 |
| repository(model) | 纯 SQL/CRUD、参数化、字段白名单 | ❌ 业务判断 |
| domain | 纯业务规则（可单测、无 IO） | ❌ DB/HTTP |
| validator(schema) | 入参结构/类型/约束 | ❌ 业务规则 |

**必须拆 service 的（含事务/多 model/编排的）**：实习分配 `assignment`、报告/日志批阅、报酬登记（合规校验）、数据报送 `reporting`、家长签署 `guardian`、benchmark 全套（任务书→鉴定→就业一条龙）、AI 编排（`aiController` 已半 service 化）。
**必须抽公共模块的**：`response`、`logger`、`metrics`、`pagination(clampPagination 已有)`、`desensitize`、`ids`、错误类型——归 `shared/`。
**必须独立 domain 的（纯规则、招投标可演示"有架构"）**：① 实习阶段状态机（准备→进行→结束的合法流转）② 报酬合规（≥试用期 80%，`stipendModel.compliant` 已是雏形，上移 domain）③ 打卡反作弊（`checkinRisk.js` 已是纯 domain，归位）④ 评分/查重规则。

**示例：报告批阅从 controller 抽到 service（含事务）**
```js
// src/services/reportReviewService.js
const { withTransaction } = require('../shared/tx');     // 新增事务助手
const reportRepo = require('../repositories/reportModel');
const { notify } = require('../shared/notify');
const { AppError } = require('../shared/errors');

async function review(reportId, teacherId, { score, comment, agree }) {
  return withTransaction(async (conn) => {
    const r = await reportRepo.findByIdForUpdate(reportId, conn);
    if (!r) throw new AppError('REPORT_NOT_FOUND', '报告不存在', 404);
    if (r.teacher_id !== teacherId) throw new AppError('FORBIDDEN', '只能批阅本人指导报告', 403);
    if (r.status !== 1) throw new AppError('BAD_STATE', '仅已提交可批阅', 400);
    await reportRepo.review(reportId, { teacher_score: score, teacher_comment: comment }, conn);
    await notify(r.student_id, '报告批阅结果', agree ? '已通过' : '被驳回', agree ? 'success' : 'warning');
    return reportRepo.findById(reportId, conn);
  });
}
module.exports = { review };
```

## 2.3 异常 / 中间件 / 审计体系

**① 统一异常**：定义 `AppError(code, message, status, data?)`，controller 一律 `try/catch → next(e)`，由全局错误中间件统一出格式（现 `app.js` 末尾已有错误处理，升级为识别 `AppError`）：
```js
// src/http/middlewares/error.js
module.exports = (err, req, res, next) => {
  const isApp = err && err.isAppError;
  const status = isApp ? err.status : 500;
  logger.error('request_error', { code: err.code, msg: err.message, path: req.originalUrl, stack: !isApp && err.stack });
  if (!isApp) require('../../shared/sentry').capture(err);   // 已有 sentry 适配
  res.status(status).json({ success: false, code: err.code || 'INTERNAL', message: isApp ? err.message : '服务器内部错误', data: err.data });
};
```
**② 权限中间件（RBAC + 数据范围）**：复用已建 `middlewares/perm.js`：`requirePermission('intern:manage')` + `attachDataScope`（all/college/class/self → `req.dataScope.filter`），service 据 `dataScope` 过滤。**新接口一律走权限码**，老 `requireRole` 兼容并存。
**③ 日志与审计**：结构化日志 + requestId（已有 `logger.js`/`requestContext.js`）；写操作审计（已有 `middlewares/audit.js` 异步落 `t_audit_log`）。**补充**：审计加 `tenant_code` 维度；导出 PII 审计已在 benchmark 做，统一上移 service。

# 第三部分：SaaS 化改造（关键核心）

## 3.1 多租户选型（已选型，给出论证）

| 方案 | 隔离 | 成本 | 运维 | 适配本系统 |
|---|---|---|---|---|
| 共享库 + `tenant_id` 行隔离 | 弱（漏 where 即串数据） | 低 | 易 | 改造面大、风险高 |
| **独立库 DB-per-tenant**（现状） | **强（物理隔离）** | 中 | 中 | **已实现** |
| 独立 schema | 中 | 中 | 中 | 不如独立库彻底 |

**推荐：维持 DB-per-tenant（已实现），不改隔离模型。**
**原因**：① 高校数据合规/招投标偏好**物理隔离**（"我校数据独立"是卖点）；② 已用 ALS+Proxy 实现，40+ model 零改动；③ 单校体量有限（千级学生），独立库性能足够；④ 私有化（single）与 SaaS（multi）同码，一鱼两吃。
**配套必补**（3.4 风险点）：连接池 LRU 上限 + 全租户迁移编排 + 按租户迭代任务运行器。

## 3.2 权限体系（学校/院系/教师/学生/企业 + 数据范围）

- **角色层**：内置 5 角色（院校管理员/分院管理员/指导教师/学生/企业导师）+ 自定义角色（`t_perm_role`，已建）。
- **数据范围**（已建 `permModel.scopeToFilter`）：`all`(院校级) / `college`(分院级) / `class`(班级) / `self`。service 查询统一接 `req.dataScope.filter`：
```js
// service 内：按数据范围收敛查询
const filter = { ...inputFilter, ...req.dataScope.filter }; // college→{collegeId}, class→{classId}, self→{userId}
return internRepo.findAll(filter, page);
```
- **租户维度天然隔离**：DB-per-tenant 下"学校"= 库，无需 `tenant_id` 列；跨校仅平台运营面可见（控制面）。

## 3.3 多学校配置化（流程不写死 → 流程引擎化）

**问题**：30 校审批/实习阶段流转不一致，现写死在 controller 状态码。
**方案**：把"流程"建模为**配置驱动的状态机**，每校一份配置（存其租户库），引擎读配置驱动流转。

**表结构（流程引擎化）**：
```sql
-- 每个租户库内
CREATE TABLE t_workflow_def (        -- 流程定义（如"实习审批"/"报告审批"）
  id INT PK, biz_type VARCHAR(40) UNIQUE,    -- intern_apply / report / leave ...
  name VARCHAR(80), enabled TINYINT DEFAULT 1, version INT DEFAULT 1
);
CREATE TABLE t_workflow_state (      -- 状态节点
  id INT PK, def_id INT, code VARCHAR(40), name VARCHAR(40),
  is_start TINYINT, is_end TINYINT, KEY(def_id)
);
CREATE TABLE t_workflow_transition ( -- 流转：from→to + 谁能操作 + 动作
  id INT PK, def_id INT, from_state VARCHAR(40), to_state VARCHAR(40),
  action VARCHAR(40),                -- submit/approve/reject/return
  role_required VARCHAR(40),         -- 角色或权限码
  perm_code VARCHAR(50) NULL, KEY(def_id)
);
CREATE TABLE t_workflow_instance (   -- 运行实例
  id INT PK, def_id INT, biz_id INT, cur_state VARCHAR(40),
  created_at DATETIME, updated_at DATETIME, KEY(def_id,biz_id)
);
```
**引擎（service）**：
```js
// src/platform/workflow/engine.js
async function dispatch(bizType, bizId, action, user) {
  const def  = await wfRepo.defByType(bizType);
  const inst = await wfRepo.instance(def.id, bizId);
  const tr = await wfRepo.transition(def.id, inst.cur_state, action);   // 查合法流转
  if (!tr) throw new AppError('WF_ILLEGAL', `当前状态[${inst.cur_state}]不允许动作[${action}]`, 400);
  if (tr.perm_code && !await perm.has(user, tr.perm_code)) throw new AppError('FORBIDDEN', '无操作权限', 403);
  await wfRepo.moveTo(inst.id, tr.to_state);                            // 落库 + 审计 + 通知
  return tr.to_state;
}
```
**V1 落地范围**：先把"实习申请审批""报告/日志审批""请假"3 条最常被各校改动的流程引擎化；其余维持代码态，渐进迁移。开通新校时**复制一份默认流程配置**，学校管理员可在后台微调（不改代码）。

# 第四部分：数据库重构

## 4.1 控制面（master 库）重构——SaaS 商品化核心

现 `t_tenant` 过薄。**新增计费/套餐/配额/开通审计**（仅 master 库，不进租户库）：
```sql
ALTER TABLE t_tenant
  ADD plan_code VARCHAR(20) DEFAULT 'standard',     -- 套餐
  ADD max_students INT DEFAULT 2000,                -- 学生数配额
  ADD max_storage_mb INT DEFAULT 51200,             -- 存储配额
  ADD ai_monthly_quota INT DEFAULT 5000,            -- AI 调用配额
  ADD expire_at DATE NULL,                          -- 到期（停服）
  ADD contact VARCHAR(80), ADD region VARCHAR(40),
  ADD created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  ADD updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP;

CREATE TABLE t_plan (        -- 套餐定义
  code VARCHAR(20) PK, name VARCHAR(40), price_year DECIMAL(10,2),
  max_students INT, max_storage_mb INT, ai_monthly_quota INT, features JSON

CREATE TABLE t_tenant_usage ( -- 用量计量（计费/超限）
  tenant_code VARCHAR(40), period CHAR(7), students INT, storage_mb INT, ai_calls INT,

);
CREATE TABLE t_tenant_event ( -- 开通/续费/停服审计
  id INT PK, tenant_code VARCHAR(40), type VARCHAR(20), detail JSON,

```

## 4.2 审计字段标准化（租户库内业务表）

通用审计模型——所有业务表应有：`id`、`created_at`、`updated_at`(ON UPDATE)、`is_deleted`(软删)、操作人(`created_by`)。现状大多已有 `create_time/update_time/is_deleted`，**统一命名**（建议 `created_at/updated_at`，或保持现名但全表对齐）。**新表一律按此模板**。无需 `tenant_id`（DB-per-tenant）。

## 4.3 索引优化

- 高频外键全建索引（多数已建）。补：`t_checkin(student_id, checkin_time)` 复合（打卡按人按时间查）、`t_intern_log(student_id, type, status)`、`t_audit_log(tenant_code, created_at)`、报送/统计的 `college_id`。
- 列表强制分页（`clampPagination` 已有，maxPageSize 100），杜绝全表扫。
- 软删表查询 `WHERE is_deleted=0` 走索引：对高频表建 `(is_deleted, <常用过滤列>)` 复合或过滤索引。

## 4.4 历史数据迁移策略（非常重要）

1. **结构迁移编排**：升级 `scripts/migrate.js` 为"**全租户迁移**"——遍历 `t_tenant` 每库执行幂等迁移并**逐库写 `t_migration` 版本对账**，输出"各校 schema 版本一致性报告"。
   ```js
   // migrations/run-all-tenants.js
   for (const t of await tenants.all()) {
     await tenancy.runWithTenant(t, async () => {
       await migrate.up();                         // 复用现幂等 runner
       report.push({ tenant: t.code, version: await migrate.head() });
     });
   }
   ```
2. **存量学校接入（一校一迁）**：每校老数据用 `scripts/import-users.js`（已支持 xlsx）+ 新增"实习/企业/分配"导入模板，先入临时表校验再入正式表；提供"试运行(dry-run)+回执"。
3. **回滚**：每次升级前 `npm run backup:db <每库>`（已有 backup/restore 脚本 + SOP）；迁移失败按校隔离回滚，不影响其他校。
4. **私有化→SaaS 数据搬迁**：`restore-db.js` 已支持指定库恢复，按校搬迁即可。

# 第五部分：API 与接口规范化

- **RESTful 化**：动词路径改资源化——`PUT /notifications/read-all` → `POST /notifications/read-states`(批量)，`/unread-count` → `GET /notifications?status=unread&count=1` 或保留为只读子资源。V1 先**冻结现有路径 + 新增规范化别名**，避免破坏前端。
- **API 版本化**：引入 `/api/v1` 前缀（`routes/index.js` 顶层挂 v1），未来不兼容变更走 `/api/v2`。改动小、招投标"接口规范"必备。
  ```js
  app.use('/api/v1', tenantMiddleware, apiRoutes);     // 现 /api → /api/v1
  app.use('/api', deprecationNotice, apiRoutes);       // 过渡：旧路径告警但仍可用
  ```
- **OpenAPI 标准化**：用 `zod` 定义 validator schema → 经 `zod-to-openapi` 自动产出 `openapi/openapi.json` + Swagger UI（`/api/docs`）。交付/对接/招标一份机器可读契约。
- **前后端契约层（schema）**：`http/validators/*` 即契约源；前端（含 `web/spa`）可由 OpenAPI 生成 TS 类型，前后端强类型对齐。

## 6.3 技术栈建议

- **后端**：Node 20 LTS + Express 5（保留）；新增 `zod`(校验/契约) + `zod-to-openapi`(文档)；保留 mysql2、jsonwebtoken、已接的 ioredis/ali-oss/sentry/sm-crypto（可选）。
- **前端**：PC 管理端**渐进迁** `web/spa`（Vite + Vue3 + Pinia + vue-router，已搭地基）；移动端 H5 PWA + 微信小程序（已有）；大屏 ECharts（已有）。
- **数据**：MySQL 8（可信创替达梦，SQL 多标准语法，迁移面可控）；Redis（限流/缓存/SSE 跨实例）。

## 6.4 部署架构（Docker / Nginx / CI/CD）

```
[GitHub] ──push──▶ [CI: GitHub Actions]
   1) lint + 单元测试(node --test，现 50 用例)
   2) docker build 后端镜像 + web/spa 构建产物
   3) 推镜像仓库
        │
        ▼
[CD] ──▶ 服务器/集群：
   docker compose：
     - app ×N (PM2 cluster 或 多容器)  ── 无状态，水平扩展
     - nginx (HTTPS 终止 + 静态 + 反代 + 限流)
     - mysql (master + 租户库；生产建议托管RDS/主从)
     - redis
   定时任务：单独 1 个 worker 容器（分布式锁已保证只跑一份）
   监控：Prometheus 抓 /metrics + Grafana 看板；Sentry 收错误
```
**关键约束**：① app 无状态（session 在 JWT、文件在 OSS）→ 可任意水平扩；② 定时任务靠 `utils/lock.js` 分布式锁，cluster 下只跑一份；③ 上传走 `STORAGE_DRIVER=oss` 多实例共享。

## 6.5 扩展路径（V1 → V2 → V3）

- **V1（可卖 30 校，本蓝图目标）**：Service 层 + 平台运营面（租户/套餐/计费/配额/开通）+ 配置化流程引擎(3 条核心流程) + /api/v1 + OpenAPI + 连接池治理 + 全租户迁移编排。**可招投标、可私有化也可 SaaS。**
- **V2（规模化 100+ 校）**：读写分离/分库分组、租户分片到多 MySQL 实例、SSE→Redis Pub/Sub 跨实例、计费对账自动化、配置化流程覆盖全部审批、监管局版跨校 GIS 驾驶舱。
- **V3（生态/智能化）**：用户中心拆统一身份服务、企业端独立子站、AI 深度（岗位智能匹配/就业预测/自动质检全覆盖）、开放 API + 第三方集成市场、信创全栈（达梦+国密TLS+麒麟）认证。

# 验证（蓝图落地后如何验收）

- **工程分层**：抽出的 service 有独立单测（不依赖 HTTP）；controller 仅做适配，`node --test` 全绿（现 50 用例为基线）。

- **运营面**：控制台开通新校→自动建库+复制默认流程+生成 admin；超配额（学生/AI）自动拦截或降级。
- **API 规范**：`/api/v1` 全通；`/api/docs` Swagger 可交互；旧 `/api` 过渡可用并告警。
- **部署**：`docker compose up` 一键起全栈；PM2 cluster 多实例下定时任务只跑一份、上传走 OSS 共享、/metrics 被 Prometheus 抓到。
