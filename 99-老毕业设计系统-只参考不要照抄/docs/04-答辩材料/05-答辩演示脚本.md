# 答辩演示脚本 / 话术

> 现场怎么点、说什么。建议总时长 8–10 分钟。**先准备、再彩排一遍、再上台。**

## 一、上台前 30 分钟准备（务必照做）

```bash
cd internship-backend
npm start                 # 1) 启动后端（另开一个窗口别关）
# 新开一个窗口：
npm run seed:demo         # 2) 灌满演示数据（30学生/10企业/全流程）
```

浏览器**提前打开这几个标签页**（避免现场敲网址）：
1. `http://localhost:3000/admin` —— PC 管理端
2. `http://localhost:3000/m/index.html` —— 移动端 H5（按 F12 → Ctrl+Shift+M 切手机视图）
3. `http://localhost:3000/screen` —— 数据大屏

演示账号（密码都是 `demo1234`）：`demo_admin` / `demo_teacher` / `demo_stu1` / `demo_ent`

> ✅ 检查：每个页面都能登录、点几个菜单不报错（已自动化验证过 120 页 0 缺陷，但现场再扫一眼更稳）。

## 三、现场演示主线（按角色切换，6–8 分钟）

> 主线就是"一个学生从找实习到拿成绩"的闭环，跨 4 个角色。每切一个角色，**退出登录重新登**即可。

### ① 院校管理员视角（demo_admin）—— "学校怎么管"
1. 登录 → 停在**工作台概览**。
   - 话术：*"登录后系统按角色自动加载菜单。管理员看到的是全校视角的工作台，左侧菜单按**实习生命周期**组织：准备期→进行期→监控预警→收尾。"*
2. 点开 **实习计划** → 展示已有计划。
   - 话术：*"实习计划由学校下达，设定打卡次数、周报月报要求，作为后续考核依据。"*
3. 点开 **风险预警 / 催办中心**。
   - 话术：*"这是市面同类系统的核心卖点——过程监管。系统自动监测脱岗、缺报，管理员可一键催办。"*
4. （可选）点 **数据大屏** 按钮 / 切到大屏标签页。
   - 话术：*"迎接上级检查时，一块大屏直观展示全校实习数据。"*

### ② 学生视角（demo_stu1）—— "学生怎么用"
1. 退出 → 登录 demo_stu1（或直接切移动端 H5 标签页演示，更有"手机感"）。
2. 移动端首页功能宫格 → 点 **打卡签到**。
   - 话术：*"学生用手机打卡，系统做 **GPS 地理围栏校验**——不在企业范围内打不了卡，杜绝代打卡。"*
3. 点 **周报月报** → 展示已提交的周报。
   - 话术：*"学生按周/按月写实习日志，教师在线批阅。"*
4. 点 **实习岗位 / 实习申请**。
   - 话术：*"学生在线浏览岗位、投递申请，全程线上流转。"*

### ③ 指导教师视角（demo_teacher）—— "老师怎么带"
1. 退出 → 登录 demo_teacher。
2. 点 **学生进度** → 展示所带学生的打卡/日志完成情况。
   - 话术：*"教师一屏掌握所带学生的实习进度。"*
3. 点 **周报月报批阅** → 打开一条 → 写评语/通过。
   - 话术：*"教师在线批阅并反馈。"*
4. 点 **巡访记录 → 新增巡访** → 选学生、填内容。
   - 话术：*"教师走访企业的记录也线上留痕，符合教学规范要求。"*

### ④ 收尾与成绩 —— "怎么算分、怎么归档"
1. 切回 demo_admin → **实习考评**。
   - 话术：*"实习成绩按多维权重（打卡/周报/月报/企业评价/学校）自动核算，再发布给学生。"*
2. 点 **档案归档**。
   - 话术：*"最后，系统按学生汇总全过程材料，完成校内核验、归档和移交，确保材料可追溯、可验收。"*

> 💡 节奏提示：不必每个菜单都点。**抓 3 个最有"科技感/卖点"的**：GPS 打卡、风险预警/催办、成绩自动核算+学信网导出。

## 四、技术亮点收尾（1 分钟）

> "技术上：后端 Node.js + Express + MySQL，前后端同源、RESTful API；
> 安全做了 **JWT 认证、RBAC 五角色权限、操作审计、首登强制改密、登录限流、SQL 注入防护**；
> 工程上我写了**自动化测试**——单元、接口冒烟、端到端闭环，还用无头浏览器**实走了 120 个页面 + 155 次交互，0 缺陷**；
> 部署上支持 **Docker 一键私有化部署**，配了备份和运维手册，是按**能真正卖给学校**的标准做的。"

## 五、答辩常见提问 & 应答

| 老师可能问 | 怎么答 |
| --- | --- |
| 和市面产品（工学云等）比有什么区别？ | "我对标了它们的核心功能并做了整合：实习+毕设**双主线打通**在一个系统里，且支持私有化部署、数据可归档上报，更贴合学校自主可控需求。" |
| 打卡怎么防作弊？ | "GPS 地理围栏，超出企业设定半径直接拒绝；并记录距离、支持照片打卡和补卡审批。" |
| 数据安全怎么保证？ | "密码 bcrypt 加密、JWT 认证、RBAC 权限隔离、所有写操作审计留痕、敏感数据脱敏导出、参数化查询防注入。" |
| 性能扛得住集中打卡吗？ | "PM2 集群模式跑满多核 + MySQL 连接池；早八集中打卡是典型场景，架构上已考虑。" |
| 怎么部署到学校？ | "一条命令 `npm run setup` 建库建表建管理员，或 Docker Compose 一键起 db+app+nginx，配了每日备份和新手部署手册。" |
| 工作量/原创性？ | "48 个功能模块、约 70 张表、PC+移动+小程序三端，全流程闭环，并自建了自动化测试体系。" |
| 测试做得怎么样？ | 翻到《功能测试报告》："105 项自动化用例 + 120 页 UI 实走全通过，过程中边测边修了若干真实缺陷。" |

## 六、翻车预案（冷静处理）

| 情况 | 应对 |
| --- | --- |
| 某页面没数据 | 先 `npm run seed:demo` 再演示；或换一个有数据的菜单 |
| 打卡演示失败 | 演示数据里 demo_stu1 已有历史打卡记录，直接在"打卡签到"页展示记录即可 |
| 服务没起来 | 检查后端窗口是否在跑；`curl http://localhost:3000/api/health` 应返回 success |
| 网络/投屏卡 | 准备好关键页面**截图**作为备份，照着讲 |
| 被问到不会的 | "这个点我下来再深入研究"——别硬编，诚实加分 |

> 最稳的做法：**上台前自己完整彩排一遍**，掐时间，把上面主线点顺。
