# backend/AGENTS.md

> 适用于 `backend/` 下所有代码。继承根目录 `AGENTS.md`，并补充后端专属规则。

## 1. 当前后端主线

仓库 `backend/README.md` 定义的唯一主线：

- Python 3.12；
- FastAPI；
- Pydantic；
- SQLAlchemy 2.x；
- Alembic；
- Uvicorn；
- Pytest；
- 正式生产与正式验收：MySQL-only（只以 MySQL 为准，utf8mb4）。

后端主要结构包括：

- `app/api/`：HTTP API（接口）入口；
- `app/services/`：业务服务；
- `app/models/`：数据模型；
- `app/schemas/`：请求 / 响应数据结构；
- `app/db/`：数据库基础设施；
- `app/core/`：核心配置与基础能力；
- `app/modules/`：领域模块；
- `app/workers/`：异步 / 后台工作器；
- `alembic/`：数据库迁移；
- `tests/`：后端测试。

先沿现有分层查找权威实现，不要把业务逻辑随意塞到路由或重复造 Service（业务服务）。

## 2. 修改前必须检查

后端写代码前至少确认：

1. 是否已有同义 API、Service、Schema、Model、Enum、Helper；
2. 是否已有对应 Alembic migration（数据库迁移）；
3. 是否已有权限、租户、数据范围、审计、幂等实现可以复用；
4. 当前接口被哪些 PC / 小程序 / E2E 消费；
5. 当前测试到底验证了什么，不要仅凭测试文件名推断业务合同。

新增一个接口通常不是只新增一个路由。要检查它是否需要：Schema、Service、Model、权限、审计、迁移和测试的同步变化。

## 3. API 与 Service 边界

### API 层

API 层负责：

- 参数接收与基础校验；
- 身份上下文接入；
- 调用现有业务服务；
- 映射明确的 HTTP 状态与响应结构。

避免：

- 在路由函数堆复杂状态机；
- 在不同路由复制同一权限判断；
- 在 API 层直接拼大段 ORM 查询绕开已有 Service；
- 为了前端方便返回与现有 Schema 不一致的临时结构。

### Service 层

Service（业务服务）负责真正的业务规则，包括必要的：

- 状态机；
- 跨表一致性；
- 事务边界；
- 幂等；
- 并发冲突；
- 权限 / 数据范围协作；
- 审计协作。

修改状态流转时，必须先寻找已有状态定义和已有调用方。禁止在新 Service 中再定义一套字符串状态。

## 4. 数据库规则

### 4.1 MySQL 是正式事实源

正式验收不得用 SQLite 代替 MySQL。

尤其以下改动必须在 MySQL 上验证：

- Alembic migration（数据库迁移）；
- unique / foreign key / index（唯一约束 / 外键 / 索引）；
- utf8mb4、排序规则、大小写相关行为；
- transaction（事务）；
- lock / concurrency（锁 / 并发）；
- JSON、时间、精度等 MySQL 特有语义。

### 4.2 Schema 改动必须有迁移

改变持久化结构时：

- 修改 Model 不等于完成；
- 必须检查 / 新增 Alembic migration；
- 不依赖应用启动时“顺便补字段”；
- 不直接修改生产数据库作为代码修复；
- 升级和回滚风险必须可解释。

### 4.3 数据完整性

写操作至少检查：

- tenant / school / user 等归属边界是否正确；
- 唯一性是否应该由数据库约束兜底；
- 重复提交是否需要幂等；
- 并发是否可能发生双成功；
- 中途失败是否会留下半成品数据；
- 审批 / 归档 / 锁定后是否仍能被非法修改。

不要只依赖前端禁用按钮保证数据库安全。

## 5. 权限、安全与审计

任何涉及读写业务数据的改动，都要确认：

- authentication（认证）：用户是谁；
- authorization（授权）：用户能不能做；
- tenant isolation（租户隔离）：是否越租户；
- data scope（数据范围）：角色能看到哪些数据；
- audit trail（审计留痕）：关键写操作是否可追踪。

禁止为了修测试：

- 去掉依赖注入里的权限校验；
- 扩大默认数据范围；
- 对无权限场景返回假成功；
- 把 403 / 409 / 422 等有业务意义的错误统一改成 200；
- 关闭生产安全限制。

## 6. 错误语义

错误响应必须表达真实失败原因。

常见语义示例：

- 400：请求语义本身非法；
- 401：未认证；
- 403：已认证但无权限；
- 404：资源不存在或按安全策略不可见；
- 409：状态冲突 / 并发冲突 / 重复操作；
- 422：结构或字段校验失败。

不要为了适配一个测试断言随意改全局错误语义；先确认当前 API 合同和现有调用方。

## 7. 测试顺序

仓库 README 当前示例：

```bash
cd backend
.venv\Scripts\python.exe -m pytest tests/test_p1_*.py -q
```

如果虚拟环境已经激活，可使用同等的 `python -m pytest ...` 精准命令。

施工时遵循：

1. 最窄失败测试；
2. 目标 Service / API 测试；
3. 受影响 MySQL 集成测试；
4. 受影响模块测试；
5. 只有封板时才扩大到必要全量门禁。

不能把“pytest 通过”自动等同于用户业务闭环通过。用户可见流程还必须按根目录 `ACCEPTANCE.md` 和 `e2e/AGENTS.md` 判断。
