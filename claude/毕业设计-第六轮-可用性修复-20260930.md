## 第 1 项：归档口径对齐（已完成）

### 问题

单个学生的「生成清单 / 提交归档」只核对 7 项旧业务状态（任务书、开题、中期、定稿、评阅、答辩、成绩）；
批量预览和备案却按当前批次**启用的材料规则**核对（例如「指导记录附件」、学校自己加的「选题志愿确认单」）。
于是单个学生页显示“材料齐全”也能提交，到备案才被拦。

### 改动

| 文件 | 改动 |
|---|---|
| `backend/app/modules/graduation/services/graduation_archive_v2_preview.py` | 新增 `student_rule_check`：单个学生直接复用批量预览的 `enrich_snapshot`，同一份规则、同一份判断逻辑。批次未启用材料规则时沿用旧结果（备案本身仍会因“未初始化材料规则”拦下）。 |
| `backend/app/modules/graduation/services/graduation_archive_consistency.py` | `_rule_check`（生成、提交、单个备案前核对共用）最后一步改为调用 `student_rule_check`。 |
| `backend/app/modules/graduation/services/graduation_archive_service.py` | ① 提交被缺件拦下时，先把最新缺件清单写回归档记录并记审计「提交归档被拦截」，再返回“还缺 N 项材料，不能提交归档：A、B、C”；② 单个学生详情（`GET gd-archives/{id}`）对未备案记录做只读实时核对，旧的“材料齐全”不会再掩盖新增缺件。 |
| `frontend/src/modules/graduation/views/GraduationRiskArchiveView.vue` | 待提交状态增加「重新核对材料」按钮；提交被拦后自动刷新台账，缺件明细直接显示；提示语改为“以上材料补齐后，点「重新核对材料」再提交归档”。 |
| `backend/tests/test_graduation_archive_rule_parity.py`（新增） | 4 条 MySQL 用例，见下。 |

未改：成绩权重、评阅人数等业务默认值；权限码与路由（无新增，无需同步权限目录与导航合同）。

## 第 2 项：秘书答辩确认页显示“还差谁未评”（已完成）

### 问题

秘书确认页只列出已经评了分的评委；没评的人根本不出现，秘书只能点“确认”后被拦，才知道缺人。

### 改动

| 文件 | 改动 |
|---|---|
| `backend/app/modules/graduation/services/graduation_defense_score_service.py` | 新增 `panel_progress`：列出当前轮次答辩组全部评委（主席 + 成员）及各自状态（未评分 / 已评分 / 缺席 / 已确认），给出“还差 N 位评委未评分：某某”。判断口径与“确认本轮成绩”完全相同（按评委的稳定身份匹配，不按姓名）。学生不在当前用户数据范围内时不返回名单。 |
| `backend/app/modules/graduation/routers/graduation_sensitive_router.py` | 评分列表 `GET gd-defense-scores` 在带 `gdStudentId` 时多返回 `panel`；不带时与原来完全一样。没有新增路由和权限码。 |
| `frontend/src/modules/graduation/api/graduation-defense-grade.api.js` | 把 `panel` 带给页面。 |
| `frontend/src/modules/graduation/views/GraduationDefenseGradeView.vue` | 答辩面板顶部新增“答辩组评分进度（第 N 轮）· 已评 X / Y 位”，红字“还差 某某 未评”，逐人显示状态和分数。 |
| `backend/tests/test_graduation_defense_panel_progress.py`（新增） | 2 条 MySQL 用例。 |
