# frontend/AGENTS.md

> 适用于 `frontend/` 下的 PC 管理端代码。继承根目录 `AGENTS.md`。

## 1. 当前前端主线

`frontend/package.json` 当前定义：

- Vue 3；
- Vite 6；
- Vue Router 4；
- Pinia；
- Element Plus；
- ESLint + Prettier；
- Node 内置测试执行器。

主要源码边界包括：

- `src/views/`：页面；
- `src/components/`：可复用组件；
- `src/layouts/`：布局；
- `src/router/`：路由；
- `src/services/`：接口服务；
- `src/stores/`：Pinia 状态；
- `src/modules/`：模块化业务代码；
- `src/security/`：前端安全 / 权限相关能力；
- `src/config/`：配置；
- `src/types/`：类型 / 结构约定；
- `src/utils/`：公共辅助函数；
- `src/mocks/`：模拟数据相关代码。

新增页面、接口调用、状态或组件前，先在这些目录搜索已有实现。

## 2. 前端不可违反的规则

### 2.1 不在页面里再造一套后端合同

禁止在单个页面临时硬编码一套：

- 业务状态；
- 角色 / 权限；
- API 地址；
- 错误语义；
- 字段映射；
- 数据范围；
- 租户逻辑。

如果仓库已有 Service、Store、Config、Type、Enum 或公共 Helper，必须优先复用。

后端返回结构变化时，先确认真正权威合同，再修改统一适配层；不要在多个页面分别写兼容分支。

### 2.2 不用前端假成功掩盖后端失败

禁止：

- 请求失败后本地直接改成成功状态；
- 提交失败仍弹“操作成功”；
- 用 mock 数据覆盖真实接口异常；
- 为通过 E2E 在按钮点击后人工写 Store 状态；
- 在生产路径中吞掉 401 / 403 / 409 / 422 等重要错误。

用户看到的状态必须能由真实后端和持久化数据解释。

### 2.3 不随意扩大公共改动面

修改公共组件、Layout、Router、Store、Service、Security 或全局样式前，先搜索调用方。

如果任务只属于一个模块：

- 优先模块内修复；
- 不顺手改全局视觉体系；
- 不全仓批量格式化；
- 不为一个页面新增第二套通用组件；
- 不删除旧路由 / 兼容入口，除非任务和规格明确要求。

## 3. 页面实现质量

用户可见页面至少考虑以下状态：

- loading（加载中）；
- empty（空数据）；
- success（正常数据）；
- validation error（输入校验错误）；
- permission denied（无权限）；
- request error（请求失败）；
- conflict（状态 / 并发冲突，如后端 409）；
- disabled / readonly（不可操作 / 只读）。

禁止只实现“接口成功、有数据”这一条理想路径。

### 表单

- 前端校验用于提升体验，但不能替代后端校验；
- 提交中要防止重复点击造成重复请求；
- 服务端返回字段级错误时尽量映射到真实输入项；
- 成功后刷新 / 重进页面应与后端真实状态一致。

### 列表与详情

- 分页、筛选、排序参数必须与后端合同一致；
- 切换筛选条件时避免旧请求覆盖新请求；
- 详情页不能依赖仅存在于上一页内存中的关键业务数据；
- reload（刷新）后仍应能从 URL / API 恢复必要状态。

## 4. 路由、权限与导航

修改 `src/router/`、菜单或权限展示时：

- 先确认现有路由是否已经存在；
- 页面隐藏不等于后端授权，不能把前端路由守卫当作安全边界；
- 保持路由参数、查询参数与页面读取逻辑一致；
- 修改公共路由时检查直接 URL、刷新、返回、重登录后的行为；
- 不用重复路由解决页面入口问题。

权限 UI 必须与真实后端能力一致：无权限时不能靠“藏按钮”冒充安全。

## 5. API / Store 使用规则

### API Service

- 优先通过现有 `src/services/` 调用后端；
- 不在页面里散落重复 `fetch` / 请求封装；
- 统一处理鉴权、公共错误和请求配置；
- 新字段要检查所有消费端，不凭猜测做宽松兼容。

### Pinia Store

Store 用于共享状态，不应成为后端数据库的影子副本。

- 业务成功以后以服务端返回 / 重新查询为事实；
- 不为绕过 API 缺陷长期保存伪造状态；
- 退出登录 / 切换身份后清理不应跨身份保留的数据；
- 避免把只属于一个组件的临时 UI 状态塞进全局 Store。

## 6. Mock 使用边界

`src/mocks/` 的存在不代表生产链路可以依赖模拟数据。

- 正式业务验收必须走真实后端；
- 不允许因为真实接口红灯而自动 fallback（回退）到 mock；
- mock 只能用于明确的开发 / 测试场景，并与生产路径隔离；
- E2E 声明真实业务 PASS 时，不得由 mock 提供核心业务结果。

## 7. 前端验证命令

当前 `package.json` 提供：

```bash
cd frontend
npm run lint
npm test
npm run build
```

施工时按改动范围从窄到宽验证：

1. 目标逻辑 / 对应测试；
2. `npm run lint`；
3. `npm test`；
4. `npm run build`；
5. 用户关键流程再进入 `e2e/` 真实浏览器验收。

不要把 `npm run build` 通过等同于业务可用；它只证明构建链没有在这一层失败。

## 8. E2E 可测试性

为了真实浏览器测试稳定：

- 优先使用语义明确的 label、role、button name；
- 不依赖随机 class 名或脆弱 DOM 层级作为唯一定位方式；
- 同一页面不要出现多个含义相同但行为不同的主按钮文案；
- 异步操作应有明确 loading / success / error 状态；
- 不为了测试新增只在测试中可见的“后门业务按钮”。

测试定位器需要修复时，先确认页面真实可访问性和交互语义是否合理，再决定改页面还是改 Runner（测试执行器）。
