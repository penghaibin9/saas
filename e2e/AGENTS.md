# e2e/AGENTS.md

> 适用于 `e2e/` 下 Playwright 真实浏览器端到端验收。继承根目录 `AGENTS.md`。

## 1. E2E 的职责

本目录不是“把 Actions 跑绿”的脚本集合，而是证明学校真实用户能否通过真实页面办完业务。

现有 `e2e/README.md` 的核心约束是：

- 使用真实 Chromium 浏览器；
- 连接真实后端；
- 使用独立 MySQL 测试库；
- 业务动作不能由 seed（预置数据）代替；
- 失败应保留 screenshot（截图）、video（录像）、trace（执行轨迹）和请求元数据等证据。

因此，浏览器门禁的通过含义必须是“页面真的完成了动作”，不能退化为“接口返回 200”。

## 2. Browser First（浏览器优先）原则

当门禁要证明某个用户流程时，核心业务动作必须通过用户实际可操作的 UI 完成，例如：

`登录 → 找入口 → 打开页面 → 填写 → 点击 → 提交 → 审批 → 刷新 / 重登 → 查询 / 查看结果`

允许 API / DB 辅助的场景：

- 创建与被测动作无关的基础前置数据；
- 查询结果用于交叉核验；
- 诊断失败原因；
- 清理测试环境；
- 明确标注为 API / DB 合同测试的用例。

禁止 API / DB 辅助的场景：

- 直接执行门禁本来要证明的提交、审批、归档、确认、撤回等业务动作；
- 直接把数据库状态改到最终值再让页面读取；
- 用 `page.evaluate`、Store 注入、本地存储注入等方式伪造核心业务完成；
- 因按钮难点就跳过真实按钮改用请求调用。

## 3. Seed（预置数据）边界

Seed 只负责“把舞台搭好”，不能替演员完成剧情。

可以 seed：

- 租户 / 学校；
- 测试账号和必要角色；
- 课程、批次等稳定基础数据；
- 被测流程合理需要的前置实体。

不能 seed：

- 本次要验证的最终审批结果；
- 本次要验证的业务状态迁移；
- 本次要验证的审计记录；
- 本次要验证的学生 / 教师真实提交结果。

如果前置数据已经包含门禁要证明的结果，该门禁无效。

## 4. 失败先分类，不先改产品

出现红灯时，必须优先取得第一处真实失败证据，然后分类：

### `PRODUCT_BUG`

例如：

- 页面没有入口；
- 按钮真实点击后接口失败；
- 状态流转错误；
- 页面刷新后状态丢失；
- 权限 / 数据范围错误；
- 后端持久化或审计错误。

处理：修生产代码，再精准重跑。

### `RUNNER_BUG`

例如：

- locator（元素定位器）错误；
- 页面已经成功但断言读错元素；
- 等待错误事件；
- 测试脚本使用过时文案 / 路由；
- Runner 自己制造登录、origin（来源地址）或 session（会话）问题。

处理：只修 Runner，不改弱生产合同。

### `ENVIRONMENT_BUG`

例如：

- 服务没有启动；
- 浏览器依赖缺失；
- 端口冲突；
- CI 网络 / 资源异常；
- MySQL 测试实例不可用。

处理：修环境或工作流，不修改业务代码。

### `TEST_DATA_BUG`

例如：

- 测试账号不满足角色前置；
- 同名旧数据污染；
- 测试数据跨 run 冲突；
- 前置实体状态不合法。

处理：修数据隔离 / bootstrap（测试前置初始化），不修改业务规则迎合脏数据。

## 5. 定位器规则

优先级：

1. `getByRole` + accessible name（可访问名称）；
2. `getByLabel`；
3. `getByPlaceholder`；
4. 稳定、业务语义明确的 test id；
5. CSS / DOM 结构定位作为最后手段。

要求：

- 不用 `.nth(7)` 这类无业务语义的脆弱定位，除非列表结构本身就是被测合同；
- 不因为重复按钮难定位就使用强制点击绕过；
- `force: true` 只能用于明确证明是浏览器遮挡 / 事件模型问题的特殊场景，不能作为常规修复；
- 页面结构变更后，优先恢复语义定位而不是叠更多选择器兜底。

## 6. 等待规则

禁止用大量固定 `sleep` / `waitForTimeout` 作为稳定性方案。

应等待真实条件：

- URL / 路由变化；
- 响应完成；
- loading 消失；
- 按钮变为可用；
- toast / dialog / row / status 出现；
- 数据刷新后的明确页面状态。

固定等待只能作为非常短的诊断手段，并应在根因确认后移除。

## 7. 证据要求

红灯至少保留能解释“第一处真实失败”的证据：

- 错误断言；
- 当前 URL；
- 关键请求状态；
- 页面截图；
- Playwright trace（执行轨迹）；
- 必要时录像；
- 对应测试数据标识；
- 对应 product SHA（产品提交版本）和 runner SHA（测试执行器版本）。

如果后续错误只是第一处失败导致的连锁反应，不要把最后一个报错误认为根因。

## 8. 重跑策略

修复后按最窄范围逐层扩大：

1. 失败断言 / 单一 spec（测试文件）；
2. 当前业务 gate（门禁）；
3. 受影响跨端 / MySQL seal（数据库封板验证）；
4. 需要最终发布时再跑 canonical final gate（权威最终门禁）。

已经在相同代码条件下证明且与修改无关的长流程，不因为一个 Runner 小修就机械从头重跑。

但如果修改影响其共享前置、权限、状态机、公共组件或数据库合同，应重新纳入受影响范围。

## 9. Playwright 命令

当前 `e2e/package.json` 提供：

```bash
cd e2e
npm test
npm run test:auth
npm run test:graduation
npm run report
```

精准施工优先使用：

```bash
npx playwright test <spec> --grep "<case>"
```

只有需要对应全目录证明时才执行完整 `npm test`。

## 10. 不允许的假绿模式

以下任何一种出现，都不能把门禁判定为 PASS：

- 核心业务动作由 API 代点；
- 核心状态由 SQL 直接改成；
- 失败断言被删除而没有等价验证；
- 断言从精确业务结果改成“页面存在即可”；
- 为了 Runner 放宽生产权限 / 限流 / 校验；
- `try/catch` 吞掉关键失败；
- 条件分支发现按钮不存在就跳过；
- 只看 network 200，不检查用户最终页面和数据结果；
- 用旧 SHA 的绿灯证明当前 SHA。

## 11. E2E 完成检查表

- [ ] 核心动作由真实浏览器完成；
- [ ] Seed 没有替代被测业务动作；
- [ ] 使用真实后端和独立 MySQL 测试库；
- [ ] 失败已分类为 Product / Runner / Environment / Test Data；
- [ ] 定位器具有业务语义，没有靠大量 nth / force 硬过；
- [ ] 没有用固定 sleep 掩盖真实同步问题；
- [ ] 提交后至少按业务需要验证 reload / re-login 后状态；
- [ ] 关键跨角色流程确实切换角色核验；
- [ ] 需要时核验数据库、权限、审计；
- [ ] 证据对应当前 product / runner SHA；
- [ ] 未执行的后续门禁没有写成 PASS。
