## 5. 业务目标、角色与闭环

- **真实问题**：小程序受屏幕/输入限制，无法完成长文档撰写、大批量材料上传、大表选课、打印盖章类业务；这些必须在 PC 完成，并与老师端同一条流程对接。
- **使用角色**：学生本人（在校生/新生/毕业班/毕设批次/实习批次，按身份投影模块）。
- **发起→处理→审核→查看→归档责任**：学生发起与提交；老师端（各中心角色）审核/审批；系统留痕归档；学生可查看状态与结果、按政策申诉。
- **主流程**：登录 → 首页待办 → 进模块办理（填表/写文档/传材料/确认签字/打印）→ 提交进审批引擎 → 老师端处理 → 状态回流学生端 → 归档。
- **异常流程**：撤回、退回整改、重复提交幂等、超时、关闭/重开，均由对应模块状态机定义（各期三级施工卡细化）。

## 8. 数据模型与迁移（原则）

- **优先复用**各中心已有主数据表与业务表；学生自助提交尽量作为现有业务表的“学生发起来源”，避免重复建表。
- 确需新增时（如门户草稿箱、电子签记录、打印/导出留痕），新增表须：带 `tenant_id` 租户隔离、关联主数据、标敏感级别、唯一/并发约束、升级+回滚脚本，走 `backend/alembic/versions/`。
- 附件统一走现有文件服务（`/files/upload?bizType=...` + `file_service`），门户只存 `file_id` 关联，不自存二进制。
- 每期三级施工卡逐表登记；本总纲不提前虚构字段。

## 9. API 契约（命名空间与通用约定）

- 读（本人聚合/查询）：复用 `/api/v1/mobile/*`（已存在）。
- 写（PC 重活）：新增 `/api/v1/portal/*`，由 `backend/app/student_portal/` 提供，内部复用共享 service。
- 通用约定：
  - 鉴权：`Bearer`（学生 token）；服务层 `_require_student` + `resolve_student` 强制“本人”。
  - 数据范围：一切以当前学生本人为界，禁止入参指定他人 id 越权。
  - 附件：先 `/files/upload` 得 `file_id`，再随业务提交携带。
  - 错误码：无权限 403 + 业务码；越权/跨租户 拒绝 + 审计；非法状态 409/业务码。
  - 审计：每个写动作落 `audit_log`（事件、对象、快照、时间、操作人）。
- 每条具体接口（method/path/请求/响应/权限码/状态限制/错误码/审计/测试）在各期三级施工卡逐条定契约，本总纲只定框架。
