# 独立岗位实习平台系统管理 PRD（产品需求文档）
**版本：第一版评审稿｜审计日期：2026年10月7日**

## 一、产品定位与真实审计结论

**这套系统管理应当让学校自己完成“建组织、导入师生、开通账号、分配职责、调整权限、配置请假审批、追查操作”，使岗位实习平台具备独立交付和日常维护能力。**

按您已确认的决定：

- 建成可以向其他学校独立交付的通用产品，以益阳项目采购要求作为当前落地依据。
- 提供预配角色和规则，学校可在安全边界内自主调整。
- 首版提供请假多级审批配置；其他实习审批沿用现有业务规则，补齐责任人配置和交接。
- 沿用现有页面风格和工作区，不引入新的前端框架，不建设多校运营、计费或通用拖拽流程平台。

## 二、功能结构与页面需求

在现有一级导航中增加 **“系统管理”**，与“岗位实习中心”并列。只对有管理职责的人显示。

**系统管理页面以学校为上下文，不要求先创建或选择实习批次。** 涉及导师分配、在办任务交接时，再明确选择对应批次。

建议设置六个分组、十八个工作页面。角色详情、导入预检、变更对比等作为工作区内的子页或步骤，不继续扩张菜单。

| 分组 | 工作页面 | 首版必须交付的能力与边界 |
|---|---|---|
| 管理概览 | **① 系统管理概览** | 展示未开通账号、未绑定学生、缺少管理范围、审批责任人缺失、失败任务、备份异常等真实问题；点击直达具体对象。新学校显示初始化步骤，已开通学校显示待处理问题。 |
| 组织与人员 | **② 组织架构** | 维护院系、专业、年级班级、校内部门及归属；专业保留国标代码、学制、培养层次。支持启停、导入和导出。校内部门与企业轮岗科室分开。 |
| 组织与人员 | **③ 教职工资料** | 维护工号、姓名、所属院系或部门、联系方式、在职状态；关联同一登录账号，显示任职、负责范围和待交接事项。只保留实习必需资料。 |
| 组织与人员 | **④ 学生资料** | 复用现有学生主档，维护学号、姓名、组织归属、年级及实习需要的基础资料；展示账号绑定和资料完整情况。实习批次中的学生名单继续引用同一主档。 |
| 账号与权限 | **⑤ 用户账号** | 查询学校管理人员、教师、学生及相关企业账号；处理启用、停用、解锁、受控重置、绑定异常及有效期。企业账号只能按企业身份规则管理，不可挂成学校教师。 |
| 账号与权限 | **⑥ 角色与权限** | 预配角色、复制角色、创建本校角色、调整功能权限和成员。一个工作区展示“成员、功能权限、负责范围、变更记录”。 |
| 账号与权限 | **⑦ 管理范围与责任关系** | 设置院系管理员、专业负责人、班主任等负责对象，检查无人负责和重复责任；支持人员交接。实习导师分配仍调用现有实习分配命令。 |
| 规则与基础配置 | **⑧ 学校资料与品牌** | 学校全称、简称、标识、校徽、平台显示名称、联系及监督咨询信息；预览各端展示效果。不能修改数据库归属、服务器地址或学校身份标识。 |
| 规则与基础配置 | **⑨ 基础字典** | 展示地区、行业、企业性质、专业代码等标准字典的来源和版本；首版允许维护公告分类、导入匹配别名等学校项。业务状态、法定类别和审批结果不能任意新增或改义。 |
| 规则与基础配置 | **⑩ 请假审批配置** | 设置一至三级顺序审批、适用批次、节点责任岗位和生效版本；提供实际责任人预览和缺失检查。首版不提供任意脚本、并行会签或通用流程设计器。 |
| 规则与基础配置 | **⑪ 通知与服务设置** | 管理站内通知模板、承办岗位、咨询电话和常见问题；查看外部消息渠道是否接通。紧急告知、关键业务回执不能被普通配置关闭。 |
| 数据与对接 | **⑫ 师生导入与账号开通** | 教师、学生共用标准电子表格导入工作区，完成预检、组织识别、冲突处理、账号开通及回执。这里是批量创建师生账号的唯一入口。 |
| 数据与对接 | **⑬ 导入导出任务** | 汇总任务进度、成功与失败数量、错误行、受控结果下载和操作记录。各业务页面产生的任务在这里查看，不另建第二套导入导出执行逻辑。 |
| 数据与对接 | **⑭ 历史数据迁移** | 按迁移批次记录来源、映射规则、组织人员对应关系、业务记录及附件对账、异常处理和验收结果。区别“数据进入系统”和“师生可以继续办理”。 |
| 数据与对接 | **⑮ 外部服务与对接** | 查看企业信息核验、地图、消息、文件扫描及两类监管对接的配置状态、最近检测、失败原因和责任人。密钥不在页面明文回显；未接通不能显示为可用。 |
| 安全与运维 | **⑯ 登录与操作审计** | 查询登录异常、账号重置、权限变更、敏感查看、导出下载及业务关键操作；可追溯人、对象、时间、原因和结果。学校端不提供删改日志。 |
| 安全与运维 | **⑰ 运行与备份状态** | 展示服务、文件扫描、审计投递、存储及备份状态，区分“备份完成”和“恢复演练通过”。学校侧查看和报障，不提供直接覆盖数据库的恢复按钮。 |
| 安全与运维 | **⑱ 版本与交付资料** | 展示当前版本、升级记录、授权服务信息、操作手册、培训材料、备案及验收文件；技术信息默认折叠。资料缺失如实提示，不生成虚假合格证明。 |

### 页面间的职责划分

- **组织与人员**负责“这个人是谁、属于哪里”；**账号与权限**负责“能否登录、以什么身份做什么”。
- **管理范围与责任关系**负责校内管理职责；**实习分配**负责某批次中谁指导哪个学生。
- 实习计划、考核比例、材料收件要求、协议模板、公告发布、企业岗位、监管报表继续留在现有实习业务页面。
- 现有“教师管理”保留业务能力，展示名称建议改为“教师工作台账”，避免与“教职工资料”混淆。
- 系统管理不设独立“菜单编辑器”。菜单、按钮和接口访问共同由真实权限控制，学校看到中文业务名称。

## 三、关键办理规则与权限设计

### 3.1 新学校开通

推荐路径：

**确认学校资料 → 导入组织与师生 → 开通账号 → 分配角色和范围 → 确认责任岗位 → 检查就绪情况 → 进入实习业务创建批次。**

具体要求：

1. 安装时创建首位学校管理账号，预置角色及基础字典，不预造真实院系、教师或学生。
2. 学校可先维护组织，也可通过师生导入提取组织信息；新增组织必须在预检中明确展示并经确认。
3. 账号、人员档案、学生绑定、角色和负责范围分别检查，不能用“账号已创建”代替“可以办理业务”。
4. 初始化检查只说明系统准备情况，不能自动将学校标为验收合格。
5. 后续重新执行初始化或升级模板，应保留学校已经修改的配置，只展示差异并受控应用。

### 3.2 师生导入与账号开通

固定流程为：

**下载模板 → 上传预检 → 确认新增与更新清单 → 确认开通 → 下载受控回执 → 正常登录验证。**

- 使用标准 `.xlsx` 文件，学号、工号、组织代码按文本保存，保留前导零。
- 预检展示新增人员、更新人员、新增组织、已有账号、绑定冲突及错误行。
- 同名组织、同名教师、多候选匹配不得自动选第一个；必须让操作者明确核对。
- 有错误的批次不能确认；预检结果持久化，不能因应用重启或切换服务实例而丢失。
- 确认必须绑定原文件、预检版本、当前学校和操作者；资料或权限发生变化时要求重新核对。
- 同一确认批次完整生效或整体回滚；重复确认不产生重复人员、账号、角色关系。
- 更新已有人员不重置其密码、不覆盖其现有角色；新增和撤销角色属于明确授权动作。
- 新账号使用随机临时凭据并强制首次修改，通过受控交付回执提供；普通人员导出、日志和通知中不得包含密码。
- 实习学生名单、岗位分配、材料等业务导入，只引用已有账号和主档，不隐式开户。

### 3.3 角色与权限

首版提供以下预配身份，学校可以复制调整，但不能突破本人、企业、院系和授权上限。

| 身份 | 默认职责 | 默认范围与限制 |
|---|---|---|
| 学校系统管理员 | 组织、人员、账号、角色、配置及系统状态 | 本校配置范围；配置身份不自动获得实习审批、学生敏感材料查看权 |
| 校级实习管理员 | 全校实习组织、办理、统计与业务规则 | 本校实习业务；不能替企业评价、删除审计或直接改业务终态 |
| 院系实习管理员 | 本院人员基础维护及实习管理 | 已指定院系；默认不能创建高权限角色或更改校级规则 |
| 专业负责人 | 本专业计划及实施协调 | 已指定专业和相关计划 |
| 班主任／辅导员 | 负责班级的过程查看、提醒和被授权办理 | 明确绑定的班级；审批权限单独配置 |
| 实习指导教师 | 指导、批阅、巡访、异常处理 | 正式分配给本人的学生和任务；保留招标要求的受控学生密码重置 |
| 督导／领导 | 授权范围内进度和质量查看 | 默认只读汇总，敏感明细单独授权 |
| 安全审计员 | 查询审计及安全异常 | 本校审计，不默认办理业务或查看全部学生材料 |
| 学生 | 本人申请、材料、进度和结果 | 仅本人，不能复制为管理身份 |
| 企业成员／企业导师 | 获授权企业范围内的协同办理 | 按现有企业成员、企业授权及业务关系控制，与学校角色体系分开 |

角色编辑统一遵守：

- 默认从预配角色复制；也可创建空白角色，但必须明确身份类型和负责范围。
- 页面以“查看、维护、审核、发布、导出、查看完整联系方式”等中文动作组织权限。
- 授权不得超过当前操作者的授权能力和范围；敏感权限逐项确认，不能通过“全选”隐式开放。
- 保存前展示新增与撤销权限、范围变化、受影响人数、待办影响。
- 清空角色权限后必须真正无权，不得回退到程序内置的宽权限。
- 一人多角色只按当前激活角色生效，不将不同角色权限自动合并。
- 角色停用、成员撤销、范围收回后，后续请求立即按新事实裁定；旧页面、旧令牌、旧下载链接不能继续沿用已撤销权限。
- 内置模板升级不得覆盖学校本地修改。
- 保护最后一个有效学校主管理账号，并覆盖两名管理员并发停用对方的情况。

### 3.4 人员、组织变更和工作交接

- 学院、专业、班级、人员及责任关系使用稳定标识关联，名称是展示字段。
- 改名不能创建第二个组织，也不能让原权限和业务关系失效。
- 人员跨院、学生换班等操作先展示受影响的管理范围、实习批次和在办事项，不静默搬迁全部业务。
- 有引用的组织只能停用或办理明确的归属调整，不能直接删除。
- 历史单据保留办理时的人员、组织和角色记录，不能随当前任职被重写。
- 正常离职先生成交接清单；紧急停用立即阻止登录，未交接任务进入异常队列，由有权人员继续交接。
- 交接改变后续承办人，不冒充原人员办理，不抹掉原审批记录。

### 3.5 请假多级审批

**首版支持一至三级顺序审批；默认保持现有指导教师一级审核，学校明确确认后启用多级。**

- 节点可选指导教师、院系责任人、校级责任人；责任人来自真实任职和当前学生关系。
- 配置按实习批次生效，一个批次在同一生效时段只有一个有效版本。
- 发布前预览实际责任人，存在空节点、循环或无法明确承办人的情况时不能发布。
- 学生提交时冻结流程版本；后续配置变化只影响新申请，不重排在办单据。
- 前一级通过后生成下一级待办。所有必需节点通过，才改变最终请假状态并触发相应考勤处理。
- 退回补正保留原单及历史；重新提交从首级重新审核，不能沿用旧材料的通过结论。
- 已明确驳回、撤回、返岗等业务动作继续遵守现有状态机，不由配置页面直接改终态。
- 承办人停用或失去权限时提示“待重新指定责任人”，不能自动跳过或自动通过。
- 学生电脑端、学生移动端、教师电脑端和教师移动端看到相同进度、退回原因和下一责任人。

### 3.6 全部管理页面共用的规则

| 控制项 | 统一要求 |
|---|---|
| 学校隔离 | 当前学校来自可信登录上下文；客户端提交学校编号不能扩大范围 |
| 权限检查 | 页面、接口、导出任务、文件下载及后台重试均检查权限和数据范围 |
| 并发编辑 | 保存携带版本；冲突时保留输入并展示差异，不自动覆盖 |
| 结果回执 | 明确已完成、处理中、部分完成或失败，提供对象和任务入口 |
| 敏感信息 | 默认脱敏；完整查看需要独立权限、用途和审计 |
| 审计 | 记录操作者、当前身份、对象、原因、必要的前后变化和结果；不记录秘密 |
| 异步任务 | 只重试失败部分；再次执行和下载时重验当前授权 |
| 界面状态 | 区分无数据、无权限、服务异常和处理中；错误不能伪装成空列表 |
| 导航 | 支持直接进入、刷新、返回和筛选恢复；学校、身份切换后清除旧上下文 |
| 运维边界 | 学校页面不提供直接执行服务器命令、覆盖数据库、清空日志或关闭关键安全检查的能力 |

## 四、接口、数据与现有系统的衔接

### 4.1 实施边界

复用当前独立产品的账号、组织、学生主档、学生账号绑定、企业成员、文件、审计和导入任务能力。原综合系统的管理实现可以作为参考，但不能整体引入其教务、学工、平台运营依赖。

系统管理与实习中心共享登录、权限上下文和工作区组件；**系统管理不挂在必须加载实习批次的业务布局下面**。

对既有数据进行增量升级，不重新初始化现库，不重建师生身份，不修改历史实习记录到终态。

- 明确未登录、禁止访问、版本冲突和输入错误的接口状态，前端统一呈现中文业务说明。

## 五、验收标准与实施顺序

### 5.1 必须真实跑通的故事

| 验收故事 | 必须取得的结果 |
|---|---|
| 空学校初始化 | 没有实习批次时，学校管理员仍能进入系统管理、建立组织、导入师生 |
| 师生开户 | 预检错误行、修正重传、确认开通、正常首次登录、本人主档绑定完整；重复确认不重复创建 |
| 院系分权 | 两个院系管理员分别只能维护本院对象；改参数、猜对象编号、导出和下载均不能跨院 |
| 学校修改角色 | 复制角色、裁剪权限、分配成员后真实生效；空权限不回退；学校修改在模板升级后保留 |
| 一人多职 | 同一教师在电脑端及移动端切换身份，菜单、待办、数据范围随之变化；迟到响应不覆盖新身份 |
| 停用与撤权 | 停用账号、撤销角色、收回范围后，旧会话及旧文件链接受到真实限制；历史记录保留 |
| 组织调整 | 同名组织可区分；改名后授权不丢失；学生换班和教师调岗正确提示相关业务影响 |
| 人员交接 | 原承办人退出、接收人收到真实待办，未完成事项可继续办理，历史责任可追溯 |
| 多级请假 | 学生提交、逐级处理、退回补正、原单重交、最终生效和跨端刷新一致；末级之前不提前改变考勤 |
| 导出及任务 | 条件、数量与页面一致；学号不失真；敏感内容受控；权限回收后不能继续领取结果 |
| 历史迁移 | 主档、关系、单据和附件逐项对账；迁入后正常师生可以查看及继续办理 |
| 备份与交付 | 展示真实备份记录；在隔离目标完成恢复演练并核对文件；备案、对接及验收资料分别标明实际状态 |

**验证分层：**

- 先检查角色权限、范围解析、版本冲突及任务重复提交等关键行为。
- 真实数据库集成验证账号、角色、绑定、审批和必需审计的一致提交及回滚。
- 真实浏览器验证上述办理故事，使用正常学校、教师、学生、企业测试身份。
- 管理端重点检查常用电脑分辨率；关联移动流程检查375、390、430像素宽度。
- 手机网页、微信构建、微信真实宿主分别报告，不相互替代。
- 本模块验收不能代替整份88项采购要求。采购中的并发、响应时间、年度稳定性和外部接收要求继续单独取证。

### 5.2 实施顺序与阶段终点

| 阶段 | 主要工作 | 达到什么才进入下一阶段 |
|---|---|---|
| 第一阶段：能独立开局 | 管理入口、组织人员、师生开户、学生绑定、初始角色、基础审计 | 新学校不依赖手工改数据库即可完成准备并正常登录 |
| 第二阶段：能由学校维护 | 可编辑角色、稳定范围、电脑身份切换、账号停用及责任交接 | 学校调整后真实生效，跨院拒绝和旧会话撤权通过 |
| 第三阶段：满足配置需求 | 请假多级审批、学校品牌、受控字典、通知服务设置 | 实际学校配置被各端消费，请假完整接续且历史不受改写 |
| 第四阶段：独立交付收口 | 任务中心、历史迁移、对接状态、备份恢复证据及交付资料 | 全部本模块故事通过，剩余外部条件逐项明示 |

每阶段先完成一条可验收故事再扩大范围。执行时继续使用当前独立产品工程，先复核其他正在进行的改动；提交、推送、合并和生产发布不包含在本次文档规划授权中。

**本稿的完成标准是：学校可以自行把人、组织、权限和责任配置正确，随后在原岗位实习页面办成业务，并能查询变更、交接和失败原因。十八个页面全部出现，仍不等于系统管理验收通过。**
