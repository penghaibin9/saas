## 一、三家成熟系统对标表

### 对标对象 A：同方知网（CNKI）大学生毕业论文（设计）管理系统

- 来源：CNKI 官方教学秘书/指导教师用户手册（多所高校教务处公开转载），[co2.cnki.net](https://co2.cnki.net/) 系统入口。
- 核心流程：选题 → 任务书 → 开题（报告+答辩）→ 中期检查 → 论文提交 → 查重检测与评阅 → 答辩 → 成绩 → 归档。
- 角色：教学秘书（流程配置/开通关闭节点）、指导教师（审核/评阅/评分）、学生（选题/提交/查重/答辩）。
- 亮点：与知网查重服务无缝集成；按学院/专业维度批量开通关闭各阶段节点；教学秘书可一键生成归档材料清单。
- 缺点：菜单按"教学秘书/指导教师/学生"三套独立入口设计，同一业务概念（如"成绩"）在三端各有一套页面，
  管理端整体信息架构偏"角色优先"而非"流程优先"，跨角色查看同一学生全流程较麻烦。

### 对标对象 B：强智科技教学微服务平台 · 毕业设计模块

- 来源：[强智科技官网](https://www.qzdatasoft.com/list-15-1.html) 产品介绍页。
- 核心流程：选题管理 → 任务分配 → 进度跟踪 → 成果提交 → 过程指导 → 评审答辩 → 质量监控。
- 角色：教务管理员、指导教师、学生（作为"教学微服务平台"的一个子模块，与教务其他模块共用统一账号体系）。
- 亮点：作为教务大平台的微服务子模块，与学籍/课程/成绩等基础数据天然打通，不需要重复维护学生主档；
  "质量监控"作为独立跨阶段模块贯穿全程（对应本项目"问题预警"）。
- 缺点：公开资料偏市场介绍，具体页面级菜单结构未公开，可验证细节有限（仅作流程阶段命名参考，未作为
  字段级证据来源）。

### 对标对象 C：维普毕业论文（设计）管理系统

- 来源：[维普 vgms.fanyu.com](https://vgms.fanyu.com/) 产品页。
- 核心流程：论文检测（查重）→ 教师审阅 → 论文送审（专家评审，名单抽取+送审+评审+数据分析）→ 数据统计分析。
- 角色：以"检测+送审"为核心卖点，強调第三方专家评审（跨校/跨院系抽取评审专家，回避指导教师本人）。
- 亮点：**专家评审强制回避指导教师**——与本项目"教师评阅"模块里"评阅人不得是该生指导教师（SoD）"的设计
  完全一致，证明本项目该设计是对的；"名单抽取"式送审流程比本项目当前"手动指定评阅人"更自动化。
- 缺点：产品定位偏"检测+评审"垂直环节，不覆盖选题/任务书/答辩等全流程，需要与其他系统配合使用。

### 补充交叉验证（不计入三家正式对标，但独立来源印证同一结论）

- 学术论文《基于 UML 的毕业设计管理系统的分析与设计》（[cnblogs](https://www.cnblogs.com/jingwhale/p/4330630.html)）：
  六大模块——选题管理、进行过程管理（含中期检查+互评）、答辩管理、后期处理、登录管理、系统维护。
- 多篇开源/课程设计毕业论文管理系统（CSDN/阿里云开发者社区等公开源码文章）反复出现的模块清单：
  选题管理、任务书管理、中期检查管理、论文管理、答辩管理、成绩管理——五个阶段性模块，而非按数据实体
  逐一拆分的十几二十个模块。

### 三家（+交叉验证）共同具备的核心能力

1. **按业务阶段分组菜单**：选题(含任务书) / 过程指导(含中期检查) / 成果检查(含查重+评阅) /
   答辩成绩 / 归档统计——五段式或六段式，不会把"查重"和"评阅"拆成与"选题"平级的独立一级菜单。
2. **查重与评阅强绑定成果检查阶段**，而不是与答辩、归档并列的独立顶级功能。
3. **评阅/评审的独立性（SoD）**——本项目已实现，与维普的做法一致，验证正确，无需改动。
4. **导师/教师作为选题-任务书阶段的执行者**，而非独立于选题流程之外的通用"人员管理"模块。
5. **归档与统计作为收尾阶段合并展示**，不是三个平级模块。

### 本项目已有能力 vs 缺失的生产级闭环

- 已有：全部业务闭环（选题/任务书/指导/中期/查重/评阅/答辩/成绩/预警/归档/统计）均已在
  2026-07-08 夜间实现为真实前后端，闭环本身没有缺失。
- 缺失：**菜单信息架构**不符合三家共同做法——本项目按"每个数据实体一个二级菜单"组织（20 个），
  而三家都按"业务阶段"组织（5~7 个）。这是本次要修的问题，不涉及业务逻辑改动。

### 本轮必须补齐（已执行）

将 `frontend/src/config/navPlan.js` 的毕业设计中心从 20 个二级模块合并为 11 个：
毕设看板、毕设批次、毕设学生、题目库、选题管理（以上 5 个是已验收模块，不改）；
导师管理与分配（合并 2→1）、过程指导（合并 3→1，含任务书/指导记录/中期检查）、开题材料（不改）、
成果检查（合并 3→1，含成果提交/查重/评阅）、答辩成绩（合并 3→1，含答辩安排/评分/成绩评定）、
预警·归档·统计（合并 3→1）。全部只改 `navPlan.js` 的菜单树结构（`mod()`/`I()`/`P()` 调用），
**未改动任何页面组件、路由、后端接口**——因为这些要合并的二级模块本来就已经是同一个 Vue 组件的
不同 `?panel=` 标签页，菜单合并后与页面实际结构完全对齐。

### 进入 backlog 的内容

1. 参照对标对象 C（维普）"名单抽取式自动送审"：本项目当前"教师评阅"仍是手动指定评阅人，
   自动抽取分配可作为后续增强（不阻断当前闭环）。
2. 参照对标对象 A（CNKI）"按学院/专业批量开通关闭阶段节点"：本项目当前无此批量开关能力，
   现状是靠 `t_gd_batch.stage_config` 时间轴配置代替，功能等价但操作方式不同，可后续对齐。
3. 题目库、选题管理是否也应参照三家合并进更大的"选题任务书"阶段分组：本轮**未做**，因为这两个
   模块本身内容量大（各 7~11 个三级项）、且是已验收模块，合并会显著增加单个二级菜单的复杂度，
   风险大于收益，留待用户后续决定是否要做更彻底的合并。

### 禁止做成假功能的内容

- 不新增"自动抽取送审专家"等 backlog 项的假按钮/假页面。
- 不因为对标发现"按学院批量开关阶段"能力缺失就臆造一个不接后端的开关 UI。
