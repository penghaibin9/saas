# 三级菜单与工作区导航整改方案

> 文档状态：方案草案，待评审
> 编制日期：2026-08-22
> 适用范围：管理端前台导航、路由、页面工作区与全局搜索
> 实施状态：仅形成方案，尚未修改业务代码

## 1. 方案摘要

当前系统的主要问题不是“三级菜单链接少了参数”，而是把能力清单直接当成了导航菜单。大量操作、筛选条件、统计维度和流程步骤都被包装成三级菜单；部分菜单虽然名称不同，却落在同一个 URL 或同一个页面状态上，导致用户点击后没有明显变化，产生“假三级菜单”的感受。

本方案建议进行一次导航信息架构整改，核心做法是：

1. 将“系统能做什么”与“用户从哪里进入”分开管理。
2. 侧边栏只保留稳定、可独立到达、可恢复的工作区入口。
3. 流程步骤、页签、筛选项、动作按钮留在页面内部，不再伪装成菜单。
4. 每个可见菜单都必须对应唯一且可恢复的页面状态，支持刷新、前进后退、复制链接和新标签页打开。
5. 建立统一的路由注册表、导航元数据和静态审计规则，防止问题再次出现。

方案不主张简单地给所有菜单追加 `?tab=`，也不主张用全局强制重建组件来掩盖状态同步问题。最终目标是让侧边栏成为清晰的“工作区地图”，让页面内部承担具体业务流程。

## 2. 文档关系与边界

本方案是下一阶段的架构提案，与现有文档的关系如下：

- `menu-freeze.md`：记录当前菜单冻结口径。
- `route-freeze.md`：记录当前路由冻结口径。
- 本文档：提出下一版导航与路由模型，不自动废止现有冻结内容。

只有在方案评审通过、迁移清单确认、兼容策略批准后，才应更新冻结文档并进入实施。本次工作只新增本文档，不修改现有业务代码、菜单配置或路由行为。

## 3. 现状审计结论

### 3.1 审计范围

本次审计覆盖：

- 管理端 `NAV_PLAN` 中的可见三级叶子菜单。
- 菜单目标 URL 的重复情况。
- 典型页面对 `tab`、`panel`、`entry`、`action` 等参数的消费情况。
- 路由变化后组件是否同步更新。
- 菜单点击、选中态、刷新、浏览器前进后退等交互。

### 3.2 核心数据

- 可见三级叶子菜单：558 个。
- 完全相同目标 URL 的重复组：19 组。
- 涉及重复入口的可见叶子菜单：41 个。
- 另有多组菜单虽然 URL 参数不同，但页面未消费参数或只在首次创建时消费，运行效果仍然等同于同页。

这意味着重复 URL 只是显性问题，更大的问题是“URL 看似变化，但页面状态没有变化”。

### 3.3 已复现的典型问题

#### 专业分流

“分流批次与分配”“学生志愿与录取结果”“分流统计”三个三级菜单都进入 `/admin/academic-affairs/major-split`。点击后 URL 和主要内容均没有形成稳定区分。

#### 校历管理

从 `?tab=holiday` 切换到 `?tab=makeup` 时，地址栏发生变化，但页面仍显示“新增节假日”和节假日列表。路由参数没有驱动页面内容更新。

#### 排课工作台

从 `?tab=rules` 切换到 `?tab=availability` 时，地址栏变化，但页面仍停留在“排课规则”。页面只在初次创建时读取状态，后续同组件路由变化没有同步。

### 3.4 问题类型

| 类型 | 表现 | 用户感受 | 技术根因 |
| --- | --- | --- | --- |
| 完全同路由 | 多个菜单指向同一个 URL | 点击像没反应 | 多个能力入口没有明确归属 |
| 参数未消费 | URL 变化，内容不变 | 菜单像假的 | 页面忽略 `tab/panel/action` |
| 参数只读一次 | 首次直达正确，页面内切换失败 | 有时能用、有时不能用 | 只在 `created()` 初始化 |
| 动作菜单化 | 导入、导出、生成、通知等成为菜单 | 层级冗长、定位困难 | 把操作按钮当作导航目的地 |
| 维度菜单化 | 按类型、按类别等成为菜单 | 同一报表被拆成许多入口 | 把筛选条件当作页面 |
| 流程步骤菜单化 | 审核、分配、确认等成为并列菜单 | 流程关系不清 | 工作流被平铺为导航树 |
| 重复归属 | 同一页面出现在多个业务组 | 不知道从哪里进入才正确 | 缺少唯一规范入口 |
| 点击补丁 | 同路由点击显示“当前已在…” | 系统在解释问题，而非解决问题 | 依赖临时选中态与提示语 |

### 3.5 根因判断

当前 `navPlan.js` 同时承担了五种职责：

1. 系统能力目录。
2. 左侧可见菜单。
3. 路由事实来源。
4. 全局搜索条目。
5. 权限展示依据。

这五类数据的生命周期和使用规则并不相同。将它们放在一棵树里，必然导致“能力越完整，菜单越臃肿”。

同时，部分页面采用同一组件承载多个视图，却没有把路由状态设计为响应式状态。`AdminAcademicAffairsLayout.vue` 中未按视图状态区分组件实例，许多页面又只在生命周期初始化阶段读取参数，因此查询参数切换无法稳定刷新内容。

## 4. 整改目标

### 4.1 业务目标

- 用户看到的每个三级菜单都代表一个真实、稳定、可理解的目的地。
- 用户能清楚判断自己当前在哪个工作区、正在处理什么对象、下一步能做什么。
- 相同能力只有一个规范入口，其他入口以快捷方式或上下文链接呈现。
- 菜单数量减少，但系统能力不丢失。
- 中国用户界面统一使用自然、明确的中文业务术语。

### 4.2 技术目标

- 一个可见导航叶子对应一个唯一的规范导航标识 `navId`。
- 路由能够完整恢复当前工作区和主要视图。
- 页面在路由变化时可靠同步，不依赖刷新。
- 支持浏览器刷新、前进后退、复制链接、新标签页打开。
- 选中态由路由元数据推导，不由“最后点击了哪个菜单”推导。
- 能通过自动化审计发现重复路由、失效参数和无归属能力。

### 4.3 非目标

本次整改不以以下事项为目标：

- 不重做所有业务页面视觉样式。
- 不改变现有后端权限含义。
- 不一次性重写所有业务模块。
- 不要求所有页面都拆成独立组件。
- 不通过删除能力来实现菜单瘦身。

## 5. 目标信息架构

### 5.1 五类模型分离

```text
能力目录 Capability Catalog
    ├── 权限系统 Permission Mapping
    ├── 全部功能页 All Functions
    └── 全局搜索 Search Index

工作区目录 Workspace Catalog
    └── 左侧导航 Sidebar Navigation

路由注册表 Route Registry
    ├── 深链接与状态恢复
    ├── 菜单选中态
    └── 面包屑与页面标题

页面动作 Page Actions
    └── 新增、导入、导出、生成、审核、发布等

页面视图 Page Views
    └── 页签、流程步骤、统计维度、筛选条件
```

#### 能力目录

回答“系统具备哪些能力”。它可以很完整，允许包含细粒度权限点、动作和查询能力，但不直接决定是否显示在侧边栏。

#### 工作区目录

回答“用户日常从哪里进入工作”。这里只保留高频、稳定、可独立到达的业务目的地。

#### 路由注册表

回答“一个 URL 到底代表什么页面状态”。它是深链接、选中态、标题、面包屑和兼容跳转的统一事实来源。

#### 页面动作

回答“用户在当前对象上可以做什么”。新增、导入、导出、生成、确认、发布等应成为按钮、工具栏动作或批量操作。

#### 页面视图

回答“用户如何查看当前工作区”。页签、筛选、统计维度、流程步骤应由页面内部组件表达。

### 5.2 推荐层级语义

| 层级 | 语义 | 示例 |
| --- | --- | --- |
| 一级 | 业务域 | 教务中心、毕业设计中心、实习中心 |
| 二级 | 工作区或业务对象 | 校历与作息、专业分流、调停课、成绩管理 |
| 三级 | 稳定目的地 | 分流批次、调停课台账、成绩录入、成绩查询 |
| 页面页签 | 同一目的地的视图 | 待处理、已完成、异常记录 |
| 页面步骤 | 同一业务对象的流程 | 设置、志愿、分配、确认 |
| 页面筛选 | 数据观察维度 | 按学院、按年级、按类别 |
| 页面动作 | 对当前对象执行操作 | 导入、导出、生成、发布 |

## 6. 三级菜单准入标准

一个能力只有同时满足以下条件，才适合作为三级菜单：

1. 有明确、独立的用户任务，而不是一个动作或筛选条件。
2. 有稳定 URL，刷新后能够恢复相同语义。
3. 与相邻菜单的主要内容、操作对象或工作流明显不同。
4. 用户有直接进入该页面的实际需求。
5. 能够形成独立的权限、标题、面包屑和帮助说明。
6. 点击后可观察到明确的页面变化。

以下内容原则上不得作为三级菜单：

- 新增、编辑、删除、导入、导出、生成、打印、发布。
- “按某某统计”“按某某查看”等统计维度。
- 一个流程中的短暂步骤。
- 仅用于打开弹窗、抽屉或定位某个控件的入口。
- 与另一个菜单落到完全相同页面且没有独立业务语义的别名。
- 只用于展示提醒数字或状态数量的入口。

### 6.1 判定矩阵

| 判定问题 | 是 | 否 |
| --- | --- | --- |
| 是否可从浏览器地址直接恢复？ | 继续判断 | 页面内部状态 |
| 是否有独立且长期存在的业务对象？ | 继续判断 | 动作/筛选/步骤 |
| 是否值得用户从全局导航直接进入？ | 继续判断 | 页面快捷入口 |
| 是否与兄弟菜单有明显内容差异？ | 可作为三级菜单 | 合并为页签或视图 |
| 是否有唯一规范归属？ | 正式菜单 | 仅保留快捷方式 |

## 7. URL 与页面状态设计

### 7.1 URL 语义规则

- `path`：稳定的业务目的地、业务对象或主要工作区。
- `query`：筛选、排序、分页、时间范围等可选观察条件。
- `hash`：页面内部锚点。
- 动作：通过按钮触发；如确需深链接，可使用受控的 `action`，但不作为菜单目标。
- 弹窗/抽屉：只有在需要分享和恢复时才进入 URL 状态。

### 7.2 推荐示例

```text
/admin/academic-affairs/calendar/events?type=holiday
/admin/academic-affairs/calendar/time-slots
/admin/academic-affairs/major-split/:batchId/choices
/admin/academic-affairs/major-split/:batchId/allocation
/admin/academic-affairs/schedule-change/ledger?status=pending
/admin/academic-affairs/stats/grades?semester=2026-1
```

其中：

- `events`、`time-slots` 是不同工作区，用路径表达。
- `type=holiday` 是事件类型筛选，用查询参数表达。
- `:batchId` 是当前业务对象。
- `choices`、`allocation` 是可恢复的批次工作流视图。
- `status`、`semester` 是筛选条件。

### 7.3 不推荐示例

```text
/calendar?tab=holiday
/calendar?tab=makeup
/calendar?tab=time-slots
/stats?tab=grade
/grade-entry?action=import
```

并不是查询参数本身有问题，而是这些参数承载了完全不同的工作区或把操作伪装成目的地。如果多个视图拥有不同数据源、工具栏、权限或生命周期，应升级为子路由。

### 7.4 不采用全局强制重建作为主方案

不建议简单给所有 `<router-view>` 增加 `:key="$route.fullPath"` 作为主要解决方式。该做法虽然能让部分查询参数切换生效，但会带来：

- 页面状态全部丢失。
- 重复请求和界面闪烁。
- 表格滚动、勾选和草稿被清空。
- 掩盖页面未正确建模路由状态的问题。

正确做法是：独立工作区使用子路由；同一工作区的筛选和页签通过计算属性或路由监听同步。

## 8. 导航与路由元数据模型

### 8.1 能力定义

```js
{
  id: 'academic.schedule.change.export',
  label: '导出调停课台账',
  type: 'action',
  permissionKey: 'academic:schedule-change:export',
  ownerWorkspace: 'academic.schedule-change.ledger'
}
```

### 8.2 工作区导航定义

```js
{
  id: 'academic.schedule-change',
  label: '调停课',
  children: [
    {
      navId: 'academic.schedule-change.ledger',
      label: '调停课台账',
      routeName: 'AcademicScheduleChangeLedger'
    },
    {
      navId: 'academic.schedule-change.apply',
      label: '发起调停课',
      routeName: 'AcademicScheduleChangeApply'
    }
  ]
}
```

### 8.3 路由元数据

```js
{
  path: 'schedule-change/ledger',
  name: 'AcademicScheduleChangeLedger',
  component: ScheduleChangeLedger,
  meta: {
    moduleId: 'academic-affairs',
    workspaceId: 'academic.schedule-change',
    navId: 'academic.schedule-change.ledger',
    viewId: 'ledger',
    title: '调停课台账',
    canonicalPath: '/admin/academic-affairs/schedule-change/ledger'
  }
}
```

### 8.4 快捷入口

快捷入口可出现在工作台卡片、待办、搜索结果和关联页面中，但不重复占用侧边栏位置：

```js
{
  id: 'shortcut.academic.grade.stats',
  label: '查看成绩统计',
  targetRouteName: 'AcademicStatsGrades',
  source: 'grade-management-dashboard',
  canonicalNavId: 'academic.stats.grades'
}
```

快捷入口不参与侧边栏唯一性统计，选中态始终落到其 `canonicalNavId`。

## 9. 交互闭环

### 9.1 从菜单进入

```text
点击真实 RouterLink
  → 路由解析 route meta
  → 定位 moduleId / workspaceId / navId
  → 加载页面或切换子视图
  → 由当前路由计算唯一选中菜单
  → 页面读取筛选参数并请求数据
```

菜单叶子应使用真实 `RouterLink`，不再使用 `javascript:void(0)` 加点击事件模拟跳转。这样才能自然支持：

- 右键新标签页打开。
- 复制链接地址。
- 键盘访问。
- 浏览器默认状态提示。
- 更可靠的无障碍语义。

### 9.2 页面内部切换

页面页签或筛选发生变化时：

1. 更新路由或页面局部状态。
2. 页面通过计算属性、组合式状态或路由监听立即响应。
3. 不改变侧边栏规范选中项。
4. 浏览器前进后退可以恢复上一个视图。

### 9.3 同一页面重复点击

如果用户点击当前已选中的菜单，可选择：

- 保持页面状态，不做操作；或
- 按统一规则滚动到顶部/刷新数据。

不再依赖“当前已在某某视图”的提示语解释同路由问题。

## 10. 分模块整改设计

### 10.1 教务中心

教务中心是本次整改的重点模块，菜单最密集、同页入口和参数视图最多。

#### 教务看板

- 侧边栏仅保留“教务看板”一个规范入口。
- 看板中的待办、预警、统计卡片作为上下文快捷入口。
- 原有多个 `panel` 菜单不再平铺为三级菜单。

#### 校历与作息

建议形成一个二级工作区，内部保留以下稳定目的地：

- 校历事件。
- 作息与节次。
- 教学周设置。
- 校历发布。

节假日、补课日、考试周等属于“校历事件”的类型或页签，不应全部成为侧边栏菜单。

#### 专业分流

建议改为“批次驱动的工作流”：

```text
专业分流
  ├── 分流批次
  └── 统计分析

进入某一批次后：
  设置 → 学生志愿 → 规则与分配 → 结果确认 → 归档
```

“学生志愿”“分配”“录取结果”属于当前批次的流程阶段，应显示为页面步骤导航，而不是全局三级菜单。

#### 调停课

建议保留：

- 调停课台账。
- 发起调停课。
- 审批处理。
- 归档查询。

“冲突检测”嵌入发起流程，“通知”嵌入审批或结果页面，“按某维度统计”进入统一统计页。

#### 排课

建议拆分为：

- 排课批次。
- 排课工作台。
- 课表查询。
- 规则与资源配置。

排课规则、教师可用时间、教室资源、冲突约束可成为“规则与资源配置”内部页签；自动排课、锁定、发布等作为工作台动作。

#### 考勤

建议形成：

- 考勤记录。
- 异常处理。
- 考勤统计。

“按点名类别统计”等全部收敛为统计页维度筛选。

#### 培养方案与教学计划

- 明确“培养方案”与“学期执行计划”的对象边界。
- 方案审核、发布作为方案工作台的状态队列或操作。
- 计划审核、发布作为学期计划工作台的状态队列或操作。
- 不以相同页面的不同按钮状态生成多个菜单。

#### 教学任务

- 保留教学任务批次与任务执行两个核心入口。
- “生成任务”作为批次页面动作。
- “执行进度”和“任务统计”进入统一分析页，通过指标视图切换。

#### 成绩、注册与教务统计

- 成绩管理负责成绩录入、审核、更正等业务操作。
- 注册管理负责注册批次和异常处理。
- 教务统计作为统一分析中心，避免“成绩统计”“注册统计”同时出现在业务组和统计组。
- 业务页面可保留“查看统计”快捷卡片，但只指向规范统计入口。

#### 预警、毕业审核、教材、评价与补考

这些模块应采用同一模式：

- 一个业务工作台。
- 页面内状态队列，如待处理、处理中、已完成。
- 页面内详情和处置动作。
- 一个规范统计/分析入口（确有必要时）。

`dashboard`、`console`、`panel` 不再自动等价于多个侧边栏菜单。

### 10.2 毕业设计中心

- “答辩评分”只保留一个规范入口。
- “我的答辩评分”根据当前身份进入同一页面的个人任务视图，不重复占用菜单。
- “毕设统计报表”和“毕设统计”合并为一个统计中心。
- 延期、优秀成果等作为答辩/成果工作区的状态视图，除非它们确实拥有独立对象、独立权限和长期高频任务。
- 已经能够正确监听路由的过程、风险和归档面板可以保留实现方式，但应统一元数据与命名。

### 10.3 实习中心

- 多类规则配置收敛为“实习规则中心”，使用规则类型页签。
- 各类统计维度收敛为“实习统计”，用维度筛选和可保存视图表达。
- 批次、学生、单位、过程记录等稳定业务对象保留为导航入口。
- 现有能够正确响应面板参数的页面可渐进迁移，不要求一次重写。

### 10.4 就业中心

- 建立“就业跟踪工作区”，统一承载跟进队列、困难帮扶和状态处置。
- `follow-up`、`assistance` 等作为工作区内部队列，不再形成伪菜单。
- 就业统计保留单一规范入口，具体口径作为页面维度。

### 10.5 系统管理及其他模块

系统组织、角色、日志等当前路由监听较完整，可作为整改参考样板。后续重点是统一元数据、规范入口和中文命名，而非无差别重构。

## 12. 已发现的参数状态问题

实施前需逐项建立参数消费清单。当前已发现的高风险入口包括：

- 教务看板的多个 `panel` 入口。
- 校历、作息与节次的 `tab` 入口。
- 教务统计的 `tab` 入口。
- 培养方案、课程、排课、预警、毕业审核、教材等控制台入口。
- 注册、补考、评价等工作台入口。
- 选课与考试页面中被忽略的 `tab`。
- 归档页面中被忽略的 `entry`。
- 教学任务 `open=generate`。
- 排课 `panel=archive`。
- 成绩录入 `action=import`。
- 成绩单 `action=export`。
- 毕业设计看板 `extension=delay/excellent`。
- 实习统计 `dimension`、批次规则 `rule`。
- 就业看板 `panel=follow-up/assistance`。

每一项必须被归类为以下三种结果之一：

1. 升级为独立子路由。
2. 保留为页面内部响应式状态。
3. 删除 URL 参数，改为页面动作或筛选。

不允许继续保留“参数存在但页面不消费”的状态。

## 13. 兼容与迁移策略

### 13.1 旧链接兼容

对于已经使用的旧 URL，提供显式重定向或规范化映射：

```js
{
  from: '/admin/academic-affairs/stats?tab=grade',
  to: '/admin/academic-affairs/stats/grades',
  canonicalNavId: 'academic.stats.grades'
}
```

兼容期内需保证：

- 收藏夹和历史链接仍可访问。
- 旧工作台卡片不会落到空页面。
- 权限校验在重定向前后保持一致。
- 重定向后地址栏显示规范 URL。

### 13.2 菜单迁移

- 第一阶段保留原能力定义，只调整其展示类型。
- 从侧边栏移除的条目转为页面动作、快捷入口、页签或全部功能页条目。
- 为每个移除条目记录“新位置”，确保能力可追溯。
- 快捷入口统一指向规范路由，并指定 `canonicalNavId`。

### 13.3 选中态兼容

迁移期间不得继续依赖 `clickedLeafKey` 作为最终选中依据。可短期保留作为兼容，但规范选中态必须逐步改为：

```text
当前路由 → route.meta.navId → 可见导航树中的唯一节点
```

如果当前路由是详情页或快捷入口，则通过 `canonicalNavId` 回落到所属工作区。

1. 校历与作息：配置型工作区。

- 删除 `clickedLeafKey` 等兼容补丁。

## 15. 测试与验收

### 15.1 静态检查

- 可见菜单的规范 URL 不得重复。
- 每个可见叶子必须存在 `navId` 和有效路由。
- 每个路由最多对应一个规范侧边栏节点。
- 每个能力必须有明确归属：菜单、页面动作、页面视图、搜索或仅权限点。
- 所有声明的路由参数必须有消费方。
- 不允许菜单目标使用 `javascript:void(0)`。

### 15.2 自动化端到端检查

对每个可见叶子菜单执行：

1. 点击后 URL 与内容发生符合预期的变化。
2. 刷新后仍停留在相同工作区和主要视图。
3. 浏览器后退和前进可恢复页面。
4. 新标签页打开有效。
5. 侧边栏始终只有一个正确选中项。
6. 页面标题、面包屑和帮助上下文正确。
7. 无权限用户看不到入口，直接访问也会被正确拦截。

### 15.3 页面状态检查

- 页签变化后内容同步更新。
- 查询参数变化不会遗留上一个视图的数据。
- 详情返回列表时保留合理的筛选和分页。
- 页面动作完成后停留位置符合业务预期。
- 异步加载期间有明确反馈，不将“无变化”误认为加载状态。

### 15.4 验收指标

| 指标 | 目标 |
| --- | --- |
| 可见菜单完全重复规范路由 | 0 组 |
| 声明但未消费的导航参数 | 0 个 |
| 菜单叶子真实路由链接覆盖率 | 100% |
| 刷新、前进后退、新标签页恢复成功率 | 100% |
| 同一页面同时高亮多个菜单 | 0 个 |
| 被移出侧边栏但无新位置的能力 | 0 个 |

## 16. 自动化治理规则

为避免后续继续产生伪菜单，建议在开发和发布流程中加入以下门禁：

### 新增菜单检查

新增三级菜单必须同时提交：

- 业务任务说明。
- 规范 `navId`。
- 路由定义和页面标题。
- 与相邻菜单的差异说明。
- 刷新恢复和权限测试。

### 重复路由检查

构建阶段扫描所有可见叶子。如果两个入口指向同一规范路由，必须显式声明其中一个为快捷入口，否则构建失败。

### 参数契约检查

路由注册表声明每个允许参数的类型、默认值和消费组件。未声明参数不得作为菜单目标，声明后未消费应在测试中失败。

### 中文体验检查

- 用户可见枚举统一通过中文映射层输出。
- 菜单、标题、页签和按钮采用用户任务语言，不直接暴露代码枚举。
- `dashboard`、`console`、`panel` 等技术概念不得直接成为面向用户的文案。

## 17. 风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 菜单减少后用户找不到旧功能 | 使用阻力 | 提供全部功能页、全局搜索、旧位置提示和迁移说明 |
| URL 变化导致收藏失效 | 历史链接中断 | 建立旧路由重定向表并保留兼容期 |
| 页面拆分导致接口重复请求 | 性能下降 | 共享查询层和缓存，不以强制重建代替状态同步 |
| 权限与导航拆分后出现漏控 | 安全风险 | 权限仍以后端和能力目录为准，导航只负责展示 |
| 一次性改动过大 | 回归范围扩大 | 采用三个试点和按工作区渐进迁移 |
| 同名业务概念口径不一致 | 用户困惑 | 在评审阶段建立业务术语表和唯一对象定义 |

## 18. 需要产品评审确认的事项

进入开发前，需要确认以下产品决策：

1. 侧边栏默认叶子数量目标，以及高频入口保留原则。
2. 是否建设“全部功能”页面作为完整能力目录入口。
3. 快捷入口是否允许出现在多个工作台，以及统一视觉标识。
4. 培养方案、教学计划、课程开设计划、教学任务之间的业务对象边界。
5. 统计中心采用统一入口还是按业务域分散入口。
6. 工作流步骤使用顶部步骤条、左侧步骤导航还是页面页签的统一规范。
7. 旧 URL 的兼容周期和移除条件。

## 21. 建议结论

建议将此次问题按“导航信息架构整改”立项，而不是作为零散的菜单跳转缺陷处理。

优先从校历与作息、专业分流、调停课三个典型工作区试点：它们分别覆盖配置型页面、批次工作流和台账审批型页面，能够验证整套模型。试点通过后再按模块渐进推广，可以在控制风险的同时解决根因。

本文档当前仅用于方案评审，尚未批准实施，也未对系统业务代码、菜单配置和路由配置进行修改。
