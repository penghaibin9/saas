## 一、待办（审批任务）

### 1.1 设计原则

- **单表 `t_unified_todo`，所有模块统一生成，禁止各建一套**。任何业务模块（岗位实习申请、毕业设计开题、学生信息更正、导入导出任务等）都不应自行发明一套待办存储结构。
- 去重键：`source_module + source_biz_type + source_biz_id + todo_type + assignee_id`。
- 类型：`APPROVAL / REVIEW / CONFIRM / RISK / MATERIAL / IMPORT / EXPORT / ARCHIVE / REMINDER`。
- 多端同步：PC 工作台、教师小程序待办、学生小程序待办**读同一张表**；`assignee_context_id` 关联当前身份，保证"切身份看到对应待办"。
- 与流程联动：`t_workflow_task` 生成时同步生成 `t_unified_todo`（`action_url` 指向处理页）。

依赖表：见冻结总册中的 `t_unified_todo`、`t_workflow_task` 表。

## 二、消息中心

### 2.1 设计原则

- **消息 ≠ 待办**：待办必须处理，消息只需知道。
- `t_message_template`（模板：编码/标题模板/内容模板/渠道/是否回执）+ `t_unified_message`（站内信实例：接收人/已读/回执/action_url）+ `t_message_channel_log`（短信/微信/企微/钉钉下发回执，append-only）。
- 渠道：站内信 / 学生小程序 / 教师小程序 / 短信 / 企微·钉钉·邮件（预留）。
- 场景：提交成功、退回修改、审核通过、审批驳回、材料补充、截止提醒、打卡异常、风险升级、归档缺失、模块即将到期/已到期、导出完成。

依赖表：见冻结总册中的 `t_message_template`、`t_unified_message`、`t_message_channel_log` 表。

### 2.2 接口清单与联调页面

## 三、催办

| 项 | 内容 |
|---|---|
| 使用场景 | 辅导员/学院管理员对逾期未处理的审批任务、未提交材料的学生发起催办（miniapp 学院管理员按钮键 `urge.send`） |
| 建议实现方式 | 催办本质是"生成一条新的提醒类消息"（`t_unified_message`，场景=截止提醒/材料补充）或"生成一条 `REMINDER` 类型待办"，具体走消息还是待办（或两者都生成），待后端确认 |
| 依赖表 | 见冻结总册中的 `t_unified_message`、`t_unified_todo` 表 |
| 联调页面 | PC：审批中心批量催办（`approval` 模块 mock 门面已有批量提醒相关方法，具体方法名待与前端 `approval.api.js` 核对）；miniapp：学院管理员身份 `urge.send` 按钮 |

- [ ] 催办功能已实现（走消息或待办，具体方式已与后端确认并记录）。
- [ ] 消息模板（`t_message_template`）覆盖共享底稿列出的场景：提交成功、退回修改、审核通过、审批驳回、材料补充、截止提醒、打卡异常、风险升级、归档缺失、模块即将到期/已到期、导出完成。

- [ ] 冒烟用例：service-apply 服务申请提交 → my-applications 我的申请列表能查到新记录 → 教师端能看到对应审批待办（如 needApprove=true，对齐 `docs/05-数据接口权限与安全/api/08-后端联调检查清单.md` 冒烟 11）；weekly-report 周报提交 → 教师端周报列表能看到新提交 → 教师退回（原因<5字应拦截，≥5字应成功）且学生端能看到退回提醒（对齐冒烟 12）。
