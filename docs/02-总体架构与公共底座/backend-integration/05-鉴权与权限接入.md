## 一、登录 / 会话策略

| 项 | 策略 | 依赖表 |
|---|---|---|
| 会话载体 | JWT 或 session（二选一，待后端确认；共享底稿未拍板具体实现方式，本文档不替后端做技术选型） | `t_user_login_log`、`t_user_credential` |
| PC 会话超时 | 30 分钟无操作自动失效，超时前 5 分钟弹窗预警（前端已有预警 UI，服务端需保证 Token/session 确实在 30 分钟无请求后失效） | — |
| 移动端会话有效期 | 7 天 | — |
| 并发会话数 | 最多 3 个，第 4 个登录会导致最早会话被踢下线，下次请求返回 `UNAUTHORIZED` | 需要服务端维护会话/Token 有效性登记（具体存储方案——DB 表或 Redis——待后端确认） |
| 首次登录强制改密 | `mustChangePassword=true` 期间仅放行改密接口，其余业务接口一律拦截 | `t_user_credential` |
| 会话失效响应 | 401（`UNAUTHORIZED`，未登录/Token 失效）；419（`SESSION_EXPIRED`，会话超时/CSRF 失效） | — |

> 会话与身份相关接口以历史冻结 `docs/05-数据接口权限与安全/api/01-认证租户与当前上下文API.md` 为权威：登录 1.1、登出 1.2、刷新 Token 1.3、当前用户 1.4。

## 二、tenant_id 从上下文解析

- `tenant_id` **前端永不传递**，后端从登录会话/Token 解析当前租户，在数据访问层（SQLAlchemy 会话级）统一注入 `WHERE tenant_id = :currentTenant` 过滤。
- 跨租户访问一律拒绝，返回 `TENANT_NOT_FOUND` 或 `NO_PERMISSION`。
- 唯一例外：平台运营端（`/api/v1/platform/*`）可查看多租户数据，但必须：
  1. 当前角色为 `PLATFORM_OPERATOR`；
  2. 拥有对应平台权限点；
  3. 每次跨租户查询/操作写入 `t_security_audit`。
- 依赖表：见冻结总册中的 `t_tenant`、`t_user` 表。

## 三、currentRoleCode + activeContextId

- 一个用户可能拥有多个身份（例如同一教师同时是辅导员+教务老师），登录后返回全部可用身份列表（历史冻结 1.6 我的身份列表）。
- 每个客户端（PC/学生小程序/教师移动端）激活**一个** `activeContextId`，对应一个 `currentRoleCode` 与一个 `dataScope`，**权限不跨身份合并**。
- 切换身份：`POST /api/v1/authz/contexts/{contextId}/activate`（教师移动端专属路径 `/api/v1/teacher-mobile/contexts/{id}/activate`）。切换后菜单、待办、数据范围、按钮、首页全部按新身份重新加载，并写身份切换审计。
- 前端通过请求头或会话携带 `activeContextId`（具体载体——请求头 `X-Active-Context-Id` 或会话内绑定——二选一，待后端确认），后端据此确定 `currentRoleCode` 与 `dataScope`，**服务端为最终裁定方，前端不参与计算**。
- 依赖表：见冻结总册中的 `t_user_context`、`t_user_active_context` 表。

### 4.1 建议聚合结构（若采纳新增聚合接口）

## 五、后端必须做服务端二次鉴权与数据范围过滤

**前端判断不可信** —— 以下是硬性要求，不因前端已有权限判断逻辑而放宽：

- 前端权限判断入口（`frontend/src/modules/workflow/context/permission.context.js` 暴露的 `canAccessPage`/`canClickButton`/`canViewMenu`/`getDataScope`/`hasRole`/`hasAnyPermission`/`filterMenusByPermission`/`filterActionsByPermission`）**仅用于前端体验优化**（隐藏菜单/按钮/字段），不能作为后端安全验收依据。
- 服务端权限校验链（对齐历史冻结总册 §五）：

```text
authMiddleware(登录) → tenantMiddleware(租户) → moduleEntitlementMiddleware(模块授权)
→ featureFlagMiddleware(功能开关) → permissionMiddleware(权限码) → dataScopeMiddleware(数据范围)
→ sodMiddleware(职责互斥) → auditMiddleware(留痕)
```

- 每个业务接口必须完整走完上述链路，**任何一环缺失都视为安全缺陷**，不能因为"前端已经隐藏了这个按钮"而跳过服务端校验。
- 数据范围判定优先级（对齐 `docs/05-数据接口权限与安全/api/05-接口鉴权与数据范围.md` §四.1）：
  1. 服务端权限校验链完整实现；
  2. 前端隐藏仅为体验优化；
  3. 每个业务接口在 `docs/05-数据接口权限与安全/api/02-PC管理端接口契约.md`/`03-miniapp接口契约.md` 中均标注"权限要求"与"数据范围要求"，后端实现须与文档一致。

## 六、CSRF 与 X-Request-Id

| 项 | 约定 |
|---|---|
| CSRF 保护方法 | `POST`、`PUT`、`PATCH`、`DELETE`（`GET` 不受保护） |
| CSRF 请求头 | `X-CSRF-Token`，客户端从登录响应或专用接口获取后每次写请求携带；校验失败返回 `SESSION_EXPIRED`（419） |
| 请求追踪头 | `X-Request-Id`，客户端可自行生成（建议 UUID）随请求发送；后端生成/透传 `traceId` 并在响应体回传 |
| 幂等 | 写操作携带 `requestId`（业务层幂等键，区别于链路追踪头 `X-Request-Id`），同一 `requestId` 重复提交但 payload 不同返回 `IDEMPOTENCY_CONFLICT` |
| 乐观锁 | 审批类写操作携带 `version` 字段，与服务端当前版本不一致返回 `APPROVAL_VERSION_CONFLICT`（409） |

## 七、越权返回码

| 场景 | 返回码 | HTTP | 前端表现 |
|---|---|---|---|
| 无对应权限码（菜单/页面/按钮/接口层面均无权限） | `NO_PERMISSION` | 403 | 页面级跳转 `/security/403`；按钮级前端隐藏（体验层）+ 服务端仍需二次校验 |
| 有权限码但访问的具体资源不在自己数据范围内 | `NO_DATA_SCOPE` | 403 | 拦截提示"当前身份无权查看该数据" |
| 有权限码、数据范围内确实没有数据 | `SUCCESS` + 空列表 | 200 | 正常空状态渲染，不视为越权 |
| 模块未授权（licenseContext 预留） | `MODULE_NOT_AUTHORIZED` | 403 | 未授权占位页 |
| 模块到期只读 | `MODULE_EXPIRED_READONLY` | 403 | 只读态横幅提示，隐藏写操作按钮 |
| 未登录/Token 失效 | `UNAUTHORIZED` | 401 | 跳登录/`/security/401` |
| 会话超时/CSRF 失效 | `SESSION_EXPIRED` | 419 | `/security/419` 重新登录 |

> 判定标准（区分"空列表"与"越权"）：**能正常访问但范围内确实没有数据 → 空列表；越权尝试访问不属于自己范围的具体资源 → `NO_DATA_SCOPE`**（待后端确认最终采纳标准，本轮统一按此原则执行）。
