# 02 · 发布前检查清单

> 每次要把新版本发到线上**之前**，逐条勾。目的是「别把坏的版本发上去」。

---

## A. 代码与构建

- [ ] 确认要发布的是**正确的代码版本**（如果用 git：`git status` 干净、`git log` 最新一条是你要发的）。
- [ ] PC 前端 `cd frontend && npm run build` **构建成功、无报错**（看最后是否有 `built in ...`，没有红色 error）。
- [ ] 小程序 `cd miniapp && npm run build:h5` **构建成功**（出现 `DONE Build complete`）。
- [ ] （要发微信小程序时）`npm run build:mp-weixin` 成功，产物在 `miniapp/dist/build/mp-weixin/`。

---

## B. 构建产物自检（本地/预览环境）

- [ ] PC：`cd frontend && npm run preview`，打开预览地址，**登录页、首页、至少一个业务页**都能打开、不白屏。
- [ ] 刷新子页面**不 404**（本地预览也应正常）。
- [ ] 浏览器 F12 控制台**没有大片红色报错**（个别 mock 提示可忽略，但 JS 报错要留意）。
- [ ] 页面上的学校名称/Logo/标题显示正常（来自品牌配置，不是乱码）。

---

## C. 发布准备

- [ ] 已想好发布方式：直接覆盖 or 版本目录 + 软链（推荐后者，见 `docs/deploy/09`）。
- [ ] **记下当前线上版本**（目录名/时间戳/版本号），万一要回滚用。
- [ ] Nginx 配置没有临时改动残留（如需改，先 `nginx -t`）。
- [ ] 选在**低峰期**发布（比如没人演示、没人用的时候）。

---

## D. 沟通

- [ ] 如果是给学校演示/正在用，先**通知相关人**「即将更新，可能短暂波动」。
- [ ] 确认发布后由谁负责验证（一般就是你，按 `03-发布后检查清单.md` 走一遍）。

---

## 特别提醒（当前阶段）

- 当前是 mock 数据，发布**不涉及数据库、不涉及数据迁移**，风险很低。
- **不要**趁发布顺手去改 `frontend/src/`、`miniapp/`、数据库文档——发布只做「build + 部署」。
- 后端接入后，这里要新增：数据库迁移是否已执行、后端服务是否就绪、接口联调是否通过等（现在不用）。
