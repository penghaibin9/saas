## HF-01｜教师退回审批

**当前**：审批中心 → 退回 → 填原因 → 确认；当前真实链实际走 reject，前端又展示 RETURNED。

**成熟厂家目标**：教师在详情页看完关键事实后，点击“退回修改”，填写原因/补交要求，提交后自动进入下一条；学生立即看到“修改并重新提交”待办。

**成熟度逻辑**：成熟厂家级必须做到状态语义不混淆、动作前后事实可追溯、处理后连续下一条。

### 具体实现

1. 底层先完成 P0-01：独立 `/return` 状态机与 allowedActions。
2. 退回弹窗显示：退回对象、当前节点、原因、需补交材料/修改项、建议完成期限；原因必填。
3. 提交锁；409 显示“该单已被其他人处理”，刷新后自动移出当前队列。
4. 成功后 toast 只作辅助，详情区先显示服务端新状态，再自动加载当前筛选队列下一条。
5. 学生端收到 todo deep link 到具体申请记录，页面展示退回原因、修改项、材料差异和重新提交按钮。

### 完成验收

RETURN/REJECT 行为完全不同；处理一条后 1 秒级进入下一条；学生无需从消息中心自行找单。

## HF-10｜处理大量审批

**当前**：当前小程序待办无真实分页；PC 审批有部分分页主链但批量/历史仍混内存；处理单条后缺少成熟的连续工作队列。

**成熟厂家目标**：PC 左侧待办队列 + 右侧详情；移动端单条详情 + 下一条。批准/退回/驳回后自动进入当前筛选队列下一条，批量动作支持部分失败。

**成熟度逻辑**：成熟厂家级目标是减少“列表↔详情”往返，让老师连续处理几十条不丢上下文。

### 具体实现

1. 服务端队列 API 支持 filter/sort/page/cursor，返回 total 和 nextId/prevId；按 urgency+submitTime 稳定排序。
2. PC 宽屏使用 queue mode：左 320px 队列，右详情；窄屏退化为详情+底部上一条/下一条。
3. 进入详情时把当前 filter snapshot/queueCursor 保存在 URL 或 store；动作成功后移除当前项并预取 next detail。
4. 409/已处理项标记 stale，自动刷新该项并继续下一条，不中断整队列。
5. 批量通过/退回返回逐条结果；失败项留在队列并可一键筛选“本次失败”。
6. 可选键盘快捷键仅在可访问性校验后启用，危险动作不能无确认快捷触发。

### 完成验收

连续处理20条不返回列表、不丢筛选；部分失败明确；每条服务端事实刷新一致。

## 高频任务统一 UX 规则

1. **任务入口必须直达业务对象。** 不允许待办跳到泛列表、消息中心或首页。
2. **处理后不让用户重新找下一条。** 审批/批阅/异常处理进入连续工作队列。
3. **筛选上下文必须保留。** 返回列表、上一条/下一条、刷新后保持当前业务范围。
4. **高风险动作必须服务端 allowedActions 驱动。** 前端不猜状态。
5. **所有写操作有明确处理中、成功、部分成功、失败、409 冲突。** 不能只有 toast。
6. **长表单不允许无提示丢失。** dirty guard 是统一底座，不按页面各写一套。
7. **材料类任务必须区分“文件上传成功”和“业务版本已提交审核”。**
