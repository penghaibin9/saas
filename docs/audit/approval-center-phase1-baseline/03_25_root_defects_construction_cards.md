## P0

### P0-01｜审批“退回”被错误实现为“驳回终止”

**影响面**：PC 审批详情/待办、教师小程序审批、审批适配层、后端状态机

**已确认事实**：`frontend/src/services/http/adapters.js` 的 returnTask 调 reject；教师小程序 `miniapp/src/services/realApi.js` 也将非 approve 统一调用 reject；后端 reject 写 `REJECTED` 终态，而前端又展示/合成 `RETURNED`。

**根因**：RETURN 与 REJECT 没有共享、可执行的跨端状态合同；前端用显示语义弥补后端端点缺失。

**最优施工方案**：

1. 后端新增正式 `POST /api/v1/approvals/tasks/{task_id}/return`，RETURN=退回申请人可修改重提，REJECT=终止原流程。
2. return/reject 都校验 tenant、dataScope、assignee、currentStatus、`version`、原因长度；使用乐观锁，旧 version 返回 409。
3. 统一响应 `{status,instanceStatus,version,allowedActions,auditId,nextTodo}`；前端不得再本地合成状态。
4. 退回同时生成申请人补交/修改待办与消息；驳回只生成终止通知，不生成重提入口。
5. PC/小程序共用状态枚举和动作文案；禁止“原因太短就自动填默认驳回理由”。

**专项测试**：同一记录分别 RETURN/REJECT/APPROVE/RESUBMIT；核对数据库、轨迹、消息、申请人按钮、处理人待办；并发旧 version=409；跨租户/越权=403。

**验收标准**：四端状态完全一致；任何页面刷新后不得出现 RETURNED/REJECTED 互换；审计能明确区分 RETURN 与 REJECT。

**施工禁区**：不得用隐藏按钮代替后端权限；不得用 toast/内存数组制造成功；无法确认的调用链先搜索证明再改。

### P3-02｜管理端仍存在 `transition: all`

**已确认事实**：共享壳层可见多处 `transition: all 0.12s`。

4. 用 Performance 面板测大型列表/侧栏交互，避免 layout thrash。

**专项测试**：菜单、搜索、主题、弹窗、列表滚动；reduced motion。

**验收标准**：交互视觉不退化，主线程/布局抖动不增加，代码不再出现未经豁免的 transition:all。

**施工禁区**：不得用隐藏按钮代替后端权限；不得用 toast/内存数组制造成功；无法确认的调用链先搜索证明再改。
