## 0. 通用约定（适用于本文所有状态机）

1. **审批复用 Workflow**：凡"是否走Workflow审批=是"的转移，均为新 `workflow_code` + `node_code` 序列，任务/实例落 `t_workflow_instance` / `t_workflow_task`，待办写 `t_unified_todo`；节点流转逻辑在学工 service 内实现。已处理任务再审 → HTTP 409 / `409001 APPROVAL_VERSION_CONFLICT`（乐观锁 version）。
2. **通知一律走统一消息**：消息类型仅允许需求输入 §6 的 8 种：`WORKFLOW_TODO / WORKFLOW_RESULT / RISK_ALERT / DEADLINE_REMINDER / STATUS_CHANGED / RETURNED_NOTICE / PUBLISHED_NOTICE / ARCHIVE_NOTICE`，写 `t_unified_message`（receiver_id 精确接收人）；待办写 `t_unified_todo`。任何模块不得自建消息表。
3. **审计**：凡"是否写审计=是"的转移，调用 `app.services.audit_log.record(action, resource, detail, result)` 落 `t_security_audit_log`；域级留痕另落 `t_affairs_*_audit_trail`（append-only）。
4. **进入学生360**：指写 `t_student_stage_event`（StageEvent 时间线数据源）+ 域记录本身可被 mobile teacher `student/{id}` 聚合端点读取。表内"进360=是"的转移必须同步写 StageEvent。
5. **非法转移统一防护**（各状态机"防护"小节为业务补充，以下为全局规则）：
   - 状态不允许该操作 → HTTP 409 / `409001 DATA_CONFLICT`，message 说明当前状态与允许的操作；
   - 角色无权限点 → HTTP 403 / `403001 NO_PERMISSION`；
   - 有权限点但目标资源不在数据范围内 → HTTP 403 / `403002 NO_DATA_SCOPE`，并写 `PERMISSION_DENIED` 审计；
   - 重复提交（同 request_id 不同 payload）→ HTTP 409 / `409001 IDEMPOTENCY_CONFLICT`；
   - 所有写操作服务端重新校验状态 + 权限点 + 数据范围三层，前端按钮隐藏仅为体验层。
6. **超时自动转移**：由统一定时任务框架执行（建议每 5~15 分钟一轮 + 每日 0 点批任务），定时转移同样写审计（created_by=SYSTEM）、发统一消息，且**不走 Workflow**。
7. **终态约定**：`ARCHIVED` 为所有业务的最终只读态，仅允许导出（走 `/api/v1/export/domain/*` 水印管线），任何写操作 → 409。`REJECTED / CANCELLED` 为业务终态，仅可被归档批次收编为 `ARCHIVED`。
8. **枚举来源说明**：请假、困难认定、违纪处分（含解除）、风险预警四个状态机的枚举在需求输入 §2.5/§2.6/§2.8/§2.9 中已明确，本文严格照抄；资助、谈话、调宿、宿舍检查异常、活动、归档五类需求输入只给了流程未给枚举，本文按同一命名风格推导并**标注"[推导枚举，需现场确认]"**，冻结前须经甲方确认（对应需求输入 §9 现场确认清单）。

**角色缩写**（8 角色，下同）：处=学工处管理员；院=学院学工管理员；辅=辅导员；班=班主任；心=心理老师；宿=宿管；资=资助老师；生=学生。

### 1.1 非法转移防护（409/403 规则）

- 非 DRAFT/RETURNED 状态提交或编辑 → 409 DATA_CONFLICT（"当前状态不允许编辑/提交"）。
- 审批节点与当前状态不匹配（如学院审批一个 COUNSELOR_REVIEW 单）→ 409；同一任务被并发审批 → 409 APPROVAL_VERSION_CONFLICT。
- 学生对非本人请假单做任何操作 → 403 NO_DATA_SCOPE（student_id 一律从 token 取，路径传他人 ID 直接拒绝并审计）。
- 辅导员审批非负责班级学生请假 → 403 NO_DATA_SCOPE + PERMISSION_DENIED 审计。
- 存在时间区间重叠的在途请假单（SUBMITTED~APPROVED/OVERDUE）再次提交 → 409 DATA_CONFLICT（重复提交拦截）。
- APPROVED 之前发起销假/续假、CLOSED 之后再销假 → 409。
- demo-school 租户任何写操作 → 403（只读锁，引导 sandbox）。

### 1.2 超时自动转移（定时任务）

| 触发 | 条件 | 动作 |
|---|---|---|
| 到期前提醒 | APPROVED 且 结束时间-24h（可配） | DEADLINE_REMINDER→学生（提醒销假）；不改状态 |
| 逾期未销 | APPROVED 且 now > 结束时间+宽限期（默认 4h，规则中心可配） | 状态→OVERDUE；生成风险预警记录（来源=请假异常，见 §6）；RISK_ALERT→辅导员；写审计 |
| 逾期升级 | OVERDUE 持续 ≥48h 无处置记录 | 风险等级上调 + RISK_ALERT→学院学工；不改请假状态 |
| 审批超时催办 | *_REVIEW 停留 ≥24h | DEADLINE_REMINDER→当前审批人；不改状态 |

### 2.1 非法转移防护

- 批次未开放（NOT_STARTED）或已截止后提交 → 409 DATA_CONFLICT（"批次未开放/已截止"）。
- 同批次重复申请 → 409（batch_id + student_id 唯一约束兜底）。
- 家庭经济字段为强敏感：无 `studentAffairs.aid.sensitiveView` 权限点查看完整值 → 403 NO_PERMISSION；有权限查看必须写 SENSITIVE_VIEW 审计（不写审计的读取路径不得存在）。
- 班级评议/初审等节点越级操作（如学院直接审 SUBMITTED）→ 409；跨学院审批 → 403 NO_DATA_SCOPE。
- ADJUST_REVIEW 仅允许从 APPROVED 发起；REJECTED 后调整 → 409（应走下一批次重新申请）。

### 2.2 超时自动转移

| 触发 | 条件 | 动作 |
|---|---|---|
| 批次截止 | now > 批次截止时间 | DRAFT 未提交单标记失效（终为 CANCELLED 语义，批次报表剔除）；DEADLINE_REMINDER 截止前 48h 提醒学生 |
| 公示期满 | PUBLICITY 满 N 天（默认 5 个工作日，可配）无未结异议 | 自动→APPROVED，入困难库，写审计与 StageEvent |
| 年度复核 | 每学年初（批次配置） | APPROVED 存量记录批量生成 ADJUST_REVIEW 待办→辅导员（WORKFLOW_TODO） |

| DORM_REVIEW | 驳回（床位不符/无空位） | 宿 | REJECTED | 是 | WORKFLOW_RESULT→学生 | 是 | 否 |
| APPROVED | 执行迁移（原床释放+新床占用，事务原子） | 系统/宿 | COMPLETED | 否 | STATUS_CHANGED→学生+两侧宿管 | 是 | 是（宿舍异动记录） |
| COMPLETED / REJECTED / CANCELLED | 批次收编归档 | 处 | ARCHIVED | 否 | ARCHIVE_NOTICE | 是 | 否 |

### 8.1 非法转移防护

- 目标床位在 DORM_REVIEW 通过与执行迁移之间被占用 → 执行时 409 DATA_CONFLICT（床位乐观锁 version），单据回 DORM_REVIEW 重选。
- 同学生存在在途调宿单再次发起 → 409。
- 宿管仅可审批目标床位在**负责楼栋**内的单据（DORM_BUILDING scope，见 §14），越栋 → 403 NO_DATA_SCOPE。
- 性别与楼栋规则不符 → 422 VALIDATION_ERROR（提交时即校验）。

### 8.2 超时自动转移

- DORM_REVIEW 停留 ≥48h → DEADLINE_REMINDER→宿管；APPROVED 后 7 天未执行迁移 → 自动 CANCELLED（床位预留释放）+ STATUS_CHANGED→学生。

## 9. 宿舍检查异常状态机（13A-11）

状态枚举 **[推导枚举，需现场确认]**：`REGISTERED / PROCESSING / ESCALATED / CLOSED / ARCHIVED`
覆盖：卫生/安全/违禁品/夜不归宿等检查异常（落 `t_cs_dorm_exception` 扩展，检查任务本身不设状态机，任务=计划+记录）。

| （检查中） | 登记异常（类型/房间/涉及学生/照片） | 宿（负责楼栋） | REGISTERED | 否 | STATUS_CHANGED→辅导员（异常同步） | 是 | 否 |

### 9.1 非法转移防护

- 宿管跨楼栋登记异常 → 403 NO_DATA_SCOPE。

- 涉及学生不在登记房间在住名单 → 422（登记时校验，允许"外来人员"类型豁免）。

### 9.2 超时自动转移

- REGISTERED ≥24h 无人认领 → DEADLINE_REMINDER→辅导员；≥48h → 自动 ESCALATED（生成风险记录，来源=宿舍异常）。
- 夜不归宿同一学生 30 天内 ≥3 次 → 自动生成风险记录并把当前异常单 ESCALATED。

## 14. 与既有 t_teacher_student_scope 机制的映射

### 14.1 既有机制（不动）

- 表：`t_teacher_student_scope(teacher_key, role_code, scope_type=CLASS/COLLEGE/STUDENT/ADVISOR, ref_value, status)`。
- 统一函数：`resolve_teacher_scope(user)` → mode=SCOPED/ADMIN_TENANT/TENANT_FALLBACK + classNames/studentNos/collegeNames/advisorNames；`scope_match_row`；`can_teacher_view_student`（越权 403 + 审计）。
- 原则：**看得见 = 能处理**——列表过滤与写操作校验共用同一 scope 函数。

### 14.2 学工角色 → scope 行映射

| 学工角色 | 主 scope_type | ref_value | 说明 |
|---|---|---|---|
| 学工处管理员 | （无行，走 ADMIN_TENANT） | — | resolve 返回 mode=ADMIN_TENANT，租户内全量 |
| 学院学工 | COLLEGE | 学院名/编码 | 既有类型直接复用 |
| 辅导员 | CLASS（可多行） | 班级名 | 与 t_class.counselor_id 双源；以 scope 表为准，班级绑定变更时同步写 scope 行 |
| 班主任 | CLASS | 班级名 | role_code=HEAD_TEACHER 区分，权限点集合不同（无审批终审） |
| 心理老师 | **PSY_STUDENT（新增）** | student_no | 授权心理学生清单；授权/回收由学工处操作并审计 |
| 宿管 | **DORM_BUILDING（新增）** | 楼栋编码 | 负责楼栋；房间/床位/在住学生经楼栋反查得出学生范围 |
| 资助老师 | **FUNDING_BIZ（新增）** | 项目类型码或 ALL | 资助业务范围：命中"存在资助业务记录的学生"，而非静态学生名单 |
| 学生 | （不入表） | — | 学生走 mobile 端，student_id 恒从 token 取，SELF 范围 |

### 14.3 新增 scope_type 语义与解析规则

1. **DORM_BUILDING**：`ref_value=楼栋编码`。解析时 `resolve_teacher_scope` 追加 `dormBuildings[]`；学生匹配 = 该生当前在住床位（t_cs_dorm_record/排宿结果）属于楼栋集合。用于：调宿 DORM_REVIEW 审批、检查任务、异常登记、在假名单只读。跨楼栋 → 403 NO_DATA_SCOPE。
2. **PSY_STUDENT**：`ref_value=student_no`（逐生授权，不支持班级/学院通配，防止心理数据范围扩散）。解析追加 `psyStudentNos[]`；仅作用于心理视图/心理类风险/心理类谈话全文。授权行的增删本身写 PERMISSION_CHANGE 审计。
3. **FUNDING_BIZ**：`ref_value ∈ {SCHOLARSHIP, GRANT, WORK_STUDY, LOAN, TUITION_REDUCTION, TEMPORARY_AID, GREEN_CHANNEL, ALL}`。动态范围：学生集合 = 在授权项目类型下存在申请/在库记录的学生（含困难库）。资助老师对范围内学生仅见"资助视图"字段集，不联带心理/处分明细。

### 14.4 需求书统一函数的落位（封装，不另起炉灶）

| 需求书函数 | 实现方式 |
|---|---|
| getCounselorScope(user) | = resolve_teacher_scope(user) 过滤 role_code∈{COUNSELOR,HEAD_TEACHER} 的行 |
| getStudentAffairsScope(user) | = resolve_teacher_scope(user) + 新三类 scope_type 的解析扩展，输出 {mode, classNames, collegeNames, studentNos, dormBuildings, psyStudentNos, fundingBizTypes} |
| canAccessAffairsStudent(user, studentId) | = can_teacher_view_student 扩展四路判定为七路（+楼栋在住、+心理授权、+资助业务命中），失败 403 + 审计 |
| filterAffairsStudentsByScope(query, user) | = 列表查询统一注入 scope 条件（与写校验共用同一解析结果，保证"看得见=能处理"） |
| assertCounselorCanAccessStudent / assertCanApproveWorkflow | = 写操作与审批前断言封装；审批断言额外校验"当前节点 node_code 允许的角色 + 学生在 scope 内"双条件 |

### 14.5 迁移与治理

- 新增三类 scope_type 仅是 `scope_type` 枚举扩展 + 解析函数扩展，**不改表结构**；Alembic 无 DDL（枚举为字符串列）。
- scope 行的创建入口：学工处/学院学工在权限管理页维护（复用现有平台/系统模块），每次变更写 PERMISSION_CHANGE 审计。
- demo-school 租户 scope 行随只读锁不可改；sandbox-school 每晚重置为演示剧本预置行。
- 兜底：教师无任何 scope 行且非 ADMIN → mode=TENANT_FALLBACK 仅用于既有六域兼容；**学工中心接口不接受 TENANT_FALLBACK**（返回空列表 + NO_DATA_SCOPE 语义按 04 文档 §三判定），倒逼授权数据补齐。
