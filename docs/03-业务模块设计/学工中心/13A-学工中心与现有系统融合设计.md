# 13A-学工中心与现有系统融合设计

> 依据：`_13-需求输入-V1.1.md`（唯一需求来源）与 `_13-现有系统集成事实速查.md`（集成事实，以代码为准）。
> 定位：学工中心（13A）是平台的业务模块，不是独立系统。本文件逐对象回答：读什么 / 写什么 / 复用哪些函数与表 / 需要扩展什么 / 禁止做什么 / 迁移步骤。
> 本文档只做设计，不写代码、不改路由、不改数据库、不提交 git。

---

## 0. 融合总原则

1. **主档只此一份**：学生身份、学籍、班级、专业以 `t_student_profile` 为唯一事实源，13A 一律外键引用 `student_id`，禁止冗余拷贝可变字段（姓名/班级等展示字段查询时 JOIN 获取）。
2. **审批只走 Workflow**：13A 所有审批 = 新 `workflow_code` + `node_code` 序列，实例与任务落 `t_workflow_instance` / `t_workflow_task`，待办进 `t_unified_todo`，不自建审批表。
3. **通知只走统一消息**：一律写 `t_unified_todo` / `t_unified_message`，消息类型限定 WORKFLOW_TODO / WORKFLOW_RESULT / RISK_ALERT / DEADLINE_REMINDER / STATUS_CHANGED / RETURNED_NOTICE / PUBLISHED_NOTICE / ARCHIVE_NOTICE。
4. **范围只走 scope 机制**：`getCounselorScope` 等需求函数 = `resolve_teacher_scope` / `can_teacher_view_student`（`app/services/mobile_teacher_service.py`）的封装扩展，"看得见=能处理"。
5. **敏感数据只走 Security 既有管线**：`*_encrypted` 存储 + 出口脱敏 + `audit_log.record` 审计 + `t_export_task` 水印导出。
6. **既有骨架优先扩展**：`t_cs_leave`（请假）、`t_cs_discipline`（处分）、`t_cs_mental_record`（心理）、`t_cs_dorm_record/exception`（宿舍）已存在，13A 在其上扩展或以新表引用，不平行再建。
7. **新表命名**：`t_affairs_*`；API 前缀 `/api/v1/student-affairs/*`（PC）、`/api/v1/mobile/affairs/*`（学生）、`/api/v1/mobile/teacher/*` 追加（教师）；PC 路由 `/admin/student-affairs/*`；权限点 `studentAffairs.<biz>.<action>`。
8. **统一响应与错误码冻结**：`{code,bizCode,message,data,traceId,timestamp}`；409001（重复/版本冲突/幂等冲突）、403001/403002、404001、422001 按既有语义使用，业务错误绝不 500。

## 1. 与 Student 学生中心的融合

### 1.1 读什么
- `t_student_profile`：student_no / real_name / college_id / major_id / class_id / grade / current_stage / student_status / id_card_encrypted。13A 所有列表、详情、画像的学生基础信息均从此读取。
- `t_student_contact`：联系方式与监护人信息，读取时强制走既有脱敏出口（`_mask_phone` / `_mask_id_card`）。
- `t_student_stage_event`：360 时间线数据源（append-only，无 is_deleted/version）。
- `t_college` / `t_major` / `t_class`（含 counselor_id / head_teacher_id）：组织与辅导员绑定关系，13A-04 班级管理的"辅导员绑定"直接读写 `t_class.counselor_id`，不建平行绑定表。

### 1.2 写什么
- **主档只读**：13A 不 UPDATE `t_student_profile` 任何字段（学籍状态变更属 13B 教务中心职权）。唯一例外：无。若业务需要"风险等级"之类学工态标签，落 13A 自己的 `t_affairs_risk_record`，不加列到主档。
- **360 沉淀双通道**：
  - 通道 A（时间线摘要）：关键节点写 `t_student_stage_event`（student_id / from_stage=null / to_stage=当前 stage 不变 / reason=事件摘要 / source_module='student-affairs' / occurred_at）。写入节点清单：请假 APPROVED 与 CLOSED、困难认定 APPROVED、奖助公示确认、处分 EFFECTIVE 与 REMOVED、风险 CLOSED、谈话完成、调宿完成、归档完成。
  - 通道 B（域明细）：完整业务记录留在 `t_affairs_*` 域表，由聚合端点按需读取。
- 需求中的 `student_affairs_events / student_360_timeline / student_risk_records` 三表映射为：前两者 = StageEvent 通道 + 域表通道（不新建同义表）；`student_risk_records` = 新表 `t_affairs_risk_record`。

### 1.3 复用哪些函数与表
- `mobile_teacher_service.resolve_teacher_scope(user)`、`scope_match_row(...)`、`can_teacher_view_student(user, stu, scope, db)`（越权 403 + 审计）。
- 教师端学生 360 聚合端点：`GET /api/v1/mobile/teacher/student/{id}`（现聚合六域 + StageEvent 时间线）。

### 1.4 需要扩展什么
- **聚合端点扩展方案**：`mobile/teacher/student/{id}` 响应新增 `affairs` 节点：
  - `affairs.leave`：近 N 条请假（状态/起止/类型）；
  - `affairs.aid`：困难等级（脱敏，仅授权角色见等级明细）+ 奖助获得记录；
  - `affairs.discipline`：生效中处分数 + 有权限者见明细；
  - `affairs.risk`：未关闭风险数 + 等级；
  - `affairs.talk`：近 N 次谈话摘要；
  - `affairs.dorm`：当前床位（楼/房/床）。
  - 每个子节点按查看者权限点裁剪（见 §3 敏感矩阵），心理相关默认不出现在该聚合中。
- PC 端新增 `GET /api/v1/student-affairs/students/{id}/profile` 与 `/timeline`（require_staff + scope 校验），timeline 合并 StageEvent 与 `t_affairs_*` 域事件按时间倒序。
- scope 机制扩展：`t_teacher_student_scope.scope_type` 新增枚举 `DORM_BUILDING`（宿管按楼栋）、`PSY_STUDENT`（心理老师按授权学生）、`AID_BIZ`（资助老师按资助业务学生）；`getCounselorScope / filterStudentsByCounselorScope / assertCounselorCanAccessStudent` 设计为对 `resolve_teacher_scope` 三函数的薄封装，禁止另起炉灶。

### 1.5 禁止做什么
- 禁止新建学生主表、学生冗余档案表；禁止在 13A 表冗余存 real_name/class_name 作为事实字段（仅可作查询期投影）。
- 禁止 13A 修改 current_stage / student_status（那是 13B 学籍状态机职权）。
- 禁止绕过 `can_teacher_view_student` 直接按 class_id 手写过滤。
- 禁止向 `t_student_stage_event` 写入敏感明细（心理内容、家庭经济数字）——只写中性摘要。

### 1.6 迁移步骤
1. P1 契约冻结期：确定 `affairs` 聚合节点 JSON Schema 与 timeline 事件类型枚举（`AFFAIRS_LEAVE_CLOSED` 等），写入契约文档。
2. P6 阶段实现 timeline 合并读取；聚合端点扩展向后兼容（新增节点，不改既有六域节点结构）。
3. scope_type 新枚举随 P5/P7 各自业务上线时增加种子数据；旧 scope 行不受影响（枚举扩展向后兼容）。

## 2. 与 Workflow 审批中心的融合

### 2.1 读什么
- `t_workflow_task`（node_code / status / version / acted_at / action_reason）：待审列表、已办列表。
- PC API `/api/v1/approvals/tasks`、`/processed`、`/cc`；移动包装 `POST /api/v1/mobile/teacher/approvals/{id}/approve|reject`（含教师范围校验 + 审计 + 409 APPROVAL_VERSION_CONFLICT）。

### 2.2 写什么
- 每个 13A 审批业务在提交时创建 `t_workflow_instance`（workflow_code + biz_id 指向 `t_affairs_*` 业务单），逐节点生成 `t_workflow_task`，同时写 `t_unified_todo`（assignee_id / student_id / todo_type=WORKFLOW_TODO / source_module='student-affairs' / due_at）。
- 审批动作（approve/reject/transfer）复用既有端点与乐观锁；节点流转后的业务状态变更在 13A 自己的 service（affairs_service）中实现回调/后置处理。

### 2.3 workflow_code / node_code 设计表（13A 全部审批清单）

| 业务 | workflow_code | node_code 序列 | 分支规则 |
|---|---|---|---|
| 请假（普通 ≤N 天） | AFFAIRS_LEAVE | COUNSELOR_REVIEW | 天数阈值走平台规则中心 |
| 请假（长假 >N 天） | AFFAIRS_LEAVE_LONG | COUNSELOR_REVIEW → COLLEGE_REVIEW | 同上 |
| 请假（重大/超长） | AFFAIRS_LEAVE_MAJOR | COUNSELOR_REVIEW → COLLEGE_REVIEW → SA_OFFICE_REVIEW | 同上 |
| 续假 | AFFAIRS_LEAVE_EXTENSION | COUNSELOR_REVIEW（超阈值追加 COLLEGE_REVIEW） | 累计天数重算层级 |
| 销假确认 | AFFAIRS_LEAVE_CANCEL | COUNSELOR_CONFIRM（单节点） | 无 |
| 困难认定 | AFFAIRS_AID_IDENTIFY | CLASS_REVIEW → COUNSELOR_REVIEW → COLLEGE_REVIEW → SCHOOL_REVIEW | 班级评议节点可配置跳过 |
| 困难等级调整 | AFFAIRS_AID_ADJUST | COUNSELOR_REVIEW → COLLEGE_REVIEW | 无 |
| 奖学金申请 | AFFAIRS_SCHOLARSHIP | COUNSELOR_REVIEW → COLLEGE_EVAL → SCHOOL_RECHECK | 公示为业务状态非审批节点 |
| 助学金申请 | AFFAIRS_GRANT | COUNSELOR_VERIFY → COLLEGE_REVIEW → SCHOOL_REVIEW | 读困难库预校验 |
| 勤工助学上岗 | AFFAIRS_WORK_STUDY | DEPT_SCREEN → COUNSELOR_CONFIRM → AID_CENTER_REVIEW | P2 |
| 助学贷款核对 | AFFAIRS_LOAN | COUNSELOR_CHECK → AID_TEACHER_REVIEW → SCHOOL_CONFIRM | P2 |
| 处分登记 | AFFAIRS_DISCIPLINE | COLLEGE_REVIEW → SA_OFFICE_REVIEW（严重追加 SCHOOL_REVIEW） | 严重级别走规则中心 |
| 处分解除 | AFFAIRS_DISCIPLINE_REMOVE | COUNSELOR_REVIEW → COLLEGE_REVIEW → SA_OFFICE_FINAL | 无 |
| 调宿 | AFFAIRS_DORM_TRANSFER | COUNSELOR_REVIEW → DORM_MANAGER_REVIEW | 目标床位校验在业务层 |
| 学工归档确认 | AFFAIRS_ARCHIVE | COLLEGE_CHECK → SA_OFFICE_CONFIRM | 无 |

### 2.4 复用哪些函数与表
- `t_workflow_instance` / `t_workflow_task`（version 乐观锁，已处理再审 → 409 APPROVAL_VERSION_CONFLICT）。
- `approval_service` 的任务创建/流转/审计逻辑；移动审批包装的范围校验与审计链。
- `t_unified_todo` 待办联动：任务创建即写待办；任务 acted 后待办置 DONE；驳回/退回向发起人写 RETURNED_NOTICE 消息。

### 2.5 需要扩展什么
- `approval_service` 注册 13A 的 workflow_code → 节点序列映射（配置化，层级阈值读平台规则中心）。
- 移动审批包装扩展：待办卡片 payload 增加 13A 业务摘要字段（如请假类型/天数），端点不变。
- 审批详情页跳转映射：todo_type + biz_id → PC 路由（如 `/admin/student-affairs/leave/:leaveId/approve`）与小程序页面路径的路由表。

### 2.6 禁止做什么
- 禁止 13A 自建 `t_affairs_approval` 通用审批表（业务快照表如 `affairs_aid_review_record` 只存业务意见附件，审批状态以 workflow task 为准）。
- 禁止绕过移动包装直接暴露教师写端点；禁止在 service 里手写"直接改 status 跳过审批"的捷径。
- 禁止各业务自发消息——审批通知一律由 workflow 联动统一写 todo/message。

### 2.7 迁移步骤
1. P1 冻结上表 workflow_code/node_code 与状态映射（业务状态 ↔ 当前节点）。
2. P3 起按业务逐个注册；既有 campus-service 简易 approve/return API 保留兼容（见 §5.1 请假迁移）。
3. 归档批次里的历史审批记录以 workflow task 快照导出，不迁移旧数据结构。

## 3. 与 Security 的融合（脱敏 × 审计 × 水印）

### 3.1 敏感字段清单 × 脱敏策略 × 查看审计矩阵

| 敏感域 | 字段（示例） | 存储 | 默认展示 | 谁可看完整 | 查看完整时审计 |
|---|---|---|---|---|---|
| 家庭经济（困难认定） | 年收入/人均收入/致困原因明细/低保证明 | 明细表隔离 + 金额区间化展示 | 区间/等级，不出明细数字 | 资助老师、学工处、本班辅导员 | `audit_log.record(action=VIEW_SENSITIVE, resource=aid_apply:{id})` 必填原因 |
| 心理 | `t_cs_mental_record` 内容、13A 心理来源风险明细 | 强权限隔离 | 普通教师仅见"需关注"布尔 | 心理老师、授权辅导员（PSY_STUDENT scope） | 每次读明细审计；导出默认剔除 |
| 处分 | 处分类型/事由/决定文书 | 域表 | 学生端只回数量不回明细（沿用 t_cs_discipline 现行为）；教师按权限点 | 学院学工、学工处、本班辅导员 | 明细查看审计 |
| 联系方式 | 手机号/身份证 | `*_encrypted` | `_mask_phone` / `_mask_id_card` | 需填原因申请完整查看 | 家校联系"看完整号码"强制原因 + 审计（需求 2.13） |
| 监护人 | 监护人姓名/电话/工作单位 | t_student_contact + 加密列 | 姓氏 + 脱敏电话 | 同联系方式 | 同上 |

### 3.2 读什么 / 写什么
- 读：`t_security_audit_log`（合规追查）、既有脱敏工具函数。
- 写：所有敏感读取与越权尝试调 `app.services.audit_log.record(action, resource, detail, result)`；13A 域级留痕新建 `t_affairs_audit_trail`（append-only，对齐 `t_cs_audit_trail` 模式）。

### 3.3 复用哪些函数与表
- `audit_log.record`（DB 模式落 t_security_audit_log，含 ip/ua/traceId）。
- 导出水印管线：`/api/v1/export/domain/{domain}`（用途必填≥5字、脱敏列、首行水印、`t_export_task` 留痕、5 次/分限流、5000 行上限、下载审计）。13A 新导出 = 注册新 domain 配置：`affairs_leave`、`affairs_aid_list`（强敏感，默认全脱敏）、`affairs_funding_result`、`affairs_discipline`、`affairs_dorm_check`、`affairs_archive_package`。
- 前端 `MobileSensitiveText` 脱敏展示组件。

### 3.4 需要扩展什么
- domain 导出配置支持"按角色的列级裁剪"（心理列对非授权角色导出时物理剔除而非打码）。
- "申请查看完整敏感字段"通用交互：前端弹窗填原因（≥5 字）→ 专用端点返回完整值 + 审计，不做长期解密授权。

### 3.5 禁止做什么
- 禁止任何端点直接返回未脱敏手机号/身份证；禁止在列表接口返回家庭经济数字与心理内容。
- 禁止自建导出通道绕开 `t_export_task`；禁止导出文件无水印落地。
- 禁止把敏感明细写进 `t_unified_message` 正文或 StageEvent reason。

### 3.6 迁移步骤
1. P1 冻结敏感矩阵（上表）与各 domain 导出列配置。
2. 各业务阶段落地时先接脱敏与审计再开放接口（测试用例含"越权读 403 + 审计有记录"）。
3. P7 归档阶段接入水印归档包（复用 export 管线打包 + sha256 登记）。

## 4. 与 Dashboard / stats 的融合

### 4.1 读什么 / 写什么
- 读：`/api/v1/stats/overview|lifecycle|risk|workbench` 既有模式（require_staff，租户内实时 count 聚合）。
- 写：不落统计中间表（V1 实时聚合）；13A 只保证业务表有可聚合的状态与时间字段。

### 4.2 复用哪些函数与表
- `stats_service._count` 聚合模式；dashboard 按角色 preset 的组装方式（`mock_dashboard_service`/`dashboard.py` 现有 preset 机制）；辅导员维度复用 scope 过滤。

### 4.3 13A 指标接入 stats_service 聚合清单

| 指标 | 口径 | 来源表 | 频率 | 范围过滤 | 下钻路径 |
|---|---|---|---|---|---|
| 在假人数 | status=APPROVED 且当前时间在起止内 | t_cs_leave（affairs_status 扩展列） | 实时 | 全校/学院/班级(scope) | 请假列表?status=APPROVED |
| 请假逾期未销 | status=OVERDUE | 同上 | 实时 | 同上 | 请假列表?status=OVERDUE→详情 |
| 请假天数分布 | 按 leave_type 聚合 duration | 同上 | 实时 | 同上 | 请假统计页 |
| 困难学生数 | 认定 APPROVED 且未失效，按等级分组 | t_affairs_aid_apply + level_history | 实时 | 学院/班级；等级明细仅授权角色 | 困难学生库（脱敏） |
| 奖助覆盖率 | 获资助去重人数 / 在籍人数 | t_affairs_funding_application(结果确认) ÷ t_student_profile | 实时 | 学院 | 资助结果列表 |
| 处分数 / 解除数 | EFFECTIVE 计入；REMOVED 计解除 | t_affairs_discipline_case | 实时 | 学院/班级 | 处分列表→详情 |
| 心理关注数 | 关注中记录数（仅授权角色可见数值） | t_cs_mental_record + 风险(心理来源) | 实时 | 心理授权 scope | 不提供普通下钻 |
| 风险学生数 | 未 CLOSED 风险去重学生，按等级 | t_affairs_risk_record | 实时 | 辅导员=所带班级 | 风险列表→学生360 |
| 谈话完成率 | 已完成 / 计划应谈 | t_affairs_talk_record/plan | 实时 | 辅导员本人/学院 | 谈话列表 |
| 宿舍异常数 | 检查异常 + 夜不归宿未闭环 | t_affairs_dorm_check_record + t_cs_dorm_exception | 实时 | 宿管=楼栋，辅导员=班级 | 宿舍检查列表 |
| 辅导员待办完成率 | DONE / 全部（时间窗内） | t_unified_todo(source_module='student-affairs') | 实时 | 本人/学院排行 | 工作台待办 |
| 归档率 | 已归档学生 / 应归档学生 | t_affairs_archive_package | 实时 | 学院 | 归档批次页 |

### 4.4 需要扩展什么
- `stats_service` 新增 `get_affairs_stats(scope)`；dashboard preset 新增三种角色视图（学工处/学院学工/辅导员），接口 `GET /api/v1/student-affairs/dashboard`（入参 tenant/current_user/current_role/data_scope/semester/date_range，出参 summaryCards/todoList/riskStudents/workflowPending/classOverview/warningTrends/recentActivities）。
- 每个卡片带下钻 route 字段，风险学生卡可点进学生 360。

### 4.5 禁止做什么
- 禁止建统计快照表/定时任务预聚合（V1 数据量下实时 count 即可，P3 再议物化）。
- 禁止指标绕过 scope（辅导员看到全校数即 bug）。
- 禁止在 dashboard 返回心理明细，只回授权后的计数。

### 4.6 迁移步骤

## 5. 与六大既有模块的逐一融合

### 5.1 campus-service：请假 = t_cs_leave 扩展方案【核心】

**现状**（已核实代码）：`t_cs_leave`（code / cs_student_id / leave_type / start_time / end_time / duration(String) / reason / status 默认 PENDING_REVIEW / apply_time / reviewer / review_time / return_reason），状态 PENDING_REVIEW/APPROVED/RETURNED，approve/return API + 批量，移动端学生提交已带防重复 409。

**决策：扩展 t_cs_leave + 必要子表**（V1 冻结口径，废止「新主表 t_affairs_leave_request」方案）：13A 请假 14 态、多级审批、销假/续假在 **t_cs_leave 原表加列**（affairs_status/workflow_instance_id/days/expected_return_at 等，见 C3 §3.1）承载；销假/续假用子表 `t_affairs_leave_cancel_record`、`t_affairs_leave_extension` 回链 `t_cs_leave.id`；附件走 `t_file_object(biz_module='student-affairs', biz_type='LEAVE', biz_id=leave_id)`，**不建 t_affairs_leave_attachment**。
- **状态机扩展**：DRAFT/SUBMITTED/COUNSELOR_REVIEW/COLLEGE_REVIEW/STUDENT_AFFAIRS_REVIEW/APPROVED/REJECTED/RETURNED/CANCELLED/EXTENSION_REVIEW/WAIT_CANCEL_LEAVE/CLOSED/OVERDUE/ARCHIVED；旧 status 列保留，affairs_status 为新权威列；旧值映射 PENDING_REVIEW→COUNSELOR_REVIEW、APPROVED→APPROVED、RETURNED→RETURNED。
- **存量数据**：**无需迁移到新主表**；只做字段补齐（nullable 加列）、affairs_status 状态映射、子表回填和兼容读写。
- **API 兼容**：既有 campus-service 请假端点保留；读/写经包装层操作 t_cs_leave（同一主单），新学工 API `/api/v1/student-affairs/leave/*` 与 `/api/v1/mobile/affairs/leave/*` 同源；防重复 409 逻辑照搬（同学生+时间重叠+非终态 → 409001 IDEMPOTENCY_CONFLICT）。

**处分同理**：`t_cs_discipline`（record_status=ACTIVE，学生端只回数量）保留为"生效台账"；新建 `t_affairs_discipline_case/decision/material/remove_apply` 承载登记→审批→生效→解除全流程；case 达到 EFFECTIVE 时**同步写/更新 t_cs_discipline 一行**（归属关系：affairs case 为流程主档，cs 行为对外只读投影，保证既有学生端"只回数量"接口零改动）；REMOVED 时更新该行 record_status。

**心理同理**：不动 `t_cs_mental_record` 结构与强权限；13A 心理关注 = 在其上追加记录 + 作为 `t_affairs_risk_record` 的 source=MENTAL 来源；心理明细读取仍走原表权限，13A 只引用 record_id。

**宿舍同理**：`t_cs_dorm_record`（当前入住事实）与 `t_cs_dorm_exception`（异常）保留；13A 新建 `t_affairs_dorm_building/room/bed`（房源）、`t_affairs_dorm_transfer`（调宿流程）、`t_affairs_dorm_check_task/record`（检查）；调宿 APPROVED 后原床释放/新床占用并**回写 t_cs_dorm_record**，夜不归宿写 t_cs_dorm_exception 并触发风险。

**禁止**：平行再建一套请假/处分/心理/宿舍事实表而不回链既有表；兼容期内双写不一致（以新表为唯一写入点，旧表只读或由新流程同步）。

### 5.2 orientation：迎新分宿 → 学工宿舍台账初始化
- 读：`t_orientation_student` 的 building/room/dorm_status（迎新分宿结果）。
- 融合：13A 宿舍房源初始化时，以迎新分宿结果为初始入住导入源（生成 t_affairs_dorm_bed 占用 + 对齐 t_cs_dorm_record）；此后宿舍事实以 13A 台账为准，迎新只负责入口一次性写入。

### 5.5 graduation：毕设异常 → 风险来源
