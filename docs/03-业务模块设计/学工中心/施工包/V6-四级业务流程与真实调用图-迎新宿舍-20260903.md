## 四级业务流程与真实函数调用图——数字迎新 × 宿舍与公寓

> 审计分支：`feat/student-affairs-v6-a1-on-theme-shell`  
> 审计提交：`291b93aa4a9cd757cbcb090ab167af018978ab46`  
> 审计目标：不再以“菜单能打开”代替“老师能完成业务”；从真实页面方法一直追踪到后端权威事实、状态变化、下一动作和返回上下文。

# 1. 本轮纠偏结论

之前的 V6 施工主要完成了：

```text
一级中心 → 二级工作区 → 三级页面
```

但老师真正办事还需要第四级：

```text
具体对象 + 当前流程实例 + 当前状态 + 阻断原因
+ 当前允许动作 + 动作结果 + 下一步 + 返回原队列
```

因此，**四级深链不是再加一层常驻菜单**。它是业务对象的连续办理上下文，例如：

```text
数字迎新
→ 报到办理
→ 宿舍确认
→ 新生 #orientationStudentId=1032
→ 当前 DormStay=RESERVED / Bed=LOCKED
→ 当前动作：办理正式入住
→ 成功后：DormStay=ACTIVE / Bed=OCCUPIED
→ 下一步：学生签发报到凭证 / 教师现场扫码
→ 返回：原批次的“待入住”队列
```

当前代码已经具备大量真实能力，但它们分散在页面、PC、小程序和多个 Service 中；UI 尚未把它们组织成老师无需培训即可执行的连续任务。

# 2. 四级信息架构定义

| 层级 | 用户看到的对象 | 数字迎新示例 | 宿舍示例 |
|---|---|---|---|
| L1 中心 | 去哪个业务中心 | 学工中心 | 学工中心 |
| L2 工作区 | 做哪类工作 | 数字迎新 | 宿舍与公寓 |
| L3 阶段 / 队列 | 当前处理哪一阶段 | 报到资格、报到办理、异常闭环 | 分配计划、入住、调宿、检查异常 |
| **L4 业务实例** | **具体对谁、做什么、做完去哪** | **某新生的材料、资格、现场报到、学院确认** | **某批次、某学生、某床位、某 DormStay、某异常** |

L4 必须携带或能解析以下上下文：

```text
source
workspace
queue
batchId
orientationStudentId
studentId
step
focus
returnTo
expectedVersion
clientRequestId
```

规则：

1. 这些字段只用于定位、续办和返回，不参与服务端授权。
2. `returnTo` 必须使用内部白名单，不接受外部 URL。
3. `expectedVersion` 来自当前真实对象，写操作不能省略。
4. `clientRequestId` 用于幂等写，不得每次重试随意换值。
5. 对象已处理、版本变化、权限变化或范围变化时，必须显示真实原因并提供安全返回。

# 5. 宿舍权威事实链

宿舍存在两套看似相似、实质不同的事实：

```text
A. OrientationStudent.building / room / dormStatus
   用途：迎新展示兼容字段

B. DormAllocationBatch / DormAllocationItem / DormStay / DormBed
   用途：正式住宿分配、预留、入住、调宿、退宿和资格判断
```

**B 才是权威链。** 报到资格服务明确读取 `DormStay + DormBed`，不能用 A 的自由文本或展示状态替代。

## 5.1 正式分配调用图

```text
DormAllocationView.load()
  ├─ listDormAllocationBatches()
  ├─ getBuildings()
  └─ getOrientationBatches()

新建批次
DormAllocationView.createBatch()
  └─ createDormAllocationBatch(payload)
      └─ POST /student-affairs/dorm/allocation-batches
          └─ dorm_allocation_service.create_batch()
              ├─ 校验 orientationBatchId
              ├─ 校验学生范围
              ├─ 校验楼栋 / 房间 / 床位资源范围
              └─ status = DRAFT

Dry Run
DormAllocationView.dryRun()
  └─ dryRunDormAllocation(batchId)
      └─ POST .../{batchId}/dry-run
          └─ dorm_allocation_service.dry_run()
              ├─ _candidate_students()
              ├─ _resource_rows()
              ├─ 性别 / 一人一床 / 已有住宿校验
              ├─ 软规则排序
              └─ DormAllocationItem = PROPOSED / CONFLICT

人工调整
DormAllocationView.manualAssign()
  └─ manualAssignDorm(batchId, studentId, bedId)
      └─ POST .../{batchId}/manual-assign
          └─ dorm_allocation_service.manual_assign()
              └─ DormAllocationItem = PROPOSED

发布
DormAllocationView.confirmPublishBatch()
  └─ publishDormAllocation(batchId)
      └─ POST .../{batchId}/publish
          └─ dorm_allocation_service.publish()
              ├─ 冻结 resolvedStudentIds
              ├─ 冻结 resolvedBedIds
              ├─ _reserve()
              │   ├─ DormBed VACANT → LOCKED
              │   ├─ DormStay = RESERVED
              │   └─ DormAllocationItem = RESERVED
              └─ _link_orientation()
                  ├─ OrientationStudent 楼栋 / 房间展示同步
                  └─ DORM = DONE
```

## 5.2 正式入住调用图

```text
DormCheckinView
  └─ 选择楼栋 → 房间 → 床位
      └─ submitCheckin()
          └─ studentAffairsB.api.dormCheckin(bedId, studentId)
              └─ core.checkinBed()
                  └─ POST /student-affairs/dorm/beds/{bedId}/checkin
                      └─ affairs_dorm_service.checkin()
                          └─ affairs_dorm_stay_service.activate_checkin()
                              ├─ 校验学生无其他 ACTIVE stay
                              ├─ 校验床位无其他 ACTIVE stay
                              ├─ 若 Bed=LOCKED，必须匹配本人 RESERVED stay
                              ├─ DormStay RESERVED → ACTIVE
                              ├─ DormBed LOCKED/VACANT → OCCUPIED
                              ├─ DormAllocationItem → CONFIRMED
                              └─ 同事务写住宿历史和审计
```

## 5.3 调宿 / 退宿 / 检查异常

```text
调宿
DormTransferView
  → 创建调宿申请
  → COUNSELOR_REVIEW
  → DORM_MANAGER_REVIEW
  → affairs_dorm_stay_service.execute_transfer()
     old DormStay ACTIVE → ENDED
     new DormStay → ACTIVE
     old Bed → VACANT
     new Bed → OCCUPIED

退宿
DormCheckinView.submitCheckout()
  → createDormCheckout()
  → affairs_dorm_stay_service.create_checkout_request()
  → PENDING_CONFIRMATION / BLOCKED
  → 宿管确认
  → ACTIVE DormStay 结束
  → Bed 释放

宿舍检查异常
DormCheckView.submit
  → submit_check_record()
  → DormCheckRecord = ABNORMAL
  → CsDormException
  → 有真实学生时创建 AffairsRiskRecord(source=DORM)
  → UnifiedTodo 分派给宿管
  → 风险中心继续正式处置
```

宿舍检查异常这条链已经真正创建正式风险单；迎新异常的 `escalate_exception()` 目前只修改迎新异常与新生风险等级，二者不能在 UI 中被描述为同一种“进入风险中心”。

# 6. 已确认的八个流程断点

| 编号 | 断点 | 代码证据 | 对老师的影响 | 处理级别 |
|---|---|---|---|---|
| O-D01 | 新生详情绿色通道动作未传 `expectedVersion` | 详情页只传 remark/reason；API 和后端 schema 要求 expectedVersion | 点“通过/退回/驳回”才发现失败 | **P0** |
| O-D02 | 迎新“确认入住”不是正式 DormStay 入住 | `batchConfirmCheckin` 只改 OrientationStudent；资格读取 DormStay/DormBed | 页面显示完成，最终资格仍可能不通过 | **P0** |
| O-D03 | 宿舍预分配使用自由文本，正式分配使用稳定 Bed ID | `OrientationDormPreassignView` 对比 `DormAllocationView / dorm_allocation_service` | 两套入口、两套口径，老师不知道哪个是真的 | **P0** |
| O-D04 | 跨页按钮不携带对象上下文 | 前往缴费/材料/宿舍只跳通用列表 | 老师进入下一页后要重新搜索学生 | **P0** |
| O-D05 | 待办队列只在内存 | `orientationWorklist.ids` | 刷新、跨页、重新登录后上/下一条丢失 | **P1** |
| O-D06 | 异常跟进显示“编辑”，API 明确未配置 | `startEditFollow` → `updateExceptionFollowUp` → fail | 可见死按钮，破坏免培训体验 | **P0** |
| O-D07 | 迎新异常“升级风险”未创建正式风险单 | `escalate_exception` 只改 OrientationException / OrientationStudent | 老师以为风险中心已接单，实际没有 riskId | **P0 / 后端决策** |
| O-D08 | 跨端现场报到没有在 PC 上形成交接 | 学生端 token、教师端扫码、PC finalize 各自存在 | 老师不知道现在轮到谁、在哪个端操作 | **P1** |

另外还有两个产品级缺口：

1. `evaluate()` 同时返回“现场报到资格”和“最终入学资格”，但 PC 页面没有把二者清楚区分；材料/缴费/宿舍可作为到场后跟进项时，容易误解为“不允许现场报到”。
2. 新生详情已经展示七步和大量域卡片，但没有一个权威的“当前主动作 / 为什么 / 完成后去哪”决策区，老师仍需自己阅读全页判断。

# 7. 免培训目标页面：不是再堆卡片

## 7.1 `OrientationStudentDetailView` 应重构为“一生一流程”

首屏只回答六个问题：

```text
1. 我正在处理谁？
2. 他属于哪个批次、哪条队列？
3. 当前走到哪一步？
4. 为什么停在这里？
5. 我现在唯一最该做什么？
6. 做完以后谁接手、我如何继续下一名？
```

冻结结构：

```text
对象身份条
  新生 / 录取编号 / 班级 / 批次 / 当前范围 / 队列位置

七步旅程条
  已完成 | 当前 | 卡点 | 待开始 | 不适用

现在要做
  主动作
  为什么
  前置条件
  禁用原因
  执行动作
  成功结果

跨端交接
  当前责任人 → 下一责任人
  PC / 学生小程序 / 教师小程序
  对方完成后这里出现什么结果

详情区（渐进展开）
  身份 / 材料 / 缴费 / 宿舍 / 异常 / 审计

底部续办
  返回原队列 | 上一个 | 下一个 | 完成并进入下一名
```

禁止：

- 把七个步骤都渲染为同等重要的大卡；
- 让老师在缴费、材料、宿舍列表中重新搜索同一学生；
- 用“前往某某管理”作为没有上下文的万能按钮；
- 在没有正式 riskId 时显示“已进入风险中心”。

## 7.2 宿舍工作区应使用“一条权威旅程”

```text
房源可用
→ 分配批次草稿
→ Dry Run / 异常处理
→ 发布并预留
→ 学生自选或管理员确认
→ 正式入住 ACTIVE
→ 调宿 / 退宿 / 检查 / 异常
```

迎新页面只能消费或引导这条权威链，不再直接维护第二套宿舍事实。

# 8. 四级深链合同草案

建议内部格式：

```text
/admin/orientation/students/{orientationStudentId}
  ?source=orientation-progress
  &queue=blocked
  &batchId={batchId}
  &step=DORM
  &focus=dorm-allocation
  &returnTo=/admin/orientation/progress
```

跨到正式宿舍：

```text
/admin/student-affairs/dorm/allocation
  ?source=orientation
  &orientationBatchId={batchId}
  &orientationStudentId={orientationStudentId}
  &studentId={studentId}
  &focus=allocation-item
  &returnTo=/admin/orientation/students/{orientationStudentId}
```

定位正式入住：

```text
/admin/student-affairs/dorm/checkin
  ?buildingId={buildingId}
  &roomId={roomId}
  &bedId={bedId}
  &studentId={studentId}
  &focus=checkin
  &returnTo=/admin/orientation/students/{orientationStudentId}
```

异常进入风险前必须拿到真实 `riskId`：

```text
/admin/student-affairs/risk/{riskId}
  ?source=orientation-exception
  &exceptionId={exceptionId}
  &studentId={studentId}
  &focus=handle
  &returnTo=/admin/orientation/exceptions
```

L4 Query 必须经过专用 builder/parser 和 allowlist；不能由各页面随手拼接。

# 9. 施工顺序

## P0：先修确定性断点

1. 新生详情绿色通道写操作传递真实 version，并处理冲突后刷新。
2. 移除或明确禁用异常跟进“编辑”死动作。
3. 新生详情中的宿舍“确认入住”停止调用平行事实链；改为展示 canonical allocation/stay 状态并进入正式宿舍动作。
4. 迎新异常“升级风险”在后端未创建正式风险单前，改成真实文案；若批准后端改动，再以幂等方式创建 `AffairsRiskRecord` 并返回 `riskId`。

## P1：建立 L4 上下文底座

1. `orientationJourneyContext`：安全生成/解析 `studentId/batchId/step/focus/returnTo`。
2. 持久队列上下文：URL + session 恢复，不使用纯内存列表作为唯一来源。
3. 目标页面消费 query，自动筛选并打开对应学生/申请/床位/异常。

## P2：重构新生详情

按“对象身份 → 当前任务 → 七步旅程 → 跨端交接 → 详情 → 下一名”重构；保留所有真实权限、状态、版本、审计和业务方法。

## P3：收口迎新宿舍

1. `/orientation/dorm-preassign` 降为兼容入口或说明页；正式入口指向 `DormAllocationView`。
2. 迎新详情读取 canonical allocation / stay 投影。
3. 正式入住只走 `activate_checkin`。
4. 入住异常进入正式宿舍异常或迎新异常时，明确事实归属和风险联动差异。

## P4：跨端验收

```text
学生小程序签发凭证
→ 教师小程序预检
→ 教师确认现场报到
→ PC 新生详情自动显示 CHECKIN DONE
→ PC 学院确认正式入学
→ 归档 / 消息 / 返回队列
```

# 10. 新验收门禁

## 老师免培训 Gate

任意真实新生进入详情后，首屏必须能直接读出：

- 当前环节；
- 阻断原因；
- 当前责任角色；
- 当前唯一主动作；
- 禁用原因；
- 下一责任角色；
- 所需操作端；
- 返回原队列和下一名入口。

## 业务闭环 Gate

- 不只点击路由，必须执行真实写操作；
- 校验数据库权威状态，而非只校验页面提示；
- 每一步重新登录后仍可恢复；
- version 冲突可恢复且不丢输入；
- 跨端完成后 PC 能读到结果；
- 对象已处理、消息过期、权限变化、范围变化均有明确状态；
- 迎新宿舍必须最终落到 DormStay / DormBed；
- 正式风险联动必须存在真实 riskId；
- 完成后能继续下一名，而不是回到首页重新找人。

## 视觉 Gate

漂亮的定义不是渐变和卡片数量，而是：

1. 当前任务最醒目；
2. 主动作紧贴当前对象；
3. 非当前步骤渐进收起；
4. 状态、责任人、截止时间和下一步不需要猜；
5. 1366×768 首屏看见对象、当前任务、主动作和至少部分队列；
6. 六主题、键盘、Focus、长文本、错误态全部可用。
