## 3. 真实业务结果与边界

- 让**学生**移动端报名/取消/扫码签到；让**发布方**PC 端看名单、审核报名（志愿类）。
- 进入条件：学生命中活动 scopeConfig（可报名）；活动 PUBLISHED（报名）/ONGOING（签到）。退出：CONFIRMED 后名单锁定。
- 上游：01 活动（PUBLISHED）。下游：03 二课积分（confirm 依据签到）。
- 本卡完成：`t_affairs_activity_signup` + 报名/取消/审核/签到 + PC 名单页 + 移动端。
- 不做：活动发布（01）、积分生成（03）。
- 学校决定：是否开启报名审核（志愿默认开）、签到方式（扫码/定位/签到码）、是否允许候补 WAITLIST。

**权限码归口（§A）**：本卡 `studentAffairs.activity.enroll / checkin / confirm`（报名/签到/名单确认）均为 13A §12 已列权威码；原"报名审核"码并入 `studentAffairs.activity.confirm`（§12 未单列 review，级别由状态节点区分）。菜单键 `menu:studentAffairs:activities` 为 navPlan 命名，非动作码。

**审计表分流（§B）**：业务动作 ACTIVITY_ENROLL / CHECKIN / ENROLL_REVIEW → `t_affairs_audit_trail`（复用 `_audit()`）；越权/满员/重复拒绝 → `t_security_audit_log`；**含隐私签到照片·定位的查看/导出 → `t_security_audit_log`**（SENSITIVE_VIEW，含水印+原因）。

**SEC-5（真实缺陷·未实现·三段式）**：现状本域后端端点仅 `Depends(require_staff)`（`backend/app/core/security.py` L97-103，仅拦学生令牌），**无细粒度强校验**；§2 grep 实证本卡端点整体 `missing`。本卡 §7/§9 已给应校验权限码（**设计**），属**编码阶段待实现项，本轮未落地**，不得记为已实现端点；移动端 `enroll/checkin` 仍须后端 SELF 范围 + 六要素强校验，**严禁停留在 `require_staff`**。
