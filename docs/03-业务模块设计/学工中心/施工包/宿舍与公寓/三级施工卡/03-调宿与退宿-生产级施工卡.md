## 3. 真实业务结果与边界

- **让谁完成什么**：学生/辅导员发起调宿→辅导员初审(本班)→宿管终审(目标楼)→系统执行换床(原床释放、新床占用、回写"我的宿舍")；退宿由卡 02 的 checkout 释放床位。
- **进入条件**：发起 `studentAffairs.dorm.transfer.create`(学生本人/辅导员代发)；审批 `studentAffairs.dorm.transfer.approve`(辅导员本班/宿管目标楼)。
- **退出条件**：EXECUTED（换床一致）或 REJECTED/RETURNED/CANCELLED（终止）。
- **上游**：学生在住床位(from_bed)、目标空床(to_bed)。**下游/回写**：床位翻转、`t_cs_dorm_record`、成长时间线(EXECUTED 事件)。**跨模块**：无风险回写。
- **本卡完成**：列表/详情/撤销/退回端点；version 条件 UPDATE 防并发抢床；提交/终审目标楼性别校验；scope+权限硬化；前端双栏页。
- **明确不做**：智能推荐目标床（backlog）。
- **仅学校可决定**：审批层级是否加第 3 级(学院/学工处)（D-13）；调宿是否限次/限期。

## 6. 主流程、异常流程与状态机

见二级总包 §7.1（以代码 8 态为准）。要点：
- 提交：在住床反查 from_bed；目标床须 VACANT(L319)，否则 409；**建议补目标楼性别校验**(现无)。防重复：**建议补"同学生仅一条在途"校验**(现无，缺口→可重复发起)。
- 终审执行：`review_transfer` L367 再判 VACANT；**须补 version 条件 UPDATE**：`UPDATE t_affairs_dorm_bed SET student_id=…,status='OCCUPIED',version=version+1 WHERE id=? AND status='VACANT' AND version=?`，影响行=0→409 DATA_CONFLICT（防双人抢同床，D 级）。
- 非法：非在途状态审批→`APPROVAL_VERSION_CONFLICT`(L352)；越栋审批→403 NO_DATA_SCOPE(需补)。
