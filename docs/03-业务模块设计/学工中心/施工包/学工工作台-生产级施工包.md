## 5. 业务目标、角色与完整闭环

- **解决的真实问题**：把散在请假/风险/宿舍/困难/奖助/处分/谈话/归档各域的"今天谁要处理、哪些学生要盯"聚合到一处首屏；不同角色进系统第一眼知道干什么。
- **购买/管理部门**：学生工作处（学工处）为主责；学院学工办、辅导员为高频用户。
- **使用角色**（据权限总控 §7.3 + service `_resolve_view`）：学工处管理员（SA_ADMIN/SCHOOL_ADMIN/SCHOOL_LEADER，全校）、学院学工负责人（COLLEGE_ADMIN/COLLEGE_SA，本院）、辅导员（COUNSELOR，本班/本人学生）、班主任（同辅导员范围规则）。
- **发起/处理/审核/查看/归档责任**：工作台**不产生业务数据、无独立状态机**，是各域**只读聚合 + 待办直达 + 下钻入口**；所有处理/审核/归档发生在目标业务页。
- **主流程**：登录→进 `/admin/student-affairs/dashboard`→后端按 `currentRoleCode` 定 view + `resolve_teacher_scope` 定范围→聚合各域 count→出指标卡/模块卡→点卡下钻到明细页处理。
- **异常/降级**：范围内无数据→空态卡；聚合失败→整页 error 可重试（`AppGlobalState`）；辅导员无带班配置（TENANT_FALLBACK）→当前看全租户（待收敛，D-09）。
- **与其他模块 I/O**：**输入**=各域只读接口（请假/困难/奖助/处分/风险/宿舍/统一待办）；**输出**=跳转到各业务处理页 + 导出台账；工作台不回写业务表。

## 7. 状态机与业务规则

**本二级模块无独立业务状态机**（业务理由：工作台是各域只读聚合，本身不创建/流转任何单据；dashboard service L85-161 只做 count 查询，无状态字段写入）。

它**消费**下游状态但不改写：
- 待办态复用统一待办 `UnifiedTodo.status`（`PENDING/DONE/CANCELLED`；dashboard 只统计 `PENDING` 数，service L99-101）；待办完结由各业务 service 在处理动作的同事务内回写 `status=DONE`，工作台只读。
- 指标口径由各域状态机终态/在途态定义，例：待审请假 = `CsLeave.affairs_status IN (COUNSELOR_REVIEW,COLLEGE_REVIEW,STUDENT_AFFAIRS_REVIEW)`（service L107-109）；逾期未销假 = `affairs_status == 'OVERDUE'`（L110-111）；在办风险 = `AffairsRiskRecord.status NOT IN (CLOSED)` 去重学生（L131-138）。

→ 不虚构状态机；仍须覆盖：重复提交（下钻处理页各自幂等）、聚合失败重试（整页 error 重试）、异常恢复（单接口失败整页降级）。

**继承的硬规则（务必落卡）**：
- **两层授权**（§12）：平台→租户模块授权（`STUDENT_AFFAIRS`）为第一层；学校→角色授权为第二层。未授权模块菜单不显示、路由拦截、接口 403、工作台不显示卡。
- **六要素合取**（§8A.1）：激活角色 + 模块授权 + 数据范围 + 业务关系 + 按钮权限 + 敏感字段权限，后端最终裁定。**当前代码只做了"角色→view + scope"两要素，缺 permission key/button/敏感字段的后端强校验**（security.py `require_staff` 只挡学生）→ D-05 补强项。
- **数据范围前端不传**（§8 L347）：一律后端 token+scope 解析；TENANT_FALLBACK 兜底看全租户属试点期行为，标准版应收敛（D-09）。
- **敏感统一控制**（§10.1）：完整敏感值需授权+原因(≥5字)+二次确认+水印+审计+导出留痕；心理明细任何导出剔除、无权限整段不返回（§10.2）。工作台只读 count 天然不返敏感明细，敏感发生在"下钻到明细"，由目标业务控制。
- **拒绝码**：401 未登录 / 403 无权限或越权（越范围表现为不存在）/ 409 状态冲突 / 422 参数校验。

**需新增/复用的 key 与 scope**：复用 `resolve_teacher_scope`（现有）；新增 menu `menu:studentAffairs:workbench`、API `studentAffairs.dashboard.view`（后端强校验）与 `studentAffairs.counselor.dashboard.view`。命名说明：**权限码统一为点式 `studentAffairs.<biz>.<action>`**（与 13A §12 权限点矩阵、route meta / `AppPermissionButton` code 一致）；旧「affairs 冒号式」错误口径（形如 affairs·biz·action 冒号拼接）本轮已全量清理、不作别名/兼容保留（收口修订登记：affairs 冒号旧码已清理，模块内 grep 为 0）；menu key 亦统一为 `menu:studentAffairs:*`，杜绝任何 affairs 冒号遗留。同一动作在页面/按钮/API/§9 权限矩阵/seed/测试处使用同一码。

**需甲方/学校确认的边界**：学院排行卡是否对学院管理员开放；统计周期按学期/学年；TENANT_FALLBACK 试点兜底是否保留；辅导员是否允许导出待办/风险名单。
