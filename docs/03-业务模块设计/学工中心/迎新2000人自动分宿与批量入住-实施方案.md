# 迎新大批量分宿与批量入住实施方案

日期：2026-09-06。范围：迎新与宿舍共同业务，教师 PC 主工作区，学生 PC、教师小程序、学生小程序同步。本文是经代码核查后的实施规格；未实现项不代表已有能力。保持现有 UI 壳，工作区采用紧凑工具栏、表格和房间/床位网格。

## 1. 学校真实做法与本系统选择

- 湘潭大学公开细则按学生类型、性别、院系校区划分住宿区域，要求班级相对集中，院系再把床位落实到人。资料发布于 2012 年，作为历史业务案例，不视为所有学校现行统一政策。[学校来源](https://hqbzc.xtu.edu.cn/info/1047/1348.htm)
- 中国石油大学（华东）化学化工学院 2026 新生答疑说明男女分别在指定楼栋、楼层，开学前分配到房号和床号。这与固定房源台账相符。[学院来源](https://cce.upc.edu.cn/2026/0806/c22676a498049/pagem.htm)
- 大连东软信息学院 2025 招生章程提供“预分班级寝室资源内自选，超过期限自动补分”的例子。自选可作为后续模式，当前先把学校统一分配做完整。[招生章程](https://zs.neusoft.edu.cn/attachment/sites/item/2025_06/05_09/5ede86243ad8c3a2.pdf)
- StarRez 的波士顿大学案例使用不同房源池和选择时段处理不同住宿安排；启发是分区规则、特殊安排、已有住户保护与发布节奏分开处理，不照搬其学校政策。[厂商客户案例](https://www.starrez.com/customers/boston-university-gender-affirming-housing)

本系统默认：学校维护真实床位 → 按迎新批次确认住宿名单 → 划定合法房源池 → 按性别与班级分组试分 → 处理冲突 → 发布预留 → 到场核验 → 批量或单人确认入住 → 与迎新完成条件联动。

## 3. 固定房源与资源池

固定层级：校区 → 楼栋 → 楼层 → 房间 → 床位。内部稳定 ID 与展示编号分离；例如房号 0101、床号 01 保留前导零。不能重新编号来迁就分配算法。

导入既有台账：先校验并预览新增/更新/冲突，按校区及楼栋编码、房号、床号匹配；重复导入不重复建床。缺失的台账行不自动删除；已住人或有预留的床位不通过导入直接换人、停用或删除。批量生成房源仅用于确实未建档的楼栋，跳号、不同房型须预览确认。

可分配数量 = 合法启用且真正空闲的床位 − 维修/封存/人工保留/其他计划占用。不能用房间设计容量替代实际有效床位数。

房源池可以按楼栋、楼层、房间缩小范围；学校已分给其他年级的区域不进入本次迎新。特殊需求由授权老师设定适用的床位要求或人工锁定，普通列表不展示隐私原因。

## 4. 规则顺序

### 必须满足，不能为了凑满自动放宽

1. 学生属于当前学校、迎新批次和操作者权限范围；有稳定身份、有效住宿需求。
2. 一人一个有效住宿关系，一床一个有效占用/预留；跨迎新、手工入住、自选、调宿使用相同校验。
3. 校区、楼栋/楼层/房间允许的住宿分区相容。性别缺失或不适用于自动规则的学生进入人工核实，不能猜测。
4. 维修床、已住床、别人预留床、人工锁定床不参加抢占。
5. 已审核的特殊床位要求、学校明确禁止跨越的区域约束必须满足。
6. 同房既有住户和预留住户也参加规则校验，不能只检查本次待分学生。

### 尽量满足，未满足时说明原因

默认顺序：同班同性别集中 → 同专业相近 → 同学院相近 → 减少跨楼、跨层 → 减少碎片空床。楼层均衡为可选低优先级，不能为了均衡把一个班打散。

“相近”先采用同房、同层、同楼的层级距离；房号排序仅是默认顺序，不冒充真实建筑距离。有东西翼、楼梯分区的学校可配置房间区域和顺序，后续再细化距离。

班级不是一个不可拆分大组：先拆为班级内住宿分区组。例如某班男 30、女 20，分别进入合法资源区；不能要求全班混住同楼。六人间的男 30 可用连续 5 间，女 20 可用 4 间且余 4 床。剩余床默认允许同专业其他班兼容学生补齐；若学校选择“不跨班混寝”，应报告由此产生的额外床位需求。

## 5. 自动分配策略

1. 批量加载名单、房源、占用和预留，完成数据校验；输出分区需求/可用/缺口，重复身份等单列。
2. 固定已有有效分配和人工锁定项；不对已有入住者重排。缺少班级者进入待补资料，可由老师明确选择按专业临时分组。
3. 按硬约束拆分学生组与合法资源区。优先处理可选床位最少的受限组，再处理一般组；同条件使用固定排序，重复试分可复现。
4. 为“班级 × 住宿分区”选择能够容纳的相邻房间块；优先同层，容不下时相邻层，再考虑跨楼，并记录拆分原因。不是给每个人单独随机挑一张床。
5. 在房间块内分配到学校已有的床位 ID；尾部零散学生按专业、学院兼容补齐。
6. 有限回退调整尚未锁定的草稿项，减少前序贪心造成的无床和拆班；未找到方案不能直接断言物理容量必然不足，应区分“确实缺口”与“当前规则未找到方案”。
7. 输出成功提议、未分原因、班级跨房/跨层/跨楼分布和剩余床；草稿不占实际床位，也不对学生显示为已分配。
8. 老师锁定或调整后只重算未锁定部分。发布前重新校验真实资源和名单，改变时展示差异；发布成功才创建有效预留。

第一阶段采用确定性分组与有限回退，不引入黑盒 AI。只有实测显示复杂限制下不足，再评估约束求解器；无论算法如何，必须通过同一套服务端硬约束校验。

## 6. 2000 人 / 10 栋 / 2000 床验收样例

以下是测试假设，不是用户学校实际数据：每栋 200 张有效床；男 1200、女 800；6 栋男区、4 栋女区。只有所有其他硬约束也满足时，才能安排满 2000 人。

| 场景 | 系统应该给出的结果 |
| --- | --- |
| 男 1200 / 女 800，男床 1200 / 女床 800 | 可继续试分，仍校验班级与房间限制 |
| 男 1200 / 女 800，男床 1000 / 女床 1000 | 男缺 200、女余 200；不能因总数相等放行不合法安排 |
| 2000 床中 30 张维修、20 张人工保留 | 实际可用 1950，缺 50；列出排除依据 |
| 总量够但某校区或特殊房型不足 | 按硬约束分区报告缺口；不擅自改校区/房型 |
| 全班不能同层 | 明确拆为哪些房间/楼层，给出可调整方案 |
| 不允许跨班混寝而班级人数不整除房型 | 报告规则造成的空床和剩余未分，不隐瞒浪费 |
| 已有 100 人有效住宿 | 从待分需求扣除并单列保留，不重新占第二张床 |
| 5 人身份/性别资料不完整 | 待核实 5，其他合法人员可试分；发布明确剩余事项 |
| 计算中另一个老师占用床位 | 发布重校验冲突；不覆盖实际入住 |

不要宣称 2000 床能同时满足 2000 人并留机动床。机动比例由学校选；若保留 20 张，则只有 1980 张可用于本批，必须真实展示缺口。

## 7. 批量入住

预留与入住分离：分配发布 → 已预留待到场 → 已核验到场待入住 → 已入住。迎新现场报到和宿舍入住是两个业务事件，谁先发生由学校流程配置，不能硬编码先完成迎新才准住宿，也不能互相卡成循环。

教师 PC 的“入住办理”：选择迎新批次，按楼栋/班级过滤，显示学号、姓名、班级、床位、到场核验、当前状态。默认只显示待办理。允许逐房间、当前页或明确的“全部筛选结果”勾选，展示准确数量与排除原因。发钥匙等现场核验完成后提交选中名单，不把尚未到校者一键变已入住。

后台生成一个批量任务，逐人复用真实入住事务。任务有固定请求标识，重复提交返回同任务；相同人员与同预留关系已成功的返回已完成，若已调宿则返回冲突，绝不能重写旧床位。分块执行、进度可恢复；一人的资料问题不让已成功的其他人员反复办理。失败清单可单独重试，页面关闭后任务仍可查询。

每项记录：学生 ID、预留 ID/版本、床位 ID/版本、结果、业务原因、操作者和实际时间。保存成功与通知投递分开，通知失败不能回滚真实入住，也不能导致重复入住。

教师小程序用于现场扫码/检索、核对预留、确认到场及入住；扫码带来的 ID 只是定位，服务端仍校验权限与状态。网络中断显示待确认，恢复后查任务结果，不能凭前端乐观状态写成入住成功。

学生 PC/小程序显示同一份住所与状态，只在发布后展示；已预留提示办理位置，已入住显示正式床位。调宿后显示新床位和办理状态，保留个人历史，不泄露室友联系方式。

## 8. 页面与菜单

迎新保留批次工作入口，“住宿安排”进入同一套宿舍分配工作区并携带 batchId，不再建第二套算法或台账。

宿舍二级模块下：房源、分配、入住、调退、检查、台账。完整名在悬浮提示和标题显示，沿用新 UI 壳。

分配工作区：顶部一行批次/计划/保存状态；下方连续四步“名单与房源 → 分配规则 → 试分与调整 → 发布”。主体左侧班级分组与人数，中间按楼层排列房间和床位，右侧仅选中时出现详情/冲突抽屉。容量用紧凑表格而非大数字卡片；颜色只表达空闲、拟分、预留、已住、不可用，并同时有文字/图例。

提供“班级分布 / 床位图 / 未分清单”切换。2000 人分页/虚拟列表，按楼层加载床位，不一次铺开 2000 个 DOM。点击空床选择待分学生；已预留床办理对应人入住；已住床查看住宿详情与合法调退操作。

## 9. 迎新收尾与异常

- 暂缓报到按有效决定保留床位；取消/未报到处置按既定规则释放未入住预留，不能删除真实入住记录。
- 迟到学生补分剩余合法床位；不自动挤掉已经公布或入住的同学。
- 房间维修或临时封闭产生受影响清单，重新安排需按权限办理，不直接改台账上的房号。
- 批次收尾对照录取/住宿需求、已分、已入住、未到、免住和待处理人数，明确计数口径，保留分配、入住、调退历史。
- 缴费、绿色通道、到场、材料、住宿与学院确认按学校流程检查；不要将未缴费一概当作不能安排宿舍。例外有审批记录且与迎新统一。

## 10. 分批施工与验收

### 发布响应丢失恢复（2026-09-06）

- 宿舍发布请求单独允许 120 秒等待；发生错误后读取真实计划详情，已发布则恢复成功结果，否则提示刷新确认。不自动重放请求，不因读不到结果宣称发布失败。
- 同一计划发布、试分、人工安排取得计划行锁，已发布计划重复发布在校验房源管理范围后返回原结果，不重复创建预留、不增加版本。独立任务/持久进度尚未实现，当前仍为同步执行；增大超时不是后台任务的替代品。
- 前端实际方法的已发布/草稿/断网三项结果恢复测试通过。后端发布变更校验与重复发布回归 1 项通过，82.77 秒；再次发布版本不变、住宿仍只有原有 2 条。
- 教师 PC 构建通过，32.12 秒。日志 `.codex-temp/dorm-publish-retry-test.log`、`.codex-temp/dorm-publish-recovery-build.log`；前端用例 `frontend/tests/dorm-publish-recovery.test.mjs`。尚未进行实际浏览器断网及多进程并发验收。

### 2000 人发布预留实测与下一步（2026-09-06）

- 修复发布前有效性缺口：所有拟分配项重新匹配当前学生名单、可用资源池、楼栋性别规则；重复床位拦截，失败保持草稿且不创建部分预留。学生锁定顺序统一按学生 ID。
- 变更回归：试分后取消一个学生、修改楼栋性别、锁定拟分床位，各自发布返回 409，无残留住宿；恢复合法数据后发布成功。
- 2000 人真实发布成功：2000 条 RESERVED 分配项、2000 条唯一学生/床位 RESERVED 住宿记录、2000 张 LOCKED 且未绑定实际入住人的床，迎新 2000 人同步 ASSIGNED，住宿 checkin_at 全为空。
- 发布本机耗时 49.543 秒，相关 2 项测试通过，总测试耗时 138.11 秒。日志 `.codex-temp/dorm-large-publish-test.log`。不是微信真机或四端批量实际入住验收。
- 重要未完成项：长耗时发布应接入可追踪任务与结果恢复，防止前端超时造成“实际成功却提示失败”；同样用于后续批量入住。当前仍为同步 HTTP，不能将功能测试通过当作大批次交互已达标。

### 2000 人试分接口实测（2026-09-06）

- 性能改动：一次读取本计划分配项并在内存复用，避免逐人 SELECT；同房空床只评分一次；管理范围校验按唯一楼栋执行，权限规则不变。
- 隔离 MySQL 数据：2000 名稳定关联新生，男 1200 / 女 800，10 栋楼（6 男 / 4 女），每栋 5 层、每层 10 间、每间 4 床，共 2000 床；50 个班，每班 40 人。
- 真实 dry-run HTTP 请求生成 2000 个不同学生/不同床位的 PROPOSED 项，无未分人员，楼栋性别全部兼容；此测试的 50 个班各自都在同一楼层；床位仍为 VACANT，未伪造实际入住。
- 本机接口实测 4.835 秒（不含测试数据准备），SQL 计数 SELECT 80、UPDATE 5、INSERT 2001；不是并发压测、生产 SLA 或所有规则组合的性能承诺。
- 与人工安排保护、同班楼层接口用例合并执行，3 项通过，总测试耗时 105.66 秒。日志 `.codex-temp/dorm-large-batch-test.log`；用例 `backend/tests/test_dorm_allocation_large_batch.py`。
- 尚未证明：2000 人发布预留/批量实际入住、大班拆层、资源碎片、复杂特殊床位、混合楼房间限制、四端并发与真机。继续保留这些验收项，不以本次试分成功替代完整目标。
