## 1. 模块定位与真实学校业务价值

### 1.1 一句话定位
把「学生活动全流程（发布→报名→签到→名单确认→学时 / 德育积分生成）」做成**一套活动闭环底座**，并将该底座**复用给第二课堂、志愿服务、社团活动、党团活动**，最终把学生的活动经历、二课学时、志愿时长、社团任职、党团发展阶段沉淀到**学生画像（360）**，供综合测评、评优、奖助评审引用。

依据：《全业务流程设计总册》§4.2（L669–675）目标「活动全流程沉淀第二课堂记录」；§4.3（L677–683）社团活动走 4.2 流程挂 `org_id`；ABCD 总表 L490「活动二课与社团 = 活动闭环复用（活动 / 二课 / 社团 / 党团）」。

### 1.2 真实学校谁用、解决什么
| 角色 | 真实场景 | 解决的痛点 |
|---|---|---|
| 学工处 / 团委老师 | 发布校级活动、审核社团年审、汇总二课积分与团建台账 | 替代 Excel + 微信群报名，学时 / 积分可核查可上报 |
| 学院学工 / 辅导员 | 发布班级 / 院级活动、确认参与名单、把活动经历带进画像 | 活动参与情况进画像，支撑评优与谈话 |
| 学生 | 手机报名、扫码 / 定位签到、查我的二课学时 / 志愿时长 | 少跑腿、进度可见、积分透明 |
| 社长 / 学生干部 | 社团纳新、成员管理、协助名单 / 签到（被授权） | 社团活动规范化，任职写入干部履历 |
| 学院党委 / 组织委员 | 入党积极分子—发展对象—预备—正式阶段台账 | 发展过程留痕、时长校验、政治面貌更新 |

依据：总册 §4.2 角色（L671）；权限总控 L269「团委老师 · 团学 / 二课 · 全校 / 本院活动 · 活动 / 志愿 / 社团 / 党团、二课积分」；L339 学生干部「仅本人 + 被授权协助项」。

### 1.3 商业价值（投标响应口径，CLAUDE.md §0.0 原则 15）
第二课堂成绩单、志愿时长认定、智慧团建台账是职校 / 高校**必答的招标条目**；一套活动底座覆盖四类组织业务，是「统一、可交付、可验收」的商业化卖点。**当前为能力池 / 补强包（planned），非底座已交付能力**，不得标 implemented（对标审计第五步第 15 条「杜绝有菜单无闭环」；navPlan 全 `P`）。

## 2. 三家成熟系统对标表（严格按 CLAUDE.md §0.0 十点）

> **对标依据说明**：仓库《商业化对标审计（第一轮）》的三家基准为**正方 / 强智 / 青果**（该文 L6 明示，对标其产品精华与业务成熟度，不抄袭界面 / 代码 / 数据库）。以下 A/B/C 即沿用该三家。
> **重要补充（需人工确认 / 建议联网核实）**：就「第二课堂成绩单 / 志愿时长 / 智慧团建」这一**细分赛道**，市场验证最充分的是**到梦空间（PU 口袋校园）/ 团中央「智慧团建」/ 易班**等专用系统。本环境未联网，未纳入 A/B/C 主对标，仅在「② 最值得吸收」处以「行业常识补充」标注，正式投标前**需人工确认或联网核实**。

### ① 对标对象 A —— 正方（教务 / 学工一体化）
- **核心流程**：活动 / 二课以「项目 → 报名 → 参与认定 → 学分 / 学时入库 → 综测引用」为主线，强调二课学分与培养方案 / 综测挂钩。
- **角色**：管理员发布、学生报名、负责人认定、综测模块消费。
- **字段**：活动名 / 类型 / 学时 / 学分规则 / 参与名单 / 认定结果。
- **亮点**：二课学分与综合测评、评奖评优打通，数据同源。
- **缺点**：移动端签到 / 志愿时长等高频体验相对弱；社团 / 党团深度一般。
- **依据 / 需人工确认**：仓库对标审计以「产品成熟度」层面引用正方（L6），**未逐字段列出正方活动模块细节**；上述流程为该赛道通识，**具体字段与开关需人工确认**。

### ① 对标对象 B —— 强智（综合教学 / 学工管理）
- **核心流程**：活动发布 → 报名 → 签到 → 结果统计，强调台账与统计报表、批量导入导出。
- **角色**：处 / 院分级发布、学生报名、管理员统计。
- **字段**：活动分类、范围、名额、时间地点、签到方式、参与统计。
- **亮点**：台账 / 报表 / 导出成熟（对标审计原则 2「所有业务必须有台账」、原则 8「导入 / 导出 / 打印 / 归档模板」）。
- **缺点**：二课积分复杂规则、志愿时长认定、社团年审换届等深度闭环需扩展。
- **依据 / 需人工确认**：对标审计原则 2 / 8（该文第三步 L77 / L89）为强智类成熟软件的通用精华；**强智活动模块具体字段需人工确认**。

### ① 对标对象 C —— 青果（学工 / 迎新）
- **核心流程**：偏学工事务与迎新，活动 / 二课作为学工台账一环，强调与学生画像、辅导员工作台聚合。
- **角色**：辅导员 / 学院为主，学生移动端参与。
- **字段**：活动记录、参与情况、进画像事件。
- **亮点**：活动经历进「学生画像」、辅导员动线聚合（对标审计原则 11 L95）。
- **缺点**：社团 / 党团 / 志愿专业深度弱于专用系统。
- **依据 / 需人工确认**：对标审计原则 11（L95）；**青果活动模块细节需人工确认**。

### ② 三家共同具备的核心功能（= 本项目必须具备的基础能力）
1. 活动 / 项目**发布**（范围 / 名额 / 时间地点 / 学时或学分规则）。
2. 学生**报名**（范围校验、名额校验、时间冲突、防重复）。
3. **签到 / 参与认定**（扫码 / 定位 / 名单确认）。
4. **学时 / 学分 / 志愿时长入库**并可追溯来源。
5. 活动经历 / 积分**进学生画像**，供综测 / 评优 / 奖助引用。
6. **台账 + 统计报表 + 导出**（脱敏 + 水印）。

依据：总册 §4.2 主流程（L672）已完整覆盖 1–5；对标审计原则 2 / 8 / 9 覆盖 6；API 契约草案 §12 端点 91–96（L353–358）已契约化 1–4。

### ③ 三家里最值得吸收的最佳做法
- **一套活动抽象复用多业务**：志愿服务复用活动状态机（`activity_type=VOLUNTEER`，状态机 §10 L396），社团活动挂 `org_id` 复用活动流程（总册 §4.3 L680）——**避免造四套轮子**（CLAUDE.md §0.0「三家共同核心即基础能力」）。
- **积分 / 学时同源，杜绝两套数**：二课学时由「活动确认」唯一出口生成 `t_affairs_activity_credit`（总册 §4.2 L672），供综测引用（§4.8 L716），**统计口径与画像口径一致**（对标审计原则 9 L91）。
- **移动端优先**：报名 / 签到高频动作全在小程序（API §17 端点 121–123 L458–460），防重复用 `createSubmitLock + request_id` 幂等（状态机 §10.1 L416）。
- **行业常识补充（需人工确认 / 建议联网核实）**：到梦空间 / 智慧团建的「学时自动认定 + 第二课堂成绩单打印 + 团组织关系电子化」是该赛道最强卖点，建议正式投标前核实并评估吸收。

### ④ 本项目当前已有能力（底座 / 契约层面）

## 4. 业务流程与状态机

> 枚举来源：状态机文档 §10（L393–422）+ 总册 §4.2/4.3/4.4。活动主状态机为 **[推导枚举，需现场确认]**（状态机 §10 L395、§附录 L645「学生活动：推导，需确认，不走审批」）。

### 4.1 活动主状态机（13A-12，志愿复用）
**枚举**：`DRAFT / PUBLISHED / ENROLL_CLOSED / ONGOING / FINISHED / CONFIRMED / CANCELLED / ARCHIVED`（状态机 §10 L395）
**报名子状态**：`ENROLLED / WAITLIST / CANCELLED / CHECKED_IN / CONFIRMED`（总册 §4.2 L673）

| 当前态 | 操作 | 责任人 | 目标态 | 通知 | 审计 | 进 360 |
|---|---|---|---|---|---|---|
| DRAFT | 编辑（范围 / 名额 / 时间地点 / 学时积分规则） | 处 / 院 / 辅（范围随角色） | DRAFT | — | 否 | 否 |
| DRAFT | 发布 | 处 / 院 / 辅 | PUBLISHED | PUBLISHED_NOTICE→范围内学生 | 是 | 否 |
| PUBLISHED | 学生报名（范围内 / 未满 / 不冲突 / 未重复） | 学生本人 | PUBLISHED（报名记录） | — | 是 | 否 |
| PUBLISHED | 取消报名（截止前，释放名额） | 学生本人 | PUBLISHED | — | 是 | 否 |
| PUBLISHED | 报名审核（志愿类可开启） | 发布方负责人 | PUBLISHED | STATUS_CHANGED→学生 | 是 | 否 |
| PUBLISHED | 报名截止（手动 / 到时） | 发布方 / 系统 | ENROLL_CLOSED | — | 是 | 否 |
| PUBLISHED / ENROLL_CLOSED | 取消活动（原因必填≥5 字） | 发布方 / 上级 | CANCELLED | STATUS_CHANGED→已报名学生 | 是 | 否 |
| ENROLL_CLOSED | 活动开始 | 系统 / 发布方 | ONGOING | DEADLINE_REMINDER→已报名学生 | 否 | 否 |
| ONGOING | 学生签到（扫码 / 定位，防连点） | 学生本人 | ONGOING（签到记录） | — | 是 | 否 |
| ONGOING | 活动结束 | 系统 / 发布方 | FINISHED | — | 否 | 否 |
| FINISHED | 确认名单 + 生成学时 / 德育积分 / 志愿时长 | 发布方负责人 | CONFIRMED | STATUS_CHANGED→参与学生 | 是 | **是（活动经历 + 二课记录）** |
| CONFIRMED | 收编归档 | 处 | ARCHIVED | ARCHIVE_NOTICE | 是 | 否 |

**非法转移防护（状态机 §10.1 L413–417）**：非 PUBLISHED / 满员 / 范围外 / 重复报名 → 409 或 403；非 ONGOING / 代签 → 409 / 403 + 幂等锁；CONFIRMED 后改名单 → 409（需撤销确认并审计，仅发布方上级）。
**超期自动转移（§10.2 L419–422）**：到截止 / 开始 / 结束时间自动流转；FINISHED ≥7 天未确认 → 提醒发布方；≥30 天 → 按签到记录自动 CONFIRMED（规则中心可关闭，参数见 §5）。

### 4.2 社团 / 成员状态机（总册 §4.3 L681 · 波次 3 · 待确认）
- **社团**：`APPLYING / ACTIVE / ANNUAL_REVIEW / SUSPENDED / DISSOLVED`。
- **成员**：`APPLYING / ACTIVE / QUIT`。
- **主流程**：建社申请（章程 / 指导老师 / 发起人）→ 团委审批 → 成立 → 纳新（入社申请→社长审）→ 年审 → 换届备案；社团活动走 §4.1 挂 `org_id`。

### 4.3 党团建设阶段状态机（总册 §4.4 L689 · 波次 3 · 待确认）

## 12. 验收标准（页面级用例）

> 遵循 CLAUDE.md §20 与《学工中心页面级验收用例总表》口径。planned 页做完一页验收一页，未达标只能 partial 并写入历史欠账（CLAUDE.md §35）。

**波次 1（活动底座 + 二课）必过项：**
1. **进入**：活动列表 / 详情可进入，无控制台报错；planned 未做的页仍进公共占位页（不空白、不假按钮）。
2. **旧路由兼容**：如有旧 `/activities` 入口，redirect 到新路由不 404（CLAUDE.md §9.1）。
3. **权限**：无 `activity.view` 权限 → 菜单不显示且接口 403；辅导员只见本班 + 自办活动，跨班活动操作 → 403002。
4. **数据范围**：学生只见「命中 scopeConfig 的可报名活动 + 本人报名记录」；范围外报名 → 403002。
5. **状态机**：满员 / 重复 / 已截止报名 → 409001；非 ONGOING 签到 → 409001；CONFIRMED 后改名单 → 409。
6. **脱敏**：名单页姓名 / 学号按配置脱敏；导出名单**带水印 + 导出台账 + 审计**。
7. **积分不可重复**：同一活动同一学生二课学时只入账一次（唯一约束），撤销确认才可重算。
8. **三态**：loading（骨架）/ empty（无活动为 0）/ error（traceId + 重试）齐全（施工图 L1524）。
9. **审计**：发布 / 取消 / 名单确认 / 报名 / 签到均可在审计中查到，可追溯到人。
10. **无假按钮 / 无 mock**：写操作真实落 MySQL，刷新后仍在（CLAUDE.md §39.5）。

**波次 2（志愿 / 统计）**：志愿复用活动状态机跑通「项目→报名→时长确认」；活动统计任一指标可下钻到明细且首页-明细对账 0 差异（对标审计原则 9）。
**波次 3（社团 / 党团）**：**API 冻结前不得开工做真闭环**，只保留占位页；冻结后按 §4.2/§4.3 状态机验收，政治面貌回写走更正接口 + 审计。

## 14. 施工顺序与依赖

### 14.1 波次与依赖
```
波次 1（活动闭环底座）——最高优先，其余全部复用
  前置：t_affairs_activity/_signup/_credit 落地（Alembic，需人工确认建表）
        + API 91–96/121–123 已契约
  内容：活动管理、活动报名与签到、第二课堂积分（学时台账）
  产出：一套活动状态机 + 报名签到 + 名单确认生成学时 + 进画像
        ↓ 复用
波次 2（复用增量）
  志愿服务（activity_type=VOLUNTEER，时长替代学时）
  活动统计（复用 stats/overview + stats/activity 下钻）
        ↓ API 冻结后
波次 3（能力池，API 未冻结先不做真闭环）
  社团管理 → 学生干部与组织 → 党团建设
  前置：/clubs、/organizations、/party-league 契约冻结（需人工确认）
```

### 14.2 复用与只读边界
- **复用**：活动状态机、报名签到、`t_affairs_activity_credit`、360 事件、公共组件（AppStatusTag / AppFileList / AppApprovalPanel / AppExportButton，navPlan L46–47）、Excel 底座、公共日期组件。
- **只读引用**：`t_student_profile.political_status`（仅党团回写走更正接口）；综测 / 评优 / 奖助**读**二课积分，不在本模块反算。
- **禁止**：重复建教师账号体系、重复建平行活动表、二课积分 mock、政治面貌直写主档、社团 / 党团页臆造 API。

### 14.3 风险点
1. **枚举未冻结**：活动状态 / 类型枚举标「推导需确认」，开工前须甲方拍板（否则返工）。
2. **社团 / 党团 API 空缺**：波次 3 无契约，**严禁为凑菜单造假闭环**（对标审计第 15 条 / CLAUDE.md §42.4）。
3. **积分重复入账**：必须唯一约束 + 撤销确认才可重算，否则综测数据失真。
4. **建表涉数据库**：需人工确认后再写迁移（CLAUDE.md §19）。
5. **德育积分规则 / 综测公式依赖外部口径**：需现场确认，先做「活动生成流水」，规则引擎进 backlog。
