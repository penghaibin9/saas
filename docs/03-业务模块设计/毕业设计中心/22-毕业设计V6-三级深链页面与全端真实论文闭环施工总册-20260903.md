> 适用仓库：`penghaibin9/saas`  
> 施工分支：`agent/graduation-v6-24page-ui-refactor-20260903`  
> PR：`#254`（保持 Draft，门禁全通过前不得合并）  
> 冻结基线：不改正式路由名、权限键、数据范围、API 契约、业务状态机、canonical FileVersion、`expectedVersion`、文件票据与扫描门。

## 1. 本轮为什么不能只改 24 个三级入口

24 个三级入口解决的是“从菜单进入哪里”；教师真正完成业务，还会继续进入新建、编辑、详情、分配、审核、评分、整改、归档等深链页。当前路由中存在约 39 个独立深链入口，加上 `formKey`、`panel`、`action` 等页内变体，实际办理形态超过 50 种。

现状主要问题不是接口全是假，而是很多页面仍停留在“字段堆叠式后台表单”：

1. 看不到从哪个队列或学生进入；
2. 看不到当前批次、业务对象和状态；
3. 不知道还缺哪些条件；
4. 保存按钮只有“成功/失败”，没有服务器回读和后续责任人；
5. 提交中仍可能切批、离页或重复点击；
6. 新建页与详情页视觉差距大，老师会误以为进入了另一套系统；
7. 窄屏或 125% 缩放时字段被挤压，但又不能通过隐藏字段解决。

因此，深链页重构必须同时解决业务上下文、视觉层级、防错、状态回读和返回路径，不能只换颜色或卡片圆角。

## 2. 深链页面统一办理结构

所有新增、编辑、处理类深链页采用以下结构；不同业务允许变化，但不得降级为通用空白表单。

### 2.1 页首：从哪里来、正在办什么

- 安全返回：优先使用白名单内 `returnTo`，否则回到所属三级入口；
- 面包屑：毕业设计中心 / 当前办理事项；
- 业务状态：新建主档、待完善、待审核、可进入发布前检查、已归档等；
- 当前批次、学生、题目、导师、答辩组等真实对象摘要；
- 提交中禁用返回，并由路由守卫阻止卸载。

### 2.2 主工作面：按真实业务分段

每个页面按业务步骤组织，不按数据库字段顺序组织。例如：

- 新建批次：批次身份 → 实施边界；
- 题目申报：题目身份 → 指导与范围 → 完成标准 → 保存方式；
- 答辩组：分组与排期 → 答辩职责 → 学生分配；
- 成绩处理：当前学生 → 原始成绩事实 → 本次命令 → 服务器回读；
- 归档：缺件事实 → 预览凭证 → 用户确认 → 执行 → 对账。

### 2.3 右侧办理栏：完成条件、风险和下一步

右侧栏只显示会改变老师判断的信息：

- 当前已满足 / 未满足条件；
- 服务端仍会校验的规则；
- 保存后进入哪个队列；
- 下一责任角色；
- 是否会影响学生端、教师端、小程序；
- 是否必须重新发布、重新预览或重新确认。

不得把 route、permission、API path、allowlist 等开发说明放进生产页面正文。

### 2.4 页底：明确命令语义

- “保存草稿”“保存并提交审核”“创建后分配学生”“保存编排”必须区分；
- 提交时锁定对象、批次、版本、路由上下文；
- 成功后重新读取服务器最新状态；
- 网络结果不确定时禁止盲目重复点击；
- 驳回、撤回、作废必须要求原因；
- 历史版本与审计记录不得被覆盖。

## 3. 深链路由审计与重构优先级

### P0：直接影响真实主链路，必须本轮闭环

| 业务域 | 深链页 | 重构目标 | 强制业务门禁 |
|---|---|---|---|
| 批次 | `batches/create`、`batches/:id/edit` | 批次身份、周期、范围、保存后规则维护 | 批次编号唯一；状态机不在前端伪造 |
| 题目 | `topic-lib/create`、`topic-lib/:id/edit` | 题目、导师、适用范围、成果标准、审核交接 | 审核通过前不得进入正式选题 |
| 学生 | `students/create`、`students/:id/assign-topic` | 主档来源、批次、题目关系、保存后去向 | 不建立第二套学生主档；跨批写入由后端拒绝 |
| 导师 | `mentors/assign/:studentId` | 当前学生、导师资格、容量、冲突、结果回读 | 无资格或超容量不得分配 |
| 过程 | `process/:studentId/:action` | 完整 WorkContext、最近事实、节点准入、保存返回 | 保留 `batchId/studentId/panel/queue/source/returnTo` |
| 成果 | `finals` 内部成果批阅工作面 | 同一队列、同一论文、同一 FileVersion、真实 PDF 阅读 | 扫描门、版本冲突、`expectedVersion` 任一失败即锁定 |
| 答辩 | `defense/groups/create`、`defense/groups/:id/edit` | 排期、真实人员身份、学生分配、发布前明显缺口 | 组长、秘书、评委、时间、地点、学生和回避规则 |
| 评分 | `defense-grade/:studentId/form` | 评委本人评分与秘书确认彻底分离 | 评委不能确认全组，秘书不能代替评委补分 |
| 反馈 | 学生 PC 评阅反馈与整改重交 | 冻结被评版本、老师意见、新版本上传、历史时间线 | 重交创建新 FileVersion，不覆盖旧版本 |

### P1：频繁使用，P0 通过后逐组施工

| 业务域 | 深链页 | 设计方向 |
|---|---|---|
| 题目维护 | `capacity`、`requirements`、`attachments`、`category`、`detail` | 统一题目身份条；每页只处理一种变化；返回原 panel |
| 选题轮次 | `topic-rounds/create` | 基本信息、开放时间、志愿规则、容量与发布检查分段 |
| 题目变更 | `topic-changes/:id` | 原题目 / 新题目对照、申请理由、审核后真实关系迁移回读 |
| 学生分组 | `students/_batch/group`、`students/:id/group` | 先预览影响范围，再提交；批量结果给出成功、失败、错误行 |
| 学生答辩组 | `students/:id/defense-group` | 当前阶段、候选组、容量、回避冲突、保存回读 |
| 导师主档 | `mentors/create/edit/detail/eval` | 资格、容量、指导负荷、评价事实分区，不堆满一页 |
| 模板 | `templates/create/edit` | 类型、适用范围、文件版本、默认模板冲突、启用状态 |
| 评阅分配 | `review-assign`、`more/peer-assign` | 回避关系、候选评阅人、容量、批量结果、可撤回条件 |

### P2：低频治理页，但不能保持旧系统质感

- 批次详情；
- 课题管理编辑 / 详情；
- 统计报表；
- 新增答辩专家；
- 互查 / 专家 / 申诉；
- 审计日志；
- 归档后只读详情；
- 其他 `formKey` 低频处理页。

P2 页面复用统一办理壳，但仍必须给出所属业务对象、当前状态、返回上下文和真实审计结果，不得变成文字占位或“万能表单”。

## 5. 真实毕业论文跨端闭环

### 5.1 唯一可信业务链路

```text
学生 PC 选择真实 PDF
  → POST /files
  → 文件安全扫描
  → 学生确认提交论文成果
  → 创建 / 绑定 canonical FileVersion
  → 教师 PC 待评成果队列出现同一论文
  → 授权 ticket 获取 PDF 字节
  → PDF.js 渲染真实 canvas
  → 老师核对论文、查重、SHA、业务版本和 FileVersion
  → 通过或退回（绑定 record + expectedVersion + fileVersionId）
  → 服务器状态回读 + 审计留痕
  → 学生 PC 收到反馈并看到被冻结的被评版本
  → 学生上传修改后的新文件并重交
  → 新 FileVersion 进入教师队列，旧版本保持只读
```

### 5.2 教师 PC 强制验收

不能只断言页面出现“文件名”或“版本”文字，必须同时满足：

1. 当前记录来自服务端待评成果队列；
2. 页面展示 canonical FileVersion 和业务 `expectedVersion`；
3. 文件安全门为通过；
4. 使用授权 ticket，不暴露永久直链；
5. `[data-preview-adapter="pdf"]` 可见；
6. PDF.js canvas 的位图宽高与可见尺寸均大于 0；
7. 历史版本只能阅读，不得用于覆盖当前版本；
8. 版本变化时旧批阅意见草稿保留，但必须人工确认是否带入新版本；
9. 通过 / 退回后重新读取服务器状态。

### 5.3 教师微信小程序强制验收

教师小程序不是另建一套论文数据。它必须：

1. 读取和教师 PC 相同的待评成果队列；
2. 展示与教师 PC 相同的 FileVersion；
3. 通过 `/mobile/graduation/material-center/files/{fileId}/ticket` 签发一次性预览票据；
4. 读取真实 PDF 字节，再交给微信原生 `openDocument`；
5. 返回批阅页后重新读取服务端详情；
6. FileVersion、SHA 或业务版本变化时锁住旧版审核；
7. 提交审核时同时发送 `materialVersion + fileVersionId`；
8. 网络或原生预览失败时给出可执行提示，不伪造“已预览”。

H5 浏览器验收用于验证票据、真实 PDF 字节、同一 FileVersion 和返回重验；微信开发者工具 / 真机验收还必须验证 `uni.openDocument` 的原生打开行为。

### 5.4 学生 PC 与学生微信端职责边界

- 学生 PC：正式论文、较大 PDF / DOCX、整改重交、版本历史与完整反馈的主工作面；
- 学生微信端：阶段状态、待办、老师反馈摘要、轻量材料、提醒和跳转；
- 大型毕业论文不在微信端强行上传，避免文件选择、网络中断和内存限制导致假成功；
- 小程序必须明确提示“到学生 PC 完成正式论文上传”，并在上传后刷新到同一服务端状态。

这不是功能缩水，而是基于终端能力的职责分工；跨端状态必须实时一致。

## 6. 新增机器门禁

### 6.1 静态合同

`graduation.v6-deep-link-and-cross-client.contract.test.mjs` 冻结：

- 公共办理壳；
- 批次、题目、答辩组三类深链；
- 教师 PC canonical FileVersion + PDF.js canvas；
- 学生 PC 冻结版本与整改重交；
- 教师小程序票据、同版本、返回重验；
- 学生小程序与学生 PC 的大型论文职责边界。

### 6.2 真实浏览器跨端门禁

`graduation-v6-thesis-cross-client.spec.mjs` 使用同一篇真实 PDF 依次验证：

1. 学生 PC 上传文件和提交论文成果；
2. 教师 PC 显示同一待办；
3. 教师 PC PDF.js 真实绘制 canvas；
4. 读取教师 PC 当前 canonical FileVersion；
5. 教师小程序显示同一 FileVersion；
6. 小程序签发票据并下载以 `%PDF-` 开头的真实字节；
7. 预览返回后重新获取服务端详情；
8. 没有版本冲突时审核按钮重新开放。

## 7. 浏览器验收矩阵

### 深链页面

每个 P0 深链至少检查：

- 1760×900；
- 1440×900；
- 1366×768；
- 1280×800；
- 1366×768 + 125% 缩放；
- 首屏能看到业务对象、关键表单和主按钮；
- 页面无横向溢出；
- 右侧完成条件不会遮挡主表单；
- 提交中返回、切批、重复点击被阻止；
- 保存 / 取消后回到原 `returnTo`；
- API 失败、无权限、无数据、版本冲突均有真实状态页。

### 全端流程

| 环节 | 学生 PC | 教师 PC | 教师微信端 | 学生微信端 |
|---|---|---|---|---|
| 任务书 | 确认 / 查看 | 下达 / 查看 | 查看 / 处理高频项 | 查看状态 |
| 开题 | 填写、上传、提交、重交 | PDF 批阅 | 移动批阅与版本重验 | 状态与反馈 |
| 过程指导 | 查看与提交材料 | 连续指导工作台 | 记录高频指导 | 查看反馈 |
| 论文成果 | 正式上传、提交、整改重交 | PDF.js 阅读、通过 / 退回 | 原生预览、通过 / 退回 | 状态、反馈、PC 接力 |
| 答辩 | 查看安排 | 编排、评分、确认 | 查看安排、本人评分 | 查看时间地点 |
| 成绩 | 查看发布结果 | 核算、复核、发布、撤回 | 高频复核 | 查看结果 |
| 归档 | 查看完成状态 | 缺件、预览、备案、对账 | 查看提醒 | 查看状态 |

## 8. 禁止的错误施工方式

1. 只改主菜单页，深链继续使用旧白底表单；
2. 为了好看隐藏容量、版本、扫描、SHA、冲突、错误行等业务证据；
3. 教师端只显示文件名，不真正读取 PDF；
4. 小程序展示另一套 mock 论文或另一套状态；
5. 让管理员代替评委提交本人评分；
6. 前端推导答辩轮次完整、论文可通过或学生可归档；
7. 重交覆盖旧文件；
8. 使用永久文件 URL 绕过 ticket；
9. 为使 CI 变绿覆盖既有 Gold；
10. 在没有机器证据时把 PR 改为 Ready 或直接合并。

## 9. 完成定义

本轮只有同时满足以下条件才算完成：

- P0 深链全部按真实办理结构完成；
- 批次、题目、答辩组真实新建 / 编辑浏览器流程通过；
- 同一篇论文在学生 PC、教师 PC、教师小程序保持同一 FileVersion；
- 教师 PC PDF canvas 真渲染；
- 微信原生预览经开发者工具 / 真机验证；
- 老师退回后学生 PC 收到真实反馈并重交新版本；
- 学生微信端能看到状态并正确接力到学生 PC；
- route、permission、data scope、API、状态机、XLSX、审计和版本合同无回归；
- CI、Graduation Targeted Validation、Exact-Head E2E 和 Playwright 全绿；
- PR 反向审计无未解释阻断。
