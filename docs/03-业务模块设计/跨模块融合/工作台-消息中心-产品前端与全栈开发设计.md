## 1. 最终产品结论

消息中心不是单一“收件箱页面”，而是全校统一的消息基础设施，由四部分组成：

1. **我的消息**：老师 PC、学生 PC、老师小程序、学生小程序读取同一份个人消息和已读状态。
2. **通知发布**：辅导员、学院、校级部门按授权范围发布人工通知。
3. **发布管理**：草稿、审核、定时、发布、撤回、失效、送达、已读、确认回执和失败重试。
4. **业务事件接入**：请假、成绩、课表、考试、实习、毕设、风险等模块通过统一服务产生消息，禁止各模块继续直接随意写消息表。

必须严格区分：

| 对象 | 含义 | 核心状态 |
|---|---|---|
| 公告/通知 | 让接收人知道一件事 | 未读、已读、已确认 |
| 待办 | 接收人必须办理一项业务 | 待处理、已处理 |
| 业务进度 | 告知本人申请状态变化 | 未读、已读 |
| 紧急消息 | 需要立即关注并可要求确认 | 未送达、已送达、已读、已确认 |

`已送达 ≠ 已读 ≠ 已确认 ≠ 业务已办理`，数据库、接口和页面不得混用。

### 2.2 当前明确缺口

1. `navPlan.js` 中 `wb-messages` 仍是 planned，没有 PC 管理端正式路由。
2. PC 顶部铃铛跳到 `/admin/approval/todos`，角标是待办数，不是消息未读数。
3. 学生 PC“全部已读”只是演示提示。
4. 老师小程序消息由业务列表临时拼装，并含固定 `sys-1` 文案，不是可追溯消息。
5. 老师小程序“全部已读”只改本地变量。
6. 消息详情“确认回执”仍提示即将开放。
7. 现有发布能力只圈学生，不能准确区分全校学生、全校教职工、全校师生。
8. 学院端选择学院仍可能手输 ID，不能接受。
9. 没有发布单、受众快照、审核、定时、撤回、失效、附件、紧急等级和统计。
10. 全校发送同步逐行写消息，存在超时、半成功和重复发送风险。
11. `receiver_id` 未声明是用户 ID、学生档案 ID 还是教师档案 ID，存在漏发、错发和 ID 碰撞风险。
12. 站内消息与 `NotificationTask/Log` 外部渠道没有统一关联。
13. 现有偏好可能把消息从聚合列表过滤掉；正式消息不应因关闭推送而消失。
14. 缺少发布频控、静默时段、敏感内容治理、深链白名单和附件鉴权。
15. 缺少多角色教师的“当前身份消息”和“个人全局消息”边界。
16. 平台运营公告、学校公告、业务自动通知之间没有清晰边界。

### 2.3 补充边界裁决

- **平台运营公告**：只发给租户学校管理员/授权人员，不直接绕过学校向学生群发。
- **学校全校公告**：由学校授权发布角色操作。
- **业务自动通知**：只能使用登记的事件码和模板，不能让业务模块传任意接收范围。
- **个人消息**：跨角色均可见；绑定某工作身份的消息只在对应激活身份下显示。
- **用户偏好**：只关闭小程序弹出、短信、微信等外部提醒，不删除站内消息。

### 2.4 专业复审后的五项不可妥协决策

1. **消息中心按三个平面建设**：
   - 控制面：编辑、受众、审核、定时、撤回、统计；
   - 投递面：受众展开、站内落库、外部渠道、重试、死信；
   - 收件面：列表、详情、已读、确认、业务跳转。
   三者共用一套领域服务和状态语义，但不能写成一个超大接口或超大 Vue 页面。
2. **业务事务与消息投递解耦**：请假审批、成绩发布等业务提交成功时，只在同一数据库事务写入事件 outbox；事务提交后再异步生成消息。消息渠道故障不能回滚已经成功的业务，业务回滚也不能留下幽灵消息。
3. **唯一接收人主键是 `user_id`**：学生档案 ID、教师档案 ID、角色 ID 只能作为来源或上下文，不能继续混装到 `receiver_id`。无法确定身份的历史记录不得猜测回填，避免把隐私消息关联给错误账号。
4. **发布接口只负责受理，不承诺同步完成**：班级或全校发布统一返回 `QUEUED/PUBLISHING` 和发布单 ID；后台任务分批展开受众并投递，前端显示真实进度。
5. **已读、确认、业务完成、外部送达永久分离**：任何“全部已读”、页面预取、推送成功都不能代替本人确认，更不能代替业务办理完成。

最终调用关系：

```text
人工发布 ─┐
业务事件 ─┼→ 发布单/事件 Outbox → 受众快照 → 个人收件记录 → PC/小程序
平台事件 ─┘                         └→ 渠道任务 → 微信/短信
                                                ↓
                                已读、确认、失败、重试、审计、统计
```

## 4. PC 前端总体设计

### 4.1 视觉原则

- 延续系统现有清透学院蓝、字体和设计 token，不硬编码新主题。
- 工作区充分利用右侧宽度，消息阅读使用“三栏式”，发布和统计使用全宽工作区。
- 标题正文为主，颜色只表达状态；紧急消息必须同时使用文字、图标和色彩。
- 默认字号不得小于现有正文标准；消息标题、紧急要求、截止时间应明显突出。
- 全部页面具备 loading、empty、error、no-permission 和 retry。

### 4.2 “我的消息”三栏布局

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 消息中心                                             [全部已读] [消息设置] │
├──────────────┬─────────────────────────────┬───────────────────────────────┤
│ 分类导航     │ 消息列表                    │ 消息详情                      │
│              │                             │                               │
│ 全部   18    │ [紧急] 校园停电应急通知     │ 校园停电应急通知              │
│ 紧急    1    │ 信息工程学院 · 10:20        │ 发布单位 / 发布时间 / 有效期  │
│ 公告    4    │ 尚未确认                    │                               │
│ 业务通知 6   │                             │ 完整正文                      │
│ 待办提醒 3   │ 成绩复核结果已发布          │ 附件                          │
│ 系统消息 4   │ 教务中心 · 昨天             │                               │
│              │                             │ [我已知晓] [去办理]            │
│ 未读         │                             │ 操作记录 / 撤回说明            │
│ 已读         │                             │                               │
└──────────────┴─────────────────────────────┴───────────────────────────────┘
```

布局比例建议：

- 左栏 180–220px；
- 中栏 360–440px；
- 右栏占剩余空间，正文最大阅读宽度约 860px；
- 窄屏时右侧详情改抽屉；禁止三栏横向挤压。

列表排序：

1. 未失效紧急且未确认；
2. 置顶重要消息；
3. 其他消息按发布时间倒序。

列表字段：

- 类型、优先级、标题、发布单位、摘要、发布时间；
- 未读点、待确认标识、附件标识、截止时间；
- 已撤回、已失效必须明确标记。

详情字段：

- 标题、发布单位、发布人快照、发布时间、有效期；
- 正文、附件、联系人、业务来源；
- 已读时间、确认时间、撤回/更正说明；
- `去办理` 使用登记的 `actionKey + params`，禁止任意外部 URL。

### 4.3 “通知发布”四步向导

```text
① 内容与级别 → ② 接收范围 → ③ 渠道与时间 → ④ 预览并提交
```

#### 第一步：内容与级别

| 字段 | 规则 |
|---|---|
| 消息类型 | 公告、业务通知、提醒、紧急消息 |
| 标题 | 必填，4–100 字 |
| 摘要 | 可选，最多 120 字；为空由后端安全截取正文纯文本 |
| 正文 | 必填，后端 XSS 清洗；禁止脚本和危险链接 |
| 优先级 | 普通、重要、紧急 |
| 发布单位 | 从当前身份和授权组织选择，不能手输冒充 |
| 联系人/电话 | 可选；电话默认脱敏，紧急联系人按授权展示 |
| 附件 | 走文件中心，类型、大小、权限和病毒扫描按公共规则 |
| 是否置顶 | 重要/紧急且有权限时可选 |
| 是否要求确认 | 重要/紧急可启用；紧急默认开启 |
| 业务入口 | 从深链注册表选择，不接受任意 URL |

#### 第二步：接收范围

不能只有模糊的“全校”，必须支持：

- 全校学生；
- 全校教职工；
- 全校师生；
- 本学院学生/教职工；
- 指定学院、专业、年级；
- 指定行政班、教学班；
- 指定角色；
- 指定个人；
- Excel 名单导入（后置能力，必须走预校验和正式 xlsx）。

必须使用 `AppCollegePicker`、`AppMajorPicker`、`AppClassPicker`、`AppRolePicker`、`AppStudentPicker`、`AppTeacherPicker`、`AppOrgCascader`，选择器数据由后端按当前范围返回。

右侧实时显示：

```text
预计接收：1,286 人
学生 1,240｜教职工 46
3 个学院｜12 个专业｜31 个班级
已排除：毕业/退学/停用账号 46 人
[查看接收名单] [查看排除原因]
```

预览名单不得泄露无权限人员的敏感信息。

#### 第三步：渠道与时间

- 站内消息：强制开启；
- PC、小程序：按接收人身份自动覆盖；
- 微信订阅、短信：仅在租户授权、渠道配置、模板报备和用户授权满足时可选；
- 未配置渠道显示“未配置”，禁止假发送；
- 立即发布/定时发布；
- 生效时间、失效时间；
- 普通消息遵守静默时段；紧急消息可绕过静默时段但必须有权限和审计。

#### 第四步：预览并提交

展示完整内容、受众、预计人数、渠道、时间、是否回执和费用提示。

- 本班普通通知：辅导员可按授权直接发布。
- 学院普通公告：学院授权发布员可直接发布。
- 全校重要/紧急消息：默认进入现有审批中心。
- 发布人和最终审核人不得是同一人。

### 4.4 “发布记录”布局

```text
筛选：状态｜类型｜优先级｜发布单位｜发布人｜时间｜关键词
指标：待审核｜定时待发｜发布中｜部分失败｜待确认
列表：标题｜范围｜人数｜渠道｜状态｜发布时间｜已读率｜确认率｜操作
```

操作：

- 编辑草稿、复制新建、提交审核；
- 取消定时、撤回、查看统计；
- 对失败渠道重试；
- 催确认仅针对要求回执且仍未确认的人群；
- 已发布内容不可原地无痕修改，只能发布“更正版本”。

### 4.5 “发布详情”布局

顶部显示状态和关键动作；下方采用页签：

1. 内容与范围；
2. 审核时间线；
3. 送达与回执；
4. 失败记录；
5. 操作审计。

送达统计必须显示绝对人数，不只显示百分比。

### 4.6 “发送统计”

- 指标：发布次数、接收人数、站内送达、已读、确认、失败；
- 维度：时间、发布单位、消息类型、优先级、学院；
- 支持从统计下钻到发布记录，再到权限范围内的未读/未确认名单；
- 统计口径必须标注分子、分母和更新时间；
- 导出使用 `AppExportButton + AppExportConfirm`，用途必填、水印和审计。

### 4.7 “消息模板”

- 模板编码、事件码、适用范围、标题模板、内容模板、变量、默认渠道、默认优先级、是否强制回执、版本和启停；
- 系统业务模板与人工发布模板分开；
- 锁定字段不能被业务调用方覆盖；
- 模板变更只影响新消息，历史消息保留发送时快照；
- 模板预览必须使用安全示例数据，不展示真实学生隐私。

### 4.8 “消息设置”

个人设置只控制外部打扰方式：

- 普通消息的小程序提醒、微信订阅、短信；
- 静默时段；
- 摘要显示偏好。

以下不可关闭：

- 站内正式消息留存；
- 紧急安全消息；
- 法定/正式送达类消息；
- 学校配置为强制送达的考试、课表重大变更等。

### 4.9 前端状态、可访问性与防误操作规格

- 收件箱筛选和当前详情写入 URL：`category/readState/priority/messageId`；刷新、复制链接、浏览器前进后退均保持上下文。
- PC 详情查询只展示内容，不因浏览器预取而自动已读；进入可视区并停留达到产品阈值后由前端显式调用 `read`，失败时保留未读状态并可重试。
- 小程序详情必须按 `messageId` 重新请求，禁止依赖内存 stash；杀进程后从分享、横幅或列表进入仍能打开。
- 发布向导每一步服务端保存草稿，显示“已保存/保存失败”；离开未保存页面必须确认。
- 受众预览返回有时效的 `previewToken + audienceFingerprint`。提交或发布时受众已变化则阻止静默发送，要求发布人重新确认人数与排除项。
- 所有破坏性或高影响操作展示“动作、范围、人数、后果”：全校发布、紧急发送、撤回、重试和导出不得只弹“是否确定”。
- 错误定位到字段和步骤；顶部给出错误摘要并可聚焦第一个错误。网络失败不清空已填内容。
- 按钮具备 loading 和防重复点击；服务端幂等是最后保障，不能只依赖前端禁用。
- 键盘可完成筛选、选人、预览和发布；焦点顺序明确，弹层关闭后焦点回到触发按钮。
- 紧急、失败、撤回等状态不得只靠颜色表达，必须同时有文字和图标；正文支持系统字号放大，200% 缩放不遮挡关键动作。
- V1 若没有可靠的后端 HTML 白名单清洗器，正文必须先按纯文本加安全换行上线；不得为了“富文本效果”直接保存和渲染未经清洗的 HTML。

## 5. 学生小程序紧急消息设计

紧急消息必须同时出现在：

1. 小程序启动/回前台时的紧急弹层；
2. 学生首页顶部持续横幅；
3. 消息中心置顶；
4. 消息详情的“我已知晓”回执。

规则：

- `onShow` 拉取本人有效且未确认紧急消息，不依赖推送一定成功；
- 未确认前重新进入继续提示；
- “稍后查看”不等于确认；
- “全部已读”不能代替确认；
- 同一紧急消息每个版本单独确认；
- 撤回后显示撤回说明，不物理删除；
- 多条紧急消息按严重度和发布时间展示；
- 锁屏/外部推送不带身份证、处分、心理、详细风险等敏感正文；
- 外部渠道失败不影响站内底账，但必须记录失败并允许重试。
- 对要求确认的紧急消息显示确认截止时间和未确认人数；催确认有频控，禁止无限弹窗轰炸。
- 到达确认截止时间仍未确认时，只触发登记好的升级流程（例如通知辅导员/值班人员），不得自动认定学生已知晓。
- 短信、微信等已经发出的外部内容无法真正撤回；站内必须显示撤回说明，发布端必须明确展示“外部渠道可能已送达”。

## 7. 状态机

### 7.1 发布单状态

```text
DRAFT
  ├─提交且无需审核→APPROVED
  └─提交需审核→PENDING_REVIEW

PENDING_REVIEW
  ├─退回→RETURNED→修改后重新提交
  ├─驳回→REJECTED
  └─通过→APPROVED

APPROVED
  ├─立即→PUBLISHING
  └─定时→SCHEDULED→PUBLISHING

PUBLISHING
  ├─全部完成→PUBLISHED
  └─部分失败→PARTIAL_FAILED

PUBLISHED/PARTIAL_FAILED
  ├─撤回→WITHDRAWN
  ├─到期→EXPIRED
  └─复制并更正→新发布单
```

### 7.2 个人接收状态

```text
CREATED → DELIVERED → READ → ACKNOWLEDGED
             └──────────────→ ACKNOWLEDGED
渠道失败：DELIVERY_FAILED，可重试
```

阅读不能自动确认；确认必须是本人明确动作并记录时间、端、账号和消息版本。

状态机附加约束：

- 待审或已批准发布单一旦修改正文、范围、级别、渠道、时间或附件，原审批立即失效并回到 `DRAFT/RETURNED`；不得拿旧审批发送新内容。
- 定时任务执行前重新检查租户、发布权限、审批有效性、模板版本和渠道配置；失效则转可诊断失败，不能继续发送。
- 个人执行“确认”时若尚未读，可在同一事务补 `read_at`，但必须同时单独写 `ack_at`；这不改变“已读不能推出已确认”的原则。
- 到期只禁止新的确认或业务动作并降低展示优先级，不删除历史收件事实。

## 8. 数据模型与兼容策略

### 8.1 新增发布单

`t_message_campaign`

- `tenant_id`
- `title/content_plain/content_html/summary`
- `category/priority/status`
- `source_kind`：`HUMAN/BUSINESS_EVENT/PLATFORM`
- `source_module/source_biz_type/source_biz_id`
- `content_mode`：`SHARED/PER_RECIPIENT`
- `template_id/template_version`
- `sender_user_id/sender_context_id/sender_org_id`
- `sender_name_snapshot/sender_role_snapshot/org_name_snapshot`
- `publish_mode/scheduled_at/published_at/effective_at/expire_at`
- `require_ack/pinned/emergency`
- `action_key/action_params_json`
- `workflow_instance_id`
- `recipient_count/delivered_count/read_count/ack_count/failure_count`
- `content_version/idempotency_key/version/audience_fingerprint`
- `supersedes_campaign_id`：更正版本指向原发布单
- `withdrawn_at/withdrawn_by/withdraw_reason`
- CommonMixin 字段

唯一约束：`tenant_id + idempotency_key`。

计数字段是查询缓存，不是事实源；真实口径以个人接收记录和渠道日志为准，由后台对账任务校正。

### 8.2 新增受众规则

`t_message_audience`

- `campaign_id`
- `audience_type/include_or_exclude`
- `target_id/target_code`
- `include_children`
- `rule_json/rule_version`
- `resolved_count`
- `resolved_at`

提交审核时保存规则；真正发布前再次校验权限并生成最终接收人快照。规则必须明确账号状态、学籍状态、人员类型、组织包含关系和排除原因，禁止用一句“本学院”在不同服务里各自解释。

### 8.3 演进个人消息表

保留 `t_unified_message`，新增：

- `campaign_id`
- `receiver_user_id`
- `receiver_type`
- `receiver_context_key`：非空，个人全局消息固定为 `GLOBAL`
- `priority/category`
- `delivered_at/ack_at`
- `require_ack`
- `action_key/action_params_json`
- `expire_at/content_version`
- `delivery_status`
- `rendered_title/rendered_content_plain`：仅个性化业务消息使用

历史 `receiver_id` 暂留兼容；新写入必须填真实 `receiver_user_id`。历史数据只有在可证明映射唯一时才回填；其余记录继续经兼容适配器读取并打迁移告警，禁止根据数值相同猜测学生或教师账号。

唯一约束：`tenant_id + campaign_id + receiver_user_id + receiver_context_key`。不要把可空的 `receiver_context_id` 直接放入 MySQL 唯一键，否则多个 `NULL` 仍可能产生重复收件记录。

人工群发使用 `SHARED`：标题和正文事实保存在 campaign 快照，个人表只保存接收及阅读状态。需要“学生姓名、审批结果”等逐人变量的业务消息使用 `PER_RECIPIENT`：campaign 保存模板版本，个人表保存发送时安全渲染后的快照；不得在阅读时用实时业务数据重新拼正文。为兼容旧消息可暂留原有标题/正文列，但同一消息只能有一个明确内容事实源。

站内 `delivered_at` 表示个人收件记录已成功建立；微信、短信等每个外部渠道的接受、送达、失败状态只写 `t_notification_task/log`，不得汇总成个人表里一个含义不清的“送达”字段。

### 8.4 附件

`t_message_attachment`

- `campaign_id/file_id/sort_no`
- 只保存文件中心 ID；
- 下载时再次校验消息接收关系或发布管理权限；
- 撤回消息不删除附件审计关联。

### 8.5 复用现有通知表

复用：

- `t_notification_template`
- `t_notification_task`
- `t_notification_log`
- `t_notification_preference`

旧文档中的 `t_message_template/t_message_channel_log` 与实际代码命名不一致。Cursor 必须以现有 model 为基线补强和迁移，禁止再建一套同义表。

### 8.6 新增业务事件 Outbox

`t_message_event_outbox`

- `tenant_id/event_code/source_module/source_biz_type/source_biz_id`
- `payload_json/recipient_refs_json/dedup_key`
- `status`：`PENDING/PROCESSING/SUCCEEDED/RETRY_WAIT/DEAD`
- `attempt_count/next_retry_at/last_error_code`
- `locked_by/locked_at/lease_expires_at`
- `occurred_at/processed_at`
- CommonMixin 字段

唯一约束：`tenant_id + dedup_key`；索引至少包含 `(status, next_retry_at, id)`。

业务模块只能在自己的数据库事务中调用统一事件写入器；写入器只落 outbox，不访问微信、短信，也不逐人创建消息。建议契约：

```python
emit_message_event(
    db=db,
    event_code="LEAVE.APPROVED",
    source_module="student_affairs",
    source_biz_type="leave_request",
    source_biz_id=leave.id,
    recipient_refs=[{"userId": student.user_id}],
    variables={"studentName": student.name, "endAt": leave.end_at},
    action_key="student.leave.detail",
    action_params={"leaveId": leave.id},
    dedup_key=f"LEAVE.APPROVED:{leave.id}:{leave.version}",
)
```

事件注册表决定模板、允许的变量、默认级别、强制渠道和深链；调用方不得传任意 HTML、任意角色或“全校”范围。

### 8.7 大批量发布与并发控制

不得在发布 HTTP 请求中同步循环全校人员。

```text
事务保存发布单
→ 受众解析任务
→ 分批写个人接收记录
→ outbox/后台任务按渠道下发
→ 原子更新统计
→ 失败进入可重试队列
```

批次写入、幂等键和唯一约束共同防重复。发布人员列表采用发布时快照，后续学生转班不改历史收件事实。

执行要求：

- 复用现有 `backend/scripts/run_scheduled_jobs.py` 和项目的 external scheduler 模式；生产多 worker 环境禁止在每个 Web 进程启动后台线程。
- 任务领取使用数据库租约；MySQL 8 可用 `SELECT ... FOR UPDATE SKIP LOCKED`，否则使用原子状态更新加 `locked_by/lease_expires_at`，崩溃后可重新领取。
- 接收记录按配置批次插入；重复任务依赖唯一键安全跳过，不能先查后插作为唯一防重手段。
- 重试采用指数退避和最大次数；超过上限进入 `DEAD`，页面显示可诊断原因，授权人员可按失败项重放。
- HTTP 发布成功仅代表“已受理”；返回 202 语义和 `campaignId/status`，完成状态由详情轮询或项目既有实时机制更新。
- 定时发布、过期、撤回、渠道重试和统计对账均使用同一调度底座。

### 8.8 必需索引与查询边界

至少建立并通过 `EXPLAIN` 验证：

```text
t_unified_message:
  (tenant_id, receiver_user_id, receiver_context_key, status, created_at, id)
  (tenant_id, campaign_id, receiver_user_id, receiver_context_key) UNIQUE

t_message_campaign:
  (tenant_id, status, scheduled_at, id)
  (tenant_id, sender_org_id, created_at, id)
  (tenant_id, idempotency_key) UNIQUE

t_message_event_outbox:
  (status, next_retry_at, id)
  (tenant_id, dedup_key) UNIQUE

t_notification_task / log:
  按 campaign_id、status、next_retry_at 补关联索引
```

所有列表使用稳定排序 `created_at DESC, id DESC`；数据量上来后优先游标分页，禁止用无上限 offset 扫描全校历史。

### 8.9 无损迁移与回滚

1. 只做新增表、列和索引的兼容迁移，先不删除旧字段和旧接口。
2. 上线兼容读取器和统一 service；新写入先走新模型，同时保留旧端可读。
3. 分批回填能够唯一映射的 `receiver_user_id`，输出成功、冲突、无法映射三类报告。
4. 四端切换到统一读取后，监测至少一个发布周期，再停止旧直接写入。
5. 旧 `/api/v1/messages`、`/portal/messages`、`/mobile/teacher/messages` 暂由适配层调用统一 service，并返回弃用日志；不能突然删除。
6. 回滚通过 feature flag 切回旧读取路径；数据库新增结构暂留，禁止用降级脚本删除已经产生的消息事实。

建议开关：

```text
feature.messageCenter.enabled
feature.messageCenter.newReadPath
feature.messageCenter.campaignPublish
feature.messageCenter.emergency
```

## 9. API 设计

### 9.1 收件端

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/messages` | 当前教师身份消息列表 |
| GET | `/api/v1/admin/messages/count` | 未读、待确认数量 |
| GET | `/api/v1/admin/messages/{id}` | 详情，严格本人；读取详情本身不自动已读 |
| POST | `/api/v1/admin/messages/{id}/read` | 标记已读 |
| POST | `/api/v1/admin/messages/read-all` | 按筛选批量已读，不确认 |

学生 PC、student-mini、teacher-mobile 保留各端前缀，但调用同一 service 和逻辑表。

多角色可见性采用“个人全局消息 + 当前激活身份消息”的并集并按 messageId 去重。顶部铃铛与收件箱使用完全相同的可见性 service；不能一个按用户查、另一个按角色查而产生角标不一致。

### 9.4 统一业务事件接入契约

业务模块不调用发布 HTTP 接口，也不直接构造 `UnifiedMessage`；它在自身 service 事务中调用 `emit_message_event()`。outbox 消费器再调用消息领域服务：

```text
事件码校验
→ 模板与变量校验
→ dedup_key 去重
→ 接收人 user_id 解析
→ 生成 SYSTEM campaign
→ 生成个人消息
→ 创建外部渠道任务
→ 标记 outbox 成功
```

首批事件码至少登记并测试：

```text
LEAVE.SUBMITTED / LEAVE.APPROVED / LEAVE.REJECTED
COURSE.SCHEDULE_CHANGED
EXAM.ARRANGED / EXAM.RESULT_PUBLISHED
```

### 9.5 响应、并发与错误码

- 统一沿用项目响应 envelope 和 trace/request ID，不再定义第二套 `{code,data,message}` 外壳。
- 详情不存在或越权且需隐藏存在性时返回项目统一 404；明确存在但动作无权为 403。
- `version` 不匹配返回 409，不得最后写入覆盖先前编辑。
- 校验错误 422 必须返回字段路径，前端可定位到发布向导具体步骤。
- 频控返回 429 和可重试时间；后台渠道失败不冒充 HTTP 发布失败。

| 错误码 | HTTP | 前端动作 |
|---|---:|---|
| `MESSAGE_NOT_FOUND` | 404 | 关闭详情并刷新列表 |
| `MESSAGE_SCOPE_DENIED` | 403/404 | 显示无权限，不泄露范围外对象 |
| `MESSAGE_STATE_CONFLICT` | 409 | 刷新发布单状态 |
| `MESSAGE_VERSION_CONFLICT` | 409 | 提示已有新版本，禁止覆盖 |
| `MESSAGE_DUPLICATE_REQUEST` | 409 | 根据原 request ID 展示原结果 |
| `MESSAGE_AUDIENCE_CHANGED` | 409 | 展示新人数并要求重新确认 |
| `MESSAGE_TEMPLATE_VARIABLE_MISSING` | 422 | 定位缺失变量 |
| `MESSAGE_ACTION_NOT_ALLOWED` | 422 | 移除非法深链 |
| `MESSAGE_ACK_NOT_REQUIRED` | 409 | 刷新详情，不伪造确认 |
| `MESSAGE_EXPIRED` | 409 | 显示已失效 |
| `MESSAGE_WITHDRAWN` | 409 | 显示撤回说明 |
| `MESSAGE_CHANNEL_UNAVAILABLE` | 422 | 显示未配置渠道 |
| `MESSAGE_RATE_LIMITED` | 429 | 显示可重试时间 |

### 9.6 深链注册表

每个 `actionKey` 必须在后端白名单和四端路由映射中登记，参数使用 schema 校验。没有对应页面的端展示“请前往教师 PC/学生 PC 办理”，不能拼接任意路径。

## 11. 安全、治理与审计补充

1. 正文 HTML 必须后端白名单清洗，防 XSS；清洗能力未完成时只允许纯文本。
2. 深链只接受注册的 `actionKey`，由各端映射合法路由。
3. 附件复用现有 `t_file_object` 和 `file_service`；下载必须重新校验租户、接收人或发布权限，不能只凭 file ID。
4. 接收人看不到其他接收人名单。
5. 发布记录保存当时的发布人、角色、组织和范围快照。
6. 全校、紧急、撤回、导出未确认名单、查看完整联系方式必须审计。
7. 发布频率和单日数量做租户规则限制，防通知轰炸。
8. 普通消息遵守静默时段；紧急消息绕过时记录原因。
9. 内容包含身份证、心理、处分等敏感词时给发布人风险提示；后端仍做敏感字段禁止规则。
10. 日志不得记录完整手机号、消息敏感正文和附件临时地址。
11. 物理删除发布记录、接收记录和渠道日志不对业务用户开放。
12. 超期消息归档而非直接删除，保留期限走租户合规配置。

审计事件建议：

```text
MESSAGE_DRAFT_CREATE
MESSAGE_DRAFT_UPDATE
MESSAGE_AUDIENCE_PREVIEW
MESSAGE_SUBMIT
MESSAGE_APPROVE
MESSAGE_RETURN
MESSAGE_PUBLISH
MESSAGE_WITHDRAW
MESSAGE_RETRY
MESSAGE_RECIPIENT_EXPORT
MESSAGE_TEMPLATE_CHANGE
MESSAGE_EMERGENCY_ACK
```

复用现有 `backend/app/services/audit_log.py::record`，不要另造消息审计框架。业务数据库提交失败时不得留下“发布成功”审计；高风险操作的审计记录失败时应阻止动作或进入可追踪补偿状态，不能静默吞掉。

| 学院给指定班级 | 多选班级 Picker + 受众预览 | 班级归属校验 + 最终受众快照 | 多班去重、排除项、人数变化阻断 |
| 全校发信息 | 全校学生/教职工/师生三个明确选项 | 独立 permission + 审批 + 异步发布 | 10,000 人性能、审批分离、无重复 |
| 学生小程序紧急信息 | 启动弹层、首页横幅、消息置顶、详情回执 | emergency + require_ack + ack_at | 回前台重现、稍后不确认、截止升级 |
| 四端消息一致 | 教师 PC/小程序、学生 PC/小程序 | 同一 messageId/userId/readAt/ackAt | 跨端读取与确认同步 |
| 各业务模块自动通知 | 请假、教务、学工、实习、毕设事件 | 同事务 outbox + 事件模板注册表 | 业务回滚无消息、失败恢复不重复 |
| 全校统计和未确认追踪 | 发布详情、发送统计 | 个人事实 + 渠道日志 + 对账 | 数字口径、权限下钻、导出审计 |
| 外部渠道真实可信 | 发布渠道、消息设置 | 现有 notification task/log/preference | 未配置不假成功、失败可重试 |

## 15. 禁止事项

- 禁止只做页面不做真实后端和 MySQL。
- 禁止页面写 mock 或点击后假成功。
- 禁止再建第二套用户、学院、班级、模板或渠道日志表。
- 禁止通过角色名称硬编码权限。
- 禁止把“全校”默认解释成所有用户。
- 禁止全校同步逐行发送。
- 禁止关闭偏好后让正式站内消息消失。
- 禁止把已读自动当成确认。
- 禁止物理删除已发送消息掩盖历史。
- 禁止任意 URL 深链和无鉴权附件下载。
- 禁止真实短信/微信未配置时伪造成功。
- 禁止覆盖当前工作区内其他人的毕业设计、岗位实习、工作台等未提交修改。

## 16. 完成定义

满足以下条件才能宣布“消息中心完成”：

- 工作台存在独立二级消息中心及全部授权内三级页面；
- PC 管理端、学生 PC、老师小程序、学生小程序读同一消息事实；
- 班级、学院、指定班级、全校学生、全校教职工、全校师生范围真实可用；
- 发布单、审核、定时、异步投递、撤回、失效、统计、已读和确认闭环；
- 学生小程序紧急消息真实可见并能回执；
- 权限、数据范围、业务关系、跨租户和审计在后端生效；
- 外部渠道未配置时诚实降级；
- 相关测试、构建和 MySQL 迁移实际通过；
- 无假按钮、无 mock 成功、无重复消息表、无用户已有修改丢失。
