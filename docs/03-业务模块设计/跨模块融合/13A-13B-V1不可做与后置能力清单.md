# 13A/13B V1 不可做与后置能力清单

> 版本：V1.0（2026-07-05）
> 定位：对甲方与开发同时生效的"V1 明确不做"清单展开件——14 项后置能力逐条说明**为什么 V1 不做、强行做的风险、P2/P3 怎么做、V1 如何预留**（表字段/规则键/接口/菜单占位四个维度）。
> 依据：《13A-13B-V1范围冻结表》§4 红线清单与 §1/§2 冻结总表、`_13-需求输入-V1.1.md` §10、《13A-13B-现有代码库融合证据报告》、文件一《学校参数配置中心设计》（规则键预留落点）、文件二《模块发布灰度与授权控制设计》（菜单占位策略统一口径）。

## 逐项展开（14 项）

### 1. 全自动排课（智能排课算法）

- **为什么 V1 不做**：需求原文明示"V1 策略：不上复杂算法——规则校验+人工排课+冲突检测"（需求 §3.7）；冻结表红线 1 进一步收紧"含任何简单贪心也不做"。自动排课依赖教室资源字典、教师不可用时段、周学时约束等前置数据（V1 教室仅 P2 最小字典），数据不全时算法输出必然不可用。
- **强行做的风险**：约束不全的算法排出的课表冲突率高，学校须人工重排——比没有更糟（信任崩塌）；算法调参周期不可控，直接吞掉 13B-P4 档期；排出的错误课表一旦发布，调停课能力（同为 P2）又不在，无法收拾。
- **P2/P3 怎么做**：P2 先交付"编排器"（可视化人工排课 + 六类冲突实时检测：教师/班级/教室/容量/类型/校区，需求 §3.7 冲突清单）；P3 在编排器数据完备一学期后上启发式自动排课（约束满足求解），输出仅进"预排草稿"，仍需人工确认发布。
- **V1 预留**：
  - 表字段：`t_aa_schedule_batch` 预留 `generate_mode`（IMPORT/MANUAL/AUTO，V1 只写前两值）；`t_aa_schedule_item` 的 `source` 字段区分导入/手工/算法。
  - 规则键：`academicAffairs.feature.scheduleEditorEnabled=false`（文件一 #54，学校不可改）。
  - 接口：课表批次 API 的 body 保留 `mode` 字段枚举含 AUTO（服务端 V1 收到 AUTO 一律 422"暂未开放"）。
  - 菜单占位：管理员端「课表管理」下不出现"自动排课"入口；配置页"规划中"分区列明 P3。

### 2. 抢课式选课（完整选课引擎）

- **为什么 V1 不做**：冻结表红线 2——V1 学生课表按行政班归属服务端推导，无选课。抢课场景=高并发库存扣减（先修校验/时间冲突/学分上限/容量并发锁），是全系统并发要求最高的单点；职校 V1 试点以行政班教学为主，选修课占比低，投入产出不成立。
- **强行做的风险**：并发扣容量不做分布式锁/排队即超卖（一个座位选进两人），开学初集中抢课把整套 SaaS 打挂，殃及其他租户（共库行级隔离，事实速查 §2）；校验引擎缺先修/冲突数据（依赖方案与课表成熟）时选出非法课表。
- **P2/P3 怎么做**：P2 做"申报式选课"（时间窗内提交志愿→窗口关闭后统一校验+按规则分配，无抢），验证校验引擎；P3 视学校诉求上实时选课（容量走 Redis 原子扣减+等位队列，独立限流）。
- **V1 预留**：
  - 表字段：`t_aa_teaching_task` 已含 `capacity` 列（V1 仅提示校验）；预留 `t_aa_enrollment` 表名（冻结表 §2"选课"行已声明依赖，V1 不建表）。
  - 规则键：`academicAffairs.feature.enrollEnabled=false`（文件一 #53）。
  - 接口：学生课表接口响应保留 `source: "CLASS_DERIVED"` 字段，P2 增 "ENROLLED" 值时前端零改动。
  - 菜单占位：无入口；学生小程序课表页不出现"选课"按钮。

### 3. 国家/省平台学籍上报

- **为什么 V1 不做**：冻结表红线 6；需求 §9 明示"是否国家/省平台上报"属**现场确认项**——对接口径（全国中等职业学校学生管理信息系统/省平台）、字段映射、报送周期均未确认；且上报属外部集成，冻结口径走 12 号集成开放中心，不在 13B 域内。
- **强行做的风险**：闭门造的报文格式与真实平台不符=全部返工；学籍上报错误直接影响学生学籍法律效力（比系统内 bug 严重一个量级）；对接需要学校在主管部门的账号与专网环境，开发环境根本无法联调。
- **P2/P3 怎么做**：P3 现场确认后在集成开放中心新建上报适配器（导出 13B 学籍/异动数据→按省规范生成报文→人工核对→报送回执登记）；先做"半自动"（生成报盘文件人工上传），跑通两个报送周期后再谈接口直连。
- **V1 预留**：
  - 表字段：`t_student_profile` 的 `id_card_encrypted`、`t_aa_status_change` 的异动类型枚举对齐国标口径命名（TRANSFER_MAJOR/SUSPENDED 等，需求 §3.3 状态已按此设计），减少未来映射成本；预留 `national_report_status` 不建列（P3 加 nullable 列）。
  - 规则键：`academicAffairs.integration.legacyAcademicSync`（文件一 #56）同族，P3 增 `integration.nationalReportEnabled`（V1 不登记，防误开）。
  - 接口：学籍名册导出 domain `academic-roster` 的列集设计时包含上报必需字段（身份证/学籍号/异动类型），保证 P3"报盘文件"可由既有导出管线生成。
  - 菜单占位：无。

### 4. 深度心理测评（量表/预约/危机干预）

- **为什么 V1 不做**：需求 §10 明示后置（冻结表"心理测评深度集成 P3"）；红线 8"V1 仅关注标记+强权限引用，不出现量表/诊断字样"。心理测评涉及专业量表版权（SCL-90 等）、施测资质、危机干预 SOP——软件问题之外的合规问题未解决前不能上线。
- **强行做的风险**：无资质提供"诊断结论"有法律责任；测评数据是最高敏感级，泄露即事故（现有 t_cs_mental_record 已按"强权限、学生端只回数量不回明细"设防，事实速查 §6）；错误的自动危机分级漏掉真实危机=不可承受。
- **P2/P3 怎么做**：P3 与有资质的心理测评供应商集成（走集成开放中心），系统只做：测评任务分发、结果**引用**（等级不落明细）、心理老师工作台、危机个案转介流程；量表计分留在供应商侧。
- **V1 预留**：
  - 表字段：`t_cs_mental_record` 结构不动（冻结表"不动结构"）；13A 风险表 `t_affairs_risk_record.source` 枚举含 PSY（V1 即用，来自人工关注标记）。
  - 规则键：`studentAffairs.psy.visibleRoles / counselorAuthorizedVisible / exportDetailEnabled`（文件一 #22–24）V1 即生效，P3 测评数据自动继承同一可见性体系。
  - 接口：scope 机制预留 `scope_type=PSY_STUDENT`（冻结表 §5.1，13A-P4 引入）——P3 测评结果可见性直接复用。
  - 菜单占位：管理员端心理板块页头注明"关注与转介（测评集成规划中）"。

### 5. 第二课堂积分引擎（复杂二课积分）

- **为什么 V1 不做**：需求 §10 明示"第二课堂复杂积分 P2/P3"；积分规则（活动类别系数/学时折算/年度达标线/申诉复核）各校差异极大且需求 §9 列为现场确认项（"德育积分规则？第二课堂已有系统？"）——学校可能已有第三方二课系统。
- **强行做的风险**：规则拍脑袋=上线即重写；若学校已有系统则重复建设+双系统积分打架；积分关联评优评奖，算错即公平性投诉。
- **P2/P3 怎么做**：P2 先做"记录层"（活动/志愿的学时与积分**流水登记**，冻结表"表名已预留"）；P3 做"规则层"（可配置系数引擎+年度结算+申诉流）或对接已有二课系统（集成中心适配器，二选一由现场确认定）。
- **V1 预留**：
  - 表字段：预留表名 `t_affairs_activity` / `t_affairs_activity_signup` / `t_affairs_second_class_record`（冻结表 13A"学生活动/志愿服务/第二课堂"行——V1 不建表只锁名）。
  - 规则键：P2 登记 `studentAffairs.secondClass.creditRules`（V1 不登记）。
  - 接口：学生 360 时间线聚合的事件类型枚举预留 ACTIVITY 值（StageEvent event_type 只增不改）。
  - 菜单占位：无（学工中心菜单不出"第二课堂"）。

### 6. 家长端门户

- **为什么 V1 不做**：需求 §10 明示 P3；红线 10"不做家长端（家校联系仅记录+审计）"。家长端需要独立的身份体系（监护人实名+与学生绑定关系核验 t_student_guardian_auth 仅规划）、独立小程序端、以及"家长能看什么"的敏感边界（成绩/处分/心理对家长的可见性各校政策不同，需求 §9 待确认）。
- **强行做的风险**：监护人身份核验不严=任何人绑定看学生隐私（比内部越权更严重的外泄面）；家长端消息（请假通知/成绩）一旦发错人即舆情；User 模型虽已有 GUARDIAN 类型（models/rbac.py user_type 枚举），但配套授权链为零。
- **P2/P3 怎么做**：P2 先做"家长通知"单向渠道（请假通过/逾期的模板消息，依赖短信/订阅消息渠道谈妥）；P3 做家长端 H5（绑定核验→只读视图：考勤/请假/通知，敏感域默认全关，逐项由学校配置开放）。
- **V1 预留**：
  - 表字段：`t_student_contact` 已存监护人电话（脱敏出口）；预留表名 `t_student_guardian_auth`（冻结表 13A"家长端"行原文"规划"）。
  - 规则键：`studentAffairs.leave.parentNotify=false`（文件一 #7，V1 即登记、渠道未接时强制置灰）。
  - 接口：13A 家校联系记录 API 的 body 预留 `notify_channel` 枚举（NONE/SMS/MINIAPP，V1 只写 NONE）。
  - 菜单占位：无家长端入口；家校联系页仅记录功能。

### 7. 一卡通硬件对接

- **为什么 V1 不做**：冻结表两模块能力清单均无一卡通条目（不在 13A/13B 需求域）；一卡通厂商协议私有（消费/门禁/水控各不同），无标准接口；采购与布线属学校基建，SaaS V1 无从对接。
- **强行做的风险**：硬件协议逆向工程周期完全不可控；消费数据涉支付合规；为演示做假数据对接=红线 14"假大空"。
- **P2/P3 怎么做**：P3 经集成开放中心（12 中心）做厂商适配器，只取**行为数据**（进出记录/消费流水摘要）供风险预警（长期未消费=疑似离校信号）；不做卡务管理本身。
- **V1 预留**：
  - 表字段：`t_affairs_risk_record.source` 枚举设计为开放字符串+字典（不写死 CHECK 约束），P3 增 CARD 来源零迁移。
  - 规则键：无（P3 随适配器登记 `studentAffairs.risk.cardSignalEnabled`）。
  - 接口：风险来源注册机制（13A-09 多来源设计）即预留点——新来源=新增一个来源写入器，不改风险主流程。
  - 菜单占位：无。

### 8. 宿舍门禁硬件对接（夜不归宿自动采集）

- **为什么 V1 不做**：V1 夜不归宿走**人工检查登记**（冻结表"夜不归宿登记随宿舍检查进 V1"）；门禁硬件同第 7 项——厂商协议私有、部署在校内网、SaaS 侧无法保证联通性。
- **强行做的风险**：门禁数据质量差（代刷/尾随/设备离线）时自动判定"夜不归宿"误报率高，直接生成风险单会淹没辅导员并引发家校误会（自动化放大错误）；实时数据接入需要边缘侧组件，V1 交付范围爆炸。
- **P2/P3 怎么做**：P3 门禁适配器（集成中心）→ 每日批量同步进出流水 → **辅助核对**视图（检查任务预填"门禁无出入记录"提示，仍由宿管人工确认后才落 t_cs_dorm_exception）——机器提示、人来定责。
- **V1 预留**：
  - 表字段：`t_cs_dorm_exception`（既有表，不动）已是异常唯一落点；13A 检查记录表 `t_affairs_dorm_check_record` 预留 `evidence_source`（MANUAL/DEVICE，V1 只写 MANUAL）。
  - 规则键：`studentAffairs.risk.autoFromDormException=true`（文件一 #27）——P3 门禁信号仍经"人工确认→异常→风险"同一链，规则键不变。
  - 接口：检查记录导入 domain `affairs-dorm-check`（冻结表 §7 已冻结）可承接 P3 设备批量数据（同一 dry-run 管线）。
  - 菜单占位：宿舍检查页不出现"设备数据"Tab。

### 9. 财务系统深度对接（缴费/退费/资助发放）

- **为什么 V1 不做**：两模块冻结表均未列财务对接（毕业资格"费用材料"项默认关：文件一 #51 feeCheck=false）；学校财务系统（用友/金蝶/自建）接口各异，资金数据准确性责任重大；奖助"发放"环节 V1 止步于名单归档（冻结表：奖助 V1=申请/评审/公示/结果，无发放记账）。
- **强行做的风险**：缴费状态同步错误→注册/毕业资格误判（卡住无辜学生）；资助金额数据不一致→审计问题；对账机制缺失时两边数字永远对不上，运维黑洞。
- **P2/P3 怎么做**：P2 先做"人工回填"（财务处按批次导入缴费状态，走既有导入 dry-run 管线）；P3 做财务适配器（集成中心）单向拉取缴费结果，资助发放仍由财务系统执行、本系统只读回执登记。
- **V1 预留**：
  - 表字段：`t_aa_registration` 预留 `fee_status`（nullable，V1 不填不判）；`t_affairs_funding_application` 预留 `grant_amount` 与 `payment_status`（V1 只写名单结果）。
  - 规则键：`academicAffairs.graduation.conditions.feeCheck=false`（文件一 #51 子项，V1 即登记、默认关）。
  - 接口：预留导入 domain `academic-fee-status`（P2 注册，V1 不注册）。
  - 菜单占位：无"财务对接"页；毕业预审异常清单里费用项显示"未启用"而非"不通过"（UNKNOWN≠FAIL，冻结表验收原则）。

### 10. 复杂绩点引擎（GPA 多制式/加权/重修覆盖策略）

- **为什么 V1 不做**：需求 §9"绩点规则？"为现场确认项；V1 成绩纯读 t_acad_grade（红线 3 零成绩写端点），绩点计算依赖成绩构成/重修覆盖/学分权重全链数据，而成绩录入链本身 P2。
- **强行做的风险**：绩点算法一旦对外展示就被引用于评优/毕业，制式选错（4.0/5.0/百分位）或重修覆盖策略错=大面积成绩争议；与学校线下惯例不一致时每学期都要人工解释。
- **P2/P3 怎么做**：P2 随成绩录入链交付"单一制式"绩点（gpa.formula 规则键生效，先只支持 FOUR_POINT）；P3 扩展多制式/自定义映射表/重修取高-取新-均值策略（`retake.scoreStrategy` 新键），并提供"试算对比"页供教务处核对后再启用。
- **V1 预留**：
  - 表字段：`t_acad_grade` 不动（权威层）；P2 过程表 t_aa_grade_record 设计时含 `gpa_point` 冗余列位（冻结表 D1 决策）。
  - 规则键：`academicAffairs.gpa.formula="FOUR_POINT"`（文件一 #44，V1 仅登记+预警换算参考，不对外出绩点值）。
  - 接口：学业预警扫描用"挂科门数+GPA 阈值"双规则（文件一 #49/50），V1 GPA 项可单独停用避免依赖。
  - 菜单占位：成绩查看页不显示绩点列（列位预留隐藏）。

### 11. 复杂毕业规则引擎（可视化规则编排/多方案组合判定）

- **为什么 V1 不做**：冻结表"复杂毕业规则/证书文书 P3"；V1 毕业资格=**预审**（七项固定条件逐项判定+两级人工复核，冻结表 13B-P6），规则引擎化（任意条件组合/分方案例外/条件间依赖）需要至少一届毕业生的真实判定数据来验证。
- **强行做的风险**：规则引擎的表达力换来的是不可解释性——毕业判定必须可向学生逐项解释（"你差 3 学分+1 门必修"），引擎化早于数据沉淀=既难写又难对；判错毕业结论是最高危输出（红线：终审经单一入口写 student_status+二次确认）。
- **P2/P3 怎么做**：P2 把七项条件的**参数**全部规则键化（阈值/开关，文件一 #51 已起步）；P3 若学校出现"专业级例外规则"诉求，再做规则条目表（t_aa_graduation_rule，按专业/年级挂条件集），引擎输出仍必须落"逐项判定明细"保证可解释。
- **V1 预留**：
  - 表字段：`t_aa_graduation_audit_result` 设计为**逐项明细结构**（每条件一列或明细子表，含 PASS/FAIL/UNKNOWN 三值）——P3 规则引擎只是"生成明细的方式"变化，结果表不变。
  - 规则键：`academicAffairs.graduation.conditions` 七项开关 + `graduation.manualReviewRequired=true`（文件一 #51/52）。
  - 接口：预审执行接口带 `rule_version` 字段（V1 恒 "v1-fixed7"），P3 引擎化后可追溯每批用的规则版本。
  - 菜单占位：毕业审核配置区仅七项开关，无"规则编排"入口。

### 12. AI 风险预测（行为大数据预警）

- **为什么 V1 不做**：需求 §10 明示 P3（"行为大数据预警"）；冻结表 13A"行为大数据预警 否（P3）——需 V1 风险数据沉淀"。模型没有训练数据（V1 才开始沉淀风险单与处置结果），先上模型=无米之炊。
- **强行做的风险**：假 AI（拍规则冒充模型）违反红线 14；真模型在零样本下输出不可信，误报消耗辅导员信任、漏报出事故追责到系统；学生风险打分涉算法伦理与可解释性要求，草率上线有合规风险。
- **P2/P3 怎么做**：P2 扩展**规则型**多来源汇聚（已在 V1 风险五来源基础上加来源加权重）；P3 在 ≥2 学期风险处置闭环数据上训练预测模型，输出仅作"建议关注排序"（不自动生成风险单、不展示给学生），并保留逐因子解释。
- **V1 预留**：
  - 表字段：`t_affairs_risk_record` 含 `source/source_ref_id/risk_level/close_reason`（处置结果即未来标签）；`t_affairs_risk_handle_record` 完整留痕处置过程（特征与标签同表系沉淀）。
  - 规则键：`studentAffairs.risk.*` 组（文件一 #25–27）为规则型底座；P3 增 `risk.aiSuggestEnabled=false`。
  - 接口：风险列表接口预留 `sort=suggest` 参数值（V1 422"暂未开放"）。
  - 菜单占位：风险页无"智能预测"Tab。

### 13. 大屏展厅版（数据驾驶舱大屏）

- **为什么 V1 不做**：冻结表两清单均无大屏条目；V1 统计是"随业务点亮"的 23 项指标（学工 12+教务 11），指标口径刚冻结尚未经真实数据校准——大屏是口径的放大器，口径不稳先上大屏=把误差投到展厅墙上。
- **强行做的风险**：大屏是纯展示工程但工作量不小（分辨率适配/轮播/动效），挤占闭环开发档期；演示驱动的大屏容易滑向 mock 数据（违反 R8"演示正常、生产报错"教训与红线 14）。
- **P2/P3 怎么做**：P2 末期指标经一学期校准后，P3 做大屏模式：**复用 stats_service 同一聚合**（证据报告 R12 统一口径红线）出全屏只读视图（/admin/data-center 增全屏路由），支持轮播与租户品牌主题（TenantBrandConfig 主色/校徽，models/tenant.py 第 30–48 行）。
- **V1 预留**：
  - 表字段：无需（大屏零新数据）。
  - 规则键：P3 登记 `platform features 布尔 dashboardWall`（套餐差异化卖点，professional 及以上）。
  - 接口：stats 端点响应结构 V1 即按"卡片数组+口径元数据"设计，大屏可直接消费同一响应。
  - 菜单占位：数据中心无"大屏"入口。

### 14. 多校集团版（集团/教育局多租户聚合视图）

- **为什么 V1 不做**：冻结表无此条目；现有租户模型是"一校一租户、行级隔离"（t_tenant 控制面，事实速查 §2），跨租户聚合会击穿隔离设计的第一原则；集团客户 V1 尚不存在（先服务好单校试点）。
- **强行做的风险**：跨租户查询一旦开口子，任何实现疏漏都是**跨校数据泄露**（比校内越权严重一级）；集团角色体系（集团管理员≠平台超管≠校管理员）需要新的授权层，V1 引入=权限模型返工；聚合口径（各校学期/规则不同）没有统一基准。
- **P2/P3 怎么做**：P3 设计"集团层"为**只读聚合**：新增 GROUP_ADMIN 用户类型 + t_tenant_group（集团-租户关系控制面表），聚合只走 stats_service 的跨租户汇总专用函数（白名单指标、不下钻到学生明细），明细下钻必须切换进单校租户上下文并按该校权限重新鉴权。
- **V1 预留**：
  - 表字段：`t_tenant.region_code` 已存在（models/tenant.py 第 19 行）可作未来分组维度；不加集团列。
  - 规则键：无。
  - 接口：stats_service 函数签名 V1 保持 `(tenant_id, ...)` 单租户入参——P3 集团聚合是**新函数**而非改签名（防止误用成跨租户查询）。
  - 菜单占位：无；平台运营端租户列表的 region 筛选即 V1 可见的"分组"雏形。

## 对甲方的一页话术（现场可直接引用）

V1 的边界不是"做不了"，而是"不该现在做"：算法类（排课/选课/AI/绩点/毕业引擎）等数据沉淀一学期后再上，才不会拿学校当调参实验场；硬件与外部对接类（一卡通/门禁/财务/国家上报）等现场口径确认后走统一集成中心，才不会做成一次性烟花；家长端与深度心理涉合规资质，宁慢勿险。每一项 V1 都留了钉子（表字段/规则键/接口/占位），P2/P3 拧上即可，不推倒重来。

### 现场常见追问与应答口径

| 追问 | 应答 |
|---|---|
| "别家演示有自动排课，你们为什么没有？" | 演示排课和可用排课差一个学期的数据治理。我们 V1 先把教室/教师/校历数据管对，P3 的算法才排得出能用的课表——先给您冲突检测，错的课表一张都发不出去。 |
| "能不能先给领导做个大屏？" | 大屏放大的是数据口径。V1 先让首页数字和列表条数分毫不差跑三个月（我们有对账验收），P3 的大屏才敢挂到展厅墙上。 |
| "家长很着急想看孩子情况" | V1 请假等关键事项已预留家长通知开关，短信渠道签约后 P2 即可开通知；家长端门户涉及监护人身份核验，我们按 P3 做严，不做一个谁都能绑的入口。 |
| "心理测评什么时候有？" | V1 心理关注与强权限保护已就位（只有心理老师和授权辅导员可见）；量表测评需要资质与专业供应商，P3 集成时这套权限直接沿用。 |
| "先上了再说，出问题再改行不行？" | 这 14 项里一半涉及学生的学籍、毕业、隐私和资金——出错不是回滚代码能解决的。冻结表和本清单就是我们双方的安全绳。 |
