# 13A/13B 异常兜底与人工处理设计

> 版本：V1.0（2026-07-05）
> 依据：`_13-现有系统集成事实速查.md`（Workflow §4：t_workflow_task 支持 approve/reject/**transfer**、version 乐观锁 409；审计 §3：audit_log.record→t_security_audit_log；导出 §8）、《13A-13B-现有代码库融合证据报告.md》（命名裁定 student-affairs/academic-affairs、t_affairs_\*/t_aa_\*）、《13A/13B-状态机与权限矩阵》两份、《13A/13B-开发阶段与验收用例》两份。
> 定位：学校现场出问题时"谁、在哪、做什么"的操作手册级设计 + 系统撤回/作废/更正能力的统一冻结。只做设计，不写代码。

## 0. 总则（五条铁律）

1. **一切修正走业务动作**：撤回/作废/更正/转办/重开是**带状态机与审计的业务操作**，不是改数据。任何"直接 UPDATE 数据库"都被禁止（§4.3 唯一例外流程）。
2. **原值永不丢失**：更正保留原值（更正记录表/append-only 流水），作废保留原单（is_voided 标记 + 作废原因），审批链留痕不可删。
3. **越改权限越高**：学生只能撤回本人未受理单据；教师只能在本节点退回；作废/更正生效数据必须管理员发起且多数走审批。
4. **动过的必审计**：本文所有动作均调用 `audit_log.record(action, resource, detail)` 落 t_security_audit_log；生效数据的更正另落域审计表（t_\*_audit_trail，append-only）。
5. **联动必须回滚成对**：作废/更正一条已生效记录时，其派生物（待办/消息/风险/投影行/统计/StageEvent）由服务端在同一事务内成对撤销或补记"冲正事件"，禁止只改主单。

统一能力动词（全文约定）：

| 动词 | 语义 | 发起者 | 典型前置 |
|---|---|---|---|
| 撤回 WITHDRAW | 发起人收回未被受理的申请，单据回 DRAFT 或 CANCELLED | 学生/发起教师 | 首节点未 acted |
| 退回 RETURN | 审批人把单据退给发起人修改重提 | 当前节点审批人 | 节点 PENDING |
| 作废 VOID | 终止一条错误单据/记录的效力，保留原单与原因 | 管理员 | 视状态，多数走审批 |
| 更正 CORRECT | 修改已生效数据，保留原值与更正记录 | 责任教师/管理员 | 生效态，走审批 |
| 转办 TRANSFER | 审批任务改派他人（既有 /approvals/{id}/transfer） | 管理员/原审批人 | task PENDING |
| 重开 REOPEN | 已关闭记录恢复处理（风险/预警既有能力） | 责任人/管理员 | 终态且有新事由 |

## 1. 十类现场异常逐条设计

### 异常 1：审批卡住（待办无人处理/审批人离职休假）

- **现象**：单据长期停在某节点；学生反复催；待办列表里任务无人认领或审批人已无法登录。
- **根因可能**：① 审批人账号停用/离职未交接；② t_teacher_student_scope 未配置导致审批人看不到任务；③ 节点配置错误（workflow_code 的 node 序列指错角色）；④ 审批人漏看（无提醒）。
- **人工处理路径**：学院/学工（教务）管理员 → PC「审批中心 /admin/approval」或模块内审批列表 → 找到该 task → 点「转办」选新审批人；scope 问题则先到 /admin/system/scopes 补配范围行再让原审批人处理；节点配置错误升级到平台侧修正 workflow 配置（仅影响新单，在途单用转办疏通）。
- **系统支持**：转办（既有 POST /api/v1/approvals/{id}/transfer，status=TRANSFERRED 留痕）；催办（发 DEADLINE_REMINDER 消息）；管理员代审见 §4.1 边界。
- **是否走审批**：转办本身不走审批，但仅 `approval.transfer` 权限（管理员/上级）可操作。
- **是否写审计**：是——transfer 既有实现已审计；补配 scope 行审计 SCOPE_CHANGE。
- **数据修复边界**：**禁止**直接 UPDATE t_workflow_task.assignee 或改 status；禁止删任务重建（会丢乐观锁与历史）。

### 异常 2：学生提交错（请假时间填错/材料传错/申请错批次）

- **现象**：学生提交后发现内容错误，找辅导员求助。
- **根因可能**：填写失误；对批次/类型理解错误；代填（家长/同学）出错。
- **人工处理路径**：优先学生自助：小程序单据详情 →「撤回」（首节点未受理时可见）→ 修改重提。已被受理：学生联系辅导员 → 辅导员在审批页点「退回」填原因 → 学生收 RETURNED_NOTICE → 修改重提。已终审通过且错误重大：学院管理员发起「作废」（走审批，见 §2 各状态机作废态）→ 学生重新提交正确单。
- **系统支持**：撤回（SUBMITTED 且首节点未 acted）；退回（各审批节点标配）；作废（生效后，走审批）。
- **是否走审批**：撤回否；退回否（本身是审批动作）；生效后作废**是**。
- **是否写审计**：撤回/退回写业务流水即可；作废必写 t_security_audit_log（VOID_\<biz>）+ 域审计。
- **数据修复边界**：禁止后台直改单据字段"帮学生改好"——错误内容必须由学生端重提形成新版本，保证签名/承诺语义（如困难认定承诺栏）真实。

### 异常 3：老师误审批（点错同意/驳回、审错人）

- **现象**：审批结果与意图相反；或把 A 的单当 B 的批了。
- **根因可能**：移动端列表连续处理时点错；同名学生混淆；摘要信息不足。
- **人工处理路径**：**误驳回**：学生按退回/驳回流程重提（成本低，首选），或管理员对 REJECTED 单执行「重开至原节点」（若该状态机支持，见 §2）。**误通过**：影响已产生（生效/联动触发）→ 学院/校级管理员发起「作废」或「更正审批结论」专项流程：/admin/{module} 单据详情 →「申请冲正」→ 上级审批 → 系统回退状态并成对撤销派生物（铁律 5）。
- **系统支持**：重开、作废（冲正）、审批链留痕（t_workflow_task 不改写，冲正生成新 task 记录）。
- **是否走审批**：误通过的冲正**必须走审批**（上级节点）；误驳回重提不走。
- **是否写审计**：是——CORRECT_APPROVAL / VOID_\<biz>，detail 含原 task_id 与原因。
- **数据修复边界**：禁止直改 t_workflow_task.status（version 乐观锁与统计会错乱）；禁止删除误批产生的 StageEvent（用冲正事件对冲，时间线如实反映"批错又纠正"）。

### 异常 4：成绩错（导入错分/张冠李戴/漏录）

- **现象**：学生查到成绩与试卷不符；挂科预警误发。
- **根因可能**：导入文件行错位；教师录错（P2 录入期）；补考成绩未按规则回写；同名学生匹配错。
- **人工处理路径**：任课教师/学院教务员 → PC 教务中心成绩页 → 定位记录 →「成绩更正申请」：填原成绩/新成绩/原因/佐证材料 → 学院审核 → 教务处审核 → 系统更新 t_acad_grade 并保留原值 → 通知学生。批量错误（整表导错）：教务处对该导入批次「批次作废」→ 派生预警批量冲正 → 重新导入。
- **系统支持**：更正（CHANGE_REVIEW 流，需求 §3.11 既定）；批次作废；预警联动重算（更正后触发该生预警重评，误发预警自动 CLOSE 并通知）。
- **是否走审批**：**是**——成绩更正一律两级审批（学院+教务处），无例外通道。
- **是否写审计**：是——GRADE_CORRECT（含原值/新值 diff）+ t_acad_audit_trail 域留痕；学生收 STATUS_CHANGED。
- **数据修复边界**：**t_acad_grade 是毕业审核/奖学金/预警的共同数据源，绝对禁止直改**；更正必须经流程使三个下游同步重算。

### 异常 5：学籍异动错（批错类型/转错专业/休学起止错）

- **现象**：学生状态/班级与实际不符；休学到期时间错导致提醒错发。
- **根因可能**：申请信息错误逐级漏审；目标班级选错；终审后发现政策不符。
- **人工处理路径**：**未生效**（审批中）：节点退回或学生撤回重提。**已生效**：教务处管理员 → 学籍详情 →「异动冲正」：新建一条反向/更正异动单（append-only，不改原单）→ 走完整异动审批 → 生效后经 `change_student_status` 单一写入口恢复/更正主档，并重绑班级与方案版本。
- **系统支持**：撤回/退回（审批中）；冲正异动单（生效后）；主档单一写入口保证 StageEvent/审计四合一。
- **是否走审批**：生效后冲正**必须**走与原异动同级的审批链。
- **是否写审计**：是——ROLL_CORRECT + StageEvent 冲正事件（时间线保留"错误异动+冲正"两条）。
- **数据修复边界**：禁止直改 t_student_profile.student_status/class_id（绕过单一写入口=学工/实习/毕设/就业全域读到脏状态）；t_aa_status_change 为 append-only，禁止 UPDATE/DELETE 既有行。

### 异常 6：处分录错（对象错/级别错/事实描述错）

- **现象**：处分挂到错误学生名下；或级别/条款引用错误；学生申诉。
- **根因可能**：登记时选错同名学生；材料归档错；级别判定后改判。
- **人工处理路径**：**未生效**：登记人/学院在审批链内退回修改。**已生效**：学工处 → 处分详情 →「处分撤销（作废）」专项流程：填撤销事由+依据 → 学院/学工处（严重级加学校）审批 → VOID 生效：同事务更新 t_cs_discipline 投影行、解除对奖助/毕业审核的拦截、360 写"处分撤销"事件（原记录保留并标注撤销）。对象错的情况撤销后对正确学生重新登记。
- **系统支持**：退回；作废（撤销）；投影行与下游联动成对回滚（铁律 5）。
- **是否走审批**：生效后撤销**必须**走不低于原处分级别的审批链。
- **是否写审计**：是——DISCIPLINE_VOID（含事由）+ 域审计；学生收送达级通知。
- **数据修复边界**：禁止直改/删除 t_affairs_discipline_case 与 t_cs_discipline 投影（毕业审核实时读最新状态，脏改=资格误判）；撤销≠删除，历史必须可查（申诉复议需要）。

### 异常 7：学生归错班（导入建档时班级错/分班调整未同步）

- **现象**：辅导员列表里多/少人；学生看不到本班课表；scope 校验把本班学生判为越权。
- **根因可能**：导入文件班级列错误；建班后调整未走异动；t_class 辅导员绑定错。
- **人工处理路径**：学院管理员 → /admin/system/org（或学生主档管理）→「班级调整」功能：选学生 → 目标班级 → 提交 → 学院确认 → 主档 class_id 经受控入口更新 + StageEvent"班级调整"。若是辅导员绑定错：直接在班级管理页改 t_class.counselor_id（配置类，无需审批但审计）。批量归错（导入事故）：走导入批次修正（见异常 8）。
- **系统支持**：班级调整（轻量单级确认，非完整异动流）；班级-辅导员绑定维护；调整后课表/学工列表/scope 即时随主档刷新（均实时读，无副本）。
- **是否走审批**：单个调整走学院一级确认；批量（≥10 人）升教务处确认。
- **是否写审计**：是——CLASS_ADJUST（原班/新班）+ StageEvent。
- **数据修复边界**：禁止 SQL 批量 UPDATE class_id（绕过 StageEvent 会使 360 与统计断档）；辅导员绑定修改不得删除历史带班记录。

### 异常 8：导入错（错文件/错列/半批脏数据）

- **现象**：名册/成绩/课表导入后发现整批或部分错误。
- **根因可能**：用错模板列序；上传了旧文件；dry-run 报告未细看直接确认。
- **人工处理路径**：管理员 → 对应模块导入页 →「导入批次记录」→ 定位批次 →「批次回滚/作废」：系统按 t_student_import_batch（及各域批次表）的批次号整批标记失效并逆向处理派生物 → 修正文件后重新 dry-run → 逐条核对行级报告 → 确认导入。已被下游消费的批次（如成绩已触发预警）：回滚同时批量冲正预警并通知。
- **系统支持**：既有管线本身兜底（dry-run 行级错误、确认整批事务、跨租户拒绝）；增补设计：**批次级作废**（V1 覆盖学籍/课表/成绩三类高危导入）。
- **是否走审批**：成绩/学籍批次作废走教务处一级审批；其余管理员双人复核（操作人+确认人不同账号）。
- **是否写审计**：是——IMPORT_BATCH_VOID（批次号/行数/影响面）。
- **数据修复边界**：禁止绕过批次机制逐行 DELETE；批次表 append-only，回滚=状态标记+冲正，不物理删除。

### 异常 9：租户授权错（模块误关/套餐配错/到期误锁）

- **现象**：学校反馈"教务中心菜单没了/全部 403"；或不该开的模块开了。
- **根因可能**：平台运营在 features 面板勾错租户；套餐变更未含新模块；租户到期日期录错触发只读锁。
- **人工处理路径**：平台运营（PLATFORM_SUPER_ADMIN + PLATFORM_ADMIN_TOKEN）→ /admin/platform/tenants → 目标租户 →「功能开关」恢复 studentAffairs/academicAffairs；到期误锁 → 租户详情改到期日/「延长试用」。学校侧无自助通道（授权是平台职权），交付工程师代提工单。
- **系统支持**：既有 platform features 即刻生效机制；模块关闭期间在途数据只读冻结、恢复后自动解冻（跨端矩阵 §3 降级口径），无需数据修复。
- **是否走审批**：平台侧双人复核（操作留痕即可，V1 不设流程审批）；对**缩权**操作（关模块/降套餐）前端强制二次确认（§3.2）。
- **是否写审计**：是——平台端"拒绝即审计"已内置；变更 features/rules 均落审计。
- **数据修复边界**：禁止直改 t_platform_config/租户状态字段；误锁期间产生的 403 属正常防护，不做数据补偿。

### 异常 10：小程序提交成功但页面未刷新（学生以为失败重复操作）

- **现象**：学生点提交后转圈/报网络错，再次提交被 409；或列表看不到刚提交的单，怀疑丢单。
- **根因可能**：弱网下响应丢失（服务端已成功）；onShow 未触发重拉；本地缓存旧列表；401 静默刷新期间的请求排队表现为卡顿。
- **人工处理路径**：现场话术三步：① 下拉刷新列表/重进页面（onShow 重拉即见单据）；② 看到 409"已存在"提示=**第一次已成功**，无需再提；③ 仍不见 → 辅导员在 PC 列表按学号查单（服务端为准），确认存在则纯前端展示问题，指导学生清缓存重登。工程师侧：查 t_security_audit_log/traceId 确认请求落点。
- **系统支持**：createSubmitLock 防连点；服务端幂等（重叠/在途 409）保证重复提交不产生第二条；realFirst 不伪造成功；消息中心回执（提交成功即发回执消息，学生可在消息页自证）。
- **是否走审批 / 是否写审计**：否/常规请求审计即可。
- **数据修复边界**：**无需任何数据修复**——本异常的处理原则是"以服务端为唯一真相"，禁止为安抚用户手工补插单据（会与幂等键冲突产生真双单）。

## 2. 状态能力总表（核心状态机 × 撤回/作废/更正能力，P1 契约冻结件）

> 约定：表中"撤回"=发起人 WITHDRAW；"作废"=管理员 VOID（保留原单）；"更正"=生效后 CORRECT（保留原值）。未列出的状态一律不允许该动作（白名单制）。所有 VOID/CORRECT/REOPEN 必写 t_security_audit_log + 域审计表，表内不再重复。

| 状态机（表） | 允许撤回的状态 | 允许作废的状态 | 允许更正的状态 | 必须走审批的更正/作废 | 必须写审计的操作（动作码） |
|---|---|---|---|---|---|

### 2.1 撤回/作废/更正的统一落表设计（P1 契约冻结件，不新建平行状态表）

| 能力 | 落表方式 | 字段要点 | 说明 |
|---|---|---|---|
| 撤回 WITHDRAW | 主表状态回写（→DRAFT/CANCELLED）+ 业务流水行 | withdrawn_at/withdrawn_reason（可空）/withdraw_count | 不建独立表；workflow 实例同事务终止（instance 置 CANCELLED，task 不删） |
| 作废 VOID | 主表 `is_voided`(bool) + `void_reason` + `void_task_id`（审批任务回链），**不改原业务状态字段** | 原状态保留供追溯；列表查询默认 `is_voided=false` | 作废审批本身是一条新 workflow（VOID_\<biz> 流程码）；派生物冲正在 on_approved 回调内同事务完成 |
| 更正 CORRECT | 各域更正记录表（append-only）：t_affairs_correction / t_aa_correction | biz_type/biz_id/field/old_value/new_value/reason/material_file_id/approve_task_id | 主表值只在更正流终审通过的回调里更新；一次更正一行，批量更正逐行展开 |
| 转办 TRANSFER | 既有 t_workflow_task（status=TRANSFERRED + 新 task 行） | 复用，零新表 | —— |
| 重开 REOPEN | 主表状态机内置迁移（CLOSED→REOPENED） | reopen_reason 落 handle_record | 风险/预警既有语义，其他状态机不开重开 |

配套约束：① 两张 correction 表按域各一张（学工/教务），不按业务再拆表，biz_type 区分；② 冲正 StageEvent 的 event_type 统一 `CORRECTION`，payload 引用 correction 行 id，360 时间线按"原事件+冲正事件"成对呈现；③ 统计口径：作废单从全部指标分母/分子同步剔除（stats_service 统一在查询层过滤 is_voided），更正单按新值即时重算。

### 2.2 现场判定决策树（先分类再动手）

```
接到"数据不对/流程卡住"求助
├─ 单据还在审批中？
│    ├─ 是：内容错 → 退回/撤回重提（异常 2）；没人批 → 转办（异常 1）
│    └─ 否（已生效/已关闭）↓
├─ 错的是"结论"还是"字段"？
│    ├─ 结论错（批错/判错）→ 作废/冲正专项流程（异常 3/5/6）
│    └─ 字段错（分数/时间/文书笔误）→ 更正流（异常 4、§2.1）
├─ 影响面是单条还是整批？
│    ├─ 单条 → 对应域的更正/作废
│    └─ 整批（导入事故）→ 批次作废 + 重导（异常 8）
└─ 以上都不是（程序 bug 写坏数据）→ §4.3 数据修复工单，禁止就地改库
```

## 4. 运维兜底

### 4.1 Workflow 卡单处理（transfer / 管理员代审的边界）

- **首选 transfer**：既有 POST /api/v1/approvals/{id}/transfer——任务改派给**同层级具备该节点角色**的其他人，原任务留 TRANSFERRED 痕。适用：审批人离职/休假/scope 缺配修复前的疏通。改派对象必须能通过该节点的角色与 scope 校验（服务端验，不允许改派给任意人）。
- **管理员代审（on-behalf）为最后手段**，边界五条：① 仅租户管理员且具 `approval.admin_act`；② 仅当无同层级可转办对象（如全院唯一学工干事离职）；③ 代审在审批链上显式标注"由 {管理员} 代 {原审批人} 处理"，学生端可见；④ **不允许代审的类型**：处分校级审批、毕业终审、成绩更正终审、处分撤销（这四类只能补人后正常审或转办给新任者）；⑤ 每次代审强审计（on_behalf 标记）并抄送学院负责人消息。
- **卡单巡检**：定时扫描 t_workflow_task 中 PENDING 超 N 天（规则键 workflow.stuck_days，默认 3）的任务 → 生成 DEADLINE_REMINDER 催办；超 2N 天 → 升级消息给上级管理员（列出可转办人选）。巡检只发提醒，**不自动转办不自动审批**。
- 禁止项：直改 task 行、删实例重建、绕 mobile 包装直调 service 造"假审批"。

### 4.2 定时任务失败重跑

覆盖任务：请假逾期扫描、公示到期流转、学业预警扫描、休学到期提醒、自动升级扫描、sandbox 0 点重置。

1. **一切定时任务必须幂等**（已在各阶段任务卡冻结：逾期以 leave_id 去重、预警以 student+source+term、公示流转以批次+状态前置）。失败重跑=直接再执行一次，禁止为重跑写一次性 SQL。
2. **失败处置流程**：任务执行记录（成功/失败/影响行数）落运行日志；失败 → 运维在服务器重跑对应入口（如 `python scripts/reset_sandbox_school.py --confirm`；业务扫描走管理端"扫描执行"页的手动触发按钮，与定时同一入口同一幂等键）。
3. **补跑窗口**：跨天漏跑（如公示到期日未流转）补跑后逻辑以**应流转日**计算（服务端按到期时间判定而非执行时间），学生看到的公示期不因运维迟到而缩短。
4. **重跑验证**：重跑后核对三点——新增记录数符合预期、无重复待办/消息（查 t_unified_todo 增量）、统计口径恢复。连续两次失败升级开发排查，禁止改数据"绕过"任务。

### 4.3 数据修复 SQL 的审计留痕流程约定（唯一例外通道）

原则重申：**业务可达的修正一律走 §1/§2 的业务动作**。仅当出现业务动作无法覆盖的底层事故（如程序 bug 写坏字段、迁移脚本缺陷）才允许 SQL 修复，且必须走以下流程，缺一环即违规：

1. **工单先行**：修复申请单（现象/根因/影响表与行数/修复 SQL 全文/回滚 SQL 全文/验证方法）由开发提出，交付负责人与学校对接人双签。
2. **只读取证**：先以 SELECT 固化修复前快照（导出留存，含行数与关键字段值）。
3. **双人执行**：一人执行一人复核；生产库禁止个人常备写权限，临时授权修复窗口内有效。
4. **审计补录**：执行完毕立即调用管理端"运维操作补录"入口（或直接 audit_log.record）写入 `DATA_FIX` 审计：工单号/SQL hash/影响行数/执行人/复核人——**t_security_audit_log 里必须能查到每一次人工修复**。
5. **域留痕**：涉及 append-only 域审计表的业务数据，修复后补写一条域审计行说明修复事由（append，不改历史）。
6. **回归验证**：跑相关模块 pytest 子集 + 现场复核页面；验证结果回填工单归档（归入交付文档包）。
7. **红线**：禁止在 demo/sandbox 之外的租户上"顺手修数据"；禁止无回滚脚本的修复；禁止修复 t_workflow_task/t_security_audit_log/各 t_\*_audit_trail（审计与审批链本身永不 SQL 修复——它们错了只能追加更正记录）。

### 4.4 兜底能力自身的验收与演练要求（并入 13A-P9 / 13B-P8）

1. **能力矩阵逐格验证**：§2 总表每个"允许"格至少 1 条正向用例、每个空白格（不允许）至少抽 1 条负向用例（动作被拒且无副作用），参数化 pytest 驱动。
2. **冲正成对性专项**：处分撤销/成绩更正/异动冲正各造一例，断言派生物（投影行/预警/待办/StageEvent/统计）全部成对回滚或对冲，无孤儿记录。
3. **卡单演练**：验收前用 sandbox 造一条审批人被停用的在途单，现场演示"转办疏通"全程 ≤3 分钟；代审演练一次并核对 on_behalf 审计与抄送。
4. **定时任务重跑演练**：手动触发逾期扫描两次，断言幂等；模拟公示到期日漏跑一天后补跑，断言按应流转日生效。
5. **数据修复流程演练**：在 sandbox 上按 §4.3 七步走一遍空转（SELECT 快照+补录 DATA_FIX 审计），确认审计可查询、工单模板可用。
6. **文档联动**：本文 §1 十类异常的处理路径写入 delivery/管理员操作手册 与 辅导员操作手册 的"异常处理"章节（交付阶段同步更新，不在本文重复维护）。
