# 13A/13B 重叠子模块归属与菜单收编设计 V1.1（甲方拍板版）

> 问题：现有工作台已有 在校服务(/admin/campus-service)、学业过程(/admin/academic) 等模块，
> 与 13A 学工中心、13B 教务中心的多个子模块业务重叠。
> **甲方拍板（2026-07）：不搞双入口——在校服务、学业过程两个 PC 菜单模块整体收编删除，
> 全部子模块统一使用学工中心 / 教务中心版本。**
> 本文件是重叠项的**唯一归属裁定**，与《融合决策与复用清单》《数据表与迁移策略草案》口径一致；冲突时以本文件为准。

## 〇、甲方拍板后的两条保命边界（必须先读）

1. **删的是"PC 菜单和页面入口"，不是数据和后端**：t_cs_*、t_acad_* 全部真源表、既有 API、小程序学生端页面（在校服务/学业页）**一律保留**——它们改由 13A/13B 的新页面驱动，数据同源。删表=删学校真实数据，绝对禁止。
2. **删菜单的时机 = 新页面上线的同一次交付**：13A/13B 尚未开发，提前删菜单会让功能真空。每个旧菜单项的摘除必须与承接它的新中心页面**同一提交**完成（"收编即交付"），期间旧路由设 redirect 防书签失效。

## 一、三层去重总原则（铁律）

| 层 | 原则 | 说明 |
|---|---|---|
| 数据层 | **一份数据，一个真源表** | 重叠业务绝不建第二套表。请假=t_cs_leave（扩展），预警=t_acad_warning（扩展），成绩=t_acad_grade（权威只读），处分=t_cs_discipline（流程新表回写），宿舍=t_cs_dorm_*（扩展），心理=t_cs_mental_record（扩展），资助=CsGrant 并入 funding 抽象 |
| 服务层 | **一个状态机，一套写接口** | 同一业务的写操作只有一组端点；新中心升级状态机时旧端点保持兼容（旧状态是新状态机子集） |
| 页面层 | **一个真实现，允许多菜单入口** | 页面组件只写一份，挂主责中心路由；旧模块菜单项保留但改为 redirect 或复用同一组件，页面顶部显示归属徽标（如「由学工中心提供」） |

**判定标准（谁是主责）**：按学校真实主管部门——学工处管的归 13A，教务处管的归 13B，就业指导中心管的留 employment，迎新留 orientation。

### 3.3 收编不动清单（防误删）
- 后端：/api/v1/campus-service/*、/api/v1/academic/* 全部端点**保留不动**（小程序与新页面共用）；
- 数据：t_cs_*、t_acad_* 全部表保留（真源）；
- 小程序：学生端「在校服务」「学业」页面保留（学生视角命名贴生活，不必跟管理端改名）；
- 前端代码：frontend/src/modules/campusService、modules/academic 的组件**迁移复用**进新中心目录，不重写；确认新页面稳定一个版本后再删旧目录。

## 四、模块授权（平台运营端）口径 —— 授权驱动菜单二选一
- 13A、13B 作为**两个新授权模块项**（student-affairs / academic-affairs）接入现有模块授权。
- 收编后菜单按授权**二选一渲染**，同一时间只见一套入口：
  - 已授权 13A → 显示「学工中心」（含收编的请假/服务大厅/资助/处分/心理/宿舍）；「在校服务」菜单隐藏。
  - 未授权 13A（基础包）→ 继续显示旧「在校服务」菜单与现状功能（旧状态机），零升级感知。
  - 13B 与「学业过程」同理。
- 数据同表：学校后续购买 13A/13B 时只是菜单与流程升级，**无数据迁移动作**——这是"扩展而非平迁"策略的商业价值。

## 五、Opus 开发红线（本文件专属）
1. 重叠子模块**禁止复制粘贴页面组件**产生第二实现；只允许 redirect 或同组件双菜单挂载。
2. 禁止为重叠业务新建平行表（出现 t_affairs_leave_request 之类平行主表=直接打回）。
3. 旧端点响应结构不得变更；新状态机必须包含旧状态为子集，存量数据 backfill 见《数据表与迁移策略草案》。
4. 每个 redirect 必须在《页面树与路由设计》登记，避免菜单幽灵项。
5. 收编动作（阶段二）单独立项，不得混入 V1 提交。

## 六、一句话备忘
> 重叠不是问题，是资产：现有模块已经把最难的真实数据和写闭环做完了，13A/13B 的价值是给它们补上**完整状态机、审批流、范围权限和管理视图**，而不是再写一遍。
