## 1. 范围外理由

同 05 卡：手册 R9 冻结范围不含本三级模块，本轮甲方拍板未扩大到本项。本模块是"质量整改"（05 卡）的进度跟踪视角，与 05 卡是**同一业务实体的两个页面/视角**，不是独立业务闭环，强依赖 05 卡（进而强依赖 01/03/04 卡的问题发现数据），本轮均未开工，本模块同样不具备独立可交付性。

## 2. 依赖与前置条件（供未来立项参考，非本轮设计）

- **强业务依赖**：跟进的对象是"质量整改"（05 卡）任务的执行进度，若整改任务本身不存在，跟进页面无数据可跟踪。
- **典型功能预期**：整改任务列表（按状态筛选：待整改/整改中/待复核/已关闭/逾期）、超期预警（提醒责任人/管理者）、跟进记录时间线（类比本项目其他模块已有的 `AppTimeline`/`AppWorkflowTimeline` 使用模式，如学籍异动详情页的审批时间线）。
- **通知/待办依赖**：整改跟进大概率需要接入项目统一待办/消息机制（`todos`/`t_unified_message`，权限总控 §5.1 学校平台管理员权责范围内的通知模板配置能力可复用），超期未整改需触发提醒，这部分设计需与 05 卡的流程设计同步完成，不能拆开单独设计通知规则。
- **与 05 卡合并立项建议**：见 05 卡 §2 最后一条，本模块建议不单独立项，与 05 卡同批次设计（"发起视角"+"跟进视角"共享同一张整改任务表与状态机）。

## 3. 触发条件

需甲方对本三级模块单独拍板，**强烈建议与 05（质量整改）卡合并为同一批次立项**（而非分别独立设计两套状态机），并与 01/03/04 卡的问题发现机制一并规划；立项时需补充专项外部证据后统一设计，不得复用本卡直接开工。
