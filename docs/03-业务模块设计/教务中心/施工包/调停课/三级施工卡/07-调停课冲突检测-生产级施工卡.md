## 3. 真实业务结果与边界

- **该三级模块让哪类学校用户完成什么工作**：为发起调课/停课/补课的教师提供"提交前先看是否冲突"的即时反馈能力，避免教师填完整张表单后才在提交时被拒。
- **进入条件与退出条件**：无独立进入/退出条件，是三个申请卡表单内的辅助能力，随表单打开而可用。
- **上游输入、下游输出**：上游=表单已填的目标时间/教室字段；下游=冲突结果（供表单展示，不落库）。**真正的强制拦截仍在`POST /schedule-changes`提交时执行**（本卡的预检是UX优化，不能替代提交时的强制校验，二者调用同一底层函数，保证结果一致，不会出现"预检通过但提交时才发现冲突"的体验断层，除非并发场景——即预检和提交之间有其他人抢占了该时段，这属于正常的最终一致性场景，由提交时的强制校验兜底）。
- **本卡必须完成**：`POST /schedule-changes/conflict-check`只读预检端点；三个申请表单集成预检结果展示区。
- **明确不做及理由**：不做"自动推荐无冲突时段"（三家外部证据均未披露该能力的实现细节，非用户任务指令要求项，backlog）；不新造第二套冲突算法（禁止重复造轮子）。
- **仅学校能够决定的业务政策**：无。

## 6. 主流程、异常流程与状态机

本卡无独立状态机（纯只读查询能力）。唯一"异常"场景是预检通过后提交时仍冲突（并发抢占，见§3），此时`POST /schedule-changes`返回409，前端应重新触发一次预检刷新提示，引导用户重新选择目标时段。

## 7. API 可编码契约

| 方法与路径 | 用途 | 请求字段 | 响应字段 | permission key | 数据范围/业务关系 | 状态限制 | 错误码 | 审计 | 测试ID |
|---|---|---|---|---|---|---|---|---|---|
| `POST /academic-affairs/schedule-changes/conflict-check` | 只读冲突预检 | `taskId, targetWeekday, targetSlotNo, targetStartWeek?, targetEndWeek?, targetWeekParity?, targetWeekNo?, targetClassroom?, excludeItemId?` | `{conflict: null 或 {type, conflictWith, detail}}` | 复用宿主申请表单的apply权限（`.apply.reschedule`/`.suspend`/`.makeup`任一） | COURSE：`taskId`须为当前用户本人教学任务（预检虽不落库，仍需防止越权探测他人课表安排信息） | 无 | `NO_PERMISSION`（非本人任务，防止被用作"探测他人课表"的信息泄露通道） | 无 | T-NORMAL/T-PERM |

**安全说明**：本端点虽是只读预检，仍需做`teacher_key`归属校验，不能因为"只是查询不落库"而放宽越权检查——否则会变成一个可被任意教师用来枚举查探"某个班级/教室/教师在哪些时段有课"的信息泄露接口，违反CLAUDE.md §6.1"后端必须校验数据范围"红线。
