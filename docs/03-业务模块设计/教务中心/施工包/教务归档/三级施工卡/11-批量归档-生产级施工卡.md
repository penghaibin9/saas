## 3. 真实业务结果与边界

- 使用角色/工作内容：教务处管理员在本工作台完成归档批次的创建、发起检查、查看9域汇总、确认封存、（异常时）取消批次；`SCHOOL_ADMIN` 在极特殊场景执行"特批解冻"。
- 进入条件：无（主入口，随时可访问）；退出条件：完成确认或取消或离开页面。
- 上游输入：调用其余9个域卡的完整性检查函数聚合执行。
- 下游输出：`t_aa_archive_batch`/`t_aa_archive_item` 落库结果；`t_aa_term.status` 状态联动写入；全站教务写端点的409拦截生效范围。
- 本卡必须完成：①批次CRUD与状态机（见§6）；②9域完整性检查的统一编排（调用其余9张卡各自的 `_check_*_domain()` 函数）；③学期写保护guard函数与接入清单（见§6）；④特批解冻。
- 明确不做：不做归档的多级审批流（教务处内部单部门操作，见二级总包D-03及待确认项U-01）。
- 仅学校能够决定的业务政策：是否需要学院会签环节（二级总包U-01）。

### 6.2 学期写保护 guard 设计与端点接入清单

**guard函数**（新建于 `academic_affairs_archive_service.py`，供其余8个（非本卡）既有写服务函数调用）：

```
def guard_term_writable(db, term_id: int | str | None) -> None:
    """学期写保护：ARCHIVED 学期禁止任何关联写操作，409 TERM_ARCHIVED。"""
    if not term_id:
        return  # 无法定位学期的写操作（如字典类新建）不拦截
    from app.models import AaTerm
    t = db.get(AaTerm, int(term_id)) if str(term_id).isdigit() else None
    if t and t.status == "ARCHIVED":
        raise AppException("TERM_ARCHIVED", "该学期已归档封存，禁止修改")
```

**33个既有写端点盘点（分类决定是否接入guard，逐条给理由，不笼统"全部端点"）：**

| 端点 | 是否term强关联 | 是否接入guard | 理由 |
|---|---|---|---|
| `POST /terms`（新建学期） | 否（新建的是别的学期） | 不接入 | 新建其他学期不受当前学期归档影响 |
| `POST /terms/{termId}/publish` | 是（termId path） | **接入** | 已归档学期不应被重新发布 |
| `POST /terms/{termId}/calendar` | 是（termId path） | **接入** | 已归档学期不应再改校历 |
| `POST /time-slots` | 否（全校字典，非单学期） | 不接入 | 作息节次是学校级字典，与单学期归档无关 |
| `POST /registration-batches`（body.termId） | 是 | **接入** | 已归档学期不应再开注册批次 |
| `POST /registration-batches/{batchId}/register` | 是（经batch.term_id间接关联，需service内先查batch再guard） | **接入** | 同上 |
| `POST /status-changes` | 部分（`term_code`字符串，非强FK，需按§3异动归档卡的判据方式关联） | **接入（按term_code/effective_date判据）** | 已归档学期不应受理新异动申请 |
| `POST /status-changes/{changeId}/review` | 同上 | **接入** | 已归档学期的异动不应继续审批流转 |
| `POST /programs`、`PUT /programs/{id}`、`.../courses`、`.../submit`、`.../review` | 否（培养方案是版本化字典，跨学期共用，不与单一学期绑定） | 不接入 | 方案编制与审核不因某学期归档而受限（方案面向未来学期） |
| `POST /programs/{programId}/bind` | 弱相关（绑定的是grade_year，非已归档的历史学期） | 不接入 | 绑定面向当前/未来年级，不影响已归档学期 |
| `POST /courses`、`PUT /courses/{id}`、`.../submit`、`.../review` | 否（课程库字典） | 不接入 | 同培养方案 |
| `POST /teaching-task-batches/generate`（body.termId） | 是 | **接入** | 已归档学期不应重新生成教学任务 |
| `POST /teaching-task-batches/{batchId}/submit` | 是（经batch.term_id） | **接入** | 同上 |
| `POST /teaching-tasks/{taskId}/assign`、`.../teacher-act` | 是（经task→batch.term_id间接） | **接入** | 已归档学期的教学任务不应再调整分配/确认 |
| `POST /schedule-batches`（body.termId） | 是 | **接入** | 已归档学期不应新建课表批次 |
| `POST /schedule-batches/{batchId}/items`、`.../import`、`.../pre-publish`、`.../publish`、`.../void-reissue` | 是（经batch.term_id） | **接入** | 已归档学期的课表不应再变更 |
| `POST /grade-tasks`（body.termId） | 是 | **接入** | 已归档学期不应新建成绩任务 |
| `POST /grade-tasks/{taskId}/scores`、`.../publish` | 是（经task.term_id） | **接入** | 已归档学期的成绩不应再录入/发布（与R1"成绩回写红线"共同构成成绩终态保护） |
| `POST /warnings/scan` | 弱相关（预警扫描是全校批量动作，非单学期写） | 不接入 | 预警扫描本身是只读分析+生成预警记录，非对已归档学期历史数据的修改；若确需限制，属于R1/R3范围的独立判断，本包不越界处理 |
| `POST /graduation-audit-batches`、`.../generate`、`.../precheck` | 弱相关（批次绑定`grade_year`而非term_id，且本包§9卡已设计"终审完成后自动推进ARCHIVED"，与此处guard是同一批次生命周期的两端） | 不接入（改由"毕业资格归档"卡的批次状态自身控制，不重复加guard） | 避免同一批次被两套机制double-guard产生冲突 |
| `POST /graduation-results/{resultId}/college-review`、`.../final` | 同上 | 不接入 | 同上 |

**决策**：guard实际接入 **14 个** 端点（学期本体2个+注册2个+异动2个+教学任务4个+课表5个中的部分，精确清单以上表"接入"标记为准，实施时需与本卡§14文件清单逐条对照插入调用点），其余端点因非单学期强关联或已有更合适的自身状态机保护而不接入。这是**本包对既有8个数据域service文件的横切增量修改**（每个文件插入1行 `guard_term_writable(db, term_id)` 调用），不改动其余业务逻辑，属于本包"批量归档"卡范围内的正当横切工程（不违反CLAUDE.md"单个二级模块"边界，因为guard的宿主逻辑仍是"教务归档"要求的写保护能力，只是物理上分布在多个既有文件里）。

### 6.3 异常与并发

批次确认与解冻均有乐观锁+强制理由+二次确认三重防误操作；guard函数对"无法定位term_id"的写操作（如课程库字典类）明确不拦截，避免过度拦截伤及无关业务。
