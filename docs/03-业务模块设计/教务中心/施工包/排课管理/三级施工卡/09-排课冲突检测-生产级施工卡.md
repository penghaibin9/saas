## 3. 真实业务结果与边界

- 让学院教务员/教务处在排课过程中随时查看"当前批次还有哪些未解决的冲突"，区分"必须清零才能预发布"（HARD）与"可以备注说明后放行"（SOFT），避免逐条落课试错。
- 进入条件：批次进入SCHEDULING后随时可查；系统在"生成冲突报告"动作触发时（教务开工手册用户点击或定时批量扫描，`ai_proposal`：本卡设计为"点击按需生成"而非定时扫描，避免过度工程）批次转CONFLICT_PENDING。
- 退出条件：全部HARD冲突处理完毕（清零或已删除冲突条目之一），批次回SCHEDULING允许预发布。
- 上游输入：`t_aa_schedule_item` 全量条目；下游输出：`t_aa_schedule_conflict` 记录 + 预发布校验的前置依据。
- 本卡必须完成：批量冲突扫描函数、冲突报告持久化与查询、HARD/SOFT分级规则、SOFT冲突备注处理。
- 明确不做：不做"自动建议解决方案"（如自动推荐空闲时段，属于算法范畴，冻结不做）。
- 仅学校能决定：哪些冲突类型归为SOFT而非HARD（本卡默认：教师/班级/教室物理冲突=HARD；容量不足/教室类型不匹配=SOFT——现状代码未实现容量/类型校验，本卡属于新增能力，需教室字典定稿后才能真正实现"教室类型不匹配"判定，过渡期该SOFT类型暂不可用，如实标注）。
