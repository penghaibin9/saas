## 3. 真实业务结果与边界

- **业务结果**：学生在批次OPEN窗口内，通过小程序浏览批次内可选课程（含实时余量），完成选课/查看已选课程/已选学分统计。
- **进入/退出条件**：进入=学生登录小程序，批次状态为OPEN；退出=批次CLOSED后本页转为只读展示已选结果+补选指引入口（跳转"补选管理"卡）。
- **上游输入**：批次+可选课程数据（"选课批次""可选课程"卡）、学生学籍状态（`t_student_profile`只读）、学生历史成绩（`AaGradeRecord`/`t_acad_grade`，供先修/未修过/重修校验）、学生当前课表（`AaScheduleItem`，供冲突校验）。
- **下游输出**：`t_aa_selection_record`选课记录，供"选课名单""选课结果""选课统计"消费。
- **本卡必须完成**：可选课程浏览（含余量/教师/学分展示）、选课按钮（含八条校验+并发容量控制）、我的已选课程列表+已选学分统计。
- **明确不做**：不做课程收藏/志愿排序/AI推荐（超出范围）。
- **仅学校决定的业务政策**：学分上限具体数值（"选课规则"卡配置项，非本卡决定）。

## 6. 主流程、异常流程与状态机（含并发设计）

### 6.1 选课八条校验实现顺序（`enroll()`函数内，均为后端强制，前端仅做体验提示）

| 序号 | 校验项 | 数据来源 | 失败错误码 |
|---|---|---|---|
| 1 | 窗口内 | 批次`status=OPEN` | 409"不在选课时间内" |
| 2 | 范围内 | 课程项`applicable_major_json`/批次`applicable_scope_json` vs 学生年级/专业/班级 | 422"不在本课程适用范围内" |
| 3 | 未修过 | 查`AaGradeRecord`/`t_acad_grade`该课程`pass_status=PASSED`历史 | 422"该课程已修读通过，如需重修请走重修选课" |
| 4 | 满足先修 | 课程项`prerequisite_codes_json` vs 学生已通过课程集合 | 422"未满足先修课程要求：{课程名}" |
| 5 | 课表不冲突 | `AaScheduleItem`(行政班课表)+本批次已选课程时间 | 422"与课表存在时间冲突：{冲突课程名}" |
| 6 | 不超学分上限 | `myCreditSelected + credit ≤ rule.creditCapValue` | 422"超过本批次学分上限" |
| 7 | 不超容量 | 见§6.2并发控制 | 409 DATA_CONFLICT"课程容量已满" |
| 8 | 符合重修规则 | 非重修生对已修未通过课程需走独立重修规则（本卡范围内=非重修生该课程无`FAIL`历史即可选；重修生资格判定复用R6补考重修免修包的重修资格接口，本包留接口位，待R6包就绪对齐） | 422"不符合重修选课资格" |

学籍前置校验（先于八条执行）：`student_status == 'SUSPENDED'` → 403（手册D-07拍板）。

### 6.2 并发控制设计（P4拍板，DB行锁+唯一约束）

```
BEGIN TRANSACTION
  SELECT selected_count, capacity FROM t_aa_selection_course
    WHERE id = :selection_course_id FOR UPDATE  -- 行锁，阻塞同课程并发请求
  IF selected_count >= capacity: ROLLBACK; RAISE 409 DATA_CONFLICT
  -- 选课八条校验（1-6,8）在此事务内或事务前完成，第7条(不超容量)即本行锁校验
  INSERT INTO t_aa_selection_record (...) ON DUPLICATE KEY 复用同一行更新（D-09策略）
  UPDATE t_aa_selection_course SET selected_count = selected_count + 1 WHERE id = :id
COMMIT
```

- 唯一约束`(tenant_id, batch_id, selection_course_id, student_id)`防止同一学生对同一课程项重复插入选课记录（与行锁配合，双重防超卖：行锁防止跨学生超容量，唯一约束防止单学生重复选同一课程）。
- 事务隔离级别沿用项目MySQL默认（`REPEATABLE READ`），`SELECT ... FOR UPDATE`在该隔离级别下对行加排他锁，足以防止并发超卖（无需更高隔离级别）。
- 不引入消息队列/分布式锁（手册P4拍板"不上消息队列"），因高职选课并发规模为百人级，MySQL单机行锁性能足够（对照`ENROLL-VEN-02-CAP`正方"5万+并发"的量级差距，本项目场景远低于该量级，行锁方案充分）。

### 6.3 主流程/异常流程/状态机

| 当前状态 | 动作 | 角色 | 前置条件(八条+学籍) | 下一状态 | 错误码 | 并发/幂等 | 审计 |
|---|---|---|---|---|---|---|---|
| （无） | 选课 | 学生 | 见§6.1+§6.2 | SELECTED | 见§6.1各行 | 行锁+唯一约束（见§6.2） | `SELECTION_ENROLL` |
| DROPPED/COURSE_CANCELLED | 重新选课 | 学生 | 批次仍OPEN，重新校验八条 | SELECTED(复用同一行，D-09) | 同上 | 同上，UPDATE而非INSERT | `SELECTION_ENROLL`(detail含reEnroll=true) |

**重复提交**：前端选课按钮点击后立即disabled（loading态），防止双击触发两次请求；后端唯一约束兜底防止极端情况下的重复插入（并发双击场景，第二个请求因唯一约束冲突捕获后转为"已选课"友好提示而非500错误）。
