## 1. 最终结论

这一组是当前教务中心相对较强的部分。代码已经坚持：

- 学生主档唯一；
- 学籍状态单一写入口；
- 多节点审批；
- 多租户与数据范围；
- 预警复用已有学业过程表；
- 统一待办和通知；
- 毕业审核跨域取数；
- 终审更新学生主档并写阶段事件。

下一步不应继续堆更多异动类型，而要补以下深度：

1. 学籍业务快照和历史解释；
2. 学籍变更生效前的跨模块影响预览；
3. 注册资格逐项结果和异常补正；
4. 专业分流的志愿、容量、规则、公示和异议；
5. 预警恢复条件、处理SLA和必做干预；
6. 毕业审核精确选择学生真实方案；
7. 毕业逐项结果、责任分派、证据冻结和规则版本。

## 3. 学籍主档与单一写入口

继续坚持：

- 不新建平行学生主表；
- `t_student_profile`是身份和当前学籍事实；
- `t_aa_status_change`保存过程和历史；
- 所有学籍语义变化通过`change_student_status()`；
- 每次生效同事务写阶段事件和审计。

### 3.1 增加CI门禁

建立脚本扫描：

- 非允许文件直接写`student_status`；
- 非允许文件直接写`major_id/class_id`完成学籍变更；
- 绕过异动流程的UPDATE；
- 直接删除异动流水。

允许白名单仅包含：

- 建档初始值；
- 注册生效；
- 学籍异动终审；
- 毕业终审；
- 经审计的主档修复工具。

## 4. 学籍异动影响预览

### 4.1 为什么必须做

转专业、休学、复学、退学、留级、转班会影响：

- 培养方案；
- 当前选课；
- 教学班成员；
- 课表；
- 考试资格；
- 成绩任务；
- 实习；
- 毕设；
- 宿舍；
- 资助；
- 辅导员；
- 毕业预计时间。

终审前必须让审核人看到影响，而不是通过后才发现数据不同步。

### 4.2 建议接口

```http
POST /api/v1/academic-affairs/status-changes/impact-preview
GET  /api/v1/academic-affairs/status-changes/{id}/impact
POST /api/v1/academic-affairs/status-changes/{id}/apply-impact
GET  /api/v1/academic-affairs/status-changes/{id}/reconciliation
```

### 4.3 转专业影响示例

```text
旧方案：软件技术2025版
新方案：人工智能技术2025版
已修课程可认定：18门
需要补修：7门
可课程替代：2门
当前选课需退出：3门
当前考试需取消/转移：2门
目标班容量：已满（阻断）
预计毕业时间：可能延后1学期
```

影响结果冻结到异动单，终审生效后逐项执行并对账。

## 5. 审批节点配置与快照

当前`CHANGE_FLOW`是代码常量。建议接入现有Workflow配置，但保留领域约束：

```text
t_aa_status_change_workflow_snapshot
- status_change_id
- workflow_code
- node_sequence_json
- policy_version
- generated_at
```

提交异动时冻结节点，避免审批过程中平台配置变化导致流程跳跃。

领域服务仍负责：

- 哪些异动允许从当前状态发起；
- 哪些字段必填；
- 哪些节点必须存在；
- 终审如何生效；
- 跨模块影响如何执行。

不能把所有领域规则推给通用Workflow。

## 7. 专业分流深化

目标流程：

```text
建立批次
→ 设置专业方向和容量
→ 冻结规则
→ 圈定学生
→ 开放志愿
→ 学生填报/修改
→ 关闭志愿
→ 自动预分配
→ 人工调剂
→ 公示
→ 异议处理
→ 最终确认
→ 学籍变更
→ 培养方案绑定
→ 教学班和课表调整
```

建议模型：

```text
t_aa_major_split_batch
t_aa_major_split_option
t_aa_major_split_volunteer
t_aa_major_split_result
t_aa_major_split_appeal
```

规则快照：

- 志愿数量；
- 专业容量；
- GPA/课程成绩权重；
- 先修条件；
- 同分排序；
- 特殊资格；
- 人工调剂权限；
- 公示时间；
- 异议期限。

系统自动预分配必须可解释每个学生为什么进入某方向。

## 8. 学业预警闭环

当前已有生成、指派、干预、提醒、升级和关闭。需要为每条规则增加：

- trigger_rule；
- recovery_rule；
- owner_role；
- due_days；
- escalation_rule；
- required_interventions；
- close_evidence；
- policy_version。

示例：

```text
挂科预警
触发：当前有效挂科>=2门
恢复：补考/重修后有效挂科<2门
责任人：辅导员
首次处理期限：7天
必须动作：至少1条谈话或学业帮扶记录
升级：14天未处理升级学院
关闭：恢复规则满足且必做动作完成
```

### 跨学工联动

- 预警待办发给辅导员；
- 谈心谈话使用学工模块真实业务；
- 家校联系由学校规则决定；
- 预警只保存引用和结果，不复制谈话记录；
- 预警关闭后统一消办。

## 11. 三个可落地方案

### 方案A：增强现有JSON结果

- 精确学生方案解析；
- 异动影响预览；
- 预警恢复规则；
- 毕业JSON增加规则版本和责任人。

优点：改动较小。  
缺点：逐项查询、分派和长期扩展仍困难。

### 方案B：逐项规则与证据（推荐）

建立资格item、规则快照、责任分派和自动复跑。

优点：毕业和注册异常真正可处置、可解释。  
缺点：迁移和前端工作量较大。

### 方案C：全生命周期资格引擎

把毕业、评奖、资助、实习、毕设等资格检查抽为通用平台。

风险：过早抽象会把各领域差异抹平。必须在方案B稳定后再考虑。

## 15. 验收标准

- 任一学籍状态变化可解释、可回放；
- 终审前能看到跨模块影响；
- 生效后有对账结果，不依赖人工同步；
- 专业分流不依赖线下Excel产生最终结果；
- 预警关闭有恢复证据和必做干预；
- 毕业审核使用学生真实绑定方案；
- 每个不通过项有责任人、期限和处理入口；
- 系统明确区分FAIL与UNKNOWN；
- 学生可查看进度和补材料；
- 终审后各模块状态一致。
