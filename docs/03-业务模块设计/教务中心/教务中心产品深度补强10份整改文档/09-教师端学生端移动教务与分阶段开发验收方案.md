## 2. 外部手册启示

### 2.1 教师端

正方教师端按“申请、信息维护、成绩、查询、评价”组织教师工作，而不是展示教务处全部菜单。教师只需要看到：

- 我需要确认什么；
- 我今天上什么课；
- 哪个班需要点名；
- 哪门成绩待录；
- 哪个申请被退回；
- 哪场考试要监考；
- 哪项评价或整改待完成。

### 2.2 学生端

正方学生端首页支持常用应用、通知、课表、校历和成绩，各类申请有草稿、提交、删除、撤销和审核状态。学生入口设计的核心不是“功能大全”，而是状态和动作清楚。

## 4. 三套目录必须分离

### 4.1 投标能力目录

用途：投标参数、产品彩页、演示说明。

- 完整保留29个二级模块；
- 展示真实三级能力；
- 每项标明PC、教师端、学生端、接口、状态机、导入导出、审计和完成度；
- 未实现不得写成支持；
- 不把新增、编辑、详情当作独立业务参数。

### 4.2 学校启用目录

用途：实施和商业套餐。

建议能力配置：

```text
tenant_id
module_key
capability_key
enabled
start_at
end_at
license_source
school_policy_version
```

学校第一期可以只启用核心模块，其他能力显示“暂未启用”，不是“没有”。

### 4.3 角色日常菜单

基于：

- permissionKey；
- 数据范围；
- 本人业务关系；
- 当前学期阶段；
- 是否存在待办；
- 学校启用状态。

教务处可看到大部分模块；普通教师日常菜单控制在约8—12个高频任务；学生只看到本人服务。

## 5. 统一任务中心

### 5.1 统一任务DTO

```json
{
  "taskId": "AA-GRADE-123",
  "taskType": "GRADE_ENTRY",
  "title": "《数据结构》成绩待提交",
  "stage": "待录入",
  "priority": "HIGH",
  "dueAt": "2026-12-28T18:00:00",
  "ownerName": "张老师",
  "sourceModule": "成绩管理",
  "sourceBizId": "123",
  "route": "/pages/teacher/academic-affairs/grade-entry?id=123",
  "blockingReason": null,
  "actions": ["处理", "查看规则"]
}
```

### 5.2 任务来源

- 统一待办；
- 教学任务确认；
- 成绩录入和返回；
- 调停课申请/审批；
- 监考确认；
- 注册核验；
- 学籍异动；
- 预警跟进；
- 评教；
- 教学质量整改；
- 教材指定；
- 场地预约。

不要让每个页面单独拼一套待办格式。

### 5.3 建议服务

`backend/app/modules/academic_affairs/services/academic_affairs_task_center_service.py`

接口：

```http
GET /api/v1/mobile/teacher/academic-affairs/tasks
GET /api/v1/mobile/academic-affairs/my/tasks
GET /api/v1/academic-affairs/task-center
```

服务端按角色和范围返回，不让前端拉全量后自行过滤。

### 6.2 应补强的教师任务

- 我的教学任务；
- 我的教学班和名单；

- 场地预约；

### 7.1 学生首页

- 今日课表；
- 待办申请；
- 选课提醒；
- 考试提醒；
- 成绩更新；
- 学业预警；
- 毕业进度；
- 校历；
- 通知。

### 7.2 统一申请状态

- DRAFT：草稿；
- SUBMITTED：已提交；
- NEED_MORE_INFO：待补材料；
- IN_REVIEW：审核中；
- APPROVED：已通过；
- REJECTED：已驳回；
- WITHDRAWN：已撤回；
- EFFECTIVE：已生效；
- ARCHIVED：已归档。

每类领域状态仍保留，但映射到统一学生语言。

### 7.3 共用组件

建议建设：

- `MobileApplicationTimeline`：申请时间线；
- `MobileMaterialChecklist`：材料清单；
- `MobileRuleExplanation`：资格与规则；
- `MobileImpactPreview`：结果影响；
- `MobileSubmitGuard`：防重复；
- `MobileTaskCard`：待办卡；
- `MobileResultNotice`：结果说明。

### 7.4 每个申请必须显示

- 当前节点；
- 当前责任部门；
- 已等待时间；
- 预计处理期限；
- 缺少材料；
- 审核意见；
- 可执行动作；
- 通过后的影响；
- 驳回后如何重新办理。

## 8. 页面帮助与培训体系

每个高频三级任务建立任务卡，而不是只写长手册：

```text
任务名称
适用角色
什么时候做
前置条件
需要准备的数据
操作步骤
常见错误
完成标志
后续影响
关联任务
```

路由增加帮助元数据：

```javascript
meta: {
  permissionKey: 'academicAffairs.grade.input',
  helpTopic: 'AA.GRADE.ENTRY',
  taskType: 'GRADE_ENTRY',
  businessOwner: '教务处'
}
```

顶部搜索可以同时查：

- 功能；
- 任务；
- 帮助；
- 常见错误；
- 业务名词。

这将直接降低售后培训成本。

## 9. 三个可落地方案

### 方案A：统一首页和状态组件

- 调整教师/学生首页；
- 建申请时间线和规则解释组件；
- 后端任务仍由多个接口聚合。

优点：4—6周快速改善体验。  
缺点：任务数据源仍分散。

### 方案B：统一任务聚合API与申请时间线（推荐）

- 建服务端统一任务DTO；
- 教师和学生共用状态、材料和时间线；
- 路由meta关联帮助；
- 所有待办按范围返回。

优点：角色体验和培训能力显著提高。  
缺点：需整理多个领域的任务映射。

### 方案C：受控智能助手

在方案B稳定后加入：

- 自然语言查任务；
- 解释规则；
- 推荐操作步骤；
- 生成填报草稿；
- 错误诊断。

AI不得绕过权限、数据范围和状态机执行高危操作。

## 14. 现实替代方案

如果短期资源不足，不要试图在所有维度同时击败成熟厂商。最有价值的路线是先形成职业院校一体化优势：

```text
教务
↔ 学工
↔ 岗位实习
↔ 毕业设计
↔ 就业
```

优先做好：

- 开学准备；
- 教学运行；
- 成绩；
- 学籍；
- 学业预警；
- 毕业资格；
- 与实习、毕设、处分的自动联动；
- 教师和学生移动端。

高级自动排课、省级上报、复杂BI和大型集成可以后置。

## 16. 自我纠错总结

本10册方案已主动纠正：

- 不再把29模块缩成8个；
- 不把菜单数量当产品深度；
- 不复制成熟厂商旧式大表格和弹窗界面；
- 不把pytest通过等同学校可用；
- 不把“有一条记录”当归档完整；
- 不把教师/学生入口存在等同移动端闭环；
- 不承诺仅靠文档和编码就整体达到强智多年积累的实施、性能和服务水平。

真正完成标准是：没有参与开发的学校用户能够独立完成高频任务，核心名单和状态在全链路一致，并且系统在一个完整学期中稳定运行。
