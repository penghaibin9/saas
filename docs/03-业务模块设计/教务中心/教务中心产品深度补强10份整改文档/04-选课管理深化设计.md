---

## 1. 最终结论

现有选课模块已经不是简单按钮原型，代码中具备：

- 选课批次六态；
- 课程供给与容量；
- 选课、退课、补选；
- 行锁控制容量，避免普通超卖；
- 轮次和抽签状态；
- 时间、容量、学分、先修和学籍等校验框架；
- 低人数课程取消；
- 名单锁定和归档；
- 管理端与学生自助入口。

但距离真实学校高峰使用还有四个核心短板：

1. 规则来自批次JSON、平台配置和代码默认值，缺不可变规则快照；
2. 每次选课成功或失败缺完整决策日志和统一中文解释；
3. 名单锁定后尚未明确写入独立教学班成员的唯一事实；
4. 未通过真实并发压测证明热门课程、批次边界、超时重试和失败补偿。

正确目标不是继续加“选课统计”“选课日志”菜单，而是做到：

> 每次选课结果可解释、可追踪、不超卖，锁定后自动形成正式教学班名单，并在高峰时可对账、可补偿。

## 4. 批次规则快照

### 4.1 建议新表

```text
t_aa_selection_rule_set
- id
- tenant_id
- batch_id
- rule_version
- strategy
- max_credits
- min_credits
- allow_retake
- allow_time_conflict
- allow_cross_major
- lottery_strategy
- drop_deadline
- priority_json
- special_policy_json
- published_hash
- status
- version
```

批次从DRAFT进入PUBLISHED时：

1. 完整校验规则；
2. 写入规则快照；
3. 计算hash；
4. 后续选课只读快照；
5. 如需变更，生成新规则版本并记录影响，不直接改旧快照。

### 4.2 统一规则码

至少定义：

- BATCH_NOT_OPEN；
- OUT_OF_SCOPE；
- STUDENT_STATUS_BLOCKED；
- DUPLICATE_SELECTION；
- ALREADY_PASSED；
- PREREQUISITE_NOT_MET；
- CREDIT_LIMIT_EXCEEDED；
- CREDIT_MIN_NOT_MET；
- TIME_CONFLICT；
- COURSE_FULL；
- COURSE_MUTEX；
- MAJOR_NOT_ALLOWED；
- GRADE_NOT_ALLOWED；
- RETAKE_NOT_ALLOWED；
- WAITLISTED；
- LOTTERY_PENDING；
- BATCH_LOCKED。

## 5. 资格检查引擎

建议新增：

`backend/app/modules/academic_affairs/services/academic_affairs_selection_eligibility_service.py`

固定检查顺序：

1. 批次是否开放；
2. 学生是否在适用范围；
3. 学籍是否允许；
4. 是否重复选；
5. 是否已修通过；
6. 先修课程；
7. 学分上下限；
8. 时间冲突；
9. 课程容量；
10. 课程互斥与替代组；
11. 年级、专业、班级限制；
12. 重修规则；
13. 黑名单/白名单；
14. 是否进入候补或抽签。

统一返回：

```json
{
  "eligible": false,
  "blockingRule": {
    "code": "PREREQUISITE_NOT_MET",
    "message": "尚未通过《数据结构》，不能选择《算法设计》",
    "howToResolve": "通过先修课程，或在学校政策允许时申请特批",
    "evidence": {"courseId": "1001", "passStatus": "FAILED"}
  },
  "warnings": []
}
```

前端不再只显示“选课失败”。

## 8. 锁定名单写入教学班

第03册教学班三表完成后，修改`lock_batch()`：

```text
锁定批次
→ 校验所有有效选课记录
→ 创建或确认选课教学班
→ 生成新的roster_version
→ 写入教学班成员
→ 计算roster_hash
→ 将选课记录置LOCKED
→ 刷新学生课表
→ 推送结果通知
→ 写审计和决策日志
```

必须在同一事务内完成。任一步失败整体回滚。

正式名单来源：

- 选课教学班：锁定选课记录；
- 重修教学班：审核通过的重修名单；
- 行政班课程：教学任务生成的行政班成员；
- 特批补选：必须产生新名单版本。

## 9. 高并发与补偿

### 9.1 不要先假设必须上Redis

先对现有MySQL行锁路径做压测：

- 500并发；
- 2000并发；
- 同一热门课程；
- 多课程分散；
- 网络超时重试；
- 重复请求；
- 批次关闭瞬间；
- 数据库短暂失败。

根据结果再决定是否引入Redis库存、排队和消息队列。

### 9.2 需要具备的保障

- Idempotency-Key；
- 数据库唯一约束；
- 课程容量行锁；
- 批次时间在数据库侧再次校验；
- 请求超时后可查询最终结果；
- 日终容量与记录对账；
- 异常补偿任务；
- 人工修复入口和审计；
- 限流和分年级/学院错峰策略。

## 10. 三个可落地方案

### 方案A：增强现有JSON规则

- 为`rule_json`定义JSON Schema；
- 发布后冻结hash；
- 统一资格解释；
- 锁定时写教学班成员。

优点：约3—5周可完成。  
缺点：规则查询、版本和审计仍偏弱。

### 方案B：规则快照 + 决策日志 + 候补（推荐）

建立规则表、决策日志、候补队列和正式名单。

优点：可解释、可追踪、公平性和稳定性更接近成熟系统。  
缺点：需要迁移和学生端改造。

### 方案C：高并发选课平台

在方案B上增加：

- Redis库存；
- 分区排队；
- 请求排队号；
- 消息队列落库；
- 异步补偿；
- 热门课程隔离；
- 完整容量压测和运维预案。

只有真实学校规模证明MySQL路径不足时再启用。

## 14. 验收标准

- 任何并发场景不超卖；
- 重复请求不产生重复记录；
- 每次拒绝都有明确中文原因、规则码和解决建议；
- 名单锁定后，选课、课表、考勤、考试和成绩人数一致；
- 学院教务只能查看授权范围；
- 学生能查看操作和抽签流水；
- 候补公平性可解释；
- 峰值压测有报告和容量结论；
- 异常可以对账和补偿。
