## 1. 最终结论

这一组决定学校开学时系统能不能真正运行。

当前系统已经具备：

- 按方案生成教学任务；
- 任课教师分配与确认；
- 合班拆班；
- 教师、班级、教室三重冲突；
- 单双周；
- 手工、导入和自动排课通道；
- 课表发布和多视图；
- 调停课申请审批与通知；
- 课堂考勤和旷课预警入口。

但最大结构性短板是：

> **教学班不是独立业务对象，教学班成员也没有成为选课、考勤、考试和成绩共同消费的唯一名单事实。**

目前教学班主要依赖教学任务行和行政班派生。这对整班必修课尚可，但难以可靠支持：

- 跨行政班合班；
- 自主选课教学班；
- 分层教学；
- 体育项目班；
- 实训分组；
- 重修班；
- 中途补退选；
- 多教师分段授课；
- 考试资格名单；
- 成绩名单冻结。

整改优先级：**先建真实教学班与成员，再深化自动排课。** 没有稳定名单时，排课算法再复杂也无法保证后续考勤、考试和成绩一致。

### 3.2 类型

`class_type`：

- ADMIN_CLASS：行政班整班；
- MERGED_CLASS：合班；
- ELECTIVE_CLASS：选课班；
- LEVEL_CLASS：分层班；
- SPORTS_CLASS：体育项目班；
- PRACTICE_GROUP：实训分组；
- RETAKE_CLASS：重修班。

`source_type`：

- EXECUTION_PLAN；
- SELECTION；
- MANUAL；
- RETAKE；
- MAJOR_SPLIT。

### 3.3 状态机

```text
DRAFT
→ ROSTER_BUILDING
→ ROSTER_READY
→ TEACHER_CONFIRMED
→ SCHEDULED
→ PUBLISHED
→ RUNNING
→ COMPLETED
→ ARCHIVED
```

名单变更不能覆盖原名单，必须产生新的`roster_version`和`roster_hash`。

### 3.4 名单冻结节点

- 教师确认前：允许普通调整；
- 课表发布前：允许受控调整；
- 选课名单锁定：生成正式版本；
- 考试资格生成：记录使用的名单版本；
- 成绩任务生成：记录使用的名单版本；
- 学期归档：永久只读。

## 4. 教学任务生成深化

### 4.1 移除固定18周

修改`academic_affairs_task_service.py`，新增：

```python
def resolve_teaching_week_span(db, term_id: int, plan_item) -> dict:
    """从校历和执行计划计算有效周次，不使用固定18周。"""
    # 读取教学周、考试周、节假、集中实训周
    # 支持前半学期、后半学期、单双周、集中周
    ...
```

周学时计算依据：

- 均匀周学时；
- 集中授课；
- 前半/后半学期；
- 单双周；
- 模块化短课；
- 连续实训周。

### 4.2 生成前差异预览

接口：

```http
POST /api/v1/academic-affairs/teaching-task-batches/generate-preview
POST /api/v1/academic-affairs/teaching-task-batches/generate
```

预览返回：

- 应新增；
- 已存在且一致；
- 已存在但计划变化；
- 无课程ID；
- 无行政班或教学班；
- 班级人数异常；
- 学时异常；
- 无已发布执行计划；
- 需要人工说明的方案外课程。

### 4.3 教师资格和工作量

分配教师前校验：

- 任课资格；
- 教师状态；
- 所属学院/跨院授权；
- 本学期工作量；
- 时间可用性；
- 多教师分段；
- 实训/技能课程所需资格。

警告与阻断要分级，不能只返回一个字符串。

## 5. 排课约束深化

### 5.1 继续保留的硬冲突

- 教师同时间冲突；
- 教学班/学生成员冲突；
- 教室冲突；
- 周次与单双周冲突。

### 5.2 新增硬约束

- 教室容量不足；
- 教室类型不符；
- 教师不可用时间；
- 教室维修或预约占用；
- 跨校区通勤时间不足；
- 同一学生属于两个同时上课的教学班；
- 连续节次不满足课程要求；
- 学期业务窗口已关闭；
- 已归档或已发布不可直接覆盖。

### 5.3 软约束

- 教师时间偏好；
- 每日最大课时；
- 上午/下午均衡；
- 同课程教室稳定；
- 专业课集中；
- 公共课错峰；
- 连续节次优先；
- 学生每天课时均衡。

### 5.4 规则快照与运行结果

建议新增：

```text
t_aa_schedule_rule_set
t_aa_schedule_constraint
t_aa_schedule_run
t_aa_schedule_run_item
t_aa_schedule_unscheduled_reason
```

每次自动排课运行保存：

- 规则版本；
- 输入任务hash；
- 输入名单版本；
- 已排数量；
- 漏排数量；
- 硬冲突数；
- 软约束得分；
- 每个漏排原因；
- 运行耗时；
- 后续人工调整数量。

算法必须“可解释”，不能只显示成功率。

## 8. 课堂考勤深化

考勤必须基于教学班正式成员和课表场次，而不是临时按行政班推导。

目标链：

```text
已发布课表生成课堂场次
→ 教师点名
→ 自动匹配学工请假
→ 教师提交
→ 补录/更正
→ 旷课规则扫描
→ 辅导员待办
→ 干预记录
→ 自动恢复/关闭或升级
```

状态：

- PRESENT；
- LATE；
- EARLY_LEAVE；
- ABSENT；
- LEAVE_MATCHED；
- OFFICIAL_DUTY；
- MAKEUP_PENDING。

补录和更正必须保存：原值、新值、原因、证据、操作者、时间和审核要求。

## 9. 三个可落地方案

### 方案A：教学任务上增加成员JSON

只适合极短期演示，不推荐。成员JSON难查询、难版本化、难被考务和成绩稳定复用。

### 方案B：独立教学班与成员（推荐）

新增教学班、成员、教师关系三张核心表；选课锁定、考务资格、成绩任务和考勤全部消费它。

优点：从根本上解决名单不一致。  
缺点：需要回填、双读和多个服务逐步切换。

### 方案C：完整教学运行引擎

在方案B上增加：

- 排课规则与运行；
- 课表版本；
- 课堂场次；
- 调停课执行核销；
- 教师工作量自动核算；
- 教学进度与计划偏差。

## 10. 推荐开发顺序

1. 独立教学班、成员、教师关系；
2. 从现有教学任务回填教学班；
3. 行政班整班成员生成；
4. 教学任务改读真实校历和执行计划；
5. 合班拆班改为操作教学班和成员版本；
6. 排课冲突切换到教学班/成员；
7. 选课锁定写教学班成员；
8. 考务、成绩、考勤读取统一名单；
9. 课表版本；
10. 调停课执行确认和学时核销；
11. 自动排课规则与解释；
12. 教学进度和工作量。

不能从高级自动排课算法开始。

## 12. 数据迁移策略

### 12.1 回填教学班

对每条有效教学任务：

1. 生成稳定教学班；
2. 旧`teaching_class_code/name`写入快照；
3. 从行政班生成成员；
4. 合班任务合并成员去重；
5. 保存来源任务ID；
6. 计算`roster_hash`；
7. 输出无法回填报告。

### 12.2 双读切换

- 第一阶段：新表回填，旧接口仍读任务字段；
- 第二阶段：详情接口返回新教学班，同时保留旧字段；
- 第三阶段：选课/考务/成绩逐个切换；
- 第四阶段：新业务强制写新表；
- 旧字段只保留历史展示，不删除。

## 14. 验收标准

- 选课、课表、考勤、考试和成绩看到的学生名单一致；
- 合班后成员不丢失、不重复；
- 教学周完全来自校历，不再固定18周；
- 每个漏排任务都有机器可读原因和处置入口；
- 课表可还原历史发布版本；
- 调停课能证明通知对象、实际执行和学时核销；
- 任课教师只能看到本人教学班；
- 复杂业务不使用右侧抽屉；
- 数据迁移有完整对账报告。
