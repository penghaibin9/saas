## 1. 最终结论

这一组目前已经“能维护基础数据”，但还没有完全成为后续教务业务可信的坐标系。主要短板是：

- 学期只有时间和状态，缺各业务窗口与版本快照；
- 校历修改缺影响分析，发布后变更可能影响课表、考试和任务周学时；
- 专业和班级缺年度生命周期及组织同步对账；
- 课程先修关系、适用专业等长期放在JSON中；
- 课程停用、版本变化没有统一引用影响分析；
- 教务看板展示了很多数量，但没有给出“本阶段能否继续”的门禁结论。

成熟教务系统的基础资源不是后台字典，而是所有下游业务共同引用、可版本化、可追溯、可做影响分析的主数据。

## 2. 外部手册带来的产品启示

强智基础资源覆盖学校、校区、单位、专业、年度专业、班级、年度招生计划、教学功能区、教师、学年学期、节次、楼栋、教室、标签和学期进度。值得借鉴的是：

1. **专业有年度属性**：同一专业在不同招生年度可能学制、方向和培养方案不同；
2. **学期是统一时间轴**：注册、选课、排课、考试、录分和归档都依赖同一学期；
3. **校历变化会影响业务**：已发布后不能像普通字典一样直接覆盖；
4. **课程有受控入库过程**：申请、审核、入库、使用情况查询是一个完整链；
5. **资源有可用性**：教室容量、类型、维修和预约共同约束排课、排考。

## 4. 目标产品结构

### 4.1 学期业务窗口

建议新增：

```text
t_aa_term_business_window
- id
- tenant_id
- term_id
- window_type
- start_at
- end_at
- target_scope_json
- status
- published_at
- version
```

`window_type`至少包括：

- REGISTRATION：注册；
- PROGRAM_EDIT：培养方案维护；
- EXECUTION_PLAN：执行计划；
- TASK_CONFIRM：教学任务确认；
- SCHEDULING：排课；
- SELECTION：选课；
- EXAM_ARRANGE：排考；
- GRADE_ENTRY：录分；
- GRADE_RECHECK：复查；
- ARCHIVE：归档。

业务窗口发布后形成快照，变更必须有原因、影响预览和审计。

### 4.2 校历版本与影响

建议新增：

```text
t_aa_calendar_version
t_aa_calendar_change
t_aa_calendar_impact
```

每次已发布校历调整必须先计算：

- 受影响的课表项；
- 受影响的考试安排；
- 受影响的调停课；
- 受影响的教师和学生；
- 总教学周是否变化；
- 教学任务周学时是否需要重算；
- 已发布通知是否需要补发。

### 4.3 年度专业与组织同步

不要新建平行学院、专业、行政班主表。建议新增教务扩展事实：

```text
t_aa_major_year
- major_id
- admission_year
- education_years
- training_level
- enroll_status
- expected_graduation_year
- program_id
- status

t_aa_org_sync_batch
t_aa_org_sync_diff
```

组织同步差异必须区分：新增、改名、停用、归属变化、班级合并、下游引用冲突。应用差异前显示影响数量，不允许静默覆盖本地数据。

### 4.4 课程关系结构化

建议把关键JSON逐步结构化：

```text
t_aa_course_prerequisite
- course_id
- prerequisite_course_id
- relation_type
- min_score
- allow_concurrent

t_aa_course_applicable_major
- course_id
- major_id
- grade_from
- grade_to

t_aa_course_outline_version
- course_id
- version_no
- file_id
- content_json
- status
- workflow_instance_id
- approved_at
```

课程停用前必须反查：

- 有效培养方案；
- 未归档执行计划；
- 当前教学任务；
- 选课批次；
- 成绩规则；
- 学生补修和毕业审核。

## 5. 教务看板升级为“阶段门禁”

看板首屏必须直接给结论：

```text
当前阶段：开学准备
总体状态：有阻断
阻断项：
1. 2个专业年级未绑定有效培养方案
2. 18门应开课程未生成执行计划
3. 7个教学任务未分配教师
4. 3个排课硬冲突未清零
责任人：对应学院教务员
最晚完成：2026-08-25 18:00
下一动作：进入开学准备处置台
```

建议新增服务：

`backend/app/modules/academic_affairs/services/academic_affairs_readiness_service.py`

建议新增接口：

```http
GET  /api/v1/academic-affairs/readiness/opening

POST /api/v1/academic-affairs/readiness/opening/{exceptionId}/assign
POST /api/v1/academic-affairs/readiness/opening/{exceptionId}/close
```

统一异常DTO：

```json
{
  "exceptionCode": "PROGRAM_NOT_BOUND",
  "severity": "BLOCKER",

  "objectId": "123",
```

## 6. 三个可落地方案

### 方案A：不改核心表的快速补强

- 新增开学准备聚合服务；
- 校历变更提供只读影响预览；
- 课程JSON保留，但统一解析和校验；
- 组织同步先用Excel差异对账；
- 看板显示阻断项和处置路由。

优点：风险低，约4—6周可见效果。  
缺点：历史版本、结构化关系和长期治理仍不足。

### 方案B：结构化商业方案（推荐）

- 学期业务窗口；
- 校历版本与影响表；
- 年度专业和组织同步批次；
- 课程先修、适用专业、大纲版本；
- 阶段门禁与异常责任中心；
- 独立详情和影响预览页面。

优点：基础资源真正成为下游可信事实。  
缺点：需要迁移、回填和双读兼容。

### 方案C：平台主数据方案

- 对接统一组织、人事、身份和教室主数据；
- 支持多校区独立校历和作息；
- 国家/省级课程标准自动比对；
- 主数据事件驱动下游模块。

适合后期，不应抢在方案B之前。

## 8. 验收标准

- 教务处用户10秒内知道开学准备是否可继续；
- 学期各业务窗口可配置、发布、追踪和审计；
- 校历修改能列出真实受影响课表、考试、教师和学生；
- 课程先修关系不再只依赖JSON；
- 停用课程前能看到影响清单；
- 组织同步不会静默覆盖数据；
- 多校区和学校差异有扩展空间；
- 页面不暴露JSON、数据库ID和技术状态码；
- 原29个二级模块和旧路由全部保留兼容。
