## 1. 最终结论

当前成绩主线已经具有较好的业务基础：

- 教学班成绩任务；
- 教师本人范围；
- 统一待办；
- 平时、期中、期末比例；
- 学院审核；
- 教务发布；
- 发布原子回写` t_acad_grade`；
- 成绩更正、复查；
- 补考、重修、缓考、免修；
- 学业预警和毕业审核联动。

真正限制产品深度的是：

> **成绩方案固定为平时、期中、期末三个分项。**

职业院校常见课程可能包含：

- 项目任务1/2/3；
- 实训操作；
- 作品成果；
- 技能考核；
- 考勤；
- 企业评价；
- 过程报告；
- 理论考试；
- 多次补测；
- 等级制或合格制。

继续向`AaGradeRecord`增加固定字段会导致模型失控。正确方向是动态成绩方案和分项明细，旧三列只作为兼容预设。

## 5. 兼容旧三分项

旧字段暂不删除。迁移时：

```text
usual_ratio > 0 → USUAL默认组件
midterm_ratio > 0 → MIDTERM默认组件
final_ratio > 0 → FINAL默认组件
```

旧成绩行生成对应组件分数。迁移后必须对账：

- 旧总评；
- 新计算总评；
- 差异；
- 舍入规则；
- 特殊状态；
- 无法迁移原因。

任何差异不得静默覆盖历史总评。首期采用双读：

- 新任务读动态方案；
- 历史任务无方案时使用旧三列；
- API同时返回旧兼容字段和新components；
- 稳定一个完整学期后再停止新建旧格式任务。

## 8. 成绩质量检查

建议新增：

`academic_affairs_grade_quality_service.py`

提交前检查：

- 名单是否完整；
- 必填分项是否全部录入；
- 权重是否等于100%；
- 分数是否在范围内；
- 特殊状态是否互斥；
- 缓考/免修学生是否误录；
- 名单版本是否变化；
- 全班同分；
- 大量满分或0分；
- 及格率异常；
- 单项与总评不一致；
- 应参加考试但无考试记录；
- 教师导入是否存在未匹配学号。

返回三类：

- BLOCKER：不能提交；
- WARNING：确认后可以提交；
- INFO：提示。

每个提示包含规则码、学生、字段、建议动作。

## 9. 审核、发布和版本

### 学院审核

审核内容不是只点“通过”：

- 名单完整；
- 方案正确；
- 分数完整；
- 分布异常已解释；
- 特殊状态有证据；
- 任课教师已确认。

### 教务发布

发布事务：

1. 锁定任务版本；
2. 重跑BLOCKER检查；
3. 计算总评；
4. 生成发布版本；
5. 投影` t_acad_grade`；
6. 更新学分、绩点；
7. 触发预警扫描；
8. 刷新毕业预审；
9. 给学生通知；
10. 写审计和outbox；
11. 全部成功才提交。

### 发布版本

新增或补充：

```text
t_aa_grade_publish_version
- task_id
- version_no
- roster_hash
- scheme_hash
- result_hash
- published_at
- operator
- status
```

## 10. 复查与更正

### 10.1 成绩复查

流程：

```text
学生在期限内申请
→ 任课教师核查
→ 学院复核
→ 无错误：回复并关闭
→ 需要改分：转成绩更正
→ 教务终审
→ 学生通知
```

申请材料：

- 课程；
- 复查类型；
- 理由；
- 佐证；
- 申请时间；
- 原成绩快照。

### 10.2 成绩更正

必须保存：

- 原始方案和分项快照；
- 原始总评；
- 新分项和新总评；
- 原因；
- 附件；
- 申请人；
- 审核链；
- 生效时间；
- 新旧投影ID；
- 对绩点、预警和毕业结果的影响。

已发布成绩不得直接UPDATE后不留版本。

## 11. 补考、重修、缓考、免修统一投影

四个业务不能各自直接改总评。建议新增统一服务：

```python
def apply_special_grade_result(
    student_id: int,
    course_id: int,
    source_type: str,
    source_biz_id: int,
    raw_score,
    rule_snapshot: dict,
) -> dict:
    """计算有效成绩、绩点和学分投影，保存来源和规则快照。"""
    ...
```

批次规则必须冻结：

- 补考及格按60还是实得；
- 重修覆盖、并存还是取最高；
- 缓考按正常考试；
- 免修是否记成绩、学分和绩点；
- 作弊是否允许补考；
- 清考的适用对象；
- 课程认定与替代如何进入有效成绩口径。

历史规则变化不能重算已发布结果。

## 12. 三个可落地方案

### 方案A：保留三分项，增加自定义JSON

优点：改动小。  
缺点：查询、导入、统计、校验和版本都困难，只适合短期兼容。

### 方案B：动态成绩方案（推荐）

建立scheme、component、component_score三层；旧三列作为兼容投影。

优点：适合职业院校复杂考核，长期可维护。  
缺点：迁移和前端矩阵工作量较大。

### 方案C：课程目标与达成度平台

在方案B稳定后增加：

- 课程目标；
- 毕业要求指标点；
- 分项与目标映射；
- 试卷分析；
- 达成度分析。

不应抢在动态成绩基础之前。

## 16. 验收标准

- 支持合理数量的动态考核项，不需要改表；
- 教师录入中断不丢数据；
- 提交前自动发现名单和分数异常；
- 学生只看到已发布成绩；
- 更正可以完整还原前后值；
- 补考重修按批次规则可解释；
- 预警、绩点和毕业使用同一有效成绩口径；
- 历史成绩迁移零静默差异；
- 全班成绩录入不使用抽屉；
- 发布失败不会出现部分学生已更新。
