## 1. 最终结论

这组六个模块决定产品在招投标中是否显得完整，也决定上线后是否能治理、追责、复盘和交付。

当前代码已经不是简单占位：

- 教材覆盖目录、选用、审核、征订、到货、发放、费用和统计；
- 教室、实训室、设备、预约、占用、冲突和维修均有入口；
- 评教支持批次、匿名、多来源评价、结果、申诉和归档；
- 教学质量已实现督导、巡课、检查、事故、整改和跟进；
- 教务统计已有多指标、多维筛选和下钻；
- 教务归档已有九域检查、学期写保护、导出和解冻审计。

真正短板集中在：

1. 教材与财务边界需要更清楚；
2. 教学资源缺统一可用性日历；
3. 评价指标、问卷、权重和样本规则缺版本化；
4. 教学质量的代码说明与真实实现已经发生漂移；
5. 统计缺口径版本和历史快照；
6. 归档完整性按“记录数是否大于0”，无法证明业务真正完成。

## 3. 教材管理深化

### 3.1 目标业务链

```text
教材目录与版本
→ 教师按教学任务指定主教材/参考教材
→ 学院审核
→ 教务备案
→ 学生自愿预订/班级数量汇总
→ 征订
→ 到货差异
→ 发放/退订/补发
→ 费用登记和财务对账
→ 归档
```

### 3.2 需要补强的事实

- 教材ISBN、版次、出版时间、适用课程版本；
- 国家/省规划教材标识及证明文件；
- 主教材、参考教材、自编教材；
- 一门课程多教材；
- 教师指定申请与替换原因；
- 学生是否自愿预订；
- 退订截止；
- 征订数量和实际到货差异；
- 班级发放、个人签收；
- 退书、破损、补发；
- 费用应收、减免、已对账、未对账；
- 财务系统回执。

### 3.3 财务边界

教务教材模块可以记录：

- 应收金额；
- 发放数量；
- 学生确认；
- 财务同步状态；
- 财务回执号。

不能在没有财务接口时宣称“已真实收费”。当前费用台账应明确标注“教务登记”或“待财务对账”。

## 4. 教学资源统一可用性

当前教室、实训室、设备、预约和维修均有能力，但排课、排考和预约必须消费同一可用性事实。

建议新增：

```text
t_aa_resource_availability
- id
- tenant_id
- resource_type
- resource_id
- start_at
- end_at
- availability_type
- reason
- source_type
- source_id
- priority
- status
- version
```

`availability_type`：

- AVAILABLE；
- SCHEDULE_OCCUPIED；
- EXAM_OCCUPIED；
- BOOKING_OCCUPIED；
- MAINTENANCE；
- CLOSED；
- RESERVED；
- TEMPORARY_BLOCK。

统一服务：

```python
def query_resource_availability(resource_type, resource_id, start_at, end_at, context):
    """排课、排考、预约调用同一函数，返回占用来源和冲突原因。"""
    ...
```

维修生效后，系统应主动找出受影响的课表、考试和预约，并生成处置待办。

### 5.2 权重快照

当前代码权重写死。应将以下内容作为批次快照：

- 学生评价权重；
- 教师自评权重；
- 同行评价权重；
- 督导评价权重；
- 领导评价权重；
- 缺失来源如何归一化；
- 最低样本量；
- 小样本隐藏规则；
- 结果分级规则。

批次发布后不能被平台配置变化重算。

### 5.3 样本有效性

结果必须展示：

- 应评人数；
- 已评人数；
- 完成率；
- 有效答卷；
- 无效/规律性答卷；
- 最低样本是否满足；
- 是否达到发布条件；
- 匿名保护规则；
- 教师可见范围；
- 学院可见范围。

学生匿名不等于系统无任何防刷机制，但普通业务查询不得反查学生身份。

## 6. 教学质量深化

### 6.1 先修正文档与代码漂移

`academic_affairs_quality_service.py:3-8`仍声明除看板和导出外的能力为planned，而后续代码已经实现真实记录和整改。第一步应：

- 更新文件头说明；
- 核对施工文档状态；
- 核对`navPlan.js`状态；
- 核对路由和测试；
- 建立自动检查，避免已实现代码仍标注planned。

### 6.2 目标闭环

```text
督导/巡课/检查发现问题
→ 问题认定
→ 是否需要整改
→ 建整改任务
→ 责任学院/教师
→ 截止时间
→ 提交整改材料
→ 复核
→ 关闭/退回/升级
→ 归档
```

教学事故等级、认定条件和处理方式属于学校规章制度，AI不得自行制定。系统提供：

- 制度版本；
- 分类字典；
- 认定流程；
- 证据；
- 处理决定引用；
- 整改；
- 申诉/复核；
- 归档。

### 6.3 SLA

每个质量问题必须有：

- severity；
- owner_role；
- owner_id；
- due_at；
- escalation_at；
- required_evidence；
- close_rule。

## 8. 教务归档语义重构

### 8.1 当前缺陷

当前逻辑的核心近似：

```python
present = record_count > 0
```

这会产生错误：

- 有一条草稿培养方案也被认为“方案域存在”；
- 有一个未发布课表批次也被认为“课表域存在”；
- 有一条未发布成绩也被认为“成绩域存在”；
- 毕业批次只建立未终审也可能有记录。

### 8.2 各域语义门禁

#### 培养方案

- 所有在招专业年级有已发布方案；
- 方案validator通过；
- 课程和规则快照完整；
- 无多个有效绑定。

#### 教学任务

- 应开课程无遗漏；
- 执行计划已发布；
- 教师确认完成；
- 教学班名单已锁；
- 未完成任务有正式豁免。

#### 课表

- 正式发布；
- BLOCKER冲突为0；
- 所有需排任务已排或有漏排特批；
- 发布版本和通知结果完整。

#### 考务

- 批次已完成或归档；
- 课程、候选人、座位和监考完整；
- 在途异常已清零或有转后续记录。

#### 成绩

- 所有应录任务已发布或有正式豁免；
- 在途复查和更正为0；
- 投影对账一致；
- 发布版本完整。

#### 毕业

- 终审完成；
- 逐项证据冻结；
- 结论与主档对账；
- 证书或后续批次状态明确。

### 8.3 建议新模型

```text
t_aa_archive_rule
t_aa_archive_check_result
t_aa_archive_evidence
t_aa_archive_package_manifest
```

`manifest`保存：

- 文件列表；
- 数据域；
- 记录数量；
- 业务状态；
- 规则版本；
- sha256；
- 导出人；
- 时间；
- 水印；
- 包hash；
- 下载审计。

## 9. 三个可落地方案

### 方案A：补现有服务规则

- 评价权重转配置并冻结；
- 资源统一查询服务；
- 归档按状态而不是数量；
- 统计增加口径说明。

优点：约6—8周，见效快。  
缺点：历史快照和证据能力仍不足。

### 方案B：规则版本 + 指标快照 + 语义归档（推荐）

建立评价模板、指标定义、指标快照、归档规则、检查结果和manifest。

优点：治理、投标和学校交付能力明显增强。  
缺点：需要跨多个服务逐步落地。

### 方案C：数据治理与电子档案平台

加入：

- 数据质量规则中心；
- 外部BI；
- 电子签章；
- 长期保存格式；
- 档案馆接口；
- 指标仓库。

需专门团队和学校实际要求后再做。

## 13. 验收标准

- 教材、资源、评价和质量均形成真实闭环；
- 评价结果可解释，权重和模板不是写死；
- 质量问题有责任人、期限、证据和关闭规则；
- 统计历史不随新口径漂移；
- 归档不再用“有一条记录”判断完整；
- 归档包可验证未被篡改；
- 已归档学期相关写入口全部被拦截；
- 教材费用不冒充财务实收；
- 文档、菜单、路由、注释和代码状态一致。
