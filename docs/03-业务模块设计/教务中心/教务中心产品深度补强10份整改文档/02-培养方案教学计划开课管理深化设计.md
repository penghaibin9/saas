## 1. 最重要的产品判断

这是教务中心当前最需要优先整改的领域。

现有系统已经具备：

- 培养方案主档；
- 方案课程；
- 专业年级绑定；
- 课程模块和学分要求；
- 毕业要求与实践环节；
- 两级审核、发布、版本、变更和归档；
- 从方案生成教学任务。

但其本质仍偏向**静态方案编制器**，尚未成为成熟教务系统中的“教学执行发动机”。关键原因：

1. 方案提交强校验主要集中在总学分；
2. 方案课程快照字段不够完整；
3. 教学计划当前主要是将培养方案、教学任务和归档页面重新收编；
4. 缺独立的学期执行计划、计划微调单和计划—实际差异；
5. 方案新版本缺系统化影响分析；
6. 发布方案与生成教学任务之间缺可审核的执行层。

正确目标：

```text
专业标准/学校规则
→ 培养方案版本
→ 专业年级/班级绑定
→ 学年执行计划
→ 学期执行计划
→ 开课计划
→ 教学任务
→ 课表/选课/考试/成绩
→ 计划执行偏差
→ 毕业达成
```

## 2. 外部成熟系统启示

强智手册在“指导培养方案”之外，单独提供：

- 培养方案维护控制；
- 版本管理；
- 课程体系；
- 教学进程；
- 审核；
- 综合查询；
- 教学执行计划；
- 计划微调审核；
- 微调情况查询；
- 学期任务查询；
- 班级进程安排。

这说明成熟系统明确区分：

- **方案**：专业人才培养的长期规则；
- **执行计划**：某年级、某学期实际准备执行的课程安排；
- **教学任务**：实际交给学院和教师执行的开课对象。

不能把三者都压在一个“方案课程列表”或“教学任务批次”中。

## 4. 培养方案目标模型

### 4.1 方案主档应表达的内容

建议在现有`AaProgram`上补字段，或建立配套规则表：

- training_level：培养层次；
- education_years：学制；
- total_credits：总学分；
- total_hours：总学时；
- theory_hours/practice_hours；
- required_credits/elective_credits；
- min_practice_credits；
- max_term_credits；
- certificate_rule_version；
- graduation_rule_version；
- source_standard_id；
- published_snapshot_hash；
- effective_from/effective_to。

### 4.2 方案课程必须冻结业务快照

目标：课程库以后改名、改学分、改考核方式时，历史方案仍能准确还原。

### 4.3 结构化模块和规则

不建议长期只用`requirement_json`。可新增：

```text
t_aa_program_module
- program_id

- credit_required
- hours_required
- required_course_count
- sort_order

- parameters_json
```

规则示例：

- 公共基础至少30学分；

## 5. 独立教学执行计划

### 5.1 为什么必须独立

学校常见情况：

- 某课程因师资原因提前或延后；
- 某学期临时增加技能训练；
- 某年级因节假、实习周调整教学周；
- 某课程由理论改为理实一体；
- 某班因分流、转专业改变人数；
- 同一培养方案在不同班级执行略有差异。

如果直接从方案生成教学任务，系统无法区分“方案本来是什么”和“本学期实际批准执行什么”。

### 5.3 状态机

```text
DRAFT
→ GENERATED
→ COLLEGE_REVIEW
→ ACADEMIC_REVIEW
→ PUBLISHED
→ EXECUTING
→ COMPLETED
→ ARCHIVED

退回：COLLEGE_REVIEW/ACADEMIC_REVIEW → RETURNED → DRAFT
```

调整单：

```text

                              └→ RETURNED/REJECTED
```

## 6. 培养方案规则引擎

建议新增：

`backend/app/modules/academic_affairs/services/academic_affairs_program_validator.py`

统一返回：

```json
{
  "passed": false,
  "summary": {"blocker": 2, "warning": 3},
  "items": [
    {
      "ruleCode": "MODULE_CREDIT_NOT_MET",
      "level": "BLOCKER",
      "path": "modules.PROFESSIONAL_CORE",
      "message": "专业核心要求30学分，当前26学分",
      "suggestion": "补充课程或调整经审批的模块要求"
    }
  ]
}
```

至少实现以下规则：

1. 方案基本信息完整；
2. 总学分、模块学分和课程学分可对账；
3. 同一课程不重复；
4. 所有引用课程为有效版本；
5. 开课学期在学制范围内；
6. 先修课程顺序合理且无循环；
7. 必修、限选、任选结构满足要求；
8. 理论/实践比例满足规则；
9. 实习、毕设、集中实践周数满足规则；
10. 学分和学时换算异常；
11. 毕业要求有可执行映射；
12. 同专业年级不存在多个有效绑定；
13. 发布前生成不可变校验报告和hash。

### 保存、提交、发布三档强度

- SAVE：允许不完整，返回提示；
- SUBMIT：所有BLOCKER必须清零；
- PUBLISH：重新校验并冻结课程、模块、规则和绑定快照。

## 7. 版本影响分析

新建方案版本前必须回答：

- 哪些专业年级和班级正在使用旧版；
- 哪些学生已按旧版修读；
- 哪些课程新增、删除、移学期、改学分、改性质；
- 哪些执行计划和教学任务已生成；
- 哪些学生可能产生补修、免修或替代；
- 哪些毕业规则变化；
- 新版本何时生效；
- 是否迁移历史学生；
- 迁移后如何对账。

建议接口：

```http
POST /api/v1/academic-affairs/programs/{id}/impact-preview
POST /api/v1/academic-affairs/programs/{id}/versions
POST /api/v1/academic-affairs/program-bindings/{id}/migration-preview
POST /api/v1/academic-affairs/program-bindings/{id}/migrate
```

影响分析只读，不应在预览阶段写入任何业务数据。

## 8. 三个可落地方案

### 方案A：强化现有方案，不建执行计划表

- 补完整课程快照；
- 建validator；
- 增加版本差异；
- 教学任务仍直接从方案生成。

优点：4—6周可完成，改动相对小。  
缺点：无法准确表达本学期临时调整和计划—实际偏差。

### 方案B：方案 + 独立执行计划（推荐）

- 培养方案负责长期规则；
- 执行计划负责学期实际安排；
- 调整单负责微调；
- 教学任务只能从已发布执行计划生成。

优点：业务层次清晰，能够接近成熟教务系统。  
缺点：需要迁移和旧生成入口收口。

### 方案C：标准驱动的培养质量平台

在方案B稳定后增加：

- 国家专业教学标准；
- 人才培养目标；
- 毕业要求指标点；
- 课程支撑矩阵；
- 达成度分析。

这可形成投标差异，但不得抢在执行计划主链之前。

## 13. 验收标准

- 方案提交前自动发现90%以上结构性缺陷；
- 任一已发布方案可以还原当时课程和规则；
- 任一教学任务可追溯到执行计划、方案版本和课程版本；
- 教务人员能看到“计划应开、实际已开、漏开、提前、延后、变更”；
- 方案变更能列出受影响学生、执行计划和任务；
- 教学计划不再只是其他页面的别名；
- 复杂编制不依赖多层抽屉；
- 普通模型可按P0-1、P0-2、P0-3、P0-4逐轮施工。

## 15. 自我纠错检查

- 是否只新增一个“教学计划”菜单就宣称完成？
- 是否仍然只验证总学分？
- 是否新版本自动覆盖历史学生？
- 是否课程库变动污染历史方案？
- 是否执行计划仍只是教学任务批次换名？
- 是否迁移没有差异报告？
- 是否过早做国家标准和达成度，而主链尚未打通？
