## 二、现有页面问题

`AaSelectionConsoleView.vue`采用左批次、右详情，并把建批次、加课程、建轮次、名单都放抽屉。数据少时可用，真实学校批次、课程和名单变大后会出现：

- 右侧区域拥挤；
- 无法复制链接到某批次某课程；
- 名单抽屉不适合数百学生；
- 规则和适用范围过于简化；
- 首屏没有选课健康度和异常队列。

## 四、批次设置页面

必须配置并解释：

- 批次名称、学期；
- 适用年级/专业/班级；
- 总学分上下限；
- 是否允许重修；
- 是否允许时间冲突；
- 先修规则；
- 退课截止；
- 轮次策略；
- 低人数取消策略；
- 消息通知。

页面保存时写现有`rule_json`，同时补：

```json
{
  "schemaVersion": 2,
  "publishedHash": "...",
  "maxCredits": 24,
  "allowRetake": true,
  "conflictPolicy": "BLOCK"
}
```

批次进入OPEN后禁止直接修改核心规则；变更需新版本/审计。

## 七、候补的边界

- LOTTERY：关轮后统一摇号；
- WAITLIST：课程已经按先到先得满额，后续有人退课时按队列递补；
- 两者可同时存在，但同一轮同一课程只能明确采用一种结果策略；
- 未中签学生不会自动成为候补，除非批次规则明确。

候补表属于`LATER`，先完成规则解释和正式名单。

## 八、锁定名单

当前`lock_batch()`只锁选课记录。第03册教学班成员上线后，事务内：

```text
锁批次
→ 校验选课记录
→ 生成/更新教学班成员新版本
→ 对账人数
→ 锁选课记录
→ 通知
→ 审计
```

失败整体回滚。

## 九、文件级实施顺序

1. 重构总览与新增批次详情路由；
2. 名单从Drawer迁独立页；
3. 规则JSON增加schema校验/版本hash；
4. 所有失败返回规则解释；
5. 学生端显示资格/冲突；
6. 教学班成员完成后接锁定名单；
7. 压测后再评估Redis/候补。

## AI施工共同约束

1. 开工前必须同时读取：本专题文档、`academic-affairs.routes.js`、对应Vue页面、对应API文件、后端model/service/router/test。
2. 先输出“事实核对表”，明确哪些能力已经存在；**不得因为文档写了“新增”就重复建表、重复建service或重复建页面。**
3. 一轮只改一个页面主任务或一条业务闭环，不允许一次重写整个教务中心。
4. 旧路由保留redirect/alias；旧接口保持兼容；旧数据采用新增列/表、回填、双读、双写、切换的安全顺序。
5. 复杂业务使用独立页面。抽屉只允许：少量字段的新建、快速确认、简单原因填写；名单、编排、规则、审核详情、影响分析不得放抽屉。
6. 页面首屏必须回答：当前阶段、是否正常、阻断数量、责任人、截止时间、下一动作。
7. 后端必须覆盖：租户隔离、数据范围、权限、状态机、幂等、并发、审计、通知、归档写保护。
8. 测试只跑本轮相关文件及必要构建，不无理由跑全仓数据库测试。
9. 禁止 `git add -A`；禁止自动commit/push；完成后只提交修改清单、测试证据和剩余风险。
