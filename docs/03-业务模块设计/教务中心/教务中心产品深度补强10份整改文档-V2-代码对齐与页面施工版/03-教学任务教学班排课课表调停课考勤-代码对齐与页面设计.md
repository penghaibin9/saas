## 一、冲突复审

原文档指出“教学班不是独立事实”是正确根因，但直接新建三表并替换现有链路风险很高。

当前事实：

- `AaTeachingTask`同时承担课程、行政班、教学班名称、教师、人数、周次和合班状态；
- 合班/拆班依赖`merged_into_id`与`merge_snapshot_json`；
- 课表项通过`task_id`关联；
- 选课课程可关联`teaching_task_id`；
- 考务、成绩也从教学任务起步；
- `AaTeachingClassScheduleView`和组织控制台已有“教学班”读视图。

因此独立教学班必须是`MIGRATE`，不得一步替换。

## 二、现有页面问题

### 教学任务列表

`AaTaskBatchListView.vue`只有批次名、状态和“生成”面板，无法判断：

- 应生成多少；
- 实际多少；
- 未分教师多少；
- 教师退回多少；
- 是否可提交。

### 教学任务明细

`AaTaskDetailView.vue`以表格+分配确认框为主，且管理端可以直接点击“教师确认”，容易混淆代办与教师本人确认。

### 排课规则

`AaSchedulingConsoleView.vue`直接显示`ruleKey`和JSON值，并允许用户填写技术键，普通教务人员无法使用。

### 选课/考务/课表

多个控制台都依赖任务中的班级字段，因此教学班迁移必须全链路设计。

## 五、独立教学班迁移路线

### 阶段1：兼容投影

新建只读服务：

```python
build_teaching_class_projection(task)
```

以现有任务和合班快照生成统一DTO：

- teachingClassKey
- sourceTaskIds
- adminClassIds
- teacherRelations
- expectedMembers
- rosterVersion=0

不建表，不改写路径。

### 阶段2：新增表并回填

创建：

- `t_aa_teaching_class`
- `t_aa_teaching_class_member`
- `t_aa_teaching_class_teacher`

但保留`AaTeachingTask.teaching_class_code/name`作为兼容快照。

### 阶段3：双写

- 任务生成/合班拆班同时维护新表；
- 对账教学班数量、班级、教师、人数；
- 课表仍读旧task_id，新表只读验证。

### 阶段4：消费者切换

顺序：

```text
选课名单 → 考勤 → 考务 → 成绩 → 课表查询
```

最后才允许新表成为正式成员事实源。

## 六、页面03：排课规则中心

### 禁止当前做法

不得让用户填写：

- `maxDailySlots`
- `avoidEvening`
- 任意JSON

### 目标页面

```text
规则方案：2026秋默认排课规则 v3 [复制] [发布]
硬约束：教师冲突✓ 班级冲突✓ 教室冲突✓ 容量✓ 类型✓

[教师每日最大课时] 6节  适用：全校  [编辑]
[课程连续节次] 2节  适用：理论课 [编辑]
```

表单使用中文业务字段，service再转换为内部规则键。

## 七、页面04：自动排课运行页

建议新增独立路由：

```text
/scheduling/run/:batchId
AaScheduleRunView.vue
```

布局：

```text
左：待排任务与过滤
中：运行结果、成功率、软约束得分
右：漏排原因与一键处置建议
底：试排 / 保存方案 / 应用到课表
```

`AaSchedulingConsoleView.vue`保留规则总览和最近运行，不承载完整自动排课操作。

## 八、页面05：人工排课工作台

复用`/schedule/:batchId/edit`与`AaScheduleMaintainView.vue`，目标三栏：

```text
左：未排/漏排任务
中：周课表网格
右：当前任务信息、候选教室、冲突、可用时间
```

拖放或点击排课前调用统一预检；冲突不能只toast，要固定显示：

- 冲突对象；
- 冲突时间；
- 冲突课程；
- 可替代时段/教室；
- 是否允许特批。

## 九、页面06：课表发布

`AaSchedulePublishView.vue`首屏显示发布门禁：

- 需排任务；
- 已排；
- 漏排（含豁免）；
- HARD冲突；
- SOFT冲突；
- 教师异议；
- 通知可达人数。

只有所有BLOCKER为0才可发布。发布后禁止直接改，必须调停课或作废重发。

## 十、页面07：调停课

现有独立申请/审批页方向正确，补强：

1. 原课信息；
2. 新安排；
3. 自动影响学生数；
4. 教师/班级/教室冲突；
5. 是否需补课；
6. 审批路径；
7. 通知送达；
8. 执行确认和学时核销。

申请页提交前固定展示影响预览，不用弹窗一句话带过。

## 十一、课堂考勤

管理端`AaAttendanceStatsView.vue`不应成为点名页，应定位为：

- 今日未提交考勤；
- 迟到/旷课异常；
- 请假未匹配；
- 补录/更正审计；
- 预警转办。

教师点名继续在移动端，名单最终切换到教学班成员。

## AI施工共同约束

1. 开工前必须同时读取：本专题文档、`academic-affairs.routes.js`、对应Vue页面、对应API文件、后端model/service/router/test。
2. 先输出“事实核对表”，明确哪些能力已经存在；**不得因为文档写了“新增”就重复建表、重复建service或重复建页面。**
3. 一轮只改一个页面主任务或一条业务闭环，不允许一次重写整个教务中心。
4. 旧路由保留redirect/alias；旧接口保持兼容；旧数据采用新增列/表、回填、双读、双写、切换的安全顺序。
5. 复杂业务使用独立页面。抽屉只允许：少量字段的新建、快速确认、简单原因填写；名单、编排、规则、审核详情、影响分析不得放抽屉。
6. 页面首屏必须回答：当前阶段、是否正常、阻断数量、责任人、截止时间、下一动作。
7. 后端必须覆盖：租户隔离、数据范围、权限、状态机、幂等、并发、审计、通知、归档写保护。
8. 测试只跑本轮相关文件及必要构建，不无理由跑全仓数据库测试。
9. 禁止 `git add -A`；禁止自动commit/push；完成后只提交修改清单、测试证据和剩余风险。
