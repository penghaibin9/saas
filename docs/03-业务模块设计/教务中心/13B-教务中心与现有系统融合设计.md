# 13B 教务中心与现有系统融合设计

> 依据：`_13-需求输入-V1.1.md`（唯一需求来源）+ `_13-现有系统集成事实速查.md`（代码事实基线，2026-07 核对）。
> 定位：教务中心（13B）是平台内业务模块，不是独立系统。本文回答"13B 的每一块与现有系统怎么接"，每节按统一六问展开：**读什么 / 写什么 / 复用什么 / 扩展什么 / 禁止什么 / 迁移步骤**。
> 本文不写代码、不改路由、不改数据库，仅为设计契约。

---

## 0. 融合总原则

1. **单一学生身份**：全平台学生唯一标识 = `t_student_profile.id`（student_id）。13B 所有新表凡涉学生，一律存 `student_id`（BIGINT，= t_student_profile.id）+ 冗余 `student_no` 便于展示，禁止再建学生主表。
2. **命名分区**：教务中心新表一律 `t_aa_*` 前缀；既有学业过程域表 `t_acad_*` 保持不动。两个前缀的职责划分见第 5 章（核心章）。
3. **API 分区**：教务中心 13B 新建 PC 端点挂在 `/api/v1/academic-affairs/*`（terms/calendar/programs/courses/teaching-tasks/schedule/enrollments/status-changes/exams/graduation-audit 等）；既有 `/api/v1/academic/students|grades|credits|makeups|retakes|warnings|audit-logs` 属学业过程域，13B 不得覆盖、不得改变其响应结构。
4. **审批只走 Workflow**（t_workflow_instance + t_workflow_task），待办/消息只写 t_unified_todo / t_unified_message，审计走 `audit_log.record` + 域级 `t_aa_audit_trail`（append-only，仿 t_acad_audit_trail）。
5. **范围复用**：教务角色范围（教务处=全校 / 学院教务员=本学院 / 专业负责人=本专业 / 任课教师=本人课程学生 / 学生=本人）通过扩展 `t_teacher_student_scope` + `resolve_teacher_scope` 机制实现，`getAcademicScope` 设计为该机制的封装，不另起炉灶。
6. **demo 只读锁、到期租户只读、PC require_staff、学生走 /api/v1/mobile/*、统一响应体与错误码**——全部无条件继承，13B 不出现任何例外路径。

## 1. 与 Student 域（学生中心）融合：学籍即主档状态

### 1.1 现状事实（已核代码）

- `t_student_profile`：`student_no / real_name / gender / id_card_encrypted / id_card_hash / college_id / major_id / class_id / grade / current_stage(默认 ENROLLED，生命周期阶段) / student_status(默认 NORMAL，§5.2：NORMAL/MERGED/RECYCLED 等) / enroll_date / status`。模型注释明示 status 与 student_status 口径待统一（TODO 以 01 中心为准）。
- `t_student_stage_event`：阶段事件表，是学生 360 时间线的数据源。
- 组织三表：`t_college(college_name/code/status)`、`t_major(college_id/major_name/code/status)`、`t_class(major_id/class_name/grade/counselor_id/head_teacher_id)`。

### 1.2 学籍 = student_status 的受控扩展（核心决策）

**决策：学籍状态不建新主表、不建平行字段，而是对 `t_student_profile.student_status` 做"枚举受控扩展 + 单一写入口 + 异动流水表"三件套。**

#### （1）状态枚举扩展方案

| 枚举值 | 语义 | 来源 | 备注 |
|---|---|---|---|
| NORMAL | 在籍在读（存量默认值，语义 = 在籍） | 既有 | **保留字面不改**，13B 读取时 NORMAL 视同"在籍" |
| PENDING_REGISTER | 迎新完成、待入学注册 | 13B 新增 | 入学注册流程入口态 |
| REGISTERED | 本学年已注册 | 13B 新增 | 学年注册标记（配合 t_aa_registration） |
| UNREGISTERED | 本学年未注册（逾期） | 13B 新增 | 触发学业预警来源 UNREGISTERED |
| SUSPENDED | 休学 | 13B 新增 | 期间禁选课/考试/实习/毕设 |
| RETAINED | 留级 | 13B 新增 | 换年级换班级换方案版本 |
| WITHDRAWN | 退学 | 13B 新增 | 终态（可归档） |
| TRANSFER_SCHOOL | 转学（转出） | 13B 新增 | 终态 |
| GRADUATED / COMPLETED / INCOMPLETE | 毕业/结业/肄业 | 13B 新增 | 由毕业资格审核批次写入 |
| MERGED / RECYCLED | 主档治理态 | 既有 | 13B 只读不碰，异动服务遇到即拒绝（422） |

说明：需求书中的 RESUMED（复学）、TRANSFER_MAJOR（转专业）**不作为驻留状态**——复学后回 NORMAL、转专业不改 student_status（只改 major_id/class_id），二者仅作为异动类型（change_type）存在，避免状态爆炸。

#### （2）单一写入口

新增教务中心服务函数 `change_student_status(student_id, change_type, from/to, reason, operator, workflow_instance_id)` 作为**全平台唯一**允许修改 student_status/college_id/major_id/class_id（学籍语义字段）的入口。该函数必做五件事：合法迁移校验（状态机白名单）→ 更新 t_student_profile（乐观锁 version）→ 写异动流水 → 写 StudentStageEvent → 写审计。

#### （3）异动流水新表 `t_aa_status_change`

| 字段 | 说明 |
|---|---|
| student_id / student_no | 主档关联 |
| change_type | ENROLL_REGISTER / ANNUAL_REGISTER / TRANSFER_MAJOR / SUSPEND / RESUME / WITHDRAW / RETAIN / TRANSFER_SCHOOL / GRADUATE / COMPLETE |
| from_status / to_status | 状态快照 |
| from_college_id / from_major_id / from_class_id / to_* | 组织快照（转专业必填 to_*） |
| reason / reason_masked | 异动原因（敏感，见第 3 章） |
| attachment_file_ids | 材料（复用文件域） |
| workflow_instance_id | 关联审批实例 |
| effective_date / term_code | 生效日期与学期 |
| status | DRAFT/SUBMITTED/IN_REVIEW/APPROVED/REJECTED/RETURNED/CANCELLED/EFFECTIVE/ARCHIVED |
| 公共字段 | tenant_id/version/is_deleted/created_by… 全套继承 |

### 1.3 StageEvent 联动

每次异动 EFFECTIVE 时写一条 `t_student_stage_event`（event_type=ACADEMIC_STATUS_CHANGE，payload 含 change_type/from/to/term），使学生 360 时间线自动出现"2026-09-01 休学生效"等节点——**不需要改 360 聚合端点**，因为该聚合已读 StageEvent。

### 1.4 班级/专业：复用 t_college / t_major / t_class 并补齐字段

**复用**：13B 的"学院/专业/班级管理"页面直接管理这三张表，不建 t_aa_college 等平行表。

**补齐字段建议（全部 nullable + 默认值，不破坏存量行）**：

| 表 | 建议新增字段 | 用途 |
|---|---|---|
| t_major | education_years(学制,默认3) / training_level(培养层次) / enroll_status(是否招生) | 培养方案与毕业年限计算 |
| t_class | class_code(班级编号) / capacity(编制人数) / graduate_year(应毕业年份) / class_status(NORMAL/GRADUATED/DISBANDED) | 教学任务班级容量校验、毕业批次圈定 |
| t_college | short_name / sort_order | 展示与排序 |

### 1.5 关键时序（文字时序图）

**时序 A：入学注册（迎新 → 在籍）**

```
迎新完成(orientation: REPORTED/PAID/材料齐)
  → 13B 注册批次圈定: student_status=PENDING_REGISTER 学生列表
  → 学院教务员预检(读 t_orientation_student 三状态, 只读跨域)
  → 确认注册 → 教务处批次复核
  → change_student_status(ENROLL_REGISTER, PENDING_REGISTER→REGISTERED)
      ├─ 更新 t_student_profile(乐观锁)
      ├─ 写 t_aa_registration + t_aa_status_change(类型=ENROLL_REGISTER)
      ├─ 写 t_student_stage_event("入学注册完成")→360 时间线
      ├─ 写 t_unified_message(学生 STATUS_CHANGED)
      └─ audit_log.record + t_aa_audit_trail
  → 学工/教务/实习/毕设/就业各域读主档即见在籍(无需推送)
```

**时序 B：休学（异动审批 → 生效 → 冻结）**

```
学生小程序发起(POST /mobile/academic/status-changes, 幂等键防重复 409)
  → 校验(本人 token/在籍/无在途单/材料) → t_aa_status_change(SUBMITTED)
  → t_workflow_instance(ACAD_STATUS_SUSPEND) + task(COUNSELOR_REVIEW)
      → 辅导员待办(t_unified_todo) → 审批 → task(COLLEGE_REVIEW) → task(ACADEMIC_FINAL)
  → 终审通过 → on_approved 回调:
      change_student_status(SUSPEND, NORMAL→SUSPENDED)
      + StageEvent("休学生效") + 学生消息(WORKFLOW_RESULT)
      + DEADLINE_REMINDER(复学到期提醒登记)
  → 各域"在籍判定"工具函数返回 false → 选课/考试/实习/毕设入口冻结(422)
```

### 1.6 六问小结

- **读什么**：t_student_profile 全量学籍语义字段、t_student_contact（出口必脱敏）、t_student_stage_event、组织三表。
- **写什么**：student_status（仅经单一入口）、major_id/class_id（转专业/复学定班）、t_aa_status_change、t_aa_registration（注册记录）、StageEvent。
- **复用什么**：主档唯一 id、乐观锁 version、组织三表、_mask_id_card 脱敏、导入管线（学籍导入注册为新 domain）。
- **扩展什么**：student_status 枚举白名单、组织三表 nullable 字段、异动流水表。
- **禁止什么**：①再建学生主表或"教务学生表"存身份字段；②任何模块绕过单一入口 UPDATE student_status；③改 NORMAL/MERGED/RECYCLED 既有字面与语义；④改 current_stage 的既有枚举（ORIENTATION/ON_CAMPUS/INTERNSHIP/GRADUATION_DESIGN/EMPLOYMENT 归学生中心管，13B 不写它）。
- **迁移步骤**：①字典登记新枚举（平台规则中心可见）→ ②建 t_aa_status_change / t_aa_registration → ③实现 change_student_status 并加单元测试 → ④存量数据零迁移（NORMAL 语义即在籍）→ ⑤学籍导入 domain 注册 → ⑥13A 学工侧（毕业资格读处分等）改为读该状态机文档口径。

## 2. 与 Workflow 域融合：审批流编码设计

### 2.1 现状事实

`t_workflow_instance(workflow_code)` + `t_workflow_task(node_code, status=PENDING/APPROVED/REJECTED/TRANSFERRED, version 乐观锁)`；已处理再审 → 409 APPROVAL_VERSION_CONFLICT；PC `/api/v1/approvals/tasks|{id}/approve|reject|transfer`；教师移动包装 `/api/v1/mobile/teacher/approvals/*`（范围校验+审计+409）。**13B 新审批 = 新 workflow_code + node_code 序列，节点流转逻辑写在教务 service，任务/实例落既有两张表，待办进 t_unified_todo。**

### 2.2 workflow_code / node_code 设计表（冻结于 13B-P1）

| workflow_code | 业务 | node_code 序列（顺序节点） | 发起人 | 终审后效果 |
|---|---|---|---|---|
| ACAD_STATUS_TRANSFER_MAJOR | 转专业 | COUNSELOR_REVIEW → COLLEGE_OUT_REVIEW → COLLEGE_IN_REVIEW → ACADEMIC_FINAL | 学生(小程序) | change_student_status(TRANSFER_MAJOR)，更新专业班级+方案绑定 |
| ACAD_STATUS_SUSPEND | 休学 | COUNSELOR_REVIEW → COLLEGE_REVIEW → ACADEMIC_FINAL | 学生 | student_status→SUSPENDED，冻结选课/考试/实习/毕设入口 |
| ACAD_STATUS_RESUME | 复学 | COUNSELOR_REVIEW → COLLEGE_ASSIGN_CLASS → ACADEMIC_FINAL | 学生 | student_status→NORMAL，重绑班级/方案版本 |
| ACAD_STATUS_WITHDRAW | 退学 | COUNSELOR_REVIEW → COLLEGE_REVIEW → ACADEMIC_FINAL | 学生/学院代发起 | student_status→WITHDRAWN，360 归档 |
| ACAD_STATUS_RETAIN | 留级 | COLLEGE_REVIEW → ACADEMIC_FINAL | 学院教务员 | 换 grade/class_id/方案版本 |
| ACAD_PROGRAM_PUBLISH | 培养方案审批 | COLLEGE_REVIEW → ACADEMIC_REVIEW | 专业负责人 | 方案 DRAFT→PUBLISHED，可绑定年级 |
| ACAD_COURSE_APPROVE | 课程库审核 | COLLEGE_REVIEW → ACADEMIC_REVIEW | 课程负责人 | 课程 DRAFT→ENABLED，方案可引用 |
| ACAD_TASK_CONFIRM | 教学任务提交审核 | ACADEMIC_REVIEW（单节点） | 学院教务员 | 任务批次→可排课 |
| ACAD_SCHEDULE_CHANGE | 调停补课 | COLLEGE_REVIEW → ACADEMIC_REVIEW | 任课教师 | 更新课表项+通知师生（P2 实施，P1 冻结编码） |
| ACAD_GRADE_CHANGE | 成绩更正 | COLLEGE_REVIEW → ACADEMIC_REVIEW | 任课教师 | 更新成绩，保留原值流水，通知学生（P2） |
| ACAD_EXAM_DEFER | 缓考 | COUNSELOR_REVIEW → TEACHER_CONFIRM → COLLEGE_REVIEW → ACADEMIC_FINAL | 学生 | 标记缓考，入缓考安排（P2） |
| ACAD_COURSE_EXEMPT | 免修 | TEACHER_REVIEW → COLLEGE_REVIEW → ACADEMIC_REVIEW | 学生 | 免修记录+学业进度标记（P2） |
| ACAD_RETAKE_APPLY | 重修申请 | ACADEMIC_REVIEW（单节点） | 学生 | 入重修选课（P2） |
| ACAD_GRADUATION_AUDIT | 毕业资格审核 | COLLEGE_REVIEW → ACADEMIC_FINAL | 系统预审触发 | 学生进入毕业/结业/延毕名单，写 student_status |

节点命名规范：`<角色域>_<动作>`，全大写下划线；退回（RETURNED）统一回到发起人节点重新提交生成**新任务**（旧任务留痕），不复活旧任务。

### 2.3 待办与消息映射（与统一消息类型对齐）

| 时点 | t_unified_todo | t_unified_message |
|---|---|---|
| 节点任务生成 | 当前节点审批人：WORKFLOW_TODO（source_module=academic-affairs，due_at 按业务时限） | 无 |
| 审批通过（非终节点） | 下一节点审批人新 todo；上一 todo 置完成 | 可选进度通知（默认关，规则中心可开） |
| 终审通过 | 全部关联 todo 置完成 | 发起人/学生：WORKFLOW_RESULT |
| 驳回 REJECTED | todo 置完成 | 发起人：WORKFLOW_RESULT（含原因） |
| 退回 RETURNED | 原 todo 置完成 | 发起人：RETURNED_NOTICE（含退回节点与原因） |
| 发布类动作（学期/方案/课表/成绩） | 无 | 受众：PUBLISHED_NOTICE（课表→教师+班级学生；成绩→学生本人） |
| 到期提醒（复学/注册窗口/成绩录入截止） | 责任人 DEADLINE_REMINDER 型 todo | 学生端 DEADLINE_REMINDER |
| 预警生成 | 辅导员+学院教务员：RISK_ALERT 型 todo | 学生：RISK_ALERT |

规则：13B 任何代码不得直接 INSERT 消息表以外的自建通道；接收人一律精确 receiver_id（不做广播表扫描）；消息文案模板集中登记，禁止散落硬编码。

### 2.4 六问小结

- **读什么**：/approvals/tasks 待审列表（教务角色按 scope 过滤）、实例状态。
- **写什么**：t_workflow_instance/t_workflow_task（经 workflow service）、t_unified_todo（WORKFLOW_TODO）、t_unified_message（WORKFLOW_RESULT/RETURNED_NOTICE）。
- **复用什么**：409 版本冲突语义、transfer 转办、教师移动审批包装、审计。
- **扩展什么**：上表 14 个 workflow_code；审批通过后的业务回调（各 service 内的 on_approved 钩子）。
- **禁止什么**：①自建审批表/审批状态字段绕开 workflow；②各模块自发消息（只走统一消息类型枚举）；③一个业务两套审批入口。
- **迁移步骤**：P1 冻结上表编码 → 各阶段按需实现节点流转 → 已有 /approvals API 零改动即可展示 13B 任务。

## 3. 与 Security 域融合：脱敏、审计、水印

### 3.1 敏感字段清单与脱敏策略

| 数据 | 存储 | 出口策略 | 查看完整值 |
|---|---|---|---|
| 身份证（学籍页/注册核验） | 复用 t_student_profile.id_card_encrypted，13B 不复制存储 | `_mask_id_card`（既有函数） | 填写原因≥5字 + audit_log.record(action=VIEW_SENSITIVE) |
| 成绩（单科/绩点/排名） | t_acad_grade / t_aa_grade_record 明文数值 | **按角色可见**：本人/任课教师(本课程)/教务员(本院)/教务处；辅导员见 pass_status 与绩点级别，默认不见分数明细（可配置） | 越权 403002 + 审计 |
| 异动原因（休学/退学常含病情、家庭隐私） | t_aa_status_change.reason | 列表页默认显示 reason_masked（截断+星号）；详情页按权限展示全文 | 展示全文即审计 |
| 联系方式 | 读 t_student_contact | 既有 `_mask_phone`，13B 不新建通道 | 同现有 360 规则 |

### 3.2 导出与水印

- 全部导出走既有 `/api/v1/export/domain/{domain}`：用途必填≥5字、脱敏列、首行水印、t_export_task 留痕（行数/sha256）、5 次/分限流、5000 行上限、下载审计。
- 13B 注册新导出 domain：`academic-roster`（学籍名册，身份证列强制脱敏）、`academic-schedule`（课表）、`academic-grades`（成绩单，**水印含导出人+traceId+时间**，敏感二次确认）、`academic-graduation`（毕业名单）。
- **成绩导出水印**为强制项：首行水印 + 每页页脚（PDF 成绩单场景 P2），t_export_task.purpose 必填，导出行为写审计并可在平台端追溯。

### 3.3 审计双轨

- 平台审计：`audit_log.record(action, resource, detail, result)` → t_security_audit_log（含 ip/ua/traceId）——所有写操作、敏感查看、导出。
- 域级留痕：新增 `t_aa_audit_trail`（append-only，仿 t_acad_audit_trail 结构），记录状态机每次迁移的 before/after 快照，供教务归档取证。

### 3.4 六问小结

- **读**：现有脱敏函数、审计服务、导出管线。**写**：t_security_audit_log（经服务）、t_aa_audit_trail、t_export_task（经管线）。**复用**：加密存储约定 `*_encrypted`、导出限流与水印。**扩展**：4 个导出 domain、成绩可见性角色矩阵（平台规则中心可配）。**禁止**：①13B 任何表复制存身份证/手机号明文或密文（一律引用主档）；②绕过 export 管线自拼 CSV；③业务错误抛 500。**迁移**：P1 注册 domain 配置与角色矩阵 → 各阶段接入。

## 4. 与 Dashboard / stats 融合：13B 指标接入清单

接入方式（既有模式）：扩展 `stats_service` 聚合函数 + `/api/v1/stats/*` 与教务首页 dashboard 按角色 preset；范围过滤统一走 getAcademicScope；全部实时 count（当前规模无需预聚合，P3 再评估物化）。

## 5. 与六大模块融合【核心章】：academic 学业过程域 = 13B 的过程数据层

### 5.1 职责划分总决策：t_acad_*（结果/台账层） vs t_aa_*（教务运行层）

已核事实：t_acad_student（GPA/学分/预警等级台账）、t_acad_grade（course_name/term/nature/credit_value/score/pass_status/exam_type）、t_acad_makeup、t_acad_retake、t_acad_warning（PENDING_HANDLE/PROCESSING/ESCALATED/CLOSED + close/escalate/assign/remind API + 移动处理端点）、t_acad_intervention、t_acad_audit_trail；PC 端点 /api/v1/academic/students|grades|credits|makeups|retakes|warnings 已上线且被小程序 `/mobile/academic/my` 与教师端消费；**203 条 pytest 覆盖其中**。

**决策 D1（成绩归属）：t_acad_grade 保留为"成绩结果权威读取层"，教务中心新增"成绩过程层"，发布即回写。**

- V1（成绩查看阶段）：教务中心**不建成绩新表**。成绩查看页（PC 教务视角 + 小程序学生视角）直接读 t_acad_grade；13B 只补一个按学期/课程聚合的查询服务。既有录入通道（/academic/grades 的新增/修改）保持给学业过程域管理员使用。
- P2（成绩录入审核发布上线时）：新增过程表 `t_aa_grade_task`（课程×教学班的录入任务，状态机 NOT_STARTED/INPUTTING/SUBMITTED/COLLEGE_REVIEW/ACADEMIC_REVIEW/PUBLISHED/RETURNED/ARCHIVED）+ `t_aa_grade_record`（平时/期末/总评构成明细，保留每次修改流水）。**发布动作（PUBLISHED）原子地把总评同步写入 t_acad_grade**（course_name/term/score/pass_status/credit_value），并更新 t_acad_student 的 GPA/obtained_credits/failed_count 台账。
- 由此：`/mobile/academic/my`、/academic/grades、毕业审核、学业预警扫描**全部继续只读 t_acad_grade，零改动**；过程数据（构成、更正流水、审核轨迹）在 t_aa_grade_*。t_acad_grade 从"手工台账"升级为"发布结果视图"，其直接写入口在 P2 后收敛为：①发布同步 ②成绩更正审批通过回写 ③学业过程域管理员补录（保留，标 source=MANUAL）。

**数据流向图（P2 后目标态）**：

```
教师录入(构成分) → t_aa_grade_record(过程,留痕)
      ↓ 提交                          ↑ 退回
t_aa_grade_task 状态机 → 学院审 → 教务发布(PUBLISHED)
      ↓ 原子同步(总评+pass_status)
t_acad_grade(结果权威层) ──→ /mobile/academic/my 学生查成绩(不变)
      ↓ 触发                    ──→ /api/v1/academic/grades(不变)
预警规则扫描 → t_acad_warning ──→ 辅导员工作台/13A 风险
      ↓
t_acad_student 台账刷新(GPA/学分/挂科数) → 毕业资格预审读取
```

**决策 D2（迁移）**：不迁移 t_acad_grade 存量数据；P2 上线时存量行统一标记 `source=LEGACY`（新增 nullable 列），新发布行 `source=PUBLISH`，更正行 `source=CHANGE`。禁止把 t_acad_grade 改名/拆表。

### 5.2 学业预警：复用 t_acad_warning，扩展来源与规则

>

## 8. PC 路由与菜单：/admin/academic 与 /admin/academic-affairs

### 8.1 现状与新增

- 现有 `/admin/academic`：学业过程模块（学业台账/成绩/学分/补考/重修/预警/审计），目录 `frontend/src/modules/academic/`。
- 新增 `/admin/academic-affairs`：教务中心（首页/学年学期/校历/学籍/异动/专业方案/课程库/教学任务/课表/成绩查看/预警管理/毕业审核/归档），独立目录 `frontend/src/modules/academic-affairs/`，路由互不重叠。

### 8.2 菜单关系（V1）与最终合并路线

**V1**：左侧一级菜单"教务教学"下并列两个二级组——"教务中心（新）"与"学业过程（原）"。两处互跳：教务中心·成绩查看页提供"进入学业台账"链接；学业过程·预警页头部提示"预警规则配置已迁至教务中心"。菜单可见性按权限点（`academicAffairs.*` 新增，`academic.*` 既有不动）。

**合并路线（三步，均为后续里程碑非本轮）**：
1. **P2 末**：学业过程的"预警列表/处置"在教务中心内以同组件复挂（同一组件两路由），数据同源，用户可从任一入口操作。
2. **P3**：/admin/academic 全部页面作为"学业过程台账"子菜单并入 /admin/academic-affairs，原路由保留 **redirect**（书签/收藏不失效），frontend/src/modules/academic 目录保留只做 re-export。
3. **终态**：单一"教务中心"菜单；/admin/academic 路由 redirect 长期保留一个大版本后再评估下线；API 层 /api/v1/academic 既有端点**永不因菜单合并而改**。

**禁止**：本轮改现有 /admin/academic 任何路由/组件；两个入口出现同名不同数的指标（口径必须同源）。**迁移步骤**：V1 双入口 → 观察使用 → P2 复挂 → P3 redirect 合并 → 验收核对无 404、无权限漏配。
