## 0. 交付给学校的使用方式

学校开通后，系统已经准备好本校已购模块对应的角色、菜单、按钮权限和默认范围规则。学校管理员导入师生、指定岗位和负责对象，就可以开始办理；学校可以直接调整本校角色或复制角色，不需要平台逐人授权。

例：学校管理员把张老师设为任课教师 → 教务分配教学任务 → 张老师在 PC 和移动端看到自己的课表和教学班 → 录入并提交成绩 → 具有相应职责的人员审核发布 → 学生在本人 PC 和移动端看到已发布成绩。模板不能提前猜出张老师负责哪个班，也不能让“任课教师”默认看全校学生。

用户确认后已开始施工：首批完成权限目录故障恢复、八组导航、局部失败恢复和初始化保留已有配置；未执行角色类型迁移或数据库权限补写。各阶段完成条件见第 11、12 节，实际结果见现有[施工报告](../../06-开发施工与质量验收/施工记录/系统管理中心商业化治理重构-施工报告.md)的2026-09-13首批实施节。

接续进度：已完成“从模板创建本校角色 → 独立调整权限 → 保存刷新回读”。沙箱缺失Permission基础定义已通过现有维护工具补齐，未改变师生现有授权；具体数据变更和测试证据记录在施工报告的“继续施工”节。旧预设角色原地转为可编辑角色、新校全套自动实例化与P4整体仍未验收。

## 3. 关键业务规则

### 3.1 唯一建号入口

只有「导入老师和学生」可批量创建账号，且仅接收 XLSX。教务、学工、毕业设计、岗位实习中的名单导入只允许关联已有账号，禁止隐式建号。

### 3.2 统一权限目录

每一个三级能力必须登记：菜单码、页面权限码、操作权限码、适用数据范围、敏感等级、后端接口。前端导航、角色授权树、路由元数据及后端鉴权均消费此目录，不再各自维护。

### 3.3 六要素权限判定

后端对每次请求至少判断：租户与模块授权、当前激活角色、菜单权限、操作权限、数据范围、真实业务关系；敏感字段还需要单独授权。前端隐藏菜单不是安全边界。

### 3.4 数据范围与业务关系

数据范围决定组织上限，例如本院、本班、授课班、指导学生；业务关系决定具体对象，例如辅导员带班、教学任务、毕设导师分配、实习指导分配、企业协议和审批节点。两者不能互相替代。

### 3.5 流程与角色不重复维护

流程只引用统一角色和权限目录。审批任务归工作台；流程配置只负责模板、节点规则和异常处理。不得在工作流中再建立一套角色或权限点。

### 3.6 审计不可篡改

账号、角色、权限、数据范围、流程、接口、导入导出和敏感查看均要记录操作人、时间、对象、原因、变更前后值和结果。学校管理员及平台人员均不可删除学校审计日志。

## 4. 角色模板初始化

### 4.1 三种东西必须分清

| 对象 | 归属与作用 | 修改规则 |
|---|---|---|
| 产品权限目录 | 产品定义哪些模块、页面、动作存在，权限码是什么意思 | 平台发布版本，学校只能分配，不能任意造权限码或写菜单地址 |
| 标准角色模板 | 我们预先配置的岗位功能包，包含权限、默认范围类型、敏感限制、适用端 | 发布后不可原地修改；升级产生新版本 |
| 本校使用角色 | 学校实际给人员分配的角色 | 学校可编辑、复制、启停和增减成员；保留模板来源和本校版本 |

**交付方案**：普通业务角色初始化为带来源版本的本校可维护角色；学校界面直接提供“编辑权限”。底层复用现有 CUSTOM 角色与来源记录，不另建 JSON 授权体系。现有 SYSTEM 角色如何安全转为本校可维护角色，必须单独做预检与迁移验证，不能只改角色类型字段。学校主管理员和学生本人身份等内置安全边界不允许改成任意角色类型。

### 4.2 默认角色包（不是强制增加这些岗位）

学校只给实际承担职责的人员分配，没人承担的角色可以保留未分配。一个人可以承担多种职责，但按当前身份和业务对象检查权限，不能把范围无条件合并。以下为产品默认建议，实际编码沿当前目录复核，不按中文名称自动发明角色。

| 包 | 初始角色与代码依据 | 默认可办 | 默认范围与限制 |
|---|---|---|---|
| 学校管理 | 学校管理员 SCHOOL_ADMIN；系统管理员 SYS_ADMIN | 学校主管理员负责本校配置和受控授权；系统管理员承担学校明确委派的日常维护 | 本校配置面；不等于自动获取心理原文、成绩发布或代替教师审批的权限 |
| 审计 | SECURITY_AUDITOR | 查询本校操作、登录和敏感访问证据 | 审计只读；导出单独授权，不参与业务审批 |
| 教务 | ACADEMIC_ADMIN、ACADEMIC_TEACHER | 管理员组织教学和相关发布；教师查课表、办理本人教学任务、录入提交成绩 | 管理员按授权组织；教师按本人教学任务；同一成绩的提交与审核职责分离 |
| 学工 | STUDENT_AFFAIRS_ADMIN、STUDENT_AFFAIRS、COUNSELOR | 全校/本院管理、带班事务办理 | 辅导员和班主任按带班关系；特殊敏感事项不随“学工”一键全开 |
| 学工专项 | PSYCHOLOGY_TEACHER、FUNDING_TEACHER、DORM_MANAGER、YOUTH_LEAGUE | 分别办理心理、资助、宿舍、团学事项 | 按个案、项目、楼栋、活动范围；保留已有专业职责，不合成全能老师 |
| 毕业设计 | GRADUATION_ADMIN、GD_COLLEGE_ADMIN、GD_MAJOR_ADMIN、GD_MENTOR、GD_REVIEWER、GD_DEFENSE_SECRETARY、GD_DEFENSE_EXPERT、GD_GRADE_ADMIN | 批次管理、指导、评阅、答辩组织、评分与发布 | 管理按组织；指导和评分按任务；秘书不因组织答辩自动获得评分权限 |
| 岗位实习与就业 | INTERN_MENTOR、EMPLOYMENT_TEACHER；实习管理角色编码待核 | 实习安排、指导、周报、风险、评价和就业衔接 | 按组织或指导任务；企业评价由企业侧身份办理 |
| 组织与普通教职工 | ORG_PERSONNEL、COLLEGE_ADMIN、STAFF | 人事组织维护、学院职责和普通教职工本人服务 | 按本部门、本院或本人；不能因组织归属自动得到所有业务权限 |
| 学生 | STUDENT | 本人课表、已发布成绩、申请进度、实习和毕设材料 | 永远限定本人；功能随已开模块和业务阶段出现 |
| 领导 | LEADER | 查看授权范围内的汇总与进度 | 只读汇总为默认，不自动开放敏感明细 |

企业导师、企业管理员在企业成员与授权体系内管理，不能通过学校师生角色分配页面授予企业权限。原规范中把企业导师列入学校初始化角色的写法在本轮纠正。

角色模板来源代码已读取 `backend/app/services/saas_role_templates.py:BUILTIN_ROLE_TEMPLATES`，它只能证明代码目录，不证明各学校已安装或每个模板已通过业务验收。当前目录中班主任是 COUNSELOR 的别名、专业课/公共课教师是 ACADEMIC_TEACHER 的别名；用户展示可用岗位称呼，不能因此重复建账号。学校可复制本校角色区分职责。

### 4.3 什么自动配，什么必须由学校提供

| 自动准备 | 学校提供或确认 |
|---|---|
| 模块对应菜单、常用角色权限包、默认范围类型、本人访问规则 | 人员名单、角色成员、所属学院部门、具体负责对象 |
| 基础字典和可编辑标记、编号方案、默认工作台 | 学校名称、校徽、本校可选项与编号适用范围 |
| 可选审批模板和通知模板 | 审批层级、节点责任人、时限和生效日期；不擅自猜学校政策 |
| 初始化检查、导入预检、缺失关系提示 | 导入错误的修正、组织匹配冲突的确认 |

缺少授课或指导关系时显示“尚未分配教学任务/指导学生”，不显示权限系统故障，也不自动扩大到全校。沙箱样例数据单独安装并标识，不作为真实客户初始化数据。

## 5. 学校自己修改权限的办理流程

入口：角色与权限 → 学校角色与成员 → 选角色。同一工作区展示“成员、功能权限、负责范围、变更记录”，不要求用户反复跳转选择同一角色。

1. 编辑本校角色：按教务、学工、实习、毕设、系统管理分组查看业务名称；有“查看、办理、审核、发布、导出”等动作，不向用户展示长串权限码。
2. 可以添加或裁剪有权分配的功能；一键按常用方案填充是草稿操作，不能立即生效。敏感明文、批量导出、授权管理等高风险权限单独确认。
3. 权限依赖要明确。例如选“审核”时提示同时需要“查看”；不能暗中添加更大的权限包。
4. 负责范围展示“本院、指定班级、本人教学任务”等业务选项。普通角色必须有明确范围；学校无权修改学生本人、企业边界等强制限制。
5. 保存前列出新增权限、撤回权限、范围变化、受影响人数以及正在办理任务的影响。用户能确认改的是哪个角色，而不是抽象权限点。
6. 提交携带真实版本；冲突时保留草稿，展示变化并让操作者重新核对，不自动覆盖他人的修改。
7. 后端校验、角色版本和必需审计一致提交。成员再次请求即按新权限校验；旧会话、缓存、下载链接、后台任务按本次撤权合同失效或重验。
8. 成功回执说明已生效的角色、影响范围和结果。通知或缓存刷新失败展示部分完成，重试只处理失败部分，不能重复授权。

**模板管理员与业务操作的区别**：学校主管理员需要的是显式的本校授权管理能力和可授予范围，不是 `*`，也不是“先给自己所有业务和敏感权限，再转授老师”。当前后端是否能区分授予上限与本人操作权限，列为 P0 契约缺口；未经验证不得直接更改鉴权核心。受限管理员只能转授显式允许委派的范围。

**避免管理员锁死**：保留至少一个有效学校主管理员。转移主管理员时先确认接收账号可登录且已完成接管，再撤回原管理员；禁止删除最后一名有效主管理员。自编辑不能绕过上限，也不能删掉自身最后恢复路径。需要恢复时走身份核验、限时、可追踪的恢复流程；不是平台永久代管学校权限。

## 6. 一校一库的数据归属与安装

| 归属 | 权威数据 | 同步与边界 |
|---|---|---|
| 平台控制面 | 学校注册及库路由、商业模块授权、版本化标准模板与产品权限目录 | 向学校发布有版本和完整性校验的配置；不靠人工逐校勾老师权限 |
| 学校业务库 | 本校用户、角色、成员、规范化权限行、负责范围、业务关系、学校配置和审计 | 客户修改只写目标学校库；不同学校允许使用不同的本校角色配置 |
| 学校模板副本（需要本地读取时） | 平台发布版本的受控只读副本 | 来源可验证且版本明确；不能用本地随意编辑副本伪造平台授权 |

一校一库是存储隔离；学校自治是产品权限设计，两者要分别实现。所有接口、worker、缓存、文件、导入导出仍使用可信学校上下文；学校来自登录会话和服务端路由，不接受前端任意指定数据库或学校后切换。

现有 IAM 投影使用 `tenant_id=0` 查询模板，这只说明当前实现方式，不能把每个学校库里的 `0` 当作已正确接入云端平台库。施工前必须与云端的一校一库路由、模板分发和模块授权读取合同对齐。缺失或无法校验时报告配置来源不可用，不开放全权限。

新校安装顺序：确认目标学校与库 → 校验 schema/迁移及模板版本 → 预览拟安装角色和配置 → 幂等应用 → 创建并验证主管理员 → 导入师生组织 → 指定人员与业务关系 → 就绪检查。重复执行不得重复建角色、覆盖本校修改或把已有人员重新绑定到默认角色。

默认角色需要记录来源模板、版本、权限摘要和安装结果；复用现有 Role、UserRole、RolePermission、RoleTemplatePermission、CustomRoleSource。是否增加字段必须先核对云端模型和当前迁移，用 Alembic 完成；不造第二套可授权 JSON。

## 7. 模板升级和新增模块

默认：**学校修改过的角色不自动被模板覆盖，普通业务角色不因升级静默新增权限。**

| 变化 | 行为 |
|---|---|
| 文案、图标、界面修复 | 可随版本更新，不改变有效权限或学校配置 |
| 标准模板升级 | 展示“有新版”和权限差异；学校选择采用，本校角色仍使用已确认版本 |
| 本校已经修改模板内容 | 做原来源版本、本校当前版本、新模板版本三方比较；冲突逐项选择，默认保留本校决定 |
| 新增模块并正式授权 | 模块及对应模板自动出现在学校可分配目录；普通老师不会因此自动获得新增业务权限 |
| 新增模块的主管理员管理能力 | 经模块开通合同和就绪核验提供，不依赖给主管理员添加通配符；审计记录管理上限变化 |
| 权限拆分、合并或废弃 | 先映射全部消费者、预览受影响角色，再发布迁移；不因改权限码把合法流程全部变403 |
| 模块暂停或到期 | 新请求按模块合同拒绝，历史数据保留；进行中任务、文件与已授权历史查看按明确合同处理，不能仅隐藏菜单 |
| 安全漏洞涉及权限撤回 | 可以按受控安全修复流程撤回危险能力，说明影响并留痕；不得顺带覆盖其他学校设置 |
| 回退 | 以历史版本生成新候选、重新检查当前上限后应用；不能恢复已经撤销的危险权限或绕过审计 |

现有 SYSTEM 角色运行时跟随已发布模板、本校 CUSTOM 角色固定来源版本，两种行为必须在过渡期明确区分。未迁移的 SYSTEM 角色不能承诺“已经支持客户任意编辑且升级不覆盖”。

## 8. 26 项施工卡摘要

每项都是能力单元，可共用工作区；默认由学校主管理员或有相应授权的受限管理员办理。操作审计人员仅处理授权的只读查询。老师和学生不默认获得系统管理权限。下表给出用户故事与完成条件，不把页面存在当成功。

| 编号 | 能力/对象 | 主要动作与成功终点 | 特别边界 |
|---|---|---|---|
| 1 | 概览、初始化项目 | 显示真实缺口并直达具体办理对象；完成后回读状态 | 模板409不得把全部系统判健康；不自动执行安装 |
| 2 | 师生账号 | 查询、编辑、启停、受控恢复；刷新后身份与角色正确 | 掩码不回写；离职撤权保留记录；学生和教师使用不同字段合同 |
| 3 | 师生导入 | XLSX预检、错误行、确认、进度和回执；本人任务可回查 | 唯一批量建号入口；失败不伪装全部成功；数据交换原有权限不可扩大 |

| 5 | 登录策略 | 预览影响、保存并验证会话和恢复行为 | 不能停掉核心审计；高风险修改留痕 |

| 15 | 学校信息品牌 | 修改、预览、保存、各端读取一致 | 学校资料与平台租户状态分离 |
| 16 | 模块业务开关 | 显示已购、学校启用、实际就绪三种状态 | 不把开关当商业授权；禁用和故障区分 |

| 19 | 流程模板 | 模板版本、发布、启停和实例引用检查 | 已运行实例保持原版本，不静默批量替换 |

| 26 | 同步与迁移任务 | 进度、错误行、重试/取消、结果回执 | 迁移与导入共享任务能力但不改变账号唯一写入口；不可重复提交已成功部分 |

每项进入代码施工前补齐一张精确合同表：旧/新菜单键、正式路由、查看和动作权限码、API方法路径、服务symbol、模型和迁移、允许身份/范围/业务关系、字段脱敏、状态与expectedVersion、必需审计、拒绝码、正反向用例。现有9处菜单/路由差异需逐一裁定是否为合法的查看与操作分层；不能看到字符串不同就批量替换。

## 9. 菜单与公共壳规则

保持已认可的新壳和五大中心导航。系统管理用8个二级工作区承载26项能力，必要的三级入口仍可直接进入，不把所有功能塞进隐藏标签。不改首页默认地址为新建表单；一级/二级点击进入各自总览或首个合法查看页。

- 标题、必要状态、主要动作收在紧凑标题栏；移除重复身份和数据范围说明条，实际后台范围检查继续执行。
- 统计默认短条或按需展开；主列表和办理表单优先进入首屏。异常提示要贴近对象，不能用全页长篇技术说明代替工作。
- 常用快捷栏不得遮挡底部按钮和分页；页签、收藏、深链保留当前对象、筛选和返回位置。
- 无权、缺前置、服务故障、版本冲突分别表达；接口仍按真实401/403/409返回。已登录的403在当前壳内展示原因，不能让整个系统退出到独立错误页。
- 模板目录失败可以局部降级读取已成功的只读区域，但不能展示可写成功假象或绕过失败的授权来源。
- PC按1366×768、1920×1080检查；窄窗口与键盘另验。此前窄窗口截图和等待8秒后的观测不等同于性能基准或桌面全尺寸验收。

## 10. 当前入口去向与迁移纪律

52个现有菜单项逐项登记在本节附表。26项是导航整理目标，既有任务、表单、日历、国标库、存储治理与历史实施记录都必须保留可达入口。完整去向核对前不删除路由或迁移业务数据。

| P1 默认交付与学校自治 | 验证角色目录与标准模板；初始化本校角色；学校编辑/复制/授权；升级保留和管理员接管 | 新校重复安装不重置；学校修改刷新有效；另一学校不变；模板更新不覆盖；主管理员不会锁死 |
| P2 入口与业务收拢 | 按52项附表映射8组26项；恢复完整字典；合并重复入口但复用原权威服务 | 每项原能力有可达去向；正式读写和历史回读通过；旧壳替代与消费者迁移有证据 |
| P3 办理体验 | 压缩壳、标题、统计和提示；错误局部恢复；保留上下文 | 表单、列表首屏可办，快捷栏不遮挡，角色切换没有旧身份迟到数据 |
| P4 精简回归 | 三类代表身份完成下述故事，自动化检查对应边界 | 正常、拒绝、保存回读、撤权、跨校与升级场景有同基线结果；不拆成六套管理员人工流程 |

顺序在原计划基础上细化：默认角色与学校自改先于导航清理，避免先改菜单后仍无法办事。按一个工作区串行施工，共享权限/路由变更集中复核。每个阶段先补本阶段精确合同和适用三级卡，未完成合同与证据不能标 design_ready。

## 12. 验收故事与四端范围

| 故事 | 代表身份/执行方式 | 必须看到的结果 |
|---|---|---|
| 开校即用 | 学校主管理员 | 模块、角色、字典预配完成；仅需指定人员和真实关系；重复安装不覆盖配置 |
| 学校自行调整 | 学校主管理员→受限管理员→普通教师 | 授权、撤权、范围修改真实生效；可见菜单能进入，允许动作可保存，拒绝有明确原因 |
| 更新不丢配置 | 学校主管理员；自动化准备模板新版 | 本校修改、人员、历史记录保留；差异确认后才扩大普通角色权限 |
| 不同学校隔离 | 自动化学校A/B身份请求 | 相同账号名、角色名、业务ID也不串库；缓存、文件、任务、统计均隔离 |
| 教务联通 | 普通教师与学生本人 | 教师只见本人课表和教学班；成绩经正式审核发布后学生才能看到；权限撤回后旧会话不能继续办理 |
| 学工、实习、毕设联通 | 同一教师账号按带班/指导角色，学生本人配合 | 带班或指导关系对应同一业务对象；切身份和范围不会串学生；正常办理与拒绝均符合实际职责 |
| 管理员接管 | 主管理员及接收账号；限隔离测试 | 有效接管后可撤原管理员；最后一个有效管理员不可直接删除或停用 |
| 冲突与失败 | 既有三类身份的双会话及故障测试 | 409保留草稿，数据库异常不放权；重试不重复写、必需审计一致、部分完成可恢复 |

P4仍只有学校主管理员、受限管理员、普通教师三类主要管理测试身份；学生只是验证其本人端结果，不新增一套管理员类别。自动化要覆盖相关精确权限与拒绝场景，不因身份少而取消后端边界测试。

系统管理编辑界面主要在Staff PC。Student PC、Teacher Mini、Student Mini不复制一套系统管理CRUD，但消费同一模块开关、角色和数据边界。H5联调、微信构建、微信宿主实测分别记录；未测微信不能宣称四端全通过。

性能以同环境冷/热加载分别记录为准，先定位重复上下文请求；不根据一次延迟就认定旧壳根因。数据库写验收使用真实MySQL、独立自动化库，人工沙箱保留记录。
