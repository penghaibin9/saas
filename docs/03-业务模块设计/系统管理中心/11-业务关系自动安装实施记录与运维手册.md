# 业务关系自动安装实施记录与运维手册

> 基线日期：2026-07-18  
> 实施状态：已完成第一版生产链路  
> 迁移版本：`0105_business_relations`

## 1. 目标与边界

学校在统一师生开户模板中填写真实人员和关系引用。系统先预检、再让学校确认，最后把关系写入各业务域既有主表；实施中心只保存候选、决定及回滚账本，不另建一套业务关系事实表。

必须遵守以下边界：

- 不按角色名称猜测具体学生、教学班、毕设批次、实习批次或楼栋。
- 不为完成关系安装而伪造教学任务、毕设学生、实习记录、宿舍楼栋。
- 毕设导师必须已经存在于导师资格库且状态为 `QUALIFIED`。
- 同一对象已经有其他负责人时标记 `CONFLICT`，必须由学校选择“明确覆盖”或“忽略”。
- 回滚前检查安装后的字段是否被人工修改；存在漂移时整批拒绝回滚，避免覆盖学校后续业务操作。

## 2. 已支持的六类关系

| 关系编码 | 主体 | 对象引用 | 写入真实主表 | 配套数据范围 |
|---|---|---|---|---|
| `COUNSELOR_CLASS` | 教师工号 | 班级编码/唯一名称 | `t_class.counselor_id` | `COUNSELOR + CLASS` |
| `HEAD_TEACHER_CLASS` | 教师工号 | 班级编码/唯一名称 | `t_class.head_teacher_id` | `COUNSELOR + CLASS` |
| `TEACHER_TEACHING_TASK` | 教师工号 | 教学班编码 | `t_aa_teaching_task.teacher_*` | 以教学任务为事实源 |
| `GRADUATION_MENTOR_STUDENT` | 导师工号 | 学号 + 可选毕设批次编号 | `t_gd_student`、`t_gd_mentor_assignment` | `GD_MENTOR + ADVISOR` |
| `INTERNSHIP_ADVISOR_STUDENT` | 教师工号 | 学号 + 可选实习批次编号 | `t_internship_record.advisor_*` | `INTERN_MENTOR + ADVISOR` |
| `DORM_MANAGER_BUILDING` | 宿管工号 | 楼栋编码/唯一名称 | `t_affairs_dorm_building.manager_teacher_key` | `DORM_MANAGER + DORM_BUILDING` |

同一学生存在多个毕设或实习记录时，必须填写“业务批次编号”，否则预览阻断。

## 3. 开户模板和引导流程

统一模板新增两个工作表：

- `业务关系`：关系类型、主体工号、对象编号/学号、业务批次编号、备注。
- `业务关系说明`：六类关系的填写规则和目标主表。

实施顺序固定为：

1. 上传模板并预检账号、组织、角色和关系格式。
2. 确认组织树与角色，安装组织和预设角色。
3. 创建师生账号。
4. 生成关系候选；状态为 `READY / ALREADY / CONFLICT / BLOCKED`。
5. 学校确认 `INSTALL / KEEP / REPLACE / IGNORE`。
6. 同一事务写入真实业务主表和安装账本。
7. 如需撤销，执行带漂移检查的整批回滚。

辅导员的 `COUNSELOR + CLASS` 数据范围可自动推导为辅导员—班级候选；显式填写的同一关系会按稳定关系键去重。

## 4. 数据表与接口

实施审计表：

- `t_system_business_relation_batch`：来源导入批次、文件指纹、候选、决定、汇总和状态。
- `t_system_business_relation_install_item`：目标表/行、变更前后字段、配套范围、安装及回滚状态。

主要接口：

- `POST /api/v1/system/implementation/projects/{id}/relations/discover`
- `PUT /api/v1/system/implementation/projects/{id}/relations/decisions`
- `POST /api/v1/system/implementation/projects/{id}/relations/apply`
- `GET /api/v1/system/implementation/projects/{id}/relations/batches`
- `POST /api/v1/system/implementation/projects/{id}/relations/{batchNo}/rollback`

权限分为关系管理、安装和回滚三类；所有查询与写入均带 `tenant_id` 条件。

## 5. 幂等、并发和回滚规则

- 文件指纹、项目和来源导入批次相同，再次发现返回原关系批次。
- `tenant_id + project_id + relation_key` 唯一，网络重试不会重复安装。
- 确认时保存目标状态指纹；应用前重新解析真实对象，发生变化返回 `DATA_CONFLICT`。
- 已安装批次重复应用直接返回 `idempotent=true`。
- 回滚只撤销本批次创建或修改的字段、导师分配历史和配套范围；不是本批次创建的范围不会删除。
- 安装后人工变更过的对象不会被自动回滚覆盖。

本阶段不等于业务数据初始化：教学任务、毕设批次与学生、实习批次与记录、楼栋房源仍由对应业务模块或学校真实数据导入产生。
