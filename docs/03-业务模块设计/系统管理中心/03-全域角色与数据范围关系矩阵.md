# 全域角色、组织与业务关系权限矩阵

## 1. 冻结结论

系统采用 **RBAC + 组织范围 + 业务关系 + 条件约束** 的混合授权模型：

```text
最终允许 = 同一租户
        AND 当前角色拥有功能权限
        AND 当前账号与目标数据存在允许的组织/业务关系
        AND 当前业务状态、学期和授权有效期允许操作
```

五层概念不得混用：

1. **账号（User）**：谁登录。一个自然人在一所学校原则上只有一个有效账号。
2. **角色（Role）**：能做什么。一个老师可有多个角色，登录后切换当前角色。
3. **组织（Org）**：属于哪里。学校、学院、专业、班级、部门是稳定的管理边界。
4. **业务关系（Relation）**：能处理谁或什么。任课、带班、指导、评阅、监考等均为业务关系。
5. **条件（Condition）**：何时、以何种状态可操作。如当前学期、成绩录入窗口、记录未归档、委托未过期。

角色不直接保存学生名单，也不为每位老师、班级、课程创建新角色。否则学校规模增长后会产生角色爆炸和高额实施维护成本。

### 1.1 四大业务系统共用一套底座

本产品不是四套系统简单拼接，而是“一个人、一份学生主档、一套组织、一套授权决策，四个业务域分别维护权威关系”：

| 共用底座 | 学工中心 | 教务中心 | 岗位实习中心 | 毕业设计中心 |
|---|---|---|---|---|
| 同一老师账号 | 辅导员—班级、个案分派 | 教师—教学班/课程/考场 | 导师—实习学生 | 导师/评阅人/答辩组—学生 |
| 同一学生主档 | 学工业务记录 | 学籍、教学与成绩记录 | 实习过程记录 | 毕设过程记录 |
| 同一组织树 | 学院/班级/楼栋范围 | 校/院/专业/教学班范围 | 校/院/专业管理范围 | 校/院/专业/批次范围 |
| 同一权限引擎 | 只读取本域关系 | 只读取本域关系 | 只读取本域关系 | 只读取本域关系 |

老师的多个角色可以共存，但当前角色的数据范围不得无条件并集。跨域领导看板优先返回汇总数据；下钻明细时仍重新执行目标业务域的权限判断。

### 1.2 学生四层状态必须分开

| 状态层 | 回答的问题 | 权威字段/记录 | 例子 | 能否决定教师看谁 |
|---|---|---|---|---|
| 账号状态 | 能否登录 | `User.status` 等账号字段 | 启用、停用、锁定 | 否 |
| 学籍状态 | 是否在籍、休学、退学、毕业 | `StudentProfile.student_status` | NORMAL、REGISTERED、SUSPENDED、GRADUATED | 否，只能作为业务条件 |
| 生命周期主阶段 | 学生当前门户和跨域待办聚焦什么 | `StudentProfile.current_stage` | 新生、在读、岗位实习、毕业、已毕业、校友 | 否 |
| 业务办理状态 | 某一笔业务进行到哪里 | 四个业务域各自记录 | 周报待批、成绩待录、开题待审、答辩已完成 | 否，由本域关系叠加状态控制操作 |

学生生命周期可复用，但只作为跨域编排和展示，不作为授权来源。统一用户文案为：

| 用户阶段 | 冻结存储值 | 处理规则 |
|---|---|---|
| 新生阶段 | `ADMITTED / PRE_STUDENT_VERIFIED / REGISTERED_PENDING_ENROLLMENT` | 细分录取、预报到核验、已报到待注册三个里程碑 |
| 在读阶段 | `ENROLLED` | 正式在读编码；运行时代码旧值 `ON_CAMPUS / STUDYING` 只读兼容到这里 |
| 岗位实习阶段 | `INTERN` | 聚焦实习门户和待办；旧值 `INTERNSHIP` 只读兼容到这里 |
| 毕业阶段 | `GRADUATING` | 毕设、实习和就业可并行；旧值 `GRADUATION_DESIGN / EMPLOYMENT` 只读兼容到这里 |
| 已毕业 / 校友 | `GRADUATED / ALUMNI` | 生命周期终态；是否在籍仍以 `student_status` 为权威 |

`current_stage` 正式枚举以《数据库设计冻结总册》§5.1 为准。四个中文阶段是面向用户的主分组，不覆盖 `GRADUATED / ALUMNI` 终态。`current_stage` 是“当前主要关注阶段”，不是排他的业务开关；现实中岗位实习、毕业设计和就业可能同时发生，所以模块可用性应由租户功能、学生业务记录和办理状态决定，不能仅凭一个阶段值禁止进入。

当前 `t_student_stage_event` 已同时承载生命周期变化、学籍异动和学工业务事件（如资助、谈话、活动），因此它是 360 时间线事件流，不能用“最后一条事件的 `to_stage`”反推 `current_stage`。后续数据库联调时应建立唯一生命周期流转服务，只有明确的生命周期事件才允许更新主档阶段，并保证事件写入与主档更新同事务、可幂等、可审计。

## 2. 为什么采用这一模型

公开可核验的成熟产品要求与大型 SaaS 授权原则高度一致：

- 强智公开操作手册描述按实际业务职责设置角色，并可将权限细化到按钮。
- 正方中标项目公开参数明确要求：一个用户可归属多个角色，功能权限与数据权限交叉管理，支持校院两级授权和限时委托。
- 正方公开项目同时体现了教师、学生基础身份与角色自动绑定，但本系统为降低多业务导入误开户风险，统一收口到系统管理的标准 Excel 入口。
- Microsoft Azure/Entra 的角色分配由“主体 + 角色 + 范围”构成，并建议采用满足需求的最小范围。
- Auth0 将组织作为 B2B SaaS 租户边界，组织成员可拥有一个或多个角色；RBAC 负责通用职责，细粒度授权再叠加属性或关系。
- AWS 建议最小权限，并用属性规则减少随资源增长而维护大量独立角色的成本。
- Google Zanzibar 用主体与对象之间的关系表达细粒度授权。对本系统而言，“老师指导学生”“教师任教教学班”就是此类关系。

## 3. 账号和角色的标准化关系

### 3.1 账号创建

- 老师、学生：只允许在 `系统管理 → 导入老师和学生` 使用标准 `.xlsx` 批量创建。
- 首位学校管理员：由平台开通学校时单独创建。
- 其他业务导入：只能匹配已有账号/主档，匹配失败即提示回到系统管理处理。
- 学生默认绑定 `STUDENT`；教师必须从 SaaS 预设角色中选择。

### 3.2 多角色老师

例如张老师可同时拥有：

```text
User: 张老师（工号 T001）
├─ ACADEMIC_TEACHER  任课教师
├─ COUNSELOR         辅导员
├─ INTERN_MENTOR     实习指导教师
└─ GD_MENTOR         毕设指导教师
```

角色只提供功能集合。进入任课教师角色时按教学任务看学生；进入辅导员角色时按所带班级看学生；进入实习指导教师角色时按实习指导关系看学生。不得简单把四个角色的数据范围做无条件并集。

### 3.3 内置角色和自定义角色

- 内置角色由平台版本化发布，学校不能删除编码、改变系统语义或通过导入隐式新增。
- 学校通常只需给老师勾选角色，不配置零散权限。
- 自定义角色作为高级功能后置，默认关闭；启用时只能从现有权限包复制并受权限上限约束。

## 4. 各业务域权威关系矩阵

| 业务域 | 角色解决的问题 | 数据范围的权威关系 | 管理范围 | 禁止做法 |
|---|---|---|---|---|
| 系统管理 | 用户、角色、组织、审计管理 | `tenant_id`、用户角色关系 | 学校管理员全校；审计员只读 | 普通业务管理员取得平台权限 |
| 教务 | 教学计划、排课、成绩、考务等操作 | 任课教师—教学班、课程负责人—课程、监考教师—考场、评教任务—被评对象 | 教务处全校；学院教务员本学院；教师仅本人任务 | 用“任课教师角色”直接看全校成绩 |
| 学工 | 日常事务、资助、心理、宿舍、团学 | 辅导员—班级、心理老师—个案学生、资助老师—项目/申请、宿管—楼栋 | 学工处全校；学院学工本学院 | 所有学工老师共用学院全量数据 |
| 毕设 | 指导、评阅、答辩和过程管理 | 学生—导师、评阅任务—评阅人、答辩组—专家/秘书 | 校级/学院/专业管理员按组织；教师仅被分配任务 | 按导师姓名匹配；导师看到非本人学生 |
| 岗位实习 | 指导、周报、打卡、风险和评价 | `InternshipRecord.advisor_user_id` | 管理员按组织；指导教师仅本人学生 | 用姓名作为新数据权威键；按班级替代带教名单 |
| 就业 | 就业跟踪、核验和帮扶 | 就业老师—学院/班级/专项学生 | 就业中心全校；学院就业老师本学院 | 因查看就业记录而获得学生账号管理权 |
| 迎新 | 新生报到流程 | 迎新批次—学院—办理点—经办人 | 迎新管理员全校；办理员仅分配办理点/学院 | 迎新名单导入自动开户 |

## 5. 关键领域的具体规则

### 5.1 教务中心

教务权限必须由业务任务自动派生，减少人工配置：

- 任课教师：只看本人承担的教学班及教学班学生；只在成绩录入窗口内录入本人课程成绩。
- 课程负责人：只维护负责课程的课程资料、教学大纲和汇总数据。
- 监考教师：只看本人监考场次和必要考生信息，不继承任课教师成绩权限。
- 教务处管理员：全校业务设置和进度监管。
- 学院教务员：本学院培养方案、教学任务、排课和审核。
- 临时助教/代录：使用带起止时间、事项和操作类型的委托，不永久增加角色。
- 历史学期默认只读；调课、换教师后按新关系立即重算范围，历史审计不覆盖。

### 5.2 学工中心

- 辅导员：以班级的 `counselor_id` 或有效带班关系为权威，可跨专业带多个班。
- 班主任：若学校区分班主任和辅导员，关系独立；不通过再造一个班级角色实现。
- 心理老师：仅查看明确分派或会诊授权的学生，敏感字段进一步按字段权限控制。
- 资助老师：按资助项目和申请处理关系授权；学院经办只看本学院申请。
- 宿管老师：按楼栋/园区授权，不因楼栋学生来自多个学院而扩大到学院全部学生。
- 学工处领导：可查看全校聚合；明细和导出必须另有权限并留审计。
- 学生转班后，辅导员范围随当前班级变化；历史业务记录保留原经办人快照。

### 5.3 毕业设计

- `GD_MENTOR` 只赋予指导功能，学生范围来自学生—导师分配关系。
- 导师库必须绑定唯一教师账号 ID；姓名仅展示，不能作为权限键。
- `GD_REVIEWER` 只看被分配的评阅任务；评阅关系不等于指导关系。
- `GD_DEFENSE_EXPERT`、`GD_DEFENSE_SECRETARY` 只看所属答辩组、场次和学生。
- 指导教师与评阅教师应支持职责分离校验，避免同一人评阅自己的学生。
- 调导师必须保留 previous mentor、原因、操作人和时间；当前范围立即切到新导师。
- 导师容量按批次控制，可设置默认值和个别调整值，超限阻止新增分配或进入待审批。

### 5.4 岗位实习

一名指导教师跨多个班带 50 名学生时，不创建 50 条权限，也不创建 50 个角色：

```text
老师 A 的 User.id = 17
t_internship_record.advisor_user_id = 17  （50 条）

老师 B 的 User.id = 18
t_internship_record.advisor_user_id = 18  （另外 50 条）
```

读取学生、周报、打卡、请假、补卡、风险、评价和归档时，指导教师查询必须包含：

```text
tenant_id = 当前学校 AND advisor_user_id = 当前账号 ID
```

- 导入名单中的指导教师必须匹配到唯一、在职且拥有 `INTERN_MENTOR` 的账号。
- 两位老师同名时按 ID 区分，不得互相看到学生。
- 历史记录没有 `advisor_user_id` 时可短期按唯一姓名兼容，并列入待回填清单。
- 容量建议按“租户默认 50 + 批次覆盖 + 教师个别覆盖”三级配置；容量是分配规则，不是权限角色。
- 改派教师后新教师立即获得范围，旧教师立即失去当前数据访问；改派历史保留。
- 如未来支持双导师，不修改角色，新增学生—导师多对多关系并标注主/协同导师。

## 6. 默认拒绝和越权防护

1. 所有查询先过滤 `tenant_id`，再过滤业务关系；前端隐藏菜单不能代替后端校验。
2. 普通教师没有有效关系时返回空集/403，不允许回落为“看全校”。
3. 管理员全校范围必须来自明确的管理角色，不能因范围配置缺失自动扩大。
4. 姓名、班级名称、课程名称只用于展示和导入匹配提示；新关系必须保存稳定 ID。
5. 写操作同时校验功能权限、数据范围、业务状态和乐观锁版本。
6. 导出、批量变更、分配/改派、角色切换、委托和敏感查看必须留痕。
7. 角色停用、账号停用、关系失效或角色切换后，令牌和权限缓存必须及时失效。

## 7. 低实施成本的自动化

新学校上线时只需：

1. 平台创建学校和首位学校管理员。
2. 系统自动初始化版本化内置角色和权限包。
3. 学校导入组织结构。
4. 在固定入口导入老师、学生账号并选择教师角色。
5. 各业务域导入或维护业务数据时自动形成关系：排课产生任课关系、带班设置产生辅导员关系、毕设分配产生导师关系、实习分配产生指导关系。

学校管理员不需要逐按钮配权限，不需要为每个班或每位教师建角色，也不需要在多个模块重复开户。

## 8. 当前代码收敛和后续联调

本隔离工作区不连接、不修改 MySQL，当前只执行代码和纯测试收敛：

- 已固化师生账号唯一 Excel 入口和全生产代码 `User(...)` 构造白名单。
- 已将岗位实习新数据的指导关系收紧到 `advisor_user_id`，姓名仅作历史兼容。
- 已要求实习指导教师拥有有效 `INTERN_MENTOR` 角色，名单导入回填账号 ID。
- 已在业务导入页面统一提示“此处不会创建登录账号”。

待教务中心开发完成并释放数据库联调窗口后，再统一做：

1. 继续扫描各业务域的旧查询；统一保持普通教师缺关系默认拒绝，禁止重新引入 `TENANT_FALLBACK` 放行。
2. 将教务域仍使用 `teacher_key` 的关系逐步统一为稳定账号 ID 或建立唯一映射层。
3. 为毕设导师库补齐教师账号唯一绑定并全链路改为 ID 授权。
4. 建立统一授权决策函数和跨域越权回归矩阵。
5. 迁移历史姓名关系并生成未匹配/同名冲突清单。
6. 持久化导入预检批次、限时委托和权限变更审计。

## 9. 最终验收场景

- 同名实习教师各带 50 人，互相查询不到对方学生。
- 任课教师只能录入本人教学班成绩，不能查看同学院其他教学班明细。
- 辅导员跨专业带两个班，可见这两个班；学生转班后范围自动变化。
- 心理老师只能查看明确分派个案，普通辅导员看不到心理敏感明细。
- 毕设导师只能看本人学生；评阅人只看被分配论文；导师不能评阅自己学生。
- 学院管理员只能看本学院，校级管理员看全校，平台人员不能默认读取学校业务明细。
- 老师切换不同角色时，菜单、操作和数据范围同步切换。
- 任何业务名单导入都不会创建账号；未找到账号时明确提示去系统管理处理。
