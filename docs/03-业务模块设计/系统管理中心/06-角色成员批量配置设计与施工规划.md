# 角色成员批量配置设计与施工规划

> 编制日期：2026-08-29
> 适用页面：`/admin/system/roles` 角色权限管理
> 本期目标：把“成员人数查看”升级为“按角色、按组织范围批量添加老师”的完整授权闭环。
>
> 2026-08-29 设计修正：原方案只完成了“人—角色”，没有把“学校 → 学院 → 专业 → 班级 → 学生”作为本次角色授权的正式上下文。对于范围型角色，仅授予角色而不指定或建立对应范围不算完成授权，必须默认拒绝业务数据访问并进入“待配置范围”。

## 1. 现状核验

### 1.1 已有能力

- 角色列表已经返回真实成员数，并可通过 `/system/roles/{roleId}/members` 分页查看当前成员。
- `role_assignment_service.grant_assignment` 已具备单人角色授予、有效期、来源、授权原因、主体缓存失效和关键审计。
- 服务端已经校验租户边界、平台角色禁授、操作者不可授予超出自身基础权限的角色。
- 教职工账号页已有“按老师配置多个角色”的入口，角色成员页与账号页共用 `t_user_role` 权威关系，不应再建第二套成员表。
- `TeacherStudentScope`、班级辅导员、宿管楼栋等业务关系承担部分角色的数据范围事实。

### 1.2 当前缺口

- 成员人数抽屉只能查看，不能搜索并添加老师。
- 没有“排除现有成员”的角色候选老师分页接口。
- 单人授权接口不适合批量提交；前端循环调用会产生部分成功、部分失败。
- 角色授权与岗位数据范围是两类事实。辅导员等角色即使授权成功，如果未绑定班级，仍可能看不到业务数据。
- `t_user_role` 只有 `user_id + role_id`，没有表达“该老师以此角色负责全校、哪些学院、哪些专业、哪些班级或哪些学生”；现有 `TeacherStudentScope` 以教师标识、角色编码和名称弱关联，未与某次角色授权及其有效期形成强关系。
- 历史软删除的 `UserRole` 需要复用并恢复，不能重复插入触发唯一键冲突。

## 2. 产品决策

保持两个互补入口，但共用同一权威数据：

- 角色成员页回答“这个角色有哪些老师”，用于按岗位批量配人。
- 教职工账号页回答“这个老师有哪些角色”，用于单人入职、调岗和兼任。

本期不新增独立路由。点击角色成员人数后仍使用现有弹窗，并在弹窗内切换“成员清单”和“添加成员”两个状态。

角色、任职归属和授权范围必须分开：

- 角色模板回答“能做什么”，例如全校只维护一个 `COLLEGE_ADMIN`，不能按学院复制出多套同名角色。
- 教职工组织归属回答“人属于哪里”，可用于默认建议，但不能自动等同于授权。
- 角色授权范围回答“以这个角色能管理哪里”，按 `SCHOOL / COLLEGE / MAJOR / CLASS / STUDENT` 五级表达，必须由管理员明确确认或由权威业务关系生成并审计。

五级范围采用上级包含下级的继承规则：

- `SCHOOL` 覆盖当前学校内全部学院、专业、班级和学生。
- `COLLEGE` 覆盖所选学院及其下全部专业、班级和学生。
- `MAJOR` 覆盖所选专业及其下全部班级和学生。
- `CLASS` 覆盖所选班级及其学生。
- `STUDENT` 只覆盖明确选择或由业务关系指派的学生。

范围判断沿组织主数据的稳定 ID 链实时解析，不批量复制所有下级 ID；学院、专业或班级调整后，权限按最新有效隶属关系生效并留下组织变更审计。一个角色成员可以拥有同一级的多个范围节点，例如同时负责两个学院；同一角色下默认不混配不同层级，确需例外时取最小明确授权集合并去除被上级范围覆盖的冗余节点。

## 3. 交互设计

### 3.1 成员清单状态

- 标题：`角色成员 · {角色名称}`。
- 展示角色编码、数据范围和当前成员总数。
- 有 `systemAdmin.user.assign-role` 权限时展示主按钮“添加成员”；只读用户不展示写入口。
- 成员表继续分页显示姓名、工号和账号状态。

### 3.2 添加成员状态

- 支持按姓名或工号搜索，只返回当前学校、启用中的非学生账号。
- 服务端排除已经持有该角色的老师，避免前端分页过滤造成空页或总数错误。
- 支持多选和跨页保留已选结果，单次最多 100 人。
- 必填授权原因，至少 5 个字。
- 到期日期可选；留空表示长期有效，到期后沿用现有自动回收链路。
- 根据角色的范围策略展示对应选择器：全校确认、学院多选、专业多选、班级多选或学生选择；批量所选老师默认共用本次范围。
- 选择器采用级联树展示“学校 → 学院 → 专业 → 班级”，学生通过班级下钻或独立检索选择，避免一次加载全校学生。
- 候选老师展示其组织归属，仅作为选择参考；允许经授权配置跨组织兼岗范围，不能偷偷把人员归属自动当成授权。
- 提交成功后返回新增数与跳过数，刷新成员清单和角色列表人数。

### 3.3 数据范围提示

角色范围为 `SCHOOL` 或 `SELF` 时，授权完成即可按既有规则使用；`SCHOOL` 必须展示“全校范围”影响确认，不能把空范围解释成全校。

下列范围需要管理员继续核对岗位关系：

- `COLLEGE`：必须选择一个或多个学院。
- `MAJOR`：必须选择一个或多个专业，且只能来自操作者可管理的学院。
- `COUNSELOR_CLASSES` / `CLASS`：必须选择班级或采用辅导员/班主任权威任职关系生成范围。
- `STUDENT`：必须明确选择学生或由临时授权、心理、资助等权威业务关系生成范围。
- `DEPARTMENT`：属于教职工组织线，不混入学生五级树，使用独立组织单元范围。
- `DORM_BUILDING`：需要配置负责楼栋。
- `GD_STUDENTS` / `INTERN_STUDENTS`：范围来自毕设、实习业务关系。
- `ASSIGNED` / `CUSTOM`：需要在数据范围或任职归属中继续配置。

本期明确“角色授权成功不等于岗位范围已配置”。学校、学院、专业、班级、学生是跨模块通用范围，应纳入统一授权范围模型；楼栋、授课、毕设和实习等非组织树范围仍以各业务模块的权威任职关系为准，不在通用授权弹窗中擅自写入。

### 3.4 成员清单的范围表达

- 增加“授权范围”列，例如“全校”“信息工程学院等 2 个学院”“软件技术等 3 个专业”“软件 2401 等 4 个班”“指定 12 名学生”。
- 增加范围类型和组织节点筛选，人数仍表示去重后的角色成员人数，不能把一人多范围重复计数。
- 范围型角色存在成员但没有有效范围时，显示红色“范围缺失”，不可把其解释为全校权限。
- 角色详情展示“成员总数 / 已完成范围 / 待配置范围”，便于治理历史数据。

## 4. 后端契约

### 4.1 候选老师

`GET /system/roles/{roleId}/member-candidates`

查询参数：`keyword`、`page`、`pageSize`。

规则：

- 当前租户、角色有效、账号有效。
- 排除学生账号、停用账号、已持有该角色的账号。
- 需要 `systemAdmin.user.assign-role` 权限。
- 返回 `items / total / page / pageSize` 标准分页结构。

### 4.2 批量添加

`POST /system/roles/{roleId}/members/batch`

请求字段：

- `userIds`：去重后的账号主键，1～100 人。
- `reason`：授权原因，不少于 5 个字。
- `effectiveAt`：可选，默认立即生效。
- `expiresAt`：可选，必须晚于生效时间。
- `sourceType`：本入口固定为 `MANUAL`。
- `scopeType`：由角色规则确定，为 `SCHOOL / COLLEGE / MAJOR / CLASS / STUDENT` 之一，前端不可自行扩大层级。
- `scopeIds`：`SCHOOL` 固定为空或 `[0]`；其他范围必填稳定主键，组织节点建议单次 1～20 个，学生点名授权建议单次 1～100 人。

事务规则：

- 全批次先完成租户、账号类型、角色状态和授权边界预检，再开始写入。
- 范围 ID 必须属于当前租户、处于有效状态并满足完整父子链；操作者只能授予自身有效范围覆盖的节点。
- 任一非法账号导致整批回滚。
- 并发下已经成为成员的账号按幂等跳过，不重复建关系。
- 复用已撤销或软删除的 `UserRole`，恢复为 `ACTIVE`。
- 角色关系、授权范围、有效期事实和关键审计在同一事务提交，任一步失败整批回滚。
- 提交后立即失效相关主体缓存。

返回：`requestedCount`、`addedCount`、`skippedCount`、`addedUserIds`、`skippedUserIds`。

### 4.3 授权范围事实模型

新增 `t_role_assignment_scope`，一行表示一条角色成员关系被授予的一个范围节点：

- `tenant_id`：学校租户。
- `user_role_id`：强关联 `t_user_role.id`，保证范围属于某次人—角色关系。
- `user_id`、`role_code`：冗余用于查询和审计。
- `scope_type`：`SCHOOL / COLLEGE / MAJOR / CLASS / STUDENT`；非五级树关系另用业务范围类型，不混写组织层级。
- `scope_id`：稳定主键；`SCHOOL` 固定为 `0`，其余分别引用学院、专业、班级或学生主键，禁止继续只存名称。
- `scope_name_snapshot`：授权时名称快照，只用于展示和审计，不能用于鉴权。
- `status`、`effective_at`、`expires_at`、`granted_by`、`reason`：与角色授权生命周期一致。

唯一约束建议为 `(tenant_id, user_role_id, scope_type, scope_id)`。登录上下文和业务范围解析只读取“角色关系有效 + 范围关系有效”的交集；范围缺失时 fail-closed，不得回退到全校。资源鉴权先解析目标学生的 `student_id → class_id → major_id → college_id → tenant_id` 祖先链，再判断是否被任一有效授权节点覆盖。

现有 `TeacherStudentScope` 暂时继续承载班级、学院、专业、楼栋、导师等历史关系；五级通用范围分阶段迁移到新表，过渡期采用双读校验、单写新表，迁移完成后停止用名称参与鉴权。辅导员、班主任等权威任职关系可投影为 `CLASS` 范围，但来源和撤销仍由任职关系驱动。

## 5. 权限与安全边界

- 查看成员：`systemAdmin.role.view`。
- 搜索和添加成员：`systemAdmin.user.assign-role`。
- 学校侧禁止授予 `PLATFORM_*` 角色。
- 操作者不能利用临时授权转授超过自身基础权限的角色。
- 学生账号禁止绑定教职工角色。
- 批量操作最多 100 人，授权原因和影响账号写入关键审计。
- 下级管理员的可授予人员、可授予角色和可选范围节点均受自身范围约束，不能把学院权限扩大到学校，也不能把专业权限扩大到整个学院。
- 人员组织归属只做默认建议；实际授权范围必须显式保存或有权威关系来源，避免“调岗即隐式扩权”。
- 高权限角色沿用后端授权边界；后续可增加前端二次确认和安全变更审批。

## 8. 验收标准

- 有权限管理员点击任意角色人数后能进入“添加成员”。
- 能搜索、多选并一次添加多位启用中的老师。
- 已有成员不会出现在候选列表，重复提交不会产生重复关系。
- 任一非法账号时整批不落库。
- 成功后成员清单与角色人数立即更新。
- 辅导员等范围型角色显示清晰的后续范围配置提示。
- 范围型角色不选择或未建立对应范围不能提交；同一成员可拥有同层多个节点且成员人数不重复计算。
- 学校范围覆盖全校，学院覆盖所属专业/班级/学生，专业覆盖所属班级/学生，班级覆盖所属学生，学生范围不向上扩张。
- 撤销或到期角色时，其范围同步失效；重新授权不得无提示继承旧范围。
- 下级管理员不能查看或授予自身范围外或高于自身层级的节点，越权请求返回 403 并写审计。
- 所有授权均有来源、原因、有效期和关键审计证据。
