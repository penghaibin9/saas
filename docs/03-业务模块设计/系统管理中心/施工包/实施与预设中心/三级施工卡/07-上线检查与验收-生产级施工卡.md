# 上线检查与验收生产级施工卡

## 0. 身份与现状

`systemAdmin.implementation.acceptance` / `sys-implementation-acceptance` / `/admin/system/implementation/acceptance`；状态 `implemented_partial`。12 类检查已写入真实检查表并按阻断条件决定 `READY_FOR_ACCEPTANCE`；WARNING 项支持责任人确认并写入确认人、时间、说明和审计，接口逐项探测和不可改验收摘要仍待增强。

## 1. 业务结果与页面

系统自动运行 12 类上线检查，按 BLOCKER/WARNING/INFO 展示结果、真实证据、责任角色、修复入口和最近检查时间。自动项来自真实表/API；仅学校政策和肉眼核验项允许责任人确认。所有 BLOCKER 通过后，学校管理员填写验收意见并封板，生成不可改的验收摘要。

## 2. 检查目录与规则

| 类别 | 关键自动检查 | 人工确认边界 |
|---|---|---|
| 学校开通/模块业务 | 租户 ACTIVE、套餐模块、profile/专业标准版本、业务开关 | 购买范围与交付范围一致 |
| 角色权限/菜单工作台 | 必备管理员、危险权限互斥、菜单/API/按钮一致、活动角色可用 | 责任岗位人选 |
| 组织/师生/业务关系 | 学院专业班级引用完整、账号重复/无组织、辅导员/教学任务/导师关系缺失 | 低置信映射确认 |
| 流程/字典编号/通知 | 启用流程均有审批人、编号不冲突、模板变量有效、站内渠道可用 | 学校政策和通知文案 |
| 安全审计 | 首登改密、锁定、会话、脱敏、水印、审计健康、高危确认 | 学校安全负责人签认 |
| 上线检查 | DB/接口/文件目录/模块授权、未处理 BLOCKER | 验收意见和责任承诺 |

## 3. 动作、API、状态

| 动作 | 规则 | API/权限 | 审计 |
|---|---|---|---|
| 运行全部/单类检查 | APPLIED/VERIFYING/READY；幂等覆盖同 check_code 最新结果并保留时间 | POST `/checks/run`；`.check.run` | `READINESS_CHECK_RUN` |
| 确认人工项 | 仅 assignee 或学校管理员；需 comment | POST `/checks/{code}/confirm`；`.check.confirm` | signer/role/comment |
| 跳转修复 | ownerRoute 必须在租户模块授权及当前角色菜单内 | 前端路由 | 修复页自行审计 |
| 验收 | BLOCKER=0、必需人工项 PASS；confirmText+意见 | POST `/accept`；`.accept` | `IMPLEMENTATION_ACCEPTED` |
| 重新打开 | 不允许修改 ACCEPTED；创建变更项目 | POST change | 新版本链 |

## 4. 数据、权限和归档

检查写 `t_system_implementation_check`，证据只存计数、编码、哈希和脱敏样例，不存学生敏感明文。学校管理员验收；责任人只能确认被分配项；审计员只读；实施管理员可运行检查但不能替学校验收。跨租户 project/check 均不泄露。验收摘要需要可下载的脱敏 PDF/JSON 后置；首轮页面打印使用浏览器打印但不作为正式电子签章。

## 5. 测试、施工与验收

测试：真实空库检查失败；补齐数据后通过；无审批人 BLOCKER；模块未授权；审计落库不健康；非责任人确认403；存在 BLOCKER 验收拒绝；重复检查幂等；跨租户；ACCEPTED 不可改。施工：check registry/runner→DB/API→矩阵页/修复深链→accept快照→pytest/UI/build。回滚验收功能不删除历史；若错误验收只能由审计授权的变更流程纠正，不能直接改状态。

甲方验收：点击“运行全部检查”，每个失败项能解释证据和修复路径；修复后重检转绿；未确认学校政策时不可验收；验收后总览和已安装页均显示版本、时间、验收人。
