# SaaS 标准化权限与自动初始化改造方案

> 文档状态：方案冻结候选稿，暂不启动最终权限收敛实施  
> 编制日期：2026-07-15  
> 适用项目：职校学生全生命周期 SaaS 系统  
> 启动条件：教务中心主体功能与权限点开发完成后，再据此实施全系统权限收敛  
> 上位约束：`00-系统管理中心-权限角色模块授权与权责边界设计.md`

---

## 1. 背景与核心目标

本项目由初创团队独立开发和维护，产品竞争力不仅来自功能和价格，还必须来自低实施、低配置、低运维成本。

本方案的核心目标是：

> 采用成熟的“岗位、角色、权限、数据范围”原理，将传统高校软件依赖实施人员逐校配置的交付方式，改造成标准化、自动初始化、尽量不需要实施人员的 SaaS 交付模式。

最终希望实现：

1. 平台创建学校租户后，系统自动完成默认角色、菜单、流程、参数和安全策略初始化。
2. 学校只需导入教师、学生以及必要的岗位关系，即可开始使用。
3. 普通学校无需理解底层权限码，也无需逐项配置菜单和按钮。
4. 平台升级角色模板后，可自动、安全地覆盖大多数租户，避免逐校维护。
5. 用户权限异常时，系统能够自动解释原因，减少开发者远程排查和人工支持。
6. 平台保持严格的租户隔离、敏感数据保护、权限审计和历史追溯能力。

本方案不追求复制大型厂商的项目制实施体系，而是用相同的成熟权限原理，构建更适合初创公司和标准 SaaS 的轻实施模式。

## 2. 公开竞品方案对照结论

根据湖南强智科技公开的高校教务系统操作资料，其权限设计体现了以下思路：

- 基于角色进行授权；
- 角色来源于学校实际岗位和业务职责；
- 用户与角色进行绑定；
- 角色配置功能权限；
- 数据权限限定到负责的学院、教学范围等资源；
- 功能权限可以细化到按钮级；
- 权限点操作与操作日志关联。

典型公开示例为：教学秘书岗位对应教学秘书角色，将用户绑定该角色，再限定其负责学院的数据范围。

因此，本方案与成熟高校管理软件在权限原理上方向一致：

```text
岗位职责 → 角色 → 功能权限 → 数据范围 → 操作日志
```

区别在于产品交付方式：

| 维度 | 传统项目制软件 | 本项目目标 |
|---|---|---|
| 角色配置 | 实施人员逐校配置 | 平台提供标准岗位包 |
| 权限配置 | 学校逐项勾选 | 模板自动生成，学校只做少量裁剪 |
| 数据范围 | 人工逐个维护 | 优先从真实业务关系自动推导 |
| 新校开通 | 实施人员初始化 | 幂等开局程序一键初始化 |
| 系统升级 | 逐校检查配置 | 模板版本和差异配置自动升级 |
| 故障排查 | 实施或开发人工排查 | 权限诊断和上线就绪度检查 |

## 3. 当前代码基础与审查结论

### 3.1 已具备的基础

当前项目已经具备继续改造所需的大部分骨架，不需要推翻重建：

- 已有 SaaS 租户、套餐、模块授权设计；
- 已有 `User / Role / UserRole / Permission / RolePermission` 数据模型；
- 已有集中式 `ROLE_PERMISSIONS` 权限映射和统一权限检查入口；
- 已有 `TeacherStudentScope` 教师数据范围映射；
- 已有用户多角色和当前激活角色的前端交互设计；
- 已有 `/auth/me`、`/auth/switch-role` 路由骨架；
- 已有用户账号、角色权限、菜单权限、数据范围、组织结构、系统配置和日志中心页面；
- 已有新学校开局向导和 dry-run/confirm 思路；
- 已有租户隔离、审计日志、模块授权和部分业务域数据范围检查；
- 已有教务、学工、毕设、实习等业务关系数据，可作为自动权限范围来源。

### 3.2 当前真实运行链路的主要断点

最终权限收敛前，需要重点解决以下问题：

1. 真实登录仍按登录名映射演示角色，没有完整读取 `t_user_role`。
2. `/auth/me` 和 `/auth/switch-role` 仍依赖 mock 身份服务，真实多角色切换未完成。
3. 系统管理中心多数页面仍使用 mock 数据，尚未接入真实用户、角色、组织和范围接口。
4. 创建学校管理员时只创建用户，尚未稳定创建并绑定学校管理员角色。
5. 部分账号查询缺少 `tenant_id` 条件，不同学校相同工号可能发生冲突或错误匹配。
6. `RolePermission` 数据表已经存在，但运行时授权主要依赖代码内置映射，两套来源尚未明确主从关系。
7. 开局导入允许未知 `roleCode` 自动创建 `SYSTEM` 角色，容易把拼写错误或越界角色写入生产库。
8. 教师范围部分使用班级名、学院名、学号等文本引用，组织改名可能导致权限失效。
9. 当前 `SCHOOL_ADMIN={"*"}` 将系统配置权限与业务敏感数据权限混合，边界过宽。
10. 当前身份切换、权限回收、Token 失效、权限版本之间还没有形成完整闭环。

### 3.3 总体判断

现有代码属于“设计骨架已经具备，但真实权限主链尚未完全贯通”。因此后续应以收敛和接通为主，不宜另起一套新的权限体系。

## 4. 总体权限模型

采用以下六层模型：

```text
用户
  ↓ 任职/兼职
岗位
  ↓ 映射
角色模板
  ↓ 授予
功能权限 + 数据策略 + 敏感权限 + 审批权限
  ↓ 结合
真实业务关系
  ↓ 解析
当前有效权限上下文
```

### 4.1 用户

用户代表自然人账号，一个用户只归属一个学校租户，但可以拥有多个岗位和多个角色。

### 4.2 岗位

岗位是学校管理员能够理解的业务名称，例如：

- 辅导员；
- 任课教师；
- 教务处管理员；
- 毕设导师；
- 实习指导老师。

学校日常操作以“给教师分配岗位”为主，不直接面对底层权限码。

### 4.3 角色模板

角色模板是平台维护的稳定授权包，包含：

- 角色编码；
- 功能权限；
- 默认菜单；
- 默认数据范围策略；
- 默认敏感数据边界；
- 可参与的审批节点类型；
- 安全红线；
- 模板版本。

### 4.4 数据范围

角色只能回答“能做什么”，数据范围回答“能对谁做”。数据范围优先来自真实业务关系，而不是人工重复配置。

### 4.5 当前激活角色

一个用户可以同时拥有多个角色，但一个会话同一时间只激活一个角色。角色切换后必须同时更新：

- 菜单；
- 页面按钮；
- 数据范围；
- 待办；
- 统计口径；
- 移动端入口；
- 敏感字段权限。

### 4.6 后端最终裁定

每次业务请求按以下顺序裁定：

```text
租户状态
→ 模块授权
→ 当前角色合法性
→ 功能权限
→ 数据范围/业务关系
→ 敏感字段权限
→ 审批节点权限
→ 审计记录
```

前端隐藏菜单和按钮只用于改善体验，不能作为安全边界。

## 5. 低维护成本的角色策略

### 5.1 不建设重型自由权限平台

第一阶段不建议允许每所学校任意组合所有菜单、按钮和敏感权限。否则容易产生：

- 每校一套不同配置；
- 升级时无法统一迁移；
- 学校误配造成越权；
- 大量“为什么看不到/为什么能看到”的支持请求；
- 开发者长期承担实施人员职责。

默认采用“固定岗位包 + 自动数据范围 + 少量差异配置”。

### 5.2 三类角色

#### 平台角色

仅平台方使用，学校不可分配：

- `PLATFORM_SUPER_ADMIN`：平台最高配置权限；
- `PLATFORM_OPERATOR`：租户、套餐、模块授权运营；
- `PLATFORM_SUPPORT`：经学校临时授权后的运维协助；
- `PLATFORM_AUDITOR`：平台审计只读。

平台角色不默认读取学校业务敏感明细。

#### 核心内置岗位角色

首期建议控制在约十二个核心岗位包：

| 角色编码 | 角色名称 | 默认数据范围来源 | 默认定位 |
|---|---|---|---|
| `SCHOOL_SYS_ADMIN` | 学校系统管理员 | 本校配置面 | 用户、角色、组织、参数、流程和审计配置 |
| `SECURITY_AUDITOR` | 安全审计员 | 本校审计 | 只读审计，不参与业务处理 |
| `SCHOOL_LEADER` | 学校领导 | 全校汇总 | 只读驾驶舱和脱敏汇总 |
| `COLLEGE_ADMIN` | 学院负责人 | 所属学院 | 本学院管理和汇总 |
| `ACADEMIC_ADMIN` | 教务处管理员 | 全校教务域 | 教务运行管理 |
| `STUDENT_AFFAIRS_ADMIN` | 学工处管理员 | 全校学工域 | 学工业务管理 |
| `COUNSELOR` | 辅导员 | 辅导员班级关系 | 所带班级和学生 |
| `COURSE_TEACHER` | 任课教师 | 教学任务/教学班 | 本人课程和学生 |
| `PSYCHOLOGY_TEACHER` | 心理老师 | 专项授权学生 | 心理业务最小必要范围 |
| `GD_MENTOR` | 毕设导师 | 毕设导师分配 | 本人指导学生 |
| `INTERN_MENTOR` | 实习指导老师 | 实习指导分配 | 本人指导学生 |
| `STUDENT` | 学生 | 账号绑定学生 | 仅本人 |

#### 可选模块岗位角色

随对应模块授权启用：

- 学院教务员；
- 学院学工负责人；
- 资助老师；
- 宿舍管理员；
- 团委老师；
- 毕设管理员；
- 专业负责人；
- 评阅教师；
- 答辩秘书和答辩专家；
- 实习管理员；
- 学院实习负责人；
- 就业老师；
- 企业导师和企业联系人。

未购买或未启用对应模块时，不向学校展示相关岗位。

### 5.3 学校自定义边界

为降低支持成本，第一阶段建议：

- 内置岗位编码不可修改；
- 学校可以修改岗位显示名称；
- 学校可以停用不用的岗位；
- 学校可以复制岗位模板；
- 复制后的角色默认只允许删减权限；
- 不允许超过来源模板或创建者自身权限；
- 不允许启用学校未授权模块；
- 敏感权限不能通过普通复制自动获得；
- 高级按钮权限编辑作为后续高级能力或高级套餐功能。

## 6. 模板继承与版本升级策略

为了避免每所学校复制一整份角色权限，建议采用“全局模板 + 租户差异”模型。

### 6.1 全局角色模板

建议包含：

```text
template_code
template_name
template_version
role_category
permission_set
default_scope_policy
sensitive_constraints
enabled_module
upgrade_policy
```

### 6.2 租户角色配置

学校只保存必要差异：

```text
tenant_id
template_code
display_name
enabled
disabled_permissions
extra_scope_limit
local_version
```

### 6.3 升级原则

- 安全修复和权限收窄可按平台策略强制升级并记录审计；
- 新增普通权限默认按模板升级策略决定是否自动启用；
- 新增敏感权限默认不自动授予；
- 学校显式禁用的权限继续保留；
- 自定义角色保留来源模板和差异，支持升级预览；
- 每次升级记录 before/after、模板版本和执行结果。

## 7. 数据范围与业务关系

### 7.1 自动推导优先

| 岗位 | 数据范围来源 |
|---|---|
| 辅导员 | 辅导员—班级/学生绑定关系 |
| 任课教师 | 学期教学任务、教学班和课程关系 |
| 学院负责人 | 用户所属学院或岗位任职关系 |
| 毕设导师 | 毕设导师分配关系 |
| 毕设评阅教师 | 评阅任务分配关系 |
| 实习指导老师 | 实习指导分配关系 |
| 企业导师 | 企业、岗位、协议、实习学生关系 |
| 宿舍管理员 | 楼栋/宿舍管理关系 |
| 学生 | 当前账号绑定的学生 ID |

### 7.2 数据范围使用稳定 ID

生产版本不应继续以班级名、学院名等易变文本作为最终授权引用。建议逐步统一为：

- `user_id`；
- `college_id`；
- `major_id`；
- `class_id`；
- `teaching_class_id`；
- `student_id`；
- `internship_assignment_id`；
- `graduation_assignment_id`；
- `dorm_building_id`。

显示名称只作冗余展示，不作为权限判定主键。

### 7.3 无范围时默认拒绝

有岗位但没有完成业务关系绑定时，系统应：

- 菜单可以显示必要的提示页；
- 业务列表返回空或明确“尚未分配负责范围”；
- 详情、修改、审批和导出默认拒绝；
- 进入上线就绪度告警；
- 禁止回退为全校数据范围。

## 8. 新学校自动初始化

### 8.1 初始化流程

```text
创建租户
→ 应用套餐与模块授权
→ 创建学校根管理员
→ 初始化核心岗位模板
→ 初始化菜单和权限元数据
→ 初始化默认流程
→ 初始化字典和学校参数
→ 初始化安全策略
→ 初始化学生默认角色
→ 生成上线就绪度报告
```

### 8.2 幂等要求

初始化程序必须满足：

- 可以重复执行；
- 已存在的数据跳过；
- 缺失的数据自动补齐；
- 不覆盖学校已确认的合法差异；
- 单步失败可重试；
- 整体有执行批次、状态和审计日志；
- 支持 dry-run，先报告将发生的变化。

### 8.3 初始化完成标准

至少满足：

- 租户有效；
- 根管理员可登录；
- 根管理员拥有真实系统管理员角色；
- 必要角色模板存在；
- 菜单和权限元数据完整；
- 关键安全策略已启用；
- 关键流程存在且无空审批节点；
- 学生默认角色可自动分配。

## 9. 学校低实施导入方案

### 9.1 学生导入模板

建议核心字段：

| 字段 | 说明 |
|---|---|
| 学号 | 租户内唯一 |
| 姓名 | 必填 |
| 学院 | 匹配学院字典 |
| 专业 | 匹配专业字典 |
| 年级 | 必填 |
| 班级 | 匹配班级 |
| 手机号 | 可选，敏感存储 |
| 状态 | 默认正常在籍 |

导入成功后自动：

- 创建或绑定学生账号；
- 绑定学生档案；
- 分配 `STUDENT`；
- 设置本人数据范围；
- 首次登录强制修改密码或完成统一身份绑定。

### 9.2 教师与岗位导入模板

建议允许同一教师出现多行，每行代表一个岗位关系：

| 工号 | 姓名 | 所属部门 | 岗位编码 | 负责对象类型 | 负责对象 |
|---|---|---|---|---|---|
| T001 | 李老师 | 信息学院 | COUNSELOR | CLASS | 软件2301 |
| T001 | 李老师 | 信息学院 | COURSE_TEACHER | TEACHING_TASK | Java教学班01 |

系统自动完成：

- 同工号合并为一个用户；
- 分配多个岗位/角色；
- 解析负责对象为稳定 ID；
- 建立数据范围或业务关系；
- 生成一次性初始凭据；
- 写入导入和授权审计。

### 9.3 导入预演

落库前必须展示：

- 将新增/更新/跳过多少用户；
- 将新增哪些组织结构；
- 哪些岗位编码无效；
- 哪些负责对象不存在；
- 哪些教师有岗位但没有数据范围；
- 哪些记录发生职责冲突；
- 哪些账号或工号重复；
- 哪些数据会改变已有授权。

默认采用原子导入：存在硬错误时整批不落库。需要跳过错误行时必须显式选择，并生成完整回执。

## 10. 权限安全与维护红线

### 10.1 学校系统管理员边界

学校系统管理员是本校配置面的最高管理员，但不应天然拥有所有业务敏感明文权限。

建议拆分：

```text
SCHOOL_SYS_ADMIN
  管理用户、角色、组织、菜单、流程、参数和审计
  不默认读取心理、资助、处分、身份证、成绩等业务敏感明细

业务管理员
  分别按教务、学工、毕设、实习等业务域授予
```

### 10.2 职责冲突

逐步增加以下冲突检查：

- 系统管理员不应作为独立审计员审计自己；
- 成绩录入人与最终发布/终审角色应分离；
- 资助经办与最终审批应按流程分离；
- 敏感权限申请人与审批人不能是同一当前角色；
- 平台运维无学校授权不得进入学校业务数据。

### 10.3 敏感授权

敏感权限建议采用“角色基础能力 + 用户专项授权”：

```text
角色基础权限
+ 指定用户
+ 指定学生/范围
+ 授权原因
+ 生效和失效时间
+ 审批人
+ 访问审计
```

新增敏感权限默认不随模板升级自动下发。

### 10.4 权限回收

角色、岗位或范围发生变更时：

- 更新用户权限版本；
- 旧权限上下文失效；
- 后续请求重新解析；
- 高风险回收可强制退出；
- Token 切换和刷新时重新校验角色归属；
- 不允许仅依赖前端刷新生效。

## 11. 降低运营和售后成本的工具

### 11.1 上线就绪度检查

示例：

```text
✓ 学校管理员已创建
✓ 核心角色模板已初始化
✓ 学生账号已导入
✓ 教师账号已导入
```

### 11.2 权限诊断器

输入用户、角色、页面或权限码，系统解释：

```text
用户：李老师
当前角色：COUNSELOR
模块授权：已授权
功能权限：已拥有 studentAffairs.leave.view
数据范围：软件2301班

```

该能力用于减少“页面为什么看不到”“按钮为什么点不了”的人工排查。

### 11.3 租户支持包

一键导出脱敏支持信息：

- 租户和套餐版本；
- 模块授权；
- 模板版本；
- 初始化状态；
- 用户角色摘要；
- 数据范围摘要；
- 最近权限拒绝事件；
- 系统版本和迁移版本；
- 不包含学生敏感明文。

### 11.4 配置健康检查

定期检查：

- 无成员角色；
- 已停用角色仍被分配；
- 有角色无范围；
- 有流程无审批人；
- 离职账号仍有有效岗位；
- 过期临时授权；
- 模板版本落后；
- 重复或失效组织引用。

## 12. 最终实施阶段划分

### 阶段 0：权限资产盘点

启动时重新扫描所有前后端权限点、菜单、路由、审批节点和数据范围实现，形成唯一权限目录，清理同义编码和失效编码。

### 阶段 1：真实认证与角色主链

- 登录按 `tenant_id + login_name` 查询；
- 登录读取真实 `UserRole`；
- `/auth/me` 返回真实角色；
- `/auth/switch-role` 校验本人角色并重新签发上下文；
- 权限回收与 Token 版本联动；
- 学校系统管理员权限边界收窄；
- 修复跨租户查询风险。

### 阶段 2：标准岗位模板

- 冻结核心角色编码；
- 建立全局模板和租户差异模型；
- 建立模板版本；
- 建立模块与岗位的启用关系；
- 禁止未知角色自动创建为系统角色。

### 阶段 3：自动初始化

- 创建租户即初始化；
- 创建根管理员并绑定角色；
- 初始化菜单、权限、流程、字典和安全参数；
- 支持 dry-run、幂等、重试和审计；
- 生成上线就绪度。

### 阶段 4：系统管理真实接口

- 用户账号；
- 岗位角色；
- 用户岗位分配；
- 数据范围；
- 组织结构；
- 模块授权只读查看；
- 系统参数；
- 审计日志。

逐页替换 mock，真实接口稳定后再删除对应 mock 数据。

### 阶段 5：师生和岗位导入

- 标准 Excel 模板；
- dry-run 校验；
- 原子写入；
- 重复导入幂等；
- 岗位到角色自动映射；
- 业务关系和稳定 ID 绑定；
- 错误清单与导入回执。

### 阶段 6：权限诊断与运营工具

- 权限诊断器；
- 配置健康检查；
- 租户支持包；
- 模板升级预览；
- 权限变更影响分析。

## 13. 验收标准

### 13.1 新学校开通

- 创建租户后无需手工执行 SQL；
- 根管理员可登录且具有真实角色；
- 必要角色、菜单、流程、字典自动存在；
- 重复初始化不产生重复数据；
- 未购买模块的角色和菜单不可启用。

### 13.2 用户与角色

- 同一教师可拥有多个角色；
- 只能切换本人拥有的角色；
- 切换后菜单、按钮、范围、待办和统计同步变化；
- 回收角色后旧权限及时失效；
- 不同租户允许存在相同工号，但不能互相登录或读取。

### 13.3 数据范围

- 辅导员只能访问所带班级；
- 任课教师只能访问本人教学任务；
- 毕设和实习导师只能访问本人指导学生；
- 无业务关系默认拒绝，不回退全校；
- 列表、详情、统计、导出和批量操作执行一致的数据范围校验。

### 13.4 导入

- 学校可通过标准模板完成师生和岗位导入；
- 导入前可完整预演；
- 错误有行号、字段和修复建议；
- 重复导入可安全跳过或更新；
- 未知岗位不会自动创建系统角色；
- 所有授权变化可审计。

### 13.5 运维成本

- 普通学校不需要逐项配置按钮权限；
- 常见权限问题可以通过诊断器自行解释；
- 模板升级不需要逐校手工修改；
- 开发者可通过脱敏支持包定位租户配置问题；
- 平台能明确显示每所学校是否具备上线条件。

## 14. 当前阶段边界与后续启动条件

当前阶段继续完成教务中心开发，不立即进行全系统最终权限收敛，原因如下：

- 教务中心权限点、教学任务、教学班、成绩、考试和审批关系仍可能继续变化；
- 过早冻结角色权限会产生重复调整；
- 任课教师、学院教务和教务处管理员的数据范围必须建立在最终教务业务关系上；
- 最终收敛应一次性覆盖教务、学工、毕设、实习、系统管理和多端入口。

教务中心主体开发完成后，按以下条件启动：

1. 教务菜单、按钮和接口基本稳定；
2. 教学任务、教学班和任课关系模型稳定；
3. 成绩、考试、调停课等审批责任稳定；
4. 教务主要接口已经具备明确权限码；
5. 现有业务测试能够作为权限收敛回归基线。

启动后首先执行“阶段 0：权限资产盘点”，再进入真实权限主链改造。

## 15. 最终产品定位

本方案形成的产品定位为：

> 平台统一维护版本化岗位与角色模板；学校只维护人员、岗位和负责对象；系统根据真实业务关系自动生成数据范围；创建学校后自动初始化；导入师生与岗位后即可运行；权限变化、敏感访问和角色切换全部可审计。

对初创公司的直接价值：

- 减少逐校实施；
- 减少现场培训；
- 减少权限误配；
- 减少版本升级工作；
- 减少售后排错；
- 保持比传统项目制厂商更低的交付和维护成本；
- 将人力成本优势转化为产品价格优势和规模化能力。
