# 教师端角色化工作台 P0–P7 实施交接方案

> 来源：Claude Code 会话 `0920f80f-5a49-4b62-abad-cd569791c232`。  
> 用途：供 Cursor 或其他开发 Agent 继续实施。本文提取的是方案、约束、验收标准和实际断点，不是聊天记录。

## 1. 核心产品判断

工作台不是“后台首页”或“菜单导航页”，而是一个跨业务域查询：

> 把散落在不同业务域中，属于当前登录人、尚未完成的事项，按紧急程度聚合到一屏，并允许直接下钻办理。

工作台必须回答三个问题：

1. 我是谁：当前真实角色是什么。
2. 什么事情属于我：哪些待办、学生、课程、审批和业务异常在我的职责范围内。
3. “属于我”如何判定：必须使用稳定身份和后端数据范围，不能依赖姓名或前端猜测。

原系统的根本问题不是页面不好看，而是同一位老师在不同域中使用了多套身份标识：

- 统一待办使用 `assignee_id`。
- 教学任务使用 `teacher_id`。
- 成绩、课表使用 `teacher_key`。
- 毕设、实习历史逻辑部分使用姓名字符串。
- 辅导员范围部分使用班级或范围字符串。

因此实施顺序必须先解决身份与数据范围，再做可视化页面。漂亮卡片不能掩盖串数据、全校口径或假数据。

## 2. 不可破坏的设计原则

1. 所有数字必须来自真实接口，禁止生产环境 mock fallback。
2. 当前角色以后端 `/todos/summary` 返回的 `role` 为权威来源，前端不自行推断。
3. 一人多角色通过已有真实 `switch_role` 切换身份和工作台，不能在前端做假的“视角切换”。
4. 数据范围由后端裁定；前端不负责过滤越权数据。
5. 身份解析失败必须 fail-closed，不能退化成全校或公共池全量可见。
6. 一线教师不能消费未按数据范围收敛的全校统计。
7. 每个数字磁贴都必须能点击，下钻到已经筛选好的真实业务列表。
8. 接口失败必须显示错误态，不能用 `0` 或默认值伪装成功。
9. 零待办应给出“今日无待办”的正反馈，不能只显示空白。
10. 从磁贴到完成业务，目标不超过三次点击。
11. 页面顺序固定为：Headline 人话结论 → Cues 数字磁贴 → 明细列表/快捷动作。
12. 未识别角色只显示通用待办，不臆造该角色的专属数据。
13. PC 与教师移动端尽量共用同一数据口径和角色配方，仅排版不同。
14. 先验证一个角色模板，再复制到其他模板；不要同时堆十二套未经验证的页面。

## 4. B1–B9 可复用积木

| 积木 | 类型 | 数据来源 | 下钻目标 |
|---|---|---|---|
| B1 待办磁贴 | Cue | `t_unified_todo`，按指派人与数据范围 | 已筛选待办列表 |
| B2 待我审批 | Cue | `t_workflow_task` | 审批列表 |
| B3 我的学生/班级 | 列表 | 后端数据范围解析器 | 学生档案 |
| B4 关键指标 | Cue | 收敛后的工作台统计接口 | 对应业务列表 |
| B5 临近截止 | 列表 | 各域 `due_at`、批次节点 | 对应任务 |
| B6 消息公告 | 列表 | `t_unified_message` | 消息详情 |
| B7 快捷动作 | 按钮 | 当前角色真实权限 | 新建或办理表单 |
| B8 我的课表 | 卡片 | `t_aa_schedule_item` | 课表页 |
| B9 引导清单 | 清单 | 用户偏好/首次登录状态 | 对应配置或业务页 |

P、B、T 不是三条先后执行的独立路线，而是嵌套关系：

- P1 建造 B1、B2 的后端。
- P2 使用 B1–B4 拼出 T4。
- P3 修正 B4 的数据范围。
- P4 补 B5、B8，并复制到 T1、T2、T7、T10。
- P5 给 T7、T10 补充 B1 的真实业务数据。
- P7 建造 B9，并为全部模板提供个性化。

## 5. P0–P7 实施路线

### P0：身份统一与越权封堵

目标：同名老师不能互相看到对方学生、课表、毕设或实习任务。

原方案计划给大量表新增 `teacher_user_id`，但实际深挖后进行了修正：

- 教务和学工已有稳定工号键，不需要大范围迁移；应移除姓名作为身份键。
- 毕设已有 `mentor_id → mentor.teacher_no` 稳定链路。
- 实习已有 `advisor_user_id` 主路径。
- 历史姓名兜底只允许在租户内可证明姓名唯一时使用；重名时 fail-closed。

验收：

- 两个同名老师不能互相访问。
- 使用工号或用户 ID 的真实关系仍能访问。
- 仅当姓名在租户内唯一时允许兼容历史数据。
- 学院/专业管理员基于授权范围的访问不被误伤。

### P1：待办读端接真库

目标：PC 与移动端工作台使用同一套真实待办可见性。

主要内容：

- 统一工作台待办服务。
- `/todos/summary`、`/admin/todos`、`/admin/todos/count`、消息计数接真实数据库。
- 可见性为“明确指派给我”加“我数据范围内的池待办”。
- 身份无法解析时 fail-closed。
- 完成待办必须校验归属。
- `overdue`、`nearDeadline`、`doneToday` 真实计算；“今日”按业务时区解释。

验收：辅导员看到自己的真实待办，列表、分类计数和汇总口径一致。

### P2：T4 辅导员样板

目标：先用数据最完整的辅导员角色验证产品方向。

页面结构：

1. 问候和一句人话结论。
2. 待处理、逾期、24 小时内到期、今日完成。
3. 请假、风险、违纪、资助、困难认定等真实分类磁贴。
4. 最近待办。
5. 我的班级、谈心谈话、风险台账等真实快捷入口。

验收：

- 真辅导员账号看到的数据与数据库和业务列表一致。
- 所有磁贴均能下钻。
- 加载失败有错误态。
- 零待办有正反馈。
- 页面已接入真实后台首页，不是孤立组件。

### P3：统计和数据范围收敛

目标：任何一线老师都不能看到未经授权的全校统计。

主要内容：

- 审计 `/stats/workbench` 和所有工作台统计接口。
- 使用后端数据范围上下文收敛班级、学院、专业、课程或指导关系。
- 无法证明范围时拒绝或不展示，而不是退化到全校。

验收：辅导员看到本班数据，院级人员看到本院数据，校级授权角色才可看到全校数据。

### P4：复制到重点角色

目标：在 T4 样板验证通过后，复制角色配方到 T1、T2、T7、T10，并补 B5、B8。

原则：

- 共用工作台外壳和积木组件。
- 差异放在角色配方中，不复制十二份页面。
- 路由、权限、数据源均由配置声明。
- 无真实数据的磁贴不能用假数字占位。

验收：专业课老师、教务老师、辅导员、毕设导师、实习老师分别看到本职任务。

之后再按商业优先级补 T3、T5、T6、T8、T9、T11、T12。

### P5：补齐毕设和实习真实待办

目标：解决 T7、T10 页面存在但没有真实数字的问题。

主要内容：

- 在开题、成果、选题变更、评阅等流程创建或更新 `UnifiedTodo`。
- 在周报、巡访、异常、请假等实习流程创建或更新 `UnifiedTodo`。
- 完成、撤回、驳回、重新提交必须同步待办状态。
- 保证幂等，避免重复待办。

验收：真实走一次业务流程后，T7/T10 磁贴、列表和业务状态同步变化。

### P6：清理假货和双入口

目标：生产环境不再出现假视角、死菜单、开发入口和重复菜单源。

主要内容：

- 删除假的角色/视角切换器。
- 删除或封闭 `/dev/components` 等开发入口。
- 收敛双菜单源。
- 删除静态假待办、无接口空壳和无落点按钮。
- 保留诚实的“待建设”提示，但不能伪装成已完成能力。

验收：生产环境没有死菜单、开发入口、假数据或前端假切换。

### P7：体验和个性化

目标：在真实业务稳定后增加个人偏好。

主要内容：

- 磁贴排序与隐藏。
- “我的常用”入口。
- 新老师首次登录引导清单 B9。
- 偏好持久化，并支持恢复默认。
- 埋点观察磁贴点击率，以真实使用数据决定保留或删除。

验收：偏好跨登录保存，不影响权限和后端数据范围。

## 7. Cursor 接手顺序

1. 先阅读本方案以及上面三个 P2 文件。
2. 用 `git status`、`git diff` 区分工作台改动和无关未跟踪临时文件。
3. 核对项目现有 HTTP 封装的调用签名，不要假设新 API 文件写法正确。
4. 核对四条接口的真实响应结构。
5. 核对角色配方中每个下钻路由确实存在且有权限。
6. 将新工作台接入真实后台首页/布局。
7. 完成 P2 后统一执行一次相关构建和测试，不要逐文件全量测试。
8. P2 验收后按 P3 → P4 → P5 → P6 → P7 继续。
9. 每一期必须给出：代码改动、测试证据、未覆盖项、风险和下一期入口。
10. 未经明确授权不要提交或推送；不要碰无关未跟踪文件。
