## 零、总判断：这份 V3.0 到底要解决什么

这份总册不是把前面所有模块文档简单汇总，也不是继续写一个“大而全”的方案。它的真正作用是：**把你前面已经设计好的 01-12、08A、08B、09A、09B、10 等文档，收口成一套可以让 Claude Code 按阶段执行的开发总纲。**

如果这份总册写得太简单，后续会出现三个问题：

```text
1. Claude Code 读文档时不知道谁是最高优先级，容易被旧总册、旧PC文档、早期学生APP口径带偏。
2. 模块之间依赖不清楚，容易先开发业务页，后面才发现权限、student_id、文件、待办、消息、审计没打通。
3. 以后想单模块卖时，发现模块授权、菜单开关、到期只读、端侧入口没有提前设计，后面返工很重。
```

所以 V3.0 必须做成“开发冻结总册”，核心任务是统一：

```text
1. 最终系统模块架构
2. 最终端侧架构
3. MVP V1范围
4. 非MVP延后范围
5. 所有模块开发顺序
6. 单模块销售拆分
7. 模块授权与到期只读
8. 代码开发前的反向扫描流程
9. Claude Code文档读取顺序
10. 每个阶段的开发刹车规则
11. 验收标准
12. 商业化落地路线
```

本总册完成后，不代表马上开发全部系统，而是代表：**从现在开始，开发只能按本文档冻结的路线推进。**

## 一、文档定位与版本冻结

### 1.1 本文档的最高优先级

从 V3.0 起，后续研发、测试、演示、部署、报价、试点、交付，均以本文档为最高级别基线。

后续 Claude Code、Cursor、人工开发、测试人员、实施人员，如果遇到文档冲突，优先级如下：

```text
第1优先级：00-职校学生全生命周期SaaS平台开发冻结总册 V3.0.md
第2优先级：00-MVP-V1开发范围冻结.md
第3优先级：00-单模块销售与授权矩阵.md
第4优先级：00-CLAUDE-模块执行总控提示词.md
第5优先级：当前模块深化设计文档
第6优先级：当前模块依赖端侧文档、底座文档、驾驶舱文档
第7优先级：旧总册、旧草稿、早期口径
```

任何早期文档中出现“学生APP”“教师APP”“PC管理端一个入口”“完整教务选课”“专业分流优先开发”等表述，均以本 V3.0 的修订口径为准。

### 1.2 与旧总册的关系

旧总册仍然保留，但定位调整为“历史总体设计基础”。旧总册里有价值的内容继续继承，旧总册里与新模块体系冲突的内容全部以 V3.0 修订。

| 旧口径 | V3.0 修订后口径 | 处理方式 |
|---|---|---|
| 学生APP | 08A 学生小程序中心 | 统一改名，不再优先做原生APP |
| 教师APP | 08B 教师移动工作台中心 | 强调老师移动处理，不做泛APP |
| PC管理端 | 09A PC管理端 + 09B 学生PC门户 | 必须拆分，学生不能进后台 |
| 完整教务系统 | 04 学业过程中心 | 只做画像、预警、学分成绩摘要，不做排课选课 |
| 专业分流 | 后续增强/学校定制 | 不纳入 MVP V1 |
| 生命周期全量开发 | 先做实践教学MVP | 先可卖，再扩全量 |

### 1.3 冻结原则

```text
1. 先冻结，再开发。
2. 先反向扫描，再修改代码。
3. 先底座，再业务。
4. 先毕业设计和岗位实习，再扩迎新、在校服务、学业过程。
5. 先可卖单模块，再组合大平台。
6. 每次只开发一个模块的一个阶段。
7. 任何模块必须接入 student_id、权限、数据范围、文件、待办、消息、审计。
8. 不允许学生PC和管理后台混用。
9. 不允许小程序和PC写成两套业务逻辑。
10. 不允许为了快而绕过模块授权，否则以后不能单模块卖。
```

## 五、端侧架构冻结

### 5.1 全端入口

```text
学生：
  08A 学生小程序
  09B 学生PC门户

老师：
  08B 教师移动工作台
  09A PC管理端教师工作台

  09A PC管理端

企业导师：
  08B 企业导师移动入口
  09A 企业导师PC门户 / enterprise route

领导：
  10 数据驾驶舱

平台运营：
  platform route
```

### 5.2 路由隔离

```text
/admin       学校PC管理端，老师、管理员、领导、审计人员使用
/student     学生PC门户，学生本人使用
/enterprise  企业导师门户，企业导师/企业联系人使用
/dashboard   数据驾驶舱，校领导和授权管理人员使用
/platform    平台运营端，SaaS运营人员使用
```

路由隔离是商业化和安全的底线，禁止学生账号进入 `/admin`，禁止企业导师进入学校后台，禁止平台运营默认查看学校业务明细。

### 5.3 端侧与业务关系

| 业务 | 学生小程序 | 学生PC | 教师移动 | 教师PC | 企业端 |
|---|---|---|---|---|---|

| 岗位实习 | 打卡、请假、查看 | 周报、总结、材料 | 批阅、风险处理 | 批量管理、统计 | 评价、录用意向 |
| 毕业就业 | 填报轻量信息、查看进度 | 复杂就业填报、材料上传 | 核验、跟进 | 就业管理、看板 | 录用确认 |

| 在校服务 | 轻量服务申请 | 复杂表单、证明下载 | 审批处理 | 事项配置、工单池 | 无 |

## 六、MVP V1 开发范围冻结

### 6.1 MVP V1 产品定位

```text
职校实践教学全过程管理平台 V1.0
```

核心目标：先把你已有基础最强、最容易演示、最容易验收、最容易成交的“毕业设计 + 岗位实习”做成真正可运行产品。

## 十、核心底座设计冻结

### 10.1 模块授权

系统必须支持单模块购买，所以模块授权必须是底层能力，而不是前端简单隐藏菜单。

```text
核心表：t_tenant_module_license

字段建议：
id
tenant_id
module_code
module_name
license_status
start_date
end_date
max_students
max_users
enabled_features
readonly_after_expired
created_at
updated_at
```

模块授权必须控制：

```text
1. 菜单是否显示
2. 路由是否可访问
3. API是否可调用
4. 按钮是否可用
5. 写操作是否允许
6. 到期后是否只读
7. 数据看板是否展示
8. 导入导出是否允许
```

### 10.2 授权状态

| 状态 | 含义 | 系统行为 |
|---|---|---|
| TRIAL | 试用 | 功能可用，但可能限制人数/期限 |
| ACTIVE | 正式开通 | 功能正常可用 |
| EXPIRED | 已到期 | 默认进入只读或禁用 |
| READONLY | 只读 | 历史可看，不可新增修改 |
| SUSPENDED | 暂停 | 学校或平台暂停使用 |
| DISABLED | 禁用 | 菜单隐藏，接口拒绝 |

### 10.3 到期只读规则

```text
模块到期后：
1. 历史数据可查看。
2. 新增按钮隐藏。
3. 编辑、提交、上传、审批、批阅按钮禁用。
4. 写接口返回 MODULE_LICENSE_EXPIRED。
5. 导入按钮禁用。
6. 导出可按合同配置是否允许。
7. 数据看板可显示历史快照。
8. 提示学校管理员联系续费。
```

### 10.4 student_id 主键规则

```text
所有业务必须绑定 student_id。
禁止业务表长期只依赖 user_id、openid、手机号、学号、身份证号。
学号、手机号、身份证号只能作为辅助匹配字段。
旧系统 user_id 必须通过 t_student_user_link 映射到 student_id。
```

### 10.5 权限与数据范围

权限判断不是简单角色判断，必须同时判断：

```text
登录状态
租户
模块授权
active_context
角色权限
按钮权限
数据范围
字段权限
资源归属
```

统一数据范围：

```text
SELF
CLASS
COUNSELOR_CLASSES
GD_STUDENTS
INTERN_STUDENTS
ENTERPRISE_AUTH_STUDENTS
MAJOR
COLLEGE
SCHOOL
DEPARTMENT
TEMP_AUTH
AUDIT_SCOPE
```

### 10.6 active_context 多身份规则

```text
同一个老师可能同时是：
辅导员
毕设导师
实习指导教师
答辩专家

不能把这些权限简单合并。
当前身份决定：
1. 当前菜单
2. 当前待办
3. 当前数据范围
4. 当前按钮
5. 当前首页
6. 当前业务操作
```

### 10.7 文件中心

文件中心必须统一承载：


## 十一、各模块边界冻结

### 01 学生主档与身份中心

定位：统一 student_id、学生阶段、学生360、身份映射、组织关系、主档更正。

MVP策略：必须在所有业务前落地。

边界：不做完整教务学籍系统，不替代学校主数据系统。

### 02 数字迎新中心

定位：录取新生导入、账号激活、预报到、材料、绿色通道、现场报到。

MVP策略：MVP后续开发，适合迎新季销售。

边界：不做复杂招生系统，不做缴费系统主体。

### 03 在校服务中心

定位：服务事项、学生申请、请假、证明、帮扶、宿舍维修、咨询工单、关怀。

MVP策略：MVP后续开发，适合学工处。

边界：不做完整OA，不做完整后勤系统。

### 04 学业过程中心

定位：课程成绩摘要、学分画像、补考重修、学业预警、证书竞赛、毕业资格预检。

MVP策略：MVP后续开发，依赖教务数据。

边界：不做排课、选课、考试安排、成绩录入。

### 05 毕业设计中心

定位：批次、课题、选题、任务书、开题、中期、成果、查重、答辩、成绩、归档。

MVP策略：MVP核心，第一个可卖模块。

边界：不做泛论文系统，不脱离学生主档。

### 06 岗位实习中心

定位：实习批次、企业岗位、分配、自主实习、打卡、周报、请假、巡访、风险、评价、成绩、归档。

MVP策略：MVP核心，第二个可卖模块。

边界：不做大型招聘平台。

### 07 毕业与就业中心

定位：毕业批次、就业去向、材料核验、实习转就业、就业看板、归档。

MVP策略：MVP做轻量闭环，后续扩高级就业质量回访。

边界：不替代国家就业系统，不做复杂招聘平台。

### 08A 学生小程序中心

定位：学生移动入口，打卡、消息、待办、轻量申请、扫码。

MVP策略：MVP基础端。

边界：不承担复杂大文件和长表单。

### 08B 教师移动工作台中心

定位：教师移动待办、快速审批、批阅、风险处理。

MVP策略：MVP基础端。

边界：不替代PC复杂管理。

### 09A PC管理端中心

定位：老师、管理员、领导、企业导师PC工作台。

MVP策略：MVP核心端。

边界：学生不得进入。

### 09B 学生PC门户中心

定位：学生电脑端复杂材料办理入口。

MVP策略：MVP核心端。

边界：不是后台管理端。

### 10 数据驾驶舱中心

定位：指标、看板、下钻、风险、归档、教师工作量。

MVP策略：MVP做轻量。

边界：不做静态大屏，不做无业务闭环图表。

### 11 权限与流程中心

定位：权限、数据范围、active_context、流程、待办、消息、SoD、审计。

MVP策略：MVP底座核心。

边界：不能只做前端菜单权限。

### 12 集成开放中心

定位：文件、导入导出、消息通道、接口预留、外部系统对接。

MVP策略：MVP做轻量。

边界：前期不强依赖真实外部系统接口。

## 十五、API 设计总原则

```text
1. API必须版本化：/api/v1/...
2. 学生PC接口建议以 /api/v1/student-pc 开头。
3. 管理端接口建议以 /api/v1/admin 开头。
4. 企业门户接口建议以 /api/v1/enterprise-portal 开头。
5. 小程序接口建议以 /api/v1/student-mini 或 /api/v1/teacher-mobile 开头。
6. 所有写接口必须支持幂等。
7. 所有列表接口必须分页。
8. 所有敏感接口必须写审计。
9. 所有接口必须校验模块授权。
10. 所有接口必须校验数据范围。
```

## 十六、数据库设计总原则

```text
1. 所有业务表必须包含 tenant_id。
2. 所有学生相关业务表必须包含 student_id。
3. 所有关键业务表必须包含 created_at、updated_at。
4. 重要业务必须有状态字段。
5. 重要流程必须有日志表。
6. 文件不直接存路径，业务表保存 file_id。
7. 金额使用 DECIMAL。
8. 状态使用稳定枚举，不要随意写中文状态。
9. 删除优先逻辑删除。
10. 大批量导入必须有批次表和错误表。
```

## 二十、重大风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 文档过多导致Claude混乱 | 读取旧口径、乱改模块 | 必须以V3.0和总控提示词为最高优先级 |
| 先做业务后补底座 | 模块不能单独卖 | 先做BASE、01、11、12 |
| 学生PC和管理端混用 | 权限混乱、学校不敢用 | 09A/09B强隔离 |
| 老师多身份权限合并 | 越权查看学生 | 必须用active_context |
| 小程序和PC两套逻辑 | 状态不一致 | 统一API、统一待办消息 |
| 没有模块授权 | 以后不能单模块卖 | 先做t_tenant_module_license |
| 只做页面没有闭环 | 演示像玩具 | 必须有流程、待办、消息、归档、看板 |
| 完整教务系统拖死项目 | 开发量爆炸 | 04只做学业过程画像和预警 |
| 没有演示数据 | 产品卖不出去 | D7必须做演示数据和脚本 |
| 一次让Claude开发太多 | 代码失控 | 每次一个模块一个阶段 |

## 二十三、开发冻结结论

本项目不能再继续无限扩设计。当前最重要的是让系统进入“可开发、可演示、可卖”的轨道。

最终冻结结论如下：

```text
第一目标：
做成职校实践教学全过程管理平台 V1.0。

第一可卖模块：
毕业设计全过程管理系统。

第二可卖模块：
岗位实习全过程管理系统。

第一组合产品：
毕业设计 + 岗位实习 + 就业轻量 + 学生PC + 小程序 + 教师PC + 教师移动端 + 数据看板。

第一开发路线：
总册冻结 → MVP冻结 → 授权矩阵 → Claude总控 → 反向扫描 → 底座 → 毕业设计 → 岗位实习 → 组合包 → 就业轻量 → 演示交付。

核心底线：
所有模块必须支持单独开通、单独到期、到期只读、历史可查、未授权不可访问。
```
