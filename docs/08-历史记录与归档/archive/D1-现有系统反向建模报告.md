# D1 · 现有系统反向建模报告（旧毕业设计/岗位实习系统）

> 阶段：D1 全项目反向扫描（**只读盘点，不改代码**）
> 扫描对象：`99-老毕业设计系统-只参考不要照抄/`
> 依据：`00-开发冻结总册 V3.0` 第八章 D1、第十章底座设计
> 结论用途：为「D2 底座开发」的**移植 vs 新写**决策与开发顺序提供事实基线
> 生成日期：2026-07-03

---

## 0. 一句话结论

旧系统不是"草稿"，而是一套**已跑通的全栈生产级产品**：Express5 + MySQL 多租户后端（57 控制器）、微信小程序（44 页）、Web 管理端（5 页 SPA）。它的技术栈与 V3.0"不引入新技术栈"的要求**完全吻合**，且已内置 SaaS 关键能力（多租户、RBAC+数据范围、审计、指标、限流）。

**建议：以"移植/再利用为主、按 V3.0 模块结构重整"的方式落地 D2 底座，而不是从零新写。** 新写会丢弃大量已验证的业务闭环代码，工数翻倍且引入回归风险。

与 V3.0 的**核心缺口**只有 4 处需要在 D2 新增（详见 §10）：
1. `student_id` 全域主键（旧系统以 `user_id` 为准）
2. `t_tenant_module_license` 模块授权与到期只读（单模块销售的底层能力）
3. `active_context` 教师多身份上下文
4. 12 种统一数据范围（旧系统仅 self/all/college 等有限范围）

## 7. 毕业设计现有能力

批次任务(`gd-tasks`) → 课题选题(`gd-topics`) → 指导记录(`gd-guidances`) → 成绩(`gd-grades`) → 成果(`gd-achievements`) → 查重(`quality-checks`) → 答辩(委员会/分组/成员/评分 4 表) → 质量报告(`quality-report`)。
**结论：05 毕业设计中心的后端骨架已基本完备**，D3 主要是按 V3.0 补 `student_id`、过程节点退回/重提状态机、归档包。

## 8. 岗位实习现有能力

实习计划(`intern-plans`) → 分配/自主(`assignments`/`applications`) → 到岗协议保险(`agreements`/`insurances`) → 打卡(`checkins`) → 周报日志(`intern-logs`) → 请假(`leaves`) → 风险(`risk`) → 企业评价(`enterprise-evals`) → 统计(`intern-stats`) → 投诉安全(`complaints`)。
**结论：06 岗位实习中心的后端与小程序端最完整**，与 handoff"06 第一主攻"一致，D4/P6-1 复用度最高。

## 9. 权限与登录现有能力

- **登录**：JWT + bcrypt，首次强制改密（`requirePasswordChanged`），微信扫码登录。
- **RBAC**：`requireRole`（角色 1=院校超管放行）+ 细粒度 `requirePermission(code)`（自定义角色引擎，`t_perm_role`/`t_perm_grant`/`t_user_perm_role`）。
- **数据范围**：`attachDataScope` 已产出 `req.dataScope`（现支持 self/all 等），控制器据此过滤。
- **多租户**：DB-per-tenant，`TENANCY_MODE=single|multi`，同码两用（私有化/SaaS），空闲连接池回收，读写分离/分片预留。
- **审计**：全局 `auditMiddleware` 异步落 `t_audit_log`。
- **可观测**：Prometheus 指标、Sentry、requestId 全链路日志、限流、安全响应头/CSP。

**结论：11 权限与流程中心的后端底座已具备 70%**，缺口是 `active_context` 多身份与 12 种数据范围枚举。

## 10. 与 V3.0 的缺口（D2 必须新增的 4 项）

| # | V3.0 要求 | 旧系统现状 | D2 动作 |
| --- | --- | --- | --- |
| 1 | `student_id` 全域主键，业务表禁止长期只依赖 user_id | 以 `user_id` 为主键 | 新增 `t_student`(学生主档) + `t_student_user_link`；业务表补 `student_id` 列并回填 |
| 2 | `t_tenant_module_license` 模块授权/到期只读/单模块销售 | **无** | 新建授权表 + 授权中间件（菜单/路由/API/按钮/写操作/到期只读七控） |
| 3 | `active_context` 教师多身份（辅导员/毕设导师/实习导师/答辩专家） | 角色合并，无上下文切换 | 新增上下文解析中间件，按当前身份决定菜单/待办/数据范围 |
| 4 | 12 种统一数据范围枚举 | 有限范围 | 扩展 `permModel.scopeToFilter` 覆盖 SELF/CLASS/COUNSELOR_CLASSES/GD_STUDENTS/INTERN_STUDENTS/… |

> 另有轻量缺口：统一文件中心（`file_id`+短期签名URL）、统一 todo/message（旧有 notification，需收口为统一待办消息）、导入 Dry-Run + 批次错误表。这些旧系统有雏形，D2 收口即可，非从零。

## 11. 高风险改造点

1. **student_id 回填**：为存量业务表加 `student_id` 并回填是全局改造，须先建映射表、灰度、双写校验，**不可一次性强改**（V3.0 §14 明令）。
2. **模块授权穿透**：授权不能只做前端隐藏菜单，必须穿透到 API 写操作；接入面广，须做成中间件统一拦截，逐路由灰度。
3. **数据范围扩容**：从有限范围扩到 12 种，涉及每个列表/详情接口的过滤条件，须有权限测试与越权测试兜底（V3.0 §17）。
4. **多租户与授权叠加**：`tenant × module_license × active_context × data_scope` 四维叠加，须统一在一处求交，避免各控制器各写一套。
5. **新旧前端并存**：新 `frontend/`(Vue3, 走 provider) 与旧 web SPA 字段口径需对齐，避免契约漂移。

## 12. 建议开发顺序（结合 handoff `11→01→09A→09B→06→05→10→07`）

```
D2 底座（移植+补 4 缺口）
  BASE-P1 新建 backend/ 骨架，移入 config(tenancy/db) + 中间件(auth/tenant/perm/audit) + utils
  BASE-P2 新建 t_tenant_module_license + 授权中间件（缺口2）
  BASE-P3 student_id：t_student + t_student_user_link + 映射回填脚本（缺口1）
  BASE-P4 active_context 中间件 + 12 数据范围枚举（缺口3、4）
  BASE-P5 文件中心 file_id / 统一 todo·message / 导入 Dry-Run 收口
  BASE-P6 /api/v1 版本化 + 路由隔离 /admin /student /enterprise /dashboard /platform
    ↓
09A/09B 管理端与学生门户接实 API（新前端已有壳，切 provider 到 real）
    ↓
06 岗位实习（复用度最高，先跑通 P6-1 三页闭环：打卡→周报→批阅）
    ↓
05 毕业设计 → 10 驾驶舱 → 07 就业轻量
```

## 附：移植 vs 新写 决策建议

| 维度 | 移植/再利用（建议） | 从零新写 |
| --- | --- | --- |
| 工数 | 低（复用 57 控制器/44 小程序页） | 高（翻倍） |
| 风险 | 中（改造点可灰度） | 高（重造已验证闭环易回归） |
| 与 V3.0"不引入新技术栈" | ✅ 完全一致 | ⚠️ 易漂移 |
| student_id/授权/上下文 | 作为 D2 增量叠加 | 也要重做，无优势 |
| 交付速度（可卖） | 快 | 慢 |

**推荐路线：移植为主 → 新建 `backend/` 模块化骨架 → 迁移旧 config/middleware/model → 叠加 4 项缺口 → 按 06→05 接新前端。**

> 本报告为 D1 只读产物，未修改任何代码。下一步需人工确认"移植 vs 新写"后，方可进入 D2。
