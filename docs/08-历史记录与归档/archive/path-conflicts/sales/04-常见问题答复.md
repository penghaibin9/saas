# 04 常见问题答复

- **文档性质**：销售/售前对客沟通材料——客户常见问题标准应答口径（Q&A）
- **适用对象**：销售、售前顾问，答疑现场直接查阅使用
- **依据**：共享事实底稿全部章节；引用冻结文档路径 `docs/database/00-数据库设计冻结总册.md`、`docs/api/00-API契约冻结总册.md`、`docs/security/00-等保三级安全基线总册.md`
- **当前阶段声明**：当前为可演示版本，后端未接入真实数据，接入按 API 契约推进中；本产品尚未经过等保三级测评

### Q1：这个系统是不是已经接了后端，能不能连我们学校的真实数据？

**标准口径**：目前还没有接入真实后端。现在演示给大家看的是 PC 管理端和学生/教师小程序的完整前端闭环，用的是演示用的模拟数据（mock 数据），业务流程、界面操作、角色权限都是真实可用的设计和实现，只是数据来源还不是学校的真实系统。后端的数据库设计和 API 接口契约已经完成并冻结，技术栈也已确定（PostgreSQL + Python FastAPI），接入真实数据是按照这份已冻结的接口契约在推进的，具体接入贵校数据需要结合项目实施计划另行安排。

### Q2：那我们现在看的这些操作，是不是"假的"，没有意义？

**标准口径**：不是假的。现在看到的界面、操作流程、按钮权限、审批逻辑，都是产品真实设计和实现的部分，只是背后的数据存储和读取，目前用的是提前准备好的演示数据集，而不是实时连接学校数据库。这就像装修好的样板间——房间结构、水电走线、门窗都是真实按图纸做的，只是还没有搬家具入住。大家在演示中提出的任何界面或流程上的意见，我们都可以直接反馈调整。

### Q3：数据安全怎么保障？有没有做等保？

**标准口径**：我们在设计上参考了等保三级的思路，做了一系列安全基线设计，比如会话超时管理（PC 端 30 分钟无操作自动超时、移动端 7 天、同一账号最多 3 个并发会话）、敏感数据分级脱敏（按公开/内部/敏感/机密四级管理，机密级信息如密码、完整身份证号禁止在前端明文出现）、文件上传白名单黑名单管控、导出分级授权并写入审计日志。但需要如实说明：**目前这些是安全基线的设计方案和前端预留实现，系统整体还没有经过专业机构的等保三级测评认证**，我们不会说"已经通过等保三级"，这是需要走正规测评流程的，我们目前的定位是"按等保三级思路做好设计准备，具备测评基础"。

### Q4：权限和数据范围是怎么控制的？会不会出现看到不该看的数据？

**标准口径**：我们的权限设计分两层：一层是"角色能做什么"（比如能不能审批、能不能导出、能不能编辑），一层是"角色能看到谁的数据"（数据范围，分全平台、本校、本学院、本班级、仅本人、被指派对象六个层级）。比如学校管理员的数据范围是"本校"，能看到全校学生数据；辅导员是"本班级"，只能看自己带的班；学生是"仅本人"，只能看自己的信息；企业导师是"被指派对象"，只能看被指派给自己的实习学生，甚至看不到毕业设计相关材料。这套模型目前在前端层面已经设计并实现了判断逻辑，真实的服务端强制校验会随着后端接入同步完成，这也是保障数据安全的关键一环，我们会确保权限校验不只停留在前端界面隐藏，而是服务端真正拦截。

### Q5：多个学校一起用这个平台，数据会不会混在一起？

**标准口径**：平台是多租户 SaaS 架构设计，每个学校在租户维度上是独立隔离的，数据不会互相看到。每个学校还可以配置自己的品牌信息，比如校名、主色调，界面上呈现的是学校自己的品牌形象，不会显示成别的学校或者一个通用平台的样子。多租户的具体隔离技术方案（比如是否物理隔离还是逻辑隔离）会在后端接入阶段按项目需求确认。

### Q6：小程序怎么上线？是要单独开发一个小程序吗？

**标准口径**：小程序基于 uni-app 技术框架开发，同一套代码可以构建成 H5 版本（网页直接访问）和微信小程序版本，目前这两种构建方式在我们内部环境都验证通过。具体上线到贵校的小程序主体（比如是挂靠学校已有的微信公众号/小程序主体，还是新注册一个），需要结合贵校的小程序资质和管理要求来确定上线路径，这部分我们会在项目启动阶段跟学校信息中心具体对接。

### Q7：是私有化部署还是 SaaS？我们学校数据能不能不出校？

**标准口径**：平台设计上同时考虑了 SaaS 多租户模式和私有化部署的可能性，具体采用哪种方式，取决于贵校的信息化管理要求和采购方式。如果学校要求数据不出校、独立部署，这属于私有化部署方案，需要结合贵校的服务器环境、网络条件另行评估工作量和周期，这部分建议在需求沟通阶段跟我们的技术团队具体确认，我目前不能给出一个通用的、适用所有学校的部署结论。

### Q8：能不能跟我们现有的教务系统、一卡通、身份认证（比如统一身份认证/单点登录）系统集成？

**标准口况**：架构设计上预留了对接第三方系统的方向和接口规划，比如统一的用户身份体系设计上是可以对接单点登录的。但具体能不能跟贵校现有系统集成，取决于贵校现有系统开放了哪些接口、接口的技术规范是什么，这需要具体调研贵校系统的接口能力之后才能给出确定结论，目前不能承诺"拿来就能对接任何系统"，这是需要双方技术团队具体调研评估的工作。

### Q9：学生的历史数据（比如老系统里已经有的学籍数据）能不能导入？

**标准口径**：平台设计了学生数据的导入导出功能，支持批量导入。具体能不能顺利导入贵校老系统的历史数据，取决于老系统导出数据的格式是否规范、字段是否完整，一般需要先做一次数据格式核对和清洗，才能保证导入质量。这部分工作通常是项目实施阶段的一个具体任务，我们会提供数据导入模板和校验规则，但数据质量的最终把关需要学校相关部门配合确认。

### Q10：实施周期大概要多久？

**标准口径**：实施周期跟几个因素有关：是否需要跟学校现有系统做深度集成、是私有化部署还是 SaaS 模式、学校历史数据迁移的复杂程度、以及学校内部的业务流程确认和验收节奏。目前平台核心模块和界面已经齐全，但真实数据的接入还在推进中，具体到贵校的实施周期，需要我们先做一轮详细的需求调研，再给出准确的排期，这个我建议留到商务洽谈阶段跟大家具体讨论，我这边不方便现在给一个笼统的时间数字。

### Q11：多少钱？怎么收费？

**标准口径**：这个问题我理解大家都很关心，但报价涉及具体的部署方式（SaaS/私有化）、学校规模（学生数、并发用户数）、是否需要定制开发、实施服务内容等多个因素，我们希望能给大家一个准确、负责任的报价，而不是先随口报一个数字。建议这个问题我们安排商务团队跟大家单独详细沟通，把贵校的具体情况了解清楚后再出方案和报价，这样对双方都更公平。

### Q12：风险预警是怎么判断的？会不会有误判或者漏判？

**标准口径**：风险预警是系统辅助发现问题的机制，比如实习出勤异常、学业预警这类情况，系统会把这些信息汇总呈现给辅导员和教务老师，帮助他们更早注意到需要关注的学生，但最终的判断和处理仍然是由老师来完成的，系统提供的是一个更系统化的发现渠道，不能替代老师的专业判断，我们也不会承诺"系统能发现所有风险情况、不会有遗漏"，这是需要老师结合系统提示和实际情况共同判断的。

### Q13：审批流程能不能按我们学校的实际制度定制？

**标准口径**：目前平台设计并演示了几类标准审批流程模板，比如岗位实习申请审批流（学生提交→指导教师审核→学院审核→辅导员抄送→结束）、实习周报批阅流、毕业设计材料审阅流，这些是通用场景下的标准流程。如果贵校的审批制度跟这些标准流程有差异（比如多一个审批节点、审批人不一样），这属于需要结合贵校实际制度做定制配置或开发的部分，需要在需求沟通阶段具体确认差异点，再评估工作量。

### Q14：老师和学生要不要专门培训才能用？操作复杂吗？

**标准口径**：从界面设计上，我们尽量做到贴近日常操作习惯（比如小程序里的申请表单、审批按钮），操作路径不会特别复杂。但任何新系统上线，一定的培训和适应期是需要的，具体的培训方案、培训材料、上线陪跑支持，这些属于项目实施阶段的服务内容，我们会根据学校规模和具体需求来设计，这个可以在后续方案沟通里进一步细化。

### Q15：这套系统现在有没有正式在其他学校使用？

**标准口径**：请允许我如实说明目前的产品阶段——这是一套核心模块和界面设计已经完成、处于可演示状态的产品，我们今天演示的内容是真实可操作的产品能力展示，但目前还没有到"已经在某所学校正式上线运行真实业务"的阶段，后端真实数据的接入还在推进中。我们不会用夸大的说法来介绍产品的成熟度，希望通过今天透明、如实的沟通，让大家判断这套产品是否符合贵校的需求和节奏。

### Q16：数据能不能导出？会不会被平台"锁死"，以后想换系统换不了？

**标准口径**：平台设计了分级的数据导出能力（按权限分为列表导出、加密归档导出、脱敏导出三档），学校对自己的数据始终拥有导出的能力，不存在"锁死"数据的设计。具体的数据归还、迁移方案（比如合同到期后的数据处理），这属于商务合同条款层面的内容，建议在采购合同洽谈阶段跟商务团队明确约定。

### Q17：如果演示中发现的问题（比如某个功能还不够好用），多久能改？

**标准口径**：我们会认真记录演示过程中大家提出的所有意见和建议，反馈给产品和技术团队评估。哪些是可以快速调整的界面细节、哪些是需要纳入需求排期的功能增强，我们会在评估后给大家一个明确、诚实的答复和时间预期，不会当场随口承诺一个不确定能兑现的时间。
