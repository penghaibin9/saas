# 13A 学工中心页面树与路由设计

> 依据：《_13-需求输入-V1.1.md》（尤其 §2 学工一级功能、§10 V1/P2P3 划分、§11 页面级落地要求 41 项规格与示例）、《_13-现有系统集成事实速查.md》（PC 路由 `/admin/<module>/…`、后端 `/api/v1/student-affairs/*`、移动端 `/api/v1/mobile/affairs/*`）。
> 本文档是 13A 全部页面级设计文档（交互矩阵 / 表单校验 / 移动端入口）的页面与路由唯一基准，其余文档引用本文页面编号与路由，不得另造。
> 图例：★ = V1 必做；☆ = P2/P3 后置。本文不写代码、不改现有路由，仅做设计。

## 1. 设计总原则

1. **路由基座**：PC 学工中心统一挂载在 `/admin/student-affairs/*`，与现有 PC 模块目录约定一致（`frontend/src/modules/student-affairs/`，含 api/ routes/ views/）。学生入口一律小程序/H5（本轮不开学生 PC 门户），见《13A-学工中心移动端入口设计.md》。
2. **路由类型区分**（§11 要求，全模块统一后缀语义）：

   | 页面类型 | 路由形态 | 示例 |
   |---|---|---|
   | 列表 | `/{biz}` | `/admin/student-affairs/leave` |
   | 详情 | `/{biz}/:id` | `/admin/student-affairs/leave/:leaveId` |
   | 新增 | `/{biz}/create` | `/admin/student-affairs/discipline/create` |
   | 编辑 | `/{biz}/:id/edit` | `/admin/student-affairs/classes/:classId/edit` |
   | 审批 | `/{biz}/:id/approve` | `/admin/student-affairs/leave/:leaveId/approve` |
   | 统计 | `/{biz}/stats` | `/admin/student-affairs/leave/stats` |
   | 配置 | `/{biz}/config` | `/admin/student-affairs/leave/config` |
   | 归档 | `/archive/*` | `/admin/student-affairs/archive/batches/:batchId` |

   注意：`create`、`stats`、`config` 等静态段路由必须注册在 `:id` 动态段之前，避免被动态参数吞掉（前端路由注册顺序约定）。
3. **谁能进 = 数据范围 + 权限点**双重判定：菜单/路由守卫看权限点（`studentAffairs.<biz>.<action>`），页面内数据看范围函数（`getStudentAffairsScope`，实现为既有 `resolve_teacher_scope` / `t_teacher_student_scope` 机制的封装扩展，新增 `scope_type=DORM_BUILDING / PSY_STUDENT / AID_STUDENT`）。看得见 = 能处理，列表过滤与写操作校验共用同一 scope 函数。
4. **审批一律走 Workflow**：新审批 = 新 workflow_code + node_code 序列，任务/实例落 `t_workflow_instance` / `t_workflow_task`，待办进 `t_unified_todo`，消息进 `t_unified_message`。审批页是「业务详情 + Workflow 任务操作区」的组合页，不另建审批引擎。
5. **请假复用决策**：13A 请假在既有 campus-service `t_cs_leave` 之上**扩展**（状态机扩展 + 审批流升级 + 销假/续假新表 `t_affairs_leave_cancel_record` / `t_affairs_leave_extension` 关联），不平行再建（详见交互矩阵文档「扩展 vs 平迁」节）。处分同理基于 `t_cs_discipline` 升级；宿舍基于 `t_cs_dorm_record` / `t_cs_dorm_exception` 扩展。
6. **配置页接平台规则中心**：长假天数阈值、审批层级、材料必传类型等可配置规则接入现有 `/admin/platform` 规则中心（safe_rule），学工侧配置页只做「业务视角的读取与提交」，不新建管理端。

## 4. 核心流程页面跳转链路

> 箭头格式沿用需求 §11 示例；「(m)」= 小程序/移动端页面，其余为 PC 页面；方括号内为关键状态/接口。

### 4.1 学生请假（小程序全流程）

```
(m)学生小程序·服务大厅「请假」
 → (m)我的请假列表 pages/student/affairs/leave/list [GET /api/v1/mobile/affairs/leave/my]
 → (m)新增请假 pages/student/affairs/leave/create（类型/起止/原因/材料，createSubmitLock 防重复）
 → 提交 [POST /api/v1/mobile/affairs/leave，重复提交 409]
 → (m)请假详情（SUBMITTED → COUNSELOR_REVIEW，展示审批进度条）
 → 辅导员待办生成 [t_unified_todo] → （见 4.2 审批链路）
 → (m)收到审批结果消息 [t_unified_message · WORKFLOW_RESULT]
 → (m)请假详情（APPROVED，显示"到期前请销假"）
 → 到期前提醒 [DEADLINE_REMINDER] → (m)详情页「申请销假」→ 上传返校证明
 → 提交销假 [POST /api/v1/mobile/affairs/leave/{id}/cancel-leave → WAIT_CANCEL_LEAVE]
 → 辅导员 PC 05-5 销假确认 /admin/student-affairs/leave/:leaveId/cancel-confirm → 确认 [CLOSED]
 → 学生360时间线出现请假记录（t_student_stage_event）→ 16-1/05-7 统计更新
```

### 4.2 辅导员审批请假（移动端）

```
(m)教师移动工作台 pages/teacher/workbench（待办角标）
 → (m)待办列表（todo_type=LEAVE_APPROVE）
 → (m)请假审批详情 pages/teacher/approvals/detail [GET /api/v1/mobile/teacher/approvals/{taskId}]
 → 同意/驳回（驳回必填原因）[POST /api/v1/mobile/teacher/approvals/{taskId}/approve|reject]
   ├─ 成功：任务消失 → 列表刷新 → 学生收 WORKFLOW_RESULT 消息
   ├─ 已被他人处理：409 APPROVAL_VERSION_CONFLICT → safeToast「该单已处理」→ 刷新列表
   └─ 长假（超阈值）：审批通过后自动流转学院节点 [COLLEGE_REVIEW]，学院学工在 PC 05-4 继续
 → PC 端联动：首页「请假待审」卡计数 -1；05-1 列表状态更新；审计落 t_security_audit_log
```

### 4.3 困难认定（批次 → 终审 → 困难库）

```
学工处 06-1 认定批次列表 → 「新建批次」（06-2 批次详情与配置：学年/时间窗/等级/材料要求）
 → 发布批次 [PUBLISHED_NOTICE 推学生端]
 → (m)学生小程序·困难申请 pages/student/affairs/aid/apply（家庭经济分组表单+材料，强敏感）
 → 提交 [POST /api/v1/mobile/affairs/aid/apply → SUBMITTED]
 → 班级评议（06-5 审核页·CLASS_REVIEW 节点，评议小组录入意见）
 → 辅导员初审（06-5·COUNSELOR_REVIEW，可退回 RETURNED → 学生端修改重交）
 → 学院复审（06-5·COLLEGE_REVIEW）→ 学校终审（06-5·SCHOOL_REVIEW，定困难等级）
 → 06-6 公示管理（PUBLICITY，公示期+异议处理）→ 期满通过 [APPROVED]
 → 06-7 困难学生库更新（等级+有效期）→ 助学金批次(07-2)可引用
 → (m)学生收结果消息 → 学生360时间线沉淀 → 06-8/16-1 统计更新
```

### 4.4 处分登记（登记 → 生效 → 联动）

```
辅导员/学院 08-2 处分登记 /admin/student-affairs/discipline/create
 （学生/违纪事实/类别/依据条款/建议处分等级/材料）
 → 提交 [POST /api/v1/student-affairs/discipline → REGISTERED]
 → 学院初审 08-4 /discipline/:caseId/approve [COLLEGE_REVIEW，可退回 RETURNED 至登记人]

 → （严重处分）学校审批 [SCHOOL_REVIEW]
 → 生效 [EFFECTIVE] → 送达通知（学生 (m)「我的处分」仅见本人生效记录；t_unified_message）

```

### 4.5 风险处置（发现 → 处置 → 关闭）

```

   ├─ 转谈话：跳 10-3 /talk/records/create?riskId=xxx（谈话完成回写风险跟进）
   ├─ 转家校：V1 在处置表单记录联系结果（完整号码需填原因+审计）；P2 跳 12-2
   └─ 升级：ESCALATED → 上级（院/处）待办
 → 关闭 [CLOSED，必填处置结论] → 学生360时间线 → 09-6/16-1 统计更新

```

## 5. 菜单结构与路由守卫建议

1. **菜单三层**：一级「学工中心」→ 二级 16 个功能组（按第 2 节页面树）→ 三级页面。V1 上线仅展示 ★ 菜单，☆ 菜单由权限点控制隐藏（不做"敬请期待"占位页）。
2. **守卫顺序**：登录态（无 token 跳 /login，沿用全站强制登录）→ 权限点（`studentAffairs.<biz>.<action>`，无权限渲染 noPermission 态而非白屏）→ 数据范围（详情类页面后端 `assertCounselorCanAccessStudent` 校验，越权返回 403002/404001，前端渲染 noPermission/notFound 态并落审计）。
3. **demo-school 只读锁**：该租户所有写操作后端 403，前端在写按钮上统一提示「演示环境只读，请前往沙箱环境操作」（sandbox-school 每晚重置）。
4. **审批页防冲突**：所有 `/:id/approve` 页提交携带 workflow task version（乐观锁），409 APPROVAL_VERSION_CONFLICT 统一弹「该任务已被处理」并刷新。
5. **跨模块跳转**（与现有模块）：工作台区块F 跳既有实习（/admin/internship）、毕设（/admin/graduation-design）、就业（/admin/employment）模块对应列表；学业预警处理沿用既有 academic 模块端点；学生360 聚合页扩展现有 mobile teacher `student/{id}` 聚合的 PC 版（03-2），13A 各业务「进360」= 写 StudentStageEvent/域记录被聚合读取。
