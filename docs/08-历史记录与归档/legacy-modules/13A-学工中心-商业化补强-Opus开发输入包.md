# 13A 学工中心商业化补强 Opus 开发输入包

> 本文件由《13A-学工中心-商业化对标审计与补丁建议（第一轮）.md》整理而来，是后续施工的唯一开发输入包。**本轮只新增本文件，未修改任何原始设计文档、未修改审计文件、未触碰 13B 教务中心。**

## 0. 本开发包用途

本文件用于指导后续 Opus / Cursor / Claude 继续开发 **13A 学工中心**。使用者拿到本文件后，应据此判断「做什么、做到哪、做完怎么验收、哪些绝对不能动」。

必须明确以下四条定位：

- **本开发包不是重新设计系统。** 系统设计已在原总册、页面树、API 契约、状态机权限、表单校验、按钮矩阵、移动端、融合设计、参数中心、数据表迁移等文档中完成；本包只做「在已完成设计之上继续补强」的施工指导。
- **本开发包不是演示模型。** 目标是真实销售、真实投标、真实部署、真实上线、真实让学校老师和学生长期使用的商业化学工产品。
- **本开发包不是替代原总册。** 原总册与各设计文档仍是权威设计源；本包是施工映射与顺序，不覆盖、不重写它们。
- **本开发包是把 13A 学工中心从「高频核心底座」继续补强成可销售、可投标、可部署、可验收、可持续迭代的商业化学工产品的施工计划。** 它只指导后续施工，不自动修改任何原设计文档。

一句话：**本包 = 「在高频核心底座上，按施工包 A–G 逐步补强成商业化产品」的施工总纲。**

## 2. 口径纠偏规则

来源：审计第一步《13A 学工中心 V1 口径纠偏表》。核心规则如下。

- **技术义的「冻结」保留。** 契约冻结、状态枚举冻结、命名冻结等表达「不再随意改动的技术基线」，是成熟度体现，**不纠偏、不误改**。
- **范围义的「V1 / V1 必做 / 不做 / 不可做 / 后置 / 只预留 / 范围冻结表 / 不可做清单」必须纠偏。** 这类表达会把系统带成缩水观感，削弱可销售、可投标性。
- **纠偏后的标准表达**：高频核心底座、商业化能力池、补强包、授权启用、配置启用、实施交付、算法接口预留、人工替代流程。
- **禁止全文批量替换。** 只能按审计纠偏表逐项定向修正——因为同一个词（如「冻结」）在技术语境正确、在范围语境才需纠偏，一刀切会误伤技术基线。
- **历史文件名保留原样。** 若引用的历史文件名带「V1 / 后置 / 不做 / 不可做」（如 `13A-13B-V1范围冻结表.md`、`13A-13B-V1不可做与后置能力清单.md`、`13A-学工中心V1范围与开发顺序.md`），文件名可保留，但正文解释必须写清：**这些是历史名称，读取时按「高频核心底座 + 商业化能力池 + 补强包」口径解释，不得按缩水版解释。**

| 历史口径 | 新口径 | 适用场景 | 禁止误用说明 |
|---|---|---|---|
| V1 | 高频核心底座 | 描述已完成、已交付、优先上线的范围 | 不得读成「产品最终范围就这些」 |
| V1 必做 | 当前已完成或优先交付的高频核心能力 | 各业务「⑰ V1必做」小节 | 不得读成「只做这些就够了」 |
| P2 / P3 / 后置 | 商业化能力池中的后续补强能力（补强包 A–G） | 智能排宿、活动、社团、党团、考评、心理测评、家校端等 | 不得读成「没有 / 不会做 / 以后再说」 |
| 不做 / 不可做 | 不在当前高频核心底座中一次性交付，但已纳入商业化能力池，按学校采购需求、实施条件、数据成熟度、授权开关逐步启用 | 红线清单、不可做清单 14 项 | 不得读成「产品做不到」 |
| 只做预留 / 仅预留 / 锁名 | 已完成数据接口、权限、配置、人工替代流程和实施接口位，后续按补强包继续施工 | 预留表、预留规则键、预留接口 | 不得读成「零进度、空占坑」 |
| V1 范围冻结表 | 高频核心底座范围与商业化能力池总表 | 文件 `13A-13B-V1范围冻结表.md` 的定位 | 文件名可留，正文按新口径解释 |
| V1 不可做与后置能力清单 | 商业化能力池实施策略与风险管控清单 | 文件 `13A-13B-V1不可做与后置能力清单.md` 的定位 | 文件名可留，正文按新口径解释 |
| 契约冻结 / 枚举冻结 / 命名冻结（技术义） | **保留不变** | API 契约、状态枚举、表名/键名基线 | 属技术基线，禁止当作范围缩水去纠偏或误改 |

禁止在本包及后续施工正文中使用以下缩水口径：`V1`、`P2`、`P3`、`后置`、`不可做`、`不做`、`只预留`、`演示版`、`MVP`、`小版本`、`样板页`、`以后再说`、`空页面`、`假按钮`、`只有菜单`。（技术义「冻结」不在此禁用之列。）

后续任何一次施工都必须遵守：

- 禁止推翻已有设计。
- 禁止重写全文。
- 禁止改技术架构（多租户隔离、Workflow、scope 引擎、错误码、导入导出管线等保持不动）。
- 禁止把已有成果当废稿。
- 禁止继续使用 V1 / P2 / P3 缩水口径。
- 禁止只做菜单（有菜单必有业务闭环）。
- 禁止空页面。
- 禁止假按钮。
- 禁止无状态机的流程（跨部门/审批业务必须有状态机）。
- 禁止无台账（业务必须能沉淀成可查、可导、可打印的账）。
- 禁止无权限（每个动作必须有权限点 + 数据范围）。
- 禁止无验收标准（每次改动必须给验收口径与验收命令）。
- 禁止未确认就批量改文件。
- 禁止改教务中心（13B 一律不动）。

## 5. 商业化开发总原则

来源：审计第三步《成熟商业学工软件精华设计原则》。每条写清：对应模块、开发时必须落到哪些内容、验收怎么看。

**原则 1 · 领导看驾驶舱，学院看分布，辅导员看待办，学生看进度。**
对应模块：学工首页、辅导员工作台、学生画像、学生移动端。开发落点：首页三角色 preset 已有，补多层级下钻（校→院→专业→班→辅导员）、学生端每类申请进度条与当前节点。验收：每层数字可下钻到明细且对账 0 差异；学生端能看到自己单子到哪、下一步做什么。

**原则 2 · 所有业务必须有台账，不只是流程。**
对应模块：全部（尤其奖助金额、宿舍、谈话、家校、风险）。开发落点：每业务补 ledger 视图 + 导出（脱敏 + 水印）+ 下载审计。验收：每业务可导出台账，字段完整、可按学院/班级/批次汇总。

**原则 3 · 所有申请必须有进度条、当前节点、退回原因、下一步动作。**
对应模块：请假、困难、奖助、处分解除、调宿、学生移动端全部申请页。开发落点：统一 StepBar 组件（节点=状态机审批段），退回原因原文醒目、下一步文案。验收：进度条节点与状态机一致；退回原因可见；下一步引导清晰。

**原则 4 · 所有老师高频动作必须支持批量处理。**
对应模块：辅导员工作台、请假审批、困难初审、奖助审核、风险处置。开发落点：批量催办、批量审批端点 + 幂等。验收：一次批量处理 N 条不产生重复待办/重复单。

**原则 5 · 所有敏感数据必须分级脱敏、授权查看、审计留痕。**
对应模块：困难、心理、家校、处分、画像。开发落点：**已达标（见第 6 节不允许破坏清单），保持即可**；新增字段按敏感矩阵登记。验收：完整号码/身份证/家庭经济/心理明细查看必填原因 + 审计；导出剔除心理明细。

**原则 6 · 所有跨部门业务必须有状态机、责任人、超期提醒。**
对应模块：请假、困难、风险、调宿、归档。开发落点：状态机已有（11 个），补责任人看板化与超期提醒触达。验收：每单有明确责任人、超期自动升级/提醒。

**原则 7 · 所有审批必须支持退回、驳回、撤回、转交、抄送、催办、超时。**
对应模块：全部审批类业务。开发落点：退回/驳回/超时已在状态机；补齐撤回、抄送、催办、转交（风险已有转办）。验收：七类审批动作可用且留痕。

**原则 8 · 所有模块必须有导入模板、导出模板、打印模板、归档规则。**
对应模块：请假、处分、困难、奖助、归档。开发落点：逐业务打印模板（请假条、处分决定书、困难公示、奖助名单）+ 归档编目。验收：打印含审批链 + 水印；导入模板行级校验；归档可编目。

**原则 9 · 所有统计必须能从汇总钻取到明细。**
对应模块：首页、统计分析、班级。开发落点：钻取从列表扩展到多层级；首页-列表对账 0 差异保持。验收：任一指标可逐层下钻到学生明细，数字对账 0 差异。

**原则 10 · 所有学生高频业务必须移动端优先。**
对应模块：学生移动端全部。开发落点：弱网草稿全覆盖、防重复、状态提示、敏感不本地缓存。验收：弱网不丢草稿不重单；敏感字段不落本地存储。

**原则 11 · 所有辅导员业务必须围绕学生画像和今日待办聚合。**
对应模块：辅导员工作台、学生画像。开发落点：待办紧急度排序、同生多风险合并、长期未跟进/待回访卡、画像限制项与摘要。验收：工作台一屏见「今天处理谁」；画像一屏见「这个学生什么情况、受什么限制」。

**原则 12 · 所有风险必须能分派、处置、升级、关闭、重开。**
对应模块：风险预警、心理。开发落点：分派/处置/升级/关闭已有，补重开（REOPEN）、领导督办、多风险合并。验收：风险可重开回 PROCESSING 并留痕；督办生成待办 + 抄送上级。

**原则 13 · 所有规则必须参数化，不要写死。**
对应模块：全部。开发落点：**已达标（56 项参数中心 + safe_rule 兜底，见第 6 节），保持即可**；新增阈值走参数键。验收：阈值改配置不改代码；非法值有兜底。

**原则 14 · 所有业务必须考虑学校实施时的数据初始化、模板、权限分配。**
对应模块：全部（实施交付层）。开发落点：逐业务实施初始化清单（导谁的数据、配哪些权限、初始化哪些模板）。验收：新学校可按清单初始化并跑通试点。

**原则 15 · 所有模块都要能形成销售话术和投标响应功能描述。**
对应模块：全部。开发落点：口径纠偏后，每模块产出「投标响应功能描述 + 底座已交付 + 补强路线」一句话。验收：每模块能被投标响应文档直接引用，无「后置/不做」缩水词。

## 8. 施工包总览

顺序：**A → B → C → D → E → F → G**。原则：高频优先、销售优先、实施优先、算法接口预留最后。

- **施工包 A：学工高频体验补强** —— 首页/工作台/画像/请假/谈话/风险做到成熟商业软件级顺手。
- **施工包 B：学工台账与报表补强** —— 请假/困难/奖助/处分/宿舍/风险/谈话/家校/归档补出台账、导出、打印、明细钻取。
- **施工包 C：学生与教师移动端补强** —— 学生少跑腿，辅导员手机能审批、处置风险、记录谈话、联系家长。
- **施工包 D：奖助勤贷补与处分联动补强** —— 项目库、批次、金额台账、资格校验、处分影响项、解除后限制释放。
- **施工包 E：宿舍与第二课堂补强** —— 宿舍检查、夜不归宿、文明寝室、活动、志愿、社团、党团、第二课堂最低闭环。
- **施工包 F：辅导员考评与学工归档补强** —— 辅导员工作量、风险处置、谈话、家校、归档、班级月报沉淀成管理与投标卖点。
- **施工包 G：算法型与集成型能力预留** —— 智能排宿、心理测评接入、家长通知、行为风险预测只补输入/约束/人工确认/失败兜底/接口预留。

**为什么先做 A**：辅导员工作台与学生画像是使用频次最高、最能立刻体现「减负」的场景，也是 demo 与投标最先被检验的地方；A 全部为「加字段/加端点/加卡片」，对底座零破坏、风险最低、见效最快。

**为什么 B/C 紧跟 A**：A 让系统「好用」，B 让系统「可交账」（台账/报表/打印是学校验收与投标响应刚需），C 让高频场景「装进手机」（学生少跑腿、辅导员移动办公）。A 产出的工作量摘要、限制项、进度条正是 B 的台账口径与 C 的移动展示基础，三者构成「好用 + 可交账 + 移动化」的销售闭环。

**为什么 D/E/F/G 不能抢在 A 前面**：
- D（奖助处分联动）依赖 A 的画像限制项与 B 的金额台账口径，否则资格校验与限制释放无处呈现。
- E（宿舍二课）是新增业务闭环，价值高但非最高频，抢在 A 前会让「基础都不顺手就铺新业务」，稀释试点体验。
- F（考评归档）必须复用 A 的 `workload-summary` 同一 stats 函数，否则出现两套数；数据未沉淀一段时间，考评也无意义。
- G（算法/集成）依赖前面业务沉淀数据与现场确认条件，且只做接口位与人工兜底，天然应最后；提前做会吞档期、产出假智能。

**每个施工包如何不破坏现有高频核心底座**：一律「加字段 / 加端点 / 加卡片 / 启用已锁名预留表 / 复用既有管线」，不改既有状态机主结构（仅 P-05 增 REOPEN 态）、不改既有表主结构、不动 scope 引擎与错误码、不开双写入口、不改 13B。每包完成后跑回归红线四项：既有 pytest 全绿 / demo 只读锁 / 教师范围机制 / 既有端点快照，零违反。

## 17. 文件修改策略

后续每一次施工必须遵守：

1. **一次只改一个施工包相关文件。** 不把多个施工包的改动混在一起。
2. **不跨施工包乱改。** A 的施工不去动 E 的文档。
3. **每次改动必须列出文件清单。** 改了哪些文件一目了然。
4. **每次改动必须有验收命令。** 见第 16 节验收模板。
5. **每次改动必须说明没有破坏当前高频核心底座。** 对照第 6 节清单逐条确认。
6. **每次改动必须同步 README / 契约 / 页面 / 权限 / 测试说明。** 接口变更同步 API 契约，页面变更同步页面树与按钮矩阵，权限变更同步状态机权限矩阵。
7. **未确认前不得自动提交。** 不 `git commit`、不 `git push`。
8. **发现无关文件变动必须立即停止并报告。** 不自行处理无关改动（如本轮工作区已存在的 99-老系统、00-新设计、13B 等无关改动，只报告不处理）。
9. **涉及技术义冻结内容时，必须保持原冻结基线，不得误改。** 契约冻结、枚举冻结、命名冻结按原技术基线保留。
10. **涉及范围义 V1 / 后置 / 不做口径时，必须按审计纠偏表定向纠偏。** 逐项修正，禁止全文批量替换。
