1. **13A 新表前缀 `t_affairs_*`**（与此前文档一致，不变）。

## 三、13A 建议表全清单（V1 新建 26 张 + 加列扩展 2 张 + P2 预留 5 张）

**读法说明（三/四章通用）**：
- 租户字段：**所有新表均含 tenant_id BIGINT NOT NULL（TenantMixin），不再逐行标注**；公共字段（总纲 3/4 条）默认全套，append-only 表按总纲 4 例外。
- "复用现有表"列：`新建` = 无可复用；否则写明复用/回写/回链哪张既有表。
- "审计"列：`SEC` = 敏感读取或写操作调 audit_log.record 落 t_security_audit_log；`TRAIL` = 同步写 t_affairs_audit_trail（append-only）。全部写操作默认 SEC+TRAIL，仅特殊点单独注明。
- "360"列：是 = 终态写 t_student_stage_event（source_module='student-affairs'）或被 teacher student/{id} 聚合读取。
- 附件一律 t_file_object（总纲 9），不再逐表列 file 字段。

## 五、迁移策略

### 5.1 建表方式（Alembic 为准，metadata 兜底）

- **现状**：`backend/app/db/init_db.py` 在 DB_ENABLED=true 时 `metadata.create_all`（测试/开发环境自动建表）；Alembic 已初始化（`backend/alembic/versions/0001_init_core_tables.py`、`0002_tenant_portal_config.py`）。
- **裁定**：13A/13B 全部 DDL 变更（新表+加列+索引）**必须落 Alembic revision**，生产以 `alembic upgrade head` 为唯一建表通道；模型文件新增 `backend/app/models/affairs.py`（13A）与 `backend/app/models/academic_affairs.py`（13B），注册进 metadata 后 create_all 在测试环境自然覆盖（两通道结构一致由 pytest 的建表冒烟用例保证）。
- **revision 切分**：按阶段一个 revision（0003_13ab_p0_naming_noop 起，每阶段建当期表，禁止一个 revision 打包全部 43 张），每个 revision 必须提供可执行的 downgrade。
- 加列一律 nullable + 默认值，禁止对存量大表做 NOT NULL 回填锁表；PostgreSQL 加 nullable 列为元数据操作，秒级。

### 5.2 存量数据 backfill 规则

| 对象 | 规则 |
|---|---|
| **t_cs_leave 状态映射（核心）** | 新列 affairs_status 按旧 status 一次性回填：`PENDING_REVIEW → COUNSELOR_REVIEW`、`APPROVED → APPROVED`（已过期且未销假的 APPROVED 行，end_time < 今天 → `OVERDUE`，否则保持 APPROVED；已明显完结的历史学期行 → `CLOSED`，界限日期做成脚本参数）、`RETURNED → RETURNED`。student_id 经 `t_cs_service_student.student_id`（为空则按 student_no 匹配 t_student_profile）回填；匹配不上的行 affairs_status 照填、student_id 留 NULL 并出对账清单人工处理。days 由 start_time/end_time 计算回填；workflow_instance_id 存量为 NULL（历史单不补流程实例，详情页显示"历史审批：reviewer/review_time 旧字段"） |
| t_cs_discipline | 不迁移。存量行 source_case_id=NULL 视为"历史台账行"；13A 上线后新处分一律 case→投影 |
| t_acad_warning 加列 | source_code/rule_code 存量 NULL（按既有 warn_type 可选做一次映射回填：MULTI_FAIL→FAIL_COURSE 等，非必需） |
| 宿舍初始化 | t_orientation_student 的 building/room/dorm_status → 生成 t_affairs_dorm_building/room/bed + 占用行，与 t_cs_dorm_record 三方对账（dry-run 差异报告 → 人工确认 → 写入），执行一次，此后台账为唯一事实源 |
| 组织三表/学籍 | 零迁移：加列 nullable；student_status 存量 NORMAL 语义即"在籍"，不回填 |
| 所有 backfill 脚本 | 幂等可重跑（以自然键/回链列判重）、先 dry-run 输出差异行数、整批事务、执行记录落 t_security_audit_log |

### 5.3 双状态列并行期（t_cs_leave 专项）

1. **写侧单点**：13A 上线起，新请假单只经 13A 服务写入，同一事务内同时维护 affairs_status（真相）与旧 status（投影：COUNSELOR_REVIEW/COLLEGE_REVIEW/STUDENT_AFFAIRS_REVIEW→PENDING_REVIEW；APPROVED/CLOSED/ARCHIVED→APPROVED；REJECTED/RETURNED→RETURNED；其余过程态→PENDING_REVIEW），保证既有 campus-service 读端点与既有 pytest 零改动全绿。
2. **旧写端点冻结**：既有 campus-service 的 approve/return/批量端点保留路径、内部转发 13A 新流程（或返回引导语义），不允许双入口各写各的。
3. **并行期时长**：13A-P8 验收通过后一个迭代内下线旧写端点；旧 status 列**长期保留**为投影列（不删列，避免破坏历史查询与报表）。
4. **对账**：每日任务比对 affairs_status→旧 status 投影规则是否一致，不一致行告警；P8 验收含"对账 0 差异"门禁。
5. 处分域同理为"主档(case)→投影(t_cs_discipline 行)"并行，一致性对账口径：EFFECTIVE 的 case 数 = source_case_id 非空且 record_status=ACTIVE 的投影行数。

### 5.4 回滚方案

| 场景 | 回滚动作 |
|---|---|
| 新表阶段性回滚 | 停用相应路由（feature 开关/路由注销）→ `alembic downgrade` 删表；新表数据为新增业务无历史包袱，删除前自动导出快照留档（export 管线） |
| t_cs_leave 加列回滚 | 新列全 nullable：停用 13A 请假路由 → 恢复旧写端点 → 新列保留不删（无害）或 downgrade 删列；期间产生的新单在旧 status 列有投影值，旧链路可继续处理 |
| backfill 回滚 | affairs_status/student_id 回填可整列置 NULL 重跑（幂等）；宿舍初始化回滚=删除 source 标记为 ORIENTATION_INIT 的台账行 |
| 投影回滚 | t_cs_discipline 按 source_case_id 非空删投影行即可恢复原状 |
| student_status 枚举回滚 | 新枚举值只入白名单不改存量行；回滚=禁用异动路由，已生效 SUSPENDED 等行人工经单一入口冲正（append-only 流水保留全程证据） |
| 红线 | 任何回滚不得物理删除 append-only 表（*_audit_trail/level_history/handle_record/contact_log/StageEvent）；回滚操作本身必须留审计 |
