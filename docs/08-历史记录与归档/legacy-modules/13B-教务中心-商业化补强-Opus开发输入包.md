## 0. 本开发包用途

本文件用于指导后续 Opus / Cursor / Claude 继续开发 **13B 教务中心**。使用者据此判断「做什么、做到哪、做完怎么验收、哪些绝对不能动」。

- **本开发包不是重新设计系统。** 系统设计已在原总册、页面树、API 契约、状态机权限、表单校验、按钮矩阵、移动端、融合设计、参数中心、数据表迁移等文档中完成；本包只做「在已完成设计之上继续补强」的施工指导。
- **本开发包不是演示模型。** 目标是真实销售、真实投标、真实部署、真实上线、真实让教务处、二级学院、教学秘书、教师、辅导员、学生长期使用的商业化教务产品。
- **本开发包不是替代原总册。** 原总册与各设计文档仍是权威设计源；本包是施工映射与顺序，不覆盖、不重写它们。
- **本开发包是把 13B 教务中心从「高频核心底座」继续补强成可销售、可投标、可部署、可验收、可持续迭代的商业化教务产品的施工计划。** 它只指导后续施工，不自动修改任何原设计文档。

一句话：**本包 = 「在高频核心底座上，按施工包 A–I 逐步补强成商业化教务产品」的施工总纲。**

## 2. 口径纠偏规则

来源：审计第一步《13B 教务中心 V1 口径纠偏表》。核心规则：

- **技术义的「冻结」保留。** API 契约冻结、状态枚举冻结、字段命名冻结、路由命名冻结表达「不再随意改动的技术基线」，是成熟度体现，**不纠偏、不误改**。
- **范围义的「V1 / 不做 / 不可做 / 后置 / 只预留」必须纠偏。** 这类表达会把系统带成缩水观感，削弱可销售、可投标性。
- **纠偏后标准表达**：高频核心底座、商业化能力池、补强包、授权启用、配置启用、实施交付、算法接口预留、人工替代流程。
- **禁止全文批量替换。** 只能按审计纠偏表逐项定向修正——同一个词（如「冻结」）技术语境正确、范围语境才纠偏，一刀切会误伤技术基线。
- **历史文件名保留原样。** 若引用的历史文件名带「V1 / 后置 / 不做 / 不可做」（如 `13A-13B-V1范围冻结表.md`、`13A-13B-V1不可做与后置能力清单.md`、`13B-教务中心V1范围与开发顺序.md`），文件名可留，但正文必须解释：**这些是历史名称，读取时按「高频核心底座 + 商业化能力池 + 补强包」口径解释，不得按缩水版解释。**

| 历史口径 | 新口径 | 适用场景 | 禁止误用说明 |
|---|---|---|---|
| V1 | 高频核心底座 | 描述已完成、已交付、优先上线的范围 | 不得读成「产品最终范围就这些」 |
| V1 必做 | 当前已完成或优先交付的高频核心能力 | 各业务「E17/⑰ V1必做」等小节 | 不得读成「只做这些就够了」 |
| P2 / P3 / 后置 | 商业化能力池中的后续补强能力（补强包 A–I） | 排课/选课/考务/成绩录入审核发布/补缓重免/教材/评价/教室/上报 | 不得读成「没有 / 不会做 / 以后再说」 |
| 不做 / 不可做 | 不在当前高频核心底座中一次性交付，但已纳入商业化能力池，按学校采购需求、实施条件、数据成熟度、授权开关逐步启用 | 开发顺序 §1.2「V1 明确不做清单」、不可做清单 | 不得读成「产品做不到」 |
| 只做预留 / 仅预留 / 锁名 | 已完成数据接口、权限、配置、人工替代流程和实施接口位，后续按补强包继续施工 | 预留表、预留规则键、接口占位 | 不得读成「零进度、空占坑」 |
| V1 范围冻结表 | 高频核心底座范围与商业化能力池总表 | 文件 `13A-13B-V1范围冻结表.md` 的定位 | 文件名可留，正文按新口径解释 |

## 5. 商业化开发总原则

来源：审计第三步《成熟商业教务系统精华设计原则》。每条写：对应模块、开发时必须落到哪些内容、验收怎么看。

**原则 1 · 领导看教学运行驾驶舱，教务处看全校，学院看本院执行，教师看授课与成绩，学生看课表/考试/成绩/毕业风险。**
对应模块：教务首页、移动端。开发落点：四角色 preset 已有，补运行执行率卡（教学任务执行率/排课完成率/成绩提交率/毕业预审通过率）+ 校→院→专业→年级→班→课程→教师多层下钻。验收：每层可下钻到明细且对账 0 差异。

**原则 2 · 所有教务业务必须有台账，不只是流程。**
对应模块：全部（尤其学籍、教学任务、成绩、考务）。开发落点：每业务补 ledger 视图 + 导出（脱敏+水印）+ 下载审计。验收：每业务可导出台账，可多维汇总。

**原则 3 · 所有申请必须有进度条、当前节点、退回原因、下一步动作。**
对应模块：学籍异动、调停课、缓考、成绩更正、毕业申诉、选课。开发落点：统一 StepBar 组件（节点=状态机审批段），退回原因原文、下一步文案。验收：进度条与状态机一致；退回原因可见。

**原则 4 · 所有老师高频动作必须支持批量处理。**
对应模块：成绩录入审核发布、教学任务确认、考务、注册核对。开发落点：批量确认/审核/发布/导入 dry-run。验收：批量处理 N 条不产生重复单/重复任务。

**原则 5 · 所有教学运行数据必须支持按学年学期/学院/专业/班级/课程/教师多维查询。**
对应模块：教务首页、统计分析、成绩、教学任务。开发落点：stats 走 getAcademicScope，独立分析页 8 维交叉。验收：任一指标可按 8 维过滤下钻。

**原则 6 · 所有跨部门业务必须有状态机、责任人、超期提醒。**
对应模块：异动、调停课、缓考、成绩审核、毕业审核。开发落点：14 个状态机已达标，补责任人看板化与超期提醒触达。验收：每单有责任人、超期自动升级/提醒。

**原则 7 · 所有审批必须支持退回、驳回、撤回、转交、抄送、催办、超时。**
对应模块：全部审批类。开发落点：退回/驳回/撤回已在状态机，补齐转交/抄送/催办。验收：七类动作可用且留痕。

**原则 8 · 所有模块必须有导入模板、导出模板、打印模板、归档规则。**
对应模块：课表、成绩、考务、毕业、培养方案。开发落点：课表/成绩单/准考证/毕业名单打印模板 + 归档编目。验收：打印含审批链+水印；导入行级校验。

**原则 9 · 所有统计必须能从汇总钻取到明细。**
对应模块：首页、统计、成绩、排课。开发落点：钻取扩展到课程→教师→学生全链；首页-列表对账保持。验收：任一率可下钻到具体课程/教师/学生。

**原则 10 · 所有学生高频业务必须移动端优先。**
对应模块：学生移动端全部。开发落点：考试/选课/补缓重申请补齐，弱网草稿、防重复、敏感不缓存。验收：弱网不丢草稿不重单；敏感不落本地。

**原则 11 · 所有教师高频业务必须围绕「我的教学任务/我的课表/我的成绩录入/我的考试安排」聚合。**
对应模块：教师移动端、成绩、考务、教学任务。开发落点：今日课程/授课班级已有，补成绩录入/监考/任务确认。验收：教师一屏见「今天上什么课、录哪门成绩、监考什么」。

**原则 12 · 所有教务风险必须能预警、分派、处置、关闭、重开。**
对应模块：学业预警、毕业风险。开发落点：SM-13 增 REOPEN，13A/13B 协同责任明确。验收：预警可重开留痕；跨中心分派清晰。

**原则 13 · 所有规则必须参数化（校历、节次、成绩构成、补考、重修、毕业审核规则）。**
对应模块：全部。开发落点：参数中心已含 grade.compose/gpa.formula/makeup.scoreRule/retake.maxCount/warning.*/graduation.conditions，保持并补齐各类预警规则键。验收：规则改配置不改代码；非法值兜底。

**原则 14 · 所有业务必须考虑学校实施时的数据初始化、模板、权限分配。**
对应模块：全部（实施交付层）。开发落点：逐业务实施初始化清单（导哪些基础数据、配哪些权限、初始化哪些模板）。验收：新学校可按清单初始化并跑通试点。

**原则 15 · 所有模块都要能形成销售话术和投标响应功能描述。**
对应模块：全部。开发落点：口径纠偏后，每模块产出「投标响应功能描述 + 底座已交付 + 补强路线」。验收：每模块能被投标响应文档直接引用，无「P2/不做/后置」缩水词。

## 8. 施工包总览

顺序：**A → B → C → D → E → F → G → H → I**。原则：高频优先、销售优先、实施优先、算法接口预留最后。

- **施工包 A：教务高频运行体验补强** —— 教务首页/学籍/课表/调停课/成绩查询/学业预警做到成熟商业软件级顺手。
- **施工包 B：学籍注册与基础数据补强** —— 学年学期/校历/作息节次/学院专业班级/学籍/注册/异动/基础台账。
- **施工包 C：培养方案、课程库与教学任务补强** —— 方案版本/课程库/教学计划/教学任务/合班拆班/教师确认/学院审核/教务发布。
- **施工包 D：课表、调停课与排课人工闭环补强** —— 人工排课/冲突检测/课表发布/调停课审批/变更通知/回滚；排课算法只做接口预留和建议草稿。
- **施工包 E：选课、考务、补缓重免补强** —— 选课轮次/容量/限制/退补选/候补/补考/缓考/重修/免修/考务安排/人工排考闭环。
- **施工包 F：成绩全流程、学业预警与毕业审核补强** —— 成绩录入/审核/发布/更正/锁定/台账/预警/毕业预审/正式审核/问题清单/人工调整。
- **施工包 G：教材、资源、评价、质量与归档统计补强** —— 教材/教学资源/教室资源/教学评价/教学质量/教务归档/统计分析。
- **施工包 H：移动端教务服务补强** —— 学生端课表/选课/考试/成绩/补缓重申请/毕业预审；教师端课表/调停课/成绩录入/监考/任务确认。
- **施工包 I：算法型与集成型能力预留** —— 自动排课/智能排考/抽签选课/欠费接口/统一消息/第三方评价与教学资源接口，只补输入/约束/冲突检测/人工确认/失败兜底/回滚/接口预留。

**为什么先做 A**：教务首页运行驾驶舱、学籍、课表、成绩查询、学业预警是使用频次最高、最能立刻体现「运行可视 + 减负」的场景，也是 demo 与投标最先被检验处；A 全部为「加字段/加端点/加卡片 + 一个 REOPEN 态」，对底座零破坏、见效最快。

**为什么 B/C/D 紧跟 A**：教务是「数据前置」极强的域——B 补齐学年学期/校历/作息/学籍/组织这些**全域前置基础数据**（无校历发布则排课/考试/课表无从谈起），C 补齐培养方案/课程库/教学任务（排课与毕业审核的依据），D 在 B/C 数据就绪后补课表/调停课/人工排课闭环。这条链是教学运行主干的自然施工序，缺一环下游无法开工。

**为什么 E/F/G/H/I 不能抢在 A 前面**：
- E（选课/考务/补缓重免）依赖 D 的课表与教室数据、C 的教学任务，抢先则无排课无考场。
- F（成绩/预警/毕业）依赖 C 的方案、E 的选课/补考名单，成绩回写与毕业审核取数才成立。
- G（教材/资源/评价/归档统计）是支撑与沉淀类，价值高但非最高频，且归档/统计需前面业务先产生数据。
- H（移动端）随各补强包上线逐入口点亮，抢先会渲染空壳入口。
- I（算法/集成）依赖前面业务沉淀数据与现场确认条件，且只做接口位与人工兜底，天然最后；提前做会吞档期、产出假智能。

**每个施工包如何不破坏现有高频核心底座**：一律「加字段 / 加端点 / 加卡片 / 启用已锁名预留表 / 复用既有管线」，不改既有状态机主结构（仅 SM-13 增 REOPEN）、不改 t_acad_* 结果层主结构（成绩仅加 source 列、经发布/更正/补录三口回写）、不动 scope 引擎与错误码、不改 /api/v1/academic 既有端点、不改 13A。每包完成后跑回归红线：既有 pytest（含 203 条 academic 回归）全绿 / demo 只读锁 / 教师范围机制 / 既有端点快照，四项零违反。

## 12. 文件修改策略

后续每一次施工必须遵守：

1. **一次只改一个施工包相关文件。** 不把多个施工包的改动混在一起。
2. **不跨施工包乱改。** A 的施工不去动 G 的文档。
3. **每次改动必须列出文件清单。** 改了哪些文件一目了然。
4. **每次改动必须有验收命令。** 见第 11 节验收模板。
5. **每次改动必须说明没有破坏当前高频核心底座。** 对照第 6 节清单逐条确认。
6. **每次改动必须同步 README / 契约 / 页面 / 权限 / 测试说明。** 接口变更同步 API 契约，页面变更同步页面树与按钮矩阵，权限变更同步状态机权限矩阵，状态变更同步状态机文档。
7. **未确认前不得自动提交。** 不 `git commit`、不 `git push`。
8. **发现无关文件变动必须立即停止并报告。** 不自行处理无关改动（如本轮工作区已存在的 99-老系统、00-新设计、13A 前几轮产物、13B 其它文档等无关改动，只报告不处理）。

10. **涉及范围义 V1 / 后置 / 不做口径时，必须按审计纠偏表定向纠偏。** 逐项修正，禁止全文批量替换。
