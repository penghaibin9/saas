### 1.3 矩阵共用铁律

1. **待办与消息只有一份**：任何端产生的待办写 `t_unified_todo`、通知写 `t_unified_message`（backend/app/models/message.py），任何端展示都从这两张表读，禁止端内自建消息/计数表。
2. **审批只有一套**：新审批 = 新 workflow_code + node_code，实例任务落 `t_workflow_instance` / `t_workflow_task`（backend/app/models/approval.py），PC 走 `/api/v1/approvals/*`，移动走 `/api/v1/mobile/teacher/approvals/*` 包装，同一 task version 乐观锁跨端生效。
3. **范围只有一个函数**：六端教师侧列表过滤与写校验共用 `resolve_teacher_scope` / `can_teacher_view_student`（backend/app/services/mobile_teacher_service.py），13A/13B 的 scope 函数是其封装（新增 scope_type=DORM_BUILDING/PSY_STUDENT/AID_STUDENT 等枚举扩展）。
4. **品牌只有一处**：`t_tenant_brand_config`（backend/app/models/tenant.py）经 `GET /api/v1/authz/tenant/brand` 下发，PC/门户/小程序统一消费，禁止硬编码校名。
5. **模块授权只有一处**：平台侧套餐/租户授权 → `GET /api/v1/authz/modules`（1.12）下发六端；关闭即各端按本文 §3 降级口径表现。

## 2. 数据联动设计（10 条）

> 每条：字符画流向图 + 落表说明。所有「→消息/待办」均指写 `t_unified_message` / `t_unified_todo`；所有「→360」均指写 `t_student_stage_event`（或域记录）被学生360聚合读取（现状聚合端点：mobile teacher `student/{id}`，13A/13B 扩展其区块）。

### L-01 学工请假 → 在校服务 / 360 / 消息 / 待办 / 风险

```
(m)学生提交请假 ──写──> t_cs_leave（扩展状态机，单一真相）
        │
        ├──> t_workflow_instance/task（AFFAIRS_LEAVE 流程）──> t_unified_todo（辅导员待办，E3/E5 同源展示）
        ├──> t_unified_message（学生回执/审批结果 WORKFLOW_RESULT）
        ├──通过──> t_student_stage_event（360 时间线「请假」条目）
        ├──到期未销──> OVERDUE ──> t_affairs_risk_record（来源=请假异常）──> 风险待办推辅导员
        └──在校服务侧──> 既有 campus-service 列表/统计同表直读（不同视图同一数据）
```

| 落表 | 说明 |
|---|---|

## 3. 跨端一致性矩阵（8 流程）

> 每流程固定回答 8 问。通用机制先行声明，流程表只写差异：
> ① 单一真相表——业务状态只存一张表（§2 各条「唯一真相」），任何端读同一行；② 统一待办/消息表——t_unified_todo/t_unified_message，处理动作在服务端置状态，各端角标 onShow 重拉、点开即调「标已读」；③ 无本地假状态——移动端 realFirst 不兜底假数据、提交锁只防连点、乐观锁 version 防跨端并发（409 APPROVAL_VERSION_CONFLICT），前端禁止本地扣减后不校准。

### 3.9 一致性的技术保障（要点）

1. **单一真相表**：每个业务对象仅一张状态表（请假=t_cs_leave 扩展、预警=t_acad_warning、成绩=t_acad_grade、主档=t_student_profile、处分=discipline case、审批=t_workflow_task），跨域联动一律「引用+实时读」，禁止字段拷贝；360 是聚合视图不是副本表。
2. **统一待办/消息表**：t_unified_todo（assignee_id/todo_type/source_module/status）+ t_unified_message（receiver_id 精确投递，已有标已读端点）。角标=服务端计数，前端 onShow 重拉校准；「处理完成」由服务端置状态驱动各端消失，不靠前端删项。
3. **无本地假状态**：小程序 realFirst 业务错误透出不兜底；写失败保留表单不伪造成功；审批/处置携带 version 乐观锁，跨端并发以 409 收敛到服务端最新状态；demo-school 只读锁在后端拦截（403），前端仅做文案引导。
4. **同一鉴权与范围**：六端同一 token 体系（userId/tid/activeContextId），教师范围同一 resolve_teacher_scope，学生身份一律从 token 取（studentNo），越权 403/404+审计——「看得见=能处理」在读写两侧同函数保证。
5. **同一品牌与授权下发**：tenant/brand 与 authz/modules 是六端渲染的公共前置数据；模块关闭的降级表现统一为「菜单/宫格不渲染 + 写 API 403 + 历史只读 + 待办停发」，各流程差异见上表。
