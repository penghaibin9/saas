## 1. 全局设计约定（所有 13A 业务共用，不得各自另造）

### 1.1 复用既有底座（硬约束，来自速查）

1. **审批**：一律走既有 Workflow —— 每个业务一个新 `workflow_code`（如 `AFFAIRS_LEAVE`），节点为 `node_code` 序列；实例/任务落 `t_workflow_instance` / `t_workflow_task`（version 乐观锁，重复处理返回 409 APPROVAL_VERSION_CONFLICT）；节点流转逻辑写在学工自己的 service 内。**不新建任何审批表**（需求中的 `affairs_*_approval / *_review` 类对象凡属"审批动作"均映射到 t_workflow_task，见 §2）。
2. **待办与消息**：只写 `t_unified_todo`（去重键 source_module+source_biz_id+todo_type+assignee_id）与 `t_unified_message`（receiver_id 精确到人）。消息类型仅允许 8 种：`WORKFLOW_TODO / WORKFLOW_RESULT / RISK_ALERT / DEADLINE_REMINDER / STATUS_CHANGED / RETURNED_NOTICE / PUBLISHED_NOTICE / ARCHIVE_NOTICE`。**禁止自建消息表、禁止新造消息类型**。
3. **审计**：操作审计走 `app.services.audit_log.record(action, resource, detail, result)` → `t_security_audit_log`；域级留痕新增 `t_affairs_audit_trail`（append-only，同 t_*_audit_trail 模式）。必审计动作：审批/驳回/退回、查看完整敏感字段、导出、归档、越权尝试。
4. **数据范围**：统一封装 `getStudentAffairsScope(user)` = 对既有 `resolve_teacher_scope(user)` 的**包装扩展**，底表仍是 `t_teacher_student_scope`，新增 scope_type 枚举值 `DORM_BUILDING`（宿管楼栋）、`PSY_STUDENT`（心理授权学生）、`AID_STUDENT`（资助业务学生）；`canAccessAffairsStudent` 复用 `can_teacher_view_student` 四路判定（学号/班级/学院/导师）+ 新两路（楼栋/授权名单）。原则不变：**看得见 = 能处理**，列表过滤与写校验共用同一函数，越权 403 + 审计。
5. **导入导出**：注册新 domain 到既有管线。导入 `/api/v1/import/domain/{domain}/validate|confirm`（dry-run 行级错误→整批事务，5000 行/20MB）；导出 `/api/v1/export/domain/{domain}`（用途必填≥5 字、脱敏列、首行水印、t_export_task 留痕、5 次/分、5000 行）。13A 注册 domain：`affairs_leave / affairs_aid / affairs_funding / affairs_discipline / affairs_dorm_assign / affairs_dorm_inspection / affairs_archive`。
6. **响应与错误码**：`{ code(数字), bizCode(字符串), message, data, traceId, timestamp }`；401001/403001/403002/404001/409001/422001/429001/400001；业务错误绝不 500。
7. **端与路由**：PC 仅教职工（require_staff），学生一律小程序。后端：PC `/api/v1/student-affairs/*`，学生 `/api/v1/mobile/affairs/*`，教师移动 `/api/v1/mobile/teacher/affairs/*`（沿 mobile_teacher 包装：范围校验+审计+409）。PC 路由 `/admin/student-affairs/*`。权限点 `studentAffairs.<biz>.<action>`。
8. **可配置规则**（长假天数阈值、公示天数、逾期宽限、材料必传规则等）：接入既有平台规则中心（/admin/platform + safe_rule），**不新建管理端**。
9. **敏感字段**：落库 `*_encrypted`，出口默认脱敏（_mask_phone/_mask_id_card 及金额/病因等同型掩码）；查看完整值 = 字段权限 + 填写原因 + 审计。
10. **学生 360 沉淀**：统一定义为——业务终态时写一条 `t_student_stage_event`（event_type 用 `AFFAIRS_*` 前缀）+ 域记录本身可被既有 mobile teacher `student/{id}` 聚合端点读取。聚合端点扩展方式：在其聚合器中追加 affairs 段（leave/aid/discipline/risk/talk/dorm 六段，各段带权限裁剪）。**不新建 timeline 表**——需求中的 `student_affairs_events / student_360_timeline` 即映射为 t_student_stage_event 的扩展用法；`student_risk_records` 映射为 t_affairs_risk_record（§2）。
11. **公共字段**：所有新表 `t_` 前缀 snake_case、BIGINT 主键、tenant_id/created_at/updated_at/created_by/updated_by/is_deleted/version。demo-school 只读锁、到期租户只读中间件对 13A 全部写操作同样生效。

### 1.2 状态机通用约定

- 状态字段名统一 `biz_status`；状态变更必须经 service 层状态机函数（校验合法转移，非法转移 409001 DATA_CONFLICT），并写 t_affairs_audit_trail。
- `RETURNED`（退回可改）与 `REJECTED`（驳回终态）语义区分：退回后单据回到**发起人可编辑态**，保留单号与历史，修改后重新进入首个审批节点；驳回后单据终结，只能新发起。
- 所有审批动作请求体带 `version`（乐观锁）+ `request_id`（幂等）+ 驳回/退回必带 `reject_reason ≥ 5 字`。

### 1.3 统计接入约定

13A 指标一律扩展既有 `stats_service` 聚合（`/api/v1/stats/*` 模式，租户内实时 count），dashboard 按角色 preset 出卡片；辅导员维度走 §1.1-4 scope 过滤。每个指标在各业务「数据中心统计」小节按**口径/来源表/更新频率/角色过滤/可下钻**五要素定义。

### 1.4 统一消息与待办映射总表（各业务只能从本表取用，新增须先扩本表）

| 触发场景 | 消息类型 | 接收人 | 同步待办（t_unified_todo.todo_type） |
|---|---|---|---|
| 审批任务生成 | WORKFLOW_TODO | 当前节点处理人 | AFFAIRS_APPROVE（action_url 指审批页） |
| 审批终审通过/驳回 | WORKFLOW_RESULT | 申请人（学生/发起人） | 无（关闭原待办） |
| 单据被退回 | RETURNED_NOTICE | 申请人 | AFFAIRS_RESUBMIT |
| 批次/公示/岗位发布 | PUBLISHED_NOTICE | 范围内学生/角色 | 无 |
| 销假到期、复核到期、跟进到期、贷款毕业确认、归档临期 | DEADLINE_REMINDER | 学生和/或责任教师 | 视场景生成（如 AFFAIRS_CANCEL_LEAVE） |
| 风险生成/升级/夜不归宿 | RISK_ALERT | 分派处理人/上级 | RISK_HANDLE |
| 状态变化知会（家长通知、检查异常同步、教务联动、绑定辅导员等） | STATUS_CHANGED | 相关人 | 无 |
| 归档完成 | ARCHIVE_NOTICE | 学工处/学院/辅导员 | 无 |
| 归档补缺 | WORKFLOW_TODO | 辅导员 | AFFAIRS_ARCHIVE_SUPPLEMENT |
| 处分送达 | WORKFLOW_TODO | 辅导员 | AFFAIRS_DELIVER |

约定：待办完结由业务 service 在动作成功的同一事务内回写（status=DONE）；消息只增不改；todo 去重键防重复推送。

### 2.3 请假「扩展 vs 平迁」决策（硬约束项）

**决策：扩展 t_cs_leave（方案 A），否决平迁新表（方案 B）。**

| 维度 | 方案 A：扩展 t_cs_leave（√ 选定） | 方案 B：平迁 t_affairs_leave_request（× 否决） |
|---|---|---|
| 既有依赖 | campus-service approve/return API、批量审批、移动端学生提交（防重复 409）全部继续可用 | 双写或切流期间两套请假单并存，学生 360 与统计口径分裂 |
| 数据迁移 | 无需搬数据，历史单据原地升级 | 需全量迁移 + 旧 API 兼容层，违反速查"不得平行再建一套请假"红线 |
| 风险 | 需谨慎处理旧状态字段兼容 | 直接违反集成红线 |

**扩展设计——t_cs_leave 新增列清单**：

| 新增列 | 类型 | 说明 |
|---|---|---|
| affairs_status | VARCHAR(32) | 新状态机（§3.5 十四态），带索引 |
| leave_type | VARCHAR(20) | SICK/PERSONAL/HOME/INTERNSHIP_RELATED/OTHER |
| total_days | NUMERIC(5,1) | 服务端按起止计算，禁止前端传 |
| expected_return_at / actual_return_at | TIMESTAMPTZ | 预计/实际返校（实际值随销假确认回填） |
| workflow_instance_id | BIGINT | FK→t_workflow_instance（主审批链） |
| notify_parent | BOOLEAN | 家长通知开关（V1 记录，渠道 P2） |

**旧状态兼容与迁移**：
1. 保留旧 `status` 列供既有端点读；服务层**单向映射**维护：affairs_status ∈ {SUBMITTED, COUNSELOR_REVIEW, COLLEGE_REVIEW, STUDENT_AFFAIRS_REVIEW, EXTENSION_REVIEW} → status=PENDING_REVIEW；{APPROVED, WAIT_CANCEL_LEAVE, CLOSED, OVERDUE, ARCHIVED} → APPROVED；{RETURNED, REJECTED, CANCELLED} → RETURNED。
2. 迁移脚本反向 backfill 存量行：PENDING_REVIEW→COUNSELOR_REVIEW；APPROVED→（end_date 已过 → CLOSED，未过 → APPROVED）；RETURNED→RETURNED；存量行 workflow_instance_id 置空（老单不补建流程实例，审批历史以旧字段呈现）。
3. 既有 campus-service approve/return 端点降为兼容端点：内部改为代理新状态机（同事务同步双列，保证演示环境旧页面不炸），V1 起新前端一律走 workflow 审批端点，P2 下线旧端点并删除 status 列。
4. 附件/销假/续假走 §2.2 三张新子表；审批任务走 t_workflow_task。
5. 迁移纳入 sandbox-school 每晚重置的种子流程；demo-school 只读锁不受影响（迁移为 DDL+backfill，属发布动作非业务写）。

### 2.4 处分归属关系（硬约束项）

- **t_affairs_discipline_case = 流程表**（立案→审→生效全过程）；**t_cs_discipline = 生效台账**（对外可见口径）。
- case 进入 EFFECTIVE 时：insert/update t_cs_discipline 一行（record_status=ACTIVE，携带 case_id 反向引用）；case 完成 REMOVED 时：update 对应 t_cs_discipline.record_status=REMOVED。
- 既有"学生端只回数量不回明细"的行为保持不变（读的仍是 t_cs_discipline）；毕业资格审核、奖学金资格校验读 **t_cs_discipline 最新状态**（不读流程表），保证既有消费方零改动。

### 2.5 心理与宿舍归属关系（硬约束项）

- 心理：V1 心理关注 = t_cs_mental_record 增删改（强权限不变：仅心理老师/授权辅导员），风险中心引用之；不建新表。
- 宿舍：入住事实唯一落 t_cs_dorm_record；异常事实唯一落 t_cs_dorm_exception；新表只承载"房源结构 / 调宿流程 / 检查流程"三类既有骨架没有的内容。

### 3.1 学工首页（13A-01）

**① 角色四问**：发起=无（只读聚合页）；审核=无；处理=点击卡片跳转各业务处理页；查看=学工处管理员（全校）/ 学院学工管理员（本学院）/ 辅导员（自动跳转辅导员工作台视图）。
**② 前置条件**：已登录 PC（require_staff，学生令牌 403）；当前身份含学工角色；租户模块已授权。
**③ 主流程**：
1. 进入 `/admin/student-affairs` → 前端携 activeContextId 调 `GET /api/v1/student-affairs/dashboard?semester=&date_range=`。
2. 后端解析 tenant_id/current_role/data_scope（token 上下文，前端不传租户），按角色 preset 组装：summaryCards（全校学生数/风险数/困难数/心理关注数/宿舍异常数/归档率等）、todoList（读 t_unified_todo 按人过滤 top N）、riskStudents（t_affairs_risk_record 未关闭，按 scope 过滤）、workflowPending（t_workflow_task PENDING 按处理人）、classOverview、warningTrends（近 30 日风险/请假/处分趋势）、recentActivities（t_affairs_audit_trail 最近域动作）。
3. 学工处视图追加「学院风险与待办排行」（按 college_id group by）；学院视图同构指标限本学院。
4. 风险学生卡片点击 → 跳该生学生 360（PC 详情页）；待办点击 → 按 todo.action_url 跳处理页。
**④ 异常流程**：范围内无数据 → 空卡片 + "当前身份范围暂无数据"（403002 仅用于明确越权，列表空态返回空 items）；聚合超时降级为分卡异步加载，单卡失败显示卡内 error 不拖垮整页。
**⑤ 退回流程**：无（只读页无审批）。
**⑥ 状态机**：无独立状态机；卡片数字口径由各业务状态机终态/在途态定义（见各业务 ⑭）。
**⑦ 权限点**：`studentAffairs.dashboard.view`（进入）、`studentAffairs.dashboard.collegeRank.view`（排行卡，仅学工处）。
**⑧ 数据范围**：学工处=SCHOOL；学院学工=COLLEGE；辅导员访问本页自动 302 至工作台。全部经 getStudentAffairsScope 过滤，禁止前端传范围参数。
**⑨ 关键字段**：无落表；响应 DTO 字段 camelCase（summaryCards[].key/value/trend/drillUrl）。
**⑩ 审批节点**：无。
**⑪ 操作记录**：页面进入不审计；点击"查看完整敏感字段"类下钻动作按目标业务规则审计。
**⑫ 消息通知**：不发消息；todoList/消息角标读 t_unified_todo / t_unified_message 未读数。
**⑬ 学生360沉淀**：无写入；riskStudents 提供跳 360 入口。
**⑭ 数据中心统计**：本页即统计消费方——指标全部来自 stats_service 扩展聚合（实时 count），口径示例：`逾期未销假数 = count(t_cs_leave where affairs_status=OVERDUE and tenant)`，角色过滤=scope，均可下钻到列表页。
**⑮ 入口**：学生小程序=无；教师小程序=无（教师看工作台）；PC=`/admin/student-affairs`（学工中心一级菜单默认页）。
**⑯ 模块关系**：Student—读 t_student_profile 汇总数；Workflow—读 t_workflow_task 待审数；Security—聚合接口过 require_staff+scope 链；Dashboard—与全局驾驶舱共用 stats_service，学工卡片是其子集；六大生命周期—就业未填报/实习异常/毕设异常三卡直接读 t_emp_* / t_internship_* / t_gd_* 既有统计口径，不复制数据。
**⑰ V1必做**：三角色 preset、8 类卡片、待办列表、风险列表、下钻。**P2P3**：趋势图细化、自定义卡片布局、学院排行导出。
**⑱ 现场确认**：学工处首页默认统计周期按学期还是学年？学院排行是否对学院管理员可见（还是仅学工处）？

### 3.2 辅导员工作台（13A-02）

**① 角色四问**：发起=无；审核=辅导员在此处理请假等待办（实际审批动作发生在各业务）；处理=辅导员；查看=辅导员（本人范围）、班主任（等同范围规则）。
**② 前置条件**：登录用户 activeContext 为辅导员/班主任身份；t_teacher_student_scope 已配置其 CLASS/ADVISOR 范围（无范围行时按速查 TENANT_FALLBACK 策略，生产环境应配置为 SCOPED）。
**③ 主流程**：
1. PC `/admin/student-affairs/workbench` 或教师小程序工作台页 → `GET /api/v1/student-affairs/counselor/workbench`（教师移动走 `GET /api/v1/mobile/teacher/affairs/workbench`）。
2. 后端 `getCounselorScope(user)`（=resolve_teacher_scope 包装）→ 得 classNames/studentNos → 组装：我的班级（t_class）、我的学生数、今日待办（t_unified_todo assignee=本人 due 今日）、待审请假（t_workflow_task PENDING & workflow_code=AFFAIRS_LEAVE）、风险学生（t_affairs_risk_record assignee=本人 未关闭）、学业预警（t_acad_warning PENDING_HANDLE/PROCESSING，按 scope）、待谈话（t_affairs_talk_plan 计划中）、困难生数（t_affairs_aid_level_history 有效）、处分跟进（t_affairs_discipline_case 在途）、就业未填报/实习异常/毕设异常（读三域既有接口口径）。
3. 子接口：`counselor/students`（filterStudentsByCounselorScope 分页）、`counselor/todos`、`counselor/risk-students`；学生快速搜索框按姓名/学号在 scope 内检索，命中即进学生 360。
4. 待办卡点击 → action_url 直达审批/处理页；处理完成后待办自动完结（t_unified_todo.status=DONE 由业务 service 回写）。
**④ 异常流程**：scope 解析为空 → 页面显示"未配置带班范围，请联系学院管理员"（非 500）；搜索越权学号 → assertCounselorCanAccessStudent 失败 → 403001 + 审计。
**⑤ 退回流程**：无（承载页；退回逻辑在各业务）。
**⑥ 状态机**：无；待办项状态复用 t_unified_todo（PENDING/DONE/CANCELLED）。
**⑦ 权限点**：`studentAffairs.counselor.dashboard.view / studentAffairs.counselor.student.view / studentAffairs.counselor.todo.handle / studentAffairs.counselor.risk.handle`。
**⑧ 数据范围**：辅导员=COUNSELOR_CLASSES（负责班级学生）；班主任=CLASS。列表与写操作共用 scope 函数（看得见=能处理）。
**⑨ 关键字段**：无新表；workbench DTO：myClasses[]/todayTodos[]/pendingLeaves[]/riskStudents[]/acadWarnings[]/counters{}。
**⑩ 审批节点**：无（跳转目标业务的节点）。
**⑪ 操作记录**：学生快速搜索查看学生 360 记 t_security_audit_log（resource=student_profile）；工作台浏览不审计。
**⑫ 消息通知**：消费方——角标未读数；本页不产生消息。
**⑬ 学生360沉淀**：无写入；是 360 最高频入口。
**⑭ 数据中心统计**：`辅导员待办完成率 = done/(done+pending)（t_unified_todo 按 assignee 聚合，实时，学工处/学院可下钻到辅导员个人）`——同时供 13A-01 首页"辅导员完成率"卡。
**⑮ 入口**：学生小程序=无；教师小程序=工作台 Tab（`pages/teacher/*` 追加学工分组卡片）；PC=`/admin/student-affairs/workbench`。
**⑯ 模块关系**：Student—students 列表读 t_student_profile；Workflow—pendingLeaves 等直读 t_workflow_task；Security—每个子接口独立过 scope，教师移动写操作全部走 /mobile/teacher 包装；Dashboard—完成率指标上报 stats_service；六大生命周期—实习异常/毕设异常/就业未填报三卡读既有域，处理动作跳既有页面（不在学工内重做处理页）。
**⑰ V1必做**：workbench 聚合、四个子接口、快速搜索、待办直达。**P2P3**：自定义卡片、批量催办、辅导员日志。
**⑱ 现场确认**：班主任与辅导员是否同权同视图？"今日待办"是否包含教务侧（学业预警处理）待办混排？

### 3.3 学生信息与画像（13A-03）

**① 角色四问**：发起=无（读为主，人工标记风险为写入口，归风险业务）；审核=无；处理=无；查看=辅导员/班主任（本班）、学院学工（本院）、学工处（全校）、心理老师（仅授权学生心理段）、学生本人（小程序"我的"简版，不含敏感段）。
**② 前置条件**：目标学生在查看人 scope 内（canAccessAffairsStudent，越权 403+审计）；学生主档存在（t_student_profile）。
**③ 主流程**：
1. `GET /api/v1/student-affairs/students/{id}/profile` → 聚合：基础信息+学籍状态（t_student_profile.current_stage/student_status，只读，不在学工侧改）、班级/辅导员（t_class）、请假汇总（t_cs_leave）、奖助（t_affairs_funding_result）、困难认定（t_affairs_aid_level_history 有效等级）、处分（t_cs_discipline，按权限）、心理关注（t_cs_mental_record，默认隐藏）、谈话（t_affairs_talk_record）、宿舍（t_cs_dorm_record+t_affairs_dorm_bed）、学业预警（t_acad_warning）、实习异常/就业状态（既有域）、风险等级（t_affairs_risk_record 最高未关闭等级）、德育积分（P2 占位）。
2. `GET /api/v1/student-affairs/students/{id}/timeline` → 读 t_student_stage_event（含 AFFAIRS_* 事件）倒序分页，构成成长时间线。
3. 敏感段按查看人权限裁剪：心理段仅 `studentAffairs.psy.view` 且 PSY_STUDENT 授权；困难段金额/病因脱敏；家庭联系方式走 t_student_contact 读时脱敏。
4. 点击"查看完整"（手机号/身份证/家庭经济明细）→ 弹窗填写原因 → `POST .../sensitive-view`（原因≥5 字）→ 返回完整值 + 写 t_security_audit_log。
**④ 异常流程**：学生不存在 404001；不在 scope 403001+审计；心理段无权限时**段落整体不返回**（而非返回空值，防试探）。
**⑤ 退回流程**：无。
**⑥ 状态机**：无自身状态机；展示各域状态徽标（枚举 label 由后端字典翻译）。
**⑦ 权限点**：`studentAffairs.profile.view`（基础）、`studentAffairs.profile.sensitive.view`（完整敏感值）、`studentAffairs.psy.view`（心理段）、`studentAffairs.discipline.view`（处分明细段）。
**⑧ 数据范围**：同 §1.1-4 六路判定；学生本人=SELF（移动端 `GET /api/v1/mobile/affairs/my/profile`，仅基础+本人可见业务，无风险等级/心理段）。
**⑨ 关键字段**：无新主表（复用 t_student_profile/t_student_stage_event）；t_student_stage_event 扩展 event_type 枚举：AFFAIRS_LEAVE_CLOSED / AFFAIRS_AID_APPROVED / AFFAIRS_FUNDING_GRANTED / AFFAIRS_DISCIPLINE_EFFECTIVE / AFFAIRS_DISCIPLINE_REMOVED / AFFAIRS_RISK_CLOSED / AFFAIRS_TALK_DONE / AFFAIRS_DORM_CHANGED / AFFAIRS_ARCHIVED。
**⑩ 审批节点**：无。
**⑪ 操作记录**：敏感查看必审计（含 ip/ua/traceId/原因）；普通画像浏览记轻量访问日志（P2 决定是否全量）。
**⑫ 消息通知**：无。
**⑬ 学生360沉淀**：本业务是 360 的**读侧规范**：各业务按 ⑬ 约定写 t_student_stage_event，本页聚合；同时扩展既有 mobile teacher `student/{id}` 聚合端点追加 affairs 段（同一套裁剪函数，PC 与移动共用 service）。
**⑭ 数据中心统计**：无独立指标；提供"风险等级分布"数据源（t_affairs_risk_record group by risk_level）。
**⑮ 入口**：学生小程序=「我的-我的档案」（简版）；教师小程序=既有学生详情页扩展 affairs 段；PC=`/admin/student-affairs/students/:id`（从工作台/首页/各业务单据学生名点入）。
**⑯ 模块关系**：Student—**只读**主档，学工不改主档字段（更正走学生中心既有更正流程）；Workflow—无；Security—本业务是脱敏/审计规则最密集处，全部走既有 mask 与 audit_log；Dashboard—供画像分布数据；六大生命周期—实习/毕设/就业/迎新段直接调用各域既有查询 service，禁止复制其数据落学工表。
**⑰ V1必做**：profile+timeline 两接口、权限裁剪、敏感查看审计、聚合端点扩展。**P2P3**：德育积分段、行为大数据画像、画像 PDF 导出（水印）。
**⑱ 现场确认**：心理段可见角色最终名单（是否含学院学工管理员）？学生本人可见哪些段（处分是否对本人可见明细）？

### 3.4 班级管理（13A-04）

**① 角色四问**：发起=学院学工管理员（建班/绑定/导入）；审核=无强审批（绑定辅导员为直接操作，记审计）；处理=辅导员（维护班干部/班级事件/材料）；查看=学工处（全校）/学院（本院）/辅导员（本班）。
**② 前置条件**：学院/专业/年级已在组织架构存在（t_college/t_major）；班级唯一性=tenant+major+grade+class_name。
**③ 主流程**：
1. 学院建班：`POST /api/v1/student-affairs/classes` → 校验专业属本学院、名称不重复 → **写既有 t_class**（不建新班级主表）。
2. 绑定辅导员/班主任：PATCH classes/{id} 更新 t_class.counselor_id/head_teacher_id → **同步维护 t_teacher_student_scope**（新增/失效对应 CLASS 行，保证 scope 与绑定一致，事务内完成）→ 发 STATUS_CHANGED 消息给新辅导员。
3. 导入学生：走既有 domain 导入管线（validate dry-run 行级错误→confirm 整批事务），本质是更新 t_student_profile.class_id；跨租户批次拒绝。
4. 设班干部：`POST classes/{id}/cadres` 写 t_affairs_class_cadre（student_id/position/start_at/end_at）。
5. 班级画像：`GET classes/{id}/profile` 实时聚合指标：人数/男女（t_student_profile）、困难（aid_level_history）、风险（risk_record）、请假在途（t_cs_leave）、处分（t_cs_discipline ACTIVE）、宿舍异常（t_cs_dorm_exception）、学业预警（t_acad_warning）、就业未填报/实习异常/毕设异常（既有域）。
6. 班级事件/材料：辅导员随时登记 t_affairs_class_event（班会/活动/事故）与上传 t_affairs_class_material（file_id）→ 归档批次可引用。
7. 画像指标进首页 classOverview 与数据中心。
**④ 异常流程**：导入行错误 → 返回行号+字段+原因，整批不落库；解绑辅导员时其名下存在未完结待办 → 提示转办后再解绑（不强制阻断，记审计）；删除班级仅允许无在籍学生时软删。
**⑤ 退回流程**：无审批流；导入 validate 不通过即"退回修改模板"。
**⑥ 状态机**：班级无流程状态；t_affairs_class_cadre 有 status（ACTIVE/ENDED）。
**⑦ 权限点**：`studentAffairs.class.manage`（建班/绑定/导入）、`studentAffairs.class.view`、`studentAffairs.class.cadre.manage`、`studentAffairs.class.material.manage`。
**⑧ 数据范围**：学工处=SCHOOL；学院=COLLEGE（只能建/管本院班）；辅导员=本班只读画像+维护干部/事件/材料。
**⑨ 关键字段**：t_affairs_class_cadre（class_id/student_id/position 枚举/status）；t_affairs_class_event（class_id/event_type/title/content/occurred_at/related_file_ids）；t_affairs_class_material（class_id/material_type/file_id/uploaded_by）。
**⑩ 审批节点**：无（直接操作 + 审计）。
**⑪ 操作记录**：建班/绑定/解绑/导入/删除全部 audit_log.record；导入落导入批次记录。
**⑫ 消息通知**：绑定辅导员→STATUS_CHANGED（新任辅导员）；导入完成→STATUS_CHANGED（操作人）。
**⑬ 学生360沉淀**：班级调整体现在 t_student_profile.class_id 变化（由导入/教务异动驱动），学工侧不直接写学生阶段事件；班干部任职写一条 t_student_stage_event（AFFAIRS 类，进个人履历）。
**⑭ 数据中心统计**：班级画像 11 项指标（口径见 ③-5，来源=各业务表实时聚合，更新=实时，过滤=scope，可下钻学生列表，可导出班级报表-水印）。
**⑮ 入口**：学生小程序=无；教师小程序=工作台"我的班级"→班级画像（只读）；PC=`/admin/student-affairs/classes`（列表/详情/学生/画像/材料五页）。
**⑯ 模块关系**：Student—班级主档即 t_class、学生归属即 t_student_profile.class_id，学工只做视图与附属对象；Workflow—无；Security—绑定操作同步 scope 表是权限体系正确性的关键点（见 ③-2）；Dashboard—classOverview 供首页；六大生命周期—班级画像的实习/毕设/就业指标调既有域统计。
**⑰ V1必做**：班级 CRUD（基于 t_class）、绑定同步 scope、干部/事件/材料、画像接口。**P2P3**：画像日快照与趋势、班级对比分析、班费/班会考勤。
**⑱ 现场确认**：建班权是否可下放到学院？班主任与辅导员是否允许同一人/是否必配？班干部职务枚举清单？

### 3.5 请假 / 销假 / 续假（13A-05）—— V1 旗舰闭环

**① 角色四问**：发起=学生（小程序）；审核=辅导员（必经）→ 学院学工（长假）→ 学工处（重大/超长假）；处理=辅导员（销假确认、逾期跟进）、宿管（知晓离返校）；查看=学生本人、审批链角色、宿管（本楼在假学生名单）、家长（可选仅通知，不登录）。
**② 前置条件**：学生在籍（student_status 正常，休学/退学不可发起）；本人发起（student_id 从 token 取，**前端不传学生 id**）；无时间区间重叠的在途/生效请假单（重叠 → 409001）；同 request_id 重复提交拦截（幂等 409）。
**③ 主流程**（学生发起→审批→生效→销假）：
1. 学生小程序「请假」→ 填：leave_type（枚举必选）/开始时间（≥当前）/结束时间（>开始）/原因（10–500 字）/材料（病假≥1 个附件，PDF/JPG/PNG≤10MB）/是否通知家长。
2. `POST /api/v1/mobile/affairs/leave`（createSubmitLock 防连点）→ 服务端校验 ②全部规则 + total_days 计算 → 写 t_cs_leave（affairs_status=SUBMITTED）+ t_file_object(LEAVE 附件)。
3. 按天数定审批流（阈值走平台规则中心，默认：≤3 天辅导员终审；3<天数≤7 加学院；>7 或出省/重大事由加学工处）：startWorkflow(workflow_code=AFFAIRS_LEAVE, 节点序列按规则裁剪) → 生成 t_workflow_instance + 首节点 t_workflow_task + t_unified_todo（辅导员）+ WORKFLOW_TODO 消息。affairs_status=COUNSELOR_REVIEW。
4. 辅导员审批（PC 或教师小程序 `/api/v1/mobile/teacher/approvals/{id}/approve`，走既有包装：scope 校验+审计+version 409）→ 通过：有后续节点则流转（COLLEGE_REVIEW → STUDENT_AFFAIRS_REVIEW），否则 affairs_status=APPROVED。
5. APPROVED：发 WORKFLOW_RESULT（学生）；notify_parent=true 时发 STATUS_CHANGED 至家长渠道（V1 仅记录待通知，短信渠道 P2 接 t_message_channel_log）；宿管楼栋名单同步可见（读侧）。
6. 到期前 24h：定时任务发 DEADLINE_REMINDER（学生+辅导员）"请按时返校并销假"。
7. 销假：学生返校 → 小程序「销假」→ 上传返校证明（可选，按规则）→ 写 t_affairs_leave_cancel_record（actual_return_at）→ affairs_status=WAIT_CANCEL_LEAVE → 辅导员待办确认属实 → affairs_status=CLOSED → 写 360 事件 AFFAIRS_LEAVE_CLOSED。
8. 续假：APPROVED 且未到期 → 学生发起 `POST leave/{id}/extension`（新结束时间+原因）→ 写 t_affairs_leave_extension → affairs_status=EXTENSION_REVIEW → 按**累计总天数**重定审批链（可能升级到学院/学工处）→ 通过更新 t_cs_leave 结束时间、拒绝维持原结束时间（单据回 APPROVED）。
**④ 异常流程**：
- 逾期：结束时间已过且未销假 → 定时任务置 affairs_status=OVERDUE → 自动生成 t_affairs_risk_record（source_type=LEAVE_OVERDUE, source_ref_id=leave.id, 分派辅导员）+ RISK_ALERT；辅导员联系后可（a）补销假→CLOSED（b）转家校联系（P2 前记入风险处置流水）（c）升级风险。OVERDUE 补销后风险记录须联动关闭（§5-6）。
- 撤销：SUBMITTED/审批中可学生自撤 → CANCELLED（workflow 实例终止，待办撤回）；APPROVED 后假期未开始可撤销（辅导员知晓消息），已开始不可撤只能销假。
- 材料缺失/校验失败：422001 字段级提示；审批人已处理再提交审批 → 409 APPROVAL_VERSION_CONFLICT 提示刷新。
**⑤ 退回流程**：审批人「退回」（RETURNED，reject_reason≥5 字）→ 单据回学生可编辑态（保留单号/附件/历史），学生修改后重新提交 → **回到首个审批节点**（辅导员）重走；「驳回」（REJECTED）终态，只能新建。
**⑥ 状态机**（枚举 14 态 + 转移）：
| From | 动作（角色） | To |
|---|---|---|
| DRAFT | 提交（学生） | SUBMITTED |
| SUBMITTED | 系统建流 | COUNSELOR_REVIEW |
| COUNSELOR_REVIEW | 通过（辅导员） | COLLEGE_REVIEW / STUDENT_AFFAIRS_REVIEW / APPROVED（按链） |
| COUNSELOR_REVIEW/COLLEGE_REVIEW/STUDENT_AFFAIRS_REVIEW | 退回 | RETURNED；驳回 → REJECTED |
| RETURNED | 修改重交（学生） | COUNSELOR_REVIEW |
| SUBMITTED~审批中 | 撤销（学生） | CANCELLED |
| APPROVED | 到期未销（系统） | OVERDUE；发起续假 → EXTENSION_REVIEW；发起销假 → WAIT_CANCEL_LEAVE |
| EXTENSION_REVIEW | 通过/拒绝 | APPROVED（新/原止期） |
| WAIT_CANCEL_LEAVE | 确认（辅导员） | CLOSED；不属实退回 → APPROVED（重销） |
| OVERDUE | 补销+确认 | CLOSED |
| CLOSED | 归档批次（系统） | ARCHIVED |
**⑦ 权限点**：`studentAffairs.leave.apply`（学生，移动）、`.approve`、`.cancelConfirm`、`.view`、`.export`、`.ruleConfig`（平台规则中心入口）。
**⑧ 数据范围**：学生=本人；辅导员=带班学生单据；学院=本院；学工处=全校；宿管=本楼栋学生的"在假名单"只读（scope_type=DORM_BUILDING）。
**⑨ 关键字段**：t_cs_leave 扩展列见 §2.3；附件 t_file_object(biz_type=LEAVE)；t_affairs_leave_cancel_record（leave_id/actual_return_at/proof 走 t_file_object/confirmed_by/confirmed_at/biz_status）；t_affairs_leave_extension（leave_id/old_end_at/new_end_at/reason/biz_status/workflow_instance_id）。
**⑩ 审批节点**：workflow_code=`AFFAIRS_LEAVE`，node_code 序列 `COUNSELOR → COLLEGE → SA_OFFICE`（按天数裁剪）；续假 workflow_code=`AFFAIRS_LEAVE_EXT` 同序列。
**⑪ 操作记录**：提交/审批/退回/销假/逾期置态/导出全记 t_affairs_audit_trail + audit_log；审批动作另有 t_workflow_task acted_at/action_reason。
**⑫ 消息通知**：提交→WORKFLOW_TODO（审批人）；通过/驳回→WORKFLOW_RESULT（学生）；退回→RETURNED_NOTICE（学生）；到期前→DEADLINE_REMINDER（学生+辅导员）；逾期→RISK_ALERT（辅导员）；家长通知→STATUS_CHANGED（渠道 P2）。
**⑬ 学生360沉淀**：CLOSED/OVERDUE 终态写 t_student_stage_event（AFFAIRS_LEAVE_CLOSED，摘要含类型/天数/是否逾期）；360 请假段聚合 t_cs_leave 本人历史（近 N 条+统计）。
**⑭ 数据中心统计**（五要素定义）：
| 指标 | 口径 | 来源 | 频率 | 过滤/下钻 |
|---|---|---|---|---|
| 在假人数/人次/天数 | affairs_status ∈ {APPROVED,WAIT_CANCEL_LEAVE} count/sum(total_days) | t_cs_leave | 实时 | 校/院/班/宿管楼栋；下钻单据 |
| 逾期未销数 | affairs_status=OVERDUE | t_cs_leave | 实时 | 同上；进首页红卡 |
| 请假类型分布 | group by leave_type（学期内） | t_cs_leave | 实时 | 学院 |
| 平均审批时长 | avg(task.acted_at - instance.created_at) | t_workflow_task | 日更 | 节点/角色维度（辅导员时效） |
| 销假及时率 | 按时销假 / 应销假 | t_cs_leave + t_affairs_leave_cancel | 日更 | 班级；供辅导员考评复用 |
**⑮ 入口**：学生小程序=「请假」全流程（发起/我的请假/销假/续假；长假>7 天仍可移动发起，规则不强制回 PC）；教师小程序=待办审批+销假确认；PC=`/admin/student-affairs/leave`（列表/详情/审批/销假确认/续假/统计/规则配置七页）。
**⑯ 模块关系**：Student—单据挂 t_student_profile，在籍校验读 student_status；Workflow—全部审批任务/乐观锁/转办复用；Security—本人校验、scope、审计、导出水印；Dashboard—§⑭ 指标；六大生命周期—实习期学生请假 leave_type=INTERNSHIP_RELATED 时同步通知实习指导教师（读 t_internship_record 的指导人，发 STATUS_CHANGED），考试期间请假联动缓考（§5-3，13B 承接）。
**⑰ V1必做**：全状态机、三级动态审批、销假/续假/逾期、消息八类映射、360、统计、导出。**P2P3**：家长短信实通道、请假热力分析、与考勤系统对接。
**⑱ 现场确认**：天数阈值（几天到学院/学工处）？病假材料是否强制？是否要求家长确认（而非仅通知）？逾期几天自动升级风险等级？

### 3.6 困难学生认定（13A-06）

**① 角色四问**：发起=学工处/资助老师（建批次）、学生（申请）；审核=班级评议小组（评议）→ 辅导员初审 → 学院复审 → 学校（学工处/资助中心）终审；处理=辅导员（组织评议）、资助老师（批次与库管理）;查看=审批链、资助老师（全库）、辅导员（本班困难生）、学生本人（自己的申请与等级）。
**② 前置条件**：批次 OPEN 且在申请时间窗内；学生在籍；同批次未提交过（唯一约束 batch_id+student_id，重复 409）；上年度等级存在时走"年度复核"通道（预填数据）。
**③ 主流程**：
1. 资助老师建批次：`POST aid/batches`（学年/申请窗/评议要求/等级枚举配置）→ 发布 PUBLISHED_NOTICE（范围内学生）。
2. 学生小程序申请：填家庭经济信息（成员/收入/致困类型：低保/建档/残疾/大病/突发等）+材料（file_id）→ 写 t_affairs_aid_apply（SUBMITTED）+ t_affairs_aid_family_economy（敏感列加密）。
3. 班级评议：辅导员组织评议小组线下评议 → 辅导员录入评议结果 t_affairs_aid_class_review（评议意见/建议等级/参评人数）→ 状态 CLASS_REVIEW→COUNSELOR_REVIEW。
4. 三级审批走 workflow（AFFAIRS_AID：COUNSELOR→COLLEGE→SCHOOL），各节点可改"建议等级"（记录于 task action_reason 结构化字段）。
5. 学校终审通过 → PUBLICITY（公示，默认 5 个工作日，可配置）：公示名单**脱敏展示**（姓名部分掩码+班级，不含金额/致困明细）；公示期异议 → 记录并可回退 SCHOOL_REVIEW。
6. 公示无异议 → APPROVED：写 t_affairs_aid_level_history（生效等级+学年+依据 apply_id，append-only）→ 学生进入**困难学生库**（=level_history 有效行）→ 360 事件 AFFAIRS_AID_APPROVED → WORKFLOW_RESULT（学生）。
7. 动态调整：辅导员/资助老师发起等级调整（家庭变故升级/情况好转降级）→ ADJUST_REVIEW（简化链：学院→学校）→ 通过写新 level_history 行，旧行置失效。
8. 年度复核：新学年批次自动带出上年困难生名单，未复核者到期自动失效（DEADLINE_REMINDER 提前 14 天）。
**④ 异常流程**：窗口外提交 422001；材料不足退回补充；评议未完成辅导员不能初审（前置校验）；公示期收到实名异议→暂停该生流转、线下核查、记录处理结论后继续或驳回。
**⑤ 退回流程**：任一审批节点退回 → RETURNED → 学生补充材料/修改 → 重新提交 → **回到班级评议已完成后的辅导员初审节点**（评议结果保留，不重评）；驳回 REJECTED 终态，本批次不可再申请（可下批次）。
**⑥ 状态机**（枚举 13 态 + 转移表）：NOT_STARTED/DRAFT/SUBMITTED/CLASS_REVIEW/COUNSELOR_REVIEW/COLLEGE_REVIEW/SCHOOL_REVIEW/PUBLICITY/APPROVED/REJECTED/RETURNED/ADJUST_REVIEW/ARCHIVED。
| From | 动作（角色） | To |
|---|---|---|
| DRAFT | 提交（学生，窗口内） | SUBMITTED |
| SUBMITTED | 系统转入评议 | CLASS_REVIEW |
| CLASS_REVIEW | 评议结果录入（辅导员） | COUNSELOR_REVIEW |
| COUNSELOR_REVIEW | 通过 | COLLEGE_REVIEW；退回 → RETURNED；驳回 → REJECTED |
| COLLEGE_REVIEW | 通过 | SCHOOL_REVIEW；退回/驳回同上 |
| SCHOOL_REVIEW | 通过（学工处/资助中心） | PUBLICITY |
| PUBLICITY | 期满无异议（系统） | APPROVED；实名异议成立 → SCHOOL_REVIEW |
| RETURNED | 补充重交（学生） | COUNSELOR_REVIEW（评议结果保留） |
| APPROVED | 发起等级调整 | ADJUST_REVIEW → 通过回 APPROVED（写新 level_history 行）/ 驳回回 APPROVED（原等级） |
| APPROVED | 学年归档批次 | ARCHIVED |
**⑦ 权限点**：`studentAffairs.aid.batch.manage / .apply（学生）/ .classReview.input / .approve / .library.view / .sensitive.view / .export`。
**⑧ 数据范围**：学生=本人；辅导员=本班申请与困难生；学院=本院；资助老师=AID_STUDENT 范围或全校（按角色配置）；学工处=全校。
**⑨ 关键字段**：t_affairs_aid_batch（academic_year/apply_start/apply_end/publicity_days/biz_status）；t_affairs_aid_apply（batch_id/student_id/difficulty_type/apply_reason/suggest_level/final_level/biz_status/workflow_instance_id）；t_affairs_aid_family_economy（apply_id/member_json/annual_income_encrypted/illness_desc_encrypted/proof_file_ids）；t_affairs_aid_class_review（apply_id/opinion/suggest_level/attendee_count）；t_affairs_aid_level_history（student_id/level 枚举 A特困/B困难/C一般困难/effective_year/status/source_apply_id）。
**⑩ 审批节点**：workflow_code=`AFFAIRS_AID`（COUNSELOR→COLLEGE→SCHOOL）；调整 `AFFAIRS_AID_ADJUST`（COLLEGE→SCHOOL）。
**⑪ 操作记录**：申请/评议录入/各级审批/公示发布/异议处理/等级变更/查看完整家庭经济（必审计+原因）/导出（水印+t_export_task）。
**⑫ 消息通知**：批次发布→PUBLISHED_NOTICE；待审→WORKFLOW_TODO；结果→WORKFLOW_RESULT；退回→RETURNED_NOTICE；公示→PUBLISHED_NOTICE；复核到期→DEADLINE_REMINDER。

### 3.7 奖助勤贷四类（13A-07，统一资助项目抽象）

四类共用 t_affairs_funding_project/batch/application/publicity/result 与 workflow，差异在**资格校验器**与**节点链**。

**① 角色四问**：发起=资助老师/学工处（项目与批次）、学生（申请）、用工部门（勤工发岗）、系统（奖学金推荐名单）；审核=辅导员初审→学院评审→学校复核（奖/助）、部门筛选→辅导员→资助中心（勤工）、辅导员核对→资助老师→学校确认（贷款）；处理=资助老师（全程运营）；查看=审批链+学生本人+辅导员（本班获助情况）。
**② 前置条件（按类型的资格校验器，服务端强制）**：
- 通用：批次窗口内、在籍、同批次未重复申请（409）、材料齐全。
- SCHOLARSHIP：学籍无异常 + **无未解除处分（读 t_cs_discipline record_status=ACTIVE 即拦截）** + 成绩达标（读 t_acad_grade 绩点/挂科规则，规则中心配置）。
- GRANT（助学金）：**必须命中困难库**（t_affairs_aid_level_history 有效行；等级决定档位）。
- WORK_STUDY：在籍正常 + 无时间冲突（V1 与本人在途勤工岗位互斥；与课表冲突校验 P2 待 13B 课表）+ 困难生优先标记。
- LOAN：在籍 + 回执材料齐全。
**③ 主流程**：
1. 建项目/批次：`POST funding/projects`（project_type/金额或档位/名额/条件 JSON）→ `POST funding/batches`（学年/窗口/适用范围）→ PUBLISHED_NOTICE。
2. 奖学金：系统按条件生成**推荐名单**（跑资格校验器出候选+排序依据）→ 学生确认申请或辅导员代提推荐 → 写 application → 辅导员初审 → 学院评审（可排序/差额）→ 学校复核 → PUBLICITY（脱敏公示）→ 确认 → result（获奖台账）→ 360。
3. 助学金：学生申请（预校验困难库命中，未命中前端即提示"请先完成困难认定"）→ 辅导员核实 → 学院 → 学校 → 公示 → result（按等级档位金额，发放记录 append-only）。
4. 勤工助学：部门发岗（岗位=project_type=WORK_STUDY 的 project，含工时/时薪/人数）→ 学生申请 → 校验器 → 部门筛选（初选名单）→ 辅导员确认 → 资助中心审批 → 上岗（application.biz_status=ON_POST）→ 月度考核：部门每月录入考核+工时 → 生成补贴 result（result_type=WORK_STUDY_MONTH）→ 离岗归档为"勤工经历"。
5. 助学贷款：学生登记（银行/年份/金额/合同号）+上传回执 → 辅导员核对 → 资助老师审核 → 学校确认 → result（贷款台账，按年滚动）→ **毕业前学期**定时 DEADLINE_REMINDER 提醒确认还款计划（联动毕业批次日历）。
**④ 异常流程**：资格校验失败 → 422001 携失败项明细（如"存在未解除处分"），**不允许提交**；名额超限 → 学院评审页强制差额排序；勤工月度未录考核 → 补贴不生成并提醒部门；公示异议同 3.6。
**⑤ 退回流程**：各节点退回 → RETURNED 回学生（或部门）修改 → 重入首审节点；评审阶段学院可"退回辅导员重新初审"（节点级退回，workflow 支持回退到指定 node_code）。
**⑥ 状态机**（application 通用 13 态 + 分型转移）：DRAFT/SUBMITTED/COUNSELOR_REVIEW/DEPT_SCREEN(勤工)/COLLEGE_REVIEW/SCHOOL_REVIEW/PUBLICITY/APPROVED/ON_POST(勤工)/REJECTED/RETURNED/CANCELLED/ARCHIVED；批次：DRAFT/OPEN/REVIEWING/PUBLICITY/CLOSED/ARCHIVED。
| 类型 | 主转移链 | 分叉点 |
|---|---|---|
| SCHOLARSHIP | SUBMITTED→COUNSELOR_REVIEW→COLLEGE_REVIEW→SCHOOL_REVIEW→PUBLICITY→APPROVED→ARCHIVED | COLLEGE_REVIEW 可"退回辅导员重审"（节点级回退） |
| GRANT | 同上（COUNSELOR_REVIEW 语义=核实困难情况） | 申请前置校验命中困难库，否则不可 SUBMITTED |
| WORK_STUDY | SUBMITTED→DEPT_SCREEN→COUNSELOR_REVIEW→SCHOOL_REVIEW(资助中心)→APPROVED→ON_POST→ARCHIVED(离岗) | ON_POST 期间月度考核不产生状态变化，只产生 result 流水 |
| LOAN | SUBMITTED→COUNSELOR_REVIEW→AID_TEACHER_REVIEW→SCHOOL_CONFIRM→APPROVED（按年滚动，无公示） | 每学年续贷新 application 引用上年台账 |
| 通用 | 任一审批态→RETURNED（回申请人重交后回首审）/REJECTED（终态）；SUBMITTED~首审前可 CANCELLED（学生自撤） | — |
**⑦ 权限点**：`studentAffairs.funding.project.manage / .apply / .recommend / .approve / .deptScreen / .publicity.manage / .result.view / .export`。
**⑧ 数据范围**：学生=本人；部门=本部门岗位申请；辅导员=本班；学院=本院；资助老师/学工处=全校。
**⑨ 关键字段**：project（project_type/name/amount_or_levels_json/quota/criteria_json/status）；batch（project_id/academic_year/window/scope_json）；application（batch_id/student_id/apply_source=SELF|RECOMMEND/check_snapshot_json 资格校验快照/biz_status/workflow_instance_id）；publicity（batch_id/list_snapshot/start_at/end_at/objection_json）；result（application_id/result_type/amount/granted_at/bank_info_encrypted(贷款)/month(勤工)）。
**⑩ 审批节点**：workflow_code=`AFFAIRS_FUNDING_SCHOLARSHIP|GRANT|WORK_STUDY|LOAN` 四条链（节点见 ③）。
**⑪ 操作记录**：推荐名单生成（记规则版本）、各级审批、公示、发放录入、导出（名单水印脱敏）全审计。
**⑫ 消息通知**：批次/岗位发布→PUBLISHED_NOTICE；待审→WORKFLOW_TODO；结果→WORKFLOW_RESULT；退回→RETURNED_NOTICE；公示→PUBLISHED_NOTICE；贷款毕业确认/勤工月考核→DEADLINE_REMINDER。
**⑬ 学生360沉淀**：result 生成时写 stage_event（AFFAIRS_FUNDING_GRANTED，摘要=项目名+学年，金额按权限显示）；360 奖助段读 result 台账；勤工经历单列。
**⑭ 数据中心统计**（五要素定义）：
| 指标 | 口径 | 来源 | 频率 | 过滤/下钻 |
|---|---|---|---|---|
| 奖助覆盖率 | distinct 获助学生 / 在籍数 | t_affairs_funding_result | 实时 | 校/院/班；下钻名单（脱敏） |
| 资助金额汇总 | sum(result.amount) 按类型/学年 | 同上 | 实时 | 导出需敏感二次确认 |
| 困难生受助率 | 获助困难生 / 困难库人数 | result join level_history | 实时 | 学院 |
| 勤工在岗数 | application ON_POST count | t_affairs_funding_application | 实时 | 部门/学院 |
| 贷款在贷人数/金额 | LOAN 台账有效行 | result（LOAN） | 实时 | 学院；毕业年级单列 |
**⑮ 入口**：学生小程序=「资助」聚合页（奖学金/助学金/勤工岗位/贷款登记四入口+我的资助）；教师小程序=审批待办+本班获助一览；PC=`/admin/student-affairs/funding`（项目/批次/申请/评审/公示/结果/统计），部门筛选页对用工部门角色开放。
**⑯ 模块关系**：Student—application 挂主档；Workflow—四链复用引擎；Security—金额/银行信息加密脱敏、公示脱敏、导出二次确认；Dashboard—覆盖率指标；六大生命周期—奖学金校验读 t_acad_grade（学业过程域，只读）、处分校验读 t_cs_discipline、贷款提醒联动毕业批次、绿色通道（GREEN_CHANNEL 类型项目）与迎新 t_orientation_green_channel 数据打通（迎新缓交记录作为申请预填）。
**⑰ V1必做**：统一抽象五表、四类主链、资格校验器（处分/困难库/成绩三校验）、公示、result 台账。**P2P3**：学费减免/临时补助/绿色通道三小类完整流程（V1 仅建 project_type 占位+简链）、银行代发对接、量化评审打分。

### 3.8 违纪处分与解除（13A-08）

**① 角色四问**：发起=辅导员/学院学工（登记违纪）、学生（处分解除申请）；审核=学院初审 → 学工处复核 →（严重：留校察看/开除类）学校审批；处理=学院学工（送达）、辅导员（教育跟进）；查看=审批链、辅导员（本班）、学生本人（**仅本人生效处分的决定信息**，沿既有"学生端只回数量不回明细"策略在移动端保持，PC 无学生端）。
**② 前置条件**：登记须绑定在籍学生且事实材料≥1（file_id）；同一违纪事实不得重复立案（同学生+同事发时间+同类型提示疑似重复，人工确认后可继续）；解除申请须处分 EFFECTIVE 且满最短察看期（规则中心配置，按处分等级）。
**③ 主流程（处分）**：
1. 登记：`POST discipline/cases`（学生/违纪类型/事实经过/发生时间/建议处分等级：警告/严重警告/记过/留校察看/开除学籍/材料 file_ids）→ t_affairs_discipline_case（REGISTERED）。
2. startWorkflow(AFFAIRS_DISCIPLINE)：学院初审 → 学工处复核 →（sanction_level≥留校察看时追加）学校审批节点。各节点可改定性与等级（记录留痕）。
3. 终审通过 → EFFECTIVE：写决定字段（decision_no 文号/decision_date/sanction_level/decision_file_id）→ **同步写 t_cs_discipline（record_status=ACTIVE, case_id 反向引用）** → 送达：生成送达任务给辅导员（t_unified_todo），辅导员线下送达并上传签收（送达回证 file_id）→ WORKFLOW_RESULT（学生，仅"您有一份处分决定，请联系辅导员"级别措辞）。
4. 生效联动（自动）：奖学金资格校验即时拦截（读 t_cs_discipline）；评优/荣誉同口径；毕业资格审核读最新 record_status；生成 t_affairs_risk_record（source_type=DISCIPLINE，分派辅导员跟进教育）；360 事件 AFFAIRS_DISCIPLINE_EFFECTIVE。
**③′ 主流程（解除）**：
5. 学生小程序发起解除申请（满察看期后入口才开放）→ 表现材料（学习/活动/辅导员评语）→ t_affairs_discipline_remove_apply（REMOVE_REVIEW）。
6. workflow AFFAIRS_DISCIPLINE_REMOVE：辅导员初审（附察看期表现意见）→ 学院 → 学工处终审 → REMOVED：case 置 REMOVED + **t_cs_discipline.record_status=REMOVED** + 360 事件 AFFAIRS_DISCIPLINE_REMOVED（**保留处分历史，不删记录**）→ WORKFLOW_RESULT（学生）。毕业审核自动读到最新状态。
**④ 异常流程**：学生对处分申诉 → V1 线下受理、结果以"撤销"动作线上化：学工处执行 CANCELLED（须填撤销依据+文号，t_cs_discipline 行置 CANCELLED，360 事件更正）；开除学籍生效 → 提示联动教务学籍异动（13B 承接，学工侧只发 STATUS_CHANGED 给教务角色）。
**⑤ 退回流程**：任一节点退回 → RETURNED 回登记人补充事实材料 → 重新提交回学院初审；驳回 REJECTED=不予处分，立案终结（记录保留仅审批链可见，不写 t_cs_discipline，不进学生可见区）。
**⑥ 状态机**（枚举 11 态 + 转移表）：REGISTERED/COLLEGE_REVIEW/STUDENT_AFFAIRS_REVIEW/SCHOOL_REVIEW/EFFECTIVE/REJECTED/RETURNED/CANCELLED/REMOVE_REVIEW/REMOVED/ARCHIVED。
| From | 动作（角色） | To |
|---|---|---|
| REGISTERED | 提交（登记人） | COLLEGE_REVIEW |
| COLLEGE_REVIEW | 通过（学院学工） | STUDENT_AFFAIRS_REVIEW；退回 → RETURNED；驳回（不予处分） → REJECTED |
| STUDENT_AFFAIRS_REVIEW | 通过且 sanction_level<留校察看 | EFFECTIVE；≥留校察看 → SCHOOL_REVIEW |
| SCHOOL_REVIEW | 通过（学校） | EFFECTIVE；退回/驳回同上 |
| RETURNED | 补充重交（登记人） | COLLEGE_REVIEW |
| EFFECTIVE | 学生满察看期发起解除 | REMOVE_REVIEW；学工处撤销（申诉成立，填依据文号） → CANCELLED |
| REMOVE_REVIEW | 三级通过 | REMOVED；驳回 → EFFECTIVE（可再申请，间隔期规则中心配置） |
| REMOVED / CANCELLED | 归档批次 | ARCHIVED |
EFFECTIVE/REMOVED/CANCELLED 三态变化均同步 t_cs_discipline.record_status（ACTIVE/REMOVED/CANCELLED），同事务完成。
**⑦ 权限点**：`studentAffairs.discipline.register / .approve / .schoolApprove / .deliver / .removeApply（学生）/ .removeApprove / .view / .cancel / .export`。
**⑧ 数据范围**：登记=辅导员本班/学院本院；审批按节点角色；明细查看=审批链+`studentAffairs.discipline.view` 且 scope 命中；学生=本人（收敛字段）。
**⑨ 关键字段**：case（student_id/violation_type/fact_desc/occurred_at/suggest_level/sanction_level/decision_no/decision_date/decision_file_id/deliver_receipt_file_id/biz_status/workflow_instance_id/cs_discipline_id）；material（case_id/file_id/material_type=事实证据|谈话笔录|检讨）；remove_apply（case_id/perform_desc/proof_file_ids/counselor_opinion/biz_status）。
**⑩ 审批节点**：`AFFAIRS_DISCIPLINE`（COLLEGE→SA_OFFICE→[SCHOOL]）；`AFFAIRS_DISCIPLINE_REMOVE`（COUNSELOR→COLLEGE→SA_OFFICE）。
**⑪ 操作记录**：登记/改等级/审批/生效/送达签收/解除/撤销/查看明细/导出全审计；t_cs_discipline 变更走 t_affairs_audit_trail 双留痕。
**⑫ 消息通知**：待审→WORKFLOW_TODO；生效/解除结果→WORKFLOW_RESULT（学生，收敛措辞）；退回→RETURNED_NOTICE；送达任务→WORKFLOW_TODO（辅导员）；教务联动→STATUS_CHANGED。
**⑬ 学生360沉淀**：EFFECTIVE/REMOVED/CANCELLED 各写 stage_event；360 处分段读 t_cs_discipline（按查看人权限：辅导员及以上见明细，其他教师仅见"存在处分记录"，学生本人见决定信息）。
**⑭ 数据中心统计**（五要素定义）：
| 指标 | 口径 | 来源 | 频率 | 过滤/下钻 |
|---|---|---|---|---|
| 处分数/解除数 | case 按状态 EFFECTIVE/REMOVED 学年计数 | t_affairs_discipline_case | 实时 | 校/院/班；下钻需 .view 权限 |
| 现存生效处分数 | record_status=ACTIVE | t_cs_discipline | 实时 | 首页卡；毕业年级单列 |
| 类型/等级分布 | group by violation_type/sanction_level | case | 实时 | 学院 |
| 平均解除周期 | avg(removed_at - decision_date) | case | 日更 | 全校 |
**⑮ 入口**：学生小程序=「我的-处分与解除」（本人生效处分+解除申请）；教师小程序=登记（简表）+审批待办+送达确认；PC=`/admin/student-affairs/discipline`（登记/列表/审批/送达/解除审批/统计）。
**⑯ 模块关系**：Student—case 挂主档，不改主档；Workflow—双链+节点级改等级留痕；Security—明细分级可见是本业务安全核心，学生端字段收敛沿既有实现；Dashboard—处分指标；六大生命周期—毕业资格（13B）只读 t_cs_discipline 最新状态（§2.4 保证零改动）、奖助校验（3.7）、开除→学籍异动（13B）。
**⑰ V1必做**：立案双链、t_cs_discipline 同步、送达、解除、四联动。**P2P3**：申诉线上化、处分文书模板生成、违纪行为分析。
**⑱ 现场确认**：处分等级枚举与最短察看期？哪一级需校长办公会（SCHOOL 节点触发条件）？学生本人可见明细边界？申诉流程线上化时点？

### 3.9 心理关注与风险预警（13A-09）

**① 角色四问**：发起=系统（规则命中自动建）+ 人工（辅导员/心理老师/宿管/任何教师"人工标记"，宿管限宿舍来源）；审核=无审批链（处置型业务，升级需上级确认）；处理=按责任规则分派——学业类→辅导员（教务侧另有 t_acad_warning 闭环）、心理类→心理老师+授权辅导员、宿舍类→宿管+辅导员、实习类→指导教师+辅导员、其余→辅导员；查看=处理人、学院学工、学工处；**普通教师只见"需关注"标记，不见来源明细；学生/家长不可见**。
**② 前置条件**：自动建：同一学生+同 source_type+同 source_ref_id 未关闭时不重复建（幂等去重，命中则追加一条 handle 流水"再次触发"）；人工标记须填来源说明≥10 字。
**③ 主流程**：
1. 风险产生：来源枚举 source_type = MENTAL（t_cs_mental_record）/ ACAD_WARNING（t_acad_warning，引用不接管）/ LEAVE_OVERDUE（t_cs_leave）/ DORM_EXCEPTION（t_cs_dorm_exception，含夜不归宿）/ DISCIPLINE（t_cs_discipline）/ LONG_NO_LOGIN（登录日志扫描）/ INTERNSHIP_ABNORMAL（t_internship_* 异常）/ EMPLOYMENT_ABNORMAL / FAMILY_DIFFICULTY（困难库变动）/ MANUAL / FAMILY_FEEDBACK。写 t_affairs_risk_record（NEW，risk_level=LOW/MEDIUM/HIGH/CRITICAL 按来源默认+规则中心可配）。
2. 分派：按责任规则矩阵自动定 assignee（见 ①），写 ASSIGNED + t_unified_todo + RISK_ALERT 消息；无法自动定人（如学生无辅导员）→ 挂学院学工池人工认领。
3. 处置：处理人填处置记录（t_affairs_risk_handle，handle_type=HANDLE，措施/结果）→ PROCESSING；需持续观察 → FOLLOWING（设下次跟进日期，到期 DEADLINE_REMINDER）。
4. 流转：转办（TRANSFERRED，换 assignee，原因必填）；升级（ESCALATED，risk_level 上调+通知学院学工/学工处 RISK_ALERT）；可一键发起谈心谈话（预填学生与主题，3.10）或家校联系（P2，V1 记入 handle 流水"已电话联系家长"文本）。
5. 关闭：处理人填关闭结论（handle_type=CLOSE，结论≥10 字）→ CLOSED → 360 事件 AFFAIRS_RISK_CLOSED；同源再触发 → REOPENED（保留历史流水）。
**④ 异常流程**：ACAD_WARNING 来源特殊——**教务预警在 t_acad_warning 自闭环**（PENDING_HANDLE/PROCESSING/ESCALATED/CLOSED），风险中心仅镜像引用：t_acad_warning 关闭时联动关闭风险记录（订阅其状态变更），风险中心关闭**不反向关闭**教务预警；CRITICAL 级 72h 未处置 → 自动升级并通知学工处。
**⑤ 退回流程**：无审批退回；转办被拒 → 回原处理人（流水留痕）。
**⑥ 状态机**（枚举 8 态 + 转移表）：
| From | 动作 | To |
|---|---|---|
| NEW | 自动/人工分派 | ASSIGNED |
| ASSIGNED | 首次处置流水 | PROCESSING |
| PROCESSING | 设跟进日期 | FOLLOWING；填关闭结论 → CLOSED |
| FOLLOWING | 跟进处置 | PROCESSING；直接关闭 → CLOSED |
| ASSIGNED/PROCESSING/FOLLOWING | 转办（换 assignee） | 态不变，流水 TRANSFERRED |
| ASSIGNED/PROCESSING/FOLLOWING | 升级（risk_level 上调+通知上级） | 态不变，流水 ESCALATED |
| CLOSED | 同源再触发（系统） | REOPENED → 自动重分派回 ASSIGNED |
非法转移 409001；TRANSFERRED/ESCALATED 为流水事件而非驻留状态（记录于 handle 表，主状态保持在途）。
**责任分派矩阵**（默认，规则中心可配）：
| source_type | 首责 | 协同 | 默认等级 |
|---|---|---|---|
| MENTAL | 心理老师 | 授权辅导员 | HIGH |
| ACAD_WARNING | 辅导员 | 学院教务员（教务侧自有闭环） | MEDIUM |
| LEAVE_OVERDUE | 辅导员 | — | MEDIUM（逾期>3 天升 HIGH） |
| DORM_EXCEPTION（夜不归宿） | 宿管 | 辅导员 | HIGH |
| DISCIPLINE | 辅导员 | 学院学工 | MEDIUM |
| INTERNSHIP_ABNORMAL | 实习指导教师 | 辅导员 | MEDIUM |
| LONG_NO_LOGIN / EMPLOYMENT_ABNORMAL / FAMILY_DIFFICULTY / FAMILY_FEEDBACK / MANUAL | 辅导员 | 视来源 | LOW/MEDIUM |
**⑦ 权限点**：`studentAffairs.risk.view / .create（人工标记）/ .handle / .transfer / .escalate / .close / .mental.view（心理来源明细）/ .export`。
**⑧ 数据范围**：处理人=被分派记录；辅导员=本班全部风险（心理来源仅"需关注"级，明细需 PSY_STUDENT 授权）；心理老师=PSY_STUDENT；宿管=本楼 DORM_EXCEPTION 来源；学院/学工处=本院/全校。**导出默认不含心理明细**（导出列配置硬编码排除，需含时走敏感二次确认+审计）。
**⑨ 关键字段**：risk_record（student_id/source_type/source_ref_id/risk_level/assignee_id/biz_status/next_follow_at/closed_at/close_conclusion）；risk_handle（risk_id/handle_type=HANDLE|TRANSFER|ESCALATE|CLOSE|REOPEN/content/from_user/to_user/created_at，append-only）。
**⑩ 审批节点**：无 workflow（处置型）；升级通知走消息不走审批。
**⑪ 操作记录**：建立/分派/每条处置/转办/升级/关闭/重开全为 append-only 流水即留痕；查看心理来源明细审计。
**⑫ 消息通知**：新风险/升级→RISK_ALERT（处理人/上级）；跟进到期→DEADLINE_REMINDER；关闭→STATUS_CHANGED（关注人）；转办→WORKFLOW_TODO（新处理人，todo_type=RISK_HANDLE）。
**⑬ 学生360沉淀**：CLOSED 写 stage_event（摘要不含心理细节）；360 风险段=当前未关闭最高等级+历史计数（明细按权限）。
**⑭ 数据中心统计**（五要素定义）：
| 指标 | 口径 | 来源 | 频率 | 过滤/下钻 |
|---|---|---|---|---|
| 未关闭风险数 | biz_status∉{CLOSED} group by risk_level/source_type | t_affairs_risk_record | 实时 | 校/院/班/处理人；心理来源下钻需权限 |
| 平均处置时长 | avg(closed_at - created_at) | 同上 | 日更 | 来源维度 |
| 心理关注数 | t_cs_mental_record 有效行 | t_cs_mental_record | 实时 | 仅授权角色卡片可见 |
| 升级率 | 含 ESCALATED 流水的风险 / 总数 | t_affairs_risk_handle | 日更 | 学院 |
| 重开率 | REOPENED 次数 / 关闭数 | 同上 | 日更 | 处置质量参考 |
**⑮ 入口**：学生小程序=无（对学生不可见）；教师小程序=工作台"风险学生"列表+处置页（填流水/关闭）；PC=`/admin/student-affairs/risk`（列表/详情/处置/规则配置/统计）。
**⑯ 模块关系**：Student—风险等级进画像；Workflow—不用（刻意决策：处置流水比审批链贴合业务）；Security—心理明细最小可见+导出排除；Dashboard—首页风险卡与驾驶舱风险页共用口径；六大生命周期—实习异常由实习域 t_internship_risk_record 触发（域内已实现转风险的沿用其钩子）、学业预警引用 t_acad_warning、就业异常读就业域。
**⑰ V1必做**：11 类来源接入（LONG_NO_LOGIN/EMPLOYMENT_ABNORMAL 可 V1.1）、分派矩阵、流水处置、双向联动关闭（LEAVE_OVERDUE/ACAD_WARNING）。**P2P3**：行为大数据预警模型、心理测评量表集成、家校反馈入口。
**⑱ 现场确认**：分派矩阵按学校组织确认（是否有专职心理中心）？CRITICAL 自动升级时限？心理明细可见角色终表？

### 3.10 谈心谈话（13A-10）

**① 角色四问**：发起=辅导员/班主任/心理老师（建计划或直接补录）；审核=无审批；处理=发起人本人（填记录、定跟进）；查看=本人记录本人及上级（学院/学工处见工作量与列表，心理类记录内容权限同 3.9）；学生=小程序可见"待谈话邀约"（时间地点），**不可见谈话记录内容**。
**② 前置条件**：谈话对象在发起人 scope 内；从风险/预警一键发起时自动带 related_risk_id。
**③ 主流程**：
1. 建计划：`POST talks/plans`（学生[可多选]/主题类型：日常|学业|心理|违纪|就业|实习|困难帮扶|宿舍异常/约定时间地点）→ t_affairs_talk_plan（PLANNED）→ 学生端 STATUS_CHANGED 邀约通知。
2. 谈话完成 → 填记录：`POST talks/records`（plan_id 可空=临时补录/实际时间/内容纪要/学生状态评估/是否需跟进）→ plan 置 DONE。
3. 跟进判断：需跟进 → 建下次计划（链式 prev_record_id）或一键转风险（写 t_affairs_risk_record source_type=MANUAL 带谈话引用）/转家校（V1 记文本，P2 建联系单）。
4. 关联闭环：related_risk_id 非空时，记录保存自动追加一条风险处置流水（handle_type=HANDLE，content="完成谈心谈话"+摘要链接）。
5. 360 事件 AFFAIRS_TALK_DONE（仅"完成 X 类谈话"，内容不进时间线）。
**④ 异常流程**：学生爽约 → plan 置 MISSED（可重约，计入学生配合度备注）；心理类谈话记录保存时强敏感标记（content 加密列），非授权角色列表中仅显示"心理类谈话 1 次"。
**⑤ 退回流程**：无；记录保存后 24h 内可修正（版本留痕），超时只可追加补充说明。
**⑥ 状态机**：plan：PLANNED/DONE/MISSED/CANCELLED；record 无状态（append 型，带 need_follow 标记）。
**⑦ 权限点**：`studentAffairs.talk.plan / .record / .view / .psyContent.view / .stats.view`。
**⑧ 数据范围**：发起人=自己创建的计划与记录+本班学生；学院/学工处=范围内列表与统计（心理内容按 3.9 规则裁剪）。
**⑨ 关键字段**：plan（student_ids/topic_type/plan_time/place/related_risk_id/biz_status）；record（plan_id/student_id/talk_time/content[心理类 content_encrypted]/student_state_eval/need_follow/prev_record_id）。
**⑩ 审批节点**：无。
**⑪ 操作记录**：记录创建/修正/查看心理内容审计；工作量统计以 record 计数。
**⑫ 消息通知**：邀约→STATUS_CHANGED（学生）；跟进到期→DEADLINE_REMINDER（发起人）。
**⑬ 学生360沉淀**：record 保存即写 stage_event（收敛摘要）；360 谈话段=次数+类型分布+最近一次（内容按权限）。
**⑭ 数据中心统计**：谈话完成率（DONE/(PLANNED+DONE+MISSED)）、辅导员人均谈话数（工作量，供辅导员考评 P2 复用）、风险关联谈话占比；实时、scope、下钻。
**⑮ 入口**：学生小程序=「消息-谈话邀约」（确认/改约请求）；教师小程序=快速补录（高频！语音转文字 P2）+我的计划；PC=`/admin/student-affairs/talks`（计划/记录/统计）。
**⑯ 模块关系**：Student—对象校验走 scope；Workflow—无；Security—心理类内容加密+裁剪；Dashboard—完成率进首页辅导员卡；六大生命周期—就业/实习类谈话可从就业跟进（t_emp_followup）/实习异常页一键发起（带来源引用）。
**⑰ V1必做**：计划/记录/跟进链/风险联动/工作量统计。**P2P3**：谈话模板库、语音录入、家校联动单。
**⑱ 现场确认**：谈话记录是否要求学生签认？心理类谈话是否强制心理老师复核？工作量是否纳入考评口径？

### 3.11 宿舍基础（13A-11：房源/入住/调宿/检查/夜不归宿）

**① 角色四问**：发起=宿管中心（房源维护/检查任务）、学生（调宿申请）、宿管（检查记录/夜不归宿登记）；审核=调宿：辅导员→宿管（目标床位校验）；处理=宿管（入住/退宿执行）、辅导员（异常跟进）；查看=学生（本人宿舍）、宿管（本楼）、辅导员（本班学生住宿）、学院/学工处（汇总）。
**② 前置条件**：房源结构已维护（楼/层/房/床，床位唯一编码）；调宿须目标床位 VACANT 且性别/楼栋规则匹配；检查任务须绑定楼栋与检查人。
**③ 主流程**：
1. 房源维护：`POST dorm/buildings|rooms|beds` 建楼/层/房/床（房间属性：性别/容量/类型；床位状态 VACANT/OCCUPIED/DISABLED）；**迎新分宿对齐**：orientation 的 building/room 文本值建立映射字典 → 迁移脚本将存量 t_cs_dorm_record 挂接 bed_id（对不上的进人工对账清单，不阻塞上线）。
2. 入住/退宿：宿管执行 `POST dorm/check-in|check-out` → 写/更新 t_cs_dorm_record（扩展 bed_id）+ 床位占用翻转（事务内，防超占：床位行乐观锁）。
3. 调宿：学生小程序发起（原因枚举+说明）→ t_affairs_dorm_change（SUBMITTED）→ workflow AFFAIRS_DORM_CHANGE：辅导员审 → 宿管审（**审批时二次校验目标床位仍 VACANT**，被占则退回改选）→ APPROVED → 事务：原床释放、新床占用、t_cs_dorm_record 更新 → 360 事件 AFFAIRS_DORM_CHANGED → WORKFLOW_RESULT。
4. 宿舍检查：宿管中心建任务（楼栋/日期/检查项模板：卫生/安全/违禁品/夜不归宿）→ 宿管按房逐项打分/记录 → t_affairs_dorm_inspection(_item) → 异常项（违禁/夜不归宿/严重卫生）**同时写 t_cs_dorm_exception** → STATUS_CHANGED 同步辅导员。
5. 夜不归宿：检查中登记或宿管单独登记 → t_cs_dorm_exception（type=NIGHT_ABSENT）→ **自动建风险**（source_type=DORM_EXCEPTION，分派宿管+辅导员，§3.9）→ 辅导员联系学生/家长 → 风险闭环（§5-5）。
6. 检查结果进统计与班级/楼栋画像；文明寝室评比 P2 基于检查分累计。
**④ 异常流程**：调宿目标床位并发被占 → 409 + 引导改选；退宿时存在未销假单/在途调宿 → 提示确认；床位 DISABLED（维修）时批量迁移向导（P2，V1 逐个调整）。
**⑤ 退回流程**：调宿被退回 → RETURNED 学生改目标床位重新提交 → 回辅导员节点；检查记录 24h 内可修正（留痕）。
**⑥ 状态机**：
- dorm_change 转移表：
| From | 动作（角色） | To |
|---|---|---|
| SUBMITTED | 系统建流 | COUNSELOR_REVIEW |
| COUNSELOR_REVIEW | 通过（辅导员） | DORM_ADMIN_REVIEW；退回 → RETURNED；驳回 → REJECTED |
| DORM_ADMIN_REVIEW | 通过（宿管，二次校验床位 VACANT） | APPROVED（事务换床）；床位已被占 → RETURNED（改选） |
| RETURNED | 修改重交（学生） | COUNSELOR_REVIEW |
| SUBMITTED~审批中 | 撤销（学生） | CANCELLED |
- bed：VACANT⇄OCCUPIED（入住/退宿/调宿，乐观锁翻转）；任意→DISABLED（维修，需先空床）。
- inspection：PLANNED→IN_PROGRESS→DONE（DONE 后 24h 内可修正条目，留痕）。
**⑦ 权限点**：`studentAffairs.dorm.resource.manage / .checkin / .change.apply（学生）/ .change.approve / .inspection.manage / .inspection.input / .exception.handle / .export`。
**⑧ 数据范围**：宿管=DORM_BUILDING scope（本楼栋房床/检查/异常）；学生=本人宿舍；辅导员=本班学生住宿+异常；学院/学工处=汇总。
**⑨ 关键字段**：building（name/campus/gender_rule）；room（building_id/floor/room_no/capacity/gender/room_type）；bed（room_id/bed_no/status/version）；dorm_change（student_id/from_bed_id/to_bed_id/reason_type/reason/biz_status/workflow_instance_id）；inspection（building_id/inspect_date/inspector_id/biz_status）+item（inspection_id/room_id/item_type/score/abnormal_flag/detail/photo_file_ids/cs_exception_id）。
**⑩ 审批节点**：`AFFAIRS_DORM_CHANGE`（COUNSELOR→DORM_ADMIN）；房源与检查无审批（直接操作+审计）。
**⑪ 操作记录**：房源变更/入退宿/调宿审批/检查提交/异常登记/导入（宿舍分配、检查结果两个导入 domain）全审计。
**⑫ 消息通知**：调宿待审→WORKFLOW_TODO；结果→WORKFLOW_RESULT；退回→RETURNED_NOTICE；检查异常→STATUS_CHANGED（辅导员）；夜不归宿→RISK_ALERT（走风险）。
**⑬ 学生360沉淀**：入住/调宿写 stage_event；360 宿舍段=当前床位+异常计数（读 t_cs_dorm_record/t_cs_dorm_exception）。
**⑭ 数据中心统计**（五要素定义）：
| 指标 | 口径 | 来源 | 频率 | 过滤/下钻 |
|---|---|---|---|---|

### 3.12 学工材料归档（13A-14）

**① 角色四问**：发起=学工处（建归档批次）；审核=学院学工（完整性审核）→ 学工处（确认归档）；处理=辅导员（补缺材料）；查看=学工处/学院（归档包）、审计角色。
**② 前置条件**：批次限定学年/范围（毕业年级或全体）；被归档业务须为终态（CLOSED/APPROVED/REMOVED/ARCHIVED 前置态）。
**③ 主流程**：
1. 建批次：`POST archive/batches`（学年/范围/材料清单模板：请假/奖助/困难/处分与解除/谈话/心理风险[目录级]/宿舍/活动/家校/风险处置/辅导员日志/班级材料）→ DRAFT→GENERATING。
2. 系统按学生生成档案包骨架 t_affairs_archive_package（student_id/batch_id）+ t_affairs_archive_item（module_code/biz_id/item_status=AUTO_FILLED|MISSING）：自动抓取各域终态记录与其 file_id。
3. 缺项 → 生成辅导员补缺待办（t_unified_todo 按班分派）→ 辅导员上传补充/标注"无此项"（理由）→ item 齐备。
4. 学院完整性审核：按班抽检/逐包核对 → 不合格退回辅导员（RETURNED_NOTICE）→ 合格提交学工处。
5. 学工处确认 → 生成正式归档包：走既有导出管线（水印+sha256+t_export_task 留痕）→ 批次 ARCHIVED → 各源业务记录联动置 ARCHIVED（只读）→ 360 事件 AFFAIRS_ARCHIVED + ARCHIVE_NOTICE。
6. 归档后访问：只读、带水印预览、每次访问审计；**心理明细默认不入包**（仅目录级"存在心理关注记录 N 条"，完整包需专项授权）。
**④ 异常流程**：在途业务（未终态）→ 生成"待办清单"阻塞该生归档（不阻塞批次其他学生）；归档后发现错漏 → 学工处发起"补档"（新版本包，旧包保留，版本号+1）。
**⑤ 退回流程**：学院审核退回 → 包回辅导员补缺态；学工处退回 → 回学院。
**⑥ 状态机**（batch 6 态 / package 6 态 + 转移表）：
| 层级 | From | 动作（角色） | To |
|---|---|---|---|
| batch | DRAFT | 启动生成（学工处） | GENERATING → 骨架完成自动 → SUPPLEMENTING |
| batch | SUPPLEMENTING | 学院提交审核 | COLLEGE_REVIEW → 通过 → SA_CONFIRM → 确认 → ARCHIVED |
| batch | COLLEGE_REVIEW/SA_CONFIRM | 退回 | SUPPLEMENTING（RETURNED_NOTICE） |
| package | GENERATED | 存在 MISSING 项 | SUPPLEMENTING；无缺项 → READY |
| package | SUPPLEMENTING | 辅导员补齐/标注无此项 | READY |
| package | READY | 学院抽检不合格 | RETURNED → 补缺后回 READY |
| package | READY | 学工处确认（批次级） | ARCHIVED → 补档 → RE_ARCHIVED（版本+1，旧包保留） |
**⑦ 权限点**：`studentAffairs.archive.batch.manage / .supplement / .collegeReview / .confirm / .package.view / .export`。
**⑧ 数据范围**：辅导员=本班包补缺；学院=本院包审核；学工处=全校。
**⑨ 关键字段**：batch（academic_year/scope_json/checklist_json/biz_status）；package（batch_id/student_id/version/biz_status/export_task_id）；item（package_id/module_code/biz_id/file_id/item_status/missing_reason）。
**⑩ 审批节点**：`AFFAIRS_ARCHIVE`（COLLEGE→SA_OFFICE），任务粒度=按学院打包审核（非逐学生 workflow，逐生用 todo）。
**⑪ 操作记录**：批次操作/补缺/审核/确认/每次归档包访问与下载（t_export_task+file 访问审计）。
**⑫ 消息通知**：补缺→WORKFLOW_TODO（辅导员）；退回→RETURNED_NOTICE；完成→ARCHIVE_NOTICE（相关角色）；临期未补→DEADLINE_REMINDER。
**⑬ 学生360沉淀**：归档完成写 stage_event（AFFAIRS_ARCHIVED）；360 显示"学工档案已归档（批次/年度）"。
**⑭ 数据中心统计**：归档率（ARCHIVED 包/应归档生数，进首页学工处卡）、补缺完成率（辅导员维度，进完成率）；实时、下钻到班。
**⑮ 入口**：学生小程序=无；教师小程序=补缺待办（可拍照上传）；PC=`/admin/student-affairs/archive`（批次/包列表/补缺/审核/确认）。
**⑯ 模块关系**：Student—包挂主档；Workflow—学院/学工处两级；Security—水印/sha256/访问审计/心理不入包；Dashboard—归档率；六大生命周期—毕业批次归档与教务归档（13B）、就业档案转递互为清单项（互相引用不复制文件）。
**⑰ V1必做**：批次/自动抓取/补缺/两级审/水印包/联动置 ARCHIVED。**P2P3**：档案馆系统对接、按国家学籍档案标准编目。
**⑱ 现场确认**：归档清单目录（校档案室要求）？纸质档案并行要求？心理材料入档政策？

## 4. P2/P3 业务精简设计（目标 / 角色 / 主流程 / 状态要点 / 联动 / 确认问题）

### 4.1 智能排宿（P2）
- 目标：新生/调整批量分床，规则化生成+人工微调，替代 Excel 排宿。
- 角色：宿管中心（建方案）、学院（确认）、学生（查看结果）。
- 主流程：选批次学生范围 → 配规则（学院聚集/专业/班级同房优先/性别硬约束/年级/特殊需求标记）→ 生成方案（床位分配草案）→ 人工拖拽调整 → 学院确认 → 发布（批量写 t_cs_dorm_record+床位占用，事务分片）→ 学生小程序可见 → 360。
- 状态要点：方案 DRAFT/GENERATED/ADJUSTING/COLLEGE_CONFIRM/PUBLISHED/CANCELLED；发布前不锁床位，发布时逐床校验冲突。
- 联动：房源/床位复用 3.11；与迎新分宿的关系=迎新期由排宿方案供数（orientation 读结果展示）。

### 4.2 学生活动 / 志愿服务 / 第二课堂（P2）
- 目标：活动全流程（发布→报名→签到→学时/积分）沉淀第二课堂记录。
- 角色：学工处/学院/社团（发布）、学生（报名签到）、负责人（确认名单）。
- 主流程：发布（范围/人数/时间/地点/学时分值）→ 报名（范围与人数校验、时间冲突提示）→ 签到（扫码/定位）→ 负责人确认名单 → 生成 t_affairs_activity_credit（学时/德育积分流水）→ 360 事件 + 第二课堂记录。志愿服务同构（项目→报名→负责人审核→签到→时长确认）。
- 状态要点：活动 DRAFT/PUBLISHED/ENROLLING/ONGOING/FINISHED/CREDIT_CONFIRMED/ARCHIVED；报名 ENROLLED/WAITLIST/CANCELLED/CHECKED_IN/CONFIRMED。
- 联动：积分供综合测评/评优引用；活动参与率进数据中心；奖学金评审可读积分。
- 确认：德育积分规则细则？是否已有第二课堂平台需对接（需求 §9 明示待确认）？

### 4.3 社团管理 / 学生组织（P2）
- 目标：社团注册、换届、成员、活动挂靠。

### 4.4 党团建设（P2/P3）
- 目标：团员/入党申请人-积极分子-发展对象-预备-正式的阶段台账（不做组织生活全流程）。
- 角色：学生、组织委员/辅导员、学院党委、学校党委。
- 主流程：阶段登记（材料+时间节点）→ 按阶段规则校验时长（如积极分子≥1 年）→ 上级确认 → 阶段推进 → 360 政治面貌更新（回写 t_student_profile 政治面貌字典字段——**唯一允许回写主档的学工业务**，走学生中心更正接口不直写）。
- 状态要点：阶段枚举即状态机（APPLICANT/ACTIVIST/DEVELOPMENT/PROBATIONARY/FULL_MEMBER），只进不退（特殊回退需学校党委权限+审计）。
- 确认：是否对接智慧党建系统（若有则本模块只读镜像）？
### 4.5 辅导员考评（P2）
- 目标：以系统留痕自动生成工作量（谈话数/待办完成率/风险处置时长/归档率/带班数），叠加学院打分出考评。

- 状态要点：周期 DRAFT/COLLECTING/SCORING/CONFIRMING/PUBLISHED/ARCHIVED。
- 联动：指标口径与 3.2/3.10/3.9/3.12 完全一致（同一 stats 函数），杜绝两套数。
- 确认：考评指标权重与申诉机制？

### 4.6 心理测评深度集成（P2/P3）
- 目标：量表测评（SCL-90/UPI 等）计划-作答-预警分级，接入风险中心。
- 角色：心理老师（计划/解读）、学生（作答）、辅导员（仅"需关注"结论）。
- 主流程：建测评计划（量表/范围/窗口）→ 学生小程序作答（断点续答）→ 自动计分分级 → 高危即时 RISK_ALERT（心理老师）→ 人工复核 → 写 t_cs_mental_record（关注结论）→ 转风险（source_type=MENTAL）。

- 红线：原始答卷与分数仅心理老师可见；任何导出不含题目级数据；量表版权合规现场确认。
- 确认：学校用哪些量表？是否已购第三方心理平台（若有走对接不自建）？

### 4.7 家校联系与家长端（P2/P3）
- 目标：家长触达通道（V1 仅"记录联系"文本；P2 联系单+短信；P3 家长小程序只读端）。

### 4.8 荣誉称号 / 综合测评 / 学费减免 / 临时补助 / 绿色通道（P2 小类）

### 5.1 核心验收用例基线（每流程 ≥4 条，必含重复提交与越权；页面级文档在此基线上扩展）

**请假闭环**：
1. 学生 A 提交 2 天病假（含材料）→ t_cs_leave 生成 affairs_status=COUNSELOR_REVIEW → 辅导员 t_unified_todo 出现待办 → 学生"我的请假"显示审批中。
2. 辅导员通过 → APPROVED → 学生收 WORKFLOW_RESULT → 旧 status 列同步为 APPROVED（兼容校验）。
3. 学生 A 用相同 request_id 重复提交 → 仅一条单据，二次请求 409001（IDEMPOTENCY）；时间区间重叠新单 → 409001（冲突明示）。
4. 学生 A 请求 `GET /mobile/affairs/leave/{B的单据id}` → 404001/403001 且写越权审计。
5. 结束时间过后未销假 → 定时任务置 OVERDUE → 自动生成风险记录且同源不重复 → 补销假确认后单据 CLOSED、同源风险联动 CLOSED。
6. 8 天长假 → 审批链自动含学工处节点；辅导员通过后学院待办出现（链路裁剪正确性）。

**困难认定**：
1. 窗口内提交 → CLASS_REVIEW 前学生可撤；窗口外提交 422001。
2. 同批次二次提交 → 唯一约束 409001。
3. 非授权教师请求家庭经济完整值 → 403001+审计；授权者查看须填原因且落审计（含 traceId）。
4. 公示期异议成立 → 回 SCHOOL_REVIEW，处理结论留痕；期满自动 APPROVED 并写 level_history。

**处分与解除**：
1. 记过处分终审通过 → case=EFFECTIVE 且 t_cs_discipline 新增 ACTIVE 行（同事务）；学生移动端仅见数量与决定信息。
2. 该生申请奖学金 → 资格校验 422 明示"存在未解除处分"。
3. 未满察看期发起解除 → 入口关闭/422；满期解除通过 → REMOVED 且 t_cs_discipline 行同步 REMOVED，毕业预审（13B 模拟）读到最新状态。
4. 已处理的审批任务被再次 approve → 409 APPROVAL_VERSION_CONFLICT。

**风险处置**：
1. 夜不归宿登记 → t_cs_dorm_exception + 风险自动生成并分派宿管+辅导员，双方收 RISK_ALERT。
2. 同一学生同源再登记（未关闭）→ 不重复建，追加流水。
3. 非处理人调用 close → 403001；处理人关闭须结论≥10 字否则 422001。
4. 普通任课教师查看该生画像 → 只见"需关注"标记，心理段整体不返回。

**调宿**：
1. 提交→辅导员→宿管通过 → 原床 VACANT、新床 OCCUPIED、dorm_record 更新（事务原子性：中断任一步全回滚）。
2. 两学生并发申请同一床位 → 后审批者宿管节点校验失败退回改选。
3. 学生撤销在途申请 → CANCELLED，待办撤回。
4. 宿管操作非本楼床位 → 403002（scope）。

## 7. 风险与冲突说明（对照《集成事实速查》自查结论）

**自查结论：本册与速查无原则性冲突；以下 5 点为已识别的差异/风险，须在实施前确认处理方式。**

1. **响应结构两套口径**：速查（代码事实）为 `{code(数字), bizCode(字符串), …}`；`docs/api/00-API契约冻结总册.md` 为 `code` 字符串业务码（"SUCCESS"）。**本册一律遵循速查（代码为准）**；API 契约总册该章节属于历史设计稿，13A API 明细文档编写时应显式声明沿用数字 code + bizCode，避免开发按旧册实现。
2. **分端前缀两套口径**：API 契约总册使用 `/api/v1/student-mini|teacher-mobile/*`；速查（代码事实）为 `/api/v1/mobile/*`、`/api/v1/mobile/teacher/*`。本册遵循速查；同理 PC 无 `/api/v1/admin` 前缀（require_staff 中间件区分）。
3. **数据库冻结总册中的 `t_leave`**：DB 冻结册教师移动映射章节引用了 `t_leave`（旧设计名）；实际代码为 `t_cs_leave`。本册按代码事实扩展 t_cs_leave；13A DDL 文档须在迁移说明中注明该命名差异，防止误建 t_leave。
4. **t_cs_leave 旧状态列的双写窗口**：§2.3 兼容映射存在双状态列（status/affairs_status）并行期，旧端点与新状态机若被并发调用可能出现映射瞬时不一致。缓解：旧 approve/return 端点改为代理新状态机（同事务内同步两列），P2 下线旧端点后移除 status 列。demo-school 只读锁环境不受影响；sandbox-school 每晚重置，迁移脚本须纳入其种子流程。
5. **t_acad_warning 与风险中心的双状态并存**：§3.9 采用"引用不接管"，存在两处状态（教务预警态/风险镜像态）。已定单向联动（教务关闭→风险关闭），反向不联动是**有意设计**（学工关闭关注不代表学业问题解决）；需在现场培训中明确口径，防止辅导员误以为关闭风险即处理了预警。
6. 其余对齐项复核通过：审批全部落 t_workflow_*（无自建审批表）；通知全部落 t_unified_todo/t_unified_message（8 类消息未新增）；scope 复用 t_teacher_student_scope（仅新增枚举值）；导入导出走既有 domain 管线；规则入平台规则中心；学生无 PC 入口；心理/处分/宿舍/请假四处均基于 t_cs_* 扩展未平行建表。
