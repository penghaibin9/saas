# 13A/13B 学校参数配置中心设计

> 版本：V1.0（2026-07-05）
> 定位：**不新建任何配置系统**。13A 学工中心 / 13B 教务中心的全部可配置参数，一律接入现有平台规则中心（`t_platform_config` + `safe_rule` 机制），并在其上补齐"学校管理端可改的参数子集"分层。
> 依据（必读输入）：`_13-现有系统集成事实速查.md` §11、`_13-需求输入-V1.1.md` §9、《13A-13B-现有代码库融合证据报告》§1.14 / 2.4、《13A-13B-V1范围冻结表》§9。
> 命名裁定沿用证据报告 2.4：13A 规则键前缀 `studentAffairs.*`、13B 规则键前缀 `academicAffairs.*`。

## 一、现有平台规则中心机制核实（以代码为准，逐条给证据路径）

### 1.1 存储层：t_platform_config（控制面 KV，已存在）

- 发现于：`backend/app/models/platform.py` 第 13–26 行。`PlatformConfig.__tablename__ = "t_platform_config"`，唯一键 `(tenant_id, config_type, config_key)`；`tenant_id=0` 表示全局默认，否则为租户覆盖；`config_json` 存 JSON 载荷。
- 已占用的 `config_type`（模型注释实读）：`PACKAGE / FEATURES / RULES / WORKFLOWS / DICT / BRAND / SECURITY`，另有 `TENANT_META / SETTINGS`（`platform_service.py` 实际写入）。
- **结论：13A/13B 参数落 `config_type="RULES"`，与现有 9 组规则同表同机制，零新表。**

### 1.2 默认值层：platform_defaults.DEFAULT_RULES（9 组，已存在）

- 发现于：`backend/app/services/platform_defaults.py` 第 32–57 行。现有 9 组：`student / approval / import / export / file / risk / message / security / trial`。
- 每组是"键 → 标量默认值"的扁平字典（bool/int/str 三型）。

### 1.3 合并与读取层：effective_rules / rule / safe_rule（已存在）

发现于：`backend/app/services/platform_service.py`。

| 函数 | 行号 | 行为 |
|---|---|---|
| `effective_rules(tenant_id)` | 90–96 | 复制 `DEFAULT_RULES` → 叠加租户 `RULES` 覆盖（仅允许已知分组、dict 结构） |
| `rule(tenant_id, group, key)` | 99–100 | 取合并结果；缺失时回落 `DEFAULT_RULES[group][key]` |
| `safe_rule(tenant_id, group, key)` | 451–455 | **任何异常（含 DB 不可用）一律返回默认值**——非法值/故障兜底的唯一出口 |
| `validate_rules(payload)` | 144–159 | 保存校验：未知分组/未知键拒绝（422 VALIDATION_ERROR）；按默认值类型强校验（bool 必须 bool，int 必须 0~1000000 整数） |
| `feature_enabled(tenant_id, key)` | 443–448 | 功能开关检查，异常默认放行（模块开关走此链，见文件二） |

### 1.4 API 层：/api/v1/platform（仅 PLATFORM_SUPER_ADMIN，已存在）

发现于：`backend/app/api/v1/platform.py`。

| 端点 | 说明 |
|---|---|
| `GET /platform/rules/defaults` | 平台默认规则（9 组） |

### 1.5 前端入口（已存在）

- 平台运营端：`/admin/platform/rules`「规则与功能开关」页——发现于 `frontend/src/config/adminMenu.js` platform 分组与 `frontend/src/modules/platform/platform.routes.js`。
- 学校管理端：`/admin/system/config`「系统与品牌配置」页已存在（`frontend/src/modules/system/system.routes.js` 第 51–54 行，permissionKey `system.config.view`）——**当前不含业务规则编辑**，本设计在其旁新增两个模块配置页（见 §4.5）。

### 1.6 业务侧消费范例（已存在，13A/13B 照此模式接入）

- `backend/app/services/approval_service.py` 第 113–119 行：`safe_rule(tid, "approval", "rejectReasonRequired") / ("approval", "rejectReasonMinLength")`——驳回原因规则。
- `backend/app/services/file_service.py` 第 118–129 行：`safe_rule(tid, "file", "uploadMaxSizeMb")` 与 `feature_enabled(tid, "fileUpload")`。
- **模式冻结：业务 service 在写路径校验点调用 `safe_rule`，不在 API 层读配置，不自建配置缓存。**

## 二、设计决策（P0 冻结）

### 2.1 决策清单

| # | 决策 | 说明 |
|---|---|---|
| D1 | 不新建配置表/配置服务/配置端 | 全部走 `t_platform_config(config_type=RULES)` + `DEFAULT_RULES` + `safe_rule` |
| D2 | 新增两个规则分组 | `DEFAULT_RULES` 增加顶层分组 `studentAffairs` 与 `academicAffairs`，组内键采用 `<biz>.<param>` 点分驼峰（如 `leave.collegeThresholdDays`）。`validate_rules` 按"分组+键+类型"白名单校验的既有逻辑零改动即可覆盖新组 |
| D3 | 规则键全名 = `<group>.<key>` | 即 `studentAffairs.leave.collegeThresholdDays`；调用形如 `safe_rule(tid, "studentAffairs", "leave.collegeThresholdDays")`。与证据报告 2.4"平台规则键 `studentAffairs.<group>.<key>` / `academicAffairs.<group>.<key>`"一致 |
| D4 | 与《V1范围冻结表》§9 键名的映射 | 冻结表 §9 曾用 `affairs.leave.college_threshold_days` 等 snake 写法，本文档统一替换为 D3 口径（`studentAffairs.leave.collegeThresholdDays`），映射见 §3 各表"冻结表§9对应"标注；本文档为规则键唯一权威，冻结表 §9 随 P0 回写 |
| D5 | 学校可改分层 = 白名单常量 | 新增 `SCHOOL_EDITABLE_RULES: dict[str, set[str]]`（platform_defaults.py），仅白名单内键允许学校管理员改；平台超管可改全部。白名单外的键学校端只读展示 |
| D6 | 学校端配置 API 新增 | `GET/PUT /api/v1/student-affairs/config`、`GET/PUT /api/v1/academic-affairs/config`（require_staff + SCHOOL_ADMIN 校验 + 白名单过滤 + `validate_rules` 复用 + 审计 `SCHOOL_RULES_UPDATE`），底层仍写同一 KV 行——与平台端改的是同一份数据，不产生第二配置源 |
| D7 | validate_rules 增强（小改） | 现只强校验 bool/int；新组含少量字符串枚举（如 `gpa.formula`），为字符串键补"枚举白名单"校验（新增 `RULE_ENUMS` 常量，未列入枚举的字符串键仅限长≤200）。改动局限 platform_service.validate_rules 一处 |
| D8 | 是否审计列的含义 | "是"= 该参数变更除 `PLATFORM_RULES_UPDATE`/`SCHOOL_RULES_UPDATE` 通用审计外，变更明细（旧值→新值）必须写入 detail；涉敏感流程参数（心理/处分/毕业）变更还需在模块内公告 |

### 2.2 分层权限模型（谁能改什么）

| 层 | 操作端 | 能改范围 | 守卫 | 审计动作 |
|---|---|---|---|---|
| 平台默认（tenant_id=0） | 平台运营端 /admin/platform/rules | 全部键的默认值（经 PUT /platform/rules/defaults 建议 P1 补，V1 默认值改代码发版） | require_platform_super_admin | PLATFORM_RULES_UPDATE |
| 租户覆盖（平台侧代配） | 平台运营端 /admin/platform/tenants/{id}/rules | 全部键 | 同上 | PLATFORM_RULES_UPDATE |
| 租户覆盖（学校自配） | PC 学校管理端两个配置页 | 仅 `SCHOOL_EDITABLE_RULES` 白名单 | require_staff + SCHOOL_ADMIN | SCHOOL_RULES_UPDATE（新增） |
| 业务读取 | 各 service 写路径校验点 | 只读，一律 `safe_rule` | — | — |

### 2.3 规则键 ↔ 权限点 ↔ workflow_code 三线对应（防止三套命名漂移）

同一业务的三类标识必须同源命名，P0 一并冻结（权限点全集见冻结表 §13，workflow_code 见冻结表 §12）：

| 业务 | 规则键组（本设计） | 配置权限点（谁能进配置页） | 受影响 workflow_code |
|---|---|---|---|
| 请假 | studentAffairs.leave.* | studentAffairs.leave.config | AFFAIRS_LEAVE / _LONG / _MAJOR / _EXTENSION / _CANCEL |
| 困难认定 | studentAffairs.aid.* | studentAffairs.aid.review（配置随评审权限，V1 不单设） | AFFAIRS_AID_IDENTIFY / _ADJUST |
| 奖助 | studentAffairs.funding.* | studentAffairs.funding.review | AFFAIRS_SCHOLARSHIP / AFFAIRS_GRANT |
| 处分 | studentAffairs.discipline.* | studentAffairs.discipline.review | AFFAIRS_DISCIPLINE / _REMOVE |
| 心理/风险 | studentAffairs.psy.* / risk.* | 平台代配（无学校配置权限点） | —（风险分派为业务动作，非 WF） |
| 宿舍/谈话/家校/归档 | studentAffairs.dorm.* / talk.* / family.* / archive.* | studentAffairs.dorm.manage / archive.confirm | AFFAIRS_DORM_TRANSFER / AFFAIRS_ARCHIVE |
| 学年学期/节次 | academicAffairs.term.* / schedule.* | academicAffairs.term.edit | —（学期发布为业务动作+审计） |
| 学籍/注册/异动 | academicAffairs.status.* / register.* | academicAffairs.statusChange.review | ACAD_STATUS_*（5 条） |
| 成绩/绩点/补重/学分 | academicAffairs.grade.* / gpa.* / makeup.* / retake.* / credit.* | 平台代配（P2 生效档） | ACAD_GRADE_CHANGE / ACAD_RETAKE_APPLY 等（P2 编码冻结） |
| 预警/毕业 | academicAffairs.warning.* / graduation.* | academicAffairs.warningRule.config / graduationAudit.execute | ACAD_GRADUATION_AUDIT |
| 子能力开关/对接 | academicAffairs.feature.* / integration.* | 平台代配 | — |

命名护栏：规则键组名（studentAffairs/academicAffairs）与权限点前缀、features 布尔键（文件二 §4.4）三者拼写完全一致；任何文档/代码出现 `academicAffairs.*` 或 `affairs.*` 旧字样按证据报告 2.5 映射表替换。

## 四、配置生效机制

### 4.1 读取时机（现状+V1 口径）

- **现状核实**：`effective_rules` 每次调用实时查 `t_platform_config`（`get_config_json` → select，platform_service.py 第 37–41 行），**无任何缓存**。平台端 PUT 后"后端业务即刻按新规则校验"（platform.py 端点 summary 原文）正是因为无缓存。
- **V1 冻结**：13A/13B 沿用实时读。调用点收敛在 service 写路径校验函数内（每请求 1–2 次 KV 查询，KV 表带 `(tenant_id, config_type, config_key)` 唯一索引，代价可接受）。
- **P2 预留**：若压测证明规则读成为热点，加"进程内 60 秒 TTL 缓存 + PUT 时主动失效"，实现位置仅限 platform_service（业务侧调用签名不变）。**禁止**业务模块自建缓存（多副本失效不一致）。

### 4.2 变更审计

| 场景 | 审计动作 | 落表 | 明细要求 |
|---|---|---|---|
| 平台改租户规则 | PLATFORM_RULES_UPDATE（已实现，platform.py 第 264 行） | t_security_audit_log | 现仅记 groups 列表；**V1 增强：detail 补记逐键 {key, old, new}**（强审计 12 项为硬要求） |
| 学校自改白名单规则 | SCHOOL_RULES_UPDATE（新增） | t_security_audit_log | 逐键 old/new + 操作人 + 角色；经 `audit_log.record`（含 ip/ua/traceId） |
| 越权尝试（学校改白名单外键） | SCHOOL_RULES_DENIED（新增） | t_security_audit_log | 403 NO_PERMISSION，拒绝即审计（对齐 require_platform_super_admin 风格） |
| 高危键变更（#22/24/51.discipline 等强审计项） | 同上 + 前端二次确认弹窗 | 同上 | 弹窗文案含影响说明；变更后模块内横幅提示 24h |

### 4.3 非法值兜底（safe_rule 默认值机制）

- **运行时**：所有业务读取一律 `safe_rule`——DB 故障、行损坏、类型异常时返回 `DEFAULT_RULES` 默认值（platform_service.py 第 451–455 行），业务永不因配置故障 500。
- **写入时**：`validate_rules` 拒绝未知分组/未知键/类型不符（第 144–159 行）；本设计追加三类校验（D7）：
  1. 字符串枚举白名单（RULE_ENUMS：gpa.formula、status.transferWindow、makeup.scoreRule、discipline.schoolReviewLevel 等）；
  2. 键间约束（leave.saOfficeThresholdDays ≥ leave.collegeThresholdDays；grade.compose 比例和=100；schedule.periodTimes 时段不重叠）；
  3. 只增枚举保护（aid.levels / discipline.types 仅允许追加项，删改存量 422）。
- **降档保护**：学期 PUBLISHED 后 term.teachingWeeks/schedule.periodsPerDay 存在被引用数据时改小 → 409 DATA_CONFLICT（不是 422，因为值本身合法、冲突在数据）。

### 4.4 生效边界

- 规则变更**只影响新发起的校验**，不回溯已生效单据（如阈值改 5 天后，存量 4 天 APPROVED 请假单不重算审批层级）。
- 在途工作流实例按**创建时刻的路由**走完（workflow_code 已在实例上固化），避免中途换轨。
- demo-school 只读锁（middleware/context.py `_demo_tenant_readonly_deny`）对配置 PUT 同样生效：演示租户配置不可改，403 引导沙箱。

### 4.5 配置页入口（分层）

| 端 | 入口 | 内容 | 权限 |
|---|---|---|---|
| 平台运营端（已有页扩展） | /admin/platform/rules 与 /admin/platform/tenants/{id} 详情 Tab | 全部 11 组规则（9 既有+2 新增）读写；新增两组按 13A/13B 业务分区渲染 | PLATFORM_SUPER_ADMIN（双闸：角色+PLATFORM_ADMIN_TOKEN，core/config.py 第 46 行） |
| PC 学校管理端（新增页×2） | /admin/student-affairs/config（权限点 studentAffairs.leave.config 等 config 类）、/admin/academic-affairs/config（academicAffairs.warningRule.config 等） | 白名单 30 项可编辑；白名单外键只读展示（灰态+「联系平台修改」提示）；每键旁显示默认值与当前生效值 | SCHOOL_ADMIN（require_staff + 角色校验；辅导员/教师无 config 权限点则整页 403） |
| 学生/教师移动端 | 无配置入口 | 仅感知生效结果（如请假表单按阈值提示"超 3 天需学院审批"） | — |

### 4.6 读取与变更时序（文字时序图）

**读取时序（以"学生提交 5 天请假"为例）**：

```
学生小程序 POST /api/v1/mobile/student-affairs/leave
  → RequestContextMiddleware：traceId / 令牌绑定租户 / demo·到期只读检查（context.py）
  → require_module("STUDENT_AFFAIRS", write=True)（文件二守卫）
  → leave_service.submit()
      ├─ safe_rule(tid, "studentAffairs", "leave.maxDaysPerRequest")   # 30 → 5 天通过
      ├─ safe_rule(tid, "studentAffairs", "leave.attachmentRequiredDays") # 3 → 需材料，缺则 422
      ├─ safe_rule(tid, "studentAffairs", "leave.collegeThresholdDays")   # 3 → 5>3
      ├─ safe_rule(tid, "studentAffairs", "leave.saOfficeThresholdDays")  # 7 → 5≤7
      └─ 路由 workflow_code = AFFAIRS_LEAVE_LONG（+学院节点），固化到实例
  → 落 t_cs_leave（扩展列）+ t_workflow_instance/task + t_unified_todo
```

**变更时序（学校管理员改阈值）**：

```
管理员 PC /admin/student-affairs/config 保存 collegeThresholdDays: 3→2
  → PUT /api/v1/student-affairs/config（require_staff + SCHOOL_ADMIN）
  → 白名单过滤（SCHOOL_EDITABLE_RULES）→ validate_rules（类型/枚举/键间约束）
  → put_config_json(tid, "RULES", ...)（同一 KV 行，与平台端共写）
  → audit_log.record("SCHOOL_RULES_UPDATE", detail={key, old:3, new:2})
  → 下一笔请假提交立即按新阈值路由（无缓存）；在途单不受影响（§4.4 生效边界）
```

**故障时序（DB 抖动）**：`safe_rule` 捕获异常 → 返回 `DEFAULT_RULES["studentAffairs"]["leave.collegeThresholdDays"]=3` → 业务按默认值继续，错误日志留痕，不 500、不拒单。

## 五、验收清单（本文件范围）

1. `DEFAULT_RULES` 新增 studentAffairs/academicAffairs 两组后，`GET /platform/rules/defaults` 返回 11 组；既有 9 组逐键零变化（响应快照对比）。
2. 平台端 PUT 未知键/类型错/枚举外值 → 422 VALIDATION_ERROR；合法变更后 `GET /platform/tenants/{id}/rules` 即刻反映且业务下一请求生效（无缓存验证）。
3. 学校管理员 PUT 白名单内键成功且审计 SCHOOL_RULES_UPDATE 含 old/new；PUT 白名单外键 403 + SCHOOL_RULES_DENIED 审计。
4. 停库演练：DB 不可用时 `safe_rule` 全部返回默认值，请假提交/审批链路不 500。
5. 阈值联动用例：collegeThresholdDays=3、saOfficeThresholdDays=7 时，2/5/10 天请假分别路由 AFFAIRS_LEAVE / _LONG / _MAJOR；把 saOffice 改 2 → 保存被 422 拒。
6. demo-school 管理员保存配置 → 403 只读锁文案；sandbox-school 可改且次日 0 点重置。
7. 高危键（psy.visibleRoles）变更走二次确认，变更审计可在 /admin/platform/security 查到完整 old/new。
8. 三线命名一致性 grep：`grep -rn "affairs\.leave\.\|academicAffairs\." backend/ frontend/ docs/modules/13A-13B-学校参数配置中心设计.md` 归零（旧键名不残留）。
9. 学期 PUBLISHED 后把 term.teachingWeeks 从 20 改 18（存在第 19/20 周课表项）→ 409 DATA_CONFLICT，提示引用位置。
10. 参数页体验：每键展示「默认值 / 当前生效值 / 覆盖来源（默认·平台代配·学校自配）」三栏，白名单外键灰态+「联系平台修改」。
