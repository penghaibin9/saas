# 帮助中心二次审计报告

审计日期：2026-08-06  
审计对象：`penghaibin9/saas`，分支 `docs/help-center-foundation-20260806`，Draft PR #48

## 1. 结论

当前系统**不是没有帮助中心**。代码中已经存在运行时帮助入口、顶部搜索联动、大量业务流程与任务卡，以及 25 份 HTML 可视化指南。PR #48 初版把问题理解成“从零建立文档库”，这个判断不完整。

真正的核心问题是：

1. 运行时内容已存在，但导航、检索、角色适配和异常排查体验仍偏基础；
2. 新增的 `docs/help` 与前端运行时内容形成两套潜在真值，长期会互相漂移；
3. 现有条目结构不完全统一，部分条目缺少前置条件、成功标准、排障、负责人和复核证据；
4. 可视化 HTML 是流程图和业务地图，不等同于真实页面截图；原方案把两者笼统称为“旧图片”，分类不够专业；
5. 当前 PR 的主 CI 存在家长端 OTP 基线失败，与帮助中心变更无因果关系，但必须如实披露，不能写成“全部测试通过”。

因此，本 PR 采用以下修正后的架构：

> **运行时帮助真值保留在 `frontend/src/config/help*`，可视化资产保留在 `frontend/public/help`；`docs/help` 只承担治理规范、审计证据、覆盖矩阵和发布检查，不再复制一套正式运行时正文。**

## 4. 根因分析

### P0：双轨内容真值

**现象：** 前端运行时已有大量帮助，PR #48 又新增 Markdown 文章目录。  
**根因：** 初次审计没有稳定读取到旧帮助代码，于是把“没有被发现”误判为“没有存在”。  
**风险：** 同一事项会维护两遍，入口、按钮和状态改动后只有一边更新。  
**处理：** 明确运行时与治理边界，并记录架构决策。

### P0：帮助内容不能证明与真实业务一致

**现象：** 任务卡很多，但元数据结构不统一。  
**根因：** 内容主要随功能迭代累积，缺少统一完成定义和自动化闸门。  
**风险：** 帮助看起来完整，实际可能指向旧路由、旧状态或错误角色。  
**处理：** 加入模型测试、链接/资产/目录校验、发布检查清单和覆盖矩阵。

### P1：查找方式仍然以系统结构为中心

**现象：** 左侧长目录优先，用户必须先知道模块名称。  
**根因：** 页面最初以“展示已有内容”为目标，而不是以“完成任务”为目标。  
**风险：** 售后仍需反复告诉老师去哪里找。  
**处理：** 增加首页、角色筛选、业务筛选、高频推荐和深度搜索。

### P1：角色字段与真实登录角色不一致

**现象：** 内容使用中文自由文本；登录上下文使用角色代码。  
**根因：** 帮助元数据和权限模型分别演进。  
**风险：** 直接按字符串过滤会误隐藏内容。  
**处理：** 建立兼容映射；未知旧角色采用宽松显示并标记质量缺口。角色筛选只做体验优化，不做权限控制。

### P2：视觉资产分类不清

**现象：** 原方案把 HTML 业务图和截图统一称为图片。  
**根因：** 没有区分概念说明资产与逐步操作证据。  
**风险：** 用流程图替代真实操作截图，或误以为已有截图覆盖。  
**处理：** 资产分为 `interactive-visual`、`screenshot`、`illustration`，分别治理。

## 5. 方案比较

### 方案 A：保留前端内容即代码，文档只做治理（本次采用）

优点：与当前实现兼容、风险最低，可马上增加测试和质量闸门。  
短板：非开发人员修改内容仍需走代码 PR，多端复用仍需后续建设。

### 方案 B：Markdown / MDX 单一源，构建时生成运行时数据

优点：适合编辑，可从一个源生成网页、搜索和培训材料。  
代价：需要解析器、构建插件、路由绑定、迁移脚本和回归测试。  
适用时机：条目结构稳定、内容负责人明确后。

### 方案 C：独立帮助 CMS

优点：售后或产品人员可直接维护，具备版本、反馈和分析能力。  
代价：权限、租户、发布审核、搜索同步和运维更复杂。  
适用时机：已有多所学校正式使用，内容更新频率和团队协作量明显上升后。
