# 1. 补审计最终结论

原计划总体方向正确，仍可作为主路线。

但最新代码已经发生 7 个提交的变化，原计划中有三类内容需要修订。

## 1.1 已经修复，不要重复施工

1. 学号已经改成**租户内永久唯一，包含软删记录**；
2. 作废后同号不再新建第二档，而是复活原 `studentId`；
3. 主档手机号新增、更新、复活路径已经使用 `encrypt_field()`；
4. 迎新、旧学业、就业新增路径的手机号已经开始加密；
5. 学生路由已经正式并入 `frontend/src/router/index.js`；
6. 主学生导入批次已经持久化，不是进程内 `_MEM`；
7. 系统管理身份导入已被文档和入口定义为师生账号正式入口；
8. 学生选择器的数据范围和最小字段返回已经补强；
9. 消息发布大名单已有数据库投递作业，不应另造第二套消息队列。

## 1.2 仍然存在，原计划继续有效

1. `StudentProfile` 仍有多个直接写入口；
2. 教务学籍导入仍是第二套主档创建器；
3. 公共学生导入仍直接创建 `StudentProfile`；
4. 系统身份导入底层仍直接创建 `StudentProfile + User`；
5. 组织父链没有在学生建档处强校验；
6. 主档更新仍无真正原子乐观锁；
7. 主档作废仍未检查活动业务；
8. 投影同步字段名仍写错；
9. 投影同步仍在主档提交后执行；
10. 四套影子学生新增入口仍存在；
11. 域导入仍使用 `_MEM` 并逐行创建影子学生；
12. 学生账号与主档仍靠“登录名 = 学号”推断；
13. 移动端仍保留姓名匹配；
14. 前端学生模块仍未进入统一权限守卫；
15. 学生菜单、路由、后端权限码仍不一致；
16. 毕设与实习仍需要后续统一批次参与人。

## 1.3 本次新发现、原计划没有充分展开的遗漏

1. **学号更正会同时影响登录、消息受众、缓存和家长授权；**
2. **学生作废后账号可能仍保持 ACTIVE，可以登录但拿不到主档；**
3. **消息系统混用 `student_id` 和 `user_id` 作为收件人标识；**
4. **消息受众通过 `User.login_name = StudentProfile.student_no` 关联账号；**
5. **学生首页缓存键仍使用 `studentNo/userId`，学号更正后可能产生旧缓存；**
6. **家长授权表复制 `student_no`，学号更正后会变成陈旧值；**
7. **部分页面把 Fernet 密文直接传给脱敏函数，显示的是“被遮住的密文”，不是被遮住的手机号/身份证；**
8. **主档 `student_status/status/current_stage/is_deleted` 多套状态共同决定资格，批次选人不能各模块自己判断；**
9. **主档风险等级仍借用 `remark`，不应成为批次筛选或正式风险源；**
10. **原计划第一轮强制上 Outbox 过重；当前内部投影更适合先改为同事务同步，Outbox 放到外部同步阶段。**

# 2. 对原计划的强制纠正

## 2.1 Outbox 不再作为第一轮强制内容

原计划提出：

```text
主档事务
→ 写 Outbox
→ 异步投影
```

长期方向正确，但当前代码的投影只有：

- `CsServiceStudent`
- `GraduationStudent`

都是同一个 MySQL 内部表。

第一轮最省 Token、最安全的实现应改为：

```text
主档事务
→ sync_student_projections_in_session(db, student)
→ 审计
→ commit
```

要求：

- 不新开 session；
- 不在 commit 后调用；
- 投影失败时整个主档修改回滚；
- 不需要第一轮新建 scheduler、worker、outbox 表。

只有后续接入：

- 外部系统；
- 搜索索引；
- Redis 大范围缓存；
- 第三方同步；

才增加 Outbox。

因此原计划中的 Outbox 调整为：

```text
第一轮：可选，不阻断
外部同步阶段：必须
```

## 2.2 不要第一轮新建 `student_master_query_service.py`

当前读取链已经存在：

```text
student_service.py
→ db_service.list_students/get_student
```

第一轮只统一写入口，不重写读服务。

正式新增文件控制为：

```text
backend/app/core/student_master_contract.py
backend/app/services/student_master_application_service.py
backend/app/services/student_org_validator.py
```

暂不新增：

```text
student_master_query_service.py
student_master_outbox_service.py
```

除非 Claude Code 证明当前代码存在 3 个以上无法复用的重复查询实现。

## 2.3 账号登录名与学号必须解耦设计

建立 `StudentAccountLink` 后：

```text
User.login_name = 登录凭据
StudentProfile.student_no = 学籍身份
StudentAccountLink = 稳定关系
```

学号更正时不能默认粗暴修改登录名。

增加租户策略：

```text
login_name_follows_student_no = true / false
```

### 策略为 true

同事务检查新登录名冲突并更新：

- `StudentProfile.student_no`
- `User.login_name`
- 账号别名或旧登录名迁移记录；
- 缓存；
- 消息受众关系无需重建，因为使用稳定链接。

### 策略为 false

- 只改 `StudentProfile.student_no`；
- 登录账号保持不变；
- 页面明确显示“登录账号与学号不同”；
- 禁止再通过 `login_name == student_no` 关联。

## 2.4 批次选人必须使用统一资格判断器

原计划主要描述组织范围，没有单独冻结“哪些学生可以进入批次”。

必须新增：

```text
backend/app/services/student_eligibility_service.py
```

至少提供：

```python
is_active_student(student)
is_eligible_for_internship(student, rules)
is_eligible_for_graduation(student, rules)
is_eligible_for_registration(student, rules)
```

禁止各模块自行写：

```python
student_status not in (...)
status == "ACTIVE"
not is_deleted
current_stage == ...
```

统一考虑：

- `is_deleted`
- `student_status`
- `status`
- `current_stage`
- 休学；
- 退学；
- 毕业；
- 合并；
- 回收；
- 未注册；
- 允许的年级和届别。
