# 2U4G 非容器部署准备与执行手册

> 当前状态：部署包已准备；按用户要求未连接真实服务器。  
> 适用：2 核 4G Linux，Nginx + MySQL + Redis + systemd。
>
> **生产数据备份/恢复的权威口径：`deploy/README-data-governance.md`。** 本文不再维护独立的每日 cron 方案。

## 一、资源口径

- FastAPI：2 workers，监听 `127.0.0.1:8000`，仅由 Nginx 反代。
- MySQL：若数据库同机，连接池每 worker 3 + overflow 3；InnoDB buffer pool 建议先从 1G 起，根据现有负载调整，不套用容器方案的 2G 默认值。
- Redis：同机可设 128—256MB；生产必须密码且只监听本机/内网。
- scheduler：只能运行 1 个，负责 6 小时逾期扫描、每日导入批次清理和可选沙箱重置。
- 构建：PC 与 H5 顺序构建，Node 最大堆 1536MB，避免 4G 主机同时构建造成内存峰值。

## 二、准备文件

| 文件 | 用途 |
|---|---|
| `deploy/env/backend.systemd.env.example` | 生产环境变量模板 |
| `deploy/env/backup.env.example` | 生产备份与异地目标模板 |
| `deploy/systemd/school-lifecycle-backend.service` | 2-worker API 服务 |
| `deploy/systemd/school-lifecycle-scheduler.service` | 单实例调度服务 |
| `deploy/systemd/school-lifecycle-backup.service/.timer` | 每 6 小时完整备份集 |
| `deploy/systemd/school-lifecycle-backup-watchdog.service/.timer` | 每小时检查备份新鲜度/完整性/异地 commit marker |
| `deploy/nginx/school-lifecycle.systemd.conf.example` | HTTPS 站点配置 |
| `scripts/deploy/preflight-linux.sh` | 只读预检 |
| `scripts/deploy/install-systemd-release.sh` | 备份、构建、迁移、版本切换 |
| `scripts/deploy/verify-systemd-release.sh` | 发布后验收 |
| `deploy/backup/backup-runner.sh` / `restore-drill.sh` | 正式备份编排与隔离恢复演练 |

`deploy/backup/backup-mysql.sh` 是正式 runner 调用的底层组件，不应再单独配 cron 作为生产成功判据。

## 三、首次只读核验

登录服务器后先看，不安装、不覆盖：

```bash
cat /etc/os-release
nproc
free -h
df -h
systemctl --type=service --state=running | grep -E 'nginx|mysql|mariadb|redis|school'
ss -lntp | grep -E ':80|:443|:8000|:3306|:6379'
```

确认现网目录、数据库名称和备份位置后，把环境模板复制到 `/etc/school-lifecycle/backend.env`，填真实值并执行 `chmod 600`。密码、JWT、字段加密密钥、短信/微信密钥不能写入 Git、聊天记录或文档；同时按数据治理说明在服务器/Git 之外保留一份受保护恢复副本。

## 四、部署前门禁

```bash
ENV_FILE=/etc/school-lifecycle/backend.env bash scripts/deploy/preflight-linux.sh
```

必须零 FAIL。首次部署还必须：

1. 域名已解析到服务器；
2. 80/443 安全组开放，3306/6379 不对公网开放；
3. HTTPS 证书已签发；
4. MySQL 备份目录空间充足；
5. `alembic heads` 唯一为当前仓库 head；
6. 当前前端已通过生产构建；
7. 异地备份桶已启用版本化/不可变保留/存储侧加密，并已准备 `/etc/school-lifecycle/rclone.conf`。

## 五、正式执行（以后部署时）

先运行不带参数的命令，确认安全保护不会写入：

```bash
bash scripts/deploy/install-systemd-release.sh --check
```

经人工确认后才执行：

```bash
sudo ENV_FILE=/etc/school-lifecycle/backend.env \
  SOURCE_ROOT=/上传后的源码目录 \
  bash scripts/deploy/install-systemd-release.sh --apply
```

脚本顺序固定为：预检 → 创建发布目录 → 发布前一致性保护 → 安装依赖 → 顺序构建 PC/H5 → `alembic upgrade head` → 原子切换 `current` → 重启 systemd 服务 → 冒烟。应用启动失败会切回上一代码目录；数据库迁移不会自动 downgrade，避免自动破坏已写入的新数据。

## 六、上线验证

```bash
sudo BASE_URL=https://正式域名 bash scripts/deploy/verify-systemd-release.sh
```

验收包含：backend/scheduler active、`nginx -t`、`/health`、`/health/ready`、当前 Alembic head、生产 `/docs` 关闭、未登录接口返回 401。

首次生产数据治理还必须完成一次：**正式 backup service 成功 → watchdog PASS → 从异地完整备份集恢复到隔离库成功**。完成后日常由 systemd 自动执行。

## 七、回滚与备份

- 代码回滚：切换 `/opt/school-lifecycle/current` 到上一 release，再重启 backend/scheduler；
- 静态站点随 current 同步切换；
- 数据库默认不降级；涉及数据库恢复时先在隔离库验证恢复点；
- 正式备份由 `school-lifecycle-backup.timer` 每天 4 次运行，基线 **RPO ≤ 6 小时、RTO ≤ 2 小时**；
- 本地默认至少保留 8 个完整恢复点，异地对象由云端版本化/不可变策略控制；
- `school-lifecycle-backup-watchdog.timer` 每小时检查备份是否过期、残缺或异地 commit marker 丢失；
- 不再使用“每天 02:00 单独执行 `backup-mysql.sh`”作为正式生产方案。

## 八、本次没有做的操作

本文只描述可执行基线，不代表已经登录真实云平台或服务器完成 COS/rclone、systemd、生产备份和恢复演练。真实环境必须在首次上线时按 `deploy/README-data-governance.md` 完成一次配置与验收。
