# SaaS 方案遗漏与后续实施路线图

## 一、目标与边界

当前目标规模为 10 所学校、每校约 1 万名学生。约 10 万学生主档本身不需要立即分库分表，优先完成单库多租户隔离、Redis、多应用实例、异步任务、对象存储、高可用和可观测性。

扩容判断不能只看学生总数，应以首页、报到、成绩发布、选课、实习打卡、消息群发、导入导出等瞬时峰值的 QPS、数据库连接、慢 SQL 和错误率为依据。

## 二、P0：正式上线前必须补齐

### 1. 异步任务队列

定时调度器不能代替任务队列。大导入、大导出、批量消息、批量预警、统计重算和文件处理需要 Celery、RQ、Dramatiq 或等价设施。

最低能力：

- 任务入队、进度、结果和失败原因。
- 自动重试、指数退避、超时和取消。
- 任务幂等，客户端重试不能重复生成结果或重复发送消息。
- 每学校并发配额，避免单校占满 worker。
- 大任务拆批执行，批次提交后及时释放数据库连接。
- 失败任务告警、人工重跑和结果文件过期清理。

### 2. 多实例对象存储

多后端副本不能依赖某个容器的本地上传目录。正式接入 COS、MinIO 或其他对象存储：

- 数据库保存文件 ID、租户、业务归属、对象 Key、哈希和大小。
- 对象 Key 按学校和业务模块隔离。
- 下载前由后端校验登录、租户、文件归属和数据范围。
- 通过短时签名 URL 下载，不暴露永久公共地址。
- 增加文件类型检测、病毒扫描、大小限制和敏感文件审计。
- 配置学校级存储配额和过期清理。

### 3. 强制租户隔离

不能长期依赖开发人员手工为每条查询添加 `tenant_id`。建议建立统一租户查询守卫：

- 普通业务模型的 select/update/delete 自动追加当前租户。
- `Session.get(Model, id)` 必须改为租户范围查询，或读取后立即验证租户归属。
- 平台跨租户操作使用专用会话或显式豁免标记，并写安全审计。
- 导入确认、导出、文件下载和后台任务重新验证租户，不能只信请求参数。
- CI 自动运行双租户读、改、删、导出和下载用例。
- 生产数据库账号不授予绕过应用隔离的额外权限。

### 4. 微信用户与学校身份模型

需要确认同一个微信用户在多学校、多角色场景下的模型：

- 微信主体与租户成员身份分离。
- 同一 `openid` 是否允许关联多个学校身份。
- 同一用户兼任教师、家长或跨校任职时如何切换身份。
- 转学、毕业、离职、解绑、换绑和账号合并流程。
- Refresh Token 按设备和身份管理，支持查看设备、单设备退出和全部强制下线。
- 微信订阅消息的用户授权、模板、额度和失败补偿。

如果 `wx_openid` 全局唯一且账号只能属于一个租户，多学校身份将受到限制，应在扩大客户数量前确定最终方案。

### 5. 核心组件高可用

多 Backend 只能解决应用实例故障，MySQL、Redis、Nginx、Scheduler 和单机磁盘仍可能成为单点。

上线基线建议：

- 使用云负载均衡，或至少双入口代理。
- MySQL 使用云数据库高可用或主从自动切换。
- Redis 使用云 Redis、Sentinel 或 Cluster，并启用认证和网络白名单。
- Binlog 持续复制到不同故障域。
- 文件进入对象存储，不依赖应用服务器磁盘。
- Scheduler 使用分布式锁或主备选举，确保同一任务只有一个执行者。

### 6. 集中监控和告警

当前进程内指标只能用于开发诊断，不能代替生产监控。需要接入 Prometheus/Grafana、云监控或同类平台：

- 逐副本采集接口 p50/p95/p99、QPS、4xx/5xx。
- 数据库池大小、占用、等待、超时和连接泄漏。
- MySQL 慢 SQL、锁等待、死锁、连接数和复制延迟。
- Redis 延迟、命中率、内存、淘汰数、连接数和故障降级次数。
- 任务队列长度、执行时间、失败数和最老任务等待时间。
- Scheduler 最近成功时间和连续失败次数。
- 备份成功时间、文件大小、SHA256 和恢复演练结果。
- 告警发送到企业微信、短信或电话，并明确值班人和升级路径。

就绪检查失败时应返回 HTTP 503，使负载均衡自动摘除故障实例，而不仅是在 HTTP 200 内容中返回 `DEGRADED`。

## 三、P1：多学校推广前完成

### 1. 零停机发布和数据库变更

- 应用采用滚动、蓝绿或金丝雀发布。
- 新旧版本在发布窗口内兼容同一数据库结构。
- 大表索引使用 MySQL 在线 DDL 或专用在线变更工具。
- 删除字段分多个版本完成，先停用、再观察、最后删除。
- 数据回填按批次执行，支持断点续跑和异常报告。
- 发布失败优先前滚修复，避免直接回滚已经产生新数据的结构。

### 2. 学校套餐和资源配额

每所学校至少记录和限制：

- 学生、教师和管理员账号数量。
- 文件存储容量。
- 短信和微信通知额度。
- API 调用量和峰值速率。
- 导入导出次数和单次最大行数。
- 后台任务并发数和每日任务量。
- 套餐模块、试用期、到期只读和续费恢复策略。
- 学校维度资源成本和异常使用告警。

### 3. 数据生命周期

- 毕业、退学、休学、转学和恢复学籍保留历史状态。
- 班级、专业、学院变化使用有效期或变更历史，不能覆盖所有历史记录。
- 规定业务数据、附件、日志和审计的保留年限。
- 学校解约时支持全量导出、冻结、延迟销毁和销毁证明。
- 支持单学校备份与逻辑恢复，避免恢复整库影响其他学校。
- 对超大历史表制定归档或分区策略。

### 4. 审计防篡改

- 关键审计采用追加写，普通管理员无修改和删除权限。
- 定期对审计批次生成哈希或签名并异地归档。
- 记录操作人、租户、身份、来源 IP、设备、对象、前后值摘要和 traceId。
- 敏感数据查看、导出、下载、批量操作和平台跨租户操作必须审计。
- 审计查询和导出本身也需要权限和审计。

### 5. 主数据与学校接入规范

- 学号、身份证号、录取号、手机号的唯一范围和变更规则。
- 重复学生识别、合并和拆分流程。
- 学籍异动和跨年度数据继承。
- 学校原有教务、学工、迎新、就业系统的同步接口。
- 导入模板版本、字段字典、错误回滚和重复导入幂等。
- 明确 `student_id` 是内部稳定主键，姓名只用于展示和模糊搜索。

## 四、P2：规模扩大后按指标建设

### 1. 搜索与报表体系

当跨多年学生数据、全文搜索和多维报表明显拖慢主库后，再考虑 Elasticsearch/OpenSearch、数据仓库或只读报表库。10 万学生阶段不应过早引入复杂搜索集群。

### 2. 读写扩展

只有在索引、查询、缓存和连接池优化后仍达到数据库瓶颈时，才逐步引入只读副本、读写分离、归档库、分区表或分库分表。

### 3. 多地域与容灾

当合同要求或客户地域扩大后，再建设同城双可用区、异地灾备、跨区域对象复制和定期切换演练。

## 五、容量与压测场景

正式验收不能只压测单接口，应至少覆盖：

1. 1 万学生在 10 分钟内自动登录并打开首页。
2. 成绩发布后学生集中查询成绩和学业预警。
3. 实习学生早晚集中定位打卡。
4. 新生报到开放时集中查询和提交资料。
5. 全校消息生成、发送和已读状态更新。
6. 一个学校执行大导入或大导出时，其他学校继续正常访问。
7. 同一写接口重复点击和网络重试，验证幂等。
8. Redis 中断、MySQL 短暂抖动、单 Backend 下线时验证降级和恢复。
9. 单学校异常高频请求时验证学校配额不会影响其他租户。
10. 多学校同时执行定时任务时验证队列和数据库连接不会耗尽。

建议上线验收目标：API p95 小于 500 ms、错误率小于 1%、首页热缓存 p95 小于 200 ms、无连接池超时、无跨租户数据返回、无重复写入。

## 六、建议实施顺序

### 第一阶段：上线阻断项

1. 确认微信用户—租户身份模型。
2. 接入对象存储并收口文件下载鉴权。
3. 接入异步任务队列，迁移大导入、大导出和批量任务。
4. 增加强制租户守卫和双租户自动化测试。
5. 建设集中监控、真实告警和 HTTP 503 就绪检查。

### 第二阶段：生产可靠性

1. MySQL、Redis 和入口高可用。
2. Binlog 异地同步和恢复演练。
3. 零停机发布、在线数据库迁移和回滚流程。
4. 学校配额、套餐和任务限额。
5. 10 校峰值模型压测和参数调整。

### 第三阶段：商业化运营

1. 学校开通、停用、续费、解约和数据销毁闭环。
2. 租户成本、用量和 SLA 报表。
3. 主数据同步、历史归档和单学校恢复。
4. 根据实际指标决定搜索、报表库和读写扩展。

## 七、当前结论

10 所学校、约 10 万学生不构成必须分库分表的规模。当前最需要优先解决的不是继续增加数据库复杂度，而是异步任务队列、多实例对象存储、强制租户隔离、微信多学校身份、高可用和集中监控。这些能力决定系统能否从单校项目稳定演进为商业 SaaS。
