# 05 · 故障应急处理

> 按「症状」查。每种症状给：先看什么 → 最可能原因 → 怎么处理。适合现场照着做。

---

## 通用第一步（任何故障都先做）

1. **自己复现**：打开出问题的页面/地址，确认问题真实存在。
2. **判断影响面**：只有你一个人这样，还是所有人都这样？只有一个页面，还是全站？
3. **想想刚才动过什么**：刚发版？刚改 Nginx？——如果是，**优先考虑回滚**（`docs/07-部署运维交付与商业化/deploy/09`）。

---

## 症状 1：页面白屏（打开是一片空白）

**先看**：浏览器 F12 → Console 有没有红色报错；Network 里 `index.html` 和 js/css 是不是都 200。

| 可能原因 | 怎么处理 |
|---|---|
| dist 没部署对 / 目录空 | 确认 `/var/www/pc-frontend/index.html` 存在；重新 `cp -r dist/* ...` |
| Nginx `root` 指错目录 | 检查站点配置 `root`；`nginx -t` 后 `reload` |
| 静态资源 404（js 没加载） | 见「症状 3」 |
| 部署到子路径但没配 base | 本项目默认根路径 `/`；如放子路径需配 `vite base`（谨慎，见 `docs/07-部署运维交付与商业化/deploy/08`） |
| 浏览器缓存了坏版本 | Ctrl+F5 强刷 |

> 若刚发版就白屏 → **直接回滚上一版**，恢复后再慢慢查。

---

## 症状 2：刷新子页面 / 直接访问某地址 → Nginx 404

**这是最常见的问题，几乎都是路由兜底没配。**

**先看**：是不是只有「首页正常，点进去也正常，但一刷新就 404」？如果是，基本确定。

**处理**：在该站点 Nginx 配置的 `location /` 里确保有：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

原理和完整说明见 `docs/07-部署运维交付与商业化/deploy/03` 第 6 节、`docs/07-部署运维交付与商业化/deploy/07` 第 2 节。

---

## 症状 3：静态资源 404（页面在但样式/图片/功能缺失）

**先看**：F12 → Network，哪个 `.js`/`.css`/图片是 404，看它请求的路径。

| 可能原因 | 怎么处理 |
|---|---|
| dist 内容没拷全 | 重新完整 `cp -r dist/* /var/www/pc-frontend/`，确认 `assets/` 也在 |
| 网站放在子路径，资源路径对不上 | 本项目默认根路径；若必须子路径，需重新配 `vite base` 后 build（谨慎） |
| 文件权限不足，Nginx 读不到（可能 403） | `sudo chown -R www-data:www-data /var/www/pc-frontend`（Ubuntu）或 `nginx:nginx`（CentOS） |
| 缓存了旧的资源清单 | 确认 `index.html` 设了不缓存；Ctrl+F5 |

---

## 症状 4：接口报 500（后端接入后才会遇到）

> **当前阶段前端用 mock，不调真实后端，正常不会有接口 500。** 如果现在就看到 500，多半是 Nginx 配置问题或误配了 `/api` 代理，检查 Nginx 配置即可。

后端接入后，接口 500 的排查思路（届时补真实命令）：

1. 看是哪个接口 500：F12 → Network 找到那条请求。
2. 看后端日志：后端服务的输出 / `journalctl -u 后端服务名 -n 100`。
3. 常见原因：后端代码异常、数据库连不上（见症状 5）、参数不对。
4. 临时缓解：若刚上线后端就大面积 500，回滚后端到上一版；前端可临时切回 mock 保证演示（由开发同学操作，运维不擅自改源码）。

---

## 症状 5：数据库连不上（后端接入后才会遇到）

> **当前没有数据库，不会遇到。** 以下为后端/数据库接入后的排查思路（届时补真实命令）。

1. 确认数据库服务在跑：`systemctl status postgresql`。
2. 确认能连：用 `psql` 或后端健康检查试连。
3. 检查后端的 `DATABASE_URL`（地址/端口/库名/账号密码）是否正确（见 `deploy/env/database.env.example`）。
4. 检查网络/防火墙：数据库端口（默认 5432）是否对后端放开。
5. 检查连接数是否被占满。
6. 看数据库日志定位具体错误。

> 处理数据库故障需要懂数据库的人参与，新手不要盲目重启/改配置，先收集日志和现象。

## 症状 6：小程序构建失败

**先看**：`miniapp/build-h5.log` 或 `build-mp.log` 的最后几十行。

| 可能原因 | 怎么处理 |
|---|---|
| 依赖没装/装坏 | `cd miniapp && rm -rf node_modules package-lock.json && npm install` 后重试（注意：这只在 miniapp 目录，不动源码） |
| Node 版本不对 | 用 Node 18/20 LTS |
| 磁盘满了 | `df -h` 看，清理空间后重试 |
| 网络导致依赖没下全 | 设镜像 `npm config set registry https://registry.npmmirror.com` 重装 |

> 若构建日志指向某个**源码文件的语法错误**，那属于开发问题：**记录报错、反馈给开发**，运维不擅自改 `miniapp/src/`。

---

## 症状 7：整个站点打不开 / Nginx 挂了

```bash
sudo systemctl status nginx           # 看是不是没运行
sudo nginx -t                         # 看配置是不是写错导致起不来
sudo tail -n 50 /var/log/nginx/error.log
sudo systemctl restart nginx          # 配置修对后重启
```

- 若 `nginx -t` 报错 → 按提示的文件和行号改回去（常见：刚改的配置有拼写错误）。改不对就**恢复上一份能用的配置**。
- 若服务器整个连不上（SSH 都上不去）→ 到云服务器控制台看机器状态、用控制台的 VNC/远程登录进去查。

---

## 回滚是最好的急救

大多数「刚发版就出事」的情况，**最快的处理不是现场硬修，而是先回滚到上一版**，恢复服务，再慢慢查原因。回滚方法见 `docs/07-部署运维交付与商业化/deploy/09-发布与回滚流程.md`。
