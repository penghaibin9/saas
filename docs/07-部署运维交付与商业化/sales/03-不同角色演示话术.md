# 03 不同角色演示话术

- **文档性质**：销售/售前对客沟通材料——针对不同听众角色的定制话术
- **适用对象**：售前顾问，在演示或答疑现场根据听众身份挑选对应章节使用
- **依据**：共享事实底稿第 1、2、3 节（PC 模块、miniapp 角色与权限、RBAC 角色）
- **当前阶段声明**：当前为可演示版本，PC 端 UI 母版对接中、使用 mock 数据；小程序为纯 mock 演示闭环；后端未接入真实数据，接入按 API 契约推进中
- **生成日期**：2026-07-04

---

## 使用说明

学校客户来听演示的往往是多角色混合听众（比如校领导带着学工处和信息中心一起来）。本文档按听众角色拆分了"关注点—话术—演示落点"，售前可以在 `02-学校客户演示脚本.md` 的主线流程中，针对不同角色在场时插入对应段落，不需要通篇照读全部六类角色的内容。

---

## 1. 校领导

### 关注点
- 学校整体治理能力是否提升，管理是否更规范
- 能不能看到全局数据，减少人工汇总报表的工作量
- 风险学生能不能被及早发现，避免出现管理疏漏
- 投入产出是否值得，别的学校有没有类似实践

### 话术
"对于校领导来说，我们这套平台最直接的价值是两点：第一，把过去分散在各部门、靠人工汇总的数据，集中到数据驾驶舱里，管理层可以直接看到在校学生规模、实习进度、就业情况这些关键指标，不用等各部门交报表；第二，风险预警机制能帮助学校更早发现需要关注的学生，比如实习出勤异常、学业预警这些情况，辅导员和教务能在系统里及时看到、及时跟进，而不是等问题变严重了才知道。另外从治理角度看，所有的审批流程（实习申请、周报批阅、毕设材料审阅）都在系统里留痕，谁审批的、什么时候审批的、退回原因是什么，管理更规范、更可追溯。"

### 演示落点
- 数据驾驶舱（DATA_CENTER）——整体数据看板
- 审批中心（APPROVAL）——审批留痕的治理价值
- 风险学生（miniapp 教师端 risk-students）——风险预警的实际界面
- 权限体系——强调"校领导能看全校数据，但具体操作是各岗位老师在做，权责清晰"

### 需要如实说明的点
数据驾驶舱当前展示的是演示数据，尚未接入学校真实业务数据；风险预警是系统辅助发现异常的机制，不能承诺"100% 不会漏掉风险学生"，只能说"提供了比人工经验更系统化的发现渠道"。

---

## 2. 学工/学生处

### 关注点
- 学生主档信息是否完整、好不好用
- 在校服务申请（请假等）流程是否顺畅
- 数字迎新能不能减轻迎新季工作量
- 审批流程是否符合学校现有的管理制度

### 话术
"学工处最关心的应该是学生日常管理这一块。我们的学生主档模块，把学生的学籍信息、身份信息、监护人信息、状态变更记录都放在一份档案里，可以按班级、按学院批量分配辅导员、批量提醒；在校服务模块承接学生日常的请假、服务申请这些高频小事，学生通过小程序直接提交，对应老师在系统里处理，不用再靠纸质单子或者微信群传来传去；数字迎新模块是为新生入学季设计的，材料收集和审核可以线上流转，这个环节因为涉及到具体材料清单和贵校迎新流程的差异，我们建议后续结合贵校实际迎新制度再细化对接。"

### 演示落点
- 学生主档（STUDENT）——列表、详情、批量操作、导入导出
- 在校服务（CAMPUS_SERVICE）——申请与审批流程
- 数字迎新（ORIENTATION）——迎新看板（简要展示，不承诺已完全对接学校迎新制度）
- miniapp 学生端 service-apply 表单

### 需要如实说明的点
数字迎新模块的入学材料审核审批流当前处于未启用的示例状态,具体材料清单和审核规则需要结合学校实际制度定制，不能说"迎新审批流程已经完全跑通、拿来即用"。

---

## 3. 教务

### 关注点
- 学业过程管理（学业预警、学籍状态变更）是否符合教务规程
- 毕业设计的选题、审核、材料审阅流程是否严谨
- 退回材料是否有据可查，避免师生纠纷

### 话术
"教务老师关心的核心是学业过程和毕业设计这两块的规范性。学业过程模块可以处理学业预警、学籍状态变更，跟学生主档的数据是打通的，不用重复登记；毕业设计模块管理选题、审核、材料审阅整个流程，指导教师批阅材料时如果要退回，必须写明退回原因，而且至少要写 5 个字以上，不能简单打回一个'不合格'就完事，这样可以减少因为退回理由不清楚导致的师生纠纷。"

### 演示落点
- 学业过程（ACADEMIC）——学业预警、学籍状态处理
- 毕业设计（GRADUATION）——选题、审核、材料审阅，重点演示退回原因的强制校验
- miniapp 教师端 graduation-guide（毕设指导）

### 需要如实说明的点
学业过程模块的预警规则、毕业设计的选题审核流程，具体判定标准和字段需要结合学校教务实际规程确认，当前演示的是通用流程框架和界面操作方式，不是已经按某个具体学校教务细则定制完成的版本。

---

## 4. 就业办

### 关注点
- 就业去向上报是否方便学生操作
- 未就业学生的持续跟进机制
- 岗位推荐、就业核实的操作是否高效

### 话术
"就业办的核心诉求通常是两个：一是让学生方便地上报就业去向，二是能持续跟进还没落实工作的学生，别让人漏掉。我们的就业服务模块里，学生可以通过小程序直接提交就业上报（employment.report），就业老师在 PC 端或者教师小程序里做就业核实、岗位推荐、持续跟进未就业学生（employment.follow / employment.verify / job.recommend），比传统靠电话逐个联系、Excel 手工登记要系统化。"

### 演示落点
- 就业服务（EMPLOYMENT）——PC 端看板
- miniapp 学生端 employment 页面 + employment.report 上报操作
- miniapp 教师端 employment-follow（就业跟进）

### 需要如实说明的点
就业数据统计口径（比如就业率如何计算、哪些情况算已就业）需要结合学校和主管部门的统计规范确认，当前展示的是流程和界面能力，具体统计口径以学校要求为准，不能替学校下统计结论。

---

## 5. 辅导员/教师

### 关注点
- 移动工作台是否真的能减少工作量，而不是增加负担
- 周报批阅是否方便
- 风险学生能不能真正帮上忙
- 多身份切换会不会造成混乱

### 话术
"辅导员和老师最实际的关注点是'这个系统会不会让我更累'。我们把老师最高频要处理的事情——待办审批、周报批阅、风险学生查看——都做进了手机端的移动工作台，不用非得开电脑才能处理。周报批阅这块，学生在实习期间提交周报，指导教师在小程序里直接批阅，不合格的话写清楚原因退回去。风险学生列表能帮辅导员一眼看到需要重点关注的学生，还可以创建关怀记录、标记跟进。另外有些老师身兼多个身份，比如既是辅导员又是毕设指导老师，登录后可以直接切换身份，切换后看到的待办和权限范围会跟着变，不会把不同身份的事情混在一起看。"

### 演示落点
- miniapp 教师端 workbench（工作台）、todos（待办）、approval（审批）
- miniapp 教师端 risk-students（风险学生）、student-detail（360 度画像）
- miniapp 教师端 internship-review（实习周报批阅）
- miniapp 教师端 role-switch（身份切换，演示账号张明远老师可切换 6 类教师身份）

### 需要如实说明的点
风险学生的判定逻辑是系统辅助识别机制，不能替代老师的专业判断，也不能承诺"发现所有风险情况"；身份切换目前是 mock 演示，真实数据下的多身份权限校验逻辑随后端接入同步完善。

## 6. 信息中心

### 关注点
- 权限体系设计是否严谨、数据范围是否真的做到隔离
- 多租户架构下，学校之间的数据边界怎么保证
- 安全基线（会话管理、敏感数据脱敏、审计日志）是什么水平
- 能不能跟现有系统（教务、一卡通、身份认证）集成
- 私有化部署还是 SaaS，技术栈是什么

### 话术
"信息中心关心的是底层的严谨性，我这里如实跟大家讲清楚现状。权限设计上，我们采用的是角色+数据范围的模型：角色决定'能做什么'（比如能不能审批、能不能导出），数据范围决定'能看到谁的数据'（全平台/本校/本学院/本班级/仅本人/被指派对象），两者是分开设计、组合生效的，不是简单的菜单开关。多租户上，每个学校的数据在租户维度隔离，学校品牌（校名、主色调）也可以独立配置。安全基线方面，我们设计了会话超时机制（PC 端 30 分钟无操作超时，移动端 7 天）、敏感字段分级脱敏、文件上传白名单黑名单管控、导出分级授权加审计留痕这些机制——但我要如实说明，这些目前是安全基线的**设计与前端预留实现**，系统整体还没有经过等保三级测评，我们不会说'已经达到等保三级'这种话，等保测评是需要专业机构按流程认证的，我们目前是按等保三级的思路在做设计准备。技术栈上，前端是 Vue3，后端技术栈已经确定为 PostgreSQL + Python FastAPI + SQLAlchemy + Alembic，接口按照统一的 REST 契约设计（`/api/v1/` 前缀，分端路由），但目前后端真实接口还没有接入，现在看到的是前端和小程序的 mock 演示。跟现有系统的集成（教务、一卡通、身份认证），我们有预留的架构设计和接口规划，具体集成方式需要结合贵校现有系统的接口能力另行评估对接方案。"

### 演示落点
- 权限与流程模块（WORKFLOW）——角色列表、权限点、数据范围配置界面
- 系统管理下的安全与审计（system.log.view）——审计事件类型展示
- 审批流模板——展示权限如何限定"谁能审批、谁能看到什么数据"（如企业导师范围限定为 ASSIGNED，不可见毕设材料）

### 需要如实说明的点（重点，信息中心是最容易被追问细节的角色）
1. 当前安全基线是设计与前端预留，**不等于**通过等保三级测评。
2. 后端真实接口尚未接入，现在权限校验逻辑在前端 mock 层面体现，真实的服务端强制校验会随后端接入同步实现。
3. 与教务、一卡通、身份认证等系统的集成需要具体调研对方接口能力，当前只能确认"架构上预留了集成能力和方向"，不能承诺"拿来就能对接"。
4. 私有化部署与 SaaS 部署的具体差异、报价、实施细节，引导到线下由技术和商务团队进一步确认（参考 `04-常见问题答复.md` 对应条目）。
