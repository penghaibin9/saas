# 06 当前阶段如实说明话术

- **文档性质**：销售/售前对客沟通材料——"实话实说"口径卡，全体销售/售前的内部培训与自查依据
- **适用对象**：全体销售、售前顾问，演示前必读，客户追问敏感问题时查阅
- **依据**：共享事实底稿"0. 项目与阶段"章节（当前真实阶段）
- **当前阶段声明**：当前为可演示版本，PC 端 UI 母版对接中、模块齐全、使用 mock 数据；小程序为纯 mock 演示闭环；后端未接入真实数据，接入按 API 契约推进中；本产品尚未经过等保三级测评
- **生成日期**：2026-07-04

## 一、当前处于什么阶段（如实底稿，销售必须记住）

| 部分 | 真实现状 |
|---|---|
| PC 管理端（frontend/，Vue3） | 正在做统一 UI 母版对接；12 个业务模块（学生主档、数字迎新、在校服务、学业过程、岗位实习、毕业设计、就业服务、数据驾驶舱、审批中心、权限与流程、系统管理、平台运营）齐全；当前使用 mock 数据 |
| 学生/教师小程序（miniapp/，uni-app + Vue3） | 纯 mock，但**可运行、可构建、可演示**；H5 和微信小程序两种构建方式均验证通过 |
| 数据库设计 | 已完成设计并冻结成文档（`docs/05-数据接口权限与安全/database/00-数据库设计冻结总册.md`），但这是"设计文档"，不等于"已经有真实数据在跑" |
| 后端（backend/） | 仅有基础配置、中间件、工具类代码，**真实业务接口尚未接入**；技术栈已确定：PostgreSQL + Python FastAPI + SQLAlchemy + Alembic |
| API 接口契约 | 已完成设计并冻结成文档（`docs/05-数据接口权限与安全/api/00-API契约冻结总册.md`），后端将按此契约实现，但**契约文档不等于接口已经实现** |

**一句话总结现状**：设计已经想清楚、写清楚、冻结了；前端和小程序的界面与操作闭环可以演示；后端把这些设计变成真实可用的系统，这件事正在推进中，还没有完成。

## 二、能承诺什么

1. 能承诺：今天演示的 PC 端界面、模块结构、操作流程、权限逻辑、审批流程，是产品真实的设计和实现，客户看到的操作路径就是未来真实系统的操作路径（细节可能随实施打磨微调）。
2. 能承诺：小程序（学生端+教师端）是可以真实运行、真实构建、真实演示的，客户可以要求现场用手机/开发者工具打开体验。
3. 能承诺：数据库设计和 API 接口契约都已经完成设计并冻结，这意味着后端接入不是"从零开始想怎么做"，而是"按已经定好的规范去实现"，方向是明确的。
4. 能承诺：安全基线（会话管理、脱敏分级、导出授权、审计留痕）在设计层面已经想清楚，并且是参照等保三级的思路设计的，具备后续测评的基础。
5. 能承诺：我们会如实、及时地反馈客户在演示中提出的问题和需求给产品/技术团队，并给出书面回复。

## 三、不能承诺什么

1. **不能承诺**"系统已经接入真实后端"或"已经在处理真实学校数据"——目前没有。
2. **不能承诺**"已经通过等保三级测评"——目前只是设计思路参考了等保三级要求，没有经过专业测评机构认证。
3. **不能承诺**"能马上连上贵校的教务系统/一卡通/身份认证系统"——集成能力是架构预留，具体能不能对接、多久能对接，需要先调研对方系统的接口能力。
4. **不能承诺**具体的实施周期数字（比如"三个月就能上线真实系统"）——这取决于部署方式、集成复杂度、数据迁移情况等多个变量，没调研清楚之前不能报数字。
5. **不能承诺**具体报价——报价需要商务团队根据学校规模、部署方式、定制内容评估后给出。
6. **不能承诺**"已经有其他学校在正式使用"——如果确实没有客户在使用真实系统，就不能这么说。
7. **不能承诺**"风险预警能发现所有风险学生、不会漏判"——这是辅助机制，不是万能保证。

## 四、如何把"演示版"讲得专业而不失真（表达技巧，不是话术造假）

- **用"样板间"类比**：这是一个装修完成、可以真实走动体验的样板间，结构、动线、设计都是真的，只是还没有家具（真实数据）搬进来住。这个类比能让客户理解"可演示 ≠ 没价值"，同时不掩盖"还没有真实数据"这个事实。
- **主动说，不要等被问**：在演示开场就主动说明当前阶段，比被客户发现后追问再解释，专业度高很多，也显得更坦诚、更有底气。
- **强调"设计已冻结"的价值，而不是回避"后端未接入"的事实**：把数据库设计冻结、API 契约冻结讲成"我们已经把最难想清楚的部分想清楚了，接下来是按图施工"，这是真实且积极的表达，不是遮掩。
- **把"正在推进中"讲成一个时间线上的确定位置，而不是含糊其辞**：比如"设计阶段已完成→当前是前端与小程序的可演示阶段→下一步是后端按契约接入"，让客户感觉到这是一个有节奏、按计划推进的项目，而不是随口说"快了快了"。
- **对专业听众（信息中心）要更精确**：面对懂技术的听众，直接说清楚"数据库设计冻结""API 契约冻结""FastAPI 技术栈已定"这些具体、可验证的事实，比笼统地说"我们技术很先进"更让人信服。

## 五、遇到客户追问后端/数据时的标准回应

### 场景 1：客户问"这是真实数据吗？"
"不是，这是我们准备的演示数据，方便大家清楚地看到系统的功能和操作方式。真实的后端数据接入正在按已经冻结的接口契约推进。"

### 场景 2：客户问"什么时候能看到真实系统？"
"这取决于具体项目的实施安排，包括部署方式的选择、跟贵校现有系统的对接需求等，我们需要先做一轮详细的需求调研，才能给出准确的时间表，这个建议留到项目洽谈阶段具体讨论。"

### 场景 3：客户质疑"你们是不是在演示一个'假系统'，忽悠我们？"
"完全理解大家的疑虑，我想澄清一下：今天演示的界面、功能、操作流程都是真实的产品设计和实现，不是效果图或者视频，大家可以现场任意点击操作。唯一还没有完成的是把这套系统接上贵校（或任何学校）的真实业务数据，这部分我们在演示一开始就主动说明了，也希望通过这种透明的方式让大家对我们的产品阶段有准确的判断，而不是等大家发现了才被动解释。"

### 场景 4：客户追问"你们凭什么说自己能做到等保三级？"
"我们没有说'已经做到'等保三级，我这边要澄清一下：我们是参照等保三级的要求思路，做了安全基线的设计和前端预留实现，比如会话管理、敏感数据分级脱敏、导出审计这些机制。但等保三级测评是需要专业测评机构按国家标准流程认证的，我们目前还没有经过这个认证流程，这个我们会如实告知，不会说过头的话。"

### 场景 5：客户说"其他厂商都说自己是成熟产品，都能马上用，你们怎么还没做完？"
"每家的产品成熟度和阶段确实不一样，我们选择在这个时间点如实地跟大家沟通我们的真实阶段，是因为我们认为这样的合作关系更长久、更值得信任。如果贵校现阶段需要的是马上能跑真实业务的系统，我们理解这可能不是最匹配的时间点；如果贵校是在做中长期的选型规划、愿意看到一个设计扎实、按节奏推进的产品，我们很希望能保持沟通，跟进我们后续的进展。"

## 六、避免过度承诺的红线清单（不可触碰）

1. **不能说**"已经接入真实后端""已经联调真实数据""系统已经上线运行"。
2. **不能说**"已经通过等保三级测评""已经拿到等保三级证书"。
3. **不能说**"已经在 XX 学校正式使用"（如果没有真实客户在使用真实系统的话）。
4. **不能说**"可以对接任何系统，包你满意"这类无条件保证型话术。
5. **不能说**具体的、未经确认的实施时间承诺（比如"一个月就能上真实系统"）。
6. **不能说**具体的、未经商务确认的报价数字。
7. **不能贬低或编造**任何具体竞品的缺点（参见 `05-竞品对比话术.md`）。
8. **不能在客户不知情的情况下**用真实数据的口吻讲述 mock 演示数据（比如把演示租户"演示职业技术学院"的数字说成"这是某某真实学校的数据"）。
9. **不能对**未在本文档或 `04-常见问题答复.md` 覆盖的技术细节**临场编造答案**——统一用"记录下来，会后确认书面回复"处理。
10. **不能因为**担心客户流失而在心理压力下临时突破以上红线——如果拿不准某句话能不能说，先不说，事后跟团队确认。
