一 核心用户角色与使用习惯
读完 82 屏小程序闭环后的关键结论：这个系统 80% 的日常用户是「队列型」用户（每天进来处理一串待办），15% 是「看面型」（看全院/全校的面），5% 是「配置型」（权限/规则/租户）。三类人要的第一屏完全不同 —— 这决定了导航必须角色自适应，而不是给所有人同一棵菜单树。
辅导员队列型 · 最高频
每天用 请假审批、催办催交、风险学生跟进、迎新联系台账
最关心 我班里谁出事了、谁没交、今天要联系谁
不该看 全校数据、其他班学生、系统配置
第一屏 今日要处理的人（按急切度排序的队列）+ 本班风险面
指导教师队列型
每天用 周报批阅、开题/中期/成果批阅、打卡异常核实、巡访记录
最关心 待批数、谁逾期、谁异常
不该看 非本人指导学生、答辩评分（SoD 回避）
第一屏 批阅队列（周报 6 · 开题 2 · 异常 2），点开即批
教务老师队列＋看面
每天用 学业过程（成绩/预警/补考重修）、学籍异动审批、教学报表
最关心 教学口径的数据准确性、异动流程合规
不该看 学生家庭经济、心理等高敏字段
第一屏 学业过程看板 + 待我审批的异动
就业老师队列型
每天用 三方协议核验、未落实学生跟进、就业去向登记核实
最关心 就业率、材料待核数、临近毕业未落实名单
不该看 范围外专业的学生、批量导出通讯录
第一屏 就业率 + 材料核验队列 + 未落实分层名单
学工老师队列型
每天用 在校服务：宿舍/资助/违纪/工单、绿色通道审核
最关心 工单时效、资助合规、住宿异常
不该看 教学成绩明细、系统配置
第一屏 服务工单队列 + 资助审核待办
学院管理员看面型
每天用 全院过程监管（实习/毕设完成率）、超期待办督办、审批
最关心 哪个环节卡住了、哪个班/老师积压了
不该看 其他学院数据、平台租户配置
第一屏 全院横切看板（生命周期各段 + 卡点）+ 待督办
学校领导 / 院系领导看面型 · 只读
偶尔用 数据驾驶舱、就业率、风险趋势、对上报表
最关心 一眼看懂全校health、能截图进 PPT
不该看 操作入口（只读，不给按钮）
第一屏 驾驶舱：大数字 + 趋势 + 风险分布，零操作
系统管理员配置型 · 低频高危
偶尔用 用户/角色/权限/数据范围、组织结构、审计日志
最关心 改动影响多少人、能不能回滚、有没有留痕
不该看 学生业务明细（可配置但默认不看数据）
第一屏 系统健康 + 待审的权限申请 + 最近变更留痕
平台运营人员配置型 · SaaS 侧
每天用 租户列表、套餐订单、集成/同步任务、活跃度
最关心 哪所学校快到期、哪个同步挂了
不该看 任何一所学校的学生个人数据
第一屏 租户健康度矩阵 + 到期/异常预警
导航设计的三条推论 ① 同一个人有多个身份（小程序 T2：一个账号 6 个身份），角色切换器是一级公民，切换后待办、数据范围、菜单、工作台全部联动。② 队列型用户的入口不是「模块」而是「待办」——他们不关心功能在哪个模块里，关心「今天轮到谁」。③ 模块树只对看面型/配置型用户重要，所以模块导航可以收进第二层级，把第一层级让给「工作台 / 待办 / 学生」。
二 三套世界级 SaaS 信息架构方向
骨架图为示意（非视觉稿）。三套的差别不在皮肤，在「第一层级给谁」。
方向 A生命周期门户 · 顶部一级导航
参照 Stripe / Vercel 的顶部域导航 · 模块即主线
工作台 学生 培养过程 ▾ 实践 ▾ 就业 数据 审批
岗位实习
导航结构 顶部一级 = 生命周期域（工作台 · 学生 · 培养过程 · 实践教学 · 就业 · 数据 · 审批 · 管理），左侧二级 = 当前域内页面。域按学生成长时间线排序，老师一看就懂。
顶部 品牌 + 域导航 + ⌘K + 数据范围 + 角色切换；左侧 仅在进入域后出现，浅色、窄（212px）。工作台 按角色渲染不同看板。
适合 学院管理员、教务等「按业务域思考」的用户；给领导演示时结构感最强。
优点
内容区最宽（表格友好）；生命周期叙事直白，售前演示有故事线；与现有 adminMenu.js 树一一对应，改造成本最低。
风险
11 个模块顶部放不下，必须收纳成 5-6 个域（需要下拉）；辅导员每天要跨 4 个域跑，队列型用户路径变长；1280 宽度下顶部拥挤。
★ 最终推荐（细节见第三节）
方向 B角色工作台 OS · 待办驱动单栏
参照 Linear 的单栏效率导航 × Workday 的角色工作台 × 飞书的待办习惯

现在最该处理
我的面
导航结构 无顶部一级导航。左侧一根浅色单栏分三段：固定锚点（工作台 / 待办中心 / 学生 360）+ 模块分组（培养过程 · 治理 · 平台，按当前角色过滤，进模块后二级菜单原位展开，手风琴式）+ 底部主题/收起。
顶部 退化为信息层：租户品牌 · ⌘K 全局搜索 · 数据范围镜片 · 通知 · 角色切换器。不承载导航，永远不拥挤。工作台 = 角色的「今天」：最该处理队列 + 角色指标 + 风险面。
模块摆放 辅导员只看到（实习 / 在校 / 学生主档 / 审批）4 项；系统管理员才看到「平台」组；领导的栏里只有工作台+数据中心。菜单是权限的镜子。
优点
队列型用户两次点击到任何工作；菜单短（≤9 项）不吓人；BasePortalLayout 一次改造全端受益；角色=菜单=范围三位一体，卖点清晰。
风险
模块全景弱——需要「全部功能」入口兜底；手风琴二级需要克制（一次只展开一个模块）；对习惯了传统树形后台的老教务有一点学习成本。
方向 C指挥舱 · 三栏检件流
参照 Superhuman / 邮件客户端的三栏批处理 · 为"批阅"而生
实习指导教师 ▾
待批队列 · 8
导航结构 最左 48px 图标轨（工作台/队列/学生/数据/管理），第二栏是「检件列表」，第三栏是详情+操作。J/K 上下切件、Enter 通过、R 驳回——把批阅做成收邮件。
工作台 即队列本身；模块 全部折进图标轨的抽屉里。适合指导教师/就业老师这类重批阅角色，效率天花板最高。
优点
批阅效率业内最强；差异化极高，售前印象深刻；键盘流对年轻教师有吸引力。
风险
三栏在 1366 屏局促；表格管理类页面（学生主档/权限）不适合塞第三栏，需要两套壳；对年长教师太"极客"，培训成本高；改造现有 80+ 页面成本最大。
三 最终方案：方向 B「角色工作台 OS」＋ C 的检件流做审批中心
① 为什么最适合职业院校
职校管理的本质是「过程催办」：打卡、周报、材料、审批，全是队列。B 把队列放在第一屏、把模块收进第二层级，与 80% 用户的真实工作形状一致。同时保留「培养过程」生命周期分组语言，领导和售前需要的叙事没有丢。
② 为什么比普通后台高级
普通后台（若依/政务风）的特征是：一棵所有人相同的深色菜单树 + 一进来是空表格。B 的特征是：菜单是权限的镜子、首屏是今天的工作、范围永远挂在顶栏。这三点都是 Workday/飞书级的产品思想，不是皮肤。
③ 为什么老师用起来不累
辅导员的菜单只有 7 项；任何待办两次点击可达；审批中心用 C 的三栏检件流，批 38 份周报不用来回跳页；全局 ⌘K 搜学生直达 360。累的根源（找入口、跳页、翻表格）被逐个拆掉。
④ 为什么能扩展到更多学校与角色
菜单树来自 adminMenu.js × 角色过滤，新角色 = 新过滤规则，不动布局；品牌来自 tenantBrandConfig，主题 6 皮肤变量化；新模块只是分组里多一行。壳（BasePortalLayout）一次升级，12 个模块与未来模块全部继承。
落到现有工程：左栏 = BasePortalLayout 的 aside 消费 getVisibleAdminMenu(ctx)（已存在，无人消费）；固定锚点 + 分组手风琴只是菜单数据的渲染升级；角色切换器复用各模块已有的 switchRole 上下文；路由零改动。
