## 一、数据库总体原则

### 1.1 命名与主键

```text
1. 所有表统一 t_ 前缀，蛇形小写（t_student_profile）。
2. 主键统一 id BIGINT，不用 AUTO_INCREMENT 自增，由应用层雪花/发号器生成
   （原因：多租户 + 未来分库分表 + 数据合并迁移，自增 ID 会冲突）。
3. 外键统一 xxx_id BIGINT；除强一致场景外，不建物理外键约束，
   由应用层保证引用完整性（原因：多租户分库、批量导入、逻辑删除场景下物理外键会卡住）。
4. 枚举统一用稳定英文大写编码字符串（如 'ONBOARD'/'RETURNED'），
   禁止在库里存中文状态、禁止用魔法数字 0/1/2 作为唯一真相（老系统的 0/1/2 在本册已翻译为英文枚举，见第 5 章）。
5. 金额统一 DECIMAL(12,2)，禁止 float/double。
6. 时间统一时间戳类型（PostgreSQL：TIMESTAMP，建议 TIMESTAMPTZ），禁止用字符串存时间。
7. 布尔统一 BOOLEAN（PostgreSQL 原生），字段名用 is_xxx / enabled。
8. JSON 字段统一 JSONB（PostgreSQL），用于"结构不固定的配置/快照/差异"，不用于需要检索过滤的业务字段。
```

**方言说明（已拍板：数据库 = PostgreSQL）**：本册第 4 章的 DDL 示例沿用通用 SQL 写法（`DATETIME`/`TINYINT(1)`/`JSON`）以便阅读，**落地时以下列 PostgreSQL 规范类型为准**（由 SQLAlchemy 模型统一约束，Alembic 生成）：

| 本册示例写法 | PostgreSQL 规范类型 | 说明 |
|---|---|---|
| `BIGINT` 主键 | `BIGINT`（应用层雪花/发号器赋值，非 `SERIAL`） | 多租户 + 合并迁移不能自增 |
| `DATETIME` | `TIMESTAMP`（建议 `TIMESTAMPTZ`） | 统一时区 |
| `TINYINT(1)` 0/1 | `BOOLEAN` | is_xxx / enabled / is_deleted |
| `INT` | `INTEGER` | version、计数 |
| `JSON` | `JSONB` | 配置/快照/差异 |
| `VARCHAR(n)` / `TEXT` / `DECIMAL(p,s)` | 同名 | 直接可用 |
| `UNIQUE KEY` / `KEY idx_*` | `UNIQUE CONSTRAINT` / `CREATE INDEX` | Alembic 迁移里显式建 |

### 1.2 每张业务表的强制公共字段

```sql
tenant_id   BIGINT      NOT NULL   -- 租户（学校）ID，行级隔离，见 §10
created_at  DATETIME    NOT NULL
updated_at  DATETIME    NOT NULL
created_by  BIGINT      NULL       -- 创建人 user_id
updated_by  BIGINT      NULL       -- 最后修改人 user_id
is_deleted  TINYINT(1)  NOT NULL DEFAULT 0   -- 逻辑删除
version     INT         NOT NULL DEFAULT 0   -- 乐观锁（关键业务表）
```

**三类表例外（重要）：**

| 表类 | 例外 | 原因 |
|---|---|---|
| 审计/日志/流水表（`t_*_audit`、`t_*_log`、`t_*_event`、`t_checkin`） | **无 `is_deleted`、无 `updated_at/updated_by`、无 `version`**，只允许追加（append-only） | 审计与流水禁止软删除替代冲正，必须不可变（总册 §16、01 §8.1） |
| 全局字典/模块定义/权限定义（`t_dict`、`t_module_def`、`t_permission`） | **无 `tenant_id`**（跨租户共享的系统级元数据） | 全平台统一定义，不属于某个学校 |
| 平台运营表（`t_tenant`、`t_saas_package`） | **无 `tenant_id`**（它们本身就是租户维度） | 控制面数据 |

### 1.3 文件不落库原则

```text
业务表禁止存大文件二进制、禁止存服务器真实路径。
业务表只存 file_id（指向 t_file_object）。
t_file_object 存：file_key（对象存储 key）、url 生成规则、hash、size、mime_type。
预览/下载走短期签名 URL；敏感材料下载写 t_file_access_log。
```

### 1.4 状态与留痕原则

```text
1. 每个业务对象有且只有一个"主状态字段"（status / current_stage），走冻结状态机（第 5 章）。
2. 旁路状态（请假中/换岗中/风险处理中）不覆盖主状态，另记子流程。
3. "退回"可重新提交；"驳回/拒绝/终止"为永久，两者语义不可混用。
4. 审批、批阅、退回、发布、归档、导出、身份切换、越权 必须留痕（第 13/16/17 章）。
5. 退回原因必填且 ≥5 字（UI V2.1 冻结）。
```

### 1.5 多租户原则（已拍板冻结）

**采用单库 / 单 schema + `tenant_id` 行级隔离。**

```text
1. 所有业务表都必须有 tenant_id（NOT NULL）。
2. 所有查询默认带 tenant_id（中间件强制注入 WHERE tenant_id = :currentTenant，禁止业务代码手写）。
3. 跨租户访问禁止。
4. 平台运营端查看多租户数据必须走权限校验 + 安全审计（不得裸查）。
5. 一期不做每校独立库，也不做每校独立 schema。
```

> 例外仍是 §1.2 列出的控制面/系统级元数据表（`t_tenant`、`t_saas_package`、`t_dict`、`t_module_def`、`t_permission`）——它们本身就是跨租户维度，不带 `tenant_id`。详见 [第 10 章](#十多租户与数据范围设计)。

## 三、核心 ER 关系说明

### 3.1 一张图看懂主干（文字版 ER）

```text
                         t_tenant（学校/租户）
                              │ 1:N
        ┌─────────────────────┼───────────────────────┐
        │                     │                        │
 t_tenant_brand_config  t_tenant_module_entitlement  t_user（账号）
   （品牌配置 1:1）        （买了哪些模块 1:N）           │ 1:N
                                                        │
                                              t_user_role ── t_role ── t_role_permission ── t_permission
                                                        │
                                              t_user_context ── t_user_active_context（当前身份）
                                                        │
                                              t_student_user_link（旧user_id↔student_id 映射）
                                                        │ N:1
                                        ┌───────────────┴───────────────┐
                                        │                               │
                              t_student_profile（学生主档·全平台唯一键 student_id = id）
                                        │ 1:N（所有业务都挂 student_id）
   ┌──────────┬──────────┬──────────┬──┴───────┬──────────┬──────────┬──────────┐
 组织关系   阶段事件   时间线    迎新       在校服务    学业      毕业设计   岗位实习   就业
 org_relation stage_event timeline onboarding_* service_*  academic_* gd_*      intern_*  employment_*
                                        │
                       所有业务共享的横切能力（不重复造）：
        t_unified_todo（待办）· t_unified_message（消息）· t_workflow_instance/task（审批）
        · t_file_object（文件）· t_security_audit（审计）· t_filing_record（归档）
```

### 3.2 五条必须记住的核心关系

1. **一切以 `student_id` 串联**：`student_id` = `t_student_profile.id`。所有业务表（毕设、实习、就业、服务、学业……）都带 `student_id` 外键，禁止长期只用 `user_id`/学号/手机号做主键。
2. **旧账号靠映射表接入**：老系统 `t_user.id`（role=4 学生）通过 `t_student_user_link` 映射到 `student_id`，不直接改老表。
3. **权限四要素叠加**：一次访问 = `模块授权(entitlement)` × `角色权限(role_permission)` × `数据范围(data_scope)` × `当前身份(active_context)`，四者求交，见第 10/11 章。
4. **待办/消息/审批/文件/审计是横切公共表**：任何业务模块不自建一套，统一挂 `source_module + source_biz_type + source_biz_id`。
5. **归档表共用**：`t_filing_record` 用 `(biz_module, biz_id)` 区分毕设/实习/就业归档，一张表服务多模块。

## 四、每张表字段设计

> 说明：**底座层与两大 MVP 核心模块（毕设、实习）给出完整字段 DDL**（这些是先开发的，字段必须精确）；**扩展模块（迎新/在校/学业/就业/集成）给出表卡**（表名+中文+用途+主键+关键字段+状态+租户+软删+页面），字段级 DDL 在各中心深化文档已有，后端阶段落地时以本册表卡为骨架、深化文档为细节。
>
> 表卡统一含 13 项：表名 / 中文 / 用途 / 主键 / 关键字段 / 外键 / 状态字段 / tenant_id / created_at·updated_at / created_by·updated_by / is_deleted / PC 页面 / 小程序页面。为节省篇幅，公共字段（§1.2）默认全部具备，表卡只标注**例外**。

### 4.1 模块 1 · SaaS 租户与学校品牌（本册新设计，无深化文档来源）

```sql
-- 4.1.1 t_tenant 租户（学校）表 —— 控制面，无 tenant_id 列（自身即租户维度）
CREATE TABLE t_tenant (
  id BIGINT PRIMARY KEY,
  tenant_code   VARCHAR(50)  NOT NULL COMMENT '租户编码（学校唯一标识，如 hnsh）',
  school_name   VARCHAR(200) NOT NULL COMMENT '学校全称',
  short_name    VARCHAR(100) NULL     COMMENT '学校简称',
  region_code   VARCHAR(50)  NULL     COMMENT '省市区编码',
  deploy_mode   VARCHAR(30)  NOT NULL DEFAULT 'SAAS' COMMENT 'SAAS/PRIVATE 部署模式',
  -- 一期固定单库+行级隔离，db_mode/db_name 仅为后期私有化预留，正常恒为 SHARED
  db_mode       VARCHAR(30)  NOT NULL DEFAULT 'SHARED' COMMENT '一期恒 SHARED（行级隔离）；DEDICATED 为后期私有化预留',
  db_name       VARCHAR(100) NULL     COMMENT '仅后期私有化独立部署时用，一期为 NULL',
  status        VARCHAR(50)  NOT NULL COMMENT 'PROVISIONING/ACTIVE/SUSPENDED/ARCHIVED',
  contact_name  VARCHAR(100) NULL,
  contact_phone_encrypted VARCHAR(500) NULL,
  created_at DATETIME NOT NULL, updated_at DATETIME NOT NULL,
  created_by BIGINT NULL, updated_by BIGINT NULL, is_deleted TINYINT(1) NOT NULL DEFAULT 0,
  UNIQUE KEY uk_tenant_code (tenant_code),
  KEY idx_status (status)
);

-- 4.1.2 t_tenant_brand_config 学校品牌配置表 —— 对应 UI 的 tenantBrandConfig，登录页/顶栏品牌全部来自这里
CREATE TABLE t_tenant_brand_config (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  platform_name    VARCHAR(200) NULL COMMENT '平台名称（顶栏主名称）',
  platform_subtitle VARCHAR(200) NULL COMMENT '平台副标题',
  browser_title    VARCHAR(200) NULL COMMENT '浏览器标题',
  logo_light_file_id BIGINT NULL, logo_dark_file_id BIGINT NULL,
  favicon_file_id  BIGINT NULL,   badge_file_id BIGINT NULL COMMENT '校徽',
  login_bg_file_id BIGINT NULL,   campus_line_file_id BIGINT NULL COMMENT '校园线稿/主楼',
  primary_color    VARCHAR(20) NULL COMMENT '品牌主色，如 #2563EB',
  secondary_color  VARCHAR(20) NULL,
  default_theme    VARCHAR(50) NULL COMMENT '默认主题：academy_blue/business_blue/eye_green/mono/gray',
  motto            VARCHAR(200) NULL COMMENT '校训',
  watermark_text   VARCHAR(200) NULL COMMENT '页面水印文案',
  config_json      JSON NULL COMMENT '其余可扩展品牌项',
  created_at DATETIME NOT NULL, updated_at DATETIME NOT NULL,
  created_by BIGINT NULL, updated_by BIGINT NULL, is_deleted TINYINT(1) NOT NULL DEFAULT 0, version INT DEFAULT 0,
  UNIQUE KEY uk_tenant_brand (tenant_id)
);

-- 4.1.3 t_saas_package 套餐定义表 —— 控制面，无 tenant_id
CREATE TABLE t_saas_package (
  id BIGINT PRIMARY KEY,
  package_code VARCHAR(50) NOT NULL COMMENT 'TRIAL/BASIC/STANDARD/PRO/FLAGSHIP/SINGLE_MODULE/PRIVATE',
  package_name VARCHAR(200) NOT NULL,
  included_modules JSON NOT NULL COMMENT '包含模块编码数组',
  max_students INT NULL, max_users INT NULL, trial_days INT NULL,
  price_year DECIMAL(12,2) NULL COMMENT '年费',
  enabled TINYINT(1) NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL, updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_package_code (package_code)
);

-- 4.1.4 t_tenant_subscription 租户订阅表
CREATE TABLE t_tenant_subscription (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
```

## 五、状态枚举设计

> 全部采用英文大写编码；老系统 0/1/2 数字状态已翻译（映射存 `t_dict`）。以下为**冻结清单**。

### 5.1 学生生命周期主阶段（t_student_profile.current_stage）
`ADMITTED → PRE_STUDENT_VERIFIED → REGISTERED_PENDING_ENROLLMENT → ENROLLED → GRADUATING → INTERN → GRADUATED → ALUMNI`
异常分支：`DEFERRED / NO_SHOW / SUSPENDED / DROPPED_OUT / TRANSFERRED / CANCELLED / MERGED / RECYCLED`

### 5.2 学生状态（t_student_profile.student_status）
`NORMAL / MERGED / RECYCLED`（学籍异动细分走阶段异常分支 + 审批单）

`GD_NOT_STARTED → TOPIC_SELECTING → TASKBOOK_PENDING → GUIDING → SUBMIT_PENDING_REVIEW →(通过)下一节点 /(驳回)RETURNED → MIDTERM_RECTIFY → DEFENSE_SCHEDULED → DEFENSE_SECOND(需二辩) → GRADE_PENDING_PUBLISH → COMPLETED → ARCHIVED`

### 5.4 岗位实习主状态机（t_assignment / 主线）
`INT_NOT_STARTED → PREPARING →(申请)APPLY_TEACHER_REVIEW → APPLY_COLLEGE_REVIEW → HIRED → READY →(到岗双确认)ONBOARD → ASSESSING → COMPLETED → ARCHIVED`

### 5.5 实习申请五级（t_intern_application.status）
`PENDING / TEACHER_AGREE / TEACHER_REJECT / COLLEGE_PASS / COLLEGE_REJECT / HIRED / NOT_HIRED`（对应老 0-6，页面须显示"卡在哪一方"）

### 5.6 周报/日志/请假（t_intern_report / t_leave）
`DRAFT / SUBMITTED / APPROVED / RETURNED`（老 0/1/2/3）

### 5.7 三方协议双状态（t_agreement）

### 5.8 打卡补卡（t_checkin.makeup_status）
`PENDING / APPROVED / REJECTED`；打卡结果 `NORMAL / ABNORMAL / MISSING`

### 5.9 成绩发布（t_gd_grade / t_intern_final_score）
`PENDING_CALC / PENDING_REVIEW / PUBLISHED / WITHDRAWN`

### 5.10 归档五态（t_filing_record.status）
`PENDING_GEN / PENDING_SUBMIT / SUBMITTED / ARCHIVED / RETURNED`（老 0/1/2/3/4）

### 5.11 模块授权（t_tenant_module_entitlement）
`TRIAL / ACTIVE / EXPIRING / EXPIRED_READONLY / SUSPENDED / ARCHIVED`

## 十、多租户与数据范围设计

### 10.1 多租户（tenant_id）—— 已拍板冻结

- **一期唯一方案：单库 / 单 schema + 行级隔离**。所有业务表带 `tenant_id`，应用层统一在每条 SQL 注入 `WHERE tenant_id = :currentTenant`，中间件层（FastAPI 依赖注入 + SQLAlchemy 会话级过滤）强制，禁止业务代码手写。
- **跨租户访问禁止**；平台运营端（`/platform`）查看多租户数据必须走权限校验 + 写 `t_security_audit`，不得裸查。
- **一期不做每校独立库、不做每校独立 schema**（`t_tenant.db_mode` 恒 SHARED，DEDICATED 仅为后期私有化预留）。
- 控制面表（`t_tenant / t_saas_package / t_tenant_subscription`）与系统级元数据（`t_dict / t_module_def / t_permission`）**不带 tenant_id**。

### 10.2 数据范围（12 种，独立于角色）

`SELF / CLASS / COUNSELOR_CLASSES / GD_STUDENTS / INTERN_STUDENTS / ENTERPRISE_AUTH_STUDENTS / MAJOR / COLLEGE / SCHOOL / DEPARTMENT / TEMP_AUTH / CUSTOM`

- 存储：`t_data_scope_rule`（角色级/用户级）+ `t_user_context.data_scope`（身份级）。
- 生效：`dataScopeMiddleware` 把范围翻译为 SQL 过滤（如 GD_STUDENTS → `student_id IN (t_student_org_relation WHERE person_id=当前教师 AND relation_type=gd_teacher)`）。
- 企业导师 `ENTERPRISE_AUTH_STUDENTS` = 仅授权在岗学生，且对毕设成果、家庭/心理/处分信息**硬隔离**（红线）。

### 10.3 权限四要素求交（一次访问）

```text
可访问数据 = 模块已授权(entitlement=ACTIVE/TRIAL)
           ∩ 角色有权限码(role_permission)
           ∩ 数据范围过滤(data_scope by active_context)
           ∩ 未触发 SoD
后端每个业务接口必须四要素全过；前端隐藏只是体验，不是安全边界。
```

### 10.4 模块到期只读（写路径拦截）

到期（EXPIRED_READONLY）后：查询放行；`create/update/submit/approve/import` 全拦截，返回 `MODULE_EXPIRED_READONLY`；历史可查；导出按合同（`t_tenant_subscription.readonly_after_expired` + 导出权限）。

## 十一、多角色与当前角色设计

- 一个 `t_user` 可有多个 `t_user_context`（辅导员/毕设导师/实习导师/答辩专家/学院管理员/企业导师……）。
- 每客户端（PC/学生小程序/教师小程序）当前只激活一个 `t_user_active_context`。
- 切换身份 → 重新加载 菜单/待办/数据范围/按钮/首页；写 `t_user_active_context` + 上下文切换审计。
- **权限不合并**：辅导员身份看本班，切到实习导师身份看实习学生，两者数据范围严格隔离（防越权）。
- 对应 UI：PC 顶栏角色切换器、教师小程序 T2 角色切换。

## 十二、待办中心设计

- 单表 `t_unified_todo`，所有模块统一生成，禁止各建一套。
- 去重键：`source_module + source_biz_type + source_biz_id + todo_type + assignee_id`。
- 类型：`APPROVAL / REVIEW / CONFIRM / RISK / MATERIAL / IMPORT / EXPORT / ARCHIVE / REMINDER`。
- 多端同步：PC 工作台、教师小程序待办、学生小程序待办读同一张表；`assignee_context_id` 关联当前身份，保证"切身份看到对应待办"。
- 与流程联动：`t_workflow_task` 生成时同步生成 `t_unified_todo`（action_url 指向处理页）。

## 十三、审批流设计

- 流程与业务分离：`t_workflow_def`（可配置、版本化 DRAFT/PUBLISHED/ENABLED/DISABLED）→ `t_workflow_node`（节点+处理人规则+可用动作+是否允许移动端）→ `t_workflow_instance`（业务实例，挂 `module_code/biz_type/biz_id/applicant_id`）→ `t_workflow_task`（待处理任务）→ `t_workflow_action_log`（每步动作留痕，append-only）。
- 处理人规则（`assignee_rule` JSON）：指定用户/角色/申请人辅导员/毕设导师/实习导师/企业导师/上级部门/自定义表达式。
- 典型流：自主实习申请（学生→辅导员→学院管理员→实习就业处备案）、成绩变更（教师→学院→教务）、主档更正（申请→责任部门，SoD 校验 applicant≠reviewer）。
- 幂等：`startWorkflow` 与 `task action` 用 `request_id` 幂等，重复返回原结果。
- SoD：`t_sod_rule` 拦截（申请人≠审批人、导出申请人≠导出审批人、毕设导师≠自己学生答辩评分人），违反写安全审计。

## 十四、文件与材料设计

- `t_file_object` 唯一文件登记表：`file_key`（对象存储 key）+ `hash_sha256`（去重/校验）+ `size_bytes` + `mime_type` + `sensitive_level` + `(biz_module,biz_id,student_id)` 归属。
- 业务表只存 `xxx_file_id BIGINT`，禁止存路径/大二进制。
- 预览/下载走**短期签名 URL**；敏感材料（证件、家庭、心理、处分、就业证明、劳动合同）下载/预览写 `t_file_access_log`（append-only）。
- 承载清单（毕设任务书/开题/中期/成果/查重报告、实习协议/保险/周报附件/企业评价、就业证明/劳动合同、迎新材料、证明文件、各类归档包）统一走 file_id。

## 十五、消息通知设计

- 消息 ≠ 待办：待办必须处理，消息只需知道。
- `t_message_template`（模板：编码/标题模板/内容模板/渠道/是否回执）+ `t_unified_message`（站内信实例：接收人/已读/回执/action_url）+ `t_message_channel_log`（短信/微信/企微/钉钉下发回执，append-only）。
- 渠道：站内信 / 学生小程序 / 教师小程序 / 短信 / 企微·钉钉·邮件（预留）。
- 场景：提交成功、退回修改、审核通过、审批驳回、材料补充、截止提醒、打卡异常、风险升级、归档缺失、模块即将到期/已到期、导出完成。

## 十六、审计日志设计

五张审计表，全部 **append-only（无 is_deleted / 无 update）**，留存 ≥3 年：

| 表 | 用途 | 触发写入 |
|---|---|---|
| t_student_field_audit | 主档字段级审计 | 任何 t_student_profile 字段/阶段/组织关系/联系方式/证照/授权变化（含系统同步） |
| t_security_audit / t_security_audit_log | 安全审计 | 登录/登出/身份切换/越权/敏感字段查看/文件下载/导入/导出/删除/合并/放行 |
| t_permission_audit | 权限审计 | 角色/权限/授权变更（before_json/after_json） |
| t_operation_audit_log | 业务操作审计 | 审批/批阅/退回/驳回/发布/归档等写操作（承接老系统 auditMiddleware 全局留痕） |

## 十七、隐私脱敏与数据导出设计

### 17.1 敏感字段清单（默认脱敏）
身份证号、手机号、家庭地址、家长电话、家庭经济困难信息、心理信息、处分信息、定位明细、企业联系人电话、成绩明细。

### 17.2 存储方式
敏感字段一律 `xxx_encrypted`（密文）+ `xxx_hash`（用于查重/匹配，不可逆），**库里不存明文**。展示按字段权限 `field:view_masked / field:view_full`。

### 17.3 三种导出模式（t_export_task）
1. **当前列表导出**（CSV/Excel）：按数据范围，敏感字段脱敏，须填用途，写 `t_security_audit_log`。
2. **加密 PDF 档案导出**：加水印 + 防伪二维码 + 时间戳 + 导出人/用途；异步任务，下载链接短期有效。
3. **脱敏外发导出**：姓名→随机编码、身份证删除/摘要、手机删除、地址删除；须填外发对象/目的/保留期限；记录脱敏规则版本 + 文件 hash。

### 17.4 导出留痕
`t_export_task`（模式/条件/字段清单/数量/文件hash/状态）+ `t_security_audit_log`；导出与导出审批走 SoD（申请人≠审批人）。

## 十九、Alembic / SQLAlchemy 迁移建议（技术栈已拍板）

> **已拍板技术栈**：PostgreSQL + Python FastAPI + SQLAlchemy + Alembic；Redis / MinIO / 对象存储后续预留。本册 DDL 示例为通用 SQL 骨架，落地以 §1.1 方言映射表的 PostgreSQL 类型为准，由 SQLAlchemy 模型统一约束、Alembic 生成迁移。

1. **分层建模**：建 `Base` + `TenantMixin`(tenant_id) + `TimestampMixin`(created_at/updated_at) + `AuditMixin`(created_by/updated_by) + `SoftDeleteMixin`(is_deleted) + `VersionMixin`(version)，各表按需混入；审计/流水表不混入 SoftDelete/Version。
2. **迁移分批**（与第 19·5 开发分期 P0–P3 对齐）：
   - `0001_base`（P0）：t_tenant / t_tenant_brand_config / t_user / 角色权限 / 数据范围 / 模块授权 / 字典 / 组织架构 / t_file_object / 审计 / t_unified_todo / 审批基础表
   - `0002_student_master`（P0/P1）：01 全部学生主档表 + 阶段/时间线
   - `0003_onboarding_teacher`（P1）：迎新 + 教师工作台/角色切换/审批详情相关
   - `0004_internship`（P2）：10 实习全表（第一主攻）
   - `0005_graduation_design`（P2）：11 毕设全表（第二主攻）
   - `0006_employment`（P2）：12 就业服务
   - `0007_academic` / `0008_campus_service`（P2/P3）
   - `0009_export_draft_message`（P3）：导出 / 弱网草稿 / 消息增强
   - `0010_platform_integration`（P3）：平台运营 / 授权套餐 / 集成开放
3. **枚举**：用 `String` + 应用层常量（PostgreSQL 也支持原生 ENUM，但为便于加值与迁移，统一用 `String` + 常量，不用 DB ENUM）；老系统 0/1/2 映射存 `t_dict`。
4. **JSON 字段**：统一 PostgreSQL `JSONB`（SQLAlchemy `from sqlalchemy.dialects.postgresql import JSONB`）。
5. **索引**：Alembic 迁移里显式建 §4 各表索引；`(tenant_id, ...)` 组合索引前置 tenant_id（配合行级隔离，命中率高）。
6. **不建物理外键**（见 §1.1），引用完整性走应用层 + 关键处 CHECK/触发器兜底（如 SoD applicant≠reviewer）。
7. **审计不可变**：审计表不加 `updated_at`；应用层禁 UPDATE/DELETE，可加 DB 触发器兜底。
8. **多租户迁移**：单库单 schema，一套库跑一次迁移即可（无需每租户重复）；租户隔离在应用层由 tenant_id 过滤保证。
9. **行级安全（可选加固）**：如需 DB 层兜底防跨租户，可后期启用 PostgreSQL Row-Level Security（RLS）按 tenant_id 加策略，与应用层过滤双保险。
