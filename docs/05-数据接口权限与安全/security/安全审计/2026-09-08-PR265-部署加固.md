## 使用边界

本批是新建空库安装的独立 production 候选配置，不是已经完成部署，不是旧 compose 的覆盖文件，也不能用来原地更换现有数据库密码或字段加密密钥。不要把 `docker-compose.security.yml` 与旧 YAML 叠加使用。**旧 HTTP 模板未被本批转换成安全生产入口，不能因此原样发布旧模板。**

已建校或已有数据的环境，必须另外审查数据库授权迁移、原加密/HMAC 密钥保留、文件卷 UID/GID、固定网段冲突、备份恢复、回滚窗口及 DNS/TLS 切换。禁止删卷重建、递归 chown 现有数据、重复跑初始化脚本，或把新生成的 Fernet/HMAC 密钥覆盖旧配置。账号与学校 IAM/商业授权的首次开通仍走现有受控流程；本包不偷偷灌账号或给首管自动授权。

## 实际配置

| 目标 | 实现 | 尚不能据此宣称 |
|---|---|---|
| HTTPS 入口 | 固定 DNS Host；80 的页面跳 443，明文 API 返回 426；TLS1.2/1.3；私有运维路径不经公网代理 | 公共证书链、自动续期、云防火墙已验收 |
| 四端静态服务 | 管理 PC `/`、学生 PC `/portal/`、企业 `/enterprise/`、H5 `/miniapp/`，history fallback；缺静态资源返回 404；HTML no-store | 四端真实业务与微信真机已经测试 |
| 凭据职责分离 | `compose.env` 只做插值；业务只读 `runtime.env`；root 仅给 mysql，迁移密码仅给 mysql/migrate | 运维 root/Docker 管理员看不到容器环境变量 |
| 数据库权限 | 空卷初始化撤销 runtime 初始权限，只授 SELECT/INSERT/UPDATE/DELETE；迁移账号仅 schema 级 ALL，没有全局权限 | 已做逐表最小权限、数据库层审计表不可变或存量账号授权迁移 |
| 应用进程 | backend、scheduler、file-scan 和 migrate 10001:10001；只读代码、cap_drop ALL、no-new-privileges；三应用资源限制及临时目录 noexec | 所有基础设施进程都非 root，或容器永远不可能逃逸 |
| 存储 | 三工作进程共享明确 uploads/exports/data 卷；空卷准备任务仅 root+CHOWN、无网络无凭据，非空错误属主拒绝 | 现有文件和 COS 配置已迁移验证 |
| 认证存储 | Redis AOF+noeviction、仅内部网络；保留应用原 Redis→MySQL 失败处理 | OOM/断网、多 HTTP worker、性能和恢复已通过 |
| 文件扫描 | 官方 ClamAV 签名卷及独立 scan 网络；扫描 worker 入栈、PING/VERSION 预检；后端与 worker 必须等扫描服务 healthy | 真实病毒样本/正常文件上传—扫描—绑定—下载、队列积压与重启恢复已完成 |

Nginx 只连接 edge，mysql 只连接 internal data；ClamAV 不连接数据库网。后台按需要具有 egress；这不是出站防火墙白名单。默认扫描器内存上限 4 GiB，应用/数据库也有独立上限，采购机器前要做总量预算和负载测试，不能据此认为低内存服务器一定能承载。

新 `backend/Dockerfile.security` 从仓库根目录构建，在 `/app/backend` 保持代码相对路径，同时复制 `/app/shared` 运行合同。原 `module_registry` 的 parents[3] 路径实际依赖它。编译工具只在 wheels 构建阶段，运行镜像仅安装冻结依赖与白名单目录；专属 dockerignore 排除 .env、密钥、测试和缓存。构建与基础镜像、发布镜像必须经扫描后固定 registry digest，校验摘要格式本身不是安全扫描。

运维探针在本机读取就绪 JSON，不把 ops token 放在 curl 命令行，不使用 HTTP_PROXY，也不跟随重定向。固定由应用归一化来源 IP，Uvicorn `--no-proxy-headers`；只信 nginx 的 `172.30.40.10/32`，不信整个私网。

## 新空库配置准备（本轮未执行真实环境操作）

在完整仓库根目录，由获授权运维人员按顺序准备：

```bash
python scripts/deploy/prepare-security-config.py --host "$PUBLIC_HOST" --new-empty-install
```

只创建新的 `deploy/env/security/`，已有目录即拒绝。目录 0700，文件 0600，随机生成相互独立的数据库/认证凭据，不输出值。六个镜像值先是 `REQUIRED_REVIEWED_DIGEST`，必须由操作者填为经过构建、漏洞扫描及验证的精确镜像引用。公钥证书和私钥分别放 `tls/fullchain.pem`、`tls/privkey.pem`（本配置要求 0600），证书必须包含精确主机 SAN，剩余有效期不少于 14 天。

应用发布镜像的构建入口是：

```bash
docker build -f backend/Dockerfile.security \
  --build-arg PYTHON_BASE_IMAGE="$REVIEWED_PYTHON_312_SLIM_DIGEST" \
  -t "$RELEASE_IMAGE_TAG" .
```

构建、扫描和受控推送完成后，使用该 APP_IMAGE registry digest；不要把本地 tag 冒充摘要。其他镜像须符合本配置的官方 MySQL 8、Redis、Nginx、ClamAV 运行合同，ClamAV 镜像还必须包含官方健康检查。操作者维护镜像更新周期，不把模板固定值当永久安全版本。

构建四端并确认 base 与上述 URL 匹配。微信/SMS/COS/SSO 等既有渠道需要合法配置，不能因为本地配置生成成功就宣称渠道已上线。**新空库初始化生成的是全新密钥；不能用于读取旧数据。**

```bash
python scripts/deploy/check-security-profile.py --repo .
```

这是只读预检。检查文件权限、四端产物、证书配对/主机/有效期、凭据强度与隔离、实际 Docker Compose 展开的 JSON、运行用户/能力/网络/端口/卷/依赖、镜像一致性、代理入口和扫描门禁。检测 shell 环境覆盖、错误值时拒绝。展开后的真实密码只存在进程内存，失败输出不回显 Docker stdout/stderr。不运行 up、迁移或其他生产写操作。

`preflightPassed=true` 仍返回 `releaseApproved=false`，不能作为公网放行证据。新环境通过独立发布审核后才由运维使用同一套文件启动；本次施工不执行该步骤。必须具备备份与对应密钥的恢复验证，不能只备份数据库文件。

### 真实失败与确认的缺陷

`Security deployment profile` run `34168137686` / job `101883155842` 实际失败，
最后回执为 `MYSQL_WAIT_FAILED`。镜像构建、非 root 镜像合同、完整 app 导入及真实
Compose 展开已经完成；不把该失败称为全项未运行，也不把上一提交的 Main/CI 成功
当成部署专项通过。旧作业未保存 MySQL 原始容器诊断，不能声称已从其日志看到退出原因。

源码追踪和真实 Bash 反例确认：官方 MySQL 入口 source 非可执行的 `.sh`，原脚本
在父 shell 启用 `set -u` 后未恢复；其后官方 `mysql_expire_root_user` 读取未设置的
`MYSQL_ONETIME_PASSWORD` 就会触发 unbound variable。此问题足以阻断首次启动；
不是通过加长等待、设置一个偶然缺失的变量或关闭安全检查来处理。

`01-accounts.sh` 现把所有选项、校验、MYSQL_PWD 和 SQL 放进一个子 shell，保留
内部严格失败退出，但不污染官方父入口；兼容 source 和直接执行，并沿用实际临时
服务的 SOCKET。只修改源码，不通过重启/删卷绕过失败的初始化。

同时修正数据库权限目标：MySQL 8.0 的库级 GRANT 中，下划线即使在反引号内也可能
作为通配符。对 `saas_lifecycle` 转义 `_`，限定精确 schema；runtime 仍仅 DML，
migrator 仍只在该 schema 有权限，不给全局权限或 GRANT OPTION。
