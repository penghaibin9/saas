## 一、权限模型：RBAC + 数据范围 + 字段权限三层

访问一条数据要同时过三道门，缺一即拒：

1. **功能权限点**（能不能用这个功能）：如 `student.profile.view`、`security.export.list`。不具备 → `NO_PERMISSION`（403）。
2. **数据范围**（这条数据在不在你能看的范围）：`ALL/SCHOOL/COLLEGE/CLASS/SELF/ASSIGNED`。不在范围 → `DATA_SCOPE_DENIED`（403）。
3. **字段权限**（这条数据里的敏感字段你能看脱敏还是完整）：`field:view_masked` / `field:view_full`（见 `03`）。

> 三层相互独立、逐层收紧：有功能权限 ≠ 能看这一行；能看这一行 ≠ 能看完整身份证。

## 二、7 类 PC 角色 × 默认数据范围

| 角色码 | 中文 | 默认数据范围 | 定位 |
|---|---|---|---|
| `PLATFORM_OPERATOR` | 平台运营 | `ALL`（跨租户） | 租户 / 授权 / 巡检；**不看学生业务明细**（见 `07`） |
| `SCHOOL_ADMIN` | 学校管理员 | `SCHOOL`（本校） | 全校业务最高权限 |
| `COLLEGE_ADMIN` | 二级学院管理员 | `COLLEGE`（本学院） | 学院级审批与管理 |
| `TEACHER` | 指导教师 | `ASSIGNED`（被指派学生） | 实习 / 毕设指导批阅 |
| `COUNSELOR` | 辅导员 | `CLASS`（本班级） | 班级学生日常管理 |
| `STUDENT` | 学生 | `SELF`（仅本人） | 本人自助 |
| `ENTERPRISE_MENTOR` | 企业导师 | `ASSIGNED` | 仅授权在岗学生；**硬隔离**毕设 / 家庭 / 心理 / 处分（见 `07`） |

> miniapp 教师身份（`COUNSELOR/MENTOR/INTERN_MENTOR/EMPLOYMENT/ACADEMIC/COLLEGE_ADMIN`）数据范围与上表语义对应，详见 `docs/05-数据接口权限与安全/rbac/04-数据范围矩阵.md`。

## 三、红线 6：普通老师只能看自己数据范围

这是最容易被忽视、也最容易越权的一条，必须后端强制：

| 角色 | 只能看到 | 典型越权（必须拒绝） |
|---|---|---|
| 辅导员 `COUNSELOR` | **本班级**学生及相关任务 | 查看 / 导出非本班级学生 → `DATA_SCOPE_DENIED` |
| 指导教师 `TEACHER` | **被指派**的实习生 / 毕设生 | 批阅非自己带教学生的周报 / 毕设 → 拒绝 |
| 就业 / 教务老师 | **本学院** | 跨学院查学生 → 拒绝 |
| 企业导师 | **授权在岗学生**，且字段受限 | 看毕设成果 / 家庭信息 → 硬隔离拒绝 |
| 学生 | **仅本人** | 猜 ID 看他人档案 → 拒绝 |

生效方式（引用 `rbac/04` 第五节）：

- **列表接口**：后端按登录上下文解析 `currentRoleCode + activeContextId + dataScope`，自动注入过滤条件（如 `WHERE class_id = :classId`）。**前端不传数据范围参数**，只传业务筛选。
- **详情接口**：查到数据行后**二次校验归属字段**（`college_id/class_id/student_id`）是否落在范围内；不在范围返回 `DATA_SCOPE_DENIED`，**不得返回"数据不存在"**（避免猜 ID 枚举）。
- **统计 / 看板接口**：先按范围过滤明细再聚合，防止"明细受限但汇总泄露超范围信息"。
- **导出接口**：先按范围过滤 → 再叠加导出权限分级与行数上限（见 `04`）。

## 四、红线 4：批量操作必须二次确认

批量分班、批量改学籍、批量催办、批量导出等影响面大，**前端二次确认 + 后端整批校验**双保险：

| 环节 | 要求 |
|---|---|
| 前端 | 弹二次确认框，显示受影响对象数量与范围摘要；高危批量（批量学籍变更）需再次输入确认或勾选风险提示 |
| 后端范围校验 | 批量对象集合**必须完全落在**当前角色数据范围内；**混入超范围 ID 整批拒绝**（或明确剔除并回告数量），**禁止"部分静默执行"** |
| 幂等 | 批量写接口带 `request_id` 幂等，重复提交返回 `IDEMPOTENCY_CONFLICT`，防重复执行 |
| 审计 | 批量操作全部写审计，记录对象数量、范围、操作人、结果（见 `05`）；批量导出另见 `04` |
| 敏感批量 | 批量学籍变更（`batchChangeStatus`）为 `SENSITIVE` 级，建议叠加审批（SoD）；批量催办为 `INTERNAL` 级 |

## 五、红线 7：逻辑删除，禁止物理删除

| 数据类别 | 删除方式 | 说明 |
|---|---|---|
| 业务表（学生主档、申请、材料等） | **逻辑删除**：`is_deleted TINYINT(1) DEFAULT 0` 置 1 | 默认查询带 `is_deleted = 0`；进 `t_student_recycle_bin` 回收站，可追溯 / 可恢复 |
| 审计 / 日志 / 流水表（`t_*_audit`、`t_*_log`、`t_*_event`、`t_checkin`） | **append-only，不可删不可改**（无 `is_deleted`、无 `update`） | 审计与流水**禁止用软删除替代冲正**，冲正须新增反向记录（见 `05`） |
| 物理删除 | **一律禁止**在业务链路出现 | 仅极端数据治理（如法定删除请求）走独立审批 + 审计的专用流程，不走常规接口 |

> 关键：删除是"标记不可见"，不是"抹掉证据"。任何"看起来删掉了"的数据都必须可被审计追溯到谁、何时、为何删除。

## 六、红线 8：后端必须再次校验，不能只靠前端

前端的菜单过滤、按钮隐藏、脱敏展示**全部只是体验优化**，真正边界在后端：

| 前端做了什么 | 后端仍必须做什么 |
|---|---|
| 隐藏无权限菜单 / 按钮 | 每个接口独立校验功能权限点，直接调 API 一样拒绝 |
| 按数据范围只展示部分列表 | 服务端强制注入 `tenant_id` + 数据范围过滤，不信任前端传参 |
| 脱敏展示身份证 / 手机号 | 服务端按字段权限决定返回脱敏值还是完整值，**DTO 层脱敏裁剪，禁止直接把表行返回前端** |
| 二次确认弹窗 | 服务端整批范围校验 + 幂等 |

固定要求（引用底稿 / DB 冻结册）：

- `tenant_id` 由后端从登录上下文解析并**中间件强制注入** `WHERE tenant_id = :currentTenant`，**禁止业务代码手写、禁止前端传**。
- 响应统一包裹 `{ code, message, data, requestId }`；**DTO ≠ 表结构**，对外必做字段脱敏与裁剪。
- 越权尝试写 `PERMISSION_DENIED` 审计事件，便于发现枚举 / 探测行为。

## 七、职责分离（SoD）与权限变更

- 高危双人原则：导出申请人 ≠ 审批人（`SOD_VIOLATION`，409）；权限授予者 ≠ 使用者。
- 角色 / 权限点 / 数据范围的任何变更**必须审计**（`PERMISSION_CHANGE`，记录 before/after，见 `05`）。
- 权限变更仅作用于本校（`SCHOOL`）范围；跨校 / 平台级授权归 `PLATFORM_OPERATOR` 模块授权范畴（见 `07`）。
