# 05-角色切换规则

- **文档性质**：角色/身份切换机制说明
- **适用端**：PC 管理端（`currentRoleCode` + `activeContextId`）+ miniapp 教师端（`role-switch` 页，`teacherIdentities` 6 类）
- **依据**：
  - 共享底稿第 5 节 API 契约基线（"当前角色 `currentRoleCode` + `activeContextId`；数据范围 `dataScope`"）
  - `miniapp/.../config/roles.config.js`（`teacherIdentities` 6 类）、`pages/teacher/role-switch`
  - `frontend/src/modules/workflow/context/permission.context.js`
  - 共享底稿第 4 节安全基线（`AUDIT_EVENT_TYPE.PERMISSION_CHANGE`）
- **当前阶段声明**：切换机制当前为前端 mock 状态管理（如 Vuex/Pinia 或本地状态），尚未接入真实后端会话/上下文服务；后端接入后，角色切换应转化为对后端"切换当前上下文"接口的真实调用，并由后端重新签发/更新会话上下文，而非纯前端状态切换。
- **生成日期**：2026-07-04

## 一、PC 端角色切换机制

### 1.1 核心概念

| 概念 | 说明 |
|---|---|
| `currentRoleCode` | 当前登录账号正在使用的角色码（如一个账号同时拥有 `COLLEGE_ADMIN` 与 `TEACHER` 两个角色时，需选择以哪个角色身份操作系统） |
| `activeContextId` | 当前生效的上下文标识（如具体某个学院 ID、某个班级 ID），用于同一角色码下可能存在的"多上下文"场景（如一个学院管理员账号被授权管理两个学院时，需选择当前在哪个学院上下文下操作） |
| `dataScope` | 由后端根据 `currentRoleCode` + `activeContextId` 解析出的数据范围，前端不可自行指定，仅展示 |

### 1.2 切换触发场景

- 同一账号被授予多个角色码（如既是"二级学院管理员"又兼"指导教师"）时，登录后或在顶部导航处提供角色切换入口。
- 同一角色码下管理多个上下文对象（如兼管两个学院）时，需切换 `activeContextId`。

### 1.3 切换后的联动效果

| 联动项 | 切换前后的变化 |
|---|---|
| 可见菜单/模块 | 依据新 `currentRoleCode` 对应的 `ROLE_MODULE_ALLOW` 重新计算，见 `02-PC端权限矩阵.md` |
| 按钮权限 | 依据新角色在 `workflow.mock.js roles[]` 中绑定的权限点重新计算 |
| 数据范围 `dataScope` | 依据新 `currentRoleCode` + `activeContextId` 重新解析（如从"学院A的 COLLEGE 范围"切换为"学院B的 COLLEGE 范围"） |
| 工作台首页 | 跳转/刷新至新角色对应的默认首页（`permissionKey` 对应的模块首页，见共享底稿第 1 节"首页 permissionKey"列） |
| 待办任务 | 待办列表按新角色的 `workflow.task.view` 权限范围重新拉取 |

### 1.4 是否需要重新鉴权/刷新上下文

- **需要**。角色切换属于安全敏感操作，切换后应：
  1. 前端清空当前已缓存的角色相关状态（菜单、按钮权限、数据范围、待办列表等），禁止沿用旧角色的缓存数据渲染新角色页面。
  2. 向后端发起"切换上下文"请求（对应接口路径待后端确认，推测应归属 `/api/v1/authz/*` 权限与身份底座域），由后端校验该账号是否确实拥有目标角色码/上下文，并返回新的角色权限与数据范围快照。
  3. 前端拿到后端返回结果后才允许渲染新角色的界面，**不能仅凭前端本地切换即认为鉴权通过**（否则等同于前端可任意伪造角色）。
- 是否需要重新登录（重新签发 token）：（待后端确认）。如角色切换不改变账号本身的登录态，可只刷新"上下文"而不强制重新登录；但若涉及跨租户切换（理论上仅平台运营可能涉及），出于安全考虑建议强制重新鉴权，具体策略待后端设计确认。

### 1.5 平台运营与学校业务隔离

- `PLATFORM_OPERATOR` 角色在 `ROLE_MODULE_ALLOW` 中**仅允许访问 `PLATFORM` 模块**，不与任何学校业务模块（`STUDENT`/`ACADEMIC`/`INTERNSHIP` 等）共享菜单或数据范围。
- 平台运营账号**不应支持切换为学校业务角色**（如 `SCHOOL_ADMIN`/`TEACHER` 等）；若确有"平台运营人员临时以某学校身份登录排查问题"的运维需求，应通过独立的"模拟登录/影子会话"机制实现，并强制留痕审计，而非通过本节的"角色切换"机制实现（该类特殊机制当前底稿未提及，待后端确认是否规划）。
- 数据范围隔离：`ALL`（全平台）范围下平台运营"不看学生业务明细"，仅能看审计、租户、模块授权类数据，这是隔离设计的核心体现（见共享底稿第 3 节角色 mock 说明）。

## 二、miniapp 教师多身份切换机制

### 2.1 背景

同一教师工号（如底稿示例教师"张明远" T20190087）可能同时承担多种教学管理职责（如既是班主任又兼实习指导教师），miniapp 通过 `teacherIdentities`（6 类：`COUNSELOR`/`MENTOR`/`INTERN_MENTOR`/`EMPLOYMENT`/`ACADEMIC`/`COLLEGE_ADMIN`）支持在同一账号下切换当前生效身份。

### 2.2 切换入口与流程

| 步骤 | 说明 |
|---|---|
| 1. 入口 | 教师端 `role-switch` 页面（教师端 11 页之一），通常从"我的"（`me`）页或首次登录后的身份选择弹窗进入 |
| 2. 展示 | 列出该教师工号绑定的全部身份（从其 6 类教师身份中取实际绑定的子集，具体某教师绑定了几类身份以 mock 数据 `mock/teacher/*` 为准，本文档不假设全部教师都绑定全部 6 类） |
| 3. 选择 | 教师选择其中一个身份作为"当前生效身份” |
| 4. 生效 | 切换后，教师端页面（`workbench`/`todos`/`risk-students` 等）按新身份的 `permissionActions` 与数据范围重新渲染，详见 `03-miniapp权限矩阵.md` |

### 2.3 切换后的联动效果

| 联动项 | 变化 |
|---|---|
| 数据范围 | 如从"辅导员身份（`CLASS` 本班级）"切换为"实习指导教师身份（`ASSIGNED`/`INTERNS` 被指导实习生）"，可见学生名单随之改变 |
| 可见页面 | 如切到"指导教师(毕设)"身份后，`graduation-guide` 页可见并可操作，而 `internship-review`、`employment-follow` 等其他身份专属页不可见 |
| 按钮键 | `permissionActions` 按钮键集合完全替换为新身份对应的按钮键（见 `03-miniapp权限矩阵.md` 第四节汇总表） |
| workbench 首页汇总 | 待办/风险学生/审批等汇总卡片按新身份的数据范围重新拉取 |

### 2.4 是否需要重新鉴权/刷新上下文

- **需要刷新上下文，不需要重新登录**（教师账号登录态不变，仅切换"当前生效身份"这一会话内状态）。
- 切换请求应发往后端身份切换接口（推测归属 `/api/v1/authz/*` 或 `/api/v1/teacher-mobile/*`，具体路径待后端确认），由后端校验该教师工号确实绑定目标身份后返回新的权限/数据范围快照，前端据此刷新页面，不能仅凭本地状态切换。
- 切换后应强制刷新（而非增量合并）本地缓存的任务列表、学生列表等数据，避免"新身份页面残留旧身份数据"的展示错误或潜在越权展示风险。

## 四、PC 端与 miniapp 切换机制对比小结

| 对比项 | PC 端 | miniapp 教师端 |
|---|---|---|
| 切换对象 | 角色码 `currentRoleCode` + 上下文 `activeContextId` | 教师身份（`teacherIdentities` 子集） |
| 切换入口 | 顶部导航/账号菜单（具体交互位置待前端 UI 确认） | 独立页面 `role-switch` |
| 是否跨角色码 | 是（如从 `COLLEGE_ADMIN` 切到 `TEACHER`） | 否，均在同一套"教师"角色码体系下切换不同教师身份子类型（本质是数据范围与业务职责的切换，而非题目 11 类角色间的切换） |
| 平台运营隔离 | 强隔离，不可切入学校业务角色 | 不适用（miniapp 无平台运营角色） |
| 是否需要后端重新鉴权 | 需要（刷新上下文，是否强制重新登录待后端确认） | 需要（刷新上下文，不需要重新登录） |
| 审计事件 | `PERMISSION_CHANGE` | `PERMISSION_CHANGE` |
