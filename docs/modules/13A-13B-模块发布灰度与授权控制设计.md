# 13A/13B 模块发布灰度与授权控制设计

> 版本：V1.0（2026-07-05）
> 定位：定义 studentAffairs（13A 学工中心）/ academicAffairs（13B 教务中心）两个新模块在租户维度的**模块生命周期 8 态**、状态机、六端表现与授权链路。原则：**复用现有授权/只读/开关基建，只补"模块级状态与灰度"这一层缺口，不新建管理端**。

## 二、模块生命周期 8 态定义

模块码（P0 登记，对齐证据报告 P0-4）：`STUDENT_AFFAIRS`、`ACADEMIC_AFFAIRS`（前端 moduleCode 与 authz /modules 同名；features 布尔键 `studentAffairs`/`academicAffairs` 作为总闸联动，见 §4.4）。

| # | 状态码 | 中文 | 语义 | 与现有枚举映射 |
|---|---|---|---|---|
| S1 | UNAUTHORIZED | 未授权 | 租户未购买/未开通该模块，无任何数据 | （新增；MOCK_MODULES 无此态=列表中缺行，本设计显式化为状态行） |
| S2 | GRANTED_DISABLED | 已授权未启用 | 合同已含/平台已授权，学校尚未择期启用；可做初始化配置（参数、scope、种子）但业务不可用 | 新增 |
| S3 | GRAY | 灰度中 | 仅灰度名单内角色/用户可见可用，其余用户视同未启用 | 新增（灰度名单见 §4.3） |
| S4 | TRIAL_RUN | 试运行 | 全员可用，页头挂"试运行"标识，允许平台/学校快速回退到 S2；数据为真实数据 | 对应 MOCK_MODULES 的 TRIAL 语义收编 |
| S5 | ACTIVE | 正式启用 | 全员正常使用 | ACTIVE（既有） |
| S6 | SUSPENDED | 停用 | 平台或学校主动关停（违约/事故/学期结束），读写均不可，菜单按策略处理，数据保留 | SUSPENDED（既有枚举，authz.py 第 150 行已过滤） |
| S7 | READONLY | 只读 | 模块可看不可写（结账期封账、争议冻结、关闭前过渡） | 新增（EXPIRED_READONLY 的"非到期"泛化） |
| S8 | EXPIRED | 到期 | 授权期届满，自动转只读表现（等价 S7 的到期特例），续费回 S5 | EXPIRED_READONLY（既有）+ EXPIRING（到期前 30 天由计算得出的**展示标记**，不是独立状态） |

**状态判定优先级**（一次请求内的判定序）：租户级 disabled/expired（中间件既有逻辑）> 模块 EXPIRED（expireAt 过期自动折算）> 模块显式状态 > features 布尔总闸（false 视同 SUSPENDED）。

## 四、存储与判定链设计（先核实、后裁定）

### 4.1 存储裁定

**核实结论（§一#8）：库内无模块授权表，唯一现成载体是 `t_platform_config` KV。** 两方案对比：

| 方案 | 优点 | 缺点 |
|---|---|---|
| A：复用 t_platform_config，新增 `config_type="MODULE_GRANT"`，`config_key=模块码`，config_json 存状态体 | 零新表零迁移；三级合并/审计/平台端 CRUD 全复用；与 FEATURES/RULES 同一管理心智 | 灰度名单若按"用户级、千人级"存 JSON 会膨胀；无法按名单成员建索引 |
| B：新建 t_platform_module_grant（tenant_id+module_code+status+expire_at+gray_json，控制面表） | 名单可索引、可按模块出报表 | 新表+迁移+新 CRUD；V1 只有 2 个模块 × 数十租户，收益不成立 |

**裁定：V1 用方案 A；P2 若灰度名单需要"用户级白名单 > 200 人"或模块数 > 10，再平迁方案 B（KV → 表的迁移脚本一次成型，config_json 结构即表结构）。**

### 4.2 MODULE_GRANT 载荷结构（config_json）

```json
{
  "moduleCode": "STUDENT_AFFAIRS",
  "status": "GRAY",                  // S1–S7 显式态；S8 由 expireAt 折算，不落库
  "expireAt": "2027-08-31T00:00:00+08:00",
  "grayRoles": ["COUNSELOR", "SCHOOL_ADMIN"],   // 灰度：按角色码
  "grayUserIds": ["db-1024"],                    // 灰度：按用户（少量补充）
  "grayCollegeCodes": [],                        // 灰度：按学院（可选维度）
  "trialRunLabel": true,
  "reason": "",                       // 停用/只读原因（≥5 字）
  "changedBy": "platform:op01",
  "changedAt": "2026-07-05T10:00:00+08:00"
}
```

- 行不存在 = S1 未授权（显式化的"缺行语义"）。
- 既有六域模块（INTERNSHIP 等）V1 不迁入 MODULE_GRANT，仍走 features 布尔——**只有 13A/13B 两个新模块走 8 态**，避免波及存量（证据报告 ⑤"增量可回滚"）。

### 4.3 灰度名单判定

`module_state(tenant_id, module_code, user) -> (state, effective_for_user)`（platform_service 新函数）：

1. 读 MODULE_GRANT（`get_config_json(tenant_id, "MODULE_GRANT", module_code)`，safe 化：异常→按 features 布尔降级判定，features 也异常→S1 拒绝开放（**与 feature_enabled 默认放行相反**：新模块故障时收紧而非放行，因为未授权租户放行=免费开放事故；此差异需在代码注释显式声明）。
2. expireAt < now → S8。
3. status=GRAY 时：user 的 currentRoleCode ∈ grayRoles，或 userId ∈ grayUserIds，或所属学院 ∈ grayCollegeCodes → 视同 S4；否则视同 S2。
4. 返回态供守卫与 /modules 出口共用——**判定函数全系统唯一**，禁止前端自行组合判断。

### 4.4 后端守卫（API 强校验，前端隐藏不作数）

- 新增 FastAPI 依赖 `require_module("STUDENT_AFFAIRS", write=True/False)`，挂在 `/api/v1/student-affairs/*`、`/api/v1/academic-affairs/*`、`/api/v1/mobile/student-affairs/*`、`/api/v1/mobile/teacher/student-affairs/*` 等全部新 router 上（写法对齐 `require_platform_super_admin`，拒绝即审计——platform.py 第 27–36 行范式；证据报告 R4 的 Opus 注意事项原文要求）。
- 与 features 布尔联动：`feature_enabled(tid, "studentAffairs")=false` 时视同 S6（平台把布尔总闸关掉即全模块急停）；FEATURE_KEYS 与五套餐 features 矩阵在 P0 登记两个新键（证据报告 P0-4）。
- 租户级到期/demo 只读中间件在守卫**之前**已拦截（中间件先行），模块守卫处理的是"租户正常、模块异常"的剩余矩阵。

## 七、到期/停用后的数据处理（保留可读/导出/不可写）

1. **数据永不因模块状态删除**：S6/S7/S8/T11 撤销授权均不删行；`is_deleted` 语义保留给业务删除，模块状态与数据生命周期解耦。
2. **S7/S8 可读可导出**：GET 与既有导出 domain（affairs-*/academic-* 系列，冻结表 §7）可用，导出仍走水印+t_export_task 留痕管线；写一律 403。
3. **S6 停用**：业务读写全 403，但学校管理员可在「联系开通」页发起**归档导出申请**（平台侧执行既有 export 管线代导，审计留痕）——防止"停用=数据扣押"的争议。
4. **T11 撤销授权（S1）**：设 90 天保留期（平台 settings 键 moduleRevokeRetentionDays，默认 90），期内平台可代导全量归档包（sha256 落 t_export_task）；期满数据仍保留（SaaS 合规删除另走租户注销流程，不在本设计范围）。
5. **历史痕迹不回收**：已写入 t_student_stage_event 的 360 事件、t_unified_todo/message 的历史待办消息、t_security_audit_log 审计**保持可见**（属学生档案与合规范畴，不随模块状态隐藏）；仅"发起新业务"的入口关闭。在途 workflow 任务在 S6/S7/S8 下冻结（审批按钮置灰，任务不超时催办）。

## 八、与 adminMenu ROLE_MODULE_ALLOW、miniapp 入口的联动

### 8.1 PC 管理端（adminMenu.js）

1. 新增菜单分组：学工中心（moduleCode=`STUDENT_AFFAIRS`，path /admin/student-affairs/*）、教务中心（moduleCode=`ACADEMIC_AFFAIRS`，path /admin/academic-affairs/*）——叶子结构对齐既有 `{ key, label, path, moduleCode, permissionKey }`。
2. `ROLE_MODULE_ALLOW`（第 98–104 行）扩展：SCHOOL_ADMIN 追加两码；COUNSELOR 追加 `STUDENT_AFFAIRS`；ACADEMIC_STAFF 追加 `ACADEMIC_AFFAIRS`；AUDITOR 不加（审计走 SYSTEM 日志页）。
3. `canSeeLeaf` 增加第四道判断：从 `GET /authz/modules` 结果取该 moduleCode 状态，按 §五/§六矩阵决定 隐藏/置灰/徽标——即**角色白名单（谁的职责）× 模块授权态（租户买没买）二维裁剪**，两个维度各自保持单一职责。
4. 前端在登录后与切换身份后各拉一次 /authz/modules（对齐 1.8 activate 返回 menusChanged=true 须重拉 1.9/1.10/1.11 的既有约定，authz.py 第 168 行）。

### 8.2 authz /modules 出口真实化（P0-4 落地）

- `/authz/modules` 从返回 `MOCK_MODULES` 改为：既有模块仍按 mock 兼容返回（存量不动），**新增两行由 `platform_service.module_state` 真实计算**（含 status、expireAt、grayHit(bool)、readonly(bool)）。响应结构不变（契约 1.12 字段一致），仅数据源替换——满足"契约字段与真实版一致，接库时仅替换 services 层"的文件头承诺（authz.py 第 5 行）。
- `/me/menus` 的 readonly 打标逻辑（第 188–193 行）自动覆盖 S7/S8。

### 8.3 miniapp 入口联动

1. **学生端**：首页入口清单由服务端聚合下发（不在前端写死）——扩展既有 `GET /mobile/me/portal-config` 风格：登录聚合响应增加 `modules: {studentAffairs: {state, entries}, academicAffairs: {...}}`；S1/S2/S6 不下发 entries，S3 按名单（学生默认不进灰度），S7/S8 下发但 readonly=true。新页面先登记 `miniapp/src/pages.json` 再发深链（R11 红线）。
2. **教师端**：工作台模块卡与待办分类同源过滤——`/mobile/teacher/todos` 按模块状态过滤 source_module ∈ {student-affairs, academic-affairs} 的待办展示（S6 隐藏、S7/S8 可见但处理按钮只读）；审批深链（pages/teacher/approval）打开时后端 task 详情接口再做一次模块守卫，防缓存穿透。
3. **消息深链兜底**：模块转 S6 后，历史消息里的深链点击进入通用「模块已停用」态页（MobileGlobalState error 分支复用），不白屏不 500。

SOP 纪律：每次放量都是 PUT modules 一次显式操作（有审计），禁止"改名单不留痕"；灰度期间产生的是真实数据，回退不清数据（§七）；demo-school 永不作为灰度对象（只读锁），灰度演练用 sandbox-school。

## 九B、风险与回滚预案

| 风险 | 场景 | 预案 |
|---|---|---|
| 状态判定函数故障 | module_state 抛异常 | §4.3 已定：降级读 features 布尔；仍异常→拒绝开放（收紧不放行）+错误日志告警；平台端有 features 布尔总闸可手工兜底 |
| 灰度名单误配（放给全员） | grayRoles 误填空数组被拒（422），但误填全角色 | PUT 时名单>N（默认 5 角色）二次确认；审计可查、T2 重配即时收回 |
| 到期误判（时钟/时区） | expireAt 折算错误批量只读 | expireAt 统一带时区存储；到期前 30 天 EXPIRING 展示标记提前暴露；误判时平台 T10 延期即时恢复（无缓存） |
| 菜单与后端不一致 | 前端缓存旧状态 | 5.1 缓存策略：403 模块类 bizCode 强制重拉；权威永远在守卫，最坏情况是"看得见点不动"，无越权 |
| 旧端点被绕过 | 有人直调既有六域端点操作 13A 数据 | 13A/13B 新表只挂新 router（全部有守卫）；复用表（t_cs_leave 等）的既有端点行为不变（旧业务），新增列仅新链路写——回归快照保证（冻结表 ⑤） |

## 十、验收用例（8 态完成度自检）

1. S1：未授权租户管理员登录→菜单置灰+联系开通页；教师/学生不可见；直调 /api/v1/student-affairs/dashboard → 403 MODULE_NOT_AUTHORIZED+审计。
2. T1→S2：平台开通后管理员可进配置页做参数初始化，业务列表页仍 403 MODULE_NOT_ENABLED。
3. T2→S3：灰度名单=COUNSELOR，辅导员账号 PC/移动端全可用，任课教师账号菜单隐藏且 API 403；名单外教师直调写接口 403+审计。
4. T3→S4：全员可用+试运行徽标；T5 回退 S2 后已建请假单可由平台导出、业务端不可见入口、深链 403。
5. T4→S5：正式态；T7→S7 后学生「新增申请」置灰、GET 正常、导出可用、POST 403 MODULE_READONLY。
6. T9→S8：把 expireAt 改为昨日（平台端 tenant expire 或模块级 expireAt），六端出现到期徽标，写 403 MODULE_EXPIRED_READONLY，续费（T10）后即刻恢复 S5（无缓存滞后）。
7. T6→S6：停用后教师移动端待办分类消失，历史消息深链进占位页；T8 恢复后待办重现且数量与停用前一致（数据零丢失）。
8. 急停演练：平台关 features 布尔 studentAffairs → 全模块视同 S6；重开恢复。demo-school 上执行任何模块状态 PUT → 被平台端豁免前缀放行（/api/v1/platform 不受 demo 锁限制，context.py 第 84–86 行），但 demo 租户业务写仍 403（双锁并存验证）。

## 十A、租户状态 × 模块状态组合判定表（最终表现速查）

> 租户状态来自 `platform_service.tenant_status`（trial/active/expired/disabled，platform_service.py 第 272–285 行）；判定优先级见 §二末行。取"更严者生效"。

|---|---|---|---|---|---|
| active（正常） | 正常读写 | 读√写403(MODULE_READONLY) | 读√写403(MODULE_EXPIRED_READONLY) | 读写403(MODULE_SUSPENDED) | 403(NOT_AUTHORIZED/NOT_ENABLED) |
| trial（试用中） | 正常读写（试用套餐 features 上限内） | 同上行 | 同上行 | 同上行 | 同上行 |
| expired（租户到期） | **读√写403**（中间件先拦，MODULE_EXPIRED_READONLY，模块守卫不再参与写判定） | 读√写403 | 读√写403 | 读写403（模块停用更严，读也不放） | 403 |
