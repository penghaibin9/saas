# 00-系统管理中心-权限角色模块授权与权责边界设计

> 文档性质：**系统级权限与权责边界设计文档**，用于指导「系统管理中心 / 平台运营端 / 学校平台管理员 / 各业务中心（学工 13A、教务 13B、毕业设计、岗位实习等）」的权限、角色、模块授权与权责边界设计。
> 定位：本文件是**全平台权限的顶层约束**，各业务中心的权限点（`studentAffairs.*`、`academicAffairs.*` 等）与数据范围（`t_teacher_student_scope` + `resolve_teacher_scope` 系函数）设计必须遵守本文件；本文件不改代码、不改前端页面、不改导航、不改数据库，只定义规则与边界。
> 复用既有事实（不另起炉灶）：控制面配置存 `t_platform_config`（KV，`(tenant_id, config_type, config_key)` 唯一）+ `platform_defaults.DEFAULT_RULES` 默认层 + `safe_rule` 兜底；平台超级管理员 `PLATFORM_SUPER_ADMIN`；数据范围机制 `t_teacher_student_scope` + `resolve_teacher_scope`（各中心封装 `getStudentAffairsScope` / `getAcademicScope`）；审计 `t_security_audit_log`（`record()`）与域级 `audit_trail`；租户隔离共库行级。
> 口径说明：历史文档中的 `V1/P2/P3/后置/只预留` 字样，按「高频核心底座 + 商业化能力池 + 补强包 + 授权启用 + 人工替代流程 + 算法接口预留」口径理解，不在原文批量替换。

---

## 1. 文档定位

本文件回答一个核心问题：**在一个 SaaS 多租户的高校学生全生命周期平台里，谁能做什么、谁不能做什么、谁给谁授权、授权到什么边界、越权如何被拦截与追责。**

它用于指导：

- **系统管理中心**（学校平台管理员使用）：本校用户、角色、菜单、按钮、数据范围、流程、参数、审计的配置界面与规则。
- **平台运营端**（平台运营方使用）：租户开通、套餐、模块授权、版本、全局安全策略、运维协助的界面与规则。
- **各业务中心**（学工 / 教务 / 毕设 / 实习 / 工作台 / 数据驾驶舱等）：其权限点命名、菜单挂载、按钮控制、数据范围、审批权限、敏感数据权限、审计责任必须落在本文件的框架内。

**本文件不定义具体业务流程**（那是各业务中心设计文档的职责），只定义**权限与权责的骨架与红线**。凡本文件与某业务文档冲突且涉及权限/权责边界的，**以本文件为准**。

## 2. 权限体系总模型

平台权限由以下 10 个要素组成，彼此**分层、正交、独立控制**，不得混为一谈：

| 要素 | 含义 | 归属层 |
|---|---|---|
| 用户账号 | 一个自然人的登录主体（工号/学号/手机号），归属唯一租户 | 学校租户内 |
| 角色 | 一组权限的集合（菜单+按钮+数据范围+审批+敏感权限的模板） | 学校租户内（部分平台角色跨租户） |
| 当前激活角色 | 用户本次会话选中的那一个角色（多角色用户同一时刻只激活一个） | 会话级 |
| 菜单权限 | 能不能**看到并进入**某个功能页 | 角色级 |
| 按钮权限 | 在页面内能不能**点某个动作**（新增/编辑/导出/打印…） | 角色级 |
| 数据范围 | 能看到/能操作**哪些学生、哪些班级、哪些学院**的数据 | 角色级（独立于菜单） |
| 模块授权 | 本校**是否购买/被授权启用**某个业务中心/能力（第一层，平台方控制） | 租户级 |
| 审批权限 | 能不能在某审批节点做**通过/退回/驳回**（属流程节点授权，非按钮） | 角色×节点级 |
| 敏感数据权限 | 能不能查看**完整手机号/身份证/家庭经济/心理明细/处分详情** | 角色级（强控制+审计） |
| 审计日志 | 谁在何时对谁做了什么敏感操作的不可篡改记录 | 全局强制 |

### 2.1 要素间关系（自上而下的授权链）

```
平台运营方
   │ 第一层授权：给学校租户授权可用模块（模块授权）
   ▼
学校租户（已授权模块集合 = 学校能力上限）
   │ 学校平台管理员在【已授权模块】内配置角色
   ▼
角色 = 菜单权限 + 按钮权限 + 数据范围 + 审批权限 + 敏感数据权限（均 ≤ 学校授权 ≤ 创建者自身权限）
   │ 分配给
   ▼
用户账号（可拥有多个角色）
   │ 登录后选择
   ▼
当前激活角色 → 决定本次会话的菜单/待办/按钮/数据范围/统计口径/移动端入口
   │ 每一次敏感操作
   ▼
审计日志（不可篡改，可追溯到人）
```

### 2.2 三条硬规则

- **一个用户可以拥有多个角色**（如一位教师既是辅导员、又是毕设导师、又是课程教师）。
- **同一时间只激活一个当前角色**：用户通过顶部「角色切换器」选择当前角色；未选择时按默认角色。
- **切换角色后，菜单、待办、按钮、数据范围、统计口径、移动端入口必须全部随之变化**——不是前端隐藏，而是后端按当前激活角色重新解析权限上下文并返回。

### 2.3 权限判定的最终裁定在后端

任何一次请求，后端按「**当前激活角色 → 权限点校验（能不能）→ 数据范围校验（看多少）→ 敏感权限校验（能不能看明细）→ 审批节点校验（能不能审）**」四层依次裁定；前端只做展示与体验优化，**前端隐藏不等于有权限**，后端必须独立校验（见第 17 章）。

## 3. 两层模块授权模型

**模块授权必须分两层，缺一不可。** 第一层决定「学校能不能用」，第二层决定「本校谁能用、用到什么程度」。

### 3.1 第一层：平台运营方 → 学校租户模块授权

平台运营方按套餐/合同给每个学校租户授权可用模块与能力。存储于 `t_platform_config`（`config_type=MODULE_GRANT`），带**授权到期时间**。第一层授权对象清单：

| 模块/能力 | 授权键（建议） | 说明 |
|---|---|---|
| 学工中心（13A） | `module.studentAffairs.enabled` | 学工全业务 |
| 教务中心（13B） | `module.academicAffairs.enabled` | 教务全业务 |
| 毕业设计中心 | `module.graduationDesign.enabled` | 毕设全流程 |
| 岗位实习中心 | `module.internship.enabled` | 实习全流程 |
| 工作台 | `module.workbench.enabled` | 多角色工作台 |
| 系统管理 | `module.systemAdmin.enabled` | 系统管理中心（默认随租户开通） |
| 数据驾驶舱 | `module.dashboard.enabled` | 数据可视化 |
| AI 能力 | `module.ai.enabled` | AI 风险预警/智能建议等（算法接口预留，授权启用） |
| 移动端能力 | `module.mobile.enabled` | 小程序/H5 入口 |
| 导入导出能力 | `module.importExport.enabled` | 批量导入导出管线 |
| 短信通知能力 | `module.smsNotify.enabled` | 短信渠道（需渠道配置，未配置强制置灰） |
| 高级报表能力 | `module.advancedReport.enabled` | 自定义/高级统计报表 |

> 说明：**第一层授权是学校能力上限。** 授权到期后模块自动进入「未授权」状态（菜单不显示、路由不可达、接口 403、卡片不显示——见第 12 章）。子能力开关（如 AI 风险预警是学工中心内的子能力）默认关闭且防误开，属第一层的细粒度延伸。

### 3.2 第二层：学校平台管理员 → 本校角色授权

学校平台管理员在**第一层已授权的模块范围内**，给本校角色分配以下能力（存于本校租户配置，不跨租户）：

- 菜单能不能看（菜单权限）
- 按钮能不能点（按钮权限）
- 数据能看到哪里（数据范围）
- 能不能审批（审批节点授权）
- 能不能导出（导出权限，敏感导出强控制）
- 能不能打印（打印权限）
- 能不能查看敏感信息（敏感数据权限）
- 能不能配置流程（流程配置权限，区别于业务审批权限）
- 能不能管理下级角色（角色管理权限，且不得超过自身）

### 3.3 两层之间的三条约束（越权拦截红线）

1. **学校管理员不能启用平台未授权模块**：第二层配置的任何权限点，若其所属模块第一层未授权，配置无效且被拒绝（保存时校验 + 运行时二次校验）。
2. **角色不能获得超过学校授权范围的功能**：角色权限集 ⊆ 学校已授权模块的权限全集。
3. **角色不能获得超过创建者自身权限的能力**：管理员创建/修改角色时，可授予的权限 ⊆ 自身当前拥有的权限（**不能把自己没有的权限授予别人**，防止提权）。

> 三条约束在**保存配置时**与**运行时鉴权时**双重校验，任何一处发现越界即拒绝并写审计。

## 4. 平台运营方权责

平台运营方（`PLATFORM_SUPER_ADMIN` / 平台运营管理员 / 平台运维支持）是**基础设施与租户管理方**，不是学校业务的参与方。

### 4.1 平台运营方能做

- 租户开通（新建学校租户、分配租户 ID、初始化根管理员）
- 套餐配置（按套餐决定第一层模块授权组合）
- 模块授权（第一层：给学校授权/取消授权模块与能力）
- 授权到期控制（设置/延期/回收授权有效期）
- 学校初始化（下发默认角色模板、默认菜单模板、默认流程模板、默认参数）
- 默认角色模板 / 默认菜单模板 / 默认流程模板（平台侧维护，学校复制后本地化）
- 全局安全策略（密码策略、登录策略、会话超时、IP 策略、全局审计开关的**开启**——注意只能开不能关关键审计）
- 版本升级（平台统一升级，灰度发布）
- 系统运维（部署、监控、容量、备份恢复）
- 异常排查（在**授权前提下**协助定位问题）
- 授权支持（响应学校运维协助工单）

### 4.2 平台运营方不能做

- ❌ 随便查看学校敏感学生数据（手机号/身份证/家庭经济/心理/处分明细）
- ❌ 绕过学校流程审批业务（不能替学校点通过/驳回）
- ❌ 替学校修改业务终态数据（已发布成绩、已生效处分、已归档单据等）
- ❌ 删除学校审计日志（审计不可删、不可改）
- ❌ 绕过授权启用模块（不能在数据库直接改开关绕过授权流程）
- ❌ 跨租户泄露数据（任何跨租户读取被隔离层拦截并审计）

### 4.3 运维协助的强约束（平台方进入学校数据的唯一合法通道）

平台方如需查看/操作学校业务数据以协助排查，必须**同时满足**以下全部条件，否则系统拒绝：

| 约束 | 要求 |
|---|---|
| 学校授权 | 学校平台管理员在系统内发起/批准「运维协助授权」（授权单） |
| 操作原因 | 必填工单原因（≥ 一定字数），关联工单号 |
| 时间范围 | 授权有临时有效期（如 24/72 小时），到期自动回收 |
| 最小权限 | 仅授予排查所需的最小范围（指定学校/指定模块/只读优先） |
| 全程审计 | 平台方在授权期内的每一次读取/操作全部写 `t_security_audit_log`，学校可查 |
| 到期回收 | 授权到期或工单关闭后权限自动失效，需重新授权 |

> 运维协助默认**只读优先**；涉及敏感明细仍需二次确认+填原因+水印；平台方**永远不能**删改学校审计日志。

## 5. 学校平台管理员权责

学校平台管理员（学校系统管理员）是**本校权限的最高配置者**，但其能力被第一层模块授权和自身权限双重封顶。

### 5.1 学校平台管理员能做

- 管理本校用户（建号、停用、重置、绑定角色）
- 管理本校角色（启用平台角色模板、维护本校角色）
- 新增自定义角色（在授权与自身权限范围内，见第 6 章）
- 配置本校菜单权限（角色能看哪些菜单）
- 配置按钮权限（角色能点哪些按钮）
- 配置数据范围（角色/用户看哪些数据）
- 配置组织结构（学院/专业/年级/班级）
- 配置学校参数（走 `t_platform_config` 学校可改层 + `safe_rule` 兜底）
- 配置审批流程（在流程配置权限内）
- 配置通知模板
- 查看本校审计日志
- 停用离职账号
- 回收权限

### 5.2 学校平台管理员不能做

- ❌ 启用未购买/未授权模块（第一层未授权则第二层配置无效）
- ❌ 跨租户查看数据（只能管本校租户）
- ❌ 删除审计日志（审计不可删）
- ❌ 关闭关键审计（敏感操作审计为强制项，不可关闭）
- ❌ 越权分配权限（不能把自己没有的权限授予别人）
- ❌ 绕过业务状态机（不能直接把单据改到非法状态）
- ❌ 直接修改数据库（一切经应用层，禁止绕过应用直连库）
- ❌ 把敏感权限批量开放给普通角色（敏感权限需逐项二次确认，不能批量勾选下发）

> 学校管理员是「配置者」不是「业务终态修改者」：他能配谁能审批，但不能替业务角色审批；他能配数据范围，但不能绕过范围看别校数据。

## 6. 学校自定义角色规则

**学校可以新增自定义角色**（这是 SaaS 多租户的必要能力，学校组织结构千差万别）。但自定义角色受严格约束：

### 6.1 自定义角色规则

- **只能在本校生效**（租户内，不跨租户，不影响平台角色）。
- **必须绑定角色类型**（见 6.2，决定其能挂哪类菜单与数据范围语义）。
- **必须绑定数据范围**（不允许「无范围」角色；默认最小范围，需显式放宽）。
- **必须从角色模板复制或从空白创建**（复制模板则继承模板权限再裁剪；空白创建则从零勾选）。
- **不能超过创建者权限**（权限集 ⊆ 创建者当前权限，防提权）。
- **不能超过学校模块授权**（权限集 ⊆ 第一层已授权模块）。
- **权限变更必须审计**（新建/改权限/改范围/停用全部写 `t_security_audit_log`）。
- **停用角色不删除历史业务记录**（角色停用后，该角色曾处理的业务单据、审批记录、责任人字段全部保留）。
- **已有业务记录保留原角色快照**（业务单据记录当时的处理人角色快照，事后改角色定义不影响历史追责——见第 17 章末条）。

### 6.2 角色类型（至少包含）

| 角色类型 | 语义 | 典型数据范围 | 可挂模块 |
|---|---|---|---|
| 管理类 | 平台/学校/学院管理 | 全校/本院 | 系统管理+按授权 |
| 学工类 | 学生事务 | 本校/本院/本班/负责学生 | 学工中心 |
| 教务类 | 教学运行 | 本校/本院/授课班级 | 教务中心 |
| 毕业设计类 | 毕设指导评阅 | 指导学生/评阅学生 | 毕业设计中心 |
| 岗位实习类 | 实习管理指导 | 指导学生/本企业学生 | 岗位实习中心 |
| 系统配置类 | 参数/流程/菜单配置 | 全校（配置面，非业务数据） | 系统管理 |
| 审计类 | 审计查看 | 全校审计（只读，不参与业务） | 审计 |
| 学生类 | 学生本人 | 仅本人 | 学生端 |
| 企业类 | 企业侧 | 本企业名下实习学生 | 实习企业端 |

> 自定义角色示例：学校新增「二级学院副书记」= 复制「学院学工负责人」模板 → 角色类型=学工类 → 数据范围=本学院 → 裁剪掉「导出全院心理明细」等敏感项。（详见第 16 章场景 1。）

## 7. 默认角色模板

平台侧维护一套默认角色模板，学校初始化时下发；学校可**复制为自定义角色**再本地化裁剪。每个角色写：角色定位 / 默认可见模块 / 默认数据范围 / 默认可用按钮 / 默认不可做事项 / 是否可被学校复制为自定义角色。**平台类角色不可被学校复制**（跨租户，属平台方专有）。

### 7.1 平台侧角色（跨租户，学校不可复制）

| 角色 | 定位 | 默认可见模块 | 默认数据范围 | 默认可用按钮 | 默认不可做 | 可被学校复制 |
|---|---|---|---|---|---|---|
| 平台超级管理员 | 平台最高权限（`PLATFORM_SUPER_ADMIN`） | 平台运营端全部 | 全平台（配置面，非业务明细） | 租户/套餐/模块授权/全局策略 | 查看学校敏感业务明细、删审计、替校审批 | 否 |

## 8. 数据范围模型

**数据范围独立于菜单权限**：有菜单不等于能看到全部数据；能进「学生列表页」的角色很多，但每个角色看到的学生集合由数据范围决定。数据范围统一经 `t_teacher_student_scope` + `resolve_teacher_scope` 系函数解析，各中心封装为 `getStudentAffairsScope` / `getAcademicScope` 等，**前端不传范围参数**，后端从当前激活角色+token 上下文解析。

### 8.1 数据范围枚举（至少包含）

| 数据范围 | 含义 | 典型 scope_type |
|---|---|---|
| 全校 | 本租户全部学生/数据 | SCHOOL |
| 指定学院 | 一个或多个学院 | COLLEGE |
| 指定专业 | 一个或多个专业 | MAJOR |
| 指定班级 | 一个或多个班级 | CLASS |
| 本人负责学生 | 辅导员带的学生 | ADVISOR / COUNSELOR_CLASSES |
| 本人授课班级 | 教师授课的教学班 | TEACH_CLASS |
| 本人指导学生 | 毕设/实习指导的学生 | MENTOR_STUDENT |
| 本人审批事项 | 当前节点分派给本人的单据 | ASSIGNEE |
| 本人创建数据 | 本人发起/录入的数据 | OWNER |
| 企业名下实习学生 | 企业导师看本企业实习学生 | ENTERPRISE_STUDENT |
| 仅本人 | 学生本人 | SELF |
| 授权心理关注学生 | 心理老师授权可见学生 | PSY_STUDENT |
| 负责楼栋学生 | 宿管负责楼栋在住学生 | DORM_BUILDING |

### 8.2 举例（数据范围的实际隔离效果）

- 辅导员只能看**自己负责班级/学生**（跨班访问 403002 + 审计）。
- 学院教务员只能看**本学院**（跨院访问 403002 + 审计）。
- 专业课/公共课/实训课教师只能看**本人授课教学班**（非全专业）。
- 实习指导老师只能看**自己指导学生**；毕设导师只能看**自己指导学生**。
- 企业导师只能看**本企业名下实习学生**（不看学生学工/学业敏感数据）。
- 学生只能看**本人数据**（`SELF`，心理原始明细不下发学生端）。
- 心理老师只能看**授权心理关注学生**的心理明细（`PSY_STUDENT`），未授权学生整段不返回。

### 8.3 数据范围与角色的组合

同一菜单权限 + 不同数据范围 = 不同的可见集合。数据范围可**叠加**（多学院/多班级）也可**收窄**（同一角色被限到某几个班）。数据范围变更属敏感操作，**必须审计**（见第 10 章）。

## 8A. 业务关系授权模型

**权限不能只靠角色名和行政数据范围判断，还必须结合真实业务关系。** 这是本平台权限体系的核心：一位教师「是辅导员」只是身份，「负责哪个班」才决定他能看谁；「是毕设导师」只是身份，「导师分配关系里带哪 12 个学生」才决定他能看哪些论文。

### 8A.1 六要素权限判定模型

系统权限判断采用**六要素合取**（全部通过才放行）：

```
系统内置角色模板  +  学校自定义角色  +  数据范围  +  业务关系授权  +  按钮权限  +  敏感字段权限
```

各要素职责分层，**互不替代**：

1. **角色**决定「这个人是什么身份」（辅导员/教师/导师…）。
2. **数据范围**决定「这个人最多能看哪个组织范围」（本院/本班/授课班…，行政上限）。
3. **业务关系**决定「这个人具体能看哪些学生、课程、事项、项目」（在行政范围内进一步按真实业务关系收敛到具体对象）。
4. **按钮权限**决定「这个人能做什么动作」（查看/审批/导出…）。
5. **敏感字段权限**决定「这个人能不能看隐私字段」（心理/困难/处分/完整号码…）。

> 关系：`角色（身份）→ 数据范围（组织上限）→ 业务关系（具体对象）→ 按钮（动作）→ 敏感字段（隐私）`。业务关系是**在数据范围之内的进一步收敛**——数据范围是「最多能看本院」，业务关系是「本院里实际只带这几个班/这几个学生」。

### 8A.2 业务关系授权定义

业务关系授权 = 用户因为与某个**学生、班级、课程、企业、项目、审批事项**存在**真实业务关系**（来自真实业务数据表，非前端角色名），才获得对应数据和操作权限。

### 8A.3 业务关系类型（逐条）

1. **辅导员关系**：辅导员绑定班级/学生（`t_teacher_student_scope` CLASS/ADVISOR）；只能看本人负责班级或学生；可处理请假、风险、谈话、家校、奖助初审等事项。
2. **班主任关系**：班主任绑定班级；可看本班学生基础信息、请假、风险摘要、班级统计；**不自动拥有心理明细、处分详情、家庭经济明细**（需再过敏感字段权限）。
3. **授课关系**：课程教师通过**教学任务/课表/教学班**获得学生名单权限；可查看本人课程学生名单；可录入/暂存/提交本人课程成绩；**不可查看无关班级成绩、不可审核自己提交的成绩、不可发布成绩**。
4. **专业负责人关系**：专业负责人绑定专业；可查看本专业培养方案、教学计划、学业风险、毕业资格预审数据；**不等于全校教务管理员**。
5. **课程负责人关系**：课程负责人绑定课程；可查看本课程下多个教学班运行情况；可维护课程大纲、考核方案、教学材料；**不自动拥有成绩发布权限**。
6. **毕设导师关系**：毕设导师通过**导师分配关系**绑定学生；只能看本人指导学生的选题、开题、中期、成果、答辩相关材料；可指导、评阅、打分；**不可查看无关导师学生材料**。
7. **评阅教师关系**：评阅教师通过**评阅分配关系**获得指定论文/成果查看与评分权限；评阅完成后保留历史责任人快照；**不自动拥有导师权限**。
8. **答辩专家/答辩秘书关系**：通过**答辩分组**获得本组学生材料、评分、记录权限；**不能查看其他答辩组无关材料**。
9. **实习指导老师关系**：指导老师通过**实习分配关系**绑定学生；只能看本人指导学生的实习单位、打卡、周报、风险、指导记录；可批阅周报、记录指导、处理异常；**不可查看其他老师指导学生**。
10. **企业导师/企业联系人关系**：企业导师通过**企业岗位或实习协议**绑定学生；只能看本企业、本岗位、本协议范围内学生；只允许查看实习相关必要字段；**不可查看学生完整学籍、心理、奖助、处分等敏感数据**。
11. **宿管老师关系**：宿管老师通过**楼栋、楼层、宿舍片区**绑定数据范围（`DORM_BUILDING`）；可处理宿舍检查、夜不归宿、公寓纪律、维修工单；**不自动拥有学生完整画像权限**。
12. **审批关系**：用户通过**审批流程节点**获得当前事项处理权限；**有审批权限不等于有全量查看权限**；审批结束后不能继续无限制操作该事项；历史审批记录保留责任人快照。
13. **创建人/责任人关系**：用户创建的记录、被分派的任务、本人负责事项，可在权限范围内查看和处理；转办、分派、关闭、重开必须留痕。

### 8A.4 业务关系授权八项要求

1. 业务关系必须来自**真实业务数据**，不允许只靠前端角色名判断。
2. 后端接口必须**校验业务关系**。
3. 前端菜单隐藏**不能替代**后端权限校验。
4. 用户同时拥有多个角色时，必须**按当前激活角色加载对应业务关系**。
5. 业务关系变更后，权限必须**同步变化**。
6. 历史业务记录必须**保留当时的责任人、角色、数据范围快照**。
7. 敏感数据即使存在业务关系，也必须**再检查敏感字段权限**。
8. 导出、查看完整手机号、查看心理/困难/处分详情**必须写审计日志**。

### 8A.5 举例：李老师的四重身份

李老师同时拥有：辅导员（负责软件 2301 班）、专业课教师（授课 Java 程序设计教学班）、毕设导师（指导 12 个毕设学生）、实习指导老师（指导 8 个实习学生）。切换当前激活角色时，业务关系随之切换：

| 切换为 | 能看 | 能做 | 不能做 |
|---|---|---|---|
| 辅导员 | 软件 2301 班学生画像、请假、风险、谈话 | 请假审批、风险处置、谈话记录 | 录入 Java 课程成绩、查看非本班学生完整画像 |
| 专业课教师 | 本人授课教学班学生名单 | 录入本人课程成绩 | 查看学生心理明细、奖助明细、处分详情 |
| 毕设导师 | 本人指导的 12 个毕设学生 | 处理开题/过程/成果/评阅相关事项 | 查看其他导师学生材料 |
| 实习指导老师 | 本人指导的 8 个实习学生 | 批阅周报、处理打卡异常、记录指导 | 查看无关实习学生 |

> 同一个自然人，因当前激活角色不同，业务关系不同 → 数据集不同、按钮不同、待办不同、敏感可见性不同。四重身份的权限**不叠加成超级权限**，而是各自独立、按激活角色隔离。

### 8A.6 业务关系授权矩阵

| 业务关系类型 | 来源数据 | 绑定对象 | 可见数据 | 可操作动作 | 不可做事项 | 叠加数据范围 | 叠加敏感字段权限 | 需审计 | 典型角色 |
|---|---|---|---|---|---|---|---|---|---|
| 辅导员关系 | `t_teacher_student_scope`(CLASS/ADVISOR) | 班级/学生 | 本班学生画像/请假/风险/谈话/家校/奖助初审 | 初审、风险处置、谈话、家校 | 跨班、看非授权心理明细、校级终审 | 是（本班） | 是（心理/困难仍需授权） | 是 | 辅导员 |
| 班主任关系 | 班主任绑定 | 班级 | 本班基础信息/请假/风险摘要/班级统计 | 查看、班级维护 | 看心理明细/处分详情/家庭经济 | 是（本班） | 是（默认不含敏感） | 是 | 班主任 |
| 授课关系 | 教学任务/课表/教学班 | 教学班/课程 | 本人课程学生名单/本人课程成绩 | 录入/暂存/提交成绩、调停课 | 看无关班级、审核自提成绩、发布成绩 | 是（授课班） | 否（不含学生隐私明细） | 是（成绩操作） | 专业课/公共课/实训课/教学班任课教师 |
| 课程负责人关系 | 课程负责人绑定 | 课程 | 本课程多教学班运行/成绩提交进度 | 维护大纲/考核方案/材料、看进度 | 审核/发布成绩、改他课 | 是（本课程跨班） | 否 | 是 | 课程负责人 |
| 专业负责人关系 | 专业负责人绑定 | 专业 | 本专业方案/计划/学业风险/毕业预审 | 参与方案/计划/预审/选题审核 | 全校教务、跨专业、改学籍终态 | 是（本专业） | 部分（预审含受限信息） | 是 | 专业负责人 |
| 毕设导师关系 | 导师分配关系 | 指导学生 | 本人指导学生选题/开题/中期/成果/答辩材料 | 指导、评阅、打分 | 看无关导师学生 | 是（指导学生） | 否（不含学工敏感） | 是 | 毕设导师 |
| 评阅教师关系 | 评阅分配关系 | 评阅论文/成果 | 指定论文/成果 | 评阅打分 | 看非评阅任务、行使导师权 | 是（评阅任务） | 否 | 是 | 评阅教师 |
| 答辩专家关系 | 答辩分组 | 本组学生 | 本组学生材料/评分/记录 | 答辩评分、记录 | 看其他答辩组材料 | 是（本组） | 否 | 是 | 答辩专家/答辩秘书 |
| 实习指导老师关系 | 实习分配关系 | 指导实习学生 | 本人指导学生实习单位/打卡/周报/风险/指导记录 | 批阅周报、记录指导、处理异常 | 看其他老师指导学生 | 是（指导学生） | 否（不含学工敏感） | 是 | 实习指导老师 |
| 企业导师关系 | 企业岗位/实习协议 | 本企业实习学生 | 本企业/岗位/协议范围内学生实习必要字段 | 考勤确认、企业评价 | 看学生完整学籍/心理/奖助/处分 | 是（企业名下） | 否（严格禁看学工学业敏感） | 是 | 企业导师/企业联系人 |
| 宿管关系 | 楼栋/楼层/片区绑定(DORM_BUILDING) | 负责楼栋学生 | 本楼栋在住/检查/夜不归宿/纪律/维修 | 检查、异常上报、维修工单 | 看学生完整画像/学业/心理/困难明细 | 是（本楼栋） | 否 | 是 | 宿管老师 |
| 审批关系 | 流程节点分派 | 当前审批事项 | 当前事项审批必要信息 | 通过/退回/驳回/转办 | 审批后无限操作、越节点、全量查看 | 否（仅本事项） | 按事项敏感另判 | 是 | 各审批节点角色 |
| 创建人/责任人关系 | 创建/分派记录 | 本人创建/负责事项 | 本人创建/被分派数据 | 查看、处理、转办、分派、关闭、重开 | 越权改他人数据 | 是（本人数据） | 按数据敏感另判 | 是（转办/分派/关闭/重开留痕） | 全角色通用 |

### 8A.7 业务关系授权的开发落地要求（十条）

1. 权限判断**不能只看角色名**。
2. 后端接口必须**同时校验**：模块授权、角色权限、数据范围、业务关系、按钮权限、敏感字段权限（六要素合取）。
3. 课程教师的数据权限必须来自**教学任务/课表/教学班授课关系**。
4. 辅导员的数据权限必须来自**辅导员-班级/学生绑定关系**。
5. 毕设导师的数据权限必须来自**导师分配关系**。
6. 实习指导老师的数据权限必须来自**实习指导分配关系**。
7. 企业导师的数据权限必须来自**企业、岗位、协议、实习学生绑定关系**。
8. 审批权限必须来自**流程节点**，不等于永久业务管理权限。
9. 业务关系变更必须影响后续权限，但**历史记录保留原责任人快照**。
10. **不允许前端写死「某角色能看某数据」的判断**。

## 9. 菜单权限、按钮权限、数据权限区别

**必须严格区分以下 9 类权限，任何一类都不能替代另一类。** 混淆是权限系统失控的首要原因。

| 权限类型 | 控制什么 | 配置人 | 生效位置 | 是否可继承 | 是否需审计 | 示例 |
|---|---|---|---|---|---|---|
| 模块授权 | 学校能不能用某业务中心/能力（第一层） | 平台运营方 | 租户级（`t_platform_config` MODULE_GRANT） | 否（租户独立） | 是（授权变更） | 学校购买学工中心，未购买 AI 风险预警 |
| 菜单权限 | 角色能不能**看到并进入**某功能页 | 学校管理员 | 角色×菜单 | 是（从模板复制） | 是（配置变更） | 辅导员能看「风险预警」菜单，宿管看不到 |
| 按钮权限 | 页面内能不能**点某动作** | 学校管理员 | 角色×按钮点 | 是 | 是（配置变更） | 辅导员能点「审批」，班主任只能点「查看」 |
| 字段权限 | 某字段**能不能显示/编辑** | 学校管理员 | 角色×字段 | 是 | 是（敏感字段） | 普通教师看不到学生身份证字段 |
| 数据范围 | 能看到**哪些学生/班级/学院**的数据 | 学校管理员 | 角色×范围（`t_teacher_student_scope`） | 部分（可叠加/收窄） | 是（范围变更） | 辅导员只看本班；学院教务员只看本院 |
| 审批权限 | 能不能在**某审批节点**做通过/退回 | 学校管理员（配节点） | 角色×流程节点 | 否（按节点授权） | 是（审批动作） | 辅导员是请假初审节点、学院是复审节点 |
| 导入导出权限 | 能不能批量导入/导出（敏感导出强控） | 学校管理员 | 角色×domain | 是 | 是（导出必审计） | 资助老师能导奖助名单（水印+审计） |
| 敏感信息查看权限 | 能不能看完整手机号/心理/困难/处分明细 | 学校管理员（逐项二次确认） | 角色×敏感项 | 否（不能批量继承） | 是（强制，填原因） | 心理老师看心理明细，普通老师看不到 |
| 系统配置权限 | 能不能配菜单/按钮/范围/流程/参数 | 学校管理员（自身权限内） | 角色×配置项 | 否 | 是（配置变更） | 学校管理员能配流程，教务员不能 |

> 关键结论：**菜单权限 ≠ 数据权限**（能进页面不代表能看全部数据）；**按钮权限 ≠ 审批权限**（能点「审批」按钮不代表在所有节点都有权审——审批权限按节点授予）；**数据范围必须独立控制**（不随菜单开放而自动放宽）。

## 10. 敏感权限规则

以下行为属**敏感操作**，需在普通权限之上叠加特殊控制：

| 敏感行为 | 归属 |
|---|---|
| 查看完整手机号 | 学生/家长联系方式 |
| 查看身份证号 | 学生证件 |
| 查看家庭经济信息 | 困难认定 |
| 查看心理明细 | 心理健康 |
| 查看处分详情 | 违纪处分 |
| 查看困难认定材料 | 困难认定 |
| 导出学生名单 | 导出 |
| 导出奖助名单 | 导出 |
| 导出心理/处分/困难数据 | 导出（强控，部分禁止或强脱敏） |
| 修改角色权限 | 权限管理 |
| 修改数据范围 | 权限管理 |
| 启用/停用账号 | 账号管理 |
| 模块授权变更 | 平台授权 |

### 10.1 敏感操作统一控制要求（全部满足）

| 控制项 | 要求 |
|---|---|
| 最小授权 | 敏感权限逐项授予，**不能批量勾选下发**；默认不授予 |
| 二次确认 | 执行前二次确认弹窗（如「修改数据范围」「模块授权变更」需二次确认） |
| 填写查看原因 | 查看完整敏感值必填原因（≥5 字），无原因被拒（422） |
| 水印 | 敏感数据导出/打印带水印（含操作人+时间+租户，可追溯到人） |
| 审计日志 | 每次敏感查看/导出/权限变更写 `t_security_audit_log`（操作人/ip/ua/traceId/原因/对象/前后值） |
| 导出留痕 | 导出走 `t_export_task`（用途必填≥5字）+ 下载审计；心理明细在任何导出被剔除（默认锁死） |
| 可追溯到人 | 审计记录不可篡改、不可删除，学校审计员/管理员可查，能定位到具体自然人 |

### 10.2 心理数据特别红线

心理明细仅心理老师/授权辅导员可见（`PSY_STUDENT` 授权）；普通老师只见「需关注」标记不见明细；**任何导出剔除心理明细列**（默认开关锁死，学校不可改）；系统**不输出诊断结论**（仅关注/引用）；无权限时该区块整段不返回（防试探）。

## 11. 审批权限与流程权限

**审批权限 ≠ 流程配置权限，必须分离。** 能处理审批的人不一定能配流程；能配流程的人不一定有权审批所有业务。

### 11.1 业务审批权限（在具体节点做通过/退回/驳回）

| 业务审批 | 典型节点角色 |
|---|---|
| 请假审批 | 辅导员（初审）→ 学院学工（复审）→ 学工处（长假终审） |
| 奖助审核 | 辅导员（初审）→ 学院（审核）→ 学工处/资助（复核） |
| 处分审批 | 辅导员（登记）→ 学院（审批）→ 学工处（终审） |
| 学籍异动审批 | 学院教务/学籍管理员 → 教务处终审 |
| 成绩更正审批 | 任课教师（发起）→ 学院教务（审核）→ 教务处（审批） |
| 调停课审批 | 教师（发起）→ 学院教务 → 教务处 |
| 实习异常处理 | 实习指导老师 → 学院实习负责人 |
| 毕设材料审核 | 毕设导师 → 专业负责人/学院毕设负责人 |

> 业务审批权限按**流程节点**授予（角色×节点），不是一个「审批按钮」；同一人可能在 A 流程是审批人、在 B 流程无审批权。

### 11.2 流程配置权限（配模板，不参与具体审批）

- 配置审批模板（workflow_code 对应的模板）
- 配置节点（节点顺序、节点角色）
- 配置条件（如长假天数阈值走加节点，接参数中心）
- 配置抄送（抄送人/抄送角色）
- 配置超时规则（超时提醒/自动升级）

### 11.3 两条硬规则

- **普通业务老师只能处理审批事项，不能配置流程模板。**（辅导员能审请假，但不能改请假流程节点。）
- **流程管理员可以配置流程，但不代表能审批所有业务。**（配流程的人不自动获得业务审批权，审批权仍按节点授予。）

## 12. 模块授权与菜单显示规则

模块的可见性由**第一层模块授权**与**第二层角色菜单权限**共同决定，分三种情形：

### 12.1 未授权模块（第一层未授权 / 授权到期）

- 菜单**不显示**
- 路由**不可访问**（前端守卫拦截 + 后端二次校验）
- 接口返回 **403**（`module not granted`）
- 工作台**不显示**相关卡片
- 搜索**不返回**相关入口
- 移动端**不显示**入口
> 即「未开通就像不存在」，不做「敬请期待」占位页、不做空壳入口。

### 12.2 已授权但角色无权限（第一层授权、第二层未给角色）

- 菜单**不显示或置灰**（按学校策略）
- 直接访问返回 **403**
- **记录越权访问日志**（`t_security_audit_log`，resource+action+denied）

### 12.3 已授权且角色有权限

- 按**数据范围**显示数据（同一页不同角色看不同数据集）
- 按**按钮权限**控制操作（可点/置灰/不显示）
- 按**字段权限/敏感权限**控制敏感字段展示与查看

> 三情形的判定链：`模块授权(第一层) → 角色菜单权限(第二层) → 数据范围 → 业务关系 → 按钮/字段/敏感权限`，任一层不通过即在该层拦截，越权访问必审计。

## 13. 角色切换规则

- **用户可以拥有多个角色**（一人多职是常态，尤其教师）。
- 顶部**角色切换器**切换当前激活角色。
- **切换后后端重新解析权限上下文并返回**，前端刷新以下全部：菜单、待办、按钮、数据范围、工作台、统计口径、移动端入口、业务关系（见 §8A）。

### 13.1 举例

李老师可同时是：辅导员、毕设导师、实习指导老师、课程教师（含专业课/兼职教师等）。不同当前角色下：

- 看到的**数据不同**（辅导员看本班、毕设导师看指导学生、课程教师看授课班）。
- 能点的**按钮不同**（辅导员有请假审批、课程教师有成绩录入）。
- 待办**不同**（辅导员待办=请假/风险，课程教师待办=成绩录入/任务确认）。
- 敏感可见性**不同**（辅导员经授权可见心理标记，课程教师不可见）。

### 13.2 硬规则

- 权限**不叠加成超级权限**：多角色不等于把各角色权限并起来同时生效；同一时刻只按**当前激活角色**裁定。
- 切换角色是**会话级重载**，不是前端 tab 切换；后端按新角色重新走六要素判定。
- 兼职/兼课能力单列为独立角色，通过切换启用，不与主岗权限混淆。

## 16. 典型场景

> 每个场景写：操作人 / 前置条件 / 允许操作 / 禁止操作 / 系统如何控制 / 审计要求。

**场景 1 · 学校新增「二级学院副书记」角色**
- 操作人：学校系统管理员。前置：学工中心已授权（第一层）。
- 允许：复制「学院学工负责人」模板 → 角色类型=学工类 → 数据范围=本学院 → 裁剪敏感项 → 保存。
- 禁止：授予超出自身权限的项；开放未授权模块菜单；给该角色批量心理明细导出。
- 系统控制：保存时校验「⊆ 学校授权 ⊆ 创建者权限」；越界拒绝。
- 审计：建角色、权限项写 `t_security_audit_log`。

**场景 2 · 给辅导员开放请假审批，但不开放心理明细**
- 操作人：学校系统管理员。前置：学工中心已授权。
- 允许：辅导员角色勾选「请假审批」节点权限；不勾选「心理明细查看」。
- 禁止：把心理明细当普通字段批量开放。
- 系统控制：审批权限按节点授予；心理明细走 `PSY_STUDENT` 授权，未授权整段不返回。
- 审计：权限变更审计；后续辅导员查心理明细无授权被拒并审计。

**场景 3 · 学校购买了学工中心，但未购买 AI 风险预警**
- 操作人：平台运营方（授权）/ 学校用户（使用）。前置：`module.studentAffairs.enabled=true`，`module.ai.enabled=false`。
- 允许：使用学工全部人工业务（风险由 11 类来源人工生成/处置）。
- 禁止：使用 AI 自动风险预警（子能力未授权）。
- 系统控制：AI 卡片不显示、AI 接口 403、无假预警；风险人工闭环照常。
- 审计：模块授权状态可查；越权调 AI 接口记日志。

**场景 4 · 学校管理员给某学院教务员配置数据范围**
- 操作人：学校系统管理员。前置：教务中心已授权。
- 允许：把该教务员数据范围设为「指定学院」。
- 禁止：设为跨租户/全校（若管理员本身无全校授予权则不能授全校）。
- 系统控制：数据范围写 `t_teacher_student_scope`；运行时 `getAcademicScope` 收敛；跨院 403002。
- 审计：数据范围变更（敏感）审计。

**场景 5 · 李老师同时是辅导员、毕设导师、实习指导老师、课程教师**
- 操作人：李老师。前置：拥有 4 个角色，各绑定真实业务关系。
- 允许：切换当前角色 → 按 §8A.5 加载对应业务关系与权限。
- 禁止：一个角色下越界访问另一角色的数据（如辅导员角色下录成绩）。
- 系统控制：会话按当前激活角色重载六要素；业务关系来自真实数据表。
- 审计：切换本身可记录；各角色敏感操作各自审计。

**场景 6 · 企业导师只能看本企业实习学生**
- 操作人：企业导师。前置：实习中心已授权，企业-岗位-协议-学生绑定存在。
- 允许：看本企业名下实习学生的实习必要字段；确认考勤、填企业评价。
- 禁止：看非本企业学生；看学生完整学籍/心理/奖助/处分。
- 系统控制：数据范围=`ENTERPRISE_STUDENT`，业务关系来自协议绑定；敏感字段一律不返回。
- 审计：企业导师访问记录审计（跨企业访问拒绝并记日志）。

**场景 7 · 平台运维需要协助排查某学校问题**
- 操作人：平台运维支持。前置：学校发起/批准「运维协助授权」（工单+原因+时间范围）。
- 允许：授权期内、最小范围、只读优先地排查。
- 禁止：无授权访问；超范围；删改审计；替校审批。
- 系统控制：授权单控制范围与有效期，到期自动回收；每次访问审计。
- 审计：平台方授权期内每次操作全程审计，学校可查（见 §4.3）。

**场景 8 · 离职老师账号停用和权限回收**
- 操作人：学校系统管理员。前置：老师离职。
- 允许：停用账号 → 回收全部角色权限 → 名下待办转办。
- 禁止：删除其历史业务记录/审计；保留可登录。
- 系统控制：停用后不能登录；历史业务单据保留**原责任人角色快照**（不因停用而丢失追责）；外聘/兼职账号到期自动回收。
- 审计：停用、权限回收、转办全部审计。

**场景 9 · 导出奖助名单必须带水印和审计**
- 操作人：资助老师。前置：有奖助导出权限。
- 允许：导出奖助名单（填用途≥5字 → `t_export_task` → 生成带水印文件）。
- 禁止：无用途导出；导出含未脱敏家庭经济/身份证；导出心理明细。
- 系统控制：金额/家庭经济脱敏；水印含操作人+时间+租户；心理列强制剔除。
- 审计：导出+下载全程审计，可追溯到人。

**场景 10 · 学生只能查看本人数据**
- 操作人：学生。前置：学生端已授权。
- 允许：看本人请假/成绩/课表/资助进度/毕业进度。
- 禁止：看他人数据；看本人风险/心理原始明细。
- 系统控制：数据范围=`SELF`，student_id 从 token 取，越权 403002/404；心理明细不下发学生端。
- 审计：学生敏感操作（如查成绩）按需审计；越权访问记日志。

**场景 11 · 专业课教师提交成绩后不能自审**
- 操作人：专业课教师。前置：授课关系存在，成绩录入/提交权限。
- 允许：录入/暂存/提交本人课程成绩；发起成绩更正申请。
- 禁止：审核自己提交的成绩；发布成绩；看无关班级成绩。
- 系统控制：成绩「提交」与「审核/发布」是不同权限点（职责分离）；同一人对同一成绩不能既提交又审核；成绩走状态机（录入→提交→学院审→教务发布）。
- 审计：录入/提交/更正申请全程审计。

**场景 12 · 监考/阅卷教师最小字段可见**
- 操作人：监考教师 / 阅卷教师。前置：监考安排 / 阅卷分配存在。
- 允许：监考看本人监考安排/考场/名单必要字段；阅卷处理分配任务、录分。
- 禁止：监考看完整成绩/学籍隐私；阅卷发布成绩、看非分配任务。
- 系统控制：数据范围=监考安排/阅卷任务，返回「任务必要最小字段」；不含成绩全貌与学籍隐私。
- 审计：阅卷录分、监考异常登记审计。

## 17. 开发落地要求

后续开发必须遵守（违反即评审打回）：

1. **不要把角色写死在页面里**（不允许前端硬编码「某角色能看某数据」）。
2. **不要只靠前端隐藏菜单**（前端隐藏是体验，不是安全）。
3. **后端接口必须校验权限**（六要素合取：模块授权+角色权限+数据范围+业务关系+按钮权限+敏感字段权限）。
4. **菜单权限和数据权限分开**（能进页面 ≠ 能看全部数据）。
5. **按钮权限和审批权限分开**（能点按钮 ≠ 在所有节点有权审）。
6. **敏感字段后端脱敏**（出口脱敏，看完整需授权+原因+审计，前端不做敏感判定）。
7. **导出必须审计**（`t_export_task` + 用途 + 水印 + 下载审计；心理明细剔除）。
8. **权限变更必须审计**（角色/范围/模块授权/敏感权限变更全部写 `t_security_audit_log`）。
9. **角色切换必须刷新权限上下文**（会话级重载菜单/待办/按钮/范围/统计/业务关系，后端按当前激活角色返回）。
10. **旧角色权限变更不影响历史审计追踪**（业务单据记录当时的责任人+角色+数据范围快照；事后改角色定义/停用角色，历史追责不变）。

> 补充：业务关系必须来自真实业务数据表（教学任务/辅导员绑定/导师分配/实习分配/企业协议等），后端据此校验；审批权限来自流程节点，非永久业务管理权；业务关系变更影响后续权限但保留历史快照。

## 18. 验收标准

以下为可检查项，逐条验收：

- [ ] 学校能新增自定义角色（复制模板或空白创建）。
- [ ] 自定义角色不能超过授权模块（超授权模块的权限项保存被拒）。
- [ ] 自定义角色不能超过创建者自身权限（提权被拒）。
- [ ] 未授权模块菜单不显示（且路由不可达、搜索/工作台/移动端不出现入口）。
- [ ] 未授权模块接口返回 403。
- [ ] 辅导员只能看自己学生（跨班 403002 + 审计）。
- [ ] 学院管理员/教务员只能看本学院（跨院 403002 + 审计）。
- [ ] 学生只能看本人（跨人 403002/404 + 审计；本人心理/风险明细不下发）。
- [ ] 企业导师只能看本企业学生（跨企业拒绝 + 审计；不看学工/学业敏感）。
- [ ] 课程教师数据来自授课关系（教学任务/课表/教学班），不含无关班级。
- [ ] 专业课教师提交成绩后不能自审、不能发布。
- [ ] 监考/阅卷/复核教师仅见任务必要最小字段，不含成绩全貌与学籍隐私。
- [ ] 角色切换后菜单变化。
- [ ] 角色切换后数据范围变化（业务关系随之切换）。
- [ ] 敏感信息查看需要填写原因（无原因 422）。
- [ ] 导出带水印（含操作人+时间+租户，可追溯到人）+ 下载审计。
- [ ] 权限变更（角色/范围/模块授权/敏感权限）有审计。
- [ ] 停用账号后不能登录（历史业务记录保留原责任人快照）。
- [ ] 旧业务记录保留原责任人（事后改角色定义不影响历史追责）。
- [ ] 平台方无授权不能查看学校敏感业务数据（运维协助需授权+原因+时间范围+全程审计+到期回收）。
- [ ] 审计日志不可删除、不可修改，可追溯到具体自然人。

## 附：需要人工确认的点

以下事项属现场/合同/组织层面决策，本文件给出默认口径，落地前需与平台方与试点校确认：

1. **套餐与模块授权组合**：各套餐（如基础版/标准版/旗舰版）对应哪些第一层模块，需商务确认。
2. **学校自定义角色的上限**：是否限制学校自定义角色数量、是否允许学校自定义角色类型（本文默认 9 类角色类型可扩展，需确认是否放开）。
3. **班主任与辅导员是否同权同视图**：本文默认班主任按辅导员范围规则，但是否同权由学校确认（各校差异大）。
4. **专业负责人在教务与毕设两域的权限并集边界**：同一自然人跨域时的数据范围叠加口径，需确认。
5. **运维协助授权的有效期与审批层级**：临时授权时长（24/72h）、由谁批准，需与学校确认。
6. **敏感导出的白名单/黑名单**：哪些名单允许导出、哪些强制禁止（如心理明细导出默认锁死），需合规确认。
7. **外聘/兼职教师账号有效期与回收策略**：默认到期自动回收，具体时长与离聘触发方式需确认。
8. **学生干部的「被授权协助项」范围**：允许学生干部协助哪些名单/签到项，需学校确认（默认最小）。
9. **企业导师可见实习字段清单**：企业侧最小必要字段的精确清单，需与合规/企业确认。
10. **审批权限与流程配置权限的角色划分**：哪些角色属「流程管理员」，需学校确认（本文默认业务老师不配流程）。

> 以上未确认项一律先按「最小授权 + 默认关闭 + 授权启用」口径落地，确认后再放宽；不得因未确认而默认开放敏感能力。
