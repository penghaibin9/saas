## 0. 命名口径裁定（最终版，全部文档以此为准）

| 维度 | 13A 学工中心 | 13B 教务中心 |
|---|---|---|
| 模块名/API 前缀（PC） | `/api/v1/student-affairs/*` | `/api/v1/academic-affairs/*` |
| 移动端（学生） | `/api/v1/mobile/affairs/*` | `/api/v1/mobile/academic-affairs/*`（既有 `/api/v1/mobile/academic/my` 属学业过程域，冻结不动） |
| 移动端（教师写操作） | `/api/v1/mobile/teacher/*` 包装追加 | 同左 |
| 新表前缀 | `t_affairs_*` | `t_aa_*` |
| 权限点 | `studentAffairs.<biz>.<action>` | `academicAffairs.<biz>.<action>` |
| PC 路由 | `/admin/student-affairs/*` | `/admin/academic-affairs/*` |
| source_module | `student-affairs` | `academic-affairs` |

**旧字样替换映射（存量 13B 文档待统一替换）**：

| 旧字样（13B 融合设计/契约草案中） | 裁定后 |
|---|---|
| `t_aa_*`（新表） | `t_aa_*`（如 t_aa_status_change → t_aa_status_change） |
| `academicAffairs.*`（权限点） | `academicAffairs.*` |
| `/admin/academic-affairs/*` | `/admin/academic-affairs/*` |
| 旧写法（已废止）`/api/v1/academic/terms|programs|...`（13B 误挂学业过程域下） | 13B 新建统一 `/api/v1/academic-affairs/*`；既有 `/api/v1/academic/*` 仅代表学业过程域，保留不动 |
| `center-dashboard` / `center-audit-logs` | `/api/v1/academic-affairs/dashboard` / `/audit-logs` |
| source_module=`academic-affairs` | `academic-affairs` |

不变项：既有学业过程域 `t_acad_*` 表与 `/api/v1/academic/*` 端点原样冻结；workflow_code 沿用两份融合设计已冻结的编码（13A=`AFFAIRS_*`、13B=`ACAD_*`，仅为审批流字符串，与表前缀无冲突）。

**七类决策定义**：
- **复用现有**：直接使用既有表/端点/服务，不建新表，至多加薄查询封装。
- **扩展现有**：在既有表/服务上加字段、加状态、加流程，并保持回链/回写关系。
- **新增独立**：现有代码无对应能力，按命名口径新建 `t_affairs_*`/`t_aa_*` 表与端点。
- **合并到现有**：需求项不单独建设，并入某个统一抽象（如统一资助抽象）。
- **后置P2P3**：V1 不实现，P1 仅冻结 workflow_code、规则键与契约占位。
- **暂不做**：本项目周期内不建设。
- **需现场确认**：学校口径未定，先按默认值设计并显式标记确认项。

## 4. Opus 开发防破坏规则（16 条）

每条：为什么不能做 → 违反后果 → 正确做法。

**规则 1：不改六大模块接口契约，除非新增兼容字段。**
为什么：迎新/在校/学业/实习/毕设/就业的端点已被 PC 与小程序既有页面消费，响应结构即契约。
后果：PC 与小程序既有页面白屏/字段 undefined 崩溃；203 条 pytest 大面积红；演示租户讲解链路断。
正确做法：只允许新增可选字段；老字段名称/类型/语义不变；契约文档同步更新；新增节点（如 360 聚合的 affairs 节点）走向后兼容评审。

**规则 2：不动统一响应结构与错误码语义。**
为什么：`{code,bizCode,message,data,traceId,timestamp}` 与 8 组错误码是全端请求层的分支依据（backend/app/core/response.py、exceptions.py）。
后果：小程序 401 单飞刷新、409 防重复文案、422 表单回显全部错位；业务错误变 500 触发前端"系统异常"误报。
正确做法：新业务错误一律映射到既有码位（业务错误绝不 500）；409001 按 DATA_CONFLICT / APPROVAL_VERSION_CONFLICT / IDEMPOTENCY_CONFLICT 三语义精确使用。

**规则 3：不新建学生/教师主表，不冗余可变身份字段。**
为什么：t_student_profile 与 t_user 是全平台唯一身份事实源。
后果：改名/换班后各处数据不一致；360、毕业审核、scope 判定读到过期身份；数据无法修复。
正确做法：外键 student_id 引用；姓名/班级等展示字段查询期 JOIN；学籍语义字段仅经 change_student_status 单一入口。

**规则 4：不绕过 Workflow 自建审批表或"直接改状态"捷径。**
为什么：t_workflow_instance/t_workflow_task 携带乐观锁与审计，是审批唯一事实。
后果：/approvals 列表与移动审批看不到任务；两人同时审批产生双通过；审批留痕缺失无法追责。
正确做法：新 workflow_code + node_code 注册；业务状态由 on_approved 回调驱动；业务快照表只存意见附件，审批状态以 task 为准。

**规则 5：不绕过统一待办/消息自建通知通道。**
为什么：t_unified_todo/t_unified_message 是工作台与消息中心的唯一数据源，消息类型限定 8 种。
后果：辅导员工作台待办不全、完成率统计失真；学生收不到审批结果；通知不可审计。
正确做法：审批联动写 todo/message；接收人精确 receiver_id；新场景先归入 8 类，归不进 = 设计问题上会，不加第 9 类。

**规则 6：不手写数据范围过滤，必须走 resolve_teacher_scope 封装。**
为什么：看得见=能处理，列表过滤与写操作校验共用同一 scope 函数（backend/app/services/mobile_teacher_service.py）。
后果：辅导员看到全校学生（越权泄露）或看得见却审不了（流程卡死）；越权行为无审计。
正确做法：getCounselorScope / getStudentAffairsScope / getAcademicScope 一律实现为 resolve_teacher_scope / can_teacher_view_student 的薄封装；新角色范围 = 新增 scope_type 枚举（DORM_BUILDING/PSY_STUDENT/AID_BIZ）。

**规则 7：不输出未脱敏敏感字段，不绕过导出水印管线。**
为什么：身份证/手机号 *_encrypted 存储 + 出口脱敏、导出走 t_export_task 水印登记是安全底线。
后果：敏感信息泄露 = 安全事故；无痕导出困难生名单/心理名单 = 合规事故。
正确做法：出口统一 _mask_* 与 MobileSensitiveText；看完整值 = 专用端点 + 原因≥5字 + 审计；导出注册 domain 走既有管线。

**规则 8：不动 t_acad_\* 既有表结构语义，不建第二套成绩/预警/补考重修表。**
为什么：t_acad_grade 是成绩权威读取层，t_acad_warning 处置链路已上线并被移动端消费。
后果：双事实源永久分叉，/mobile/academic/my 与毕业审核读到不同成绩；预警重复推送骚扰辅导员。
正确做法：只加 nullable 列（source/rule_code/batch_id/apply_id）；成绩过程层 t_aa_grade_* 发布时原子回写 t_acad_grade；预警只经既有创建逻辑 + 幂等键。

**规则 9：13A 不写 student_status/current_stage；13B 只经单一入口写。**
为什么：学籍是教务职权，current_stage 归学生中心；多点写入 = 状态机失控。
后果：休学学生仍能选课实习；毕业审核读到脏状态；MERGED/RECYCLED 治理态被误改。
正确做法：13A 的学工态标签落 t_affairs_risk_record 等自有表；13B 全部经 change_student_status（白名单校验 + 乐观锁 + 流水 + StageEvent + 审计五件套）。

**规则 10：不硬编码业务规则，一律走平台规则中心。**
为什么：长假天数、处分层级、补考计分、绩点算法等是各校差异项且多为现场确认项（/admin/platform + safe_rule 已存在）。
后果：换校部署要改代码重发版；现场确认后无法当场调整；规则变更无审计。
正确做法：P1 注册规则键与默认值；读取走平台配置路径 + 本地缓存；禁止为 13A/13B 新建规则界面。

**规则 11：不破坏 demo-school 只读锁与 sandbox 重置机制。**
为什么：demo（…003）中间件写 403、sandbox（…007）每晚 0 点重置是演示与试用的安全边界。
后果：演示数据被改坏无法讲解；为"演示方便"开后门 = 生产越权通道。
正确做法：13A/13B 写端点在 demo 租户自然 403 并提示去沙箱；种子数据扩展进 reset_sandbox_school.py；测试不依赖 sandbox 隔夜数据。

**规则 12：不改既有 pytest 断言迁就新代码；新功能必须带测试。**
为什么：backend/tests/ 下全量用例（速查口径 203 条）是六域行为的冻结快照。
后果：改断言 = 悄悄改契约，回归失去意义；无测试的新流程上线即赌运气。
正确做法：既有用例必须原样全绿；每个新业务至少 4 条用例且必含"重复提交 409"与"跨学生越权 403/404"；回写类逻辑（t_cs_discipline/t_acad_grade/t_cs_dorm_record）必须有一致性用例。

**规则 13：不在前端另建请求封装/toast/mock 机制。**
为什么：miniapp request.js（realFirst/createSubmitLock/401 单飞）与 frontend services/http（withFallback）承载全部容错与安全分支。
后果：新页面防连点缺失→重复提交；401 处理不一致→登录死循环；mock 漂移→演示与真实两套行为。
正确做法：新模块 import 既有封装；提交按钮必包 createSubmitLock；mock 按域目录追加且结构与冻结契约一致。

**规则 14：不违反数据库公共字段与建表约定；改既有表只允许加 nullable 列。**
为什么：t_ 前缀/BIGINT 主键/tenant_id/version/is_deleted 等公共字段是中间件（租户过滤、乐观锁、软删）的依赖。
后果：缺 tenant_id = 跨租户泄露；缺 version = 并发覆盖；对既有表加 NOT NULL 列 = 存量行与迁移脚本崩。
正确做法：新表 13A 用 t_affairs_*、13B 用 t_aa_*，公共字段全套继承；改既有表（t_class/t_major/t_acad_*）只加 nullable + 默认值列；留痕表 append-only 不带软删。

**规则 15：不占用、不覆盖既有路由与 API 路径。**
为什么：/api/v1/academic/*（学业过程域）、/admin/academic（PC 学业过程模块）、六域全部路径已被消费。
后果：路由覆盖导致既有页面 404/数据错乱，且极难排查。
正确做法：13B 全部新端点挂 /api/v1/academic-affairs/*、PC 路由 /admin/academic-affairs/*（本文件 §0 裁定，与既有路径零交集）；CI 加路由重复注册检查；新增前先跑一次全路由清单 diff。

**规则 16：不信任前端传入的身份与租户参数。**
为什么：student_id 从 token 取、tenant 从上下文取是既有安全模型（学生端只能看/写本人）。
后果：请求体带 student_id 即可越权替他人请假/查成绩；带 tenant_id 即跨租户。
正确做法：学生写操作端点从 token claims（studentNo/userId）解析身份；教师写操作一律走 /api/v1/mobile/teacher/* 包装（范围 + 审计 + 409）；任何"帮学生代提交"场景显式设计并审计。
