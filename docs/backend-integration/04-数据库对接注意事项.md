# 04 · 数据库对接注意事项

> 文档性质：数据库对接注意事项（全部以引用/约束方式表达，不重写表结构）
> 适用端：后端开发（FastAPI + SQLAlchemy + Alembic）
> 依据：`docs/database/00-数据库设计冻结总册.md` §一（总体原则）、§十（多租户与数据范围）、§十六（审计）、§十七（脱敏与导出）；共享事实底稿 §3、§4
> 当前阶段声明：数据库表结构以 `docs/database/00-数据库设计冻结总册.md` 为**唯一权威**，本文档禁止新增/修改任何表或字段，只做对接约束说明

## 一、总原则：一律以冻结总册为准，禁止改表

- **数据库唯一权威**：`docs/database/00-数据库设计冻结总册.md`，冻结约 150 张表、20 大模块。任何接口实现中发现字段不够用/命名不一致，**先提出待确认问题，不擅自改表**，走冻结总册的下一版本评审流程。
- **本清单不写建表 DDL、不写 Alembic 迁移脚本**，具体迁移由后端团队按冻结总册 §十九"Alembic / SQLAlchemy 迁移建议"章节执行。
- 冻结总册技术栈声明已拍板：PostgreSQL（单库/单 schema + `tenant_id` 行级隔离）+ SQLAlchemy + Alembic，一期不做每校独立库/独立 schema。

## 二、多租户 tenant_id 隔离

| 要求 | 说明 |
|---|---|
| 所有业务表必须带 `tenant_id NOT NULL` | 三类例外：审计/日志/流水表（见下节）不受影响仍需 `tenant_id`；全局字典/模块定义/权限定义（`t_dict`/`t_module_def`/`t_permission`）**无 tenant_id**（跨租户共享元数据）；平台运营表（`t_tenant`/`t_saas_package`）**无 tenant_id**（控制面数据，自身即租户维度） |
| 查询强制注入 | 中间件层（FastAPI 依赖注入 + SQLAlchemy 会话级过滤）强制 `WHERE tenant_id = :currentTenant`，**禁止业务代码手写**，避免遗漏导致跨租户泄露 |
| 跨租户访问 | 一律拒绝，返回 `TENANT_NOT_FOUND`/`NO_PERMISSION` |
| 唯一例外 | 平台运营端（`/api/v1/platform/*`）查看多租户数据，必须走权限校验 + 写 `t_security_audit`，不得裸查 |

## 三、软删除 / 审计字段

每张业务表的强制公共字段（冻结总册 §1.2）：

```text
tenant_id   BIGINT      NOT NULL
created_at  DATETIME    NOT NULL
updated_at  DATETIME    NOT NULL
created_by  BIGINT      NULL
updated_by  BIGINT      NULL
is_deleted  TINYINT(1)  NOT NULL DEFAULT 0   -- 逻辑删除
version     INT         NOT NULL DEFAULT 0   -- 乐观锁
```

**三类表例外（必须记住，后端实现时不要对这三类表套用上述公共字段）：**

| 表类 | 例外 | 原因 |
|---|---|---|
| 审计/日志/流水表（`t_*_audit`、`t_*_log`、`t_*_event`、`t_checkin`） | **无 `is_deleted`、无 `updated_at/updated_by`、无 `version`**，只允许追加（append-only） | 审计与流水禁止软删除替代冲正，必须不可变 |
| 全局字典/模块定义/权限定义（`t_dict`、`t_module_def`、`t_permission`） | **无 `tenant_id`** | 全平台统一定义 |
| 平台运营表（`t_tenant`、`t_saas_package`） | **无 `tenant_id`** | 控制面数据 |

- PostgreSQL 落地类型对照：`BIGINT` 主键（应用层雪花/发号器赋值，非 `SERIAL`）；`DATETIME` → `TIMESTAMP`（建议 `TIMESTAMPTZ`）；`TINYINT(1)` → `BOOLEAN`；`JSON` → `JSONB`。

## 四、时间与时区

| 要求 | 说明 |
|---|---|
| 数据库存储 | 统一时间戳类型（PostgreSQL 建议 `TIMESTAMPTZ`），禁止用字符串存时间 |
| 接口返回 | ISO8601 带时区字符串，如 `2026-07-04T14:05:00+08:00` |
| 前端处理 | 前端不做时区换算，后端统一转换为约定格式返回 |

## 五、枚举与前端常量对齐

> 本节为核心对照表，后端实现枚举字段时必须与前端已使用的常量码保持一致（前端码来自 `frontend/src/modules/workflow/` 与共享事实底稿，数据库侧码来自冻结总册）。**发现下方标注"（待与冻结总册核对）"的条目，实现前必须先与数据库冻结总册维护方确认，不得擅自决定取舍。**

### 5.2 DATA_SCOPE 数据范围 —— **重要差异提示，必须先与后端确认收敛方案**

前端 workflow 模块与共享事实底稿使用的是**简化 6 值**数据范围口径；数据库冻结总册 §10.2 定义的是**完整 12 值**数据范围口径。两者**不是同一套枚举**，后端实现时必须做映射收敛，不能简单二选一：

| 前端/共享底稿口径（6 值，`DATA_SCOPE`） | 数据库冻结总册口径（12 值，`t_data_scope_rule`/`t_user_context.data_scope`） | 对照关系（本轮推断，待与冻结总册核对） |
|---|---|---|
| ALL（全平台） | SCHOOL / DEPARTMENT / CUSTOM 等跨校维度暂无对应，平台侧另有独立语义 | 待后端确认：ALL 是否对应"平台运营端跨租户"这一特殊场景，还是应归入 12 值枚举扩展 |
| SCHOOL（本校） | SCHOOL | 命名一致，可直接映射 |
| COLLEGE（本学院） | COLLEGE | 命名一致，可直接映射 |
| CLASS（本班级） | CLASS、COUNSELOR_CLASSES（辅导员多班场景） | 待确认：CLASS 是否等价于 COUNSELOR_CLASSES，还是二者需要区分单班/多班 |
| SELF（仅本人） | SELF | 命名一致，可直接映射 |
| ASSIGNED（被指派对象） | GD_STUDENTS（毕设指导学生）、INTERN_STUDENTS（实习指导学生）、ENTERPRISE_AUTH_STUDENTS（企业导师授权学生） | 待确认：ASSIGNED 是否是 GD_STUDENTS/INTERN_STUDENTS/ENTERPRISE_AUTH_STUDENTS 三者的统称，前端侧不区分，后端需要在服务端按角色类型翻译为具体的一种 |
| （前端无对应） | MAJOR（专业维度）、TEMP_AUTH（临时授权） | 前端当前未使用，（待后端确认）是否本期需要支持，或作为后续扩展预留 |

**建议处理原则（本轮推荐，待后端最终拍板）**：
1. 前端 6 值 `DATA_SCOPE` 作为**对外/权限体验层的简化展示口径**，服务端内部仍按数据库冻结总册 12 值实现具体的 SQL 过滤逻辑（如 `dataScopeMiddleware` 把 `GD_STUDENTS`/`INTERN_STUDENTS`/`ENTERPRISE_AUTH_STUDENTS` 都翻译为具体过滤条件，但对前端统一以 `ASSIGNED` 展示）。
2. 后端在 `t_data_scope_rule` 或等价配置表中维护"前端展示码 ↔ 数据库内部码"的映射关系，避免前端因为看到陌生的 12 值枚举而需要改动。
3. 此项**必须在步骤 3（用户角色权限）联调前确认**，否则会影响后续所有模块的数据范围过滤逻辑，见 `03-接口联调顺序.md` 步骤 3。

## 六、分页与索引建议（不写 DDL）

- 所有列表接口分页结构统一 `{list, total, page, pageSize}`（详见 `docs/api/04-统一响应结构与错误码.md` §二），单次 `pageSize` 上限 100。
- 索引建议方向（不给出具体 `CREATE INDEX` 语句，由后端按实际查询模式设计）：
  - 所有业务表的 `tenant_id` 应建立索引（多租户过滤是每次查询的必经条件）。
  - 高频按 `student_id` 关联查询的表（实习/毕设/就业/学业/迎新/在校服务各业务表）应对 `student_id` 建索引。
  - 按角色数据范围过滤常用的关联字段（`class_id`/`college_id`/`mentor_id`）应建索引，避免 `dataScopeMiddleware` 注入的过滤条件全表扫描。
  - 审计/日志类 append-only 表按时间范围查询频繁，应对 `created_at` 建索引（注意这类表无 `updated_at`，见上文例外说明）。
  - 具体索引方案（复合索引顺序、是否分区表等）待后端根据实际数据量与查询模式确认，本文档只给方向建议，不代替数据库设计评审。
