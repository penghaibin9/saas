### 2. 按模块逐个推进，模块内部按业务闭环施工

业务主线：批次与名单准备 → 企业岗位准备 → 申请与岗位匹配 → 导师、协议、保险及上岗核验 → 实习过程 → 评价与成绩 → 材料归档与就业衔接。

风险、请假、调岗、退岗和事故是按实际情况触发的分支，不是所有学生必须经过的线性阶段。哪些条件阻止上岗、允许返岗或影响结项，以真实服务端规则和有效政策为准。

首次先核对一次最小全链路图：参与身份、核心业务对象、已实现入口、关键前置条件、下游结果和主要断点，明确可复用能力、模块范围及顺序。已有有效记录则只复核变化，不每次重做全中心调研。全链路图用于确定施工依赖，不要求先编写整套新设计总册才开始当前模块。

**每次以一个完整业务模块为交付范围。** 默认对应经审计确认的二级工作区；现有归组不合理时可按真实流程调整并记录映射，不以菜单数量划定业务能力。开工写清模块边界、所有三级业务页、四级深链及相关弹窗/抽屉、四端职责、上下游和内部闭环顺序。模块内部逐个完成从发起到结果可见、待办消退和下一环节接续的全部适用页面、接口与配套，再收口模块。跨模块的必要依赖先修复，独立模块的全面重构按顺序另行推进。任务跨回复或需要分步施工时，仍继续当前模块；真实外部阻碍须登记未完成项和所需条件，不用拆分方式宣布整模块完成。

### 2.1 批次和实习记录贯穿全流程

- 先明确当前租户、身份、授权范围、实习批次及具体实习记录。学生主档、某次实习记录、岗位申请、在岗分配不是同一个对象；不得仅凭 studentId 推断应审核哪条实习记录，也不能用学期替代批次。
- 列表、详情、工作台、通知深链、页签和快捷入口携带需要的真实业务上下文。多批次并行时不得取查询结果第一条作为永久工作批次；无可用批次、无权查看、批次服务失败与尚未选择要分别表达。
- 切换批次或身份时，不继续沿用上一批次对象、审核队列、选择项和敏感缓存；存在未保存内容时走已有保护。打开特定批次的记录后，页面范围与实际记录归属一致，刷新及返回也要验证。
- 调岗或导师变更后，当前关系和历史关系按现有契约保留；哪些协议、保险、计划、评价需要重核，以真实规则决定，不批量覆盖历史事实。已结束、已归档和只读批次的查看与写入边界分别验证。
- 匹配成功不自动等于允许上岗，材料上传不自动等于协议已签署或保险有效，提交报告不等于批阅通过，完成评价不等于成绩已发布，结束批次不等于档案已完整归档。界面反馈必须与实际落库结果一致。

### 2.2 容易被主流程和菜单遗漏的业务

下列项目必须在相关闭环开工时逐项判定“已具备可复用 / 需要适配 / 缺失但适用 / 不适用”。它们是本提示词的审计与覆盖要求，不代表当前系统都缺少，也不意味着一律新建菜单、页面或接口。适用性依据当前学校配置、有效业务文件及真实代码确认，不从历史设计中的政策数字推导现行制度。

| 补查项 | 必须核对的完整办理内容 | 纳入阶段 |
|---|---|---|
| 岗前安全教育与知情确认 | 核验课程/材料下发、学习与测验、补学/重测、完成证据及对上岗条件的影响；学生本人和适用监护人的知情确认分别核验身份、正文版本、确认结果、失效/重发/撤销。学生转发邀请或学校代录不能冒充监护人本人确认。复用现有学习与受控协同入口，不默认新建家长平台 | 实习准备、上岗确认；材料变化时重核 |
| 实习报酬与权益求助 | 核对岗位和协议中已有的报酬约定、适用登记与学生反馈，明确记录来源；约定金额或登记记录不等于实际到账。学生求助/投诉、企业投诉学生、一般预警要区分来源、受理人、进度反馈、证据可见范围和转风险关系；被投诉方的材料访问权限单独检查，不能因其是导师或企业联系人而默认可见全部内容 | 岗位准备、协议、实习过程、风险处置 |
| 尚未落岗和特殊学业路径 | 未申请、未录用、暂缓、延期、免实习、实习中断后重新安排或补修等，核对是否适用、谁受理、依据材料、期限、后续安排与最终统计去向；待安置学生不能从名单和工作台消失。合规检查项豁免、免实习和实习正常完成是不同结果，不共用一个“已完成”状态 | 实习准备、人岗确定、异常分支、结果认定 |
| 在岗期间条件失效 | 核验保险覆盖期、协议/企业资质有效期、岗位停用、导师离岗，以及缺勤/失联等实际规则；不能只在首次上岗时检查。到期提醒、逾期扫描、复核、必要限制、替代安排与恢复条件形成责任闭环。自动任务按时间推进和重复执行验证，阈值来自真实配置，不在提示词中预设天数 | 上岗确认、过程执行、异常分支 |
| 规则版本与历史结果 | 对批次规则、成绩权重、协议正文、课程和材料要求，核对生效范围、适用版本和历史快照。规则调整后说明哪些在途记录采用旧规则、哪些需复核；已发布成绩和已归档事实的纠错走授权流程，不因修改设置而静默重算或覆盖。学分是否回写教务、失败如何对账，也要核验现有正式契约 | 实习准备、过程执行、结果认定、结项 |
| 特殊备案和对外报送 | 根据学校实际业务核验跨区域/特殊实习备案、校内审核、适用报送渠道、接收结果与退回重报。校内备案完成、生成导出文件、已提交外部平台和已获接收回执分别展示；没有真实对接规范或回执不能显示“监管已接收”。不为补齐提示词擅自接入外部平台 | 岗位准备、上岗确认、异常分支、结项 |
| 结项是否达到学校要求 | 除材料齐全外，核对实际采用的实习时长/任务、考勤请假、指导与多方评价等认定依据；明确不合格、延期补交、补修、成绩修订和最终离岗/结项交接的去向。时长、成绩、学分与毕业要求的关系依据真实学校规则，不在实习模块复制一套教务判定 | 结果认定、结项交接 |

### 3.1 每个模块的关联代码审计与施工前置门

**执行顺序固定为：模块及关联代码审计 → 真实流程与问题清单 → 依赖顺序和设计就绪 → 四端内容页面设计制作及后端修复 → 联调验证 → 记录收口。** 在审计和必要设计门禁完成前，不按原型的假定状态直接改正式业务。

沿每个适用三级业务页、四级深链和动作追踪实际调用链，包括由页内按钮、通知、搜索、快捷栏进入的详情、编辑和审核状态，至少覆盖：

- 四端入口、路由、菜单、工作区、表单/附件、API 适配、对象标识、批次及状态展示。
- 后端 router、schema、service、状态转移、数据模型/迁移、事务、幂等和版本冲突处理。
- 身份与租户、学校/企业关系、校内指导教师与企业导师、审批节点、授权数据范围、实习资格和敏感字段。
- 上游触发条件、下游结果使用方、岗位名额与匹配结果、协议保险和上岗条件、考勤与报告、评价成绩、待办通知、文件绑定、审计、统计、归档、定时或异步任务。
- 同一接口的其他端与企业协同调用方、旧路由和历史参数兼容、适用测试及安全测试环境；不只审计前端当前打开的页面。

审计结论写入当前模块施工包或施工记录，至少包括三张可复核清单：

1. **代码关联清单：** 页面/动作 → 接口 → 服务与模型 → 上下游调用方 → 测试，带当前基线、真实路径和 symbol/行号。
2. **实际流转清单：** 发起条件 → 当前批次和业务对象 → 当前责任人与节点 → 可执行动作 → 下一状态 → 四端及适用协同方可见结果；分别记录正常、退回、终止、超时、变更和冲突等实际存在的分支。
3. **问题及施工顺序：** 问题证据、受影响端/动作、类型（代码错误、流程断点、页面缺失或设计改进）、优先级、前置依赖、修复落点和验证方式。阻断提交、审核、正式落岗、返岗、成绩发布或结果落库的缺陷优先处理。

明确区分“代码阅读确认”“已复现”“待运行核验”，未执行的链路不能写已经走通。检查空实现、假成功、接口字段和状态不匹配、错误审批节点、批次错用、岗位超额、重复提交、反馈丢失、敏感信息越界、关系变更后权限未收敛、成功后下游未接续等问题，但不得预设它们一定存在。

按审计结果安排当前模块内部顺序：通常先校正契约、状态和必要后端缺陷，再实现四端页面，最后验证通知、台账和跨模块结果。成熟业务逻辑和合适组件优先复用，旧页面布局须按本次师生任务重新评估和设计。四端设计清单应在施工前同时列清，不能先交完 PC 就把两套小程序留作未登记的后续事项。

### 3.2 以办理结果判断闭环是否完成

每个闭环的验收结果必须能回答：

1. 谁从哪个真实入口发起，使用哪个批次和实习对象？
2. 操作是否真实落库，当前状态、责任人和下一步是否正确？
3. 对应学生、教师及适用企业协同方是否能在自己的授权端查看或接续？
4. 本环节待办是否正确产生、转交或结束，通知是否指向真实记录？
5. 下一环节是否已经接收到正确结果；若尚未开放，是否明确显示实际原因？
6. 退回、失败、重复提交、权限不足、切批次和并发冲突等适用情况是否可恢复？

和框架原生能力和最小封装。两套 PC 复用一致的视觉规则，不共享角色特权业务逻辑。教师小程序改造必须形成真实 uni-app 页面；HTML 手机框、H5 截图不能证明微信运行正常。

### 4.1 便捷性与实际办事体验

以下是逐模块适用性检查项，不代表当前代码都存在缺陷。根据实际流程选择实现或复用；不适用项写理由。每次至少核验首次办理、熟练重复办理、出错后继续办理三类情境，不能只检查页面能否打开。

| 容易遗漏的场景 | 设计与实现要求 |
|---|---|
| 不知道从哪里办 | 常用业务从工作台/待办、菜单或搜索可达；搜索使用中文业务名及合理别称。同一事项的不同入口指向同一记录；不要让用户必须记住两字菜单含义 |
| 不知道能否参加或上岗 | 填写前说明真实资格、批次范围、开放/截止时间、必需材料和未满足条件。未分配导师、岗位已停用、无可用批次、保险待核验等按实际原因给出下一步或联系岗位，不只留灰按钮，不编造学校制度 |
| 选错批次或实习记录 | 多批次、多申请和历史记录明确区分；页面显示足以确认对象的学生、岗位、企业、实习周期。切批次、通知直达、刷新和返回不串用对象，不把上一批次选中项带入批量审核 |
| 重复填写已知信息 | 当前身份、授权基础资料、已确定企业岗位和导师等合理带入；已提供且仍有效的信息优先复用或供选择。主档字段按权限只读或走原变更流程，不在实习表单中偷偷改主档，不为方便把身份证、定位或协议等敏感数据存入浏览器持久缓存 |
| 不清楚该改哪一项 | 必填、格式、日期和附件限制在输入处说明；错误定位到字段且保留其他输入。退回原因与待补材料对应，展示现有材料和版本；不给用户一条笼统的“操作失败” |
| 提交后不知道下一步 | 清楚区分申请受理、待补正、匹配/接收、待签署、待核验、在岗、待评价、待发布和归档等真实状态；说明当前处理岗位、可见记录、下一步和适用时限。成功后可查看结果或继续下一件 |
| 连续批阅和核验很多事项 | 保留合理范围内的队列位置，处理后回到队列或进入下一件。批量分配导师、审核、提醒、导出等仅在业务允许且真实接口支持时提供；明确范围、条数、影响和逐项失败，不盲目扩展到整校数据，不为每个动作强加确认框 |
| 手机现场办理受阻 | 检查打卡定位、相机/文件权限、上传与预览返回、巡访记录、输入键盘、底部安全区和网络中断。位置失败、定位异常和考勤异常分别表达；真实支持补卡/核验时给出入口，不伪造打卡成功 |
| 中途被打断或超时 | 切页、返回、登录过期、断网和上传失败时给出准确状态与恢复路径。需要草稿时受控保存；未支持跨端草稿就明确说明。写请求超时先核对结果或使用现有幂等机制，避免重复申请、重复分配、重复批阅或重复发布 |
| 通知收到却办不了 | 待办与普通消息分清，已读不等于办结。通知进入对应端真实详情，登录后在授权范围内恢复目标；已办结、记录不可见、导师变化或批次归档时给出说明，不跳空页。不许诺未经配置和验证的微信通知必达 |
| 请假、返岗和调岗互相脱节 | 实习请假返岗与学工请假返校是不同业务结果；需要联动时通过明确契约，不互相冒充办结。调岗审核后核对岗位、企业、导师、协议保险和任务的真实影响，保留前后版本与待办交接，不无条件重置全流程 |
| 评价完成但成绩看不到 | 说明评价任务主体、提交状态、成绩计算来源、待审核/待发布原因和学生可见范围。企业评价不能冒充综合成绩；规则或来源变化后按契约重算/复核，不能静默改写已发布成绩 |
| 导入导出、结项和归档耗时 | 复用文件、Excel 和异步任务能力展示真实进度或明确处理中状态；可找到结果、缺项和逐项失败。档案缺失、接口失败与空档案分别表达；按实际规模分页查询，在安全测试环境测量典型操作，不主观宣称“响应很快” |
| 换导师、换企业或跨学期后卡住 | 核验批次、实习周期、师生和企业导师关系、审批岗位与开放范围。自然日/工作日、请假扣减、报告周期、评分权重等不擅自设值；无处理人时复用授权的异常处理或转派能力，不自动跳过审核 |
| 新版接入后旧单据丢失 | 除新建记录外，验证在岗记录、待审核申请、退回材料、历史协议保险、未完成变更、已发布成绩和已归档记录。规则、班级、企业或身份变化后的在途记录按现有契约处理，不按新页面默认值重写历史事实 |

- W3C WAI：[Understanding SC 3.2.4: Consistent Identification](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification)。

本次提示词改编没有重新核验上述网页；后续实际引用时记录查阅日期和适用内容。通用交互资料不证明实习政策、厂商采用情况或本项目已实现，也不替代正式外部证据门或 WCAG 验收。

### 4.2 必要配套随当前模块完成

关联审计中把配套项分为两类并明确记录：

- **当前办理必需：** 缺失会导致用户找不到入口、对象/批次不明确、填不完、无法提交/审核、不能落岗/返岗、看不到结果、无法继续办理或旧单据断流。包括直接关联接口与中文适配、必要角色/范围和导师配置入口、企业协同落点、文件材料、待办通知、台账、失败恢复、历史兼容及相关公共组件缺陷；在当前模块内一起完成或明确阻碍，不能因为“原计划只改页面”而遗漏。
- **独立扩展：** 与当前办理无直接关系的新业务、整套基础平台重建、第三方商业服务或额外插件，登记为后续建议，不自动扩大施工。就业衔接复用现有就业中心，文件和电子签署优先复用现有正式能力；不得为本模块另造平行平台。

“配置入口”是交付学校人员按授权维护业务配置的能力，不等于代替学校更改真实审批政策、角色授权、保险要求、评价权重或生产数据。前置配置缺失时先查原因和已有入口，必要时补充可操作提示；重大业务决定仍交用户明确。

### 4.3 三级业务页与四级深链重新设计

三级、四级按用户实际进入业务与办理记录的层次识别，不按 URL 斜杠数量判断。四级深链包括当前模块的详情、新建、编辑、审核、补正、处理记录及可直达的页内状态；不要求把它们都新增为侧栏菜单。

1. **先盘点再设计。** 每个模块列清全部三级业务页及关联四级页面，包含菜单未展示、由列表按钮/待办/通知/搜索/快捷栏进入的内容。可运行的旧页面留存截图并记录具体问题；无法运行时记录代码审计结果与待查看项，不声称已观察到页面。新壳与导航已接入不代表正文已完成重构。
2. **自行确定每页的信息顺序与布局。** 写清谁来办理、首先需要知道什么、主要动作、次要资料和成功后的去向，再选择工作队列、检索列表、分组表单、详情或材料与审核并列等合适结构。普通方案自行定稿并实现，不要求用户提供线框图或逐页拍板。原有组件结构不能反过来决定新的业务布局。
3. **教师 PC 面向连续处理。** 按任务需要清楚组织筛选与待办、学生和岗位背景、材料核验、处理意见及历史记录；高频审核支持明确的当前对象和处理后去向。减少重复标题、装饰性统计卡、层层套卡片和不必要跳转，让材料、关键判断信息与可执行动作容易找到。
4. **学生端面向自己办完一件事。** 优先展示本人实习进度、当前条件、下一步、待补材料与办理结果；申请表单按自然顺序分组，退回原因对应需修改内容。学生 PC 与两套小程序分别适配任务、屏幕和身份，不照搬教师台账或把桌面表格机械缩小。
5. **四级页面有完整的独立上下文。** 深链进入后能识别所属模块、批次、学生/本人实习记录、企业岗位、当前状态和可执行动作。长表单与复杂材料审核采用适合持续办理的空间；轻量操作可用弹窗/抽屉，不能把复杂审批硬塞进小窗口。主操作、返回和处理后继续路径位置清楚，底部固定区不遮挡正文、键盘焦点或手机安全区。
6. **真实深链可直达、可恢复。** 核验直接打开、刷新、登录后恢复、返回列表、页签恢复及批次切换；兼容旧 URL 与必要参数，避免错记录、丢筛选和未保存内容丢失。记录不存在、无权限、已办结、只读、加载失败分别有准确反馈和可用去向。抽屉等依赖列表上下文的入口若要支持分享或通知直达，应通过项目既有路由约定恢复，不能只能从某个按钮点击才打开。
7. **每个模块同时检查视觉与办理。** 对三级页和四级深链分别检查典型正常、长内容及适用异常状态，在实际 PC 窗口和移动视口查看整体布局；核验字号、间距、信息密度、表格溢出、材料可读性、焦点与主操作。提供能说明主要变化的真实页面截图，明确原型、隔离样例与真实业务的区别；截图好看不能代替权限与流程验证，测试通过也不能代替正文设计检查。
8. **模块完整后再推进下一个。** 同一模块的列表、详情、表单、审批、反馈状态和四端适用内容按统一规则连续完成，记录设计与实现各自的状态。只重做三级入口、让四级仍跳旧正文，或只完成教师 PC 后遗漏学生与移动页面，均属于本模块未完成。

### 5. 真实权限与验证

沿用后端租户、模块授权、角色权限、数据范围、学校/企业和师生关系、敏感字段、状态机与版本/并发检查。学生仅处理本人允许的事务；教师只能处理被授权批次、学生及节点；企业身份只能访问自身授权企业、岗位及对应记录。内部风险调查、事故证据、未公开评分、联系方式、协议与身份材料等按真实字段规则控制，不随学生同壳暴露。

菜单可见、路由可进、对象可读、字段可见和动作可写分别核验。查看权限不能被管理权限误挡，开放查看页后也不能顺带开放编辑、冻结名单、结束批次或成绩发布。前端隐藏或禁用不能代替后端拒绝。权限矩阵及正反向测试必须对应当前三级页面、四级深链和动作，包含绕过菜单直接访问的情况。

在独立测试环境验证当前模块的实际正常及适用异常链路：创建/申请、受理、退回补正、重提、驳回、撤回、超时、重复或并发处理、最终结果、通知及台账。不存在的动作标不适用，不为凑流程增加接口。岗位实习额外按当前模块核验：

- 本人/他人、指导关系/非指导关系、企业归属、角色/节点、跨租户、跨批次及敏感字段的允许与拒绝场景。
- 岗位名额和开放范围变化、资格不足、导师缺失、协议/保险未满足条件、批次只读或归档后的真实行为。
- 过程报告/考勤核验后四端结果一致；请假与返岗、风险处置与调岗退岗衔接正确，不错误恢复不具备条件的在岗状态。
- 企业、学生、教师评价来源可追溯；核算、审核发布、申诉复核和历史成绩版本符合现有契约。
- 结束/归档就绪检查、缺项补交、文件版本、统计口径与就业交接有真实结果，不能只验证成功提示。

先跑最小相关检查，再按改动风险扩大；命令以各工程 package.json、后端说明和 e2e/README.md 为准。改动四端时运行相应测试、lint（存在时）和构建；小程序检查 H5 与 mp-weixin 构建，区分构建、浏览器、微信开发者工具与真机验证。后端和迁移在独立 MySQL 测试库验证，真实 E2E 必须满足项目安全门。每项记录实际命令、退出码、数量、环境和本次工作区/候选基线，不引用旧通过记录替代当前验证。

原型、mock 和隔离组件样例只用于设计或组件检查，不能当真实业务验收。登录态或安全测试环境缺失时，完成可以独立进行的代码与检查，记录未验证项；需要用户配合时请其在测试页面登录，不索取聊天明文密码，不绕过认证，不试用生产账号或数据库。未能验证企业协同、第三方签署/保险状态或微信能力时分别标记，不用学校端样例覆盖缺口。

每个模块额外提交一份简短的“实际办事检查”：分别以首次参加实习的学生、经办/指导教师、学校实习管理员身份说明从哪里进入、选择哪个批次或记录、填写什么、哪里容易出错、办完去哪里；涉及企业动作时增加实际协同方路径。四端使用同一组安全测试记录检查交接，修复已确认的重复输入、无必要跳转、返回后状态丢失和没有下一步的问题。附实际执行的步骤和结果，区分智能体走查与真实用户试用；未做真人测试不能声称小白用户已验证。

最终给用户可直接打开的测试入口、适用身份和少量具体操作步骤，让用户评价“是否看懂、是否顺手、是否符合学校实际”。路径、字段、权限、数据库和技术回归由智能体核验，不要求用户自己找技术遗漏。

### 5.1 整体交付验收，不以各模块截图相加代替

各闭环完成后，在同一安全测试环境用可追溯测试记录串起“名单资格 → 申请匹配 → 上岗条件 → 实习过程 → 评价发布 → 结项归档”的完整链路，并穿插一条适用的退回/变更异常链。每次切换学生、教师及适用协同方身份，核对前后端和四端看到的是同一事实；阶段或接口尚未接通时明确停点。

整体收口还要核对以下交付项，按已有工程能力和根规则执行，不为此顺手重建基础平台：

- **学校能独立开新一轮实习：** 有可操作的配置入口和必要说明，能配置批次、责任岗位、适用企业/导师关系与材料要求；不得依赖开发者直接改数据库才能正常开工。
- **历史记录能继续办理：** 新旧页面接入、版本发布和数据变更后，在途记录与旧深链可续办；必要的数据迁移、兼容窗口、失败恢复及回滚方案有证据。是否发布、何时切换仍需既有授权。
- **后台任务和故障可发现：** 核验通知、文件处理、到期提醒、逾期扫描和报送等实际异步任务的执行记录、失败重试与异常反馈；验证系统故障不会把真实成功的业务改成失败或重复处理。
- **真实规模与恢复能力：** 按明确的测试规模检查典型查询、批量审核、导入导出及归档耗时；对涉及的数据变更与正式交付，按根规则核验备份恢复和回滚。记录实际环境与结果，不虚构并发量、响应时间或完成率。
- **可用性证据完整：** 检查 PC 常用窗口尺寸、键盘与焦点、长内容和大字号，手机权限拒绝、弱网、文件预览返回及安全区；微信正式环境/开发者工具/真机结果与 H5 结果分开记录。未做真实用户试用、恢复演练或真机验证时明示未做。

局部页面和组件可以先形成可审阅结果；只有全部适用交付条件满足，才能按根规则标记对应的可交付或上线状态。缺少真实登录或安全测试环境时保留这些待验项，不因界面施工结束而注销。

### 6. 续接与收尾

首次执行本提示词时，在现有 `docs/06-开发施工与质量验收/施工记录/` 下创建 `岗位实习核心业务四端落地进度.md`；已有同一任务的有效总记录时先核对并衔接，避免互相矛盾的进度册。以后更新同一记录，不反复新建总册。按模块记录总体进度，内部逐项跟踪业务闭环、三级页面及四级深链，至少记录：

- 模块名称与边界、顺序、所属施工阶段、内部闭环编号、关联模块、全部适用三级页面、四级深链及页内动作；新工作区和旧施工包的映射。施工阶段与业务实习批次分别记录，避免混淆。
- 模块关联代码审计、实际流转、问题清单和经审计确定的施工顺序。
- 批次与实习对象上下文、企业/导师关系和上游前置条件、下游结果接续。
- 当前流程必需配套、便捷性检查、历史/在途单据兼容及未实施的独立扩展。
- 四端路由/页面、后端与必要企业协同落点、适用和不适用范围。
- 当前代码基线、原有及本次改动、重新设计的布局与决策、三级和四级页面的实际截图及视觉走查、实现/验证证据；旧布局保留部分需说明适用依据，不能默认沿用 main。
- 各端及链路的实际状态、缺口、阻碍和当前模块下一步的准确入口；模块内尚未完成的闭环、三级/四级页面及验证分别列清，完成后再记录下一模块。

遵守实际根规则对 planned/partial/implemented/verified/deliverable/deployed 的定义。未提交工作区检查要注明，不标成候选 commit 已验证。当前模块未完成时下次继续该模块及其未完成步骤；没有安全测试环境不抹掉剩余验证，也不反复执行已经通过且未受后续改动影响的检查。8 个工作区的壳层接入、导航测试通过或本提示词文件存在，都不能直接把模块标成四端 verified。

最终先说明“当前模块完成什么、还缺什么”，提供实际入口、三级/四级页面主要设计变化、实际测试和四端验证结果、必要企业协同验证、数据库/迁移/权限/批次及旧路由影响、当前 Git 状态和当前模块下一步；模块收口后再说明下一模块。截图明确是真实测试业务、隔离样例还是原型。用户应能按完整办理过程验收，而不是代替智能体核对技术文件。

本提示词不授权自动提交、推送、部署、生产操作、删除真实数据、不可逆迁移、认证/权限核心重构或大批删除旧文件；遵守根规则中对应的明确决定要求。不得因任务量大静默缩减当前模块的三级/四级页面和适用四端内容，或漏记尚未完成的闭环与验证。默认顺序执行，不自动创建其他用户任务或并行智能体。

现在根据续接记录和代码选择当前模块。没有记录时先做最小全链路依赖核对，默认从“批次与学生”模块开始，先核验批次、名单与资格：四端入口、当前批次选择、参与资格、名单范围、必要规则、预览/冻结与启用的实际链路。列清该模块完整三级/四级页面后，自行规划并完成四端设计施工、其他适用内部闭环、必要配套、缺口修复、验证和模块收口，再进入下一模块。若审计发现更早的直接阻断，自行调整修复顺序并说明依据。只创建/修改本提示词文件的任务，不执行这一开工指令。
