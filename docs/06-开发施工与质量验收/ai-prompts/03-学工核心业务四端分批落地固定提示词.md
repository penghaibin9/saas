用途：供用户在后续任务中重复调用，依据已确认的 UI 壳，逐模块完成正式业务页面、四端流转和验证。本文是执行任务的提示词，不是模块施工包、设计就绪证明或完成证明；不替代根目录 AGENTS.md 和有效的模块施工包门禁。

来源：用户在 2026-09-05 确认当前 UI 外壳满意，要求四端工作区内容页面一起设计制作；每个模块必须先审计模块及其关联代码，理清流程与顺序后再施工，并明确授权修复代码问题和走不通的业务流程。本文件编写时仓库为 main，HEAD 为 `6810bd6284b4d5c69a78947560f808cd7738327e`，存在未提交的学生 PC 同壳改动；执行时必须重新核验，不能沿用这里的旧状态。

## 每次使用

在同一项目任务中发送下面这段即可；无需每次重新解释设计方向：

```text
请读取并执行 docs/06-开发施工与质量验收/ai-prompts/03-学工核心业务四端分批落地固定提示词.md 中的“固定提示词正文”。根据当前代码、实际验证证据和续接记录，继续最早未完成的模块；没有续接记录就从第一批“请假返校”开始。每个模块先审计模块及关联代码，理清实际流程、断点和施工顺序，再保持已确认的 UI 壳，一起设计制作学生 PC、教师 PC、学生小程序、教师小程序的全部适用工作区内容页面，完成真实流转验证。以普通老师和学生能顺手办完事为验收目标，当前流程必需的配套改动一并完成，不把技术查漏交给用户。代码有问题、流程走不通，可以修复。完成后写清下一模块和剩余缺口。
```

用户明确指定某批、某模块时，以该指定为本次入口，仍保留其他未完成事项。仅说“继续”时恢复当前模块；不能因一次回复结束而跳过缺口。

## 固定提示词正文

你在“职校学生全生命周期系统”仓库中工作。现在执行学工核心业务的分批落地任务，持续完成当前模块的实现和验证，不停在建议、静态 HTML、流程演练或施工文档阶段。

### 1. 已确认的产品决定

1. 教师 PC 和学生 PC 使用用户已确认的同一套 UI 壳：紧凑顶部、二三级双窄栏、悬浮展开、独立固定/取消、可关闭和恢复的页签、可编辑快捷栏、搜索与专注工作区。配色保留雾蓝、护眼绿、石墨紫、曜石黑，不重新启动整套外观选型。业务内容是主工作区，避免恢复大面积欢迎横幅、重复标题和层层导航。
2. 二、三级菜单可按真实学校业务自由调整名称和排列。用具体任务命名，窄栏可保留两字简称，同时提供全称、所属路径、选中态和键盘访问。原 URL 兼容和刷新直达必须保留；尚未可用的功能不得包装成可办理入口。
3. **四端工作区内容页面一起设计制作，是每个模块的必做范围。** 覆盖该端全部适用的列表、表单、详情、审批、结果、记录及相关弹窗/抽屉和反馈状态；教师小程序业务页面也要设计实现。先查看真实页面及典型状态，再调整待办列表、详情、材料查看、审批意见、底部主操作和现场办理。遵循微信小程序和 uni-app 的原生交互，关注安全区、输入键盘、点击范围和返回行为。PC 的双侧栏、多页签不直接搬到手机。
4. 学生小程序与教师小程序保持相同的品牌语言、状态和反馈习惯；界面按身份任务设计。学生 PC 同壳不等于共享教师菜单、管理权限或内部敏感信息。
5. 已授权读取本项目相关代码、文档、本地设计和必要的公开互联网/GitHub资料，并实施当前模块相关的前后端、四端页面、契约、测试和文档改动。**审计发现的代码错误、断开的流转、错误状态、接口不一致及直接关联缺陷，允许一并修复并补测试，不限于改样式。** 以成熟实现为基础修复、适配，不因重新设计界面而删除成熟能力或重写无关底座；涉及末节列出的高风险操作仍按根规则执行。
6. 用户不负责查路径、找接口或决定普通实现细节。可以从代码查明的内容自行核验；一般布局、组件选择和局部交互自行完成。学校审批政策、无法从有效依据确定的重大业务取舍，按根规则提出一个具体问题，同时继续不依赖答案的工作。
7. 用户明确要求考虑使用便捷性，并授权“该附带的就附带”。当前模块正常使用所必需的关联修复、入口、提示、反馈和配置配套属于本次范围，主动查漏并完成；以实际任务为依据，不为凑清单新增插件、重复平台能力或无关功能。用户主要验收办理效果，智能体负责技术核验、边界和证据。

### 2. 分批顺序与执行粒度

下表是排期分组，不代表一次重做一整批。**每次执行只负责其中一个真实二级模块及其全部三级页面**；核验模块边界，完成后记录下一模块。顺序先以表为默认，再根据每个模块的关联代码审计明确实际前置依赖与施工先后；若需调整次序，记录证据和影响，不静默跳过模块。跨模块可修复阻断当前链路的直接关联缺陷，并验证受影响调用方；独立新业务拆为后续模块，不顺手改写其他业务。

| 批次 | 按顺序推进的模块 | 这批关注的完整过程 |
|---|---|---|
| 第一批 | 请假返校 | 申请、材料、审批、退回补正、驳回、续假、返校确认、逾期跟进、台账与统计；同步接入本业务待办和通知 |
| 第二批 | 困难认定 → 奖助服务 | 批次与资格、申请、评审、公示、异议复核、结果；认定结果衔接相应奖助资格，奖助评审衔接发放记录 |
| 第三批 | 住宿管理 | 房源与分配、入住、调宿、退宿、检查、整改复检、住宿异常、统计 |
| 第四批 | 风险处置 → 谈话家校 → 心理关怀 → 违纪处分 | 核实、分派、跟进、转办或升级、复核与办结；处分包括决定、送达、申诉及解除；按业务边界衔接 |
| 第五批 | 学生档案 → 班级工作 → 迎新报到 → 活动成长 → 统计归档 → 今日工作汇总 | 本人资料与补交材料、班级与辅导员关系、报到、活动签到及积分、离校关联手续、归档；最后汇总已落地业务的工作台 |

“今日工作”相关待办随各模块逐步接通，最后统一收口，不等到第五批才展示已接通事项。学生、班级、辅导员关系等前置依赖在每个模块开工前核验并复用；第五批是对应页面的完整适配，不是前面各批凭空模拟基础数据。

排期名称是产品分组，不能据此臆造数据库域或接口。以实际 navPlan、路由和施工包映射真实二级边界；若一个分组对应多个二级模块，拆成连续任务。数字迎新进入其现有中心索引；补交材料、离校按当前归属接入，不另造平行流程。

### 3.1 每个模块的关联代码审计与施工前置门

**执行顺序固定为：模块及关联代码审计 → 真实流程与问题清单 → 依赖顺序和设计就绪 → 四端内容页面设计制作及后端修复 → 联调验证 → 记录收口。** 在审计和必要设计门禁完成前，不按原型的假定状态直接改正式业务。

沿每个适用三级页面和动作追踪实际调用链，至少覆盖：

- 四端入口、路由、菜单、工作区组件、表单/附件、接口适配及状态展示。
- 后端 router、schema、service、状态转移、数据模型/迁移、事务和版本冲突处理。
- 身份与租户、角色与审批节点、数据范围、学生/班级/辅导员等业务关系及敏感字段。
- 上游触发条件、下游结果使用方、待办、通知、文件绑定、审计、统计、归档、定时或异步任务。
- 同一接口的其他调用方、旧路由兼容、适用测试和安全测试环境；不只审计前端当前打开的页面。

审计结论写入当前模块施工包或施工记录，至少包括三张可复核清单：

1. **代码关联清单：** 页面/动作 → 接口 → 服务与模型 → 上下游调用方 → 测试，带当前基线、真实路径和 symbol/行号。
2. **实际流转清单：** 发起条件 → 当前责任人与节点 → 可执行动作 → 下一状态 → 四端可见结果；分别记录正常、退回、终止、超时和冲突等实际存在的分支。
3. **问题及施工顺序：** 问题证据、受影响端/动作、类型（代码错误、流程断点、页面缺失或设计改进）、优先级、前置依赖、修复落点和验证方式。阻断提交/审核/结果落库的缺陷优先处理。

明确区分“代码阅读确认”“已复现”“待运行核验”，未执行的链路不能写已经走通。检查空实现、假成功、接口字段与状态不匹配、错误审批节点、重复提交、丢失反馈、敏感信息越界和成功后下游未接续等问题，但不得预设它们一定存在。

按审计结果安排当前模块内部的依赖顺序：通常先校正契约/状态与必要后端缺陷，再实现四端页面，最后验证通知、台账和跨模块结果；已有完整实现直接复用。四端设计清单应在施工前同时列清，不能先交完 PC 就把两套小程序留作未登记的后续事项。

### 4. 当前模块必须形成的设计与实现

先将各三级页面和动作逐一映射到真实流程：发起人、前置条件、材料、处理人及范围、当前节点、允许动作、下一节点、时限、结果去向、异常分支、通知与审计。明确“已有可复用”“需要修改”“缺失待补”，标明代码或外部依据；学校政策参数不凭经验硬编码。

四端按职责覆盖：

- 学生 PC：长表单、附件整理、申请记录、补正、结果与完整时间线。
- 学生小程序：便捷申办、补交、接收通知、查看进度及适合手机的确认操作。
- 教师 PC：工作队列、筛选、材料核验、审批、配置、台账、统计和适用的 Excel 操作。
- 教师小程序：授权节点待办、详情与材料、意见提交、返校/入住等现场确认及跟进。

不是每个教师管理功能都要放到学生端或手机端；不适用的端和动作明确说明理由。四端共用同一业务记录、服务端状态和权限裁决，不在各端另存一套流程真值；一端处理后，其他端按现有刷新/消息机制更新，过期页面提交必须得到明确冲突反馈。

使用“三级业务/动作 × 四端页面”的覆盖表统一设计和跟踪。各适用格必须列出真实路由、内容布局、字段与操作、异常状态、接口和验证结果；不适用格写业务理由。不能用换壳、跳转旧页面、单张通用空模板或仅一端截图代替四端正文设计。页面可以复用合适的成熟组件，但需按本次流程完成交互适配和实际检查。

页面实现至少覆盖：

1. 列表/工作队列：紧凑筛选、中文状态、当前责任人、待处理事项和必要的主操作；回到列表时按业务需求保留筛选、分页和滚动，不用全局缓存冒充完整状态恢复。
2. 申请/编辑：字段分组、条件校验、真实文件上传及补正反馈。保存/提交失败保留内容，阻止重复提交；需要草稿时核验或实现真实草稿能力，明确未保存状态，不把页签恢复称为表单恢复。
3. 详情/审批：材料、业务信息、处理记录与状态时间线清楚；按角色及当前节点提供动作。审批成功之后才更新结果，退回补正与终止性驳回分开；审核冲突不能显示成功。
4. 全状态：加载、空数据、失败与重试、无权限、只读/到期、正常和处理中；不能将请求失败显示为数量 0 或空列表。界面全中文，状态/异常经统一展示适配，不透传内部枚举、权限码或技术异常。
5. 相关公共链路：附件、通知、待办、敏感字段、审计、Excel、统计及归档分别说明真实落点或不适用原因。正式发放台账不冒充银行到账；消息投递失败不抹掉已成功提交的业务。

优先现有公共组件、框架原生能力和最小封装。两套 PC 复用一致的视觉规则，不共享角色特权业务逻辑。教师小程序的改造要在当前模块中形成真实 uni-app 页面；HTML 手机框、H5 截图不能证明微信运行正常。

### 4.1 便捷性与实际办事体验

以下是逐模块适用性检查项，不代表当前代码都存在缺陷。根据实际流程选择实现或复用；不适用项写理由。每次至少核验首次办理、熟练重复办理、出错后继续办理三类情境，不能只检查页面能否打开。

| 容易遗漏的场景 | 设计与实现要求 |
|---|---|
| 不知道从哪里办 | 常用业务可从工作台/待办、菜单或搜索到达；搜索使用中文业务名及合理别称。入口分工明确，同一事项的不同入口指向同一业务记录；不要让用户必须记住两字菜单含义。 |
| 不知道能否申请 | 在填写前说明当前资格、开放/截止时间、必需材料与下一步。未配置批次、没有班级或审批人等情况与“没有记录”分开，给出符合权限的处理入口或明确联系岗位，不只留灰按钮。依据真实配置和接口返回生成提示，不编造学校制度或正式帮助文案。 |
| 重复填已知信息 | 当前身份、有效学期、本人基础信息等从授权数据合理带入；同一流程已提供且仍有效的信息优先复用或供选择。主档字段按权限只读或走原变更流程，不在申请里偷偷修改主档；不把敏感信息写入浏览器持久存储以追求方便。 |
| 不清楚该改哪一项 | 必填、格式和材料限制在输入处说明；错误定位到对应字段且保留其他输入。退回原因与待补内容对应，展示已有材料及补正入口；不给用户一条笼统的“操作失败”。 |
| 提交后不知道结果 | 清楚区分已提交、待补正、审批中、已办结等实际状态，说明当前处理岗位、允许查看的处理记录、下一步和适用时限。成功后可查看结果或继续下一件；“通过审批”与后续确认、发放、归档分开。 |
| 连续处理很多事项 | 列表筛选、分页、滚动和返回位置按合理范围保留，审批后可回到队列或处理下一件。业务允许且真实接口支持时提供批量操作/常用意见；明确选中范围、条数、动作影响和逐项失败结果，不盲目扩展到整校数据，不为每个动作强加确认框。 |
| 中途被打断 | 切页、返回、登录过期、断网和上传失败时给出准确状态与恢复路径。需要草稿的长流程用真实受控保存，未支持跨端草稿就明确说明；写请求超时先核对结果或使用现有幂等机制，避免直接重试造成重复提交，不用离线假成功掩盖断网。 |
| 通知收到却办不了 | 本业务待办与普通消息分清，已读不等于办结。通知进入对应端真实详情；登录后在授权范围内恢复目标。旧通知遇到已办结、记录不可见或权限变化时有说明，不跳空页；使用现有通知机制，未经真实授权不能许诺微信通知必达。 |
| 手机办理不顺手 | 检查拍照/文件选择、预览返回、长表单输入、键盘遮挡、底部安全区和网络中断。四端相同动作名称与状态含义一致，手机根据任务重新排版；确保字号、焦点、点击范围和放大显示可用，状态不能仅靠颜色区分。 |
| 导入导出等操作时间长 | 复用现有文件/Excel/异步任务能力展示真实进度或明确处理中状态；能找到完成结果、失败原因和适用的重试入口。表格按实际规模分页/查询，避免一次加载所有数据；在独立测试环境测量典型操作，不能仅凭主观写“响应很快”。 |
| 新学期或换老师后卡住 | 核验学校时区、学年学期、批次、班级及辅导员绑定、审批岗位与开放范围。区分自然日/工作日口径；规则来源不明不擅自设值。人员离岗、无处理人或岗位交接时，复用授权的异常处理/转派能力，不自动跳过审批。 |
| 新版接入后旧单据丢失 | 除新建记录外，验证历史记录、处理中申请、退回补正单据和旧链接。规则调整、换班及身份变化后的在途单据依据现有契约处理，保留必要历史信息，不按新页面默认值重写旧业务事实。 |

这些便捷性要求综合用户决定、现有项目边界和设计建议，实际能力以代码审计为准。通用原则参考如下，已于 2026-09-05 打开核验；它们不证明学校业务政策、任何厂商采用情况或本项目已实现，也不替代模块正式外部证据门：

- Nielsen Norman Group，[10 Usability Heuristics for User Interface Design](https://www.nngroup.com/articles/ten-usability-heuristics/)，§1 状态反馈、§3 用户控制、§5 预防错误、§6 识别、§7 效率、§9 错误恢复：用于检查下一步提示、减少记忆负担与恢复路径。
- W3C WAI，[Understanding SC 3.3.7: Redundant Entry](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)，Success Criterion / Intent：同一流程中仍有效的信息可带入或供选择；这不要求跨会话保存，也不能据此扩大敏感数据留存。
- W3C WAI，[Understanding SC 3.2.4: Consistent Identification](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification)，Intent：相同功能保持一致识别；四端动作命名一致是本项目据此提出的设计要求，不代表已完成 WCAG 全项验收。

### 4.2 必要配套随当前模块完成

关联审计中把配套项分为两类并明确记录：

- **当前办理必需：** 缺失会导致用户找不到入口、填不完、无法提交/审批、看不到结果、无法继续办理或旧单据断流。包括直接关联接口和中文适配、必要角色/范围配置入口、文件与材料、待办和通知落点、结果台账、失败恢复、历史兼容及相关公共组件缺陷；在当前模块内一起完成或明确阻碍，不能因为“原计划只改页面”而遗漏。
- **独立扩展：** 与当前办理无直接关系的新业务、整套基础平台重建、第三方商业服务或额外插件，登记为后续建议，不自动扩大施工。已有公共能力优先复用；确需修改公共组件时，说明调用方影响并检查其他已接入模块。

“配置入口”是交付学校人员按授权维护本业务配置的能力，不等于代替学校更改真实审批政策、角色授权或生产数据。前置配置缺失时，先查真实原因和已有入口，必要时补充可操作提示；重大业务决定仍交用户明确。

### 5. 真实权限与验证

沿用后端租户、模块授权、角色权限、数据范围、业务关系、敏感字段、状态机和版本/并发检查。学生仅处理本人允许的事务；教师只能处理被授权范围与节点，内部风险、心理、调查材料不能随学生同壳暴露。权限矩阵及正反向测试必须与当前三级页面和动作对应。

在独立测试环境验证当前模块的实际正常及适用异常链路：发起、受理、退回补正、重提、驳回、撤回、超时、重复或并发处理、最终结果、通知及台账。不存在的动作标不适用，不为凑流程增加接口。至少验证本人/他人、角色/节点、跨租户、敏感信息的允许与拒绝场景。

先跑最小相关检查，再按改动风险扩大；命令以各工程 package.json、后端说明和 e2e/README.md 为准。改动四端时运行相应前端测试、lint（存在时）、构建；小程序检查 H5 与 mp-weixin 构建，并区分构建、浏览器检查、微信开发者工具/真机验证。后端和迁移在独立 MySQL 测试库验证，真实 E2E 必须满足项目安全门。每项记录实际命令、退出码、数量、环境和本次工作区/候选基线，不引用旧通过记录替代当前验证。

原型、mock 和隔离组件样例只用于设计或组件检查，不能当真实业务验收。登录态或安全测试环境缺失时，完成可以独立进行的代码与检查，记录未验证项；需要用户配合时请其在测试页面登录，不索取聊天明文密码，不绕过认证，不试用生产账号或数据库。

每个模块额外提交一份简短的“实际办事检查”：分别以新学生、经办教师、学校业务管理员身份说明从哪里进入、需要填写什么、哪里容易出错、办完去哪里。四端使用同一组安全测试记录检查交接；记录多余重复输入、无必要跳转、返回后状态丢失和没有下一步的页面，并修复已确认问题。附经过实际执行的简短步骤和结果，区分智能体走查与真实用户试用；未做真人测试不能声称小白用户已验证。

最终给用户可直接打开的测试入口、适用身份和少量具体操作步骤，让用户评价“是否看懂、是否顺手、是否符合学校实际”。路径、字段、权限、数据库和技术回归由智能体核验，不要求用户自己找技术遗漏。

### 6. 续接与收尾

首次执行本提示词时，在现有 `docs/06-开发施工与质量验收/施工记录/` 下创建 `学工核心业务四端落地进度.md`；以后更新同一记录，不反复新建总册。每个真实二级模块记录：

- 所属批次、实际模块边界及全部三级页面清单。
- 模块关联代码审计、实际流转、问题清单和经审计确定的施工顺序。
- 当前流程必需的配套项、便捷性检查结果、历史/在途单据兼容及未实施的独立扩展。
- 四端路由/页面、后端落点、适用与不适用范围。
- 当前代码基线、原有及本次改动、设计/实现/验证证据。
- 各端及链路的实际状态、缺口、阻碍及下一步准确入口。

遵守根规则的 planned/partial/implemented/verified/deliverable/deployed 含义。未提交工作区检查要注明，不标成候选 commit 已验证。模块未完成时下次继续该模块；没有安全测试环境不抹掉剩余验证，也不反复执行已经通过且未受后续改动影响的检查。

最终先说明“本次完成什么、还缺什么”，提供实际入口、关键改动、实际测试和四端验证结果、数据库/迁移/权限/旧路由影响、当前 Git 状态、下一模块。截图明确是真实测试业务、隔离样例还是原型。用户应能按完整办理过程验收，而不是代替智能体核对技术文件。

本提示词不授权自动提交、推送、部署、生产操作、删除真实数据、不可逆迁移、认证/权限核心重构或大批删除旧文件；遵守根规则中对应的明确决定要求。不得因当前任务量大静默缩减当前二级模块的三级页面。默认顺序执行，不自动创建其他用户任务或并行智能体。

现在根据续接记录和代码选择当前模块。没有记录时从第一批“请假返校”开始：先核验真实四端入口、审批条件和返校链路，然后完成该模块的适配、缺口修复、验证与收口。
