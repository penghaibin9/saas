# Codex｜前端重构与四端核心流程验收

> 与根目录 `AGENTS.md` 配套，修改前端、业务办理路径或跨端合同才读取。
> 本文是执行与验收规范，不证明现有页面、后端或测试已经实现。没有执行证据不得填 PASS。
> 核心目标：真实师生能找到事、看懂事、办完事；不是把同一张后台表格复制到四端。

## 1. 先决定这一轮要让谁办成什么

每轮在原任务记录中写一张短卡，不另外生成几十份施工文档：

| 项目 | 必须写清 |
| --- | --- |
| 业务故事 | 一位具体角色完成的一件事；与用户本轮任务一致 |
| 成功终点 | 真实业务状态与接收方结果，不是按钮出现或 HTTP 200 |
| 发起/处理/接收角色 | 实际学校角色，必要时包含企业、平台协助 |
| 正式入口 | 工作台、待办、业务列表到二/三/四级精确对象的真实路由 |
| 关联身份 | tenantId、businessId 或正式关联链、batchId/termId 等实际必需上下文 |
| 设计依据 | 用户认可的具体版本、文件/截图；没有提供时沿现有体系精修，不擅自换风格 |
| 代码依据 | 当前 SHA 下页面、client、router、服务/模型和相关 tests |
| 不变合同 | 状态机、权限/范围、租户隔离、接口、冻结文件，以及本轮不可触碰区 |
| 已知阻断 | 用户体验与真实业务阻断分开，指出一处根因影响哪些端 |
| 验证计划 | 正常、退回、失败恢复、权限负向、刷新、相关构建和浏览器路径 |

技术字段和真实入口由 Codex 查明。只有审批层级、时间窗口等真正的学校政策才需要业务方决定。

## 2. 业务主业的故事候选

以下是故事拆分建议，不是新增功能授权，也不是现有代码已通过的声明。以当前模块真实合同确定动作和终点；任务没要求的模块不施工。

| 中心 | 可选的一条核心故事 | 不能跳过的交接检查 |
| --- | --- | --- |
| 学工 | 学生请假 → 对应教师处理/退回 → 学生修改重交 → 审批完成 → 按真实规则销假/办结 | 退回原因、原单关联、下一责任人、待办变化、台账回读 |
| 学工迎新/宿舍 | 新生激活与材料办理 → 资格核验/报到 → 正式身份衔接 → 按实际制度入住 | 新生/学生身份对应、批次、缴费或绿色通道真实证据、床位占用，不能假报到/假入住 |
| 教务 | 教师成绩录入 → 审核/发布 → 学生查分 → 适用的复核/更正 → 结果留痕 | 未发布不可见、退回可修改、正式结果一致、历史变更可追溯 |
| 岗位实习 | 学生申请 → 学校/企业确认 → 适用的协议材料 → 过程记录/异常处理 → 评价成绩/归档 | 实际企业责任动作、指导关系、材料绑定、异常是否阻断下一步 |
| 毕业设计 | 选题/开题 → 成果提交 → 查重/定稿 → 答辩评分 → 成绩与归档 | 批次/导师/评委身份、退回重交、版本证据和各阶段真实状态 |

故事太长时可分可验收段，但保留同一总体目标、前后交接和剩余范围。不得把“做完一段”报告成“整个中心完成”。
系统管理只处理该故事所需的身份、角色、菜单、能力、规则等依赖；平台主管只处理相关授权或初始化。没有证据不扩成平台全面翻新。

## 3. 三种前端任务，三种边界

### 3.1 UI-only 视觉调整

只改布局、间距、色彩、排版、控件呈现和明确允许的交互，不擅自改变路由、API、角色、状态与后端规则。
验收受影响状态、分辨率和关键点击；后端本来阻断时指出证据，不能假装改好，也不能自行全面改后端。

### 3.2 前端流程重构

在既有业务语义下调整任务入口、对象工作区、返回位置、材料对照、退回重交和下一动作。
同步迁移该流程的导航、client 与深链消费者；需要直接后端修复时，先说明同一根因和影响，在授权范围内完成。

### 3.3 核心业务闭环修复

前端、后端、worker、MySQL、消息、权限和测试围绕同一阻断根因一起修；不是只隐藏按钮或新增一层兼容包装。
完成相关跨端主路径和关键异常验证，再精修视觉。与本轮无关的架构升级、模块开发、依赖大版本升级不得混入。

## 4. 四端角色矩阵

| 端 | 应当重点验证 | 不应强求 |
| --- | --- | --- |
| Staff PC | 任务直达、筛选与批量办理、材料对照、审核、结果与台账 | 把所有参数配置放到老师日常办理首屏 |
| Student PC | 长表单、材料版本、我的办理、退回修改、进度和结果 | 承担学校管理员配置 |
| Teacher Mini | 今日待办、准确对象、少输入、便捷处理、指导与异常 | 原样照搬 PC 大表格/低频复杂配置 |
| Student Mini | 高频发起、补材料、查看进度、接收反馈与确认 | 强迫手机重复 PC 的重型全量作业 |

同一事实跨端显示一致，但动作是否可用取决于角色和状态。一个端只读也是有效职责，必须验证只读而非强行赋权。

每个故事必须填：
```text
端/角色｜真实账号类型｜发起/办理/只读/不适用｜页面路径｜关键动作｜结果/对象关联｜证据
```

N/A 必须是业务职责不适用；尚未实现、无测试工具、连接失败属于缺口或 NOT_RUN。
移动端证据另分：教师 H5、学生 H5、微信构建、微信宿主交互；H5 成功不得顶替微信宿主验收。

## 5. 同一故事的最低验收集合

1. **正常办理**：从真实入口开始，用正常测试角色执行被验收的核心点击；达到真实终点，接收方能看到结果。
2. **退回修改**：在真实存在退回的环节退回，发起人读到原因、保留原单关系、修改并重交；原版本历史不丢失。无退回动作时验证实际修正路径。
3. **写后回读**：提交后读服务端，再刷新/重进；状态、附件、台账、适用的待办和统计一致；异步结果显示处理中，不抢报完成。
4. **访问拒绝**：正常角色不得执行他人/别班/别校的动作；直接调 API、猜对象/文件 ID 也拒绝，不只验证按钮隐藏。
5. **上下文隔离**：切学校、角色、批次或学期，不显示旧上下文数据；A 的慢响应不能覆盖 B，未保存输入有明确处理。
6. **失败恢复**：网络异常保留合理输入，冲突不自动覆盖；有幂等需求的命令重复提交不产生两条业务事实。
7. **精确深链**：工作台/消息/待办进入正确业务对象；刷新、返回与重新登录后的合法导航不丢所需上下文。
8. **附件和批量**：涉及材料时验证上传、扫描状态、预览/下载、业务绑定；涉及 xlsx 时验证模板、错误行、结果、权限及审计。

同一故事可以有多个相关业务 ID，但必须展示正式关联链；不能拿四端互不相关的数据凑结果。
结果验证优先用正常读取 API，必要时只读核验隔离测试库。不能直接改业务表到终态代替主流程。
外部短信、支付、对象存储、微信能力有替身时明确边界，不能据此报告真实外部集成成功。

## 6. 浏览器测试实施要求

- 先读现有 `e2e/README.md`、配置和辅助函数，复用框架；不要为了此次重构安装一套新的测试平台。
- 为每个参与角色创建独立上下文，测试数据按租户和测试故事隔离。复用登录态需验证仍是正确用户/角色/学校。
- API/seed 只准备前置数据与适用授权，不在测试请求前偷偷改状态，不给所有测试开全功能或超级权限。
- 主操作用用户可见控件完成；等待有意义的响应、状态或元素，不靠增加固定等待时间掩盖竞态。
- 优先按角色、标签、可访问名称和稳定测试标识定位；不要让测试过度绑定 CSS 层级或内部函数名。
- 浏览器通过之外还断言正确对象、状态和必要副作用；只看 toast、只看页面没报错不够。
- 改动布局后不得无审查整批更新快照；明确差异来自认可设计而非遮挡、空态或错误数据。
- 失败保留可定位的 trace、网络错误与截图；敏感信息脱敏，证据留在指定测试产物路径，不提交运行日志和真实账号数据。
- `--list` 只证明用例能被发现；源码字符串合同仅作补充；结果必须记录实际执行的节点而非工作流总名称。
- 测试环境不可用时先修可安全修复的环境问题；无法运行则报 NOT_RUN，不改成 API 调用后宣称 UI 验收通过。

## 7. 易用性检查表

这些是本项目执行准则，不是行业统计或已取得的用户测试结果。默认不能出现本轮相关的阻断性易用性问题。

| 检查 | 判定办法 |
| --- | --- |
| 入口准确 | 从待办打开的是该任务的正确对象，不是回到大列表重新找人 |
| 状态可懂 | 普通用户能看到业务中文、当前责任与阻断，不只有状态码“PENDING” |
| 下一步明确 | 完成动作后能知道交给谁/等什么；来源不明则明确未取得，不猜审批人 |
| 不重复输入 | 已知学校、学生、批次不反复选择；已填字段在失败后尽量保留 |
| 退回能续办 | 原单展示原因和修改入口，不要求另建单或找另一个系统模块 |
| 返回不丢现场 | 列表筛选、分页、滚动/选中位置按合理范围保留，身份切换不串数据 |
| 高风险可理解 | 展示对象、数量/影响、必要原因与确认，不只有浏览器原生“确定吗” |
| 移动端可操作 | 375/390/430px 下主按钮不被底栏/键盘遮挡，长中文和附件可读可用 |
| 操作可感知 | 提交中、成功、失败、冲突和部分完成不同；不可操作时解释原因 |
| 视觉有业务价值 | 首屏优先对象/动作/进度；不为漂亮堆空卡片、重复说明或弱化有效业务信息 |

每轮选本故事关键指标记录重构前后：从任务入口到目标对象的点击数、跨页次数、重复输入项、找不到下一步的节点。
没有计时实测就不报节省百分比；不预设“所有业务三步内”之类脱离风险与流程的统一指标。
“无需培训”只能作为目标；没有真实师生试用时，报告“已完成内部可用性检查”，不能替学校签署验收。

## 8. 根因与修复范围

对每个阻断先判断：前端调用/DTO、后端业务规则、状态与授权、测试前置、环境还是外部服务。
若几个端在同一错误码或服务边界失败，只修一次权威根因，并回归全部直接消费者；不四端各写一个 fallback。
后端没有 `allowedActions`/流程上下文字段时先核对已有等价合同，不强行要求数据库新增这些同名列。
共享组件一处变化触及多个中心时，挑受影响的关键消费者验证；不能靠一个页面好看证明全站无回归。

## 9. 执行顺序与门槛

| 阶段 | 应有证据 | 不等价的“假通过” |
| --- | --- | --- |
| 事实 | 当前 SHA、故事、设计版本、真实路由与调用链 | 只看旧报告或 navPlan 的 implemented |
| 修复 | 问题复现、最小完整 diff、对应回归 | 新加 wrapper/alias 或删除报错按钮 |
| 工程 | 相关 lint/test/build；后端改变时真实 MySQL 验证 | 编译成功当流程成功 |
| 业务 | 同一故事的跨角色主路径、异常分支、写后回读 | 四端各打开一页或用 API 代点主动作 |
| 体验 | 前后截图/导航路径、易用性检查结果 | 自评“10分”“顶级UI” |
| 集成 | 相应 head/base/checkout 下实际运行的必要门禁 | 用旧 SHA、skipped 或不同部署版本拼全绿 |

规则文件不会自行创建测试或启动浏览器。缺少覆盖时，Codex 应在授权任务中补测试并验证其被实际选中。
每轮只运行本轮相关最小集合，再按共享影响扩大；阶段收口/发布验收才集中验证全部核心故事，避免无变化的全仓重跑。

## 10. 给非技术负责人的验收摘要

每轮提交以下一页式结果，不让用户阅读上千行工具日志：
```text
业务结果：谁现在能顺利办完哪件事。
四端结果：Staff PC / Student PC / Teacher Mini / Student Mini 分别 PASS、FAIL、NOT_RUN 或有依据的 N/A。
关键交接：同一对象关系、退回/重交、写后回读、下一责任与待办结果。
便捷性：具体减少的绕路或重复输入；前后截图/真实路径；内部检查与师生试用分开。
工程证据：修改范围、相关用例、命令、通过/失败/跳过；MySQL、H5、微信构建、微信宿主各自状态。
风险边界：剩余阻断、未验证项、是否动后端/权限/迁移/旧路由；实际提交/推送/合并/部署状态。
下一步：一个最重要的业务动作，只有必要时请用户作业务决定或授权。
```
