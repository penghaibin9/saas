## 二、为什么会这样（根因）

1. **施工说明直接写进了界面。** 开发时为了让 AI、测试“看懂”，把“由服务端校验、不使用浏览器估算、以正式记录为准”这类工程约束写成了页面提示。
2. **“提交结果不确定”被做成了用户要处理的事。** 网络超时后，系统让用户自己点“只读核对原命令”。这一个交互模式贡献了“回读 / 原命令 / 只读核对 / 待核实 / 不会重发 / 不能证明”几百处文字。
3. **帮助中心一层叠一层。** `frontend/src/config/help/` 有 41 个文件、560KB：HelpCards → CleanHelpCards → CoreFlowHelpCards → VerifiedOverrides → V305B / V305C，正文写满权限码和状态码。
4. **后端错误原样上屏。** 435 处 `error.message` 直接展示；后端提示里有字段名（“taskId 必填”）、内部概念（“幂等重放”“投影”“名单版本”）。
5. **状态值没有中文时显示原值。** 模板里有 38 处 `|| row.status }}` 这类兜底，字典缺项时页面就露出 `PENDING_REVIEW`。

### 3.2 三条硬规则

1. **ID 不上屏。** 任何 `id`、`xxxId`、`#数字` 都不显示。对象用“课程名 + 班级 + 时间”“学生姓名 + 学号”这类方式描述。确实需要报问题时，在详情页底部放一个灰色小按钮“复制问题编号”（复制 traceId），不在正文显示。
2. **状态一律中文。** 建全局状态字典（`frontend/src/utils/` 下已有的 label 工具统一成一个）。字典缺项显示“其他状态”，**绝不显示原值**；38 处 `|| xxx.status` 兜底全部改掉。小程序、学生 PC 用同一份字典（放 `shared/contracts/`，生成到各端）。
3. **错误提示说人话。** 后端 `AppException` 的 message 是给用户看的：不出现字段名、英文、内部概念；字段错误写中文字段名（“请填写教学任务”而不是“taskId 必填”）。前端 `normalizeUiError` 增加最后一道过滤：message 里含英文标识符或禁用词时，换成按错误码映射的通用中文提示，原文只写进控制台。

### 3.3 “提交结果不确定”统一处理（替代几百处“只读核对”）

- 新建公共工具 `submitWithConfirm`（前端 PC、小程序、学生 PC 各一份同逻辑实现，放各端 `services/`）：
  1. 提交时带幂等键（现有 `clientRequestId` 机制复用）；
  2. 超时或断网时，自动用同一幂等键或业务键查询结果，最多 3 次，间隔 1s / 2s / 4s；
  3. 界面只有三种状态：“正在提交…”→“正在确认是否提交成功…”→“已提交” / “没有提交成功，请重试”。
- 删除所有“核对原命令 / 只读核对 / 结果待核实 / 等待核对结果”按钮和文案，以及每个页面各自写的 recovery 文件（如 `write-result.js`、`approval-recovery.js`、`parallel-c/*-recovery.js`、`unconfirmedWrite.js`）。
- 后端已有的幂等保护不动，只改交互。

### 3.4 帮助中心重写

- 41 个文件合并成：**每个业务模块一份 × 每个角色一节**。正文写“这件事在哪办、怎么办、办完谁处理、常见问题”。
- 不出现权限码、状态码、接口名、版本号；状态流转用中文（“草稿 → 学生确认 → 企业确认 → 学校确认 → 生效”）。
- 旧版本文件（`*V305B*`、`*V305C*`、`*Clean*` 与原版并存的、`verifiedHelpOverrides`、`legacyHelpPolicy`）合并后删除。
