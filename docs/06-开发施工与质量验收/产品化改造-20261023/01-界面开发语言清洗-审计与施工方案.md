## 二、为什么会这样（根因）

1. **施工说明直接写进了界面。** 开发时为了让 AI、测试“看懂”，把“由服务端校验、不使用浏览器估算、以正式记录为准”这类工程约束写成了页面提示。
2. **“提交结果不确定”被做成了用户要处理的事。** 网络超时后，系统让用户自己点“只读核对原命令”。这一个交互模式贡献了“回读 / 原命令 / 只读核对 / 待核实 / 不会重发 / 不能证明”几百处文字。
3. **帮助中心一层叠一层。** `frontend/src/config/help/` 有 41 个文件、560KB：HelpCards → CleanHelpCards → CoreFlowHelpCards → VerifiedOverrides → V305B / V305C，正文写满权限码和状态码。
4. **后端错误原样上屏。** 435 处 `error.message` 直接展示；后端提示里有字段名（“taskId 必填”）、内部概念（“幂等重放”“投影”“名单版本”）。
5. **状态值没有中文时显示原值。** 模板里有 38 处 `|| row.status }}` 这类兜底，字典缺项时页面就露出 `PENDING_REVIEW`。

## 三、改写规范（按业务语义改写，不做机械替换）

### 3.1 改写原则

1. **先看这句话在说什么，再决定怎么说。** 下表是常见开发词的改写方向，不是一对一替换表。同一个词在不同语境下意思不同，按语境改。
2. **意思必须不变。** 真实的业务限制、提醒和风险要保留，只换成大白话。例如“提交后不能修改”要保留；“未发现占用不代表已取得使用资格”可以改成“提交后由管理员审核”，但不能直接删掉。
3. **状态不能说错。** 特别注意：
   - “待核验 / 待核对”表示**还没核验**，不能改成“未填写”。可改成“待审核”“等待确认”等。
   - “结果尚未确认 / 待核实”表示**不知道成功没有**，不能改成“提交失败”，也不能改成“已提交”。可改成“正在确认提交结果，请稍后刷新查看”。
   - “暂无数据”只用于确实没有数据；加载失败、无权限不能写成“暂无数据”。

| 常见开发词 | 改写方向（按语境选择） |
|---|---|
| 回读、已回读正式记录 | 已保存、已更新、已刷新 |
| 原命令、命令引用、只读核对、只读刷新 | 上次提交、刷新查看结果（**保留原按钮和恢复操作**，只改名字和说明） |
| 重发、重放、幂等、不会重提 | 描述用户能感知的结果，如“不会重复提交”；纯技术说明删掉 |
| 正式事实、事实、真值 | 记录、信息、已确认的结果 |
| 服务端、后端、前端、接口、数据库、字段、枚举、权限码、令牌、缓存 | 系统；或删掉这句技术说明 |
| 门禁、闸门、原子、事务、持久化、写链、主链、链路、闭环、兜底、降级 | 删掉技术说明，保留其中真正的业务限制 |
| 投影、契约、快照版本、记录版本、冻结名单、名单版本、指纹 | 删掉，或改成“更新时间：××”“名单已锁定” |
| 生效策略、来源新鲜度、口径 | 删掉，或改成“统计范围：××” |
| 责任队列、责任接力、当前责任、下一责任 | 待办、下一步由 ×× 办理 |
| 对象、当前对象、业务对象 | 具体名词：课程、学生、申请、批次 |
| 权威、稳定（课程身份 / 工号） | 删掉修饰词 |
| 预检、预校验 | 检查 |
| 证据、证据链、证据包 | 材料、记录；管理端审计场景可保留“留痕记录” |
| 阻断、阻断项 | 必须先处理的问题 |
| 不代表、不等于、不能证明、以 ×× 为准 | 改成一句正向提示；含真实限制时保留限制 |
| 预留、兼容、旧版、演示数据、mock、占位、待施工、P0 / V2 / 第二轮等内部编号 | 删除 |
| 英文装饰标题（ACCOUNT SECURITY 等） | 改成中文或删除 |

**可以保留**：Excel、PDF、Word、二维码、学号、工号，以及管理端的“台账”“回执”。

### 3.2 硬规则

1. **内部编号不进业务正文。** 数据库 ID、`xxxId`、`#数字` 从正文移除，对象用“课程名 + 班级 + 时间”“学生姓名 + 学号”描述。**保留**：学号、工号、业务单号（如申请编号、准考证号），以及现有的问题反馈编号（如“复制问题编号”）。
2. **状态显示中文，复用现有工具。** 用各端已有的中文状态和错误展示工具（如 `frontend/src/utils/` 下的状态 label 工具、`normalizeUiError`）补齐缺失的中文。**不新建全局状态系统，不新增共享契约文件。** 不修改接口字段、状态值、权限码或错误码；只在展示层把原值换成中文。
3. **后端提示只改文字。** 后端 `AppException` 等返回给用户的 message 改成大白话、去掉字段名和内部概念；错误码、HTTP 状态、返回结构不变。断言这些文字的测试同步更新。

### 3.3 不做的事（原方案中已删除的要求）

- **不新建统一提交工具**（原 `submitWithConfirm`），不加“轮询三次后判定失败”，不删除各页面的恢复文件（如 `write-result.js`、`approval-recovery.js`、`*-recovery.js`、`unconfirmedWrite.js`）。现有提交恢复、操作记录和防重复机制全部保留，只改其中的文字。
- **帮助中心只改正文**：不合并、不删除、不改名任何帮助文件，不改变帮助匹配规则和跳转地址。
- 不修改审批流程、考勤默认值、成绩计算、角色权限、菜单结构和登录策略。
- 不改代码注释、变量名、日志。
- 不为了扫描“零命中”删掉真实业务限制。扫描结果用于定位和复查，合理保留项写明理由即可。

## 五、验收

1. **意思一致**：每批抽查改写前后，业务含义一致，真实限制没有丢；状态没有说错（见 3.1 第 3 条）。
2. **扫描复查**：`devlang_scan.py` 对本批目录复查；剩余命中逐条处理，或在 CSV“建议”列写明保留理由。不以“零命中”为硬指标。
3. **测试**：断言旧文案的测试同步改成新文案，**不允许删断言**；受影响端 `node --test`、`eslint` 通过，后端改提示的跑相关 pytest（顺序执行）。
4. **构建**：受影响端构建通过。
5. **页面检查**：能启动系统时，在真实页面检查正常、出错、无权限、结果未确认等状态的显示。环境里没有可用数据库、启动不了时，如实写“页面未验证”，不要用截图拼凑。
6. 只改文案，不要求重跑全系统业务验收。

## 六、注意事项

- 扫描是静态规则，约有 1–2% 误报（例如学生填写示例里的“CAD, PLC”）。Codex 逐条判断，误报在 CSV 的“建议”列注明“保留”。
- 只改用户看得见的字符串；代码注释、变量名、日志不在本文档范围。
- 同一句话改写时保留原有业务含义（例如“提交后不能修改”这类真实限制要保留，换成大白话）。
- 导航文案若由源头生成（如导航契约），改源头后用命令重新生成，不手改生成结果。
