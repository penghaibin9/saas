# 迁移基线重建

状态：`fixed_verified` — 2026-08-10 已修复并实测收敛为 **0 差异**。
证据产出方式：Docker MySQL 8.0（生产同款 `collation-server=utf8mb4_unicode_ci`）
真实双路径重放比对，非静态阅读、非推理。

---

## 一、修复前的问题

同一份代码，**老学校和新学校跑在不同的数据库结构上**。

| | 老学校（2026-07-14 装机后升级到 HEAD） | 新学校（全新安装到 HEAD） |
|---|---|---|
| 表数量 | 427 | 427 |
| 结构不一致的表 | \- | **245 / 427** |
| 列/索引差异 | \- | **3583 处** |

实测样例（`t_aa_archive_batch`）：老库有 `status DEFAULT 'DRAFT'`、
`created_at DEFAULT (now())`、索引 `(tenant_id, status)`；新库这些默认值全都没有，
索引退化成 `(status)`。

真实后果：依赖数据库默认值的写入，在老学校成功、在新学校 MySQL 严格模式下报
`Field 'status' doesn't have a default value` —— 这类缺陷"只在某些学校复现"。

## 二、根因

`0001_init_core_tables` 执行 `metadata.create_all()`，把**当天 ORM 里的全部表**
一次建光。而全仓有 **291 张表本来配有正式建表迁移**（带 `server_default`、带
`(tenant_id, xxx)` 复合索引）。全新安装时 0001 抢先按 ORM 把它们建了出来，
后面那些正式建表迁移一看"表已存在"就整段 `return`，里面写好的 DDL 一次都没执行。

即：**新装的学校拿到的才是降级结构**，老学校反而是对的。
（246 个迁移里有 225 个带存在性判断，正是这层兼容写法把分裂一路掩盖到今天。）

另外发现并一并修掉的隐患：两条路径都存在
`utf8mb4_unicode_ci` 与 `utf8mb4_0900_ai_ci` **混用**（裸 SQL 里
`DEFAULT CHARSET=utf8mb4` 不写 COLLATE 时，MySQL 8 给 0900_ai_ci）。
混用会让跨表字符串比较直接报错 1267。

## 三、修复内容

1. **`0001_init_core_tables` 不再抢建有正式迁移的表。**
   冻结清单 `TABLES_OWNED_BY_LATER_MIGRATIONS`（291 张）写死在迁移文件里；
   0001 只建那 133 张"全仓没有任何正式建表脚本、只能由 ORM 生成"的表。
   清单是冻结的，**不要改成运行时扫描**——那等于把时间旅行换个地方重演。

2. **新增 `20260810_schema_reconcile`**：把既有老库补齐到同一结构。
   - 差异清单一次性算好，冻结在同目录 `20260810_schema_reconcile_data.json`；
   - 幂等：每条先查 `information_schema`，已正确则跳过，在正确的库上是空操作；
   - 只补不删：不删列、不删表、不动业务数据；冗余索引会删，但避开外键依赖的索引；
   - 统一表级字符集/排序规则到 `utf8mb4_unicode_ci`（生产声明值）。

   实跑结果：老库 `排序规则统一=17 列补齐=516 新建索引=79 删冗余索引=30 失败=0`；
   新库 `排序规则统一=44 列补齐=516 失败=0`。

3. **CI 排序规则对齐生产**。此前 CI/本地用 MySQL 8 默认的 `0900_ai_ci` 建库，
   与生产的 `utf8mb4_unicode_ci` 不同，会让比对结果掺进环境噪音、结论不可信。
   `迁移库门禁` 与 `迁移升级路径收敛门禁` 均已显式 `ALTER DATABASE ... COLLATE`。

## 四、修复后的实测结果

```
迁移路径收敛 OK：老库升级结果与全新安装结果完全一致
```

- 结构不一致的表：**245 → 0**
- 列/索引差异：**3583 → 0**
- `check-migrated-schema-parity.py`：✅ 迁移库与 ORM 模型一致（424 张表）
- `alembic heads`：单 head `20260810_schema_reconcile`

## 五、常设门禁

| 门禁 | 位置 | 作用 |
|---|---|---|
| 迁移升级路径收敛 | `ci.yml` job `迁移升级路径收敛门禁` | 老库升级结果 ≠ 全新安装即红 |
| 禁止新增 create_all 迁移 | `scripts/check/check-migration-time-travel.py` | 冻结在 1 个（仅 0001），不许新增第二个 |
| 迁移库 ↔ ORM 一致 | `check-migrated-schema-parity.py` | 迁移产出与模型不得分裂 |

## 六、剩余一步（非阻断）

0001 仍对那 133 张"纯 ORM 表"使用 `create_all`。它们全仓没有任何正式建表脚本，
所以两条路径都从 ORM 生成、结果一致，当前不产生分裂。要彻底消灭时间旅行，
需要为这 133 张表各自补上显式 `op.create_table`。这是下一步优化，不阻断上线。

## 七、复现方法

```bash
docker run -d --name mig-conv -e MYSQL_ROOT_PASSWORD=root -p 33318:3306 mysql:8.0 --log-bin-trust-function-creators=1 --collation-server=utf8mb4_unicode_ci
```

```bash
docker exec mig-conv mysql -uroot -proot -e "CREATE DATABASE conv_fresh; CREATE DATABASE conv_upgraded"
```

全新库直接 `alembic upgrade head`；老库先用 `50d6a2f0`(2026-07-14) 的工作树跑
`alembic upgrade head`、再用 HEAD 跑一次；两库分别 `dump-mysql-schema.py` 后
`compare-schema-dumps.py` 比对。

注意：比 `50d6a2f0` 更早的 commit 无法重放——已实测三种断法：
`0015_excel_import_job` revision 缺失、`alembic_version.version_num` 列宽不足
33 字符、迁移链出现 2~3 个 head。
