# 小程序高频使用承载能力审计报告

- 审计日期：2026-07-13
- 审计方式：只读代码审计（后端 + miniapp 前端），未修改任何文件，未 push
- 审计范围：登录鉴权、首页聚合、待办、实习打卡、周报提交、毕业设计材料提交、教师审核、文件上传、Excel 导出
- 结论：核心提交链路（打卡/周报/审核）已具备幂等与权限隔离，达到生产可用水准；但**列表全量拉取、上传无防护、导出同步大文件**是三处会在真实学校高频使用下暴露的真实缺陷，不是文档问题。

## P0（阻断真实高频使用，必须修）

### P0-1 教师端台账列表 SQL 无 LIMIT 全量拉取 + N+1 查询
- 证据：`backend/app/modules/internship/services/internship_service.py:266-288`（`list_checkins`）、`:322-`（`list_attendance_exceptions`）、`:425` 附近（`list_weekly_reports`）
- 现象：`select(...).where(tenant_id==...)` 不带 `.limit()`，先把当前租户全部行查出来，再在 Python `for` 循环里对每一行各执行 `db.get(InternshipRecord)` + `db.get(StudentProfile)` 两次额外查询，最后在内存里做关键字过滤、数据范围过滤、切片分页。
- 影响：一学期几千名学生每日打卡，该表迅速到十万行级；教师每次刷新台账都是全表拉取 + 2N 次单行查询，随数据量线性变慢，早晚拖垮请求或超时。
- 建议：改成 SQL 层 `JOIN` + `WHERE` + `LIMIT/OFFSET`（数据范围过滤也下推到 SQL），去掉逐行 `db.get`。

### P0-2 Excel 导出复用上面的无限制列表函数，同步生成大文件
- 证据：`internship_service.py:291-313`（`export_checkins`/`export_exceptions`），内部 `list_checkins(1, 100000, ...)` 硬编码 100000 上限并直接同步 openpyxl 打包返回。
- 影响：导出请求线程内既要承受 P0-1 的全量+N+1 查询，又要在内存中拼一个可能几万行的 Excel，长耗时同步请求容易超时/占满 worker。
- 建议：导出走后台任务（Celery/线程池+轮询下载）或至少限制导出范围（按学期/班级/时间区间强制筛选），不接受无条件全量导出。

### P0-3 小程序列表页无分页/上拉加载，前端也是一次性全量请求
- 证据：miniapp 全仓搜索 `onReachBottom`/`pageSize`/`loadMore`/`hasMore` 在 `src/pages` 下零命中；`realApi.js` 中 `internshipAgreements`/`internshipLeaves`/`teacherInternshipReal`/`teacherRiskStudents` 等接口调用均未传 page/limit 参数。
- 影响：与 P0-1 互为因果——前端本来就没打算分页，后端自然也没做分页，数据量增长后小程序首屏直接变慢甚至白屏。
- 建议：前后端同步补分页协议（page/size + hasMore），列表页加上拉加载。

### P0-4 上传前无大小限制/压缩，大文件直传后端无防护
- 证据：miniapp 中 `chooseFile`/`chooseImage`/`chooseMessageFile` 调用均未传 `sizeType`/`quality` 等压缩参数，仓库内搜不到任何 `maxSize`/`fileSize`/压缩判断；上传统一走 `uni.uploadFile` → 后端 `/files/upload` 中转，未对接对象存储预签名直传。
- 影响：学校老师/学生选一个几十 MB 的材料 PDF 或高清照片会直接尝试整体上传，容易超时失败且用户看不到失败原因；毕设截止日、实习周报集中提交这类高峰期会集中冲击后端带宽和磁盘。
- 建议：前端加文件大小上限提示 + 图片压缩（`sizeType:['compressed']`）；后端/接口层评估腾讯云 COS 预签名直传（跳过应用服务器中转）。已确认 `backend/app/services/storage/cos.py` 已有真实 COS SDK 集成能力，只是当前默认走本地磁盘、且未做预签名直传改造。

### P0-5 `/files` 假上传接口与真实上传接口并存
- 证据：`backend/app/api/v1/files.py:27,47,55,60` —— `_REGISTRY: dict[str, dict] = {}` 是进程内存字典，返回的 `url` 是 `/mock-storage/{file_id}?sign=placeholder&expires=900` 占位链接；与真正落盘/落 COS 的 `app/api/v1/file.py` 的 `/upload` 并存。
- 影响：只要有任何调用方（含未来新页面）指向了这个占位路由，文件会在多 worker/重启后"丢失"或返回假地址，属于潜在的静默数据丢失风险。
- 建议：确认无业务方在用 `files.py` 的占位实现后直接下线，或改造为真实实现，不应该让两套语义不同的上传接口同时存在。

### P0-6 学工请假/服务申请页"假附件"——选完文件从未上传
- 证据：`miniapp/src/pages/student/service-apply/index.vue:104-109`：`pickFile()` 调 `uni.chooseImage`，成功回调只把 `fileName` 文案设成"已选择 1 个附件"，**没有调用任何上传接口**，选中的文件对象没有被上传或关联到提交数据。
- 影响：学生/老师以为附上了证明材料，实际提交数据里没有这个文件——这是功能性缺陷，不是性能问题，但会在真实使用中造成"证明材料丢失"的业务事故。
- 建议：补上 `uni.uploadFile` 调用并把返回的文件 ID 挂到提交表单，这是本次审计里代价最小、优先级最高的一处修复。

## P1（建议尽快做，但不阻断当前上线）

### P1-1 首页统计/待办/字典/租户配置无缓存层
- 证据：全仓无 Redis 引用，`lru_cache` 仅用于 pydantic settings 单例；`backend/app/api/v1/mobile.py` 的 `overview`/`todos` 每次都直接查库。
- 建议：给首页统计、待办计数、字典、租户品牌配置加短 TTL 缓存（Redis 或进程内 TTL cache 均可），降低高并发刷新首页时的数据库压力。

### P1-2 部分高频状态字段缺索引
- 证据：`t_weekly_report.status`、`t_risk_record.status/risk_level` 无索引；`TenantMixin`（`backend/app/models/base.py:28`）只给 `tenant_id` 建单列索引，`created_at`/`is_deleted` 无索引；教师端按状态筛选缺匹配复合索引。
- 建议：为 `(tenant_id, status)`、`(tenant_id, created_at)` 等高频查询组合补充复合索引，随下一次相关表的 Alembic 迁移一并加上。

### P1-3 毕业设计学生提交页部分按钮未包 `submitLock`
- 证据：`student/graduation/index.vue` 的 `submitProposal`/`submitFinal`/`submitRectify`/`submitAppeal` 只用各自 `xxxSubmitting` 布尔位控制 `disabled`，没有像 `choiceLock`/`changeLock` 那样包 `createSubmitLock`。
- 影响：disabled 生效前有极短时间窗口理论上可重复点击，但打卡/周报等核心链路已有 DB 唯一约束兜底，实际风险较低。
- 建议：统一改用 `createSubmitLock` 封装，保持与其他提交入口一致。

### P1-4 学生端首页部分内容仍是 mock 骨架
- 证据：`realApi.js` 的 `enrichHome`/`enrichTeacherWorkbench` 只用真实数据覆盖 `mockHome` 骨架里的 stage/todos count/metrics 等少数字段，今日课程、通知、快捷服务等大部分首页内容仍来自 mock 数据。
- 影响："首页能打开"不等于首页数据真实，学校老师/学生会看到假的课程/通知信息。
- 建议：按模块补齐真实数据源，逐步替换 mock 骨架。

### P1-5 无字典/用户信息/租户配置本地缓存
- 证据：miniapp 全仓 `setStorageSync`/`getStorageSync` 仅用于 `token`/`refreshToken`（`request.js`）和角色切换会话（`stores/session.js:118,128`）。
- 建议：对基本不变的字典数据、当前用户资料等做本地短期缓存，减少重复请求。

- 现状：`backend/app/services/storage/` 已支持本地磁盘和腾讯云 COS 双后端，平台运营端可配置+测试连接，但默认路径仍是"客户端 → 后端 → COS/磁盘"而非预签名直传。

## 已确认达标项（无需修复，供对照）

- 首页聚合：学生端 `/mobile/me/overview`、教师端 `/mobile/teacher/overview` + `/mobile/teacher/todos` 已是单次聚合请求，前端 `home/index.vue`、`workbench/index.vue` 的 `onLoad/onShow` 也确认只调用这一个聚合接口，不存在首页并发多接口的问题。
