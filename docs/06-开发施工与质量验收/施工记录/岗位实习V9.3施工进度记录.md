## 3.12 首次创建并发：实测结论与总册不同（总册 §9/§11）

**先扫底数**（全部实体的 DB 唯一约束现状）：
- **已有约束（3）**：`WeeklyReport(tenant,internship,week_number)`、`InternshipProcessReport(tenant,internship,report_type,period_key)`、`InternshipSafetyCompletion(tenant,internship,course_id)`
- **无约束（8）**：请假、补卡、变更申请、意向、知情同意、特殊备案、免修申请、学生自评

**实测结论：周报与学生自评的首次创建并发不是缺口，无需修复。** 三个 service 虽然都没接 `IntegrityError`，但都用了 `SELECT ... FOR UPDATE`；InnoDB 的间隙锁会让第二个事务阻塞、待第一个提交后重新读到该行，从而走「已存在」分支返回 **409**，既没有 500 也没有重复行。3 用例真库验证通过。

**因此没有加任何约束或异常处理**——加了就是给不存在的问题打补丁。新增的测试是**回归锁**：这份安全性来自一个看起来像普通查询的 `FOR UPDATE`，谁把它删掉都会静默重新引入竞态，有了测试就会立刻变红。

**这是总册第二次严重度偏高**（第一次是旧学生路由，见 §4 结论修正）。两次都是「报成开放漏洞、实测已有防护」。**总册的条目必须先实测再估工作量**，照单全收会把大量工时花在不存在的问题上。

**仍待核实的 8 个无约束实体**：它们的不变量是「同一时刻只能有一条**活动**记录」（如只能有一个待审批请假），普通唯一约束表达不了，需要本仓已有的 STORED GENERATED 列 + 唯一索引写法（先例见 `20260806_discipline_package11.py` 的 `active_student_id`）。**但按上面的教训，动手前必须先逐个实测它们是否已被 FOR UPDATE 挡住。**

## 3.14 约束必须 ORM 与迁移双写（差点漏掉）

测试夹具（`conftest.py`）用 ORM `metadata.create_all()` 建测试库，**不跑 alembic**。所以只写在迁移里的约束，测试库根本不会有——测试照样红，而且会误导人以为修复无效。conftest 自己的注释就警告过这种「迁移库与 ORM 库分裂」。

**做法**：约束同时写两处，且表达式逐字一致——
- 迁移：`ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED` + `create_index(unique=True)`
- 模型：`mapped_column(BigInteger, Computed("...", persisted=True))` + `__table_args__` 里的 `UniqueConstraint`

仓库另有 `scripts/check/check-migrated-schema-parity.py` 专门查这类分裂，双写也是为了让它保持绿。

## 3.21 已核实：U14 跨端计数一致性（总册 §41 的说法只对了一半）

### 基础口径：一致，销账

### 真实发现：不是口径分裂，是导出接口漏筛一个参数（未修，登记）

安全教育（课程+完成记录）、特殊备案、事故、应急预案、豁免、证据包 8 组完整列表全拉出来，
首屏「待处理数量」（6 项统计）是遍历这些已加载列表现算的——批次学生一多，首屏就跟着变慢，
且在统计数字算出来之前，前端没法只显示数字、不拉明细。

### 先查有没有别的调用方（改之前必须做）

`grep` 全仓：`get_workbench()` 只有一个调用方——路由 `GET /internship/compliance/workbench/{batch_id}`；
该路由只有一个前端调用方——`compliance.api.js` 的 `workbench()`；这个 API 又只有一个页面在用——
`InternshipComplianceView.vue`。miniapp 里同名的 `teacher/workbench` 是完全不相关的通用教师待办页
（`miniapp/src/pages/teacher/workbench`），不是这个接口。确认干净后才动手拆。

### 拆法：三层共用同一套取数/统计函数，口径锁死一致

`internship_compliance_workbench_service.py` 重构为：

- `_group_consents/_group_safety/_group_filings/_group_incidents/_group_emergency_plans/
  _group_exemptions/_group_evidence_packages`：每组明细单独一个函数（原逻辑原样抽出，不改行为）；
- `_counts()`：6 项统计**全部改 SQL `COUNT`**，不读取任何一组已加载的列表。其中「事故」和
  「证据包」两项各自有一条与角色相关的可见性规则（批次/企业级事故、批次/企业级证据包只对
  校级角色可见），原来是 Python 里 `continue` 跳过，现在原样翻译成 SQL 条件（`OR` 组合），
  不是简单套一个模板；
- `get_workbench_summary(batch_id, user)`：批次信息 + `_counts()`，首屏只调这个；
- `get_workbench_group(batch_id, group, user)`：按 Tab 单独取一组明细（`consents`/`safety`/
  `filings`/`incidents`/`exemptions`/`evidence`）；
- `get_workbench()`：**保留**给未迁移的调用方兜底，内部改成调用同一套 `_group_*`/`_counts()`
  函数——旧接口、summary、group 三条路径不可能出现"页面一个数、导出/旧接口另一个数"，
  因为它们现在是同一份代码。

路由新增（不删旧的）：

GET /internship/compliance/workbench/{batch_id}/summary    新：首屏统计

### 修复 1：导出静默丢弃 riskCode（老师会拿到比页面更多的数据）

**根因链**（三处都缺，缺任何一处都不生效）：

1. 路由 `POST /risks/export` 未声明 `riskCode` 形参 → FastAPI 静默丢弃该查询参数；
2. `export_risks()` 签名没有 `risk_code`，接不住也传不下去；
3. `list_risks()`（导出走的列表函数）**根本没有 risk_code 过滤能力**——它只是页面列表
   `list_risk_students()` 的兄弟投影，后者早就支持 `risk_code`，两边一直没对齐。

**修法**：三处补齐并串通。同时把 `list_risks()` 的 `keyword` 口径也对齐成
「姓名**或学号**」（原来只匹配姓名）——页面一直是姓名或学号，导出用学号搜会得到 0 条。
当前前端未暴露关键字搜索框，属尚不可达的暗坑，一并按同一口径修掉，避免将来加个搜索框
就踩雷。

**前端无需改动**：`InternshipRiskView.exportFn()` 早就把 `riskCode` 一起传了
（`{ ...this.filters, batchId }`），漏的确实只在后端——这也解释了为什么这个 bug 能长期
存在而没人发现：前端看起来完全正确。

**回归锁** `test_internship_v93_risk_count_cross_surface.py`（22 用例全绿）：

- **16 种筛选组合参数化**（无筛选 / 6 种 risk_code 含不存在值 / 3 种等级 / 3 种状态 /

### 复审发现 4：我自己写的前端有一个组件用法错误（自查，已修）

`AppInlineAlert` 的 `type` validator 只接受 `info|success|warning|danger`，我第一版写了
`type="error"`——不在枚举内，会渲染成没有样式的 `is-error`，红色警示直接消失。

**同一文件里原本就有一处同样的错误**：审计持久化异常告警（`auditHealth.healthy === false`）

### 复审发现 5：加载中/加载失败时，表格在骗人（自查，已修）

懒加载后，明细还没到达时 8 张表格仍然渲染「暂无知情任务 / 暂无特殊备案 / 暂无事故记录…」。
**系统其实还不知道有没有数据，却告诉老师"没有"**；请求失败时同样显示"暂无"。
合规台账是要拿去应付检查的，这种"没查到"被显示成"没有"，比慢危险得多。

抽出 `showEmpty(list)`：仅当 `!groupLoading && !groupError && 列表为空` 才显示空态文案，
8 处统一改用。失败横幅同时补了**重试按钮**（`AppInlineAlert` 的 `actions` 插槽），
不再需要老师切走再切回来才能重试。

### 复审发现 6：切批次时的竞态会把上一个批次的台账并进当前视图（自查，已修）

`ensureGroupLoaded()` 原来直接把响应 merge 进 `this.workbench`，不校验这次响应是否还
属于当前这一轮。老师快速切批次时，**在途的旧批次分组请求**回来后会被合并进新批次的视图——
合规台账串批次，是会导致误判的。

加 `loadSeq` 轮次令牌：`load()`（含"未选批次"的早退路径）先自增使所有在途请求作废；
分组响应回来时比对 `loadSeq` 与 `batchId`，不属于当前轮次的直接丢弃，且不去动
`groupLoading`（交给接手的那一轮管理）。

顺带修了一个更小的：切到「已加载过的 Tab」或「总览」时走的是提前 return 分支，
没有清 `groupError`，导致老师会在一个数据完全正常的 Tab 上看到别的 Tab 的报错横幅。
