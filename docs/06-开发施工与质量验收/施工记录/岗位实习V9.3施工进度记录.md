## 3.12 首次创建并发：实测结论与总册不同（总册 §9/§11）

**先扫底数**（全部实体的 DB 唯一约束现状）：
- **已有约束（3）**：`WeeklyReport(tenant,internship,week_number)`、`InternshipProcessReport(tenant,internship,report_type,period_key)`、`InternshipSafetyCompletion(tenant,internship,course_id)`
- **无约束（8）**：请假、补卡、变更申请、意向、知情同意、特殊备案、免修申请、学生自评

**实测结论：周报与学生自评的首次创建并发不是缺口，无需修复。** 三个 service 虽然都没接 `IntegrityError`，但都用了 `SELECT ... FOR UPDATE`；InnoDB 的间隙锁会让第二个事务阻塞、待第一个提交后重新读到该行，从而走「已存在」分支返回 **409**，既没有 500 也没有重复行。3 用例真库验证通过。

**因此没有加任何约束或异常处理**——加了就是给不存在的问题打补丁。新增的测试是**回归锁**：这份安全性来自一个看起来像普通查询的 `FOR UPDATE`，谁把它删掉都会静默重新引入竞态，有了测试就会立刻变红。

**这是总册第二次严重度偏高**（第一次是旧学生路由，见 §4 结论修正）。两次都是「报成开放漏洞、实测已有防护」。**总册的条目必须先实测再估工作量**，照单全收会把大量工时花在不存在的问题上。

**仍待核实的 8 个无约束实体**：它们的不变量是「同一时刻只能有一条**活动**记录」（如只能有一个待审批请假），普通唯一约束表达不了，需要本仓已有的 STORED GENERATED 列 + 唯一索引写法（先例见 `20260806_discipline_package11.py` 的 `active_student_id`）。**但按上面的教训，动手前必须先逐个实测它们是否已被 FOR UPDATE 挡住。**

## 3.14 约束必须 ORM 与迁移双写（差点漏掉）

测试夹具（`conftest.py`）用 ORM `metadata.create_all()` 建测试库，**不跑 alembic**。所以只写在迁移里的约束，测试库根本不会有——测试照样红，而且会误导人以为修复无效。conftest 自己的注释就警告过这种「迁移库与 ORM 库分裂」。

**做法**：约束同时写两处，且表达式逐字一致——
- 迁移：`ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED` + `create_index(unique=True)`
- 模型：`mapped_column(BigInteger, Computed("...", persisted=True))` + `__table_args__` 里的 `UniqueConstraint`

仓库另有 `scripts/check/check-migrated-schema-parity.py` 专门查这类分裂，双写也是为了让它保持绿。

## 3.18 已完成卡：批次二 · MySQL 索引审计（只测量不改造）

对实习域 43 张表跑 `information_schema.statistics` 盘点，并与 ORM 声明逐条比对。

### 核心发现：ORM 声明了 49 个索引，真实库一个都没建

涉及 13 张表。其中**7 张表在真实库里只有主键，没有任何二级索引**（连 `tenant_id` 都没有）：

`t_internship_compliance_exemption` / `t_internship_consent` / `t_internship_emergency_plan` /
`t_internship_enterprise_inspection` / `t_internship_remuneration_record` /
`t_internship_safety_course` / `t_internship_special_filing`

**根因**：迁移 `0131_internship_p2_compliance.py` 的 `_create()` helper 只建列和唯一约束，
**从不调用 `op.create_index`**。ORM 里写的 `index=True` 和 `Index(...)` 全部落空。

### EXPLAIN 实测（不是推断）

| 查询 | type | possible_keys | key |
|---|---|---|---|
| 知情同意 create_pending 的查重+加锁查询 | ALL | NULL | NULL |
| 特殊备案 create 的查重+加锁查询 | ALL | NULL | NULL |
| 合规豁免 列表/评估查询 | ALL | NULL | NULL |

全表扫描，**连可用索引都没有**。

### 这条与 §3.14 是同一个陷阱的两个方向

§3.14 记的是「只写迁移、没写 ORM」→ 测试库没有约束。
这次是反过来：「只写 ORM、没写迁移」→ **真实库**没有索引。

**由此带来一个必须记住的测量偏差**：测试夹具用 `create_all()` 建库（**有**这些索引），
真实库走 alembic（**没有**）。所以 §3.17 里「知情同意靠间隙锁挡住了并发」这个结论，
是在**有索引**的测试库上测到的；真实库没有索引时，InnoDB 要扫全表加锁，
挡是能挡住（锁得更狠），但代价完全不同。**并发结论在两种库上不能互相外推。**

### 不在本批次建索引

按开工说明：候选索引必须先 `EXPLAIN FORMAT=JSON` 证明有效才能建。当前这 7 张表数据量都是
0～个位数，建索引对今天的体感为零；真正要建是后面性能批次的事，且应与「补齐 0131 漏掉的
索引」一起做成一条独立迁移。本卡只交现状表。

## 3.19 已完成卡：批次二三个首次创建竞态修复（甲方指令：真实学校在用，必须修）

§3.17 测出的三个缺口全部修完。手法与上一批请假/补卡完全一致，不新造第二套机制。

### 不变量与生成列表达式（与各 service 的去重谓词逐条对齐）

| 实体 | 活动状态谓词 | 生成列 | 唯一索引 |
|---|---|---|---|
| 变更申请 | `status='PENDING'` | `active_pending_internship_id` | `(tenant_id, 该列)` |
| 意向 | `status IN ('DRAFT','SUBMITTED')` | `active_record_id` | `(tenant_id, 该列)` |
| 合规豁免 | `status='PENDING_REVIEW'` | `active_pending_internship_id` | `(tenant_id, 该列, check_code)` |

**豁免为什么只锁 PENDING_REVIEW 不含 APPROVED**：已批准的豁免会随 `valid_until` 过期，
过期后学校应当能重新申请；而 MySQL 生成列必须确定性、不能引用 `NOW()`，"是否过期"进不了
约束。已生效豁免的重复申请改由 service 层显式校验拦截——那本来就不是竞态（已有行是可见的），
数据完整性由唯一索引兜底。两种"已存在"给不同提示，因为老师该做的事不同。

### service 层三处同步改造

1. **豁免原本连查重都没有**，补 `_assert_no_active_exemption()`；
2. 三个创建函数的 `flush()` 与 `commit()` **双包** `IntegrityError` → 转成业务 409。
   §3.13 踩过的坑：`db.add(); db.flush()` 这步 INSERT 就已发出，唯一约束在 flush 时就拒绝，
   只包 commit 的话输家照样拿 500；
3. 串行提示与并发提示抽成同一个常量（`_DUP_*_MSG`），避免将来改一处漏一处——
   老师不该因为"手快了一点"就看到两种不同的故障说明。

### 死锁一并消失，没有加重试机制

§3.17 记录的豁免 MySQL 死锁(1213)，**修完竞态后自动消失**（修复后 5 轮 0 次，撤回后 4 次）。
根因就是 §3.18 那条：这张表当时**一个索引都没有**，InnoDB 只能全表扫描加锁，两个线程的
加锁顺序不定就互等。有了唯一索引之后加锁点唯一且确定，冲突退化成干净的"输家拿 409"。

**所以没有加死锁重试**——那会是给一个已经不存在的问题打补丁。这也再次说明 §3.18 的索引
缺失不只是性能问题。

### 验证证据（真实 MySQL 独占库）

  - 还原后六个文件逐个 md5 校验与备份一致
- 迁移 `20260814_ix_first_create`：Docker 空库跑完整链到 head，三个唯一索引经
  `information_schema` 核对建成；`downgrade -1` 干净拆除（索引数 3→0）
- **脏数据守卫实测**：手工造出同一实习记录两条 PENDING 变更申请后再跑迁移，
  迁移**拒绝执行**并打印冲突分组 `[(1, 999, 2)]`，**没有删任何数据**，版本不前进；
