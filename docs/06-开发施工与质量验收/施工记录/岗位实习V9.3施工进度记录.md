## 3.1 已完成卡：事故上报幂等键 DB 唯一约束（总册 §10）

**问题（CONFIRMED-CODE）**：`internship_incident_service.report_incident()` 用应用层「先 SELECT 查重、查不到再 INSERT」保幂等，而 `InternshipIncident.idempotency_key` 只有普通索引、无唯一约束。并发可双双穿透；且 severity=HIGH/CRITICAL 会派生 `RiskRecord`、每次上报写审计，一次穿透同时造出重复事故 + 重复风险 + 重复审计。本项目其它幂等写入方（`uk_aa_status_change_idem` / `uk_campaign_tenant_idem` / `uk_affairs_job_idem`）早已带同款约束，岗位实习事故是唯一漏网的。

**改动**：
- `backend/app/models/internship_compliance.py`：加 `UniqueConstraint("tenant_id","idempotency_key", name="uk_ix_incident_idem")`
- `backend/alembic/versions/20260813_internship_incident_idem_unique.py`（新建，down_revision=`20260810_grad_audit_text`，保持单头）：历史重复行**不删**，改写较晚行的键为 `#dup<id>` 变体后建约束；带事后残留校验
- `backend/app/modules/internship/services/internship_incident_service.py`：INSERT 包 `IntegrityError` 处理，并发输家返回幂等结果或 409，禁止 500

**施工中发现并修正的自身 bug**：迁移初版用 `LEFT(CONCAT(key,'#dup',id), 80)`，接近 80 字符上限的长键会把 `#dup` 后缀截没，改写后依然重复、`ALTER TABLE` 真实报 1062。真 MySQL 影子表探针抓出，改为「先按后缀长度截原串再拼接」并加残留组校验。**未跑探针就提交的话，这个迁移会崩在客户现场。**

**验证证据**（真实 MySQL 8.0.46，非 SQLite）：
- 新增 `backend/tests/test_internship_v93_incident_idempotency_concurrency.py` 3 用例：串行幂等 / 2 线程同键并发 / 5 线程重试风暴
- **反证有效性**：临时撤掉唯一约束后，两条并发用例立即失败（「同一幂等键造出了 N 条事故事实」），串行用例仍通过——证明测试确实在测约束，不是碰巧绿

## 3.2 已完成卡：巡访计划并发（总册 §13）

**问题（CONFIRMED-CODE）**：`transition()` / `update_visit_plan()` 都是「读 status → 校验 → 改 → Python 里 version+1 → commit」，无行锁无版本条件。`version` 只是普通列，模型未配 SQLAlchemy `version_id_col`，所以自增的 version 只是记录了冲突而没有阻止冲突。两个教师并发 START/CANCEL 双双通过校验，后提交者静默覆盖。

**改动**：两个入口都改走项目既有 `versioned_update`（`UPDATE ... WHERE version=读到的版本 AND status=读到的状态`）。`expectedVersion` 保持可选——PC 端 `guidance-visit.api.js` 目前不传，强制要求会直接打断页面；正确性由条件更新保证，客户端传了则额外做过期校验。

**施工中发现并修正的自身 bug 两个**：
1. `_apply()` 直接改 ORM 实例，autoflush 会在条件更新执行前把改动无条件落库——输家拿到 409 但数据已被它写进去。改为纯函数 `_resolved_values()`，编辑路径全程不碰实例。
2. 首版测试只用 barrier 同步线程**起跑**，先跑完的线程提交后另一个会读到新版本，两次先后保存都成功本属正确行为，断言等于没测。改为断言真正的不变量：**两个教师都在 version=0 时打开页面，不能都保存成功**（双方显式带 expectedVersion=0）。

**验证证据**（真实 MySQL 8.0.46）：5 用例 + 事故 3 用例合跑 **8 passed**；撤掉 `transition` 修复后 2 条并发用例立即变红。反证脚本这次带了 `assert 替换模式命中`——上一轮就是因为脚本静默没匹配却照常打印"已撤销"，让我误判了一整轮。

## 3.4 已完成卡：企业考察租户边界 + 审核并发（总册 §14，并发现总册未提的跨租户写）

**总册只说缺 version/lock。实际核验发现更严重的问题：跨租户写。**

**问题（CONFIRMED-CODE，反证已验）**：
- `create()` 直接把请求里的 `companyId` 存进去，不校验企业归属；路由层（`internship_compliance.py:112`）只查 `internship.enterprise.inspection.manage` 权限，不查归属。
- `review()` 用裸 `db.get(EmpCompany, x.company_id)` 取企业并改写 `access_valid_until`（企业还能不能接收实习生的准入事实），同样无租户校验。
- 结果：**A 校管理员用自己合法的权限，可以改掉 B 校某企业的准入有效期。**
- 另有总册指出的并发缺口：`submit()` / `review()` 均为 `db.get → 查状态 → 改 → commit`，两人同时审可一个 APPROVE 一个 REJECT 双双成功，准入事实取决于谁晚提交。

**改动**：
- 引入项目既有 `app.core.tenant_scoped.tenant_get`（他校命中返回 None，不泄露存在性），`create()` 校验企业与批次归属。
- `review()` 落库前**二次确认**企业归属——只在创建处校验的话，归属校验上线前的历史脏数据仍能在下一次审核时改掉他校准入。这是纵深防御，不是重复代码。
- `submit()` / `review()` 改走 `versioned_update` 条件更新（版本 + 期望状态），企业准入更新与考察结论保持同一事务。

**验证证据**（真实 MySQL）：新增 `test_internship_v93_enterprise_inspection_guards.py` 4 用例（创建时拒绝他校企业 / 历史脏数据审核不得改他校准入 / 本校正常审核确实写入准入 / 并发 APPROVE+REJECT 单赢家且结论与准入自洽）→ **4 passed**；撤掉租户校验后 **2 条立即变红**，证明跨租户写真实可复现。反证脚本带 `assert 模式命中`。

### V93-02 结论修正：总册对旧路由的风险定性偏高

总册 §7/§8 称旧 route 可让 `explicit context` 被绕开，暗示这是越权/覆盖写风险。**逐函数核验后此定性不成立**：

- 真实调用链是「页面 → `miniapp/src/services/studentApi.js`（门面）→ 分流」。`internshipApi.js` 里 canonical `/context/*` 函数确实已建好，但门面把 leave/makeup/application/plan/agreement/self-eval 的写操作**仍分流到 legacy `real.*`**——canonical 入口建好了没接上（这一条总册没写出来，比总册描述更值得记）。
- 但 legacy 链**并非漏洞**：
  - `expectedVersion` 校验在 service 层（如 `internship_student_eval_service.py:194` `_expected(..., required=True)`），新旧路由都强制生效，没有被绕过。
  - 「回退到当前实习记录」的 `resolve_student_internship_context`（`internship_record_resolver.py:144-175`）是 **fail-closed** 的：多条进行中 → 写操作抛 `NEED_SELECT` 拒绝，不会静默挑一条；0 条进行中 / 已归档 / 批次禁写 → 一律 `DATA_CONFLICT` 拒绝。

**因此重新定性**：双写链并存是**架构债**（两套入口需同时维护，将来易改漏一边），不是今天会出事的正确性 bug。优先级从 Tier1 下调，排在 VisitPlan / Enterprise Inspection 并发锁之后。这条修正的意义在于：总册其余「NOT SEALED」条目同样需要逐条核验后再定性，不能照抄严重度。
