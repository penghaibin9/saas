## 3.12 首次创建并发：实测结论与总册不同（总册 §9/§11）

**先扫底数**（全部实体的 DB 唯一约束现状）：
- **已有约束（3）**：`WeeklyReport(tenant,internship,week_number)`、`InternshipProcessReport(tenant,internship,report_type,period_key)`、`InternshipSafetyCompletion(tenant,internship,course_id)`
- **无约束（8）**：请假、补卡、变更申请、意向、知情同意、特殊备案、免修申请、学生自评

**实测结论：周报与学生自评的首次创建并发不是缺口，无需修复。** 三个 service 虽然都没接 `IntegrityError`，但都用了 `SELECT ... FOR UPDATE`；InnoDB 的间隙锁会让第二个事务阻塞、待第一个提交后重新读到该行，从而走「已存在」分支返回 **409**，既没有 500 也没有重复行。3 用例真库验证通过。

**因此没有加任何约束或异常处理**——加了就是给不存在的问题打补丁。新增的测试是**回归锁**：这份安全性来自一个看起来像普通查询的 `FOR UPDATE`，谁把它删掉都会静默重新引入竞态，有了测试就会立刻变红。

**这是总册第二次严重度偏高**（第一次是旧学生路由，见 §4 结论修正）。两次都是「报成开放漏洞、实测已有防护」。**总册的条目必须先实测再估工作量**，照单全收会把大量工时花在不存在的问题上。

**仍待核实的 8 个无约束实体**：它们的不变量是「同一时刻只能有一条**活动**记录」（如只能有一个待审批请假），普通唯一约束表达不了，需要本仓已有的 STORED GENERATED 列 + 唯一索引写法（先例见 `20260806_discipline_package11.py` 的 `active_student_id`）。**但按上面的教训，动手前必须先逐个实测它们是否已被 FOR UPDATE 挡住。**

## 3.13 已完成卡：请假/补卡首次创建并发（总册 §9、§11 —— 这次总册是对的）

## 3.14 约束必须 ORM 与迁移双写（差点漏掉）

测试夹具（`conftest.py`）用 ORM `metadata.create_all()` 建测试库，**不跑 alembic**。所以只写在迁移里的约束，测试库根本不会有——测试照样红，而且会误导人以为修复无效。conftest 自己的注释就警告过这种「迁移库与 ORM 库分裂」。

**做法**：约束同时写两处，且表达式逐字一致——
- 迁移：`ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED` + `create_index(unique=True)`
- 模型：`mapped_column(BigInteger, Computed("...", persisted=True))` + `__table_args__` 里的 `UniqueConstraint`

仓库另有 `scripts/check/check-migrated-schema-parity.py` 专门查这类分裂，双写也是为了让它保持绿。

## 3.11 反证方法论（今晚栽了两次，务必照做）

并发修复的「反证」只有满足两个条件才算数，缺一条就会给出假绿：

1. **撤销脚本必须带 `assert 模式命中`**。首版脚本字符串没匹配上却照常打印「已撤销」，我据此误判了一整轮——以为代码有问题，其实文件根本没被改。
2. **必须撤到真正的原始实现，不能只撤一半**。投诉那张卡我只去掉了条件更新，却留下显式的 `expectedVersion` 过期校验；两个线程都传 0 时后读的那个被显式校验挡下并 409，「单赢家」表面成立，**条件更新有没有都绿**。正确做法是 `git show HEAD:<path> > <file>` 取原文件。

推论：**测试写完先证明它会红，再证明它变绿**。顺序反了就是在给自己发合格证。

### V93-02 结论修正：总册对旧路由的风险定性偏高

总册 §7/§8 称旧 route 可让 `explicit context` 被绕开，暗示这是越权/覆盖写风险。**逐函数核验后此定性不成立**：

- 真实调用链是「页面 → `miniapp/src/services/studentApi.js`（门面）→ 分流」。`internshipApi.js` 里 canonical `/context/*` 函数确实已建好，但门面把 leave/makeup/application/plan/agreement/self-eval 的写操作**仍分流到 legacy `real.*`**——canonical 入口建好了没接上（这一条总册没写出来，比总册描述更值得记）。
- 但 legacy 链**并非漏洞**：
  - `expectedVersion` 校验在 service 层（如 `internship_student_eval_service.py:194` `_expected(..., required=True)`），新旧路由都强制生效，没有被绕过。
  - 「回退到当前实习记录」的 `resolve_student_internship_context`（`internship_record_resolver.py:144-175`）是 **fail-closed** 的：多条进行中 → 写操作抛 `NEED_SELECT` 拒绝，不会静默挑一条；0 条进行中 / 已归档 / 批次禁写 → 一律 `DATA_CONFLICT` 拒绝。

**因此重新定性**：双写链并存是**架构债**（两套入口需同时维护，将来易改漏一边），不是今天会出事的正确性 bug。优先级从 Tier1 下调，排在 VisitPlan / Enterprise Inspection 并发锁之后。这条修正的意义在于：总册其余「NOT SEALED」条目同样需要逐条核验后再定性，不能照抄严重度。
