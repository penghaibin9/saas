### #1【P0】PC 管理端硬编码 mock 身份

- **复现步骤**：demo-school/admin 登录 → 顶栏正常显示"陈管理/演示职业技术学校/学校管理视角"（恰好和 mock 常量相似，不易察觉）→ 不刷新页面，退出登录后改用 sandbox-school/teacher2 登录 → 工作台仍显示"你好，学校管理员"「演示职业技术学院」「25 个模块」「学校管理视角」，与真实登录的王老师/体验沙箱学校/辅导员视角完全不符。
- **证据**：`sessionStorage` 中 JWT 已正确是 teacher2/COUNSELOR，但页面文案未变；`traceId` 确认 `/api/v1/auth/login` 已 200 返回正确身份。
- **根因**：`frontend/src/security/auth/auth.context.js` 是遗留的纯前端 mock 认证上下文（文件顶部注释自述"当前为纯前端 mock，不接真实认证后端"），`state.auth` 初始化为写死的 `MOCK_AUTH`（displayName: 学校管理员 / schoolName: 演示职业技术学院 / roles: [SCHOOL_ADMIN]），从未与真实 JWT 同步。该模块被 13 个文件依赖，包括 `SecurityWatermark.vue`（顶栏防泄漏水印）、`audit-event.helper.js`（前端审计事件的 operatorName/operatorId）、`route.guard.js`/`button.guard.js`/`upload.guard.js`/`download.guard.js`（会话有效性判断）。
- **影响面核实**：
  - `SecurityWatermark.vue`、`audit-event.helper.js` 的 operatorName/operatorId/schoolName 全部来自这个假数据 → 水印失去追溯意义。
  - `audit-event.helper.js` 经代码核验确认是**纯前端内存队列，不落库、不接真实 API**（"当前仅生成前端事件对象并入内存队列...sendAuditEventToBackend 为预留"），后端真实审计（`app/services/audit_log.py`）走的是服务端 `get_current_user` 真实校验，**不受此 bug 影响**（已在学工看板"操作审计入口"实测确认，见 §7）。
  - `route.guard.js`/`button.guard.js` 只用 `isAuthenticated()/isSessionExpired()`（判断是否登录/超时），不读身份字段，客户端软门禁始终"已登录"，真正鉴权仍在后端 403，**不构成越权**，但会话超时的前端提示不准。
- **修复**：
  - `frontend/src/services/http/client.js`：`currentUserFromToken()` 补充返回 `loginName`/`tenantName`（此前只解出 userId/realName/userType/currentRoleCode/tenantId）。
  - `frontend/src/security/auth/auth.context.js`：新增 `syncAuthFromRealToken()`，在 `getAuthContext()`、`isAuthenticated()` 每次调用时用真实 token 覆盖身份字段（userId/username/displayName/roles/tenantId/schoolId/schoolName），无 token 时清空。MFA/强制改密/会话超时时间等后端尚未提供的字段维持原 mock 占位，未伪造。挂在读取侧同步而非要求 `client.js` 反向 import 通知，避免循环依赖。
- **测试结果**：
  - `npm run build` 通过。
  - 真实点击复测：demo-school/admin 登录（"你好，陈管理"/"演示职业技术学校"，与之前的 mock 巧合值肉眼可辨差异）→ 不刷新页面，退出后登录 sandbox-school/teacher2 → 页面正确变为"你好，王老师"「体验沙箱学校」「辅导员视角」「18 个模块」（模块数正确从 25 降到角色应有的 18），文案不再残留上一账号。

### #2【P0】并发 401 刷新竞态导致误踢下线

- **复现步骤（后端）**：拿同一个 refreshToken 并发发两次 `/api/v1/auth/refresh`：第一个 200 拿到新 token，第二个 401「refreshToken 无效或已使用，请重新登录」（后端设计就是一次性轮换，接口 summary 明确写"refreshToken 一次性轮换"）。
- **根因**：`frontend/src/services/http/client.js` 的 `tryRefresh()` 无任何去重/单飞机制。页面一旦有多个请求同时因 access token 过期收到 401（真实场景：仪表盘首屏并行发起多个业务请求，恰好在 token 过期节点触发），每个请求各自调用 `tryRefresh()`，都读到同一个（尚未轮换的）refreshToken 并发出真实网络请求。只有最先到达后端的一个成功换到新 token，其余因 refreshToken 已被消费而 401，其 catch 分支执行 `_holdTokens('', '')` **清空了刚刚由另一个并发调用换到的合法新 token**，随后触发 `_redirectToLogin()`，用户被强制踢回登录页——即便会话其实仍然有效。
- **修复**：`tryRefresh()` 增加模块级 `refreshPromise` 单飞缓存，并发调用共享同一个 in-flight Promise，只真正发起一次 `/auth/refresh` 请求，全部并发调用等待同一个结果（一起成功或一起失败），消除竞态。
- **测试结果**：
  - 真实浏览器验证：动态 `import('/src/services/http/client.js')` 拿到运行中应用的同一个模块单例，把 `state.token` 替换为一个后端会判 401 的假值（refreshToken 保留真实有效值不变），并发发起 3 个 `request('/auth/me')`；修复前（代码核验+后端并发 curl 复现）会有 1 个成功 2 个失败并清空登录态；修复后 3 个请求全部 `OK`，`getToken()` 仍是一个有效 JWT，`read_network_requests` 确认整个过程只有 **1 次** `POST /api/v1/auth/refresh`。

### #3【P1】导出下载走 window.open 丢失鉴权

- **复现步骤**：sandbox-school/teacher2 登录 → 学工看板 → 点击「导出 Excel 台账」→ 浏览器整个标签页跳转到 `http://127.0.0.1:5173/api/v1/export/tasks/2/download`，页面显示裸 JSON：`{"code":401001,"bizCode":"UNAUTHORIZED","message":"未提供认证令牌"}`，用户拿不到文件。
- **根因**：`studentAffairsB.api.js#exportProfileLedger()`（以及 `services/http/adapters.js` 的另一处凭证回执导出）走「先建异步导出任务、再单独下载」模式，返回 `{filename, downloadUrl}` 而非 `{contentBase64}`；共享组件 `AppExportButton.vue` → `utils/xlsxDownload.js#downloadXlsxFromApi()` 对 `downloadUrl` 分支用 `window.open(url, '_blank')` 触发下载。后端 `download_export`（`backend/app/api/v1/import_export.py`）用 `Depends(require_staff)` 强制 `Authorization: Bearer` 鉴权，**无 query token / Cookie 后备通道**，普通浏览器导航（`window.open`）不可能携带自定义 header，必然 401。
- **修复**：`utils/xlsxDownload.js` 新增 `downloadAuthedUrl()`，downloadUrl 分支改为带 `Authorization: Bearer` 的 `fetch` 取 blob 再触发保存，失败自弹 toast；保持 `downloadXlsxFromApi` 原有同步、不抛异常的签名，不强迫其余 25+ 处 base64 调用方改成 `await`（避免同步异常变成未处理 rejection，扩大影响面）。
- **测试结果**：`npm run build` 通过。真实点击复测：同一个「导出 Excel 台账」按钮，`GET /api/v1/export/tasks/3/download` 返回 **200 OK**，页面停留在学工看板未再跳转到错误页。

### #4【P1】顶部 Toast 遮挡顶栏按钮点击

- **复现步骤**：登录后顶部出现"✓欢迎，陈管理"成功提示条，恰好与顶栏右上角(视角切换/待办/帮助/退出登录)同一屏幕区域重叠；`document.elementFromPoint` 命中的是 `.app-toast__item`（`pointer-events:auto`）而不是按钮本身，点击「退出当前登录」被 Toast 吞掉，无任何请求发出。
- **根因**：`AppToast.vue` 的 `.app-toast` 容器 `top: var(--space-5)`(20px)，恰好与 `BasePortalLayout.vue` 固定 56px 高的顶栏(`.bpl-topbar`)重叠；容器本身 `pointer-events:none` 但每条 toast item 是 `pointer-events:auto`（要支持点击叉号关闭），在它可见的这段时间内会挡住底下的顶栏按钮。
- **修复**：`.app-toast` 的 `top` 改为 `calc(56px + var(--space-3))`，让 toast 出现在顶栏下方，不再与顶栏控件重叠。
- **测试结果**：修复前 `document.elementFromPoint(顶栏按钮中心)` 命中 toast；修复后命中按钮本身（`sameEl:true`）。真实点击复测「退出当前登录」，`POST /api/v1/auth/logout` 200，成功跳回登录页。

### #5【P1】请假记录双状态列分裂 — 学生自视图两条路径

- **复现步骤**：demo-school/student 登录学生 PC 门户 → 「我的档案」「我的申请」正确显示 2 条请假记录（PERSONAL/PENDING_REVIEW、SICK/APPROVED）→ 切到「学工事务」「请假销假」Tab，记录列表显示"暂无请假记录"。
- **证据**：`GET /api/v1/portal/affairs/leave` 返回 `{"items":[]}`；同一时刻 `GET /api/v1/portal/affairs/applications` 返回这 2 条完整记录。直查 MySQL `t_cs_leave` 确认这 2 条记录只有 `cs_student_id` 有值，`student_id`/`affairs_status` 均为 NULL。
- **根因**：`t_cs_leave` 表历史遗留列 `cs_student_id`+`status`（经 `t_cs_service_student` 中转关联）与 13A-P2 新增列 `student_id`+`affairs_status`（直连 `t_student_profile.id`）并行存在（模型注释自述"P0 §4.2 集成①"）。当前真实提交入口分两条：
  1. 学生 PC 门户「学工事务·请假销假」的"提交请假"按钮走 `campus_service_apply` 通用事务申请，只写 `cs_student_id`；
  2. `affairs_leave_service.py` 的 13A 范式请假闭环走 `student_id`+`affairs_status`，反而把 `cs_student_id` 写成哨兵值 `0`。
  - `mobile_student_service.py#my_applications()`（「我的申请」用）只按 `cs_student_id` 查，漏掉走 13A 新链路创建的记录；
  - `mobile_affairs_service.py#leave_my()`（「请假销假」页用）只按 `student_id`+`affairs_status IS NOT NULL` 查，漏掉走旧链路创建的记录。
  两个查询各自只认一半，导致同一学生的请假记录在两个页面显示不一致。
- **修复**：两处查询都改为「`student_id` 命中 **或** 按 `student_no`/姓名解析出的 `cs_student_id` 命中」的 `OR` 条件，状态展示统一用 `affairs_status or status` 兜底；`leave_my` 新增按需解析 `CsServiceStudent` 分支（此前完全不查这张表）。
- **测试结果**：
  - 独立 `:8010` 后端实例校验（同一份 MySQL 开发库，未重启被另一会话占用的 :8000）：`GET /api/v1/portal/affairs/leave`（demo-school/student）从 `items:[]` 变为正确返回 2 条记录；`GET /api/v1/portal/affairs/applications` 回归无异常。
  - 新增回归测试并跑通：`test_leave_visible_via_old_cs_student_id_link`（`backend/tests/test_portal_affairs.py`）、`test_mb1b_leave_my_sees_old_cs_student_id_link`（`backend/tests/test_affairs_mobile.py`），分别构造只挂 `cs_student_id` 的老式记录，验证 `/portal/affairs/leave`、`/portal/affairs/applications`、`/mobile/affairs/leave/my` 三个端点都能看到。真实执行命令：`.venv/Scripts/python.exe -m pytest tests/test_portal_affairs.py tests/test_affairs_mobile.py -v`（MySQL 真库 `student_lifecycle_test`），结果 `1 failed, 15 passed, 435 warnings in 582.74s`——失败的是无关的既有用例 `test_discipline_appeal`（见 §6），**新增的 2 个回归测试均 PASSED**，`test_mb1_leave_my_sees_own`/`test_mb2_student_isolation` 等既有用例全部保持 PASSED，确认无回归。
  - 真实点击复测（sandbox-school/student2）：因该账号历史遗留多条真实待审请假，重复提交被 `409 DATA_CONFLICT`（"该生存在时间重叠的在途请假，不可重复提交"）正确拦截，顺带验证了重复提交防护有效；未追加新记录，直接用既有真实数据验证读取端点行为符合预期。

## 6. 未修复问题与原因

### #6【P1，未修复】学工看板"待审请假"计数遗漏老链路记录

- **现象**：sandbox-school/teacher2（辅导员视角）「学工看板」显示"待审请假 0 件"，但该角色数据范围内的学生（如 student2）在消息中心能看到多条"请假待审批"通知，说明实际存在待处理请假。
- **根因**：`backend/app/services/affairs_dashboard_service.py#get_dashboard()` 的 `pending_leave` 统计只按 `CsLeave.student_id.in_(_students_in_classes(...))` + `affairs_status.in_([COUNSELOR_REVIEW,...])` 查询，是 #5 同一个双状态列分裂问题在**教师端聚合计数**上的第三处症状——只统计走 13A 新链路的记录，遗漏走旧 `campus_service_apply` 链路（`cs_student_id`）的记录。
- **未修复原因**：这里涉及按班级/学院的数据范围裁剪（`_allowed_class_ids`/`ctx.allowed_class_ids`），要补齐旧链路分支需要同时按范围内学生解析对应的 `CsServiceStudent` 集合、换算旧状态词表（`status` 而非 `affairs_status`）、并避免重复计数，属于数据范围安全敏感代码。会话时间预算不足以在有把握不引入范围泄漏的前提下完成并回归验证，**判断为"宁可不动、明确报告"优于"仓促改出新的越权口子"**，故只定位未修复。

### #14【P1】培养方案提交审核短路校验（已修复）

- **复现步骤**：sandbox-school/admin2 → 培养方案 → 新建方案（不设总学分）→ 提交审核 → 请求 200 成功，
  方案进入 `COLLEGE_REVIEW`，随后两次"审核通过"一路推进到 `PUBLISHED`——一个 0 门课程、从未设置
  毕业总学分的空方案，走完整个审批链变成了正式发布、可被绑定年级、约束真实学生毕业资格的生效方案。
- **根因**：`academic_affairs_program_service.py#submit_program()` 原代码
  `if p.total_credits and csum < float(p.total_credits): raise ...` 用 `and` 短路，`total_credits`
  为 `None`（未设置）时整段学分达标校验被跳过，等价于"没配置总学分 = 自动视为达标"。
- **修复**：拆分成两条独立判断——`total_credits` 未设置直接拒绝（"毕业总学分尚未设置，不可提交"），
  再检查课程学分合计是否达标，两条校验都不可再被绕过。
- **测试结果**：真实点击复测（sandbox-school/admin2）：不设总学分的新方案提交返回 400
  `毕业总学分尚未设置，不可提交`。同步修复了依赖旧 bug 行为发布测试方案的既有测试辅助函数
  `test_aa_program_tier1_r3.py#_publish()`（改为真实设置总学分+补等额学分课程后再提交），并新增
  回归测试 `test_submit_rejects_when_total_credits_unset_or_course_sum_short`。真实 MySQL 测试库
  执行 `pytest tests/test_aa_program_tier1_r3.py`：**7 passed**（含新增用例）。测试过程中不慎把
  开发库里的真实方案 id=1 推进到 `COLLEGE_REVIEW`，已用精确 `UPDATE t_aa_program SET status='DRAFT'
  WHERE id=1 AND tenant_id=...` 复原并核实。

### #15【P1，核心链路阻断】教学任务批次生成对"留空"绑定失效（已修复）

- **复现步骤**：培养方案发布并"绑定年级"（`AaProgramConsoleView.vue` 的"方案发布"页，"行政班ID"字段
  明确标注"选填，留空=全专业该年级"，不填直接绑）→ 教学任务 → 生成任务批次 → `tasksGenerated: 0`，
  批次明细页显示"本批次暂无教学任务"，全程无任何报错或提示——这是教学任务模块的核心生成入口，
  一旦命中就 100% 失效。
- **根因**：`academic_affairs_task_service.py#generate_batch()` 原查询条件
  `AaProgramBinding.class_id.is_not(None)` 直接把 `class_id` 为空的绑定整条排除在外。而
  `bind_grade()` 服务层本身完全支持 `class_id=None`（"全专业该年级"），前端文案也明确承诺这个用法，
  但生成逻辑完全没有处理这个分支——凡是按文案指引"留空"绑定的方案，教学任务永远生成不出来；
  更严重的是，"深编辑器"（`/admin/academic-affairs/programs/:id`，日常主操作入口）的"绑定年级"
  表单干脆没有行政班字段，走这条主路径的方案 **100% 必然触发这个 bug，没有例外**。
- **修复**：`generate_batch()` 改为 `class_id` 为空时按 `(major_id, grade_year)` 展开该年级全部

  显示接近 0。同一份代码库里 `academic_affairs_quality_service.py` 的同名指标口径
  （`status.in_(["PUBLISHED", "ENABLED"])`）才是正确的。
