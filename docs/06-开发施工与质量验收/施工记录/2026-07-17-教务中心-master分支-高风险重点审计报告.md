             page: int = 1, pageSize: int = 20, user=Depends(require_staff)):

### P0-3 选课"退课"存在真实并发竞态——可导致选课人数突破课程容量上限【已本人核验代码逻辑,竞态本身未做并发压测复现】

- Service:`academic_affairs_selection_service.py:629-664`(`student_drop`)、`683-707`(`adjust_record`)。
  ```python
  rec = db.query(AaSelectionRecord).filter(...).first()          # 纯读,不加锁
  if not rec or rec.status != _REC_SELECTED:
      raise _invalid("无可退课的选课记录")
  ...

  db.query(AaSelectionCourse).filter(
      AaSelectionCourse.id == c.id, ..., AaSelectionCourse.selected_count > 0).update(
      {AaSelectionCourse.selected_count: AaSelectionCourse.selected_count - 1}, ...)
  ```
- 失败场景:同一条选课记录被并发发起两次"退课"(双击、弱网重试、多标签页)。两个事务都在对方提交前读到 `status==SELECTED`,check 都通过,随后各自对 `selected_count` 发起"`>0` 才减 1"的原子更新——第二个事务提交时该条件仍然满足,会再减一次。结果:一次真实退课,`selected_count` 被减了两次,课程"剩余名额"被虚增,后续学生选课会因容量数字失真而被放行,真实选中人数突破 `capacity` 上限。
- 对照:同文件 `student_enroll`(594-602行)用"条件更新+返回行数判断"的正确写法防超卖;`student_drop`/`adjust_record` 却用"先查对象、判状态、再各自发两条独立语句"的错误写法,是同一文件内部两套不一致的实现。
- 建议方案:把 `student_drop`/`adjust_record` 的状态迁移改成和 `student_enroll` 一致的条件更新写法(`UPDATE ... WHERE status='SELECTED'` 返回行数判断是否真正生效),或显式加行锁。

### P0-5 补考/清考通过后,毕业资格审核与学业预警仍按未去重的历史挂科行误判——已补考通过的学生仍会被判定"未达标"【已本人核验】

- 根因:`t_acad_grade` 表"挂科"判定全模块没有统一口径。
- 正确的一处(有 dedup):`academic_affairs_grade_service.py:516-549` `_refresh_aggregates` 按 `course_name` 取最高分去重后统计 `failed_count`/学分/绩点。
- 错误的一处(核验通过):`academic_affairs_graduation_service.py:91-106` `_check_course_required`:
  ```python
  rows = db.scalars(select(AcademicGrade).where(
      ..., AcademicGrade.nature == "REQUIRED", AcademicGrade.record_status == "ACTIVE", ...)).all()
  failed = [r.course_name for r in rows if r.pass_status == "FAILED"]
  ok = not failed
  ```
  直接扫该生该必修课**全部历史行**(含 PUBLISH + MAKEUP + CLEARANCE),只要其中任意一行是 FAILED 就判定该课未通过——完全不管后面是否已有补考行覆盖。`academic_affairs_warning_service.py:264-269` 的 `scan_warnings` 同样按 `pass_status=='FAILED'` 直接 group by 计数,不做去重。
- 根源:`academic_affairs_makeup_service.py:274-288` `finish_makeup_batch` 补考通过后只新增一条 `source=MAKEUP` 的 PASSED 行,**从不把原 `source=PUBLISH` 的 FAILED 行标记为非 ACTIVE 或做任何清理**。这个行为对"有 dedup"的台账刷新无害,对"无 dedup"的毕业审核和预警扫描是致命的。
- 具体场景(是常规流程,不是边界情况):学生 S"高等数学"正常考试 45 分(FAILED),补考 65 分通过,新建 `MAKEUP` 行 PASSED。`_refresh_aggregates` 正确把 GPA/学分/`failed_count` 刷新为合格。但毕业预审 `precheck()` 依然读到原 PUBLISH 行 FAILED,判定 `COURSE_REQUIRED` 为 FAIL——**S 已经真实通过、学分已入账的课程,毕业预审仍判定"存在未达标条件"**;`scan_warnings` 也会持续为 S 生成/重开挂科预警。`fail_list`(grade_service.py:895-914)和教务统计的"挂科率"同样长期虚高。
- 建议方案:抽出 `_refresh_aggregates` 里"按 course_name 取最高分去重"的逻辑为公共函数,让 `scan_warnings`、`_check_course_required`、`fail_list`、`stats_service._i_fail_rate` 统一调用,而不是各自直接扫原始行。

### P0-6/P0-7 自动排课/自动排考引擎对"人工排的课/人工建的考场"完全失明——会真实撞车【已本人核验代码逻辑,未做运行时复现】

- 根因:`AaScheduleItem.classroom_id`、`AaExamRoom.classroom_id` 字段设计上应该在有具体教室字典关联时才填,但**人工/导入通道从未填过这个字段**——`schedule_service.py` 的 `add_item`/`import_items`/`adjust_item`/`move_item`,以及 `academic_affairs_exam_service.py:277-296` 的 `add_room`,都只写 `classroom_text`(纯文本),对应请求体 `ScheduleItemBody`/`ExamRoomBody` 压根没有 `classroomId` 字段。
- 自动排课引擎的教室占用索引 `autoschedule_service.py:183-191` `_Grid.occupy`:`if rid: self._put(self.room, (int(rid), wd, sl), ...)`——`rid` 就是 `classroom_id`,人工排的课恒为 `None`,**这些课的教室占用根本不会被记进占用索引**。
- 自动排考引擎更直接:`autoexam_service.py:140-152` 构建占用索引时**显式** `AaExamRoom.classroom_id.isnot(None)` 过滤,把所有人工建的考场直接排除。
- 具体场景:教务员手工给 A 课程排了"周一第1节·教学楼A101"(`classroom_id=None`)。对同批次跑自动排课,某任务候选教室池选中 A101,索引里查不到这条人工记录的占用,判定"教室空闲",于是把另一个班的课也排进周一第1节的 A101——同一间教室同一时间被两个班占用,系统不报冲突,直到学生/教师到场才发现撞车。考试场景同理,人工建的考场会被自动排考引擎当作空闲考场再次分配,导致撞考场。
- 测试覆盖也证实了这个盲区:`test_aa_autoschedule.py`/`test_aa_autoexam.py` 里凡涉及"避让人工记录"的用例,给的人工记录都没有设 `classroom_id`/`classroomText` 对应的教室维度,所以测试通过不代表这条链路真的安全。
- 建议方案:人工/导入通道在保存时应尝试按 `classroom_text` 反查教室字典并回填 `classroom_id`(找不到字典项则保持 `None` 并在 UI 提示"该教室未登记字典,自动排课无法感知冲突");或者自动引擎的占用索引改为同时按 `classroom_text` 做兜底匹配。

### P0-8 教师异议改排(`adjust_item`)不会把来源标记转回 MANUAL——下次自动清空重排会把教务员刚改好的结果一并删除【已本人核验,与 move_item 对照确认】

- `move_item`(`schedule_service.py:760-789`)有保护:
  ```python
  if getattr(it, "source", None) == "AUTO":
      it.source = "MANUAL"
  ```
- `adjust_item`(`schedule_service.py:392-419`)**没有这一行**——本人已逐字核对,确认该函数体内自始至终未触碰 `it.source`。
- 具体场景:某课是自动排课引擎排的(`source=AUTO`)。教师对该条目提异议,学院教务员通过"定点改排"(`adjust_item`)把它挪到新空档——这是官方的"人工介入修正自动结果"流程,教务员的这次改排是实打实的人工劳动成果。但由于 `source` 仍是 `AUTO`,下一次教务处对该批次调用"清空重排"(`WHERE source=='AUTO'`)时,**会把这条教务员刚改好的记录当成自动排课残留一并删除**——直接违反了模块反复强调、且在 `move_item` 里已经正确实现的"只清 AUTO 不动人工"红线。
- 建议方案:在 `adjust_item` 里补上和 `move_item` 完全一致的 `if it.source == "AUTO": it.source = "MANUAL"`。

## 三、P2 / 观察项(非阻断,建议记账)

- `register_student` 并发重复注册有 DB 唯一约束兜底,不会产生脏数据,但未捕获 `IntegrityError`,极端并发下用户可能看到未处理的 500。

## 四、Alembic 迁移链分叉(阻断性技术欠账)

**结论:master 分支的 Alembic 迁移历史存在两个互不连通的 head,对全新库或已到 0098 的库执行 `alembic upgrade head` 都会直接报 `CommandError: Multiple head revisions are present`,不会随机套用某条链或静默成功,必须显式指定两个具体 revision 或先补一张真正的 merge migration。**

- head① (数字链):`0098_aa_workload_declaration`(down_revision=`0097_aa_eval_multisource`)
- head② (命名链):`aa_correction_material_r3`(down_revision=`aa_resources_r3`)
- 精确分叉点:`aa_jxrw_tier1_r1` 被两个不同文件同时声明为 down_revision——`0084_user_preference.py:16` 和 `aa_orgs_tier1_r2.py:18`。这是全仓库 114 个迁移文件里唯一一个被两个子节点同时指向的 revision(逐文件解析 revision/down_revision 交叉验证,非猜测)。

- 全仓库搜索 `down_revision = (` (元组写法,合并迁移的标志)**零命中**——不是合并迁移写错了,是压根没人写过合并迁移。
