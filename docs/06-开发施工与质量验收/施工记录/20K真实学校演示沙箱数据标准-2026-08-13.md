# 20K 真实学校演示沙箱数据标准（2026-08-13）

> 适用租户：`sandbox-school`（tenant_id=`1000000000000000007`）  
> 用途：售前演示、培训、真实数据量功能巡检、20K 学校容量基线数据。  
> 禁止用途：复制真实学校/真实个人信息；把本沙箱结果直接当生产容量认证。  
> 时间真值：2026-08-13。

## 1. 本次治理为什么必须做

历史 `sandbox-school` 的目标是开发期快速验页：约 100 名学生，再由 `_seed_sandbox_coverage.py` 根据 ORM 状态自动补 `DEMO-xxx`、`演示数据-xxx` 和 marker 关系 ID。它能帮助开发发现空页面，但不符合正式售前演示的业务真实性要求。

本次治理把两类数据彻底分开：

- **开发覆盖数据**：只有显式 `allow_generic=True` 才允许生成；不得进入正式售前沙箱。
- **售前标准学校数据**：所有主数据、业务事实、状态、时间、外键与统计数字都必须能由真实学校场景解释，并由事实表对账。

## 3. 数据隐私与虚构规则

1. 学校名称、人员、企业、手机号、家庭经济与业务文本全部是**确定性虚构数据**。
2. 不从任何真实学校或真实个人复制花名册、身份证、手机号、收入等信息。
3. 手机、家庭收入/负债等强敏感字段继续使用现有 `field_crypto` 加密路径；需要检索的字段同时使用 HMAC hash。
4. 不允许为了演示把 `*_encrypted` 字段回退成明文。
5. 不允许用不存在的 9 亿段 marker ID 假装关联关系；所有业务父子关系必须指向本租户真实主键。

## 7. 就业数据遵守当前时间真值，不制造“漂亮就业率”

当前 20,000 人是 2024/2025/2026 在校生，其中 2024 级刚进入三年级与岗位实习阶段。此时间点如果直接制造“95% 已就业、已毕业”会与学生生命周期冲突。

因此就业域只覆盖 2024 级 6,400 人，并复用实习域同一批 80 家企业、160 个专业岗位和 StudentProfile，不建立第二套企业/学生真值。当前确定性分布为：

- SIGNED：768（12.0%，订单班/提前录用/实习转录用）
- FURTHER_STUDY：128（2.0%）
- FLEXIBLE：64（1.0%）
- ENLISTED：32（0.5%）
- STARTUP：32（0.5%）
- FREELANCE：32（0.5%）
- UNEMPLOYED：5,344（83.5%）

这里的 `UNEMPLOYED` 表示**毕业前仍处于求职准备/岗位匹配阶段**，不是“毕业后失业率”。同时生成 6,400 份就业材料、合理比例的跟进/重点帮扶与待办；已签约学生中只有符合当前事实的一部分来自实习转录用。

若销售必须展示完整毕业后就业结果，应单独增加**历史已毕业届**数据包，并与当前 20,000 在校生规模分开统计，不能污染本届时间真值。

## 8. 全量重建与现场恢复必须分开

### 8.1 全量 20K 重建

这是几十万行数据写入操作，只允许用于：

- 首次部署演示环境
- 数据结构升级后重新建站
- 明确的运维维护窗口

命令：

```bash
cd backend
python scripts/reset_sandbox_school.py --dry-run --profile standard-20k
python scripts/reset_sandbox_school.py --confirm --profile standard-20k
python scripts/check_sandbox_20k_school.py
```

正式验收必须使用 MySQL。

**禁止把全量 20K 重建作为每晚自动任务或普通 HTTP 同步请求。** 20K 加密、成绩、考务、宿舍等事实写入会占用明显 CPU/DB 时间，放进 Web 请求容易触发代理超时或中途失败。

### 8.2 售前现场恢复

平台历史 `reset-sandbox-data` URL 保持兼容，但已按沙箱档位分流：

- legacy-100 继续调用旧 `reset_sandbox()`，保留开发 fixture 兼容；
- standard-20k 不执行几十万行全量重灌，只恢复李体验（迎新）、陈思雨（学生事务）、周启航（岗位实习）三条轻量销售故事线；
- 20K 背景学生、组织、账号、成绩、课表、宿舍、历史事实全部保留；
- 路由与轻量恢复语义由 `backend/tests/test_sandbox_story_reset_route.py` 锁定。

因此现场演示可以快速恢复可写故事，不把全量建站操作塞进普通 HTTP 请求。

## 10. 这份数据能证明什么、不能证明什么

能证明：

- 页面和 API 面对单校 20K 数据量时是否仍使用真实分页、数据范围、索引和聚合；
- 销售演示时学校规模、组织、时间、状态、统计是否像一所真实职业院校；
- 多域之间是否容易出现主键错挂、状态冲突、统计漂移；
- 全量重建在真实 MySQL 空库上可以完成并通过跨域关系、资源预算与旁租户保护验收。

不能直接证明：

- 300/500/1000 并发一定满足 SLA；
- 大文件、大导入导出、登录洪峰一定可承载；
- 多校 10 万/20 万用户已经通过容量认证。

容量认证仍须在本标准数据集上另外执行 k6/真实写链压测，并把 p95/p99、DB pool、慢 SQL、Redis、CPU/内存作为硬门禁。
