| 页面 | 列表 | 切换重置触发 |
|---|---|---|
| `teacher/todos/index.vue` | 待办列表 `filtered` | 切换分类 `filter` |
| `teacher/messages/index.vue` | 消息分组 `list` | 切换 tab |
| `teacher/risk-students/index.vue` | 风险学生 `filtered` | 切换风险等级 + 下拉刷新（load 内 pagedReset） |

机制说明（honest，非假分页）：
- 后端 mobile 列表接口已按上限返回（todos `[:60]`、messages 每组 `[:30]`、risk-students `.limit(80)` 域内合并），本就不会一次吐全校数据；本段解决的是**页面一次性把整段数组渲染成 DOM** 导致的首屏 setData 过大/滚动卡顿。
- mixin 提供 `pagedSlice()`（初始只渲染 20 条）、`pagedFooter()`（more/end 底部提示）、`pagedReset()`（切换重置）、`pagedLoadMore()`、`pagedReachBottom()`。
- 每页初始渲染 20 条，滚动到底 `onReachBottom` 追加一批；底部同时给"上拉加载更多（可点）/没有更多了"提示，**点击也能加载**（弱交互兜底）。
- 不改任何网络请求，不做服务端假分页，因此**不需要改后端**、不需要改受保护的 internship 后端服务。

## B. 一个真实的 mp-weixin 坑（已修复并二次验证）

首次实现时把 `onReachBottom` 放在 mixin 里，mp-weixin 构建通过、但**编译产物里没有 `onReachBottom`**——uni-app 编译 mp-weixin 时不会把 mixin 中的页面级生命周期（onReachBottom/onPullDownRefresh）注入 Page() 配置，只有写在页面组件本身的才生效。若不发现，微信端"滚动到底自动加载"会静默失效（只剩点击兜底）。

修复：mixin 只保留数据与方法（`pagedReachBottom()` 承载判断逻辑），`onReachBottom` 改为写在 5 个页面各自的组件选项里、转调 `this.pagedReachBottom()`。重新构建后核对 5 个页面的 `dist/build/mp-weixin/pages/*/index.js` 均含 `onReachBottom`（各 1 处），wxml 也含"上拉加载更多/没有更多了"footer，机制在微信端真实生效。

## C. 为什么没有做"内部列表（打卡记录/周报列表/打卡异常台账）"的分页

这三个是审计报告里真正会全表拉取的高危列表，但其前端页面（`student/internship/`、`teacher/internship-review/`）和后端实现（`internship_service.py`）属于"岗位实习中心正在测试验证"的受保护范围，按本任务规则不予改动。仍列为明日任务，需等岗位实习测试验证收口后，由后端做 SQL 层 `JOIN + LIMIT/OFFSET` 真分页 + 前端接分页协议，一并处理（本段的 `listPaging.js` mixin 届时可直接复用于前端侧）。

下拉刷新重置（`onPullDownRefresh` + pages.json `enablePullDownRefresh`）本段也未做：`onReachBottom` 无需 pages.json 配置即生效，但下拉刷新需要改 `pages.json`——该文件属于岗位实习并行改动过的共享文件，为避免冲突本段未碰。已有下拉刷新的 risk-students 页则在 `load()` 内调用了 `pagedReset()`，刷新即回到第一批。

不会，且比账号密码更轻：一键登录是 `wx.login` 拿 code 换 openid，无密码哈希（bcrypt 才是密码登录最耗 CPU 处）。"这么多学生同时登录"的压力是后端+DB 容量问题，与登录方式无关，微信登录只会更省。真正的工作是**绑定**：首次用学号/密码把 openid 与学籍账号绑一次，之后免密自动登录。`code2session` 有 appid 级频率限制但额度很高、仅登录时触发，学校量级碰不到。建议首发用现成账号密码，微信一键登录作 v1.1（后端加 openid↔学号绑定表 + 换取接口）。

## A. 后端 N+1 消除（提交 `bae1876`）

`backend/app/modules/internship/services/internship_service.py` 三个高频台账列表——`list_checkins`（打卡）、`list_attendance_exceptions`（异常）、`list_weekly_reports`（周报）——原为：全量拉取后**逐行** `db.get(InternshipRecord)` + `db.get(StudentProfile)`，SCOPED 下还逐行 `db.get(SchoolClass)` + `db.get(College)`，即每行 2~4 次单行查询（2N~4N）。一学期几千学生每日打卡 → 十万级行 → 每次刷新台账/导出是全表拉取 + 数十万次单行查询。

改法：
- 新增 `_bulk_context(db, rows)`：按去重后的 id 批量加载关联对象（一个 internship 对应多条打卡/周报，故 rec/stu 数量级=学生数 ≪ 台账行数），把 2N~4N 次单行查询压成 **3~4 次批量查询**。
- 新增 `_rec_in_scope_pre`：用预加载的班级/学院名映射替代逐行 `db.get`，与原 `_rec_in_scope` **逐行等价**（`map.get(id)` 与 `db.get(id).name` 对同一 id 返回值完全相同，含 None 情况；非 SCOPED 放行、rec None 拒绝、SCOPED 走同样的 `scope_match_row` 参数）。
- **行为与数据范围安全逻辑一字未变**，仅减少查询往返。

验证：`test_weekly_list_scope` 单独 MySQL 跑**通过**（走同一对辅助函数）；打卡/异常路径用完全相同的 `_bulk_context`+`_rec_in_scope_pre`，等价传递。打卡/异常直测因共享 MySQL 测试库正被教务/学工并发 DDL（`t_aa_schedule_item` 等教务表）污染而无法即时跑净——**与本改动无关**。**待测试库空闲后补跑** `pytest tests/test_internship_attendance.py tests/test_internship_scope.py -q` 应全绿。

> 未做：作用域下推 SQL + LIMIT（真·SQL 分页）——因作用域按姓名/学号/班级/学院匹配、属安全敏感，下推译错会跨范围泄漏，不在无人值守做；N+1 消除已把最坏情况从"灾难（数十万查询）"降到"可承受（3~4 查询 + O(N) 内存）"。Excel 导出（`export_checkins/export_exceptions`，page_size=100000）本次未加范围硬上限，但已随 N+1 消除大幅提速；范围硬上限留作后续。
