## 3. 关键实现决策（含"不照文档做"的地方）

**3.1 C5 不逐行调用 `_allowed_risk_actions`。**
V5 总册要求列表 `allowedActions` 必须复用 `_allowed_risk_actions`。直接逐行调用会
N+1：`build_affairs_context` 与 `has_permission` 对 `role_type=CUSTOM` 的角色都会
走 `_db_granted` 另开一个 DB 会话读 `t_role_permission`。
改为 `_risk_action_evaluator(user)` 把与记录无关的身份事实解析一次，返回逐行纯函数；
`_allowed_risk_actions` 变成它的单条包装。规则仍是同一份 `RISK_TRANSITIONS`，
列表与详情不可能各算一套（已有合同用例逐条比对两者相等）。

**3.2 `_row` 只在显式给出时才带 `allowedActions`。**
`_row` 有 9 处写服务返回路径。若默认下发空数组，写响应会出现
`allowedActions: []`（语义上等于"什么都不能做"，是错的）。已核实 PC
`runAction` 与教师小程序 `processRisk` 都丢弃写响应体直接重新 load，
无消费方。因此采用最保守方案：写响应保持原样不带该字段，列表/详情显式传入。
这同时让既有守卫 `test_affairs_round3_risk_contract.py` 的源码文本断言
（要求出现 `row["allowedActions"]`）**原样通过，未修改任何既有测试**。

**3.3 C3 summary 与列表共用同一份 `conds`。**
没有新建第二套 scope 算法。`_teacher_requirement_scope` 是列表、COUNT 和聚合的
单一条件来源；`material_overview` 单会话内完成列表与聚合。
敏感级别过滤命中既有索引 `ix_affairs_material_requirement_sensitivity(tenant_id, sensitivity_level, status)`。

## 9. 第二批收尾：C8 与复审发现的两个真问题

### C8 材料登记去手工 bizId/itemCode（`ca833ffae`）

按总册第 49 节优先做 A 路径。后端两个只读入口：`biz-context`（按 bizType+bizId
解析业务与学生，授权链与登记材料完全一致，越权按"不存在"）、`item-suggestions`
（本校**已真实用过**的材料项，按使用次数排序）。

**刻意不引入"标准材料项目录"**：学工域没有这张表，标准材料项属于学校自己的业务
政策，系统不能编造。没用过的业务域返回空，并有合同断言锁住这一点。

前端：材料中心接受 `?bizType=&bizId=` 深链，解析成功后只读展示业务与学生、
隐藏手填 ID，保留"改为手工指定"退路；材料项编码接 datalist 建议；
困难认定详情新增"要求补材料"。写链、itemCode 正则、敏感度分级、乐观锁一个没放宽。

### P0-1：材料事件码从未注册，登记材料缺项在生产上完全不可用（`6029ffb44`）

做 C8 时发现：登记材料缺项恒返回
`422 / VALIDATION_ERROR / 未登记的消息事件码：MATERIAL.REQUIRED`。

根因不是缺模板定义，而是**注册代码从来没被执行**：
`affairs_operations_service._register_message_templates()` 只被同文件的
`install()` 调用，而 `install()` **全仓没有任何调用方**。于是 MATERIAL.* 五个
事件码从未进入 `message_event_outbox_service._EVENT_TEMPLATES`。

已在 clean `origin/main`（post-PR100 `d57774c67`）用真实 API 调用复现确认，
非本轮引入。修法取最小：把 5 个事件码按原定义登记进权威模板表
（`communication_registry` 的注释明确"真实来源永远是 `_EVENT_TEMPLATES`"），
不去触发 `install()`——它还会 monkey-patch 学生合同与宿舍风险投影，爆炸半径过大。
新增 AST 守卫：材料服务实际 emit 的所有 `MATERIAL.*` 必须已登记。

### P0-2：PR100 的会话竞态守卫在 Windows 本地静默失效（`82de2f43b`）

`auth-session-race-contract.test.mjs`（2 条）与
`student-portal-auth-session-race-contract.test.mjs`（1 条）用结构性正则匹配
`client.js` / `request.js` 源码，正则按 LF 书写；而本仓 `core.autocrlf=true`
且无 `.gitattributes`，Windows 检出得到 CRLF，`\n}\n\nexport async function`
永远匹配不上。Linux CI 是 LF 所以 PR100 合并时是绿的。

后果不是误报，而是**这些安全守卫对本仓唯一的开发环境不起作用**。
修法：读源码时把 CRLF 归一成 LF，只统一换行，不放宽任何断言。
被守卫的两个源文件与 `origin/main` 逐字节一致。

### 复审自查发现并修复：材料项建议未过数据范围（`5b686febc`）

`list_item_suggestions` 只做了 `_require_biz_permission`，没有应用数据范围，
跨全租户聚合 `item_code / item_name / usedCount`。只管一个班的辅导员能看到
全校用过的材料项及使用次数——跨范围聚合信息泄露。总册 §36 要求"候选"类
接口同样要过 dataScope。已改为复用 `_teacher_requirement_scope`，
并新增 `test_item_suggestions_respect_data_scope`，在独立 MySQL 上做过红→绿闭环。
