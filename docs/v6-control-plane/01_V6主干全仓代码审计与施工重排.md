## 1. 审计结论

当前仓库不是“只有页面原型的空系统”，而是一个已经拥有大量真实模型、路由、状态机、四端入口和公共文件底座的复杂单体应用。V6 最大风险不是功能缺失，而是以下五类**权威源不唯一**：

1. 租户状态：`t_tenant.status` 与 `TENANT_META.status/expireAt/readonly` 双源。
2. 权限：内置角色代码基线、自定义角色数据库权限、临时授权 JSON 文档三轨叠加。
3. 数据范围：结构化 `DataScopeRule`、角色 remark 回落和业务域关系解析并存。
4. 配置：环境变量、`PlatformConfig`、`SysConfig`、`SystemJsonDoc` 与代码默认值多级回退。
5. 菜单与能力：真实路由、能力目录、navPlan 和 `PlatformCapabilityView` 承载页不能等同于真实完成度。

因此成功率最高的施工原则是：**先收口权威解析器和安全边界，再建设工作区；先完成可回滚的写侧，再建设总览与运营聚合。**

## 2. 审计覆盖与边界

本轮覆盖：

- 仓库规则、模块清单与三个前端工程；
- FastAPI 启动、路由聚合、补充路由和安装守卫；
- SQLAlchemy/Alembic/MySQL/Redis 配置；
- 认证、租户登录门禁、权限、范围和前端 permissionGate；
- 系统管理、平台运营、文件、数据交换；
- 组织、学期/校历、实施、流程、待办、消息、Outbox、审计；
- 模型聚合、pytest 公共夹具和代表性 GitHub Actions。

本轮没有虚假宣称“逐行人工审查了每一个业务模块的全部代码”。对于学工、教务、实习、毕设等业务域，审计重点是它们与 V6 控制面的共享路由、权限、范围、文件、消息和任务依赖。

## 3. 架构事实

### 3.1 路由层

- 后端不是简单的一个 router：存在主聚合、补充路由、兼容路由和启动时 `install_*` 守卫。
- 教务路由存在临时重排/恢复操作，学工路由大量依赖安装顺序。
- 控制面卡只能修改白名单内路由，禁止顺手重构业务域注册结构。

### 3.2 数据与迁移

- 当前静态顶部 revision 为 `0154_file_storage_quota_reservation`。
- PR #25 有单一 head 和 MySQL 8 空库升级历史证据，但当前 `main` merge commit 没有可直接读取的绿灯状态。
- 所有迁移卡开工必须重新执行 `alembic heads` 和空库升级；禁止预写 `0155`。
- `models/__init__.py` 是高冲突聚合文件，所有新增模型卡必须独占预约。

### 3.3 认证、权限与范围

- 真实账号以 `UserRole -> Role` 为来源，未分配角色默认拒绝；保留少量明确演示账号兼容。
- 内置角色仍主要读取代码 `ROLE_PERMISSIONS`；自定义角色才完整读取 `t_role_permission`。
- `SCHOOL_ADMIN` 仍有 `*`，`SYS_ADMIN` 仍有 `systemAdmin.*`。
- `mock_rbac_service.py` 仍承担真实 current-context 投影，同时保留旧静态菜单/按钮和重复数据范围目录。
- 范围 provider 的毕设/实习路径存在 `limit(500)` 后 Python 遍历，不能支撑真实规模。

### 3.4 租户与商业控制

- 租户状态字段语义不一致：模型状态与 TENANT_META 的 trial/expired/readonly 不同。
- 缺少 TENANT_META 或读取异常时，多处代码默认 active。
- 租户列表存在全量读取、逐租户多次 count 和 Python 过滤的 N+1。
- `usedStorageMb` 仍可能从租户元数据默认值读取，而不是 FileObject 权威聚合。
- 平台路由全部只允许 `PLATFORM_SUPER_ADMIN`，尚无职责分离。

### 3.5 学校系统管理

- 账号、角色、范围、菜单、配置、临时授权、实施项目和业务关系安装均已有真实表或服务。
- 问题不是“没有表”，而是代码基线、数据库和 JSON 文档的有效值没有统一版本/激活机制。
- SYS-02 已有项目、段配置、安装快照、检查、验收和回滚账本，应做增强而不是重建。

### 3.6 文件与数据交换

- ImportJob、ExportJob、ImportRowError、FileObject 和确认适配器都是真实底座。
- SYS-18 当前仍按操作者隐式过滤，列表存在 Python 全量合并分页，汇总由当前页计算。
- 后端支持 `Idempotency-Key`，学校端客户端没有发送。
- `systemAdmin.file.manage` 同时控制治理 API，并被内容访问服务视为文件管理员。
- SYS-18 → RBAC-09 → PLAT-02 → PLAT-15 → PLAT-03 → SYS-19 是第一条必须串行的主链。

### 3.7 流程、消息、任务与审计

- WorkflowDefinition/Node/Instance/Task、UnifiedTodo 已存在。
- UnifiedMessage、MessageCampaign、DeliveryJob、EventOutbox 已存在。
- SecurityAuditLog 为 append-only，并有 traceId 字段。
- SYS-14/15/16/21 应统一注册、策略、ServicePolicy、证据和解释，不能重复创建第二套公共表。

### 3.8 存储与灾备

- COS 精确 Key、STS、上传会话、完成核验、扫描和分区迁移已存在。
- 平台存储配置仍“保存即 `reset_backend`”，密钥加密根来自 JWT 密钥。
- PLAT-07 必须版本化、测试、批准、排期、激活、回滚；PLAT-12 必须做真实隔离恢复。
- 两者通过前不得展示“生产就绪”。

### 3.9 测试可信度

- 测试公共夹具有大量历史契约自动补齐，说明旧测试可能在运行前修补请求或测试数据。
- 新 V6 测试必须同时包含：直接服务测试、原始 API 请求测试、两租户测试、并发/版本测试和旧回归。
- 每张卡只跑与其相关的定向测试和必要关联回归，不做无目的的全库长跑。

## 6. 顺序解释

### 第一阶段：公共数据和跨租户安全

`SYS-18 → RBAC-09 → PLAT-02 → PLAT-15 → PLAT-03 → SYS-19`

先用边界清晰、无迁移优先的 SYS-18 验证施工机制；随后拆权限。租户有效状态和平台人员职责在商业、配额和文件治理前完成，避免继续扩张单超管和默认 active。

### 第二阶段：学校有效时间、组织和安全版本

`SYS-12 → SYS-04 → SYS-11 → SYS-06 → SYS-08 → SYS-09 → SYS-10`

学期/校历给组织未来版本、配置生效和冻结窗口提供时间轴；有效配置先于权限激活；角色、范围、激活、解释严格串行。

### 第三阶段：学校账号、关系和实施闭环

`SYS-13 → SYS-03 → SYS-05 → SYS-07 → SYS-02 → SYS-17`

模块四态先稳定，再处理账号；业务关系先登记，再自动生成有效期角色身份；最后使用现有实施底座完成新学校开局和验收。

### 第四阶段：学校横切公共服务

`SYS-14 → SYS-15 → SYS-16`

先收口流程动作安全，再统一消息事件，最后给文件、导入、消息和同步 worker 建立 ServicePolicy/JobRegistry。

### 第五阶段：平台交付和运行控制

`PLAT-08 → SYS-20 → PLAT-04 → PLAT-09 → PLAT-11 → SYS-21`

服务目录是影响计算基础；学校集成进入目录后，自动开通才可做完整健康验证；事件、变更和证据随后形成闭环。

### 第六阶段：存储、灾备和运营治理

`PLAT-07 → PLAT-12 → PLAT-06 → PLAT-10 → PLAT-13 → PLAT-14`

PLAT-07 代码先完成但保持不可激活，PLAT-12 完成真实恢复后再解锁外部 COS 验收。随后建设底座运行中心、Problem、计量公平使用和治理证据。

### 第七阶段：只读聚合与经营

`SYS-01 → PLAT-05 → PLAT-01`

总览永远最后。SYS-01 聚合学校权威服务，PLAT-05 在此基础上计算客户健康，PLAT-01 最后聚合经营、成功和运行，不建第二套统计器。
